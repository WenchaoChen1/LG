### 1. LG-TEST-JAVA-Y — `financial_normalization` 数值溢出（91967 events）✅ 根因已确认

> ⚠️ **多数事件来自 environment=dev（开发者本地反复触发），不代表生产/测试真实流量**。但代码 bug 真实存在，跟 UAT-2Y 同源。

- **原标题**: `DataIntegrityViolationException` → `PSQLException: 数字字段溢出. 精度为50,范围是10的字段必须四舍五入到小于10^40的绝对值`
- **Sentry 链接**: https://lookingglass-3t.sentry.io/issues/LG-TEST-JAVA-Y
- **代码位置**: `FinancialNormalizedServiceImpl.processMessage` (SQS 消费入口 `SQSMessageListener.java:126` `onNormalizedQueue`)

**精确根因**（从 stack 拿到具体值）：
```
mrr_yoy_growth_rate = 2.1069849088239617e58   ← 远超 NUMERIC(50,10) 上限 1e40
sales_efficiency_ratio = 同样超限
mrr=724945.10, last_year_mrr_source = {"date":"2023-10-01","Mrr":10.0}
```

公司 `49013b5b-2a4a-4636-8cc4-6f1fab7cef2a`，月份 `2025-08-01`，environment=`dev`。

`lastYearMrr=10` 当分母时算出 `(724945.10 - 10) / 10 = 72494.5`，但实际入库值 `2.1e58` 说明计算公式不止简单除法（可能有 `^2 / e^x` 之类）。

**修改方案**（**与 UAT-2Y/1S 同源**，详见 [UAT 报告](./uat-java-2026-05-13-to-2026-05-20.md) #14/#15）：

```java
// 引入 FinancialMathUtils.safeRatio / clampToNumeric 通用工具
public static BigDecimal safeRatio(BigDecimal numerator, BigDecimal denominator) {
  if (denominator == null || denominator.abs().compareTo(MIN_DENOMINATOR) < 0) return null;
  BigDecimal result = numerator.divide(denominator, 10, RoundingMode.HALF_UP);
  return clampToNumeric50_10(result);
}

public static BigDecimal clampToNumeric50_10(BigDecimal v) {
  if (v == null) return null;
  if (v.abs().compareTo(MAX_NUMERIC_50_10) > 0) {
    log.warn("[math] numeric overflow, clamp: {}", v);
    return v.signum() > 0 ? MAX_NUMERIC_50_10 : MAX_NUMERIC_50_10.negate();
  }
  return v;
}
```

→ **一处工具类可同时消除 UAT-2Y / UAT-1S / TEST-Y / TEST-1C** 等多个同类 issue。
