### 3. LG-TEST-JAVA-7Y — 共享 `SimpleDateFormat` 并发损坏导致 500（1 event / 累计 37）✅ 根因已确认

- **原标题**：`Unhandled exception traceId=bad4c0a3-aab3-4664-93c5-987be5aaf267: java.lang.ArrayIndexOutOfBoundsException: Index 19 out of bounds for length 13`
- **Sentry 链接**：https://lookingglass-3t.sentry.io/issues/LG-TEST-JAVA-7Y
- **缺陷根源**：`CIOaas-api/gstdev-cioaas-common/src/main/java/com/gstdev/cioaas/common/utils/DateUtils.java:42`
- **抛出点**：`CIOaas-api/gstdev-cioaas-web/src/main/java/com/gstdev/cioaas/web/fi/service/FiDataCalculateServiceImpl.java:1013` `getEndOfRunwayByDate`
- **请求**：`GET https://admin-test.lgpi.io/web/financialEditing/dataset`，environment=`test`，server=`java-business-557f78c6c9-phhcc`，线程 `http-nio-5213-exec-12`
- **首见/末见**：2026-07-19 ~ 2026-09-08（偶发，累计 37 次 / 3 个用户）
- **调用链**：
  - `FinancialEditingController.java:135` `dataset`
  - `FinancialStatementServiceImpl.java:576` `financialEntryAndForecastData`
  - `FiDataCalculateServiceImpl.java:737` `buildFiDataList`
  - 抛点：`FiDataCalculateServiceImpl.java:1013` `getEndOfRunwayByDate` → `DateUtils.format4.format(...)`

**精确根因**：

```
at java.base/sun.util.calendar.BaseCalendar.getCalendarDateFromFixedDate(BaseCalendar.java:457)
at java.base/java.util.GregorianCalendar.computeFields(GregorianCalendar.java:2358)
at java.base/java.util.Calendar.setTimeInMillis(Calendar.java:1827)
at java.base/java.util.Calendar.setTime(Calendar.java:1793)
at java.base/java.text.SimpleDateFormat.format(SimpleDateFormat.java:978)
at com.gstdev.cioaas.web.fi.service.FiDataCalculateServiceImpl.getEndOfRunwayByDate(FiDataCalculateServiceImpl.java:1013)
```

异常发生在 JDK 内部 `BaseCalendar` 的月份查表处（长度 13 的月份累计天数表，被读到 index 19），
这是 **`SimpleDateFormat` 非线程安全**的教科书级特征：`SimpleDateFormat.format()` 会把入参写进
实例内部持有的那**一个** `Calendar`；两个 http 线程同时 format 时，一方刚 `setTime`、另一方就 `computeFields`，
`Calendar` 内部字段被写成互相矛盾的中间态，月份字段变成 19 这种越界值。

而 `DateUtils` 把 8 个 formatter 全声明成了**跨全应用共享的 public static 单例**：

```java
// DateUtils.java:16-57
public static final DateFormat format0 = new SimpleDateFormat("yyyy-MM-dd", Locale.ENGLISH);
...
public static final DateFormat format4 = new SimpleDateFormat("MMM yyyy", Locale.ENGLISH);   // ← 抛异常的这个
...
public static final DateFormat format7 = new SimpleDateFormat("yyyy-MM-dd HH:mm:ss", Locale.ENGLISH);
```

单 `format4` 在 `src/main` 就有 **14 处真实调用点**（跨 7 个文件：`FiDataCalculateServiceImpl` ×3、
`FinancialOverviewServiceImpl` ×4、`FinancialStatementServiceImpl` ×2、`QuickbooksHistoriesService` ×2、
`FinancialForecastDataMapper` / `FinanceManualDataServiceImpl` / `FinancialForecastHistoryServiceImpl` 各 1），
8 个 formatter 合计 24 处；其中多条在 `/web/financialEditing/dataset`、财务预测重算等并发路径上。
所以这不是 test 环境独有：**同一份代码在 uat / prod 一样是并发定时炸弹，被撞上的概率随 QPS 走**。
累计 37 次、影响 3 个用户、横跨近两个月的稀疏分布，正符合并发竞态特征。

**修改方案**：把 8 个共享 `DateFormat` 换成线程安全的形式，调用点从 `DateUtils.format4.format(x)` 收敛为 `DateUtils.format4(x)`：

```java
// CIOaas-api/gstdev-cioaas-common/src/main/java/com/gstdev/cioaas/common/utils/DateUtils.java

// 方案 A（最小侵入）：每次 format 走新实例——语义等价、无锁、无竞态
private static final String PATTERN_4 = "MMM yyyy";

public static String format4(Date date) {
  return date == null ? null : new SimpleDateFormat(PATTERN_4, Locale.ENGLISH).format(date);
}

// 方案 B（更彻底，推荐）：改用不可变的 DateTimeFormatter
public static final DateTimeFormatter FORMAT_4 =
    DateTimeFormatter.ofPattern("MMM yyyy", Locale.ENGLISH);

public static String format4(Date date) {
  if (date == null) return null;
  return FORMAT_4.format(date.toInstant().atZone(ZoneId.systemDefault()));
}
```

> ⚠️ **改造时注意时区**：现有 `SimpleDateFormat` 用 JVM 默认时区，方案 B 必须显式写
> `ZoneId.systemDefault()` 保持行为一致，否则 `MMM yyyy` 会在跨月边界上产生 off-by-one-month 的
> 财务月份错位——这类错位比现在这个 500 更难发现。改完需回归财务页月份列显示。

**兜底（若本周来不及做全量替换）**：先只给抛点包一层，止血 `/web/financialEditing/dataset` 的 500：

```java
// FiDataCalculateServiceImpl.java:1013
return new SimpleDateFormat("MMM yyyy", Locale.ENGLISH).format(calendar.getTime());
```

## 🟢 P2 - 配置 / 环境（非代码缺陷，属日志级别噪音）

### 2. LG-UAT-JAVA-1Q — UAT 邮件白名单拦截被当成 error 上报（11 events / 累计 114）✅ 根因已确认

- **原标题**：`Send email failed: Target user is not whitelisted for uat environment. Please contact developers for access.`
- **Sentry 链接**：https://lookingglass-3t.sentry.io/issues/LG-UAT-JAVA-1Q
- **代码位置**：`CIOaas-api/gstdev-cioaas-web/src/main/java/com/gstdev/cioaas/web/fi/service/FinancialForecastDataServiceImpl.java:2431` `sendNewForecastGeneratedEmail`
- **拒绝逻辑**：`CIOaas-api/gstdev-cioaas-web/src/main/java/com/gstdev/cioaas/web/system/service/EmailServiceImpl.java:111-122`
- **触发链路**：SQS `SQSMessageListener.onForecastQueue` → `buildForecastDataForCompanyById` → `sendAlertNotificationAndEmail` → `sendNewForecastGeneratedEmail`
- **首见/末见**：2026-04-21 ~ 2026-09-09（持续，累计 114 次）

**精确根因**：这**不是 bug，是设计内的行为**。`EmailServiceImpl.sendEmail` 在 stage/uat 环境下只放行白名单用户与 qq.com 邮箱：

```java
// EmailServiceImpl.java:111-122
if (environment.equals("stage") || environment.equals("uat")) {
  ...
  if (!(isWhiteList || isQQ)) {
    return Pair.of(false, MSG_NOT_WHITELISTED_PREFIX + environment + " environment. Please contact developers for access.");
  }
}
```

问题出在调用方对返回值的处理级别——`sendNewForecastGeneratedEmail` 一律打 `log.error`：

```java
// FinancialForecastDataServiceImpl.java:2429-2432
if (!sendResult.getFirst()){
  log.error("Send email failed: {}", sendResult.getSecond());
}
```

Sentry 的 logback appender 把 `error` 全量上报，于是「每个非白名单收件人 × 每次预测生成」= 一条 Sentry 事件。

**对照组**：新链路 `EmailSendSqsHandler.java:77` 已经识别了这个前缀并按「不可重试」单独处理——
`EmailServiceImpl.MSG_NOT_WHITELISTED_PREFIX` 这个常量就是为此存在的，只是旧的直调路径没跟上。

**修改方案**：复用已有常量，把白名单拒绝降级为 `warn`，真实发送故障仍走 `error`：

```java
// FinancialForecastDataServiceImpl.java:2429-2432
if (!sendResult.getFirst()) {
  String reason = StringUtils.defaultString(sendResult.getSecond());
  if (reason.startsWith(EmailServiceImpl.MSG_NOT_WHITELISTED_PREFIX)) {
    // 非 prod 环境白名单拦截：预期行为，不是故障，不该进 Sentry
    log.warn("Skip email (recipient not whitelisted): companyId={}", companyId);
  } else {
    log.error("Send email failed: {}", reason);
  }
}
```

> 📌 顺带排查：全仓还有哪些直调 `emailService.sendEmail` 后无脑 `log.error` 的地方，
> 一起套上同一个 `startsWith(MSG_NOT_WHITELISTED_PREFIX)` 判断，避免同类噪音再冒出来。
> 命令：`grep -rn "emailService.sendEmail(" CIOaas-api --include=*.java`

## 🟤 P3 - 三方组件噪音（观察即可）

### 1. LG-UAT-PYTHON-K — OpenTelemetry 自动埋点跨 Context detach 失败（14 events）✅ 根因已确认

- **原标题**：`ValueError: <Token var=<ContextVar name='current_context' default={} at 0x...> at 0x...> was created in a different Context`
- **Sentry 链接**：https://lookingglass-3t.sentry.io/issues/LG-UAT-PYTHON-K
- **代码位置**：**无业务代码帧**。栈全在 K8s sidecar 注入的 agent 目录里：
  - `/otel-auto-instrumentation-python/opentelemetry/context/__init__.py:155` `detach`
  - `/otel-auto-instrumentation-python/opentelemetry/context/contextvars_context.py:53` `detach` → `self._current_context.reset(token)`
- **上下文**：`handled: yes`、`mechanism: logging`、`logger: opentelemetry.context`、Users 0、CPython 3.12.14、`uvicorn main:app --port 8090`
- **首见/末见**：2026-08-22 ~ 2026-09-09

**精确根因**：OTel 用 `ContextVar` 保存当前 span context，`attach()` 拿 token、`detach()` 用 token `reset()`。
`ContextVar.reset()` 要求 token 必须在**同一个 `contextvars.Context`** 里创建。在 asyncio + uvicorn 下，
span 的 attach 与 detach 会落在不同 Task/线程（典型场景：`run_in_executor`、`asyncio.create_task`
派生的子 Context、以及跨 await 边界的中间件），token 就跨 Context 了，`reset()` 抛 `ValueError`。

OTel 内部把它 `try/except` 住并 `logger.exception("Failed to detach context")`——**异常已被处理，
不会中断任何请求**（Users=0、`handled: yes` 印证）。它之所以出现在 Sentry，只是因为 Sentry 的
`LoggingIntegration` 默认把 `logger.exception` 当 error 事件上报。

同期归档的 `LG-UAT-PYTHON-N`（span 批量导出到 `cloudwatch-agent.amazon-cloudwatch:4316` 读超时）
与本条同源——都是 uat 那套 otel auto-instrumentation sidecar 的自身健康问题，与 CIOaas-python 业务无关。

**修改方案**：Sentry 侧静音该 logger，不动 otel（三方 agent 由 K8s 注入，业务仓改不了）：

```python
# CIOaas-python/source/main.py:338 附近（sentry_sdk.init 之前）
from sentry_sdk.integrations.logging import ignore_logger

# otel auto-instrumentation 在 asyncio 下跨 Context detach 会抛 ValueError，
# 它自己已 try/except 兜住（handled=yes、不影响请求），仅因 logger.exception 被 Sentry 收走。
# 三方 agent 由 K8s sidecar 注入、业务仓改不了，故在上报侧静音。
ignore_logger("opentelemetry.context")
ignore_logger("opentelemetry.sdk.trace.export")   # 一并静音 LG-UAT-PYTHON-N 的导出超时

if _sentry_settings.enabled:
    sentry_sdk.init(
        dsn=_sentry_settings.dsn,
        ...
        before_send=_scrub_sensitive_headers,
    )
```

> 若希望保留可观测性而不是彻底静音，替代做法是在 `_scrub_sensitive_headers` 里按
> `event.get("logger")` 判断后 `return None`——但 `ignore_logger` 更直白，符合本仓 YAGNI 原则。
