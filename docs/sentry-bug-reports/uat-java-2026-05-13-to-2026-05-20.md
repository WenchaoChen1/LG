### 1. LG-UAT-JAVA-1H — EventBridge schedule cron 表达式无效（9818 events）

- **原标题**: `ValidationException: The schedule expression cron(47 01 17 02 ? 2026), with StartDate 2026-05-20T01:01:22.829 and EndDate 2031-05-19T01:01:22.829, is invalid because it will never schedule an invocation.`
- **Sentry 链接**: https://lookingglass-3t.sentry.io/issues/LG-UAT-JAVA-1H
- **代码位置**: `gstdev-cioaas-web/src/main/java/com/gstdev/cioaas/web/scheduler/service/SchedulerServiceImpl.java:40` `createSchedule(ScheduleRequestInput request)`

**根因**：
上游调用方（`BenchmarkEmailPlanner.scheduleFirstTick` / `FinancialForecastHistoryServiceImpl.createAutoFillScheduleTask` 等）生成 cron 时算出了**过去时刻**（如 `cron(47 01 17 02 ? 2026)` 即 2026-02-17 01:47）。AWS EventBridge 检查 cron 在 `[StartDate, EndDate]` 区间内至少要匹配一次，过期 cron 直接 400。**每次调度尝试都重复抛错**，单一公司一直在重试 → 9818 次。

**修改方案**（`SchedulerServiceImpl.createSchedule` 入口加防御）：

```java
public void createSchedule(ScheduleRequestInput request) {
  // 提前防御：trigger_time 必须在未来（留 60 秒 buffer 避免临界点抖动）
  Instant trigger = parseTriggerTime(request);
  if (trigger == null || trigger.isBefore(Instant.now().plusSeconds(60))) {
    log.warn("[scheduler] skip creating expired schedule: name={}, trigger={}",
        request.getName(), trigger);
    return;
  }
  // ... 原逻辑
}
```

同时回查上游：`createAutoFillScheduleTask` 用 `alert.getTriggerTime()` 生成 cron，确认 `triggerTime` 计算来源（应该是 `now + 10 天`，过期一般是因为 alert 是历史 row 但没被消费掉）。

### 3. LG-UAT-JAVA-30 — baseline percentile NOT NULL 违反（436 events）✅ 根因已确认

- **原标题**: `DataIntegrityViolationException` → `PSQLException: null value in column "percentile" of relation "financial_benchmark_position_baseline" violates not-null constraint`
- **Sentry 链接**: https://lookingglass-3t.sentry.io/issues/LG-UAT-JAVA-30
- **代码位置**:
  - `BenchmarkPositionMonitorServiceImpl.java:462` `saveBaseline` （**真实行号**）
  - 触发上游：`BenchmarkPositionMonitorServiceImpl.java:420` `phase2Diff`

**精确根因**（从 stack 拿到具体数据）：

```sql
-- 失败的插入行：
INSERT INTO financial_benchmark_position_baseline (..., percentile, peer_snapshot, ...)
VALUES (
  ...
  NULL,  -- ❌ percentile = NULL，但列是 NOT NULL
  '[{"value": null, "companyId": "9410d975-..."},
    {"value": null, "companyId": "de8290f8-..."},
    {"value": null, "companyId": "1900eb2b-..."}]',  -- ⚠️ 所有 peer.value 都是 null
  ...,
  'SILENT_NEW_BASELINE',  -- trigger_reason
  ...
)
```

- **现象**：决策是 `SILENT_NEW_BASELINE`（首次基线静默写入）
- **直接原因**：peer 组里**所有公司**该 metric 都没数据 → 算 percentile 时分母为 0 → percentile 计算返回 `null`
- **数据问题示例**：metric=`met-runway`、closed_month=2026-04-01、benchmark_source=PLATFORM，peer 组 3 家公司 own_value 都是 null

**修改方案**（`BenchmarkPositionMonitorServiceImpl.java` 在 `saveBaseline` 前加 guard，约 line 460 附近）：

```java
// 已有：方法签名约 line 462
private void saveBaseline(SnapshotInput snap, DiffDecision d, String runId) {
  // ⭐ 新增：percentile 为 null 时（peer 全空），不写 baseline
  if (snap.percentile() == null) {
    log.warn("[baseline] skip null-percentile baseline: companyId={} metricId={} reason=peer_all_null",
        snap.companyId(), snap.metricId());
    return;
  }
  // ... 原 INSERT 逻辑
}
```

或者两选一：**让 percentile 列允许 NULL**（业务上"无 peer 数据"是合法状态，应该能存）：

```sql
ALTER TABLE financial_benchmark_position_baseline
  ALTER COLUMN percentile DROP NOT NULL;
```

推荐**两个都做**：DB schema 放宽 + 代码 skip 减少噪音。

### 5. LG-UAT-JAVA-1V — `getLastSyncTime` 入参 null（120 events, 7 users）✅ 根因已确认

- **原标题**: `NullPointerException: Cannot invoke "java.time.Instant.toEpochMilli()" because "instant" is null`
- **日志 message**: `getLastSyncTime error`
- **Sentry 链接**: https://lookingglass-3t.sentry.io/issues/LG-UAT-JAVA-1V
- **代码位置**（**精确到行**）:
  - `FiDataCalculateServiceImpl.java:302` `getLastSyncTime` （NPE 抛出点）
  - 调用链：`FinancialStatementsController.java:56` → `FinancialStatementServiceImpl.java:675` `financialEntryAndForecastData` → `FiDataCalculateServiceImpl.java:263` `buildFinancialMetaDto` → `getLastSyncTime`
  - 最终崩点：`java.util.Date.from(Date.java:1363)`

**精确根因**：
`getLastSyncTime` 内部调 `Date.from(instant)` 但 `instant` 是 null。
`instant` 应该来自 QuickBooks 最近一次同步时间——但对于**没接 QBO 的 Manual 模式公司**，该字段为 null。

**修改方案**（`FiDataCalculateServiceImpl.java:302` 附近）：

```java
public Instant getLastSyncTime(...) {
  Instant lastSync = quickbooksQueryService.getQuickbooksMaxPullTime(...);
  if (lastSync == null) {
    // Manual 模式公司或 QBO 未同步过 → 返回 null（前端按"未同步"展示）
    return null;
  }
  // 原本可能是：return Date.from(lastSync).toEpochMilli() 之类的崩点
  return lastSync;
}
```

或更上层 `buildFinancialMetaDto`（约 line 263）调 getLastSyncTime 时容忍 null：

```java
metaDto.setLastSync(
    Optional.ofNullable(getLastSyncTime(...))
        .map(Instant::toEpochMilli)
        .orElse(null)  // 或 0L
);
```

### 6. LG-UAT-JAVA-1Y — `Instant.parse(null)`（61 events, 4 users）✅ 根因已确认

- **原标题**: `NullPointerException: text`（其实是 `Objects.requireNonNull(text)`，参数名叫 text）
- **日志 message**: `getLastSyncTime error`
- **Sentry 链接**: https://lookingglass-3t.sentry.io/issues/LG-UAT-JAVA-1Y
- **代码位置**（**精确到行**）:
  - `QuickbooksQueryService.java:42` `getQuickbooksMaxPullTime` （**真正抛点**）
  - 调用链：同 LG-UAT-JAVA-1V，但走的是另一个分支 → `FiDataCalculateServiceImpl.java:298` `getLastSyncTime` → `QuickbooksQueryService.getQuickbooksMaxPullTime` → `Instant.parse(null)` (line 397)
  - 触发：`Objects.requireNonNull(Objects.java:235)` 校验 "text"（即 Instant.parse 的字符串入参）

**精确根因**：
`getQuickbooksMaxPullTime` 内部调用 `Instant.parse(maxPullTimeStr)`，但 `maxPullTimeStr` 来源（DB 查询字段）为 null（公司从未通过 QBO 拉过数据）。

**修改方案**（`QuickbooksQueryService.java:42`）：

```java
public Instant getQuickbooksMaxPullTime(String companyId) {
  String maxPullTimeStr = quickbooksRepository.findMaxPullTimeByCompanyId(companyId);
  if (StringUtils.isBlank(maxPullTimeStr)) {
    log.debug("[qbo] no pull history for companyId={}", companyId);
    return null;  // 让上层 (getLastSyncTime) 容忍 null
  }
  return Instant.parse(maxPullTimeStr);
}
```

**注意**：这个 bug 和 LG-UAT-JAVA-1V **是同一棵调用树的两种空值场景**——一个是中间环节 instant 为 null，一个是字符串入参为 null。补 1V 的 fix 还要补这个上游 null safety。**两个 issue 一起修，影响 181 个 events**。

### 9. LG-UAT-JAVA-21 / 31 / 1Q — 邮件白名单（283 events 合计）

- **错误**: `Send email failed: Target user is not whitelisted for uat environment.`
- **Sentry 链接**:
  - https://lookingglass-3t.sentry.io/issues/LG-UAT-JAVA-21

  - https://lookingglass-3t.sentry.io/issues/LG-UAT-JAVA-1Q

**根因**：UAT 环境邮件白名单保护机制——非白名单用户的邮件**故意**被拒。这不是 bug，但 ERROR 级别日志会被 Sentry 报警。

**修改方案**：

降低日志级别 + 单独异常类型：

```java
try {
  emailService.sendEmail(email, context, template, type);
} catch (WhitelistRejectedException wre) {
  log.warn("[email] whitelisted-only env rejected non-whitelist target: {}", wre.getTargetEmail());
  // 不上报 Sentry
} catch (Exception e) {
  log.error("[email] send failed", e);  // 真异常才上报
}
```

定义 `WhitelistRejectedException extends RuntimeException`，在 SendGrid 调用层把 "not whitelisted" 错误包装成该异常。

### 14. LG-UAT-JAVA-2Y — financial_normalization 数值溢出（2 events）✅ 根因已确认

- **原标题**: `DataIntegrityViolationException` → `PSQLException: numeric field overflow. A field with precision 50, scale 10 must round to an absolute value less than 10^40.`
- **Sentry 链接**: https://lookingglass-3t.sentry.io/issues/LG-UAT-JAVA-2Y
- **代码位置**:
  - `FinancialNormalizedServiceImpl.processMessage` （SQS 消费入口）
  - `SQSMessageListener.java:126` `onNormalizedQueue` → `lg-uat-normalized-queue`

**精确根因**（从插入语句的 raw 值定位）：

```sql
-- 失败的列：mrr_yoy_growth_rate
mrr_yoy_growth_rate = 281969376581003199999999999999999999999999.00
                      ≈ 2.82e41

-- 列定义：NUMERIC(50, 10) 允许的最大绝对值 < 10^40
```

公司：`bc93cb56-9edb-41cb-b607-db2cc610ccf8`
当月：`2026-02-01`

数据特征：
- `mrr = 284566.32`
- `last_year_mrr_source = {"date":"2026-01-01","Mrr":100.0000000000}` ← **2026-01-01 的 MRR 只有 100**

**问题数学公式**：
```
mrrYoyGrowthRate = (currentMrr - lastYearMrr) / lastYearMrr
                 = (284566.32 - 100) / 100
                 = 2845.66  ← 但插入的值是 2.82e41 ???
```

→ 实际溢出值 `~2.82e41` 表明计算逻辑除了用 lastYearMrr=100 作分母，还**乘了别的什么巨大值**（或者源数据 lastYearMrr 实际是接近 0 的浮点而非 100）。

**修改方案**（`FinancialNormalizedServiceImpl` 算 mrr_yoy_growth_rate / debt_assets_ratio 等比率字段时）：

```java
// 任何比率计算都加 clamp + 极小分母防御
private BigDecimal safeRatio(BigDecimal numerator, BigDecimal denominator) {
  if (denominator == null || denominator.abs().compareTo(MIN_DENOMINATOR) < 0) {
    return null;  // 或 BigDecimal.ZERO，看业务
  }
  BigDecimal result = numerator.divide(denominator, 10, RoundingMode.HALF_UP);
  // clamp 到 NUMERIC(50, 10) 范围
  if (result.abs().compareTo(MAX_NUMERIC_50_10) > 0) {
    log.warn("[normalize] ratio overflow, clamp: num={} denom={}", numerator, denominator);
    return result.signum() > 0 ? MAX_NUMERIC_50_10 : MAX_NUMERIC_50_10.negate();
  }
  return result;
}

private static final BigDecimal MIN_DENOMINATOR = new BigDecimal("0.0000000001");
private static final BigDecimal MAX_NUMERIC_50_10 = new BigDecimal("9999999999999999999999999999999999999999.9999999999");
```

**同样的修复也覆盖 LG-UAT-JAVA-1S**（详见下面 #15）。

### 15. LG-UAT-JAVA-1S — company_index_verify 数值溢出（69 events）✅ 根因已确认

- **原标题**: `DataIntegrityViolationException: could not execute batch [Batch entry 0 insert into company_index_verify ...]`
- **Sentry 链接**: https://lookingglass-3t.sentry.io/issues/LG-UAT-JAVA-1S
- **代码位置**: `FinancialForecastDataServiceImpl.saveIndicatorVerificationDataInternal`

**精确根因**（从 stack 拿到具体数据）：

失败行的 `value` 字段值约为 `1.126e36`（具体：`1126513018961440643563810806543909801.79...`）。
公司 `e3c7ecd3-6f9d-4db8-a3dd-bb14677f9c5e`（"Helen Company New 6-Month Eur"），月份 `2028-01`，indexName `Gross Revenue`。

formula: `revenue = revenueBase × (resultGrowthRate + 1)^diff_month × factor`

**这是个复利公式**——`(resultGrowthRate + 1)^diff_month` 当 growth rate 异常（如 50%）+ diff_month 大（48 个月）时：
- `1.5 ^ 48 ≈ 9.7e8`
- 如果 growth rate 是 100%：`2^48 ≈ 2.8e14`
- 极端 `growthRate=200% + diff=48`：`3^48 ≈ 7.98e22`
- 实际溢出到 1e36 说明 growth rate 或 diff_month 还更夸张

→ 跟 2Y 一样是**比率/复利计算时没做 clamp**。

**修改方案**：

在 `saveIndicatorVerificationDataInternal` 写入前 clamp value：

```java
// 写入前 clamp 到 DB 列精度范围（看具体是 NUMERIC(50,10) 还是别的）
BigDecimal value = computedValue;
if (value != null && value.abs().compareTo(MAX_NUMERIC_VALUE) > 0) {
  log.warn("[index-verify] value overflow, clamp: companyId={} indexName={} value={}",
      companyId, indexName, value);
  value = value.signum() > 0 ? MAX_NUMERIC_VALUE : MAX_NUMERIC_VALUE.negate();
}
```

**更上游**修：复利公式计算时给 growth rate 和 diff_month 都加业务上限（如 growth rate ≤ 100% / diff_month ≤ 36），避免离谱数据触发指数爆炸。
