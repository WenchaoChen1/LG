## 一、全局约定

### 1.1 知识库空间与按类型的产物归属

#### Memory 与知识库的关系

需求路由表有 1a / 1b / Founder KB / Portfolio KB 四列。它们在系统里对应**已有的 Memory 页与知识库页**（两页现为 Goldie Base 的 Memory Settings / Knowledge Base 两个 Tab，9.11.3 / 9.11.2），不是四套存储。代码现状（2026-10-09 调研，Python 仓库 HEAD `defa2e1c`，路径相对 `python/CIOaas-python`）：

| 事实 | 出处 |
|---|---|
| Memory **没有独立的表**，也没有写入接口与合并步骤。Memory 页列出的是**知识库条目的摘要**：登记表 `ai_file_registry`（`purpose='rag'`、`business_type='KNOWLEDGE_BASE'`、`deleted=false`、`ai_rag_entry_id` 非空）圈定范围，再取 `ai_rag_entry.summary` 非空的条目 | `source/lg/db/service/file_registry.py:240-278`、`source/rag/domain/repository/entry_repository.py:175-206` |
| 分层按端：**Company Memory = end_type `APP` 的条目；Portfolio Memory = end_type `ADMIN` 的条目**，都按 `company_id` 列出 | `source/memory/application/memory_service.py:43-51` |
| Memory 页只读；入口对管理端与 Company Admin 开放，公司端普通用户无入口 | web `src/pages/askGoldie/memorySettings/MemorySettingsPage.tsx:103` |
| 知识库页列的是登记行对应的文件，可下载 | `source/file_registry/domain/repository/file_registry_repository.py:113-181` |

**落点**（本方案，2026-10-09）：四列正好对应知识库条目的「摘要 + 正文」——

| 知识库条目 | 摘要（Memory 页展示） | 正文（知识库页展示的 markdown 文件） |
|---|---|---|
| 一条 **APP 端**条目 | 1a Founder Memory | Founder KB |
| 一条 **ADMIN 端**条目 | 1b Admin Memory | Portfolio KB |

不新建记忆存储。条目的具体形态见 1.3。

#### 空间清单

沿用现有 RAG 的空间机制：`ai_rag_business_association` 以组合键 `(end_type, business_type, company_id 或 organization_id)` 唯一确定一个知识库空间，chatbot 检索时按身份解出可见的 `space_ids`。**隔离主要靠「谁能解出哪个空间」**，行级过滤只在 KB-ADMIN（`company_id`）与公司端普通用户（`created_by`）两处存在。

| 代号 | 组合键 | 粒度 | 隔离方式 | 谁能召回（改造后） | 写入的产物 |
|---|---|---|---|---|---|
| **KB-APP** | `(APP, APP_COMPANY, company_id)` | 每公司一个 | 空间层 | 该公司公司端用户 + 可访问该公司的管理端 | GS → 创始人的会议条目 |
| **KB-ADMIN** | `(ADMIN, ADMIN_COMPANY, organization_id)` | **每组织一个（公司 id 隔离）** | **行级 `company_id`** | 仅管理端（可访问公司） | GS 内部 / Partner 的公司层条目 |
| **机构层** | 组合键开发设计定（种子已有 `ADMIN_ORGANIZATION`） | 每组织一个 | 空间层 | 本组织**全体**管理端 | LP 的基金层条目 |
| **证词-匿名** | `(APP, EXPERT_TESTIMONY, organization_id)` | 每组织一个 | 空间层 | 公司端；另经 Playbook 第二路（Add to playbook 打开的条目），管理端也可能召回，去重见 9.11.6 | 证词匿名版 |
| **证词-署名** | `(ADMIN, EXPERT_TESTIMONY, organization_id)` | 每组织一个 | 空间层 | 管理端 | 证词署名版 |
| **跨公司** | `(APP, CROSS_COMPANY, organization_id)` | 每组织一个 | 空间层 | 公司端 + 管理端 | Cross-Company（**仅审核放行的**） |

处理类型均为 `STANDARD`。**租户 = organization**（一把 API key 归属一个租户，见 9.2.1）。

**机构层**承接 LP 的基金层内容：需求路由表 GS → LP 的 1b 即「组合（基金）级别摘要」，故基金层摘要不丢弃；对全体管理端可见（可见范围为本方案），但**不建基金实体**——归属落在 organization 一层，条目 `company_id` 为空，配合 Summary Records 的 Portfolio 标记（仅为标记，不作权限依据，9.5）。本方案倾向**独立空间**而不是在 KB-ADMIN 里放 `company_id` 为空的条目：KB-ADMIN 里管理端会话文件的 `company_id` 也为空，两者在行级上无法干净区分（见下方「召回边界」）。组合键开发设计阶段定。

**需新增两个业务类型**：`EXPERT_TESTIMONY` 与 `CROSS_COMPANY`，均按组织键控。关联业务类型有白名单——种子在 `source/rag/domain/enums.py:52-67`，`business_association_service.py:38,83` 校验，不在种子里的组合键建不出空间（第八章）。两者的份数不同：

- **`EXPERT_TESTIMONY` 两份**——管理端要在 Goldie 内看到署名、公司端永不看到（《会议内容提取规则》II 证词权限），而署名直接存正文、不做召回后处理，故按 `end_type` 分匿名版与署名版各存一版
- **`CROSS_COMPANY` 一份**——两端在 Goldie 里看到的都是同一份匿名内容（需求路由表跨公司只有一列「Tenant-shared 跨公司抽取内容」）；管理端回溯原会议有两处：Goldie Base 的 Cross company content Tab（审核放行后，每条带会议名称与元数据，PM / PGM / SA 只读，9.11.4），以及会议管理页（Summary Records 详情的 Content Routing Matrix，仅 PGM / Super Admin，9.6，审核与编辑的唯一入口），都不经 Goldie

**Cross-Company 只投影已审核放行的条目**：需求 I.2「管理员会在任何信息传播前进行审核」，所有类型都需审核（用户决定 2026-10-10），Authorize 默认不勾（1.7、9.6.4），放行后才写入跨公司空间。

证词与跨公司条目**不进 Memory 页**：它们不属于任何公司，登记行 `company_id` 为空（1.2）。管理端在 Goldie Base 的 Cross company content / Expert Testimony 两个 Tab 查看（9.11.4 / 9.11.5）。

#### 召回边界的关键事实

管理端的检索范围已包含各可访问公司的 APP 空间（`source/ai/tools/knowledge_base_tool.py:124-135` 并入 `find_app_space_ids`），**反向不成立**——公司端只解出自己公司那一个 APP 空间。因此：

- 进 KB-APP 的内容管理端自动可见，GS → 创始人只写 APP 条目即可同时满足 1b 与 Portfolio KB
- 只允许管理端看到的内容写进 ADMIN 端空间，即结构性对公司端不可见，**不需要额外加过滤**
- **KB-ADMIN 的公司隔离是行级的**（同一组织共用一个物理空间，靠条目上的 `company_id` 区分），故 `company_id` 必须填对

现有召回链路有三处取不到会议条目，需改造（第八章）：

| # | 缺口 | 现状 | 受影响的产物 |
|---|---|---|---|
| 1 | 公司端普通用户只召回本人上传的 | 叠 `created_by == 本人`（`knowledge_base_tool.py:114`；`chunk_repository.py:85-90`），Company Admin 不叠 | 系统写入的 KB-APP 会议条目；需求路由表 1a / Founder KB 要求公司端可见 |
| 2 | 管理端行级过滤对**整次召回的全部空间**生效 | 过滤 `company_id IN 可访问公司 OR thread_id`（`knowledge_base_tool.py:116-135`；`chunk_repository.py:66-83`），`filters` 对每个空间共用（`source/rag/infrastructure/processor/factory.py:270-276`） | `company_id` 为空的条目：机构层、证词署名版、跨公司——解出空间也会被整片滤掉 |
| 3 | 公司端只解本公司 APP 空间 | `knowledge_base_tool.py:103-114` | 证词匿名版、跨公司 |

> **不能用「放开 `company_id IS NULL`」解决第 2 条**：管理端会话文件的 `company_id` 同样为空、靠 `thread_id` 区分（`chunk_repository.py:66-83`），放开即把别人会话里的文件召回出来。正确做法是行级过滤**按空间施加**——只对 KB-ADMIN 叠公司 / 会话析取，其余空间靠空间层隔离已足够。

### 1.2 登记表业务类型

会议派生的每条条目都写一行 `ai_file_registry`，`business_type = FIREFLIES`（该列为 `VARCHAR(40)` 自由文本，无 CHECK 约束，新增取值不需要 DDL 改动）。现有登记函数 `upsert_kb_registration` 把业务类型写死为 `KNOWLEDGE_BASE`（`file_registry.py:115,128`），需新增 Fireflies 的登记函数。

| 条目 | `end_type` | `company_id` | 出现在 |
|---|---|---|---|
| GS → 创始人条目 | `APP` | 关联公司 | Memory 页 Company Memory；公司端与管理端知识库页 |
| 公司层条目（GS 内部 / Partner） | `ADMIN` | 命中公司 | Memory 页 Portfolio Memory；管理端知识库页 |
| 基金层条目（LP） | `ADMIN` | **空** | Memory 页与管理端知识库页的机构层展示（改造后） |
| 证词两版 / 跨公司 | `APP` / `ADMIN` | **空** | 不出现在两个页面；管理端在 Goldie Base 各自的 Tab 查看（9.11.4 / 9.11.5） |

`organization_id` 一律填租户。证词与跨公司的 `company_id` **必须为空**：它们已匿名、不属于任何公司；若填来源公司，会以该公司条目的身份出现在其 Memory 页与知识库页。

**对 Goldie 检索无影响**——召回按空间走，`recall` 使用的 `business_type` 取自 `ai_rag_space`（`search_service.py:222`），与登记表的同名字段无关。

**对两个页面有影响**——Memory 页与知识库页现只取 `KNOWLEDGE_BASE`（`file_registry.py:271`；`file_registry_repository.py:137`），需把 `FIREFLIES` 纳入这两处查询（第八章）。

**按会议定位**：登记表不加会议列。中间表记录每个去向投影出的条目、登记行与文件 id（9.6.4），重投影时按它软删（1.6）。

### 1.3 产物形态

**每个知识库条目 = 一个 markdown 文件 + 一个条目**：

| 层 | 存储位置 | 说明 |
|---|---|---|
| **原文** | `ff_meeting` / `ff_meeting_sentence`（新建） | 永久留存，审计源、重算依据与 n-gram 比对基准；不进向量库 |
| **中间表** | 新建（9.6.4） | 每场会、每个去向一行，矩阵的可编辑正本；知识库条目由其中已授权的行投影而来 |
| **正文** | markdown 文件（`files` 行 + S3）→ 按 800/100 切片（`chunk_kind=body`） | 知识库页（Goldie Base 的 Knowledge Base Tab，9.11.2）展示、可下载；Goldie 检索细节 |
| **摘要** | `ai_rag_entry.summary` + 单片 `chunk_kind=summary` | Memory 页（Goldie Base 的 Memory Settings Tab，9.11.3）展示；Goldie 检索概览；**不超过 150 个英文单词**（用户决定 2026-10-10；需求原文「1,000 字以内」，产物为英文，按单词计更好执行） |

文件、`ai_rag_entry` 与 `ai_file_registry` 三者一起写，走新增的「会议派生 markdown 入库」路径（第七、八章）。不能用 `ingest_text`：它不建登记行（`ingest_service.py:461`），条目进不了 Memory 页与知识库页。

**各条目的摘要与正文**

| 条目 | 摘要 | 正文 | 来源 |
|---|---|---|---|
| GS → 创始人 | 1a = 1b，≤150 个英文单词 | Founder KB = Portfolio KB，不设长度上限 | Fireflies `summary.overview` → 大模型整理为 markdown；overview 为空时从原始转录生成（正文同此，本方案补充） |
| 公司层（GS 内部 / Partner） | 1b，≤150 个英文单词 | Portfolio KB markdown，**附原始转录链接、不复制原文**（本方案） | 从原始转录抽取（第六章） |
| 基金层（LP） | 1b 基金层，≤150 个英文单词 | Portfolio KB 基金层 markdown，附原始转录链接 | 从原始转录抽取 |
| 证词两版 | 不写 | 证词 markdown，首行为来源行（3.4） | 从原始转录抽取 |
| Cross-Company | 不写 | 洞察 markdown，带标签与类别（`category`，四类之一，6.9（P6）） | 从原始转录抽取 |

约束：

- **产出一律 markdown，统一经大模型生成或整理**（markdown 为本方案；经大模型整理见需求 I「LLM 摘要层」）。Fireflies 自带的 overview 也要过一遍大模型，不原样入库
- **凡进 Memory 页的条目都必须写摘要**：Memory 页只列摘要非空的条目，摘要为空的会议条目会从 Memory 页消失。原「内容短于阈值时只存 body、不写 summary」作废。内容本身很短时摘要与正文接近，接受这一重复
- 证词与 Cross-Company 不进 Memory 页，正文本身就是一条短洞察，不另写摘要
- **摘要由我方传入，跳过系统的二次 `summarize`**——向量化链在 `factory.py:364` 无条件调用系统摘要器，不跳过会变成「摘要的摘要」；且系统摘要器产出的是纯文本英文摘要，≤150 词（`summarizer.py:59,96`），不是 markdown。超长压缩是写入前我方主动做的（6.5（P2）），不走系统 `summarize`
- **GS → 创始人的摘要不做筛选**：撤销此前「按公司结构化记忆分类筛选」与「创始人安全版过滤」两条规则（用户决定 2026-09-30 删除），定稿只做整理与压缩
- **overview 同样过 n-gram 近逐字剔除**：它是 Fireflies 的 LLM 摘要，不保证不照抄原句。比对基准仍是原始转录（6.11 机械清洗）
- Memory 页现按纯文本展示摘要，与 markdown 口径的衔接见第十章
- 产物语言为英文（6.1）
- 提取前先在识别阶段走**质量判断**（程序硬门槛 + 6.4（P1），9.3.4），判定为无实质内容的直接跳过，不产出条目

### 1.4 去逐字化适用矩阵

《会议内容提取规则》I 的去逐字化分两层：LLM 摘要层（非逐字表达）与机械擦除层（实体/姓名剥离 + n-gram 近逐字剔除）。三种处理**按去向分别适用**：

| 去向 | 非逐字表达 | n-gram 近逐字剔除 | 实体/人名剥离 |
|---|---|---|---|
| 1a | ✅ | ✅ | ❌ |
| 1b（含基金层） | ✅ | ✅ | ❌¹ |
| Founder KB | ✅ | ✅ | ❌ |
| Portfolio KB | ✅ | ✅ | ❌¹ |
| Cross-Company | ✅ | ✅ | ✅ |
| 专家证词 · 匿名版 | ✅ | ✅ | ✅ |
| 专家证词 · 署名版 | ✅ | ✅ | ✅ |

> **图例**：✅ 做 ／ ❌ 不做
>
> ¹ **GS → LP 例外**：1b 中提到其他被投公司时剥掉对方标识（本方案）。本类型只有基金层条目（不按公司拆分，用户决定 2026-10-10，3.3），它对全体管理端可见、不按公司圈定，其中提到的被投公司一律剥标识、改为泛指——具体公司的内容不写入，也不进任何知识库（本方案）。这一处由 6.7（P4）的提示词处理，不套 1.5 的整张清单。

**判据：实体剥离只在「内容跨出本公司」的去向做。**

实体剥离要防的是 A 公司的信息被 B 公司的人读到。1a / 1b / Founder KB / Portfolio KB 都按 `company_id` 绑定、只对本公司与管理端可见，剥离在这里没有收益，只会破坏可用性——1a 剥掉本公司名与产品名后，Goldie 连"Acme 那单谈得怎么样"都召不回。Cross-Company 与证词库是跨公司复用的，必须剥。

**各格依据**：

| 处理 | 依据 |
|---|---|
| 非逐字表达 / n-gram：1a、Founder KB、Cross-Company、证词 | 《会议内容提取规则》I「任何面向 Founder 的界面绝不呈现原始逐字表述」 |
| 非逐字表达 / n-gram：1b、Portfolio KB | 用户决定（1a / 1b 经 Goldie 召回的都是转义后的）；GS → 创始人的 1a 与 1b 是同一份文本，本就无法分开处理 |
| Cross-Company 做实体剥离 | 路由表该列为「Tenant-shared 跨公司抽取内容」，对全租户共享、内容跨出本公司——需求 I.2 剥离清单末句「管理员会在任何信息传播前进行审核」指向的正是这类传播 |
| 证词两版做实体剥离 | 《会议内容提取规则》II 证词权限「不向 Founder 展示任何来源信息」，GS → Founder 证词「同样适用匿名化处理」 |
| 1a / 1b / Founder KB / Portfolio KB 不做实体剥离 | 用户决定（2026-09-22）；GS → 创始人：创始人已经参与会议，不做敏感信息过滤（本方案）；GS 内部 / Partner 的 1b 是交易事实（被兜售、估值、买方、价格）的唯一去处（路由表「只放该公司 1b」），剥离会把规则要保全的内容抹掉（GS → LP 不按公司拆分，交易事实不落 1b，3.3） |

**需求 I.2 的适用范围**：需求把剥离清单写在「机械擦除层」之下，字面像对所有面向 Founder 的界面生效；但清单末句「管理员会在任何信息传播前进行审核」指向的是跨公司传播。本方案按后者理解——剥离清单只用于 Cross-Company 与证词两版。

**证词两版的内容完全相同（均为匿名内容）**，差别只在程序附加的首行来源行（本方案）——署名版**不是**在内容里保留实体。这与交易事实不进证词（需求证词表「同样适用……交易敏感规则」）自洽：公司具体交易事实根本不进证词库（只落 1b；GS → LP 连 1b 也不落，1.7），证词内容中本就不应存在可识别的公司实体。

### 1.5 实体/人名剥离的范围

以《会议内容提取规则》I.2 的清单为准，本方案补充其未列的处理细则。**仅适用于 1.4 中标 ✅ 的去向**（Cross-Company 与证词两版）。

**直接标识符——机械层为主**

| 类别 | 处理 | 出处 |
|---|---|---|
| 公司名及其简称、变体、曾用名 | 剥离 | 需求 I.2 |
| 产品名、品牌名 | 剥离 | 需求 I.2（产品名） |
| 人名（全名 / 名 / 姓 / 昵称） | 剥离 | 需求 I.2 |
| 邮箱、域名、URL | 剥离 | 需求 I.2（邮箱、域名）；URL 本方案补 |
| 客户 / 供应商 / 合作伙伴 / 投资者名 | 剥离 | 需求 I.2 |
| 「公司 + 职位」组合（如"Acme 的 CTO"） | 剥公司，保留职位 | 本方案 |
| 具体数字：收入、ARR、员工人数、估值、交易条款，以及金额、百分比 | **转量级**，如"约百万级 ARR"、"两位数下滑" | 需求 I.2；金额与百分比本方案补 |
| 具体日期、时间点 | **转阶段**（"A 轮后"、"上一财年"）或**时长**（"约一个季度内"、"连续两个季度"）；**禁止绝对时点**——年份、季度、月份一律不保留（"2026 Q3"、"去年 Q3"、"今年 8 月"） | 本方案 |
| 地区以下的细分地理信息（如"我们西雅图办公室"） | 剥离，最多保留到地区一级 | 需求 I.2 |

机械层只认得**已知实体**：候选公司清单、参会人姓名、注册表里的姓名与机构、本机构名称与基金名称（本租户 Portfolio 名称列表，供基金层过滤兜底，用户决定 2026-10-10），以及邮箱 / 域名 / URL / 数字 / 日期这类模式。清单外的客户、供应商、投资者名靠 LLM 层改写，机械层只对已知的那部分兜底。

**准标识符与需判断的事项——机械层无能为力，靠 LLM 层处理**

单个属性都不敏感，**组合起来可唯一定位**。例："一家做**牙科 SaaS** 的、**A 轮后**、**Q3 丢了最大客户**的公司"——三个属性各自无害，凑在一起在组合内可能只对应一家。

这类内容没有可匹配的实体词，机械层扫不到。**诉讼与纠纷**（需求 I.2）同理：没有固定词形，由 LLM 层整段不写。所以双层防护实际是**分工**而非冗余：

- **机械层**：处理直接标识符，确定性高、可测
- **LLM 层 + 可迁移判据**：处理准标识符与需判断的事项，靠「脱离这家公司仍然成立才保留」把独特细节整体抹掉

这也是 Cross-Company 采用「只抽可迁移的内容」（Portable Trends Only，需求 (3)）而非「整场匿名化」的原因——后者只过得了机械层，准标识符会原样留在文本里。

**保留（剥了即失去价值）**：行业 / 垂直范围、公司阶段（ARR 区间、轮次）、通用职位（CEO / CTO，不带公司）、问题类型、应对方式。需求 I.2：「保持纵向范围和 ARR 区间的大致轮廓，否则洞察力将毫无用处」。

**兜底原则**（需求 I.2）：剥离后剩余信息仍指向单一公司 → 继续剥离。需求允许「在共享方面存在误差」，前提是传播前有管理员审核——对应 Cross-Company 默认不授权、审核后才发出（1.7）。

n-gram 阈值可配置（需求 I），实施期用真实数据调优。

### 1.6 幂等与重算

**按 `meeting_id` 覆盖**：先软删旧条目，再写新条。避免改判会议类型或重跑加工后，Goldie 同时召回同一场会的新旧两版。

**条目只能整条替换**：条目内容没有更新接口（`source/rag/interfaces/routes.py` 只有 retry `:349` 与 DELETE `:471`）。中间表是正本（9.6.4），markdown 文件与 `ai_rag_entry` 都是它的投影，因此任一来源的改动——矩阵编辑、授权、改判或公司增删后的重提取——都按同一步骤**重投影**：

1. 软删旧条目及其登记行
2. 按中间表当前内容重新生成 markdown 文件
3. 走会议派生入库路径写新条目与新登记行（1.2），重新向量化，摘要直传（1.3）
4. 中间表改为指向新条目

取消授权只做第 1 步；重新勾选从第 2 步做起。

- **已下载的副本不追**：用户此前从知识库页下载到本地的文件不随之更新
- 编辑保存时重跑机械层清洗、不重跑 LLM 改写（9.6.3）

### 1.7 机密性规则

以现行需求与用户决定为出处；超出需求的部分标注「本方案加严」。

| 规则 | 出处 | 内容 | 本方案适用范围 |
|---|---|---|---|
| **在途交易隔离**（Live-deal Quarantined） | 《会议内容提取规则》II (3)；路由表跨公司列「所有进行中的交易信息永不放出，只放该公司1b」（GS → Founder 一格写明，其余三类「同上」） | 正在跟进、尚未成交的商业项目、谈判细节、竞标数据，不得混入趋势摘要 | **四类会议的 Cross-Company**，统一执行（需求明文） |
| **交易事实只落 1b** | 路由表跨公司列「所有进行中的交易信息永不放出，只放该公司 1b」（四类会议统一）；证词表「同样适用……交易敏感规则」 | 具体交易事实：被兜售、估值、买方、价格、时间表 | GS 内部 / Partner 的 1b / Portfolio KB 是唯一去处；GS → 创始人的留在该公司的 APP 条目（1a = 1b，1.1）；**GS → LP 不落任何去向**——本类型不按公司拆分（用户决定 2026-10-10，3.3），只留原始转录；四类会议都不进证词、不进 Cross-Company |
| **Partner 的 1b 默认扣留** | 路由表 Partner 行 1b「敏感，默认保留，进入待分配」；Portfolio KB 随 1b 一并扣留（本方案） | 整条默认不放行 | GS → Partner 的 1b 与 Portfolio KB：Authorize 默认不勾，人工放行后才投影（9.6.4） |
| **保密过滤**（Confidentiality Filter） | 《会议内容提取规则》II (4) | 剔除保密、敏感、受 NDA 约束的信息：核心财务数据、未公开客户清单、敏感条款 | 需求挂在 LP 证词下；**本方案加严**到**四类会议的 Cross-Company**（LP 与 Partner 原已执行，GS → 创始人与 GS 内部随跨公司口径统一扩入，用户已知悉），以及 **Partner 证词、创始人证词**（用户决定 2026-10-10）——跨公司库对全租户公司端可见，NDA 内容漏进这里比漏进证词库后果更重，且口径统一才能共用一份提示词片段（6.3「敏感过滤要求」）；Partner 是买方、投行、并购顾问，其证词最易夹带受 NDA 约束的内容（5.6） |
| **LP 保密** | 本方案规则；范围收窄（用户决定 2026-10-10） | 剥 **GS 自有基金**的具体信息（本基金的募资进度、回报指标、LP 构成）与 LP 身份；行业层面的募资与配置趋势（不指向 GS 的基金、也不指向某个 LP）不剥——它对创始人有参考价值，原「基金层信息」的说法太宽、会误伤 LP 证词与跨公司里的行业判断。GS 自己的基金按本租户 Portfolio 名称列表识别：作为 `firm_profile` 传入 P5 / P6，机械层再按名称兜底（1.5） | LP 证词、Partner 证词、创始人证词（三类证词共用一个提示词 6.8（P5），过滤统一，本方案）；**四类会议的 Cross-Company**（GS → 创始人与 GS 内部随跨公司口径统一扩入，本方案加严）。**对 1b 是保全规则**：GS 自有基金信息与 LP 身份落机构层条目（1.1）。GS → LP 的 Cross-Company 另加两项附加剥离：GS 自有基金的相关内容、全部 LP 身份信息（3.5，用户决定 2026-10-10） |
| **实体剥离清单** | 《会议内容提取规则》I.2 | 见 1.5 | Cross-Company、证词两版（1.4） |
| **Cross-Company 审核后发出** | 需求 I.2「管理员会在任何信息传播前进行审核」；用户确认所有类型的跨公司内容都需审批（2026-10-10） | — | 所有类型的 Cross-Company：Authorize 默认不勾，放行后才投影到跨公司空间 |

**执行方式**：

- 命中的内容**在写入阶段就不产出**，对所有受众排除（含 Portfolio Manager），不是存入后按角色隐藏——召回侧只有空间层与少数行级过滤，`SearchHitDTO` 也不透出 metadata（3.4 批注），内容一旦入库就拦不住
- 证词与 Cross-Company 是**两条独立管道**，LP 保密与保密过滤在各自管道各执行一遍，不假设对方已做（3.6）
- 「默认扣留」与「审核后发出」都落在 Authorize 的初始状态上（9.6.4），与 `Pending` 会议共用一套人工放行流程，不另建审核队列

> **Cross-Company 的过滤四类会议统一**（需求路由表跨公司列：GS → Founder 一格写明，LP / GS 内部 / Partner 均为「同上」）：
>
> - **在途隔离已是需求明文**，四类一样；原「Partner 每场按在途处理、GS 内部为本方案加严」的按类型区分取消
> - **保密过滤与 [LP 保密] 扩到四类**：原只在 LP / Partner 的 Cross-Company 执行，现统一——**本方案加严**（用户已知悉）。跨公司对全租户可见、漏出后果最重；口径统一才能四类会议共用一个提示词（6.9（P6））
>
> 统一后的口径：**具体交易事实只落该公司 1b**（GS → LP 没有公司层 1b，不落任何去向，3.3），仅可迁移的内容允许进 Cross-Company，过滤 [去身份] + [在途隔离] + [保密过滤] + [LP 保密] 每类会议都执行。

### 1.8 参会人姓名回退匹配

适用于 1.9 匹配链中的 Cheat Sheet 与 HubSpot 两级：**先用邮箱匹配，未命中再用姓名**（《AI Meeting Type 自动映射标准》平台外人员识别第 3 条）。LG 平台用户只按完整邮箱识别（1.9 ①），不做姓名匹配。

| 项 | 规则 |
|---|---|
| **匹配对象** | Cheat Sheet 登记人员，按会议日期取当时生效的版本（9.7.2）；HubSpot 联系人（MVP 跳过，见 1.9） |
| **匹配方式** | **完全匹配**，不做模糊、不做近似 |
| **重名** | 匹配到多条 → **直接进 Pending Assignment**，不猜测 |

**姓名取值来源**：Fireflies 的 `meeting_attendees` 中 `displayName` / `name` 实测**全为 null**，取不到「日历邀请中的姓名」。可用源为：

1. `meeting_attendance[].name`——平台出席记录，最接近日历邀请，**首选**
2. `speakers[].name`——ASR 说话人识别，**仅作兜底**（人名易被识别错，用于匹配注册表风险更高）

> 采用完全匹配而非模糊匹配，是因为姓名匹配的误判代价不对称：匹配不上只是进 Pending 等人工处理，匹配错则把外部人当成内部人（或相反），直接改变会议类型与整条路由。

### 1.9 参会人识别与公司归属

以《AI Meeting Type 自动映射标准》为准。**明确禁止使用会议标题作为识别依据。**

**参会人来源**：会议在 **Microsoft Teams** 内召开、将 Fireflies 拉入，因此 Fireflies 返回的参会人即 Teams 会议的参会人。实测样本亦印证——`calendar_type = "outlook"`、`meeting_link` 指向 `teams.microsoft.com`。取值用 `participants`（邮箱数组）与 `meeting_attendance`（出席记录，含姓名与进出场时间）。

识别要产出两样**互相独立**的东西：

| 产出 | 用途 | 缺失的后果 |
|---|---|---|
| **人的身份** | 决定会议类型（GS 方 / Founder / LP / Partner） | 类型判不出 → 会议进 Pending |
| **公司归属** | 决定产物落哪家公司 | 该公司的产物无处可落 |

**匹配链（命中即止）**

| 顺序 | 匹配方式 | 匹配对象 | 产出 |
|---|---|---|---|
| ① | **完整邮箱** | LG 平台用户 | 管理端用户 → **GS 人员**；公司端用户 → **Founder**，并取其所属公司（公司状态限 Active / Thriving / Needs Intervention / Needs Guidance） |
| ② | **邮箱 → 姓名**（1.8） | Cheat Sheet，按会议日期取当时生效版本；该日身份有重复取最新一条 | 人员确定 + 角色 / 专长标签 |
| ③ | **邮箱 → 姓名** | HubSpot 联系人 | 人员确定（MVP 跳过，见下） |
| ④ | **邮箱域名** | `goldensection.com` / `whalesongproduct.com` / `gstdev.com` | **仅判定「此人属 GS 方」**，不对应到具体人员 |
| ⑤ | **LLM 推断** | 转录正文 | **只推断公司**，不解决「人是谁」（2026-09-22 澄清） |
| ⑥ | —— | —— | Pending Assignment |

**GS 人员**的三个来源（取并）：① 管理端用户、② Cheat Sheet 中 role = `GS staff`、④ 三个域名回退——回退只在既不是管理端用户、也未登记在册时才用。Cheat Sheet 里的 `GS staff` 与 `Founder` 指**未使用 LG 平台**的人员。

> **域名匹配的唯一用途是判定 GS 方**（用于会议类型分类），**不做人员对应**——同一域名下有多个账号，域名本身无法定位到人，也无此必要。

**HubSpot**：三个仓库都没有 HubSpot 集成（2026-10-09 复核，零命中）。**MVP 先跳过该级**——Cheat Sheet 未命中即进入域名判定。代价：仅存在于 HubSpot、未登记进 Cheat Sheet 的外部人识别不出来，会多一批 Pending。是否补建见第十章。

**公司归属**

| 来源 | 规则 |
|---|---|
| **参会人完整邮箱** | 匹配公司在 LG 中的 Team 记录（即该公司的公司端用户，①）→ 关联该公司。**不按域名** |
| **正文提及**（⑤，6.4（P1）） | GS 内部 / Partner 的公司层拆分靠它（GS → LP 不按公司拆分、不做公司识别，用户决定 2026-10-10，3.3）；仅凭 Cheat Sheet Founder 判出的 GS → 创始人也靠它反推公司——**正文识别恰好给出一家高置信公司才采纳，零家或多家一律 Pending**（1.10、2.1） |
| **人工指定** | Summary Records 页增删公司（9.5.3） |

- 一场会议可关联**多个公司**
- 域名不参与公司归属
- 需求要求管理端能追溯「这场会议为何关联到此公司」（原型已包含）：命中依据写入 `IDENTIFY` 审计（9.10.2），Summary Records 按公司展示依据文案（9.5.3）

**关键规则**

- **LLM 推断这一级只推断公司，不推断人的身份**。因此人未识别时，即便推断出了公司，会议类型仍判不出——**会议照常进 Pending**
- **Pending 阻断的是内容提取，不是识别**。识别阶段照常跑完并留痕——参会人身份、公司归属（程序按邮箱 + 6.4（P1）的正文提及识别）都要产出，管理端 Summary Records 页要展示它们、人工审核也靠它们。被阻断的是**内容提取**：调用哪些提示词、P3 / P5 传入什么按类型参数都由会议类型决定（复用矩阵见 6.2），类型未定就无从选择，强行提取只会拿到质量不可控的结果。**等人工在 Summary Records 页补齐后再触发提取**
- **发言人映射也属识别阶段**：逐句的 `sentences[].speaker_id` 经 `speakers[].name` 映射到已识别的参会人，**映射不上即视为该参会人未识别，整场进 Pending**。`speakers[].name` 来自 ASR（昵称、听错拼写、`Speaker 2`、两人合并为一个 speaker 都会导致对不上），故这一步要在调用 LLM 之前做完——证词的来源行与专家推测都依赖它，留到提取后才发现就晚了
- 识别结果（公司、外部人员、角色、专家标志）传递给下游分类与提取步骤；专家标志的识别见 1.11

### 1.10 会议状态

两组状态，分属两个管理端页面。

**Raw Data 页 · `Invalid`**

> 当会议非常短且没有实质内容时，判定为无效会议，显示灰色 "Invalid" 标签（《Fireflies Raw Data》）

复用 1.3 的「提取前质量判断」，**判定结果作为字段存在 `ff_meeting` 上**——页面要展示标签就必须持久化。两个判据、两个时机与优先级见 9.3.4。

**Summary Records 页 · `Passed` / `Pending`**（《Fireflies Summary Records》）

| 状态 | 触发条件 | 是否阻断路由 |
|---|---|---|
| **Passed** | AI 判出会议类型与参会人、内容已路由，且**没有待审核内容**；或 Pending 会议经管理员应用路由（9.6.5） | 否 |
| **Pending**（待识别） | 参会人 Unidentified；或会议类型未判定成功；或 GS → 创始人仅凭 Cheat Sheet Founder 判出、正文反推不出恰好一家高置信且为到场者所在的公司（2.1）（本方案，2.1） | **是**，**内容提取与路由阻断**；识别结果（参会人、公司归属）照常产出并展示，等人工补齐后再提取 |
| **Pending**（待审核） | 提取已完成，但有待审核内容：Cross-Company 行、GS → Partner 的 1b / Portfolio KB 行（默认不授权，1.7）。只要有待审核内容，状态就是 Pending（用户决定 2026-10-10） | **否**：已授权的其余内容照常路由，只有待审核行等管理员放行；管理员 `Confirm & Apply Routing` 即视为审核完成（勾选的放行、未勾选的不放行），会议转 `Passed` |

> **`Flagged` 已取消**。它原有两个用途：提示人工判断 GS → Founder 是否应改判 Board Call，以及给「仅凭 Cheat Sheet Founder、公司靠正文反推」的路径做人工复核。Board Call 类型取消后前者已无意义；后者改为只采高置信度、低置信度一律 `Pending`——GS → 创始人的内容进创始人可读空间，错绑即客户侧泄漏，宁可阻断。
>
> **两种 Pending 在列表上标出原因**（待识别 / 待审核），管理员能分清是要补识别还是要审内容（9.4.2）。重新提取由管理员发起、经 `Confirm & Apply Routing` 才生效，应用即审核，所以「待审核」只出现在自动提取之后。

### 1.11 专家身份：补充识别与专家推测

以《AI Meeting Type 自动映射标准》「特殊说明」与《Cheat Sheet》为准。

#### 分类与补充分两步

| 步骤 | 做什么 | 规则 |
|---|---|---|
| **分类** | 定每位参会人的身份，进而定会议类型 | 1.9 匹配链，命中即止 |
| **补充**（enrichment） | 对**每位**参会人另查名册，识别专家身份 | 不论分类命中哪一级都查；按会议日期取 Cheat Sheet 当时生效的版本（9.7.2），先邮箱后姓名（1.8） |

两步互不覆盖：补充查到的名册记录**不改变分类结果**——LG 平台用户在名册里另有登记时，身份仍以平台账号为准（1.9 ①），名册只贡献专家标志与专长标签。

例：某人按 LG 公司端用户被判为 Founder → 会议为 GS → 创始人；补充时查名册发现其为专家 → 同一场会还产出专家证词（2.5）。**一场会可同时产出分类结果与专家证词。**

#### 「被标记为专家」的判定

需求未定义具体字段，本方案定为：**该人在 Cheat Sheet 中、按会议日期生效的版本至少带一个专长标签**，即视为专家。

- 只看专长标签，不看角色：角色描述身份，专长标签描述领域
- Area of expertise 是自由文本，只作描述、不参与路由（《Cheat Sheet》），也不参与专家判定
- LG 平台用户（如创始人）要被认作专家，同样须在 Cheat Sheet 有登记。这与「Cheat Sheet 中的 Founder 指未使用 LG 平台的创始人」的口径如何对齐，见第十章

#### 专长标签

| 项 | 规则 | 出处 |
|---|---|---|
| **取值** | 受控列表，初始 5 项：Multiples、Buyer behavior、Exit trends、Software usage、Commercial buying behavior | 《Cheat Sheet》 |
| **新增** | 在 Cheat Sheet 的标签下拉中手动新增，只有管理员可加 | 《Cheat Sheet》；《AI Meeting Type 自动映射标准》特殊说明 |
| **删除** | 已被使用过的标签不允许删除 | 《Cheat Sheet》 |
| **用途** | 专家判定、证词的专长标签（按会议日期回溯）、专家推测的归类目标 | — |

专长标签**不参与会议类型判定**——GS → Partner 只看角色（5.1）。维护页面与数据模型见 9.8。

#### 专家推测

| 项 | 规则 |
|---|---|
| **对象** | 非 GS 的参会人（GS 人员口径见 1.9），且尚未被标记为专家。**GS 员工永不推测** |
| **触发** | 在证词类别（专长标签领域）中提出**实质性主张**，且同一场会 ≥ 2 条。「实质性主张」按 6.10（P7）的四条判据界定：本人主动陈述、落在标签领域内、讲一类情况而非个例、带依据（用户决定 2026-10-10） |
| **归类** | 每条主张归到一个专长标签；标记带上主张中出现过的标签；归不进任何标签的不算 |
| **排除** | 该人 email 在本租户的**拒绝名单**中 → 不推测 |
| **展示** | Summary Records 参会人标签显示「可能为专家」；管理员点姓名弹详情框（9.5.6） |
| **同意** | 写入 Cheat Sheet，带对应专长标签，来源标识 `From FF Summary Records`（9.5.7） |
| **拒绝** | 记录该人 email 进拒绝名单，之后不再对此人推测——需求原话：「避免 Goldie 每周重复询问同一人」 |

**抽取侧**：由 6.10（P7）完成，GS → 创始人 / GS → LP / GS → Partner 三类会议各跑一次，与该类型的其余提示词并行调用。程序先剔除 GS 人员、已是专家的人、拒绝名单中的 email，只把剩下的发言人交给它；返回的每个人带上其实质性主张及依据，程序按门槛（≥ 2 条）决定是否标记，主张与依据作为管理员确认时的参考。GS 内部会全员为 GS 人员，不调用。

**同意只更新名册**，影响此后会议的补充识别；本场已提取的内容不回溯补抽证词（见 9.5.6「不回溯本场」与 9.5.8）。

## 二、GS → 创始人（默认类型）

### 2.1 判定条件

**GS 方 ≥ 1 且 公司方 ≥ 1**（《AI Meeting Type》触发规则「≥1 位 GS 人员 + ≥1 位 founder 人员」），两侧各自按下列口径判定。逐人识别按 1.9 的匹配链命中即止，本节只列与本类型相关的口径。

**GS 方 ≥ 1**——参会人中任一命中即成立（顺序同《AI Meeting Type》「何为 GS 人员」）：

| # | 条件 | 覆盖谁 |
|---|---|---|
| ① | 完整邮箱匹配 LG **管理端**用户 | 已注册平台的 GS 人员 |
| ② | Cheat Sheet 中 role = `GS staff` | **未使用 LG 平台**的 GS 人员 |
| ③ | 回退：邮箱域名为 `goldensection.com` / `whalesongproduct.com` / `gstdev.com` | 既不是管理端用户、也未登记在册的 GS 人员 |

> 三个域名在平台用户表中各有 45 个账号，量级一致；`whalesongproduct.com` 亦为 Fireflies 实测参会人邮箱的实际域名。另存在 `gstdemo.com` / `gstvc.com` 各 1 个账号，**不计入** GS 方。

**公司方 ≥ 1**——参会人中任一命中即成立：

| # | 条件 | 覆盖谁 |
|---|---|---|
| ① | 完整邮箱匹配 **LG 公司端用户**，且其所属公司 `status ∈ {2,3,4,5}` | 已注册平台的创始人／公司成员 |
| ② | Cheat Sheet 中 role = `Founder` | **未使用 LG 平台**的创始人（手动维护） |

公司状态取 `CompanyStatusEnum` 的四项：Needs Intervention(2) / Needs Guidance(3) / Thriving(4) / Active(5)；排除 Exited(1) / Shut down(6) / Off journey(7)。**不额外要求公司挂 portfolio**（比现成的 `isActiveCompany` 宽）。

**董事会会议并入本类型**：《AI Meeting Type》类型表与《会议内容提取规则》路由表都已删除 Board Call 行（连同 care flag）。董事会会议与普通 GS → Founder 会议从参会数据上本就区分不出来，现一律按本类型处理，不再有「改判为 Board Call」的路径。

**公司归属**——判定「有没有公司方」与确定「是哪家公司」是两件事：前者只要身份，后者要 `company_id`。

| 情形 | 判定 | 公司归属 |
|---|---|---|
| 会上有 LG 公司端用户（无论是否也有 Cheat Sheet Founder） | ✅ 本类型 | 按参会人**完整邮箱**匹配公司在 LG 的 Team 记录取 `company_id`（不按域名）；多家公司的用户同时到场则关联多家 |
| **只有 Cheat Sheet Founder，无公司端用户** | ✅ 本类型 | Cheat Sheet 条目只有 `Organization` 文本、**没有 `company_id`**，只能**由正文提及反推**（6.4（P1）） |

**本类型的公司归属只来自到场的创始人**：正文里提到、但没有创始人到场的公司**不关联**——否则那家公司的创始人会读到一场自己没参加的会。会上有公司端用户时公司已由邮箱确定，6.4（P1）只做质量判断、不做公司识别（用户决定 2026-10-10）；只有 Cheat Sheet Founder 时才靠 P1 的正文提及反推公司。

**Cheat Sheet Founder 路径只采高置信度，低置信度一律 Pending**（阻断内容提取，等人工在 Summary Records 指定公司后再提取）。本类型误判代价比其余类型高一个量级：

| 类型 | 公司归属误判的后果 |
|---|---|
| GS 内部 / Partner | 内容落入错误公司的 **1b**，Portfolio Manager 看到越界内容（管理端） |
| **本类型** | 内容落入错误公司的 **APP 空间**，**该公司创始人可直接读到别家公司的会议摘要**（客户侧泄漏） |

据此，本路径的采纳条件（本方案加严）：

- 6.4（P1）**恰好给出一家**公司，且为 `high`、且 P1 判为到场者所在公司（`attendee_company = true`）→ 采纳
- 只有 `low`、没有结果、或给出多家 → **整场 Pending**

多家也进 Pending，是因为本路径要找的是该创始人**所属**的公司，而 6.4（P1）识别的是正文**提到**的公司——创始人谈起另一家被投公司时，后者同样可能高置信命中，自动关联就会把本场内容送进那家公司创始人的空间。恰好一家但只是被讨论的公司（非到场者所在，`attendee_company = false`）同样不采纳、整场 Pending（本方案，审核修复）。

> 原设计在此以 `Flagged`（凡判为 GS → Founder 一律进人工复核）兜底。《Fireflies Summary Records》的状态已只剩 Passed / Pending，Flagged 随 Board Call 一并取消——它原本就是为了提示人工判断是否改判 Board Call。现改由 Pending 兜底，理由不变；人工指定公司后的首次提取 Authorize 默认不勾（9.6.4），内容仍须人工放行才进入创始人可读的空间。

本类型为**兜底类**：LP 或 Partner 若同时也是某家在营公司的公司端用户，按「LG 平台用户优先、命中即止」即判为 Founder，会议归入本类。

**分类之后另有一步补充**（《AI Meeting Type》特殊说明）：对每位参会人另查 Cheat Sheet，识别专家身份。会上的创始人被标记为专家时，本场额外产出专家证词，见 2.5。补充不改变分类结果。

### 2.3 提取规则

**1a + 1b（同一份摘要）**

- **来源**：Fireflies `summary.overview`；为空时从原始转录生成（本地样本 2/43 场为空）
- **处理**：经大模型整理为 markdown，**≤150 个英文单词**，超长的在这一步一并压缩（本地样本 6/41 场 overview 超过 150 个单词，最长约 240 词）。Fireflies 自带摘要也必须过这一遍，不原样入库
- **粒度**：1a 与 1b 用同一份文本，两处不存在漂移
- **去逐字化**：大模型整理即非逐字表达；定稿后再过 n-gram 近逐字剔除，比对基准是原始转录（overview 是 Fireflies 的 LLM 摘要，不保证不照抄原句）
- **不做敏感过滤、不做实体剥离**：创始人已经参与会议（本方案）；公司名、产品名、人名照常写出（1.4）
- **不按记忆分类筛选**：2026-09-29 写入的「按记忆分类筛选」「创始人安全版过滤」两条规则，用户决定 2026-09-30 删除，随之撤销

**Founder KB + Portfolio KB（同一份文档）**

- **来源**：Fireflies `summary.overview`；为空时按纪要结构从转录生成（6.5；本方案补充）
- **处理**：经大模型整理为 markdown，**无长度上限**
- **粒度**：公司端与管理端关联同一份
- **去逐字化**：同 1a（大模型整理 + n-gram）
- **不做敏感过滤、不做实体剥离**

> 原设计的「纪要」（从原始转录生成的去逐字化全文）：overview 非空时 KB 正文以整理稿为准（用户决定 2026-09-30）；为空时按 6.5（P2）情形 B 写会议纪要。

**多家公司**：一场会关联多家公司时，每家一条，内容不裁剪。本类型下安全——关联公司只来自到场的创始人（2.1），各家均实际到场听过全场，不存在新增暴露。

### 2.5 创始人为专家时的专家证词

出处：《会议内容提取规则》II「GS→Founder / 专家证词」段；《AI Meeting Type》特殊说明「Founder 为专家时的识别」。

**触发条件**

- 会议已按 2.1 归入本类型；补充阶段查 Cheat Sheet（先邮箱、未命中再姓名，1.8），发现到场的某位创始人**被标记为专家**——口径见 1.11：该人在 Cheat Sheet 中按会议日期生效的版本至少带一个专长标签
- 一场会可同时产出 2.2 的全部去向与本节证词；多位创始人均为专家时各自抽取
- **只开放给创始人**：同场其他已在册的专家（如董事会会议上的外部董事）不在本类型产出证词——需求只开放了「该创始人」这一路（本方案口径）
- 创始人未被标记为专家 → 不产出。其发言达到 6.10（P7）专家推测门槛的，按 1.11 打「可能为专家」标记；管理员同意后写入 Cheat Sheet，按 9.5.6 不回溯本场，要本场也产出证词需管理员重新提取（9.9）

**抽取范围**

| 规则 | 口径 |
|---|---|
| 发言人 | 只抽该创始人**本人**的发言（`speaker_ref` 限于该创始人） |
| 主题 | 该创始人当日生效的**专长标签**所覆盖的领域（初始 5 项见 5.2，管理员新增的标签同样适用）；标签之外的领域不抽 |
| **只讲市场** | 必须是对市场情况的判断；**绝不涉及创始人自己的公司、自身数据、客户或计划**。这些只留在该公司的 1a / Founder KB（2.3），同行因此无法反推出说话人（需求原文） |
| 交易敏感 | 交易事实与在途交易信息不进证词（需求「同样适用……交易敏感规则」） |
| 保密过滤 | 剔除机密、未公开客户名单、NDA 限制条款、核心财务数据——**本方案加严**（用户决定 2026-10-10）：需求对创始人证词只要求匿名化与交易敏感规则；但创始人谈市场时同样可能带出受 NDA 约束的内容（如某客户合同里的续约条款），去身份后认不出是谁、内容本身仍不可外传。与 LP / Partner 证词统一（1.7） |
| 基金层过滤 | 剔除 GS 自有基金的具体信息与 LP 身份（[LP 保密]，1.7）——三类证词共用一个提示词（6.8（P5）），过滤统一后随之加上（本方案）；创始人会上很少谈及基金层，对本类型证词基本无实际影响 |
| 匿名化 | 按 1.5 剥离清单，两版都做；去逐字化（LLM + n-gram） |

判据示例：「垂直 SaaS 的企业买家近来把安全审查前置到试用阶段」保留；「我们的大客户把安全审查前置了，所以我们的销售周期拉长了一个季度」剔除——后者讲的是自己的客户与数据，同行可据此反推。

**存储与可见**：与 LP / Partner 共用同一套证词库与两版结构（3.4）——匿名版 + 署名版，正文相同、只差首行。署名版来源行的角色为 `Founder`，组织与姓名取该创始人在 Cheat Sheet 中会议当日生效的版本；专长标签同样按会议日期回溯。可见范围同 2.2 专家证词行。

与 Cross-Company **不互斥**（3.4）：同一段话两边的标准都满足时，两边都产出。

**提取方式**：由 6.8（P5）独立调用完成，与本类型其余提示词并行；仅当专家创始人名单非空时调用。各调用属同一次加工任务、读同一份转录快照（6.1）。

### 3.3 1b 与 Portfolio KB 提取规则

需求路由表本类型 1b 与 Portfolio KB 均为「组合（基金）级别摘要」，本类型只产出**基金层**一层，只进管理端。

**基金层**

- **内容**：组合（基金）级别的摘要——募资进度、基金整体回报、LP 结构与关切（组合级别摘要见需求路由表，细项为本方案）
- **归属**：**不建基金实体**。归属 = 机构（租户 / organization）层面，每场会一条；配合 Summary Records 详情的 **Portfolio 标记**（多选、默认不选、非必选，仅为标记、**不作任何权限依据**，9.5），供管理员识别所属基金；管理端知识库页另可在该条目上手动选基金标签（9.11.2，同样仅为标签）
- **可见**：对全体管理端可见，不按公司隔离
- **不写具体被投公司的事实**（本方案规则）：本类型不按公司拆分，涉及某家被投公司的内容不写，也不进任何知识库（见下）；基金层确需提及时改为泛指、剥掉对方标识。理由：基金层对全体管理端可见，而 PM 只能看自己管辖的公司——写进基金层等于绕过公司隔离
- 没有基金层内容 → 不产出

原设计「绑不到公司的内容直接丢弃」作废；原「是否引入 `ADMIN_PORTFOLIO` 业务类型」的设想改为机构层归属，落点见本节末「落库」。

### 3.4 专家证词提取规则

**抽取内容**：融资 / 市场 / 估值倍数。定义引自《会议内容提取规则》(4)：

| 类别 | 定义 |
|---|---|
| **融资**<br/>Fundraising | 会议中关于引入外部投资、融资轮次、估值预期、向投资人展示的业务进展及资金使用计划的讨论 |
| **市场**<br/>Market | 宏观市场环境、行业规模、竞争格局及外部需求变化 |
| **估值倍数**<br/>Multiples | 资本市场或可比同业公司常用的估值指标（P/E、P/S、EV/EBITDA 等），用于评估公司估值或定价基准 |

一句话概括：提炼适用于**融资路演与估值对标**的市场 / 行业信息。

> **保密过滤（Confidentiality Filter）**——需求 (4)：总结时**自动剔除保密、敏感或受 NDA 约束的信息**（核心财务数据、未公开的客户清单、敏感条款等）。与 [LP 保密] 叠加执行（3.6）。

> **「市场」与 Cross-Company 的关系**
>
> 证词的「市场」（需求 (4)）与 Cross-Company 的「市场趋势」（需求 (3)）主题重叠，都含市场行情、倍数。
>
> **不做互斥分流，接受重复**（2026-09-22 用户决定）：两条管道各自按本管道的标准独立抽取，同一段话同时满足两边标准时**两边都产出**。理由——
>
> - 两个库的**受众不同**：证词库管理端看得到来源、创始人只看匿名内容；Cross-Company 两端都是匿名内容。同一句话在两处的形态与可见范围本就不同，不构成真正的重复
> - 需求把两者**分成两块写**，本身就说明它们不是同一批内容的两种切法。互斥会把这层区分抹平
> - 这两个库的定位**尚未稳定**：Cross-Company 可能演化为「适用于所有公司的泛化描述」，专家证词也未必要求跨公司。在定位定下来之前，互斥规则很可能定错方向，而多产出一条的代价远小于漏产出
>
> 代价是已知的：Goldie 召回时同一观点可能带来源和不带来源各出现一次。**先接受**，等两个库的定位明确后再回来处理。

**随条目携带的标签**（需求证词表：「发言人角色标签、时间戳，以及登记册中对应会议日期的专长标签」）：

- **角色标签**：取 Cheat Sheet 角色枚举（5.2）。本类型实际值域为 `GS staff` / `LP` / `Strategic Partner` / `Exit Partner`；全局值域另因 2.5 含 `Founder`
- **专长标签**：按**会议日期**从 Cheat Sheet 有效期回溯当时生效的那一版，历史证词不因当事人当前登记变化而被重贴
- **时间戳**：该发言在会议中的时间点

**存两份**（因权限分层，且来源行直接存正文、不做召回后处理）：

| 版本 | 空间 | 正文 |
|---|---|---|
| 匿名版 | `(APP, EXPERT_TESTIMONY, organization_id)` | 匿名内容 + 首行**专长摘要**，固定格式 `Expertise: <expertise tag>`（当日无专长标签时不附首行） |
| 署名版 | `(ADMIN, EXPERT_TESTIMONY, organization_id)` | **同一份匿名内容** + 首行**署名**，固定格式 `Source: <Organization> <Role> <Name>`（来源行用英文，用户决定 2026-10-10） |

**两版的正文内容完全相同**（均已实体剥离），差别只在程序附加的那一行首行——LLM 只抽一次，不存在两版内容漂移的风险。两行取自同一份 Cheat Sheet 版本（会议当日生效的那一版）。

**匿名版首行只写专长、不写角色**：需求证词表的权限列写明「管理端可查看完整来源信息（提供者及其角色/组织）；Founder 仅能看到内容摘要与专长摘要；不向 Founder 展示任何来源信息」。角色属于来源信息，故匿名版只附专长标签。专长是这条证词可信度的来源（匿名不等于无出处），且不含姓名、组织、角色，不构成身份泄漏。

> 原设计匿名版首行为 `来源：某<专长标签>领域的<角色>`，依据是已删除的旧需求文档中「某医疗 IT 买家指出……」的措辞；现行需求明确角色不向 Founder 展示，按现行需求改。这一点对 2.5 的创始人证词尤其要紧——匿名版若写出「某……领域的创始人」，同行可据此缩小范围，正是需求要防的反推。

公司端只解匿名版空间、管理端只解署名版空间，**两端都不会重复命中同一条证词的两个版本**。例外是 Add to playbook：打开后 Playbook 第二路对管理端也返回匿名版，可能与知识库那路的署名版在同一轮各出现一次；本方案同一轮里两路命中同一中间表行时丢弃第二路那条（去重键为中间表行，证词两版视为同一行，9.11.6），去重后上述结论仍成立。

**管理端页面**：Goldie Base 的 Expert Testimony Tab 一条证词一行（两版正文相同，不分两行），PM / PGM / SA 可见；PGM / SA 另显示说话人姓名、组织、角色与专长标签，PM 都不显示（9.11.5）。公司端没有这个 Tab，只经 Goldie 召回匿名版。

> 署名**不能放 `chunk.metadata`**：`SearchHitDTO` 只透出 `chunk_id / content / entry_id / entry_title / space_id / space_name / similarity / match_type / uploaded_at / chunk_kind / file_id`，**metadata 不在返回字段中**，管理端召回后拿不到。

**创始人端可召回的前提**：证词空间按 `organization_id` 键控，而创始人登录时 `organizationId` 解析自 `r_organization_user`（`OrganizationRepository:47`），创始人不在该表中，**解出为 null**。需在 Java 登录处补兜底：查不到时用 `companyId` 走 `r_organization_company` 反查（`OrganizationRepository:50` 已有现成查询）。

**检索侧**：`knowledge_base_tool` 公司端分支需多解一个证词空间；**调高 top_k**，具体召回效果在工具内优化。

> 已知行为：`_normalize_and_merge`（`factory.py:289-317`）按 `business_type` 分组做 min-max 归一，**每组内最高分恒归一为 1.0**。证词自成一组，因此即使本轮提问与证词无关，组内最相关的一条也会以满分参与全局排序、挤占公司文档名额。已接受此行为，后续在工具层优化。

**机密性**：[去身份] + [LP 保密] + [保密过滤]；交易事实不进证词（详见 3.6）。

**专家候选**：同 2.3，规则见 1.11。

### 3.5 Cross-Company 提取规则

按 2.3 的四类会议统一规则执行（需求路由表本类型为「同上」），由 6.9（P6）抽取。从**原文**提取（与证词并列，两条独立管道、各自独立调用，均在同一次加工任务内完成）。落 `(APP, CROSS_COMPANY, organization_id)` 空间。

**口径变化**：原「只抽市场趋势」作废，与其余三类会议一样抽四类（市场趋势、商业趋势、战略决议闭环、全公司视角），经可迁移判据过滤后剩多少算多少（用户决定 2026-10-10）。四道过滤 [去身份] + [在途隔离] + [保密过滤] + [LP 保密] 原本就是本类型的口径，现推广到四类会议（2.3）。

**本类型的附加剥离**（用户决定 2026-10-10）：LP 会议是基金与 LP 信息最集中的场合，四类统一的 [LP 保密]（只剔除 GS 自有基金的具体信息与 LP 身份）不够，本类型的 Cross-Company 另做两项剥离：

| 剥离 | 范围 | 处理 |
|---|---|---|
| **GS 自有基金的相关内容** | GS 自己的基金（识别方式同 1.7）：募资（进度、目标规模、关账）、业绩（IRR / TVPI / DPI、整体回报）、条款（管理费、carry、存续期与延期、关键人条款）、LP 出资（承诺、续投、追加、份额转让）、资本调用与分配、基金策略与组合构建（配置节奏、储备金、组合整体表现） | 一条内容夹带基金相关部分时删去该部分，删后仍满足可迁移判据的保留，否则整条不输出。**改写成泛指也不保留**：跨公司内容的读者是 GS 被投公司的创始人，「某支基金已投出六成」一看就知道说的是 GS |
| **LP 身份信息** | 全部 LP，**含本场到会的 LP**（统一规则只剥身份，这里连可定位的描述、出资关系也剥）：机构名与人名；LP 类型、地区、规模等组合起来可定位的描述（如「某州教师养老金」）；与 GS 的出资关系（出资额、从哪一期开始出资）；其内部配置决策与投委会安排 | LP 一律写成泛称（an institutional LP / LPs）；剥后仍可能定位到某个 LP 的整条不输出 |

- **边界**：行业层面的 LP 行为趋势（如「LP 普遍在降低对早期基金的配置」）既不指向 GS 的基金、也不指向某个 LP，剥掉身份后可作为市场趋势保留（本方案解读，待确认：10.2 #39）
- **机械层兜底不变**：到会 LP 的姓名与机构在参会人与注册表中，机械层按 1.5 精确剥离；「可定位的描述组合」「GS 自有基金的相关内容」没有固定词形，靠 LLM 层
- **剥下来的内容不丢**：GS 自有基金的相关内容与 LP 的关切本就落基金层 1b（3.3、6.7（P4））
- 交易事实与在途交易信息照旧不进 Cross-Company；本类型不按公司拆分，它们也不落 1b，只留原始转录（3.3、3.6）。需求「所有进行中的交易信息永不放出，只放该公司 1b」在本类型按「不放出」理解（10.2 #49）
- 提示词侧：P6 只在本类型多拼一段「LP 会议附加剥离要求」（6.9（P6）），其余三类不拼

**须管理员审核后发出**（需求 I.2；用户决定 2026-10-10）：Authorize 默认不勾，审核放行后才投影到跨公司空间（9.6.4）。编辑入口只有 Summary Records 的 Content Routing Matrix 一处（9.6.3）。

**一份匿名版即可**——管理端回溯来源走**会议管理页**（PGM / SA 在 Summary Records 详情的 Content Routing Matrix 里，每条跨公司内容都挂在所属会议下，9.6），或 Goldie Base 的 Cross company content Tab（审核放行后，每条带会议名称与元数据，PM / PGM / SA 只读，9.11.4），都不经 Goldie；Goldie 链路上两端看到的都是匿名版。回溯时从 `ff_meeting` / `ff_meeting_sentence` 按 `meeting_id` 查，不经过 RAG。

与专家证词的关系见 3.4：**不做互斥**，本管道按自己的标准独立抽取，与证词内容重叠时两边都产出。

### 3.6 机密性

本类型适用的机密性规则：

| 标记 | 规则 | 出处 | 适用去向 |
|---|---|---|---|
| **[交易敏感]** | 具体交易事实（被兜售 / 估值 / 买方 / 价格 / 时间表）不进证词与 Cross-Company；本类型不按公司拆分，也不落 1b，只留原始转录（3.3） | 需求路由表、证词表「同样适用……交易敏感规则」；不落 1b 为用户决定 2026-10-10 | 证词、Cross-Company 一律不进 |
| **[在途隔离]** | 所有进行中的交易信息永不放出、只放该公司 1b：正在跟进、尚未落地的商业项目、谈判细节、竞标数据隔离，不得混入趋势总结。本类型没有公司层 1b，按「不放出」执行（3.3） | 需求路由表（四类会议统一，2.3）；需求 (3) Live-deal Quarantined | Cross-Company |
| **[保密过滤]** | 剔除保密、敏感、受 NDA 约束的信息（核心财务数据、未公开客户清单、敏感条款） | 需求 (4)，挂在证词下；Cross-Company 为本方案加严（2026-09-22 确认；现四类会议统一，2.3） | 证词、Cross-Company |
| **[LP 保密]** | 剥除 GS 自有基金的具体信息与 LP 身份（行业趋势保留，1.7）；本类型的 Cross-Company 扩为剥离 GS 自有基金的全部相关内容与全部 LP 身份信息（含到会 LP，3.5） | 本方案规则；本类型附加剥离为用户决定 2026-10-10 | 证词、Cross-Company；对 1b 是保全规则（3.3） |
| **[去身份]** | 按剥离清单剥离（1.5） | 需求 I.2 | 证词两版、Cross-Company |

- **[LP 保密] 的理由**：LP 身份与基金运作属于 GS 与 LP 之间的机密关系，不应经证词或 Cross-Company 流到创始人端
- 证词与 Cross-Company 是**两条独立管道**，[LP 保密] 与 [保密过滤] **各执行一遍**，不得假设对方已做
- 命中的内容**在写入阶段就不产出**到对应去向，不是存入后按角色隐藏；GS 自有基金信息与 LP 身份的去处是基金层 1b，交易事实在本类型不落任何去向、只留原始转录（3.3）
- **[保密过滤] 扩展到 Cross-Company 的理由**：跨公司库对全租户创始人可见，NDA 内容漏进这里比漏进证词库后果更重。四类会议的 Cross-Company 统一执行（2.3），提示词落在 6.3 共用片段「敏感过滤要求」，P5、P6 都拼接
- Cross-Company 另有管理员审核一道（3.5），但审核是兜底，不替代上述写入阶段的过滤

> 本类型调用 P1、P4、P5、P6、P7（复用矩阵见 6.2），P1 只做质量判断、不做公司识别（不按公司拆分，3.3）：基金层 1b 见 6.7（P4），证词见 6.8（P5），跨公司见 6.9（P6），专家推测见 6.10（P7）。

### 4.3 1b 与 Portfolio KB 提取规则

**归属方式**：本类型参会人全是 GS 人员、映射不到在营公司，公司归属只能靠**正文提及**识别（6.4（P1））→ 仅 `high` 采纳 → 一场会 N 家公司产出 N 条 → `company_id` 必填。**本类型没有基金层**（需求路由表本类型为「涉及具体公司的摘要」），绑不到任何公司的内容不入 1b——可迁移的部分按 4.4 进 Cross-Company。

**公司提及识别策略**（GS 内部与 GS → Partner 共用，5.4；原写在 3.3 的 LP 公司层下，GS → LP 不按公司拆分后移到此处）：由会议上下文推断，**仅 `high` 才采纳**；`low` 不采纳，连同 evidence 留在识别记录里，管理员可在 Company 字段手动补（9.5.3），不阻断本场其余内容的提取。别名表列为可选优化项。

> 错误代价不对称：漏识别只是该公司 1b 少一条内容（静默）；**错识别会让 A 公司的交易事实进入 B 公司的 1b**，而 Portfolio Manager 只能看自己管辖的公司，这构成跨边界泄漏。故宁可漏不可错。
>
> 系统现状：**不存在「按名称匹配公司」的能力**，需新建。（按邮箱域名反查公司的能力同样没有，但公司归属已改走完整邮箱匹配，不再需要它——见 1.9。）

**抽取范围：只抽结论性内容**，不抽过程。

| 抽 | 不抽 |
|---|---|
| GS 对该公司的判断与评估 | 讨论过程、谁说了什么 |
| 决定采取的动作 | 争论与分歧本身 |
| 风险评估结论 | 未形成结论的发散讨论 |
| 资源投入决定 | |
| 具体交易事实（[交易敏感]，只能落这里，需求路由表「只放该公司 1b」） | |

> 理由：1b 是「管理端记忆」，供 Goldie 推理时调用，需要的是结论而非过程。GS 内部会可能整场都在聊同一家公司，若整场抽取，1b 体量会失控且信噪比很差。
>
> 代价：无法追溯「当初为什么这么决定」。需要追溯时走 `ff_meeting` 原文。

**具体抽取细节（结论的粒度、如何判定「已形成结论」）**：判定规则见 6.6（P3）的纪要写法。

**1b 与 Portfolio KB 的关系**：同一批内容，1b 为 ≤150 个英文单词的摘要；Portfolio KB 为 markdown 文档，管理员可打开、编辑，附原始转录链接、不复制原文（本方案）。去逐字化 ✅；不做实体剥离与敏感过滤（1.4）。

**落库**：每家命中公司一条 ADMIN 端条目（摘要 = 1b，正文 = Portfolio KB markdown），落 KB-ADMIN `(ADMIN, ADMIN_COMPANY, organization_id)`，**`company_id` 必填**——它是公司隔离与召回过滤的唯一依据，不填则召不回。登记、文件、摘要同 2.4。

### 4.4 Cross-Company 提取规则

按 2.3 的四类会议统一规则执行（需求路由表本类型为「同上」），由 6.9（P6）抽取。落 `(APP, CROSS_COMPANY, organization_id)` 空间。

**口径变化**：原「只抽战略决议闭环、全公司视角（需求 (2)）」作废，与其余三类会议一样抽四类，市场趋势、商业趋势（需求 (3)）也抽；经可迁移判据过滤后剩多少算多少（用户决定 2026-10-10）。过滤由原 [去身份] + [在途隔离] 扩为 [去身份] + [在途隔离] + [保密过滤] + [LP 保密]，后两项为本方案加严（2.3）。

**本类型的侧重**：

- **在途交易**：原「本方案加严」的说法取消——需求把「所有进行中的交易信息永不放出，只放该公司 1b」写进四类会议共用的一格，已直接覆盖本类型。本类型仍最需要留意：GS 内部会恰恰是最可能密集讨论在途交易的场合，讨论某笔交易得出的决议只落该公司 1b（4.3），不得抽成「战略决议闭环」匿名主题、经 Cross-Company 被其他公司创始人感知
- **结论与可迁移内容分流**：与某家公司有关的结论落该公司 1b（4.3）；Cross-Company 只收脱离这家公司仍成立的部分，某家公司自己的战略决议过不了判据就不产出
- **[LP 保密] 新增后的去向**：GS 内部会谈到的 GS 自有基金信息与 LP 身份不再进 Cross-Company（行业层面的募资趋势照常可进，1.7）；本类型没有基金层（4.3），这部分不落任何去向，需要时走 `ff_meeting` 原文

> **关于「全公司视角」的口径更正（2026-09-21）**：本文档此前判定 MVP 不抽，理由是 EPIC 无定义、且它属跨多家组合公司的**聚合**而非单场**提取**。《会议内容提取规则》给出定义后，两条理由均不成立——
>
> - 定义已明确；
> - 「跨部门、跨业务线」指的是 **GS 机构内部的部门与业务线**，不是跨组合公司。因此它是单场 GS 内部会议上不同业务板块的人当场发表的全局看法，**单场提取即可得到，不需要周期性聚合任务**。
>
> 现改为**抽取**。

**须管理员审核后发出**（需求 I.2；用户决定 2026-10-10）：Authorize 默认不勾，审核放行后才投影到跨公司空间（9.6.4）。

> 本类型调用 P1、P3、P6（复用矩阵见 6.2）：1b 见 6.6（P3），跨公司见 6.9（P6）。

## 五、GS → 战略伙伴 / 退出伙伴（合并）

### 5.0 「合并」的含义

原设计是两个独立类型——`Strategic Partner`（商业合作方：渠道、技术伙伴、联合销售）与 `Exit Partner`（退出交易相关方：买方 PE、投行、并购顾问）。《AI Meeting Type》将两者合并为 `GS → Partner` 一类：「两者无需区分，统一为一类」。

**下游从严，现有现行出处**。旧需求曾写「下游按更保守的 Exit Partner 处理」，该句删除后，「对每场 Partner 会议都做在途隔离」一度失去出处。现行《会议内容提取规则》路由表已直接写明：

- Cross-Company：GS → Founder 一格写「**所有进行中的交易信息永不放出，只放该公司 1b**」，Partner 行为「同上」——这已是四类会议的统一规则（2.3），不再是本类型独有
- 1b：Partner 行「涉及具体公司退出的摘要（**敏感，默认保留，进入待分配**）」

即从严处理由需求直接规定，不再依赖设计推论。

误判代价不对称原是从严的理由：把 Exit 会当成 Strategic 会 → 隔离放松 → 交易信息流入 Cross-Company。现在在途隔离四类会议统一，Exit / Strategic 之分不再影响 Cross-Company；合并后本类型独有的从严只剩 1b 与 Portfolio KB 默认扣留。

合并落成三条规则：判定不区分、只看角色（5.1）；证词范围取并集（5 类，5.6）；1b 与 Portfolio KB 默认扣留（5.4）。Cross-Company 按四类会议统一规则（2.3、5.5），不因合并另设口径。

### 5.1 判定条件

GS 方 ≥ 1（口径同 2.1），**且**无参会人属于公司方（否则归 GS → Founder），**且**非全员 GS（否则归 GS 内部），**且**存在参会人的 Cheat Sheet **角色** ∈ {`Strategic Partner`, `Exit Partner`}。

**只看角色**。需求触发规则写作「参与人命中注册表中 Strategic 或 Exit Partner」；专长标签已改为 5 个证词领域（5.2），不再含 Strategic / Exit Partner，这句只能指角色。原「角色 + 专长标签都命中」的口径及其「已澄清」结论作废。

**匹配顺序**：先邮箱、未命中再姓名，规则见 1.8（LG 系统内 → Cheat Sheet，完全匹配，重名进 Pending）；按会议日期取 Cheat Sheet 当时生效的版本。

与 LP 一样**强依赖 Cheat Sheet**，未收录即判不出，进 Pending Assignment。

### 5.2 注册表字段口径（本类型引入，全局适用）

以《Cheat Sheet》为准。

| 字段 | 性质 | 取值 | 回答什么 | 用途 |
|---|---|---|---|---|
| **角色**<br/>Role | 受控枚举，**固定 6 项** | `LP`、`Strategic Partner`、`Exit Partner`、`Founder`、`GS staff`、`Other` | 这人是什么身份 | 会议类型判定 + 证词署名版的角色 |
| **专长标签**<br/>Expertise tags | 受控列表，下拉多选 | 初始 5 项：`Multiples`、`Buyer behavior`、`Exit trends`、`Software usage`、`Commercial buying behavior`；在 Cheat Sheet 的标签下拉中手动新增，**已被使用过的不可删**（9.8） | 这人擅长什么领域 | 专家判定与专家推测归类（1.11）+ 证词专长标签。**不参与会议类型判定** |
| **专业领域**<br/>Area of expertise | 自由文本 | — | 这人专长的背景说明 | 仅作上下文描述，**不参与路由** |
| **有效期**<br/>Validity period | From 必填 / To 可空（空 = present） | — | 上述各项在会议当日的版本 | 历史证词不因当事人当前登记变化而被重贴 |

**「外部人员角色」「角色类型」「证词发言人角色标签」三者是同一个字段**，取值即上表角色枚举。

**`Founder` 与 `GS staff` 是有意保留的，不是笔误**——《Cheat Sheet》明确说明：「并不是所有的 GS 人员和 Founder 人员都有 LG 的账户，所以 Cheat sheet 保留这两个角色标签」。判定时 `GS staff` 计入 GS 方、`Founder` 计入公司方（2.1）。

**有效期与版本规则**：

- 编辑弹窗用两个日历选择器，From 必填、To 可不选（代表无限制，显示为 `present`）
- **会议发生时间落在的区间若与其他历史记录重合，以最后一个该时间的记录为准**（《AI Meeting Type》同口径：该日身份重复取最新一条）
- 超过 90 天未复核的条目标记 `Needs review`
- 姓名是唯一识别符，发布后不可更改
- History 页按生效日期排序，每个版本保留完整快照：Name、Email(s)、Role、Organization、Expertise tags、Area of expertise、有效期

**证词角色标签的实际值域**：证词来自 GS → LP、GS → Partner 两类会议，以及 GS → Founder 中被标记为专家的创始人（2.5），因此实际出现的是——

```
GS staff、LP、Strategic Partner、Exit Partner、Founder
```

其中 `Founder` 只来自 2.5，`Other` 不会出现。角色只写在署名版来源行；匿名版只附专长、不写角色（3.4）。

### 5.4 1b 与 Portfolio KB 提取规则

**归属方式与 GS 内部一致**（4.3）：按正文提及识别公司（6.4（P1））→ 仅 `high` 采纳 → 一场会 N 家公司产出 N 条 → `company_id` 必填。**本类型没有基金层**（需求为「涉及具体公司退出的摘要」），绑不到公司的内容不入 1b。

**抽取内容**（以退出为主轴；「退出」借用需求术语 (1) 的定义，用户决定 2026-10-10）：

1. **退出就绪度**（Exit-Readiness，术语 (1)）——公司为 IPO、并购、融资或业务剥离所做的准备：合规性、资产清晰度、运营成熟度、风险筛查；以及任何关于"公司是否满足资本市场或投资人要求的标准"的讨论

4. 退出计划与时间表
5. 买方 / 伙伴对该公司的意向与估值判断

术语 (1) 在需求 09-21 版挂在「GS → 董事会 / 创始人」的 1b「退出准备 / 战略方面的摘要」上，董事会类型取消后现行路由表已无处引用；它讲的正是退出准备，借来作本类型「涉及具体公司退出的摘要」的定义（第十章 #50）。

- 改判 / 重跑后的授权状态按 9.9.5：改判前已放行的沿用，否则保持扣留

> **口径沿革**：旧路由矩阵该格曾为「涉及公司，按敏感处理**？**」；后改为「涉及具体公司退出的内容摘要」，范围收窄为退出相关；现行需求补上「敏感，默认保留，进入待分配」——问号所指的「敏感处理」有了明确含义：默认扣留、人工放行。

### 5.5 Cross-Company 提取规则

**口径变化**：

### 5.6 专家证词提取规则

**与 LP 共用同一套证词库**（本方案）——同一个 `EXPERT_TESTIMONY` 空间，同样匿名版 / 署名版两份（3.4），仅抽取主题不同。

**抽取内容（5 类）**：

| 类别 | 定义 | 细化（本方案） |

| **商业采购行为**<br/>Commercial Buying Behavior | 企业级客户在购买、评估、决策软件及服务时的习惯与流程。如：采购决策链条变长、更看重 ROI、对安全合规要求提高、倾向集成化方案（需求 (5)） | 采购流程、预算负责人、销售周期、ACV、价格敏感度 |

五类与专长标签的初始 5 项一一对应（5.2）。

**标签来源**：

- **角色标签** → 取 Cheat Sheet 角色枚举（5.2），本类型实际值域为 `GS staff` / `LP` / `Strategic Partner` / `Exit Partner`；只写在署名版来源行
- **专长标签** → 按会议日期经有效期回溯当时版本
- **时间戳** → 该发言在会议中的时间点

**机密性**：[去身份] + [LP 保密] + [保密过滤]；交易事实不进证词。

**[保密过滤] 为本方案加严**（用户决定 2026-10-10）：需求 (4) 只把它挂在 LP 证词下。但 Partner 是买方 PE、投行、并购顾问，证词五类里的买方行为、估值倍数、退出趋势恰好是他们手上最常受 NDA 约束的信息——例如「某大型买方私下透露今年并购预算砍了一半」，匿名、不涉及具体交易，去身份与「交易事实不进证词」都拦不住，只有保密过滤拦得住。加上本管道不做在途隔离，它是四条证词 / 跨公司管道里过滤最少的一条。

**专家候选**：同 2.3，规则见 1.11。

### 5.7 机密性

| 标记 | 本类型口径 | 适用去向 |
|---|---|---|
| **[交易敏感]** | 交易事实只落该公司 1b | 证词、Cross-Company 一律不进 |
| **[在途隔离]** | 所有进行中的交易信息永不放出，只放该公司 1b；四类会议统一，原本类型独有的「每场适用」口径取消（2.3、5.5） | Cross-Company |
| **[LP 保密]** | 剥除 GS 自有基金的具体信息与 LP 身份，行业趋势保留（1.7）；两条管道**各执行一遍**（本方案规则） | 证词、Cross-Company |
| **[保密过滤]** | 需求 (4) 只挂在 LP 证词下；本方案扩展到 Cross-Company（四类会议统一，理由见 2.3、3.6）与证词（用户决定 2026-10-10，理由见 5.6） | 证词、Cross-Company |
| **[去身份]** | 按剥离清单剥离（1.5） | 证词两版、Cross-Company |
| **默认扣留** | Authorize 默认不勾，经 Pending Assignment 放行（5.4） | 1b、Portfolio KB |
| **审核后发出** | Authorize 默认不勾，审核放行后才投影（5.5） | Cross-Company |

- 命中的内容**在写入阶段就不产出**到对应去向，不是存入后按角色隐藏

> 本类型调用 P1、P3、P5、P6、P7（复用矩阵见 6.2）：1b 见 6.6（P3），证词见 6.8（P5），跨公司见 6.9（P6），专家推测见 6.10（P7）。

### 9.2 Configuration

**连接方式只支持 API Key**（《Fireflies Configuration》明确）。MCP / OAuth 仅为调研记录，不实现。

#### 9.2.1 归属层级

**一个租户一条连接**，不按公司、不按项目。

Fireflies 的 API key 代表一个 **workspace**，`transcripts` 返回的是整个工作区可见的全部会议（实测该 key 的 `num_transcripts` 为 1，列表却返回 43 场）。工作区是 GS 侧的，不属于任何一家被投公司——会议拉进来之后才按内容分派到各公司。因此连接的归属只能是 `organization_id`，与证词 / Cross-Company 空间的键控层级一致。

#### 9.2.2 能否复用 `third_party_connection`

**不复用，新建 `ff_connection`。** 四条理由，前两条是硬的：

| # | 问题 | 说明 |
|---|---|---|
| 1 | **归属维度不兼容** | 该表 `company_id` / `project_id` 均 `NOT NULL`，唯一键是 `(project_id, tool_id)`。Fireflies 是租户级，两列都没有对应值。要么填假值，要么把两列改成可空——后者会放松现有 6 个 DI 工具的约束 |
| 2 | **凭据明文存储** | `access_token TEXT`，全表无加密，现有 DI 工具沿用此做法。Fireflies key 能读取整个工作区的会议转录（含在途交易、机密商业内容），不能继承这个做法 |
| 3 | **业务域与字段不对口** | 该表服务 DI 域，`tool_id` 外键指向 `d_tool`（DI 工具字典），`repository` / `host_url` / `target_addresses` / `aws_access_key_id` / `business_scope` 全是 DI 专用列。Fireflies 只用得上 `access_token` 一列，其余全空 |
| 4 | **同步状态语义不同** | `sync_status` 是 ETL 三态（`underway` / `succeed` / `failure`），描述的是"这一次跑得怎么样"；Configuration 页要的是连接四态（见 9.2.4），描述的是"这条连接现在健不健康"。两者不是一回事，硬套会让其中一个语义失真 |

> 若将来要统一管理所有第三方凭据，正确做法是抽一张与业务域无关的凭据表（凭据 + 归属 + 加密），而不是把租户级连接塞进按项目键控的 DI 表。这属于独立的技术改造，不在本次范围。

#### 9.2.3 数据模型 `ff_connection`

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `organization_id` | 租户，**唯一**——一个租户一条 |
| `api_key_cipher` | **加密后**的 API key，密文存储 |
| `account_email` / `account_name` | key 持有者账号，来自 `user` 查询，供页面展示「connected as …」 |
| `connection_status` | 四态，见 9.2.4 |
| `last_success_sync_at` | 最近一次**成功完成**的拉取时间 |
| `last_attempt_at` / `last_error` | 最近一次尝试的时间与失败原因，供排障 |
| `consecutive_failures` | 连续失败次数，达阈值转 `Disconnected` |
| `created_by` / `created_at` / `updated_by` / `updated_at` | 审计 |

**密钥存储**：密文入库，只在服务端解密后使用；**任何接口都不回传 key 原文或密文**。参考系统内 QuickBooks 集成的现状（token 明文存两张表并明文上传 S3、client secret 提交进部署配置），此处不复制该做法。

#### 9.2.4 连接状态

| 状态 | 判定 | 展示 |
|---|---|---|
| `Unconnected` | 从未配置过 key | 灰点 |
| `Connected` | 最近一次调用成功 | 绿点 |
| `Failed` | 有 key，但调用返回鉴权错误（key 错 / 被吊销） | 红点 |
| `Disconnected` | 曾连通，此后连续 N 次调用失败（N 走配置） | 灰点 |

**状态转移**

```
Unconnected --Link 成功--> Connected
Connected   --鉴权错误--> Failed
Connected   --连续 N 次非鉴权失败--> Disconnected
Failed / Disconnected --Link 成功 或 Sync 成功--> Connected
```

`Failed` 与 `Disconnected` 分开，是因为处置动作不同：前者要换 key，后者多半是对方服务波动、等一等或手动 Sync 即可。合并成一个状态会让用户不知道该做什么。

#### 9.2.5 Link

原型上输入框**常驻且始终为空**，已连接时也一样——**页面从不回显 key，连掩码都不显示**。换 key 就是输入新的再点一次 Link，覆盖旧的。没有断开按钮（原型无此入口，本设计也不加）。

流程：

1. 输入框非空时 `Link` 按钮激活
2. 点击后先调 Fireflies `user` 查询做校验——它是最轻的一个接口，同时能拿到 `email` / `name`，一次调用解决"key 对不对"和"连的是哪个账号"两件事
3. 校验失败：直接报错，**不落库**；页面状态不变（避免存下一个用不了的 key）
4. 校验通过：加密落库，写 `account_email` / `account_name`，状态置 `Connected`，`consecutive_failures` 清零

#### 9.2.6 Sync

**Sync now**：手动触发一次增量拉取，与每日定时拉取走**同一入口**，不走两套逻辑。

- 拉取进行中按钮置灰，避免并发拉取产生重复
- 拉取范围按 `last_success_sync_at` 增量取
- **首次连接回溯最近 14 天**（默认值，走配置可调）。全量回溯会在首次连接时灌进整个工作区的历史会议，量不可控且多数已无处理价值

**Last sync 只记成功**：失败的那次不覆盖 `last_success_sync_at`，否则页面显示"刚刚同步过"而实际数据是旧的，比不显示更糟。失败信息进 `last_attempt_at` / `last_error`，需要时在状态区提示。

**定时拉取**：每日一次，服务端排程，页面上没有频率配置项（需求与原型均未提供）。

#### 9.2.7 接口

| 接口 | 作用 | 返回要点 |
|---|---|---|
| `GET /api/web/fireflies/connection` | 页面加载 | 状态、`account_email`、`last_success_sync_at`、是否正在同步。**不含 key** |
| `POST /api/web/fireflies/connection/link` | 提交 key | 校验 + 落库；失败返回具体原因（鉴权失败 / 网络不可达） |
| `POST /api/web/fireflies/connection/sync` | 手动同步 | 立即返回，拉取异步执行；重复调用直接拒绝 |

**权限**：仅管理端，且限本租户的 Portfolio Group Manager / Super Admin。连接是租户级资产，普通管理端账号不应能改。

### 9.3 Raw Data

该页是**原始逐字稿 + 元数据**的留存与查看入口，保证底层数据完整可追溯（需求原话）。它只对**原文**负责——派生产物一律归 Summary Records。

#### 9.3.1 拉取

**一次调用拉 50 场，含正文。** `transcripts` 与 `transcript` 在 Fireflies 是同一个 `Transcript` 类型，`sentences` 可以直接写进列表查询——实测一次 `transcripts(limit:50)` 返回 43 场会议、19,261 条句子。**不要**做成「列表 + 逐场详情」两段式，那会把每 50 场的配额消耗从 1 次变成 51 次。

| 项 | 取值 |
|---|---|
| 增量依据 | `fromDate` / `toDate`（ISO 8601），起点取 `last_success_sync_at` |
| 分页 | `limit` **上限 50**，配合 `skip` |
| 首次回溯 | 最近 14 天（9.2.6） |
| 触发 | 每日定时 + 手动 Sync now，同一入口 |

**幂等**：以 Fireflies 的 `id` 为业务唯一键。重复拉到同一场会时 upsert 元信息、逐句先删后插——Fireflies 侧的转录可能被重新处理，句子数会变，增量比对不如整场重写简单可靠。

#### 9.3.4 `Invalid` 标记

需求：「当会议非常短且没有实质内容时，判定为无效会议，显示灰色 `Invalid` 标签」。这句话里其实是**两个判据、两个时机**：

| 来源 | 时机 | 判据 | 是否调 LLM |
|---|---|---|---|
| 程序硬门槛 | 拉取后、识别前 | 时长 / 句数低于阈值（环境变量，见 6.4） | 否 |
| LLM 质量门槛 | 识别时：参会人识别与类型判定之后、内容提取之前（6.4（P1）） | `quality.usable = false`——通篇寒暄、设备调试、无实质讨论 | 是 |

**判定顺序：`Invalid` 优先于 `Pending`。** 硬门槛先跑，判为 `Invalid` 的会议**不再做参会人识别、不调 LLM**。这样既省掉无意义的调用，也让状态自洽——不会出现"一场两句话的会因为参会人认不出而挂在 Pending 队列里等人工"。LLM 质量门槛同样在识别阶段判出：P1 对每场会都跑（含参会人认不出的会），`usable = false` 即置 `Invalid`（覆盖已判出的类型或 `Pending`）、不调用其余提示词，Pending 队列里因此不会出现空会。

**`Invalid` 不删数据**：原文照常入库、照常可在本页查看。需求要的是"完整可追溯"，`Invalid` 只是一个不再往下走的标记。

**Pending 会议在本页不带任何标记**——该页只回答"原文能不能用"，`Pending` 是派生侧的状态，归 Summary Records。

#### 9.3.5 原始逐字稿详情

每行末尾 `Raw transcript` 链接进入详情页，展示带时间戳与说话人的完整逐字稿。

> 面包屑与页面命名原型尚未统一（列表 `Fireflies Raw Data`、详情 `Fireflies Meeting Data`），**待定，不在本轮范围**。

**页头**：标题 + 一行元信息 `Raw verbatim transcript — 9,420 words · unclassified and unmodified · captured <ingested_at>`。「unclassified and unmodified」是固定文案，用于向管理员明示本页与其余界面的区别。

**信息卡**：Date / Time / Duration / Participants，与列表同源。

**正文**：

- 用 `text`（清洗后）；`raw_text` 存着备查，页面不展示两版
- 时间戳按 `start_time` 折算成 **`[hh:mm:ss]`**（原型为 `[00:00:04]`），不用 `mm:ss`——超过一小时的会议会歧义
- 说话人用 `speaker_name`（ASR 识别值，可能与注册表姓名不一致，此处**照原样显示**，不做替换——这里是原文界面，替换会破坏可追溯性）
- 页尾 `End of transcript · N words total · stored in the admin library prior to any classification or routing.`

> **长会议的渲染**：448 句/场是均值，长会议更多，一次性渲染会卡。**接口要支持按 `idx` 区间取**，不要做成只有全量一种取法。
>
> 但这里是**加载批次，不是分页**——原型为整篇连续滚动，转录要能从头读到尾、能 Ctrl+F 查找，切成一页页翻会同时破坏这两件事。故不套用列表的 10 条，改为滚动到底续加载，每批数百句量级，具体值在开发设计按渲染性能定。

> **这是系统内唯一保留原文措辞的界面。** 其余所有经 Goldie 触达的产物都已去逐字化（1.4）。因此访问只给需求列明的两类人：管理端 PGM / Super Admin，以及**参加了该会议的创始人本人**（9.3.6）。
>
> 后者与《会议内容提取规则》I「任何面向 Founder 的界面绝不呈现原始逐字表述」并不矛盾：那条保证针对的是派生产物——防止 A 的原话经 Goldie 流到别人眼前；参会人本人读自己在场的那场会的原文，不构成新的暴露。《Fireflies Raw Data》「创始人本人可查看自已参加的会议」同此口径。

#### 9.3.6 权限与留存

以《Fireflies Raw Data》权限条为准（原「仅管理端、创始人端无任何入口」作废）：

| 谁 | 能看什么 |
|---|---|
| **PGM / Super Admin** | 本租户全部会议（按 `organization_id` 隔离） |
| **Portfolio Manager** | **不可见**——需求权限只列 PGM、Super Admin。菜单不出，接口同样拒绝，不靠隐藏入口 |
| **创始人本人**（公司端） | 仅自己参加过的会议的列表项与逐字稿详情 |
| 同公司未参会的公司端用户（含 Company Admin） | 不可见（需求「未参加的本公司人员不可见」） |

**"本人参加过"的判定**（本方案口径）：该用户的账号邮箱出现在该场会的 `participants` 中——与 1.9 平台用户的完整邮箱匹配同口径。**姓名回退匹配（1.8）命中的不算**：姓名匹配的误判落在原文上，就是让一个人读到别人的完整转录，代价与收益不对称。Cheat Sheet 中的 `Founder`（未使用 LG 平台的人）没有账号，自然无从查看。

**公司端入口**：需求只给了权限，没给入口（页面放在公司端何处、以什么形态出现），未决，见第十章。本章只定鉴权口径，接口按上表预留。

**留存**：

- **永久留存**（需求 Mode A），不随派生产物的重算而删除
- 幂等重写只影响逐句与元信息，`ingested_at` 保留**首次**入库时间

#### 9.4.2 Status 与阻断关系

**只有两态**（需求已删除 `Flagged`）：

| 状态 | 含义 | 是否阻断 |

- 改判本身不触发提取，点 Start Extraction 才触发；重算范围见 9.9

**每个公司下方展示识别依据**，即需求《AI Meeting Type 自动映射标准》要的「管理端应支持追溯"这场会议为何关联到此公司"」。识别链见 1.9，**只展示命中的那一条依据与命中的具体值**，不展示整条链：

| 命中方式 | 依据文案 |
|---|---|
| 参会人完整邮箱 → LG 公司端用户（该公司的 Team 记录） | `Matched via <email> (LG company user)` |
| 正文提及（6.4（P1），仅高置信） | `Inferred from transcript — <evidence>` |
| 人工指定 | `Assigned by <user> on <date>` |

> **没有"邮箱域名"这一条**。原型与需求示例写的是 `Matched via email domain northwindlabs.io`，但公司关联走的是**完整邮箱**匹配公司 Team 记录，域名只用于判定 GS 方、不参与公司归属（1.9）。页面按实际命中的完整邮箱展示。
>
> 手动添加的公司也要写依据，否则时间一长分不清哪些是 AI 判的、哪些是人改的——而这两者的可信度不同。

**下拉的候选范围**：LG 系统内的公司，可搜索。

> **待澄清**：原型只画了一个 `Company` 占位下拉，看不出候选范围。需求写的是「可多选，可搜索下拉添加公司」（即全量 LG 公司）；另一种口径是只列「LLM 识别出来且在 LG 系统内存在」的公司。两者差别很大——后者管理员**无法补充 AI 没识别出的公司**，而 Pending 会议往往正需要人工补。本设计按**全量可搜索**实现，若要收窄需明确（9.12）。

#### 9.5.4 Portfolio 标记

需求《Fireflies Summary Records》新增：**可多选，默认不选，非必选；选择后激活下方 Confirm 按钮；仅为标记，不作为任何权限划分依据。**

| 项 | 口径 |
|---|---|
| 候选 | 本租户在 LG 中已有的 Portfolio（`company_group`，按 `organization_id` 圈定），可搜索 |
| 用途 | 给会议打"涉及哪个基金组合"的标记——即 GS → LP 基金层内容的**基金标签**。本租户的 Portfolio 名称列表同时作为本机构的基金清单，供基金层过滤识别 GS 自己的基金（1.7）。基金层内容归属机构（租户）层面、不建基金实体（1.1 / 3.3），Portfolio 标记是它在会议级的基金维度；条目级另有管理端知识库页的基金标签（9.11.2） |
| 不做什么 | **不参与检索过滤、不参与可见范围、不参与路由**。LG 里的 Portfolio 平时是权限单位（`r_portfolio_user`），需求特意写明此处"不作权限依据"，即不能拿它去收窄谁看得到这场会的内容 |
| 存储 | 存在会议级，一场会一份；机构层条目经会议溯源取得，**改标记不重提取、不重投影** |
| 生效 | 选择变动 → 激活 `Confirm & Apply Routing`；不激活 Start Extraction |

所有会议类型都可打标记（需求未限定类型），但只有 LP 基金层内容会用到它——知识库页该行没手动选基金标签时，以它作显示回退（9.11.2）。

#### 9.5.5 参会人

**展示格式**：胶囊标签 `姓名 · 组织 (角色)`，按身份着色。

| 身份 | 示例 | 样式 |
|---|---|---|
| GS 方 | `Sarah Chen · GS (PM)` | 蓝 |
| 创始人 | `James Wilson · TechVision (Founder)` | 橙 |
| 外部伙伴 / LP | `Jane Doe · Acme Capital (Strategic Partner)` | 紫 |
| 未识别 | `Michael Brown · — (Unidentified)` | 灰 + 红点 |

两种附加徽标，叠加在上述样式上：

| 徽标 | 何时出现 |
|---|---|
| `Expert` | 该人按会议日期生效的注册表版本带专长标签，即**已标记为专家**（1.11）。需求「补充识别以显示其专家标志」 |
| `Possible expert` | 专家推测命中、尚未处理（9.5.6） |

**点击行为按来源分**：

| 来源 | 举例 | 点击 |
|---|---|---|
| **LG 平台内用户**（按完整邮箱匹配到管理端 / 公司端账号） | `Sarah Chen · GS (PM)` | **无弹框**（需求明确）——姓名、组织、角色以平台账号为准。**唯一例外**：带 `Possible expert` 时弹专家确认框（9.5.6） |
| **外部人员**（注册表已登记，或未识别，或身份来自 HubSpot / LLM 推断） | `Jane Doe · Acme Capital (Strategic Partner)`、`Michael Brown · — (Unidentified)` | 可编辑，改动回流 Cheat Sheet |

**外部人员的两个弹框，按"是否已在注册表"选一个**：

| | `Edit external party` | `Assign new external party` |
|---|---|---|
| 触发 | 点注册表中已有的人 | 点带红点的 `Unidentified`，或点身份来自 HubSpot / LLM 推断、尚未入册的人 |
| **Name** | **置灰只读** | **可编辑** |
| 已带入的值 | 注册表中按会议日期生效的那一版 | 已知的部分（邮箱，及推断出的姓名 / 组织 / 角色） |

**Name 的可编辑性差异是有意的**：姓名是注册表的唯一识别符（《Cheat Sheet》明确，确认发布后不可改）。已在册的人改名等于换了一个人；而尚未入册的人此刻还没有姓名这个识别符，ASR 或推断给的姓名可能是昵称或听错的拼写（`Mike` / `Michael`、`Speaker 2`），**必须允许订正后再入册**。需求写的「已识别者 Name 只读」按"已在册"理解——HubSpot / LLM 推断得到的身份没进过注册表，同样适用订正逻辑。

**弹框字段**：Name、Email(s)（可多个）、Organization、Role、Expertise tags、Area of expertise、Validity period（From 必填，To 留空表示 open-ended）——**与 Cheat Sheet 页的新增 / 编辑弹框完全一致**（9.7.4）。需求这里列的字段没有 Area of expertise，但两处写的是同一张表，用同一个表单，不为一个字段维护两套。

> 原型在这两个弹框里多画了一个 `Company` 下拉，**是画错了**，不实现。外部人员的所属机构只有 `Organization` 一个自由文本字段，注册表不持有 `company_id`。

#### 9.5.6 专家推测

需求《Fireflies Summary Records》与《AI Meeting Type 自动映射标准》「特殊说明 · 专家推测」新增。识别侧规则（谁会被推测、怎么归类）见 1.11，本节只管页面。

**候选从哪来**：专家推测提示词 6.10（P7）对 GS → 创始人 / GS → LP / GS → Partner 三类会议各跑一次，列出每人符合四条判据的实质性主张，程序按 ≥ 2 条的门槛决定是否给出候选（发言人、标签、主张与依据）；GS 内部全员为 GS 人员，不调用。以下三类人在调用前就被排除、回来后再挡一次，**不显示徽标**：

| 过滤 | 依据 |
|---|---|
| GS 人员（管理端用户、注册表 `GS staff`、三域名） | 需求「GS 员工永远不会被标记」 |
| 已标记为专家的人（按会议日期生效版本带专长标签） | 推测只针对"尚未被标记为专家"的人 |
| 拒绝名单中的邮箱 | 需求「拒绝记录将保存该人员的 email」 |

候选只在提取之后才有——`Pending`（待识别）会议没跑提取，不会出现 `Possible expert`。

**点击姓名 → 专家确认框**：

| 区块 | 内容 |
|---|---|
| 推测依据 | 按标签列出的实质性主张及其依据（转述、不引原句，带时间点） |
| 登记字段 | 同 9.5.5 弹框：Name、Email(s)、Organization、Role、Expertise tags（预选建议的标签，可改）、Area of expertise、Validity period（**From 默认带会议日期**） |
| 按钮 | `Confirm`（同意）/ `Decline`（拒绝）/ 关闭（不处理，徽标保留） |

Name 是否可改沿用 9.5.5：已在册的人只读（同意 = 给他追加一个带标签的新版本），未在册的人可订正后入册。

| 动作 | 结果 |
|---|---|
| **同意** | 写入 Cheat Sheet（来源 `From FF Summary Records`，9.5.7），此人从生效日起即为专家；徽标变为 `Expert` |
| **拒绝** | 记录该人邮箱进**拒绝名单**，此后任何会议都不再对他推测；徽标消失 |

**LG 平台用户被确认为专家**：典型是 GS → 创始人会上的创始人。同意时同样在注册表建一条（角色 `Founder`，姓名取平台账号姓名），**只为承载专长标签**；他的身份分类仍以平台账号为准——识别链对平台用户命中即止（1.9），注册表这一条只在补充识别（1.11）时被查到。这改变了"平台用户在注册表里没有副本"的旧口径；与《Cheat Sheet》「Founder 指未使用 LG 平台的人」的口径如何对齐，未决，见第十章。

**拒绝名单**：按 `(organization_id, email)` 记录，附操作人、时间、来源会议。没有撤销入口——误拒的补救是直接在 Cheat Sheet 给此人加专长标签，加了就是专家，不再需要推测。

**不回溯本场**：同意后本场会议不自动重提取。GS → 创始人会议要补出这位创始人的专家证词（2.5），管理员点 Start Extraction（同意算作一次参会人改动，按钮激活）。From 默认带会议日期，正是为了让这次重提取能按会议日期回溯到新登记的标签。

#### 9.5.7 回填注册表

在本页登记的人**自动写入 Cheat Sheet**（《会议内容提取规则》III / 《Summary Records》「保存后回流到 cheat sheet」），并带 `From FF Summary Records` 来源标识。三个入口都走这里：`Assign new external party`、`Edit external party`、专家确认框的 `Confirm`。

- 新登记 → 注册表新增一条，`Updated by` 记为系统导入并标明来源会议（原型 History 页的 `System (FF-09 import)` 即此）
- 编辑已有条目 → 按 Cheat Sheet 的版本规则产生新版本（见 9.7）
- **姓名冲突**：新建时填入的姓名若已存在于注册表，不能直接新建——姓名是唯一识别符。此时应提示"该姓名已登记"，并让管理员选择关联到已有条目还是改名

弹框 `Confirm` 即写注册表，**不随页面的 `Discard Changes` 撤销**——注册表是独立的追加写版本表，写错了再编辑一版即可（9.7.2）。

#### 9.5.8 保存与生效

| 改动 | 怎么提交 | 何时生效 |
|---|---|---|
| 类型、公司 | 改完点 Start Extraction 生成草稿 → `Confirm & Apply Routing` | 应用时替换当前生效版本 |
| 参会人登记 / 专家确认与拒绝 | 弹框内 `Confirm` / `Decline` | 立即写注册表 / 拒绝名单；对本场会议的影响要经 Start Extraction（9.9.3） |
| Portfolio 标记 | `Confirm & Apply Routing` | 应用时 |
| 矩阵内容、授权 | 见 9.6.5 | |

- 参会人登记影响注册表与**此后**会议的识别，**不自动回溯已提取的会议**（含本场，本场要管理员点 Start Extraction）
- 所有动作写审计日志（9.10）

### 9.6 Content Routing Matrix

矩阵三列：`Content`（内容块，可编辑）、`Visible to`（谁能看到这一行）、`Authorize`（勾选则授权）。

#### 9.6.1 矩阵从哪来

**矩阵是提取结果的呈现**，不是独立数据。提取产物先落中间表（9.6.4），按去向铺成矩阵的各行。

- `Pending` 会议**初次进来时矩阵为空**——识别做了、内容没提取。人工补齐必填项、点 Start Extraction 后才出现
- 页头的类型、公司、参会人改动后，点 Start Extraction 重新提取；产物先作为**草稿**展示在矩阵里，`Confirm & Apply Routing` 才生效，`Discard Changes` 丢弃
- 改判类型会让矩阵**整体重来**，因为不同类型的产物形态不同（见 9.6.2）
- 公司增删只影响**按公司分行**的那些行（1b / Portfolio KB），Cross-Company 与证词行不变（9.9.1）

#### 9.6.2 行的构成：按会议类型

**一行 = 一个内容块 + 它的全部去向。** 同一份内容落多个去向时合并成一行展示（需求原话：「不同角色看到的如果是同样的内容，则合并展示」）。

#### 9.6.3 Content 编辑

**整格文本框编辑**：一个多行 `textarea`，保存的是一整段字符串。改动后该格出现琥珀高亮边框。

需求写的「每行一条 bullet」是**排版约定，不是数据结构**——系统不认识"条"这个概念，不做逐条的增删改与排序。据此：

- 各提示词的文本输出**保持字符串**（6.5（P2）~ 6.9（P6）），提示词侧要求 LLM **一行一条**输出即可
- 中间表该列是一个文本字段
- 审计的 `CONTENT_EDIT` 记改前改后的整段文本，不记"哪一条被改了"

摘要行的上限与生成时一致：**≤150 个英文单词**（1.3），超长不允许保存。

**行内 `Save` / `Cancel`**（需求）：`Save` 只保存该行，`Cancel` 还原该行。

**保存时重跑清洗**（需求「点击保存，应再次走去逐字化和脱敏流程，完成后再保存」）。原「编辑后不做任何处理」作废。本方案口径：

| 重跑什么 | 说明 |
|---|---|
| **n-gram 近逐字剔除** | 管理员改过的文本与原转录比对，命中即剔除（阈值同提取时，1.4） |
| **该去向适用的实体剥离** | 只对 Cross-Company 与证词两版做（1.4 / 1.5）；1a / 1b / Founder KB / Portfolio KB 不剥离，与提取时一致 |
| **不重跑 LLM 改写** | 人工改的就是想要的措辞，LLM 重写会把它覆盖掉；需求要的"去逐字化"由机械层承担即可——管理员手打的内容本就不是原话，n-gram 是兜住"从原文粘贴回来"的那种情况 |

**两步提交**：

1. `Save` → 服务端对该行跑上述清洗，**不落库**，返回清洗后文本与命中明细（被剔除的片段、被剥离替换的实体）
2. 无命中 → 直接落库；有命中 → 回显清洗结果，管理员确认后落库，或继续改

落库后：该行属于**当前生效版本**且已授权 → 立即重投影（9.6.4）；属于**草稿**（Start Extraction 之后、Confirm 之前）→ 只改草稿，随 Confirm 一起生效；未授权 → 只改中间表。

证词行改正文时，两版共用的正文一起更新，各自的来源行由程序重新附加（6.11）。

**编辑入口只有本矩阵一处**：跨公司内容同样在这里修订，没有第二个编辑入口（9.1）。Goldie Base 的 Cross company content Tab 只读（Add to playbook 开关除外，9.11.6）。

#### 9.6.4 Authorize 与落库时机

**`Authorize` 是放行开关**：勾选后 `Visible to` 里的角色才看得到这一行，未勾选的内容不进 RAG 空间、Goldie 召不回。

**提取产物一律先落中间表**，知识库条目是其中已授权那部分的投影：

```
提取完成 ──→ 中间表（每场会、每个去向一条，始终保留）
              │
              ├─ 已授权 ──→ 投影：生成 markdown 文件 + 写知识库条目 + 登记（1.1 / 1.3），Goldie 可召回
              └─ 未授权 ──→ 只在中间表，管理端可见、Goldie 不可见
```

中间表不只是"授权前的暂存区"——它是矩阵的**可编辑正本**，知识库条目由它派生。这样 `Content` 的编辑、授权的开关、以及重算，都只操作一份数据。Start Extraction 的产物在中间表里以**草稿**存在，与当前生效版本并存，`Confirm & Apply Routing` 时切换（9.6.5）。

中间表行另带 `in_playbook` 标记（Add to playbook，默认关，9.11.6）：Goldie Base 两个新 Tab 的开关写这里，Playbook 召回按它实时读；它不影响授权与投影。

**证词行的结构化字段**（本方案）：中间表的证词行除正文外另存**发言人**（speaker_ref → 参会人、姓名、组织、角色）与**回溯后的专长标签**（按会议日期，3.4）；正文与来源行分开存——内容列只存正文（9.6.3 的文本字段），来源行由程序按这些字段生成，矩阵里只读显示、投影时拼进正文首行（3.4、6.11）。Goldie Base 的 Expert Testimony Tab 按这些字段显示说话人与专长标签（9.11.5）。

**初始授权状态**

| 场景 | 初始状态 |
|---|---|
| 识别齐全、自动提取完成 | **默认已勾选**，落中间表的同时投影——与需求「`Passed` = AI 已路由全部内容」一致。**两类例外**见下两行 |
| └ 所有类型的 **Cross-Company** 行 | **默认不勾**——Cross company 内容需管理员审核后发出（需求 I.2；用户决定 2026-10-10）；会议因此置 `Pending`（待审核，1.10） |
| └ GS → Partner 的 **1b / Portfolio KB** 行 | **默认不勾**——「敏感，默认保留，进入待分配」（《会议内容提取规则》路由表；Portfolio KB 随 1b 一并扣留为本方案）；会议因此置 `Pending`（待审核，1.10） |
| `Pending` 会议人工指定后首次提取 | **全部默认不勾**，只落中间表（本方案：首次提取 Authorize 默认不勾 → Confirm & Apply Routing） |
| 已提取过的会议再次 Start Extraction | 见 9.9.5 |

"经 Pending Assignment 放行"落到页面上，就是管理员在本矩阵勾选 `Authorize` 并 `Confirm & Apply Routing`——与 Pending 会议人工处理走同一个页面、同一套按钮，不另建审核队列。

**投影操作**

知识库条目**没有内容更新接口**（只有 retry 与 DELETE），改内容 = 软删旧条目 + 写新条目（重新向量化、重新生成 markdown 文件），即 1.6 的幂等机制。

| 操作 | 中间表 | 知识库条目 |
|---|---|---|
| 编辑 `Content`（`Save`） | 更新 | 该行已授权且已生效 → 软删旧条目 + 写新条目；未授权或属草稿 → 不动 |
| 勾选 `Authorize`（应用后） | 置为已授权 | 按中间表当前内容写入 |
| 取消勾选（应用后） | 置为未授权，**内容保留** | 软删（幂等规则同 1.6），Goldie 立即召不回 |

取消勾选不删中间表的内容——撤回是可逆的，重新勾上应当恢复原样，而不是要求管理员重新提取或重打一遍。

已被用户从知识库页下载到本地的旧文件不追（1.3）。

> **为什么不能"先写入、再按标记隐藏"**：现有检索侧除 `company_id` 外不做行级过滤，`SearchHitDTO` 也不透出 metadata（见 3.4 批注），召回后拿不到授权标志。未授权只能靠"不写入"来保证。
>
> 这是对 6.11「后置程序步骤」中落库一步的结构性改动——落库从提取的收尾动作，变成**中间表 → 知识库**的一次投影，投影范围由授权状态决定。

#### 9.6.5 保存与生效

两类改动，两种提交方式并存（需求《Summary Records》写的是按行 Save / Cancel，《会议内容提取规则》III 与原型写的是页面级 `Discard Changes` / `Confirm & Apply Routing`——两者管的不是同一件事）：

| 改动 | 提交方式 | 理由 |
|---|---|---|
| **Content 编辑** | 行内 `Save` / `Cancel`，只作用于该行 | 内容是逐行审的，保存时还要逐行回显清洗结果（9.6.3），放到整页一起交会让回显无从对应 |
| **路由级改动**：类型 / 公司 / 参会人改动后的草稿、`Authorize` 勾选、Portfolio 标记 | 页面级 `Confirm & Apply Routing` / `Discard Changes` | 授权与改判往往要一起判断（看完新提取的内容才决定放不放行），按行提交会让管理员在部分授权、部分未授权的中间态里来回切换，也更难写一条完整的审计记录 |

**`Confirm & Apply Routing`**：把本页所有路由级改动一次性应用——有草稿则用草稿替换当前生效版本（旧版本的条目软删，草稿中已授权的行投影），再应用授权勾选与 Portfolio 标记。`Pending` 会议应用后转 `Passed`。

**`Discard Changes`**：还原到上次应用后的状态——丢弃草稿（含草稿行上已 Save 的内容）、还原页头的类型与公司、还原未应用的勾选与标记。**不撤销**：当前生效行上已 Save 的内容（已落库并投影）、注册表写入与专家确认 / 拒绝（9.5.7）。

**按钮状态**：

| 情形 | `Confirm & Apply Routing` | `Discard Changes` |
|---|---|---|
| 无未应用的路由级改动 | 置灰 | 置灰（原型即此） |
| 只改了授权勾选 / Portfolio 标记，或 GS → LP 的公司增删 | 激活 | 激活 |
| 改了类型、公司（不含 GS → LP：其 Company 不参与路由，9.5.3）或参会人，但还没跑 Start Extraction，或提取进行中 | **置灰**——页头与矩阵内容不一致时不能应用 | 激活 |
| 草稿已生成 | 激活 | 激活 |
| 类型改为 `Unknown` | 激活——无需提取，应用即打回 Pending（9.9.2） | 激活 |

有行处于编辑未保存状态时点 `Confirm & Apply Routing`，先提示该行 `Save` 或 `Cancel`。

每次应用写审计记录（9.10），含改了哪些行、授权了哪些去向；行内 `Save` 各写一条 `CONTENT_EDIT`。

### 9.7 Cheat Sheet

平台外人员的登记表。字段口径见 **5.2**（角色 6 项枚举、专长标签、有效期规则），"专家"的判定见 **1.11**（按会议日期生效的版本带至少一个专长标签即为专家），本节只管页面、数据模型与版本机制。

#### 9.7.1 数据模型：单表存版本

**一张表，一行一个版本快照**，不设单独的主体表。

**`ff_registry_party`**

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `organization_id` | 租户 |
| `name` | **唯一识别符**，确认发布后不可改。`(organization_id, name)` 即标识一个人，同一人的多个版本共用同一值 |
| `emails` | 可多个 |
| `organization` | 外部机构名，自由文本 |
| `role` | 6 项枚举之一（5.2）：LP、Strategic Partner、Exit Partner、Founder、GS staff、Other |
| `expertise_tags` | 多选，存**标签文本**而非字典外键；非空即为专家（1.11） |
| `area_of_expertise` | 专业领域，自由文本，**仅作上下文描述，不参与路由**（《Cheat Sheet》） |
| `valid_from` / `valid_to` | From 必填，To 可空（空 = `present`） |
| `source` | `MANUAL`（Cheat Sheet 页新增）/ `FF_SUMMARY_RECORDS`（审核会议时登记，含专家确认） |
| `updated_by` | 操作人；系统导入时记为 `System (<会议 id> import)` |
| `updated_at` | 写入时间，**重合裁决与复核时间的依据** |

**每次 Confirm 追加一行**，不修改旧行。

| 要什么 | 怎么取 |
|---|---|
| 列表的当前状态 | 按 `(organization_id, name)` 分组，取 `updated_at` 最大的一行 |
| History | 该 `(organization_id, name)` 的全部行 |
| 某场会议当时的登记 | 见 9.7.2 的回溯算法 |
| 最近复核时间 | **最新一行的 `updated_at`**——不单设 `last_reviewed_at` 字段 |

> **为什么不用主体 + 版本两张表**：主体表唯一能承载的是姓名和复核时间。姓名不可改，本身就是稳定标识，不需要代理 id；复核时间又与最新版本的 `updated_at` 等价。拆两张表只换来一个多余的 join，还要维护两处的一致性。
>
> 代价是姓名唯一性**没法用数据库约束表达**（同一人本就有多行），新建时的重名校验落在应用层。这是可接受的——`Assign new external party` 那条路径本来也要做同样的校验（9.5.7）。

> **为什么姓名能当唯一识别符**：原型的 History 里，同一个人换过邮箱（`m.whitfield@meridian-health.com` → `eleanor@northbridge-cap.com`）、换过机构（Meridian Health Group → Northbridge Capital）、换过角色（Strategic Partner → LP）。邮箱和机构都会变，能把这些版本串成一个人的只有姓名。

> **被引用时也用姓名**：证词的发言人、参会人识别结果指向的都是 `(organization_id, name)`，不需要代理 id。

**`Founder` / `GS staff` 角色**：指未使用 LG 平台的创始人与 GS 人员（《Cheat Sheet》「并不是所有的 GS 人员和 Founder 人员都有 LG 的账户」）。唯一的例外是专家确认：LG 平台用户被确认为专家时也会在这里建一条，只为承载专长标签（9.5.6）。

#### 9.7.2 有效期与版本裁决

**允许重合，重合时取最新的那条**——按版本的 `updated_at` 取最晚写入的，**不是**按 `valid_from` 最晚的（《Cheat Sheet》「以最后一个此时间的记录为准」；《AI Meeting Type 自动映射标准》「该日此人员身份有重复，则使用最新一条」）。

不自动闭合上一版的有效期。管理员填什么就是什么，重合由裁决规则兜底。

这条规则顺带解决了**订正**：改错别字、补一个漏填的邮箱时，**有效期保持不变**再提交即可——新版本与旧版本区间完全重合，但写入更晚，于是自然生效，旧版本留在 History 里可查。不需要为"订正"单设一种操作。

**按会议日期回溯的取值算法**（1.8 的姓名回退、1.9 的注册表匹配、1.11 的专家判定、6.11 的标签回溯用的都是它）：

```
取该 party 下满足 valid_from <= 会议日期 <= COALESCE(valid_to, 无穷) 的全部版本
 → 按 updated_at 降序取第一条
```

> ⚠️ **邮箱匹配也要走这套回溯，不能只用最新版本的邮箱。** 1.9 按完整邮箱匹配注册表，若只查最新版本，一个换过邮箱的人在**旧会议**里就匹配不上——原型那位 2023 年用的是 `m.whitfield@meridian-health.com`，而最新版本里根本没有这个地址。角色、专长标签、邮箱三者同源，回溯规则必须一致。

#### 9.7.3 列表

**顶部汇总条**：`N entries are overdue and flagged "needs review".`——原型有、需求没写，是整页唯一的主动提示。

**列**：Name、Email(s)、Organization、Role、Expertise tags、Validity period，行末 `History` / `Edit`。Area of expertise 不进列表（需求列表字段未含），在弹框与 History 中展示。

| 列 | 展示 |
|---|---|
| Name | 姓名；审核会议时导入的在下方加 `From FF Summary Records` 标签 |
| Email(s) | 多个**纵向堆叠全部展示**（原型如此），实在放不下再用省略号 |
| Role | 蓝色标签 |
| Expertise tags | 灰色小标签，多个换行展示 |
| Validity period | `Aug 2, 2026 – present`；逾期未复核的在下方加琥珀 `Needs review` 徽章 |

**搜索**：模糊匹配 Name、Email(s)、Organization、Expertise。Expertise 同时匹配专长标签与 Area of expertise——两者都在描述"这人懂什么"，搜的人不会区分。
**筛选**：按 Role。
**分页**：每页 10 条，同其余管理页面。

#### 9.7.4 新增与编辑

`Add external party` / `Edit`，两者字段相同，差别只在 Name：

| | Add | Edit |
|---|---|---|
| Name | 可填 | **置灰只读** |
| 其余字段 | 空 | 带入最新版本的值 |

**字段**：

| 字段 | 控件 |
|---|---|
| Name | 文本 |
| Email(s) | 可多个，支持 `+ Add another email` 与逐行 × |
| Organization | 文本 |
| Role | 下拉，6 项固定（5.2） |
| Expertise tags | 下拉多选，取值来自专长标签字典；**下拉内可直接新增标签**（9.8） |
| Area of expertise | 自由文本，选填；仅作描述，不参与路由 |
| Validity period | 两个日历选择器，From 必填 / To 可空 |

弹框内提示文案：`"From" is required. Leave "To" empty to show the period as open-ended.`

**Confirm 前弹二次确认**，告知姓名提交后不可编辑（需求明确）。

**姓名重复**：租户内已存在同名时不允许新建——姓名是唯一识别符。此时提示已登记，引导去 `Edit`。Summary Records 页的 `Assign new external party` 同此（9.5.7）。

#### 9.7.5 Needs review

最新一行的 `updated_at` 距今超过 90 天即标记。

**不单设"复核"按钮**——任何一次 `Edit` 提交即刷新它。复核的实质就是有人看过并确认，单独加一个"我看过了"的控件只会多一个没人点的按钮。

**"看过但无需修改"**：`Edit` 弹框什么都不改直接 `Confirm` 时，**原地更新最新一行的 `updated_at` 与 `updated_by`，不追加新行**。这样 History 里不会多出一条内容完全相同的噪音记录，而那行显示的更新时间恰好就是复核时间——语义是准的，确实有人在那天看过它。

#### 9.7.6 History

独立页面，不做行内展开。面包屑 `Fireflies / Cheat Sheet / Role History`，前两级可跳回。标题 `<姓名> — Role History`。

**每行一个完整快照**（以《Cheat Sheet》为准）：Name、Email(s)、Role、Organization、Expertise tags、Area of expertise、Validity period，外加 Updated by（含更新日期）。角色为蓝色标签，专长标签为灰色小标签。

**排序**：按 `valid_from` 倒序（原型如此）。同一生效日期有多行时（订正场景），再按 `updated_at` 倒序——与 9.7.2 的裁决口径一致，排在最上的就是当前生效的那条。

**`Updated by` 可以是系统**：由 Summary Records 审核时登记的版本（含专家确认），记为 `System (<会议 id> import)`，与人工操作区分。

### 9.8 专长标签维护

《Cheat Sheet》已不再提独立的 Expertise Tags 配置页：**标签是受控列表，在 Cheat Sheet 的 Expertise tags 下拉内维护**。数据上仍是一张标签字典表。

#### 9.8.1 取值与维护入口

**初始 5 项**（需求给定，原「取值清单待确认」关闭）：

```
Multiples、Buyer behavior、Exit trends、Software usage、Commercial buying behavior
```

即 GS → Partner 证词的五个领域（5.6）。租户开通时预置，存量租户由迁移脚本补齐。

**维护入口**：Cheat Sheet 新增 / 编辑弹框（及 Summary Records 页的同款弹框）的 Expertise tags 下拉——输入不存在的值时下拉末尾出现 `Add "<输入值>"`，确认即加入字典并选中；未被使用过的标签在下拉选项旁带删除入口。

**排序**：种子 5 项在前，新增的按添加顺序追加在末尾，不做字母序。

**标签用在哪**：

| 用途 | 说明 |
|---|---|
| 专家判定 | 按会议日期生效的版本带至少一个标签即为专家（1.11） |
| 专家证词来源行 | 匿名版首行 `Expertise: <expertise tag>`；署名版首行 `Source: <Organization> <Role> <Name>`（3.4；来源行用英文，用户决定 2026-10-10） |
| GS → 创始人专家证词的抽取主题 | 该创始人标签覆盖的领域（2.5） |
| 专家推测的归类范围 | LLM 把实质性主张按字典中的领域归类（1.11、6.10（P7）），新增的标签同样参与 |

**不再参与会议类型判定**：GS → Partner 只看角色（5.1），原「角色 + 专长标签都命中」作废。

#### 9.8.2 数据模型

**`ff_expertise_tag`**

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `organization_id` | 租户，标签按租户隔离 |
| `name` | 标签文本，**租户内唯一**（不区分大小写） |
| `is_seed` | 是否为预置的 5 项 |
| `sort_no` | 展示顺序，新增追加在末尾 |
| `created_by` / `created_at` | 审计 |

**物理删除，不设软删**：能删的只有从没被用过的标签（9.8.3），它不在任何快照、证词里出现过，删了不留痕迹也不会让任何历史显示出错。原设计的软删是为了"已用标签被删后历史照常显示"，这个场景已经不存在。

#### 9.8.3 增与删

**新增**：《Cheat Sheet》「可手动新增」；《AI Meeting Type 自动映射标准》「只有管理员可以添加新的类别」——能进 Cheat Sheet 的即为管理员（9.1）。租户内重名直接拒绝并提示，不做大小写敏感区分（`M&A` 与 `m&a` 视为同一个）。

**删除**：

| 标签 | 能否删除 | 依据 |
|---|---|---|
| 种子 5 项 | **不可删** | 《AI Meeting Type 自动映射标准》称其为「固定集合」；且它们与证词五类一一对应 |
| 已被使用过的标签 | **不可删** | 《Cheat Sheet》「已被使用过的标签不允许删除」 |
| 新增后从未被使用的标签 | 可删 | 加错了的补救 |

**"被使用过"** = 出现在 `ff_registry_party` 的**任一版本**中（含历史版本），不只看当前版本——历史版本照样被按会议日期回溯、照样出现在证词来源行里。

**不提供改名**，这是有意的：

> Cheat Sheet 的版本快照存的是标签**文本**而非字典外键（9.7.1）。若提供改名，管理员会预期历史登记跟着改，而实际不会——一个做不到用户预期的功能比没有更糟。新加的标签写错了，在被使用前删掉重加即可。

#### 9.8.4 已使用不可删（取代原「删除不级联」）

原设计允许删除已在用的标签、靠"删除不级联"保住历史显示。现行需求直接禁止删除已使用的标签，问题从根上消失：

- 快照里出现过的标签永远在字典里，新建 / 编辑时始终可选，历史版本的显示也不存在"字典里已经没有这个标签"的情况
- 证词的专长标签按会议日期回溯到某个版本（6.11），已生成证词的来源行不会凭空少掉一个标签

代价是过时的标签只能留着。这是需求的取舍，接受。

### 9.9 改判与路由重算

#### 9.9.1 三种触发源

Review 页上能改的三样东西，改完点 Start Extraction 触发重算，范围各不相同：

| 改了什么 | 影响什么 | 重算范围 |
|---|---|---|
| **会议类型** | 产物形态整体改变 | 见 9.9.2 |
| **公司增删**（类型不变） | 只影响**按公司分行**的那些行 | 新增公司 → GS → 创始人：为该公司写同一份摘要 / 正文（内容不裁剪，2.3），不调 LLM；GS 内部 / GS → Partner：为该公司补跑 1b / Portfolio KB 抽取（6.6（P3））。移除公司 → 软删该公司的行。GS → LP 不按公司拆分（3.3），公司增删不影响任何行、不触发提取。Cross-Company 与证词不受影响 |
| **参会人**（登记、改登记、专家确认，类型不变） | 可能改变类型判定（9.9.3）；类型不变时，影响证词来源行、GS → 创始人是否产出专家证词（2.5） | **整场重跑**——逐项增量换来的只是少跑一次提取，规则却要多出一套 |

多项同时改动时取最大的范围。

`Portfolio` 标记不在此列——它不触发提取（9.5.4）。

#### 9.9.2 按类型改判的重算范围

| 改判 | 重算 |
|---|---|
| `Pending` → 指定类型 | **首次提取**，按新类型跑完整流程；授权全部默认不勾（9.6.4） |
| 任意类型之间 | **整场重跑**——产物形态完全不同，无法增量 |
| 任意类型 → `Unknown` | 无需提取。`Confirm & Apply Routing` 后打回 `Pending`：软删全部产物（中间表与知识库条目均软删，保留可追溯），停止路由 |

原「GS → 创始人 ⇄ Board Call 只补跑 1b」一行随 Board Call 类型取消删除。

**公司识别不重跑**。它在识别阶段独立完成（6.4（P1）），改判不影响其结果。例外：P1 此前跳过了公司识别——GS → 创始人且会上有公司端用户，或 GS → LP（均为用户决定 2026-10-10）——改判为 GS 内部 / GS → Partner 后，提取前补跑一次 P1，只取正文提及的公司。

#### 9.9.3 参会人登记引起的连锁

在 Review 页登记一个此前未识别的外部人，可能把会议类型**从 `Pending` 变成可判定**——比如认出一位 LP，会议就该归 GS → LP。

因此参会人登记提交后：

1. 重跑类型判定（程序，按 2.1 / 3.1 / 4.1 / 5.1 的规则）
2. 判得出 → 提示管理员"已可判定为 X 类型，是否应用"，**不静默改判**；应用即把下拉设为该类型，仍要点 Start Extraction
3. 仍判不出 → 保持 `Pending`

不静默改判，是因为管理员在 Review 页的下拉里可能已经手动指定了类型；程序重判的结果与之冲突时，应当由人裁决。

#### 9.9.4 重跑与人工编辑的冲突

同一行的 `content` 有两个写入方——LLM（提取与重跑）和管理员（矩阵编辑）。重跑会盖掉人工改过的内容，而需求又要求「更改 content → 新的内容将被应用」。

**定：重跑直接覆盖**（在 `Confirm & Apply Routing` 应用草稿时）。改判即以新类型的 AI 产出为准，人工编辑视为对**旧口径**的临时修正，随旧口径一并作废。不弹确认框、不做"保留人工条目"的例外。

理由：改判意味着这场会的**口径整体换了**——从 LP 改判为 GS 内部后，那条 LP 口径的证词本来就不该存在，保留它只会产生自相矛盾的混合结果。而系统无法区分"对旧口径的修正"（该丢）与"对内容本身的修正"（该留），一律按前者处理，规则简单可预期。

**应用前看得到**：重跑产物先是草稿，管理员在矩阵里看过新内容才会去点 `Confirm & Apply Routing`，覆盖不会在他不知情时发生。

**人工编辑不会凭空消失**：每次编辑都写了 `CONTENT_EDIT` 审计（9.10.2，含改前改后全文），需要时可从审计日志查回并重新填入。

**范围提醒**：

| 重算 | 被覆盖的范围 |
|---|---|
| 类型改判 / 参会人改动（整场重跑） | 全部行，含已放行后改过措辞的 Cross-Company 行 |
| 新增公司 | 只新增该公司的行，已有行的人工编辑安全 |
| 公司移除后再加回 | 该公司的行——加回来的是 AI 原文，不是人工改过的版本 |

#### 9.9.5 重跑后的授权状态

重跑产出新内容，应用时旧的知识库条目先软删。草稿各行的勾选初值：

| 情形 | 授权初值 |
|---|---|
| 该去向重跑前已授权 | **沿用已授权**——**Cross-Company 与 GS → Partner 的 1b / Portfolio KB 除外** |
| Cross-Company、GS → Partner 的 1b / Portfolio KB | **一律不勾**——审核放行针对的是具体内容，内容换了就要重审 |
| 该去向重跑前未授权 | 保持未授权 |
| 重跑后**新出现**的去向 | 未授权，需人工放行 |
| `Pending` 首次提取 | 全部不勾（9.6.4） |

沿用而非清空，与 `Passed` 默认已勾选是同一条口径（9.6.4）——AI 产出默认可路由，人工审核只在需求要求或 AI 没把握的场合才是必经步骤。

这只是草稿的初值：重跑由管理员发起、必须经 `Confirm & Apply Routing` 才生效，应用前管理员可以逐行调整。原设计"改判后的新内容未经人眼即对创始人可见、由 Flagged 兜底"的顾虑随之消失。

**Add to playbook 标记**：重新提取产生的新行 `in_playbook` 重置为关，需管理员在 Goldie Base 重新打开——同「内容换了就要重审」（9.11.6）。

### 9.10 审计日志

需求要求「所有路由决策与覆写操作都会写入审计日志」。系统现状是 `LogAspect` 的 `@Component` 已被注释、无任何写入（见第七章）。

#### 9.10.1 不复用 LogAspect

`LogAspect` 是被停用的通用切面，恢复它要评估全站所有接口的影响，且它记的是**接口调用**，而这里要记的是**业务决策**——同一次 `Confirm & Apply Routing` 只有一次接口调用，但要记类型变化、重算范围、受影响的去向、授权变化好几件事。

新建 **`ff_audit_log`**，只服务 Fireflies 域。

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `organization_id` | 租户 |
| `event_type` | 见 9.10.2 |
| `meeting_id` | 关联会议；注册表类事件为空 |
| `target` | 受影响对象的标识（去向 + 公司、party 姓名、邮箱等） |
| `before` / `after` | 变更前后的值，JSON |
| `operator` | 操作人；自动决策记为 `System` |
| `created_at` | 时间 |

#### 9.10.2 事件清单

| 事件 | 触发时机 | 关键内容 |
|---|---|---|
| `IDENTIFY` | 识别阶段完成 | 参会人识别结果（每人命中识别链的哪一步）、补充识别查到的专家身份、公司归属与依据、质量判断（程序硬门槛结果、P1 的 `quality.usable` 与 `reason`；P1 最终失败则记失败并置 `Pending`，6.11）、判定出的类型 |
| `EXTRACT` | 内容提取结束（含整场作废） | 触发方式（自动 / Start Extraction）、会议类型、各提示词调用结果（成功 / 失败、重试次数）、各去向产出条数、专家候选（人、建议标签）；内容类提示词（P2~P6）任一最终失败 → 记本次提取作废、不落任何条目（管理员可 Start Extraction 重跑）；P7 失败 → 记专家候选缺失 |
| `TYPE_CHANGE` | 改判应用 | 原类型、新类型、重算范围、被覆盖的人工修改条数 |
| `COMPANY_CHANGE` | 公司增删应用 | 公司、动作、依据文案 |
| `PORTFOLIO_MARK` | Portfolio 标记应用 | 改前改后的 Portfolio |
| `CONTENT_EDIT` | 矩阵行内 `Save` | 去向、改前、管理员提交稿、清洗后定稿、清洗命中（n-gram 剔除的片段、实体剥离替换项） |
| `AUTHORIZE_CHANGE` | 勾选 / 取消勾选应用 | 去向、新状态 |
| `PLAYBOOK_TOGGLE` | Goldie Base 两个新 Tab 上的 Add to playbook 开关变化（即时生效，不经 `Confirm & Apply Routing`，9.11.6） | 操作人、中间表行 id（及其去向、所属会议）、开 / 关 |
| `REGISTRY_IMPORT` | 从 Review 页登记外部人 | party 姓名、来源会议 |
| `EXPERT_CONFIRM` | 同意专家推测 | party 姓名、确认的专长标签、LLM 理由、来源会议 |
| `EXPERT_DECLINE` | 拒绝专家推测 | 邮箱、LLM 理由、来源会议 |

一次 `Confirm & Apply Routing` 可能同时产生 `TYPE_CHANGE` / `COMPANY_CHANGE` / `PORTFOLIO_MARK` / `AUTHORIZE_CHANGE` 多条。

**自动决策（`IDENTIFY` / `EXTRACT`）必须记**，不能只记人工动作——Pending 审核时管理员要回答"AI 当初为什么这么判"，靠的就是 `IDENTIFY` 里那条命中步骤记录。9.5.3 页面上展示的识别依据，取的也是它。

**`CONTENT_EDIT` 记三段文本**：管理员提交的是一版、清洗后落库的可能是另一版。只记落库版，事后看不出清洗动过什么；只记提交版，又对不上 Goldie 实际召回的内容。

**注册表变更不进审计日志**：`ff_registry_party` 本身就是追加写的版本表（9.7.1），每行自带 `updated_by` / `updated_at`，History 页即其审计视图。再抄一份到审计日志只会两处不一致。`EXPERT_CONFIRM` 记的是**决策**（谁凭什么理由确认了哪个标签），不是注册表快照，两者不重复。拒绝名单同理，名单本身是功能数据，`EXPERT_DECLINE` 记决策。

**标签字典不进审计日志**：新增有 `created_by` / `created_at`；能删的只有从未被使用的标签，删了不影响任何历史。

#### 9.10.3 保留与查看

- **不随产物重算而删除**——重算会软删中间表与知识库条目的行，但审计记录必须留着，否则"这条内容当初是怎么来的"就断了
- 查看入口在管理端；MVP 可先不做页面，接口与数据先落地
- 按 `organization_id` 隔离
