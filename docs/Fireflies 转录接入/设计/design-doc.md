## 一、全局约定

以下约定对所有会议类型生效，各类型章节不再重复。

### 1.1 知识库空间与业务类型

沿用现有 RAG 的空间机制：`ai_rag_business_association` 以组合键 `(end_type, business_type, company_id | organization_id)` 唯一确定一个知识库空间，chatbot 检索时按身份解出可见的 `space_ids`。**隔离靠「谁能解出哪个空间」，不靠检索时的行级过滤。**

#### 空间清单

| 代号 | 组合键 | 粒度 | 隔离方式 | 谁能召回 | FF 写入 |
|---|---|---|---|---|---|
| **KB-APP** | `(APP, APP_COMPANY, company_id)` | 每公司一个 | 空间层 | 该公司创始人 + 管理端 | ✅ |
| **KB-ADMIN** | `(ADMIN, ADMIN_COMPANY, organization_id)` | **每组织一个（公司 id 隔离）** | **行级 `company_id`** | 仅管理端 | ✅ |
| **证词-匿名 / 证词-署名** | `(APP / ADMIN, EXPERT_TESTIMONY, organization_id)` | 每租户各一个 | 空间层 | 匿名版两端 / 署名版仅管理端 | ✅ |
| **跨公司** | `(APP, CROSS_COMPANY, organization_id)` | 每租户一个 | 空间层 | 创始人 + 管理端 | ✅ |

处理类型均为 `STANDARD`。**租户 = organization**（需求口径：一把 API key 归属一个租户）。

#### 按会议类型的产物归属

**类型一 · GS → 创始人**

| 产物 | 空间 | 份数 |
|---|---|---|
| 摘要 + 纪要（1a / 1b / Founder KB **共用一份**） | KB-APP | 每关联公司一条 |
| Cross-Company 洞察 | 跨公司 | 0~N 条 |

> 三个目的地共用一份，是因为矩阵给它们的都是「摘要」，内容相同；且管理端能召回 KB-APP，无需另写。

**类型二 · Board Call（手动改判后）**

| 产物 | 空间 | 份数 |
|---|---|---|
| 摘要（1a + Founder KB） | KB-APP | 每关联公司一条 |
| **退出准备 / 战略摘要（1b）** | **KB-ADMIN** | 每关联公司一条 |
| Cross-Company（带 care flag？） | 跨公司 | 0~N 条 |

> ⚠️ **本类型不能共用一份**：矩阵给 1a 的是「摘要」、给 1b 的是「退出准备/战略方面的摘要」，**内容不同**，必须分别产出、分落两个空间。

**类型三 · GS → LP**

| 产物 | 空间 | 份数 |
|---|---|---|
| 1b（按正文提及的公司拆分） | KB-ADMIN | 每命中公司一条 |
| 证词 · 匿名版 | 证词-匿名 | 0~N 条 |
| 证词 · 署名版 | 证词-署名 | 与匿名版一一对应 |
| Cross-Company 市场趋势 | 跨公司 | 0~N 条 |

**类型四 · GS 内部**

| 产物 | 空间 | 份数 |
|---|---|---|
| 1b（按正文提及的公司拆分，只抽结论） | KB-ADMIN | 每命中公司一条 |
| Cross-Company（战略-决议闭环、全公司视角） | 跨公司 | 0~N 条 |

**类型五 · GS → Partner**

| 产物 | 空间 | 份数 |
|---|---|---|
| 1b（按正文提及的公司拆分，退出相关） | KB-ADMIN | 每命中公司一条 |
| 证词 · 两版 | 证词-匿名 / 证词-署名 | 0~N 条 |
| Cross-Company 市场与商业趋势 | 跨公司 | 0~N 条 |

**关键事实**：管理端的检索范围已包含各可访问公司的 APP 空间（`knowledge_base_tool.py:127-135` 并入 `find_app_space_ids`），**反向不成立**——公司端只解出自己公司那一个 APP 空间。因此：

- 内容进 KB-APP 后管理端自动可见，**仅当 1a 与 1b 内容相同时才可共用一份**（只有类型一满足）
- 只允许管理端看到的内容写进 KB-ADMIN，即结构性对创始人不可见，**不需要额外加过滤**
- **KB-ADMIN 的公司隔离是行级的**（同一组织共用一个物理空间，靠条目上的 `company_id` 区分），故 `company_id` 必须填对——这是本方案唯一一处不靠空间层隔离的地方
- **绑不到公司的内容直接丢弃，不写入**（见 3.3 / 4.3 / 5.4）。即便写入也无意义——管理端召回叠 `company_id IN 可访问公司集 OR thread_id` 的析取过滤，`company_id` 为空则两个条件都不满足，永远召不回

**需新增两个业务类型**：`EXPERT_TESTIMONY` 与 `CROSS_COMPANY`，均按租户（organization）键控。具体创建与定位细节留到开发设计阶段。

两者的份数不同：

- **`EXPERT_TESTIMONY` 两份**——权限分层要求管理端在 Goldie 内看到署名、创始人永不看到，而署名直接存正文、不做召回后处理，故按 `end_type` 分匿名版与署名版各存一版
- **`CROSS_COMPANY` 一份**——§7.5 规定管理端回溯原始转录与署名走**管理端系统入口、非跨公司 KB 前台**，Goldie 链路上两端看到的都是匿名版，内容完全相同，故两端共用一份

> 另有 `ADMIN_PORTFOLIO` 的设想（为 LP / GS 内部中绑不到具体公司的基金层内容提供归属），**尚未决定是否引入**，见 3.2 的批注。

### 1.2 登记表业务类型

`ai_file_registry.business_type = FIREFLIES`（该列为 `VARCHAR(40)` 自由文本，无 CHECK 约束，新增取值不需要 DDL 改动）。

该取值**不影响检索**——召回按空间走，`recall` 使用的 `business_type` 取自 `ai_rag_space`（`search_service.py:222`），与登记表的同名字段无关。

### 1.3 产物形态

每条知识条目最多三份产物：

| 产物 | 存储位置 | 说明 |
|---|---|---|
| **原文** | `ff_meeting` / `ff_meeting_sentence`（新建） | 永久留存，审计源与重算依据；不进向量库 |
| **去逐字化纪要**（= body） | `ai_rag_entry.content_text` + 按 800/100 切片 | Goldie 检索细节 |
| **摘要** | `ai_rag_entry.summary` + 单片 `chunk_kind=summary` | Goldie 检索概览；**≤1000 字符** |

**「去逐字化」与「完整纪要」是同一份产物**——前者是处理动作，后者是处理结果。

约束：

- 摘要与纪要的**输入都是原始转录全文**，不直接采用 Fireflies 自带的 `overview` / `notes`（§6.1 的机械清洗层需要原文作为 n-gram 比对基准）
- 摘要由我方生成后**直接写入**，需跳过系统的二次 `summarize`，否则会变成「摘要的摘要」
- **内容短于阈值时只存 body、不生成 summary**（阈值实施期定），避免两者近乎重复、在召回中互相挤占
- 提取前先走**质量判断**，判定为无实质内容的直接跳过，不产出条目

### 1.4 去逐字化适用矩阵

§6.1 的去逐字化包含三种处理，**按去向分别适用**：

| 去向 | 非逐字表达 | n-gram 近逐字剔除 | 实体/人名剥离 |
|---|---|---|---|
| 1a | ✅ | ✅ | ❌ |
| 1b | ✅ | ✅ | ❌ |
| Founder KB | ✅ | ✅ | ❌ |
| Cross-Company | ✅ | ✅ | ✅ |
| 专家证词 · 匿名版 | ✅ | ✅ | ✅ |
| 专家证词 · 署名版 | ✅ | ✅ | ✅ |

> **图例**：✅ 做 ／ ❌ 不做

**判据：实体剥离只在「内容跨出本公司」的去向做。**

实体剥离要防的是 A 公司的信息被 B 公司的人读到。1a / 1b / Founder KB 三者都按 `company_id` 绑定、只对本公司可见，剥离在这里没有收益，只会破坏可用性——1a 剥掉本公司名与产品名后，Goldie 连"Acme 那单谈得怎么样"都召不回。Cross-Company 与证词库是跨公司复用的，必须剥。

**各格依据**：

| 处理 | 依据 |
|---|---|
| 非逐字表达 / n-gram：1a、Founder KB、Cross-Company、证词 | 需求明文 §6.1「任何面向创始人的界面永不出现原文措辞」 |
| 非逐字表达 / n-gram：1b | 用户决定——§6.1 只覆盖面向创始人的界面、管理端不在其中，此项为「1a / 1b 经 Goldie 召回的都是转义后的」这一决定的结果 |
| Cross-Company 做实体剥离 | 需求明文 §7.5「内容为公司标识**完全剥离**后的匿名主题 / 洞察」 |
| 证词两版做实体剥离 | 需求明文 §7.4 存储字段为「**匿名内容**」 |
| 1a / 1b / Founder KB 不做实体剥离 | 用户决定（2026-09-22）。需求侧三处佐证：§5.x「上传内容**完整存入本公司 1a / 1b**，不做去逐字化」——同一空间里自传文档原样存、会议摘要却剥离说不通；§9.3 Board Call 派生物进创始人 KB「**不做第三方来源匿名处理**」；§9.1 要求 1b 保全「X 公司被兜售给 Y 买家，价格 Nx」这类交易事实，若剥离则"Y 买家"与"Nx"会被抹掉，规则要保全的内容不复存在 |

**证词两版的内容完全相同（均为匿名内容）**，差别只在署名版额外附一行来源信息——**不是**内容里保留实体。这与 §9.1 自洽：公司具体交易事实根本不进证词库（只落 1b），故证词内容中本就不应存在可识别的公司实体。

### 1.5 实体/人名剥离的范围

§6.1 仅写「实体/人名剥离」，未定义范围。以下为本方案补充的清单，**仅适用于 1.4 中标 ✅ 的去向**（Cross-Company 与证词两版）。

**直接标识符——机械清洗层处理**

| 类别 | 处理 |
|---|---|
| 公司名及其简称、变体、曾用名 | 剥离 |
| 人名（全名 / 名 / 姓 / 昵称） | 剥离 |
| 产品名、品牌名 | 剥离 |
| 客户名、供应商名 | 剥离 |
| 域名、邮箱、URL | 剥离 |
| 「公司 + 职位」组合（如"Acme 的 CTO"） | 剥公司，保留职位 |
| 具体金额、百分比 | **转量级**，如"约百万级 ARR"、"两位数下滑" |
| 具体日期、时间点 | **转阶段**（"A 轮后"、"上一财年"）或**时长**（"约一个季度内"、"连续两个季度"）；**禁止绝对时点**——年份、季度、月份一律不保留（"2026 Q3"、"去年 Q3"、"今年 8 月"） |
| 可定位的地理信息（如"我们西雅图办公室"） | 剥离 |

**准标识符——机械层无能为力，靠 LLM 层处理**

单个属性都不敏感，**组合起来可唯一定位**。例："一家做**牙科 SaaS** 的、**A 轮后**、**Q3 丢了最大客户**的公司"——三个属性各自无害，凑在一起在组合内可能只对应一家。

这类内容没有可匹配的实体词，机械清洗层扫不到。所以 §6.1 的「双层保障」实际是**分工**而非冗余：

- **机械清洗层**：处理直接标识符，确定性高、可测
- **LLM 摘要层 + 可移植性判据**：处理准标识符，靠「脱离这家公司仍然成立才保留」把独特细节整体抹掉

这也是 Cross-Company 采用「只抽可移植洞察点」而非「整场匿名化」的原因——后者只过得了机械层，准标识符会原样留在文本里。

**保留（剥了即失去价值）**：行业 / 垂直领域、公司阶段（ARR 区间、轮次）、通用职位（CEO / CTO，不带公司）、问题类型、应对方式。

n-gram 阈值需在实施期用真实数据调优。

### 1.6 幂等与重算

按 `meeting_id` 覆盖：**先软删旧条目，再写新条**。避免改判会议类型或重跑加工后，Goldie 同时召回同一场会的新旧两版。

### 1.7 机密性规则的适用范围

> **出处说明（2026-09-22）**：§9.1 活跃交易隔离与 §9.2 LP／基金机密性过滤**只存在于已改名作废的《Fireflies_Integration过期》**。现行需求中仅《会议内容提取规则》的 Partner 行保留「实时交易信息全部隔离」及关键词 (3) 的 `Live-deal Quarantined` 定义，其余条款（交易事实只落该公司 1b、对所有 Partner 全量适用、LP 基金层过滤、对 Portfolio Manager 亦排除）均无现行出处。
>
> **机密性部分正在重写中，新版发布前以作废文档为准**，本文档照此实现。新版出来后本节需重新对齐。

| 规则 | 需求原文适用范围 | 本方案适用范围 |
|---|---|---|
| §9.1 活跃交易隔离 | GS → Partner、GS → LP | GS → Partner、GS → LP、**GS 内部** |
| §9.2 LP / 基金机密性过滤 | LP 派生物进入面向创始人界面前（**Cross-Company 匿名主题**与**专家证词匿名版**——LP 不产出 1a、不进 Founder KB），两条管道各执行一遍 | 同左；对 1b 则是**保全**规则 |

> ⚠️ **GS 内部纳入 §9.1 是本方案有意加严**，不是需求原文的要求（EPIC 原文为 "live-deal quarantine, now applied universally to all GS → Partner meetings"）。
>
> 理由：GS 内部会议恰恰是最可能密集讨论活跃交易的场合，而矩阵允许 GS 内部产出 Cross-Company 主题。不加严就存在一条泄漏路径——内部会讨论的交易事实被抽成"战略/解决闭环"匿名主题，经 Cross-Company 被其他公司创始人感知。
>
> 加严后的口径与其他两类一致：**具体交易事实只落该公司 1b**，仅可移植的市场趋势允许进 Cross-Company。

### 1.8 参会人姓名回退匹配

邮箱匹配未命中时，用**姓名**回退匹配，规则如下：

| 项 | 规则 |
|---|---|
| **匹配顺序** | ① **LG 系统内用户**姓名 → ② **Cheat Sheet 维护人员**姓名。命中即止 |
| **匹配方式** | **完全匹配**，不做模糊、不做近似 |
| **重名** | 匹配到多条 → **直接进 Pending Assignment**，不猜测 |

**姓名取值来源**：Fireflies 的 `meeting_attendees` 中 `displayName` / `name` 实测**全为 null**，取不到「日历邀请中的姓名」。可用源为：

1. `meeting_attendance[].name`——平台出席记录，最接近日历邀请，**首选**
2. `speakers[].name`——ASR 说话人识别，**仅作兜底**（人名易被识别错，用于匹配注册表风险更高）

> 采用完全匹配而非模糊匹配，是因为姓名匹配的误判代价不对称：匹配不上只是进 Pending 等人工处理，匹配错则把外部人当成内部人（或相反），直接改变会议类型与整条路由。

### 1.9 参会人识别与公司归属

**明确禁止使用会议标题作为识别依据。**

**参会人来源**：会议在 **Microsoft Teams** 内召开、将 Fireflies 拉入，因此 Fireflies 返回的参会人即 Teams 会议的参会人。实测样本亦印证——`calendar_type = "outlook"`、`meeting_link` 指向 `teams.microsoft.com`。取值用 `participants`（邮箱数组）与 `meeting_attendance`（出席记录，含姓名与进出场时间）。

识别要产出两样**互相独立**的东西：

| 产出 | 用途 | 缺失的后果 |
|---|---|---|
| **人的身份** | 决定会议类型（GS 方 / 公司方 / LP / Partner） | 类型判不出 → 会议进 Pending |
| **公司归属** | 决定产物落哪家公司 | 该公司的产物无处可落 |

**匹配链（命中即止）**

| 顺序 | 匹配方式 | 匹配对象 | 产出 |
|---|---|---|---|
| ① | **完整邮箱** | LG 系统内用户（管理端 + 公司端） | 人员确定；公司端用户同时得到 `company_id` |
| ② | **完整邮箱** | 第三方维护的邮箱——Cheat Sheet，其次 HubSpot | 人员确定 + 角色 / 专长标签 |
| ③ | **邮箱域名** | `goldensection.com` / `whalesongproduct.com` / `gstdev.com` | **仅判定"此人属 GS 方"**，不对应到具体人员 |
| ④ | **姓名** | LG 系统内 → Cheat Sheet（完全匹配，规则见 1.8） | 人员确定 |
| ⑤ | **LLM 推断** | 转录正文 | **只推断【公司】**，不解决"人是谁" |
| ⑥ | —— | —— | Pending Assignment |

> **域名匹配的唯一用途是判定 GS 方**（用于会议类型分类），**不做人员对应**——同一域名下有多个账号，域名本身无法定位到人，也无此必要。
>
> **公司归属只来自 ①**（完整邮箱 → LG 公司端用户 → `company_id`）与 **⑤**（正文推断）。域名不参与公司归属。

**关键规则**

- **LLM 推断这一级只推断公司，不推断人的身份**。因此人未识别时，即便推断出了公司，会议类型仍判不出——**会议照常进 Pending**
- **进 Pending 即阻断提取**：抽取提示词按会议类型分别编写（6.3~6.7），类型未定就没有提示词可选，强行提取只会拿到质量不可控的结果。Pending 会议停在识别阶段，**等人工在 Summary Records 页指定会议类型后再触发提取**
- **发言人映射也属识别阶段**：逐句的 `sentences[].speaker_id` 经 `speakers[].name` 映射到已识别的参会人，**映射不上即视为该参会人未识别，整场进 Pending**。`speakers[].name` 来自 ASR（昵称、听错拼写、`Speaker 2`、两人合并为一个 speaker 都会导致对不上），故这一步要在调用 LLM 之前做完——证词的来源行依赖它，留到提取后才发现就晚了
- 一场会议可关联**多个公司**
- 识别结果（公司、外部人员、角色）传递给下游分类步骤

### 2.1 判定条件

**GS 方 ≥ 1 且 公司方 ≥ 1**，两侧各自按下列口径判定。

> ⚠️ **仅靠 ② 成立时，会议判得出类型但定不出公司归属**。
>
> 判定「有没有公司方」与确定「是哪家公司」是两件事：前者只要身份，后者要 `company_id`。而 Cheat Sheet 条目只有 `Organization` 文本字段，**没有 `company_id`**。
>

>
> | 情形 | 判定 | 公司归属 |

> | **只有 Cheat Sheet Founder，无公司端用户** | ✅ 第一类 | **取不到 `company_id`** —— 1a 定位不出 KB-APP 空间、1b 无法做行级隔离，**产物无处可落** |
>
> **处理方式**：**由会议正文提及反推公司**，复用 LP / GS 内部 / Partner 所用的同一套「公司提及识别」（见 3.3）——从候选公司清单匹配，仅高置信度采纳，低置信度不采纳并记 Pending。
>
> ⚠️ **本类型的误判代价比其余类型高一个量级**：
>
> | 类型 | 误判后果 |
> |---|---|
> | LP / GS 内部 / Partner | 内容落入错误公司的 **1b**，Portfolio Manager 看到越界内容（管理端） |
> | **本类型** | 内容落入错误公司的 **KB-APP**，**该公司创始人可直接读到别家公司的会议摘要**（客户侧泄漏） |
>
> 因此本路径的置信门槛应高于其余类型。**兜底**：按《Fireflies Summary Records》，`Status = Flagged` 的定义即「AI 判定为 GS-Founder 类型的会议」——**本类型默认全部进人工复核**，不直接放行，反推出的公司归属会被人工过一道。

本类型为**兜底类**：LP 或 Partner 若同时也是某家在营公司的公司端用户，按本规则即归入本类。

**1a / 1b / Founder KB（同一份）**

- 纪要：去逐字化后的完整会议内容

**Cross-Company**

不做整场匿名化，只抽**可移植洞察点**，一场会产出 0~N 条独立条目：

1. **可移植性判据**：脱离这家公司仍然成立才保留。「B2B SaaS 在这个阶段普遍低估实施成本」保留；「我们的实施成本超了 40%」剔除
2. **硬性剥离**：公司名、产品名、人名、客户名、具体金额与百分比（改为量级描述）、具体时间点（改为阶段描述）
3. **保留**：行业/垂直领域、公司阶段（ARR 区间、轮次）、问题类型、应对方式
4. **产出 0 条是正常结果**——多数例行沟通没有可移植内容，不为凑数降低匿名强度

理由：整场匿名化后仍极易通过上下文还原公司身份（「一家做牙科 SaaS 的公司在 Q3 丢了最大客户」，组合里做牙科 SaaS 的可能只有一家）。

### 3.3 1b 提取规则

**归属方式**：LP 会议的参会人映射不到在营公司，公司归属只能靠**正文提及**识别。一场会提到 N 家组合公司 → 产出 N 条 entry，`company_id` 必填。

**绑不到公司的内容直接丢弃**——纯基金层内容（募资进度、基金整体回报、LP 结构）不入 1b。

**公司提及识别策略**：由会议上下文推断，**仅高置信度才入**；低置信度不入并记 Pending 供人工确认。别名表列为可选优化项。

> 错误代价不对称：漏识别只是该公司 1b 少一条内容（静默）；**错识别会让 A 公司的交易事实进入 B 公司的 1b**，而 Portfolio Manager 只能看自己管辖的公司，这构成跨边界泄漏。故宁可漏不可错。
>
> 系统现状：**不存在「按名称匹配公司」的能力**，需新建。（按邮箱域名反查公司的能力同样没有，但公司归属已改走完整邮箱匹配，不再需要它——见 1.9。）

**抽取内容**（限该公司相关）：

1. **具体交易事实**——被兜售 / 估值 / 买方 / 价格 / 时间表。§9.1 明确规定此类内容**只能落该公司 1b**，其他去向一律不可
2. LP 对该公司的评价、关切、要求
3. GS 对该公司的退出计划与估值判断
4. 该公司在基金层面的定位——提及其他被投公司时剥掉对方标识

**§9.2 相关信息不得遗漏**：9.2 要求把基金层与其他 LP 信息从面向创始人的产物中剥离，这些信息的归宿就是 1b。对 1b 而言 9.2 是**保全规则**而非过滤规则。

**落库**：落 **KB-ADMIN** 空间（该组织的管理端知识库），每命中公司一条 entry，**`company_id` 必填**——它是公司隔离与召回过滤的唯一依据，不填则召不回。

### 3.4 专家证词提取规则

**抽取内容**：融资 / **市场？** / 倍数收益。定义引自《会议内容提取规则》(4)：

| 类别 | 定义 |
|---|---|
| **融资**<br/>Fundraising | 会议中关于引入外部投资、融资轮次、估值预期、向投资人展示的业务进展及资金使用计划的讨论 |
| **市场？**<br/>Market | 宏观市场环境、行业规模、竞争格局及外部需求变化 |
| **倍数收益**<br/>Multiples | 资本市场或同类对标企业常用的估值指标（P/E、P/S、EV/EBITDA 等），用于评估公司估值或定价基准 |

一句话概括：提炼适用于**融资路演与估值对标**的市场 / 行业信息。

> **保密过滤（Confidentiality Filter）**——《会议内容提取规则》(4) 要求：总结时**自动剔除机密、敏感或受 NDA 限制的信息**（核心财务数据、未公开的客户名单、敏感条款等）。这是在 §9.2 基金层过滤之外的又一道，两者叠加执行。

> **「市场」与 Cross-Company 的关系（`？` 标记项）**
>
> 需求 §10.1 自己指出这一条未闭环：「"市场趋势"到底是从证词库读取还是从主题库读取，两条管道的过滤责任划分未闭环」。两处主题范围重叠（都含市场行情、倍数）。
>
> **不做互斥分流，接受重复**（2026-09-22 用户决定）：两条管道各自按本管道的标准独立抽取，同一段话同时满足两边标准时**两边都产出**。理由——
>
> - 两个库的**受众不同**：证词库管理端看得到署名、创始人只看匿名内容；Cross-Company 两端都是匿名共识。同一句话在两处的形态与可见范围本就不同，不构成真正的重复
> - 需求把两者**分成两块写**，本身就说明它们不是同一批内容的两种切法。互斥会把这层区分抹平
> - 这两个库的定位**尚未稳定**：Cross-Company 可能演化为"适用于所有公司的泛化描述"，专家证词也未必要求跨公司。在定位定下来之前，互斥规则很可能定错方向，而多产出一条的代价远小于漏产出
>
> 代价是已知的：Goldie 召回时同一观点可能带署名和不带署名各出现一次。**先接受**，等两个库的定位明确后再回来处理。

**随条目携带两个标签**（均来自注册表）：

- **角色类型标签**：取注册表角色枚举（见 5.2）。本类型实际值域为 `GS staff` / `LP` / `Strategic Partner` / `Exit Partner`
- **专长标签**：按**会议日期**从注册表 Effective Dating 回溯当时生效的那一版，历史证词不因当事人当前角色变化而被重贴

**存两份**（因权限分层，且署名直接存库、不做召回后处理）：

| 版本 | 空间 | 正文 |
|---|---|---|
| 匿名版 | `(APP, EXPERT_TESTIMONY, organization_id)` | 匿名内容 + 附一行**泛化来源**，固定首行格式 `来源：某<专长标签>领域的<角色>` |
| 署名版 | `(ADMIN, EXPERT_TESTIMONY, organization_id)` | **同一份匿名内容** + 附一行**署名**，固定首行格式 `来源：<组织> <角色> <姓名>` |

**两版的正文内容完全相同**（均已实体剥离），差别只在程序附加的那一行首行——LLM 只抽一次，不存在两版内容漂移的风险。

**匿名版为什么也要附一行**：需求 §7.4 描述创始人端的措辞是「某医疗 IT 买家指出……」——匿名不等于无出处，泛化的角色 + 领域是这条证词可信度的来源。不附则创始人读到的是一条无主的断言，§7.4 要的那层感受就没了。泛化来源只用注册表的角色与专长标签，**不含姓名、不含组织**，不构成身份泄漏。

两行的取数完全同源（注册表角色 + 按会议日期回溯的专长标签），差别只是署名版多出组织与姓名。

公司端只解匿名版空间、管理端只解署名版空间，**两端都不会重复命中同一条证词的两个版本**。

> 署名**不能放 `chunk.metadata`**：`SearchHitDTO` 只透出 `chunk_id / content / entry_id / entry_title / space_id / space_name / similarity / match_type / uploaded_at / chunk_kind / file_id`，**metadata 不在返回字段中**，管理端召回后拿不到。

**创始人端可召回的前提**：证词空间按 `organization_id` 键控，而创始人登录时 `organizationId` 解析自 `r_organization_user`（`OrganizationRepository:47`），创始人不在该表中，**解出为 null**。需在 Java 登录处补兜底：查不到时用 `companyId` 走 `r_organization_company` 反查（`OrganizationRepository:50` 已有现成查询）。

**检索侧**：`knowledge_base_tool` 公司端分支需多解一个证词空间；**调高 top_k**，具体召回效果在工具内优化。

> 已知行为：`_normalize_and_merge`（`factory.py:289-317`）按 `business_type` 分组做 min-max 归一，**每组内最高分恒归一为 1.0**。证词自成一组，因此即使本轮提问与证词无关，组内最相关的一条也会以满分参与全局排序、挤占公司文档名额。已接受此行为，后续在工具层优化。

### 3.5 Cross-Company 提取规则

从**原文**提取（与证词并列，两条独立管道，均在同一次加工任务内完成）。落 `(APP, CROSS_COMPANY, organization_id)` 空间。

| 概念 | 定义 |

| **仅可移植趋势**<br/>Portable Trends Only | 仅提取**可复用 / 普适性**的趋势。排除局限于某一特定客户、单一项目或一次性交易的临时现象，只保留对未来有长期参考价值、可在多业务或多场景间迁移复制的行业洞察 |

## 五、GS → 战略伙伴 / 退出伙伴（合并）

### 5.0 「合并」的含义

原设计是两个独立类型——`Strategic Partner`（商业合作方：渠道、技术伙伴、联合销售）与 `Exit Partner`（退出交易相关方：买方 PE、投行、并购顾问）。因**从参会数据无法可靠区分**，合并为 `GS → Partner` 一类，**下游一律按更保守的 Exit Partner 处理**。

误判代价不对称是合并的依据：把 Exit 会当成 Strategic 会 → 隔离放松 → 交易信息流入 Cross-Company，是实质泄漏；反之只是过度保守、少共享一些商业趋势。

合并落成三条规则：判定不区分、证词范围取并集（5 类）、**§9.1 全量适用**（见 5.5）。

### 5.1 判定条件

GS 方 ≥ 1（口径同 2.1 的五选一），**且**无参会人属于公司方（否则归第一类），**且**非全员 GS（否则归 GS 内部），**且**存在参会人同时满足：

- **角色** ∈ {`Strategic Partner`, `Exit Partner`}
- **且 Expertise Tag** ∈ {`Strategic Partner`, `Exit Partner`}

《AI Meeting Type 自动映射标准》的触发规则写作「参与人命中注册表中 Strategic 或 Exit Partner」——**该句指的是 Expertise Tag**，角色条件隐含未写出。两者都要命中。

**匹配顺序**：先用邮箱匹配注册表；邮箱未命中则**姓名回退匹配，规则见 1.8**（LG 系统内 → Cheat Sheet，完全匹配，重名进 Pending）。

与 LP 一样**强依赖注册表**，未收录即判不出，进 Pending Assignment。

> **备注口径的变化**：旧需求写「两者**不可靠区分**，统一为一类；**下游按更保守的 Exit Partner 处理**」，现行需求改为「两者**无需区分**，统一为一类」——**"按保守的 Exit Partner 处理"一句已删除**。§9.1「对所有 GS → Partner 会议全量适用」正是以该句为依据，现失去出处，见 5.5 与 9.2。

### 5.2 注册表字段口径（本类型引入，全局适用）

以《Cheat Sheet》为准。

| 字段 | 性质 | 取值 | 回答什么 | 用途 |
|---|---|---|---|---|
| **角色** | 受控枚举，**固定 6 项** | `LP`、`Strategic Partner`、`Exit Partner`、`Founder`、`GS staff`、`Other` | 这人是什么身份 | 会议类型判定 + 证词脱敏转义 |
| **专长标签** | 受控枚举，**下拉多选** | 选项来自独立的 **Expertise Tags 配置页**（可增删） | 这人擅长什么领域 | 会议类型判定 + 证词专长标签 |
| **有效期** | From 必填 / To 可空（空 = present） | — | 上述两者在会议当日的版本 | 历史证词不因当事人当前身份变化而被重贴 |

**「外部人员角色」「角色类型」「证词发言者角色标签」三者是同一个字段**，取值即上表角色枚举。《会议内容提取规则》证词表中的 `LP / PE / IB / 买家 / 专家` 是**尚未改完的残留**，`PE` / `IB` / `Buyer` / `Expert` 作废。

**`Founder` 与 `GS staff` 是有意保留的，不是笔误**——《Cheat Sheet》明确说明：「并不是所有的 GS 人员和 Founder 人员都有 LG 的账户，所以 Cheat sheet 保留这两个角色标签」。

**有效期规则**：

- 编辑弹窗用两个日历选择器，From 必填、To 可不选（代表无限制，显示为 `present`）
- **会议发生时间落在的区间若与其他历史记录重合，以最后一个该时间的记录为准**
- 超过 90 天未复核的条目标记 `Needs review`
- 姓名是唯一识别符，发布后不可更改；History 页按生效日期排序，每个版本保留完整快照

**证词角色标签的实际值域只有 4 项**：证词仅由 GS → LP 与 GS → Partner 两类会议产生，这两类的参会人范围是 GS 人员、LP、Strategic Partner、Exit Partner，因此实际出现的是——

```
GS staff、LP、Strategic Partner、Exit Partner
```

`Founder` 与 `Other` 不会出现在证词中。脱敏转义直接用角色名，如「某退出伙伴指出……」「某 GS 员工指出……」。

### 5.4 1b 提取规则

**归属方式与 LP / GS 内部完全一致**：按正文提及识别公司 → 仅高置信度才入 → 一场会 N 家公司产出 N 条 → `company_id` 必填 → 绑不到公司的内容丢弃。落 **KB-ADMIN** 空间（该组织的管理端知识库），每命中公司一条 entry，**`company_id` 必填**——它是公司隔离与召回过滤的唯一依据，不填则召不回。

1. **具体交易事实**——§9.1 全量适用，此类内容**只能落这里**

3. 对方（伙伴）对该公司的评价与意向

> **口径已明确（2026-09-21）**：旧路由矩阵该格为「涉及公司，按敏感处理**？**」，带问号。《会议内容提取规则》已改为「**涉及具体公司退出的内容摘要**」——问号去掉，且**范围收窄为「退出相关」**，不再是泛指的"敏感处理"。

> 因此本节抽取内容以**退出相关**为主轴：交易事实、退出计划与时间表、买方意向与估值判断。商业合作与采购类内容若与退出无关，按 Cross-Company 的可移植趋势处理，不入 1b。

### 5.5 Cross-Company 提取规则

**§9.1 在本类型是全量适用**——不做「本场是否提及活跃交易」的条件判断，**默认每一场都涉及**。

操作含义：

| | 其他类型 | 本类型 |
|---|---|---|
| §9.1 触发 | 条件触发（提及被兜售/估值的公司时） | **无条件，每场都适用** |
| 公司具体事实 | 匿名后部分可进 Cross-Company | **一律只落该公司 1b** |
| Cross-Company 可得 | 匿名洞察 | **仅完全脱离具体公司的趋势** |

**抽取范围**，定义引自《会议内容提取规则》(3)：

| 概念 | 定义 |
|---|---|
| **市场趋势**<br/>Market Trends | 外部宏观层面的变化：行业新技术动向、用户需求偏好转变、竞争对手动向、政策法规变化等 |
| **商业 / 变现趋势**<br/>Commercial Trends | 业务与商业化层面的变化：新的盈利模式、定价策略调整、渠道转化效率、客户采购行为的变化等 |
| **仅可移植趋势**<br/>Portable Trends Only | 只保留可复用 / 普适、可跨业务或跨场景迁移的洞察，排除局限于单一客户、单一项目或一次性交易的临时现象 |
| **在途交易隔离**<br/>Live-deal Quarantined | **具体正在跟进、尚未落地**的商业项目、谈判细节或竞争性投标数据，严格过滤隔离，不得混入趋势总结 |

一句话概括：提取与**外部行业风向、竞争态势、商业变现或客户采购偏好**相关的外部情报与洞察。

**判据**：沿用第一类的可移植性判据——*脱离这家公司仍然成立才保留*——并因 §9.1 全量适用而加严：**任何能指向特定公司的内容一律不进**，即使匿名。Live-deal Quarantined 的定义给出了可操作的排除项（正在跟进未落地的项目、谈判细节、竞争性投标数据）。

> **仍待确认**：介于两者之间的内容如何判定，例如"某买方最近对垂直 SaaS 的估值逻辑变了"——它既像可移植的市场趋势，又可能透露在途交易中的买方态度。尚无边界示例。

### 5.6 专家证词提取规则

**与 LP 共用同一套证词库**（按默认实现，待确认）——同一个 `EXPERT_TESTIMONY` 空间，同样匿名版 / 署名版两份，仅抽取主题不同。

**抽取内容（5 类）**：商业采购行为、软件使用、倍数、买方行为、退出趋势。其中两类的定义引自《会议内容提取规则》(5)：

| 类别 | 定义 |
|---|---|
| **商业采购行为**<br/>Commercial Buying Behavior | 企业级客户在购买、评估、决策软件及服务时的习惯与流程。如：采购决策链条变长、更看重 ROI、对安全合规要求提高、倾向集成化方案 |
| **软件使用情况**<br/>Software Usage | 终端用户或企业客户实际使用软件产品时的行为数据与反馈。如：功能活跃度、高频使用场景、痛点、流失原因、对特定模块的依赖度 |

一句话概括：提炼客户在**企业采购决策模式**与**实际软件产品使用偏好 / 习惯**方面的洞察。

**标签来源**：

- **角色标签** → 取注册表角色枚举（5.2），本类型实际值域为 `GS staff` / `LP` / `Strategic Partner` / `Exit Partner`。脱敏转义时直接用角色名，如「某退出伙伴指出……」
- **专长标签** → 取专长标签枚举，按会议日期经有效期回溯当时版本

## 六、抽取提示词

> 本节为核心抽取提示词。落地时按项目惯例迁到 `source/ai/prompts/fireflies/`（`.md` 为权威源，`.py` 经 `_md_loader` 加载，`{{var:name}}` 占位）。

### 6.1 分工与约定

**分工**：LLM 只做「判断与转述」，机械处理交程序。

| 环节 | 谁做 |
|---|---|
| 非逐字转述、内容分类、可移植性判断、公司提及识别、质量判断 | **LLM** |
| 实体/人名剥离、n-gram 近逐字剔除、署名附加、专长标签回溯、落库路由 | **程序** |

**语言**：提示词中文，**产物英文**（与现有 `ai_rag_entry.summary` 及 Goldie 默认作答语言一致）。

**输出**：一律 JSON，`json_mode=True`。截断（`finish_reason=length`）时**整体判失败重试，不抢救半成品**——半份合法外观的结果比没有更危险（沿用 `excel_extract_agent` 的口径）。

**单次处理**：一次调用产出该会议类型的全部派生物，下游不再读原文（需求 §6.1）。

> **唯一例外：改判为 Board Call 后的补跑**（6.4）。需求 §6.1 防的是「下游各自去读原文导致口径不一致」，而改判后的补跑是**加工环节自身的二次触发**，不是下游；且需求 §8.2 要求改判后路由自动重算，重算本就必须重读原文。补跑只产出 1b，不重跑已入库的其余产物。


**已定**：摘要 ≤1000 字符（同 §1.3）；**纪要不设长度限制**——它的职责是完整承载会议内容，截断只会丢信息，切片由 800/100 负责。

```
**在途交易隔离（从严）**：具体正在跟进、尚未落地的商业项目、谈判细节、竞争性投标数据，一律不得进入此处。任何能指向特定公司的内容一律不输出，即使已匿名。
```

### 6.8 后置程序步骤（非 LLM）

**前置**：`Pending` 在提取**之前**就已判定（参会人未识别或类型未判出），这类会议**不调用 LLM**，停在识别阶段等人工指定类型，下列步骤一概不执行。

抽取返回后，程序依次执行：

1. **写会议状态**——`quality.usable = false` → 置 `Invalid`（1.10）；类型为 GS → Founder → 置 `Flagged`（仅提醒，不阻断）；其余 `Passed`
2. **机械清洗**——按去向执行实体/人名剥离与 n-gram 近逐字剔除（适用矩阵见 1.4、范围见 1.5）
3. **来源行附加**——证词两版均在正文首行附来源行，取数同源（注册表角色 + 步骤 4 回溯的专长标签）：署名版附 `来源：<组织> <角色> <姓名>`，匿名版附 `来源：某<专长标签>领域的<角色>`（无姓名、无组织）
4. **标签回溯**——按会议日期从注册表取当时生效的角色与专长标签（按 1.8 的有效期规则，区间重合取最后一条）
5. **公司归属裁决**——`company_mentions` 中仅 `confidence = high` 的采纳；低置信度不采纳并记 Pending；**无公司归属的内容直接丢弃、不写入**
6. **路由落库**——按各类型的空间映射写入（1.1），`company_id` 必填项校验
7. **幂等**——按 `meeting_id` 软删旧条目后写新条
