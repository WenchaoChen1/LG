## 一、全局约定

以下约定对所有会议类型生效，各类型章节不再重复。

### 1.1 知识库空间与业务类型

沿用现有 RAG 的空间机制：`ai_rag_business_association` 以组合键 `(end_type, business_type, company_id | organization_id)` 唯一确定一个知识库空间，chatbot 检索时按身份解出可见的 `space_ids`。**隔离靠「谁能解出哪个空间」，不靠检索时的行级过滤。**

| 用途 | 组合键 | 处理类型 | 谁能召回 |
|---|---|---|---|
| 1a 创始人记忆 / Founder KB | `(APP, APP_COMPANY, company_id)` | STANDARD | 该公司创始人 + 管理端 |
| 1b 管理端记忆 | `(ADMIN, ADMIN_COMPANY, organization_id)` | STANDARD | 仅管理端 |
| 专家证词 · 匿名版 | `(APP, EXPERT_TESTIMONY, organization_id)` | STANDARD | 创始人 + 管理端 |
| 专家证词 · 署名版 | `(ADMIN, EXPERT_TESTIMONY, organization_id)` | STANDARD | 仅管理端 |

**关键事实**：管理端的检索范围已包含各可访问公司的 APP 空间（`knowledge_base_tool.py:127-135` 并入 `find_app_space_ids`），**反向不成立**——公司端只解出自己公司那一个 APP 空间。因此：

- 写进 APP 空间的内容，**1a 与 1b 共用一份即可**，无需重复写入
- 只允许管理端看到的内容，写进 ADMIN 空间即结构性对创始人不可见，**不需要额外加过滤**

`EXPERT_TESTIMONY` 为**新增**业务类型，需加入 `ASSOCIATION_BUSINESS_TYPE_SEEDS` 白名单（该白名单在 `business_association_space_id` 中强校验）。参照 `ensure_erl_space` 新写 `ensure_testimony_space`，两端均按 `organization_id` 键控（不能复用 `ensure_kb_space`——后者是 APP 按公司、ADMIN 按组织）。

### 1.2 登记表业务类型

`ai_file_registry.business_type = FIREFLIES`（该列为 `VARCHAR(40)` 自由文本，无 CHECK 约束，新增取值不需要 DDL 改动）。

该取值**不影响检索**——召回按空间走，`recall` 使用的 `business_type` 取自 `ai_rag_space`（`search_service.py:222`），与登记表的同名字段无关。

### 1.3 产物形态

每条知识条目最多三份产物：

| 产物 | 存储位置 | 说明 |
|---|---|---|
| **原文** | `ff_meeting` / `ff_meeting_sentence`（新建） | 永久留存，审计源与重算依据；不进向量库 |
| **去逐字化纪要**（= body） | `ai_rag_entry.content_text` + 按 800/100 切片 | Goldie 检索细节 |
| **摘要** | `ai_rag_entry.summary` + 单片 `chunk_kind=summary` | Goldie 检索概览；**≤1000 字符** |

**「去逐字化」与「完整纪要」是同一份产物**——前者是处理动作，后者是处理结果。

约束：

- 摘要与纪要的**输入都是原始转录全文**，不直接采用 Fireflies 自带的 `overview` / `notes`（§6.1 的机械清洗层需要原文作为 n-gram 比对基准）
- 摘要由我方生成后**直接写入**，需跳过系统的二次 `summarize`，否则会变成「摘要的摘要」
- **内容短于阈值时只存 body、不生成 summary**（阈值实施期定），避免两者近乎重复、在召回中互相挤占
- 提取前先走**质量判断**，判定为无实质内容的直接跳过，不产出条目

### 1.4 去逐字化适用矩阵

§6.1 的去逐字化包含三种处理，**按去向分别适用**：

| 去向 | 非逐字表达 | n-gram 近逐字剔除 | 实体/人名剥离 |
|---|---|---|---|
| 1a | ✅ | ✅ | ✅ |
| **1b** | ✅ | ✅ | **❌** |
| Founder KB | ✅ | ✅ | ✅ |
| Cross-Company | ✅ | ✅ | ✅ |
| 专家证词 · 匿名版 | ✅ | ✅ | ✅ |
| 专家证词 · 署名版 | ✅ | ✅ | ❌ |

**1a / 1b 经 Goldie 召回到的内容一律是转述后的**，不出现原话措辞。

1b 与证词署名版**不做实体剥离**的原因：§9.2 要求这些敏感信息在管理端侧完整保全，剥掉实体后「X 公司被兜售给 Y 买家、价格 Nx」只剩一句空话。「换个说法表达同一事实」与「把事实里的主体抹掉」是两回事，不冲突。

n-gram 阈值需在实施期用真实数据调优。

### 1.5 幂等与重算

按 `meeting_id` 覆盖：**先软删旧条目，再写新条**。避免改判会议类型或重跑加工后，Goldie 同时召回同一场会的新旧两版。

### 1.6 机密性规则的适用范围

| 规则 | 需求原文适用范围 | 本方案适用范围 |
|---|---|---|
| §9.1 活跃交易隔离 | GS → Partner、GS → LP | GS → Partner、GS → LP、**GS 内部** |
| §9.2 LP / 基金机密性过滤 | LP 派生物进入面向创始人界面前 | 同左；对 1b 则是**保全**规则 |

> ⚠️ **GS 内部纳入 §9.1 是本方案有意加严**，不是需求原文的要求（EPIC 原文为 "live-deal quarantine, now applied universally to all GS → Partner meetings"）。
>
> 理由：GS 内部会议恰恰是最可能密集讨论活跃交易的场合，而矩阵允许 GS 内部产出 Cross-Company 主题。不加严就存在一条泄漏路径——内部会讨论的交易事实被抽成"战略/解决闭环"匿名主题，经 Cross-Company 被其他公司创始人感知。
>
> 加严后的口径与其他两类一致：**具体交易事实只落该公司 1b**，仅可移植的市场趋势允许进 Cross-Company。

## 二、GS → 创始人（默认类型）

### 2.1 判定条件

参会人邮箱中 `@goldensection.com` 数量 ≥ 1，**且**参会人邮箱经 email 表（未删除）映射到 company_id、且公司 status ∈ {2,3,4,5} 的数量 ≥ 1。

公司状态取 `CompanyStatusEnum` 的四项正常态：Needs Intervention(2) / Needs Guidance(3) / Thriving(4) / Achieving(5)；排除 Exited(1) / Shut down(6) / Off journey(7)。**不额外要求公司挂 portfolio**（比现成的 `isActiveCompany` 宽）。

本类型为**兜底类**：LP 或 Partner 若同时也是某家在营公司的联系人，按本规则即归入本类。

### 2.2 路由

| 目的地 | 是否产出 | 形态 |
|---|---|---|
| 1a 创始人记忆 | ✅ | 摘要 + 纪要 |
| 1b 管理端记忆 | ✅ | **与 1a 共用同一份** |
| Founder KB | ✅ | **与 1a 共用同一份**，区别仅在前台有无浏览入口 |
| Cross-Company | ✅ | 匿名可移植洞察点 |
| 专家证词 | ❌ | 不产出 |

### 2.3 提取规则

**1a / 1b / Founder KB（同一份）**

- 摘要：≤1000 字符，我方生成
- 纪要：去逐字化后的完整会议内容
- **一场会关联多家公司时，每家一条 entry，内容不裁剪**。本类型下安全——关联公司由参会人邮箱反推，各家均实际到场听过全场，不存在新增暴露

**Cross-Company**

不做整场匿名化，只抽**可移植洞察点**，一场会产出 0~N 条独立条目：

1. **可移植性判据**：脱离这家公司仍然成立才保留。「B2B SaaS 在这个阶段普遍低估实施成本」保留；「我们的实施成本超了 40%」剔除
2. **硬性剥离**：公司名、产品名、人名、客户名、具体金额与百分比（改为量级描述）、具体时间点（改为阶段描述）
3. **保留**：行业/垂直领域、公司阶段（ARR 区间、轮次）、问题类型、应对方式
4. **产出 0 条是正常结果**——多数例行沟通没有可移植内容，不为凑数降低匿名强度

理由：整场匿名化后仍极易通过上下文还原公司身份（「一家做牙科 SaaS 的公司在 Q3 丢了最大客户」，组合里做牙科 SaaS 的可能只有一家）。

### 2.4 落库

| 项 | 取值 |
|---|---|
| 空间 | `(APP, APP_COMPANY, company_id)`，STANDARD |
| 条目 | `ai_rag_entry`，每家关联公司一条 |
| 登记 | `ai_file_registry.business_type = FIREFLIES` |
| 原文 | `ff_meeting` / `ff_meeting_sentence` |

## 三、GS → 有限合伙人（LP）

### 3.1 判定条件

GS 邮箱 ≥ 1，**且**无参会人能映射到在营公司（否则归第一类），**且**有参会人命中注册表 Role = LP。

邮箱未命中时，用姓名回退匹配注册表（需求文档 130 行）。

**姓名源**：Fireflies 的 `meeting_attendees` 中 `displayName` / `name` 实测**全为 null**，取不到「日历邀请中的姓名」。可用源为 `meeting_attendance[].name`（平台出席记录，最接近日历邀请），`speakers[].name`（ASR 说话人识别）仅作兜底——后者人名易错，用于匹配注册表风险更高。

**匹配到重名 → 直接进 Pending Assignment**，不猜测。

**前置依赖**：本类型判定 100% 依赖专家/参与人注册表（需求 §5.2），注册表未建成前本类型实际不可用。

### 3.2 路由

| 目的地 | 是否产出 | 形态 |
|---|---|---|
| 1a 创始人记忆 | ❌ | |
| 1b 管理端记忆 | ✅ | 仅能绑定到具体公司的内容 |
| Founder KB | ❌ | |
| Cross-Company | ✅ | 仅可移植市场趋势，一份匿名版 |
| 专家证词 | ✅ | 融资 / 市场 / 倍数收益 |

### 3.3 1b 提取规则

**归属方式**：LP 会议的参会人映射不到在营公司，公司归属只能靠**正文提及**识别。一场会提到 N 家组合公司 → 产出 N 条 entry，`company_id` 必填。

**绑不到公司的内容直接丢弃**——纯基金层内容（募资进度、基金整体回报、LP 结构）不入 1b。

**公司提及识别策略**：由会议上下文推断，**仅高置信度才入**；低置信度不入并记 Pending 供人工确认。别名表列为可选优化项。

> 错误代价不对称：漏识别只是该公司 1b 少一条内容（静默）；**错识别会让 A 公司的交易事实进入 B 公司的 1b**，而 Portfolio Manager 只能看自己管辖的公司，这构成跨边界泄漏。故宁可漏不可错。
>
> 系统现状：**不存在任何「按名称匹配公司」的能力**（连邮箱域名→公司匹配也没有），需新建。

**抽取内容**（限该公司相关）：

1. **具体交易事实**——被兜售 / 估值 / 买方 / 价格 / 时间表。§9.1 明确规定此类内容**只能落该公司 1b**，其他去向一律不可
2. LP 对该公司的评价、关切、要求
3. GS 对该公司的退出计划与估值判断
4. 该公司在基金层面的定位——提及其他被投公司时剥掉对方标识

**§9.2 相关信息不得遗漏**：9.2 要求把基金层与其他 LP 信息从面向创始人的产物中剥离，这些信息的归宿就是 1b。对 1b 而言 9.2 是**保全规则**而非过滤规则。

**落库**：`(ADMIN, ADMIN_COMPANY, organization_id)` 空间，`company_id` 必填（管理端召回时叠 `company_id IN 可访问公司集` 的析取过滤，不填则永远召回不到）。

### 3.4 专家证词提取规则

**抽取内容**：融资 / 市场 / 倍数收益。

**随条目携带两个标签**（均来自注册表）：

- **角色类型标签**：LP / PE / IB / 买家 / 创始人 / 专家
- **专长标签**：按**会议日期**从注册表 Effective Dating 回溯当时生效的那一版，历史证词不因当事人当前角色变化而被重贴

**存两份**（因权限分层，且署名直接存库、不做召回后处理）：

| 版本 | 空间 | 正文 |
|---|---|---|
| 匿名版 | `(APP, EXPERT_TESTIMONY, organization_id)` | 不含署名 |
| 署名版 | `(ADMIN, EXPERT_TESTIMONY, organization_id)` | **署名写入正文**，建议固定首行格式如 `来源：<组织> <角色> <姓名>` |

公司端只解匿名版空间、管理端只解署名版空间，**两端都不会重复命中同一条证词的两个版本**。

> 署名**不能放 `chunk.metadata`**：`SearchHitDTO` 只透出 `chunk_id / content / entry_id / entry_title / space_id / space_name / similarity / match_type / uploaded_at / chunk_kind / file_id`，**metadata 不在返回字段中**，管理端召回后拿不到。

**创始人端可召回的前提**：证词空间按 `organization_id` 键控，而创始人登录时 `organizationId` 解析自 `r_organization_user`（`OrganizationRepository:47`），创始人不在该表中，**解出为 null**。需在 Java 登录处补兜底：查不到时用 `companyId` 走 `r_organization_company` 反查（`OrganizationRepository:50` 已有现成查询）。

**检索侧**：`knowledge_base_tool` 公司端分支需多解一个证词空间；**调高 top_k**，具体召回效果在工具内优化。

> 已知行为：`_normalize_and_merge`（`factory.py:289-317`）按 `business_type` 分组做 min-max 归一，**每组内最高分恒归一为 1.0**。证词自成一组，因此即使本轮提问与证词无关，组内最相关的一条也会以满分参与全局排序、挤占公司文档名额。已接受此行为，后续在工具层优化。

### 3.5 Cross-Company 提取规则

从**原文**提取（与证词并列，两条独立管道，均在同一次加工任务内完成）。

只抽可移植市场趋势，**一份匿名版**即可——§7.5 规定管理端回溯原始转录与署名走**管理端系统入口、非跨公司 KB 前台**，Goldie 链路上两端看到的都是匿名版。管理端回溯时从 `ff_meeting` / `ff_meeting_sentence` 按 `meeting_id` 查，不经过 RAG。

### 3.6 机密性

- 证词与 Cross-Company 是**两条独立管道**，§9.2 的基金层 / 其他 LP 身份剥离**必须各执行一遍**，不得假设对方已做（此即需求 §10.1 指出的「过滤责任未闭环」的处理方式）
- §9.1 / §9.2 命中的内容对**所有受众**排除（含 Portfolio Manager），**在写入阶段就不产出**，不是存入后按角色隐藏

## 四、GS 内部

### 4.1 判定条件

**全员 GS 域名**——所有参会人邮箱均为 `@goldensection.com`，且人数 ≥ 2。

任一参会人邮箱非 GS 域名（含 GS 员工的私人邮箱）即**不判为本类**：能映射到在营公司 → 第一类；命中注册表 LP / Partner → 对应类；都不是 → **Pending Assignment**。

> 采用严格域名判定而非"没有外部方"的宽松判定，是为避免一场实际有外部人参加的会被误判成内部会——后者会让外部人的发言以"内部讨论"的身份进入 Cross-Company。

### 4.2 路由

| 目的地 | 是否产出 | 形态 |
|---|---|---|
| 1a 创始人记忆 | ❌ | |
| 1b 管理端记忆 | ✅ | 与某个公司有关的结论性内容 |
| Founder KB | ❌ | |
| Cross-Company | ✅ | **仅战略、解决闭环**（不含全公司视图，见 4.4） |
| 专家证词 | ❌ | §7.4 的来源只列 LP、GS → Partner、有外部董事的 Board Call |

### 4.3 1b 提取规则

**归属方式与 LP 完全一致**：按正文提及识别公司 → 仅高置信度才入 → 一场会 N 家公司产出 N 条 entry → `company_id` 必填 → 绑不到公司的内容直接丢弃。落 `(ADMIN, ADMIN_COMPANY, organization_id)` 空间。

**抽取范围：只抽结论性内容**，不抽过程。

| 抽 | 不抽 |
|---|---|
| GS 对该公司的判断与评估 | 讨论过程、谁说了什么 |
| 决定采取的动作 | 争论与分歧本身 |
| 风险评估结论 | 未形成结论的发散讨论 |
| 资源投入决定 | |
| 具体交易事实（§9.1，只能落这里） | |

> 理由：1b 是"管理端记忆"，供 Goldie 推理时调用，需要的是结论而非过程。GS 内部会可能整场都在聊同一家公司，若整场抽取，1b 体量会失控且信噪比很差。
>
> 代价：无法追溯"当初为什么这么决定"。需要追溯时走 `ff_meeting` 原文。

**具体抽取细节（结论的粒度、如何判定"已形成结论"）待定。**

### 4.4 Cross-Company 提取规则

只抽两类，**不抽"全公司视图"**：

| 类别 | 说明 |
|---|---|
| **战略** | 可移植的策略判断，如"这个阶段应该先收紧获客再谈融资" |
| **解决闭环** | 问题 → 采取的动作 → 结果。最有价值的可移植资产 |

匿名化要求同第一类的 Cross-Company 规则（可移植性判据 + 硬性剥离 + 保留项），并叠加 §9.1（本方案已扩展至 GS 内部，见 1.6）。

**为何不抽全公司视图**

1. **EPIC 中无可落地定义**。原文仅一句 "GS Internal-sourced themes additionally support a strategy-resolution loop and firm-wide views (full interactive resolution UI is candidate for post-MVP build)"。Business Requirements 段无解释、5 条 Acceptance Criteria 中仅第 5 条原样复述、UX Considerations 完全未提。连 "firm-wide" 指 GS 机构层面还是整个组合层面都不确定。
2. **它不属于"提取"，属于"聚合"**。全公司视图按定义是跨多家公司的共性模式，而单场 GS 内部会只提供其中一个样本。强行在单场加工任务里产出，得到的只会是某人的一句主观概括冒充聚合结论。真要做需要独立的周期性聚合任务，与本文档设计的"单场会议 → 提取 → 路由"流水线不是一回事。

**为将来铺路（现在就做）**：战略与解决闭环条目**打结构化标签**——行业/垂直、公司阶段（ARR 区间或轮次）、问题类型。单场提取时顺手产出，成本近乎为零；将来做聚合任务时按标签分组即可，无需回头重跑历史会议。

## 五、GS → 战略伙伴 / 退出伙伴（合并）

### 5.0 「合并」的含义

原设计是两个独立类型——`Strategic Partner`（商业合作方：渠道、技术伙伴、联合销售）与 `Exit Partner`（退出交易相关方：买方 PE、投行、并购顾问）。因**从参会数据无法可靠区分**，合并为 `GS → Partner` 一类，**下游一律按更保守的 Exit Partner 处理**。

误判代价不对称是合并的依据：把 Exit 会当成 Strategic 会 → 隔离放松 → 交易信息流入 Cross-Company，是实质泄漏；反之只是过度保守、少共享一些商业趋势。

合并落成三条规则：判定不区分、证词范围取并集（5 类）、**§9.1 全量适用**（见 5.5）。

### 5.1 判定条件

GS 邮箱 ≥ 1，**且**无参会人映射到在营公司（否则归第一类），**且**非全员 GS 域名（否则归 GS 内部），**且**存在参会人同时满足：

- **角色** ∈ {`Strategic Partner`, `Exit Partner`}
- **且 Expertise Tag** ∈ {`Strategic Partner`, `Exit Partner`}

> ⚠️ **待确认（2026-09-21 记）**：角色与 Expertise Tags 两个枚举若都含这两个值，"两者都要命中"等于同一条件判两遍，不产生区分力；且会漏掉「角色 = `PE`、标签 = `Exit Partner`」这类组合（私募基金的人同时是 GS 的退出伙伴），使其掉进 Pending。
>
> 待 Expertise Tags 的新枚举清单确定后复核。**当前按用户指示实现"两者都要命中"。**

与 LP 一样**强依赖注册表**，未收录即判不出，进 Pending Assignment。

### 5.2 注册表字段口径（本类型引入，全局适用）

| 字段 | 性质 | 取值 | 回答什么 | 用途 |
|---|---|---|---|---|
| **角色** | 受控枚举 | `LP`、`Strategic Partner`、`Exit Partner`、`PE`、`IB`、`Buyer`、`Expert`、`Other` | 这人是什么身份 | 会议类型判定 + 证词脱敏转义 |
| **Expertise Tags** | 枚举（清单待提供） | 待定 | 这人擅长什么 / 与 GS 何种关系 | 会议类型判定 + 证词专业标签 |
| **Effective Dating** | — | — | 上述两者在会议当日的版本 | 历史证词不被当前身份重贴 |

「外部人员角色」「角色类型」「证词发言人角色标签」**三者是同一个字段**，取值即上表角色枚举。

相比需求文档现状的差异（文档尚未更新，见第八节）：角色枚举补入 `PE` / `IB` / `Buyer` / `Expert`，去掉 `Founder`（笔误——注册表只登记外部人员）与 `GS Staff`（GS 员工靠邮箱域名识别）；`Expertise Tags` 由自由文本改为枚举。

> `Founder` 从**注册表角色**中去掉，但**证词角色标签**将来可能需要它——§7.4 允许有外部董事在场的 Board Call 产出证词，创始人本人发言被抽成证词时视角即 Founder。当前 Board Call 归入第一类且不产证词，暂不需要。

### 5.3 路由

| 目的地 | 是否产出 | 形态 |
|---|---|---|
| 1a 创始人记忆 | ❌ | |
| 1b 管理端记忆 | ✅ | 涉及公司的内容 |
| Founder KB | ❌ | |
| Cross-Company | ✅ | 仅完全脱离具体公司的市场 / 商业趋势 |
| 专家证词 | ✅ | 商业采购行为、软件使用、倍数、买方行为、退出趋势（**5 类**） |

### 5.4 1b 提取规则

**归属方式与 LP / GS 内部完全一致**：按正文提及识别公司 → 仅高置信度才入 → 一场会 N 家公司产出 N 条 → `company_id` 必填 → 绑不到公司的内容丢弃。落 `(ADMIN, ADMIN_COMPANY, organization_id)` 空间。

**抽取内容**：

1. **具体交易事实**——§9.1 全量适用，此类内容**只能落这里**
2. 该公司相关的商业合作、采购决策、软件选型讨论
3. 对方（伙伴）对该公司的评价与意向

> **「按敏感处理」的含义 —— 按默认实现，待确认**：路由矩阵该格原文为「涉及公司，按敏感处理**？**」，带问号。当前按**无额外动作**处理——即归 1b 且受 §9.1 约束，与 LP 的 1b 同样对待。
>
> 理由：需求全文未定义过"敏感标记"机制，也无配套权限规则。若需实质区别（打标记、收窄至仅 PGM 可见等），需另行定义。

### 5.5 Cross-Company 提取规则

**§9.1 在本类型是全量适用**——不做「本场是否提及活跃交易」的条件判断，**默认每一场都涉及**。

操作含义：

| | 其他类型 | 本类型 |
|---|---|---|
| §9.1 触发 | 条件触发（提及被兜售/估值的公司时） | **无条件，每场都适用** |
| 公司具体事实 | 匿名后部分可进 Cross-Company | **一律只落该公司 1b** |
| Cross-Company 可得 | 匿名洞察 | **仅完全脱离具体公司的趋势** |

**判据（按默认实现，待确认）**：沿用第一类的可移植性判据——*脱离这家公司仍然成立才保留*——并因全量适用而加严：**任何能指向特定公司的内容一律不进**，即使匿名。

边界示例（"某买方最近对垂直 SaaS 的估值逻辑变了"这类介于市场趋势与交易信息之间的内容如何判定）**尚未给出可执行判据，待确认**。

### 5.6 专家证词提取规则

**与 LP 共用同一套证词库**（按默认实现，待确认）——同一个 `EXPERT_TESTIMONY` 空间，同样匿名版 / 署名版两份，仅抽取主题不同。

**抽取内容（5 类）**：商业采购行为、软件使用、倍数、买方行为、退出趋势。

**标签来源**：

- **角色标签** → 取注册表角色枚举（5.2）。脱敏转义时直接用角色名，如「某退出伙伴指出……」「某买方指出……」
- **专业标签** → 取 Expertise Tags，按会议日期经 Effective Dating 回溯当时版本

### 5.7 机密性

- §9.1 全量适用（见 5.5），§9.2 的过滤在证词与 Cross-Company 两条管道**各执行一遍**
- §9.1 / §9.2 命中的内容对**所有受众**排除（含 Portfolio Manager），**在写入阶段就不产出**
