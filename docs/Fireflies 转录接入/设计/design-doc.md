## 一、全局约定

以下约定对所有会议类型生效，各类型章节不再重复。

### 1.1 知识库空间与按类型的产物归属

#### Memory 与知识库的关系

需求路由表的 1a / 1b / Founder KB / Portfolio KB 对应**已有的 Memory 页与知识库页**（Goldie Base 的 Memory Settings / Knowledge Base Tab，9.11.3 / 9.11.2），不是四套存储：

- Memory 没有独立的表：Memory 页列的是知识库条目的摘要——`ai_file_registry`（`purpose='rag'`、`business_type` 为 `KNOWLEDGE_BASE` 或 `FIREFLIES`、`deleted=false`、`ai_rag_entry_id` 非空）圈定范围，取 `ai_rag_entry.summary` 非空的条目（`source/lg/db/service/file_registry.py`、`source/rag/domain/repository/entry_repository.py`）
- **Company Memory = end_type `APP` 的条目，Portfolio Memory = `ADMIN` 的条目**，按 `company_id` 列出（`source/memory/application/memory_service.py`）
- Memory 页只读，管理端与 Company Admin 有入口，公司端普通用户没有；知识库页列登记行对应的文件，可下载

| 知识库条目 | 摘要（Memory 页） | 正文（知识库页） |
|---|---|---|
| 一条 **APP 端**条目 | 1a Founder Memory | Founder KB |
| 一条 **ADMIN 端**条目 | 1b Admin Memory | Portfolio KB |

> 摘要与正文在矩阵与中间表里是两行（开发设计 7 #Q9），同一去向、同一公司合投**一条条目**（开发设计 7 #Q42）：正文写 `content_text`，摘要写同一条目的 `summary`，登记 `FIREFLIES`。摘要跟着正文走——正文未授权时条目不上线；页面上两者一起勾选、一起取消（开发设计 7 #Q55）。

#### 空间清单

`ai_rag_business_association` 以 `(end_type, business_type, company_id 或 organization_id)` 唯一确定一个空间，chatbot 按身份解出可见的 `space_ids`。**隔离主要靠「谁能解出哪个空间」**，行级过滤只在 KB-ADMIN（`company_id`）与公司端普通用户（`created_by`）两处。

| 代号 | 组合键 | 粒度 | 隔离方式 | 谁能召回 | 写入的产物 |
|---|---|---|---|---|---|
| **KB-APP** | `(APP, APP_COMPANY, company_id)` | 每公司一个 | 空间层 | 该公司公司端用户 + 可访问该公司的管理端 | GS → 创始人的会议条目 |
| **KB-ADMIN** | `(ADMIN, ADMIN_COMPANY, organization_id)` | **每组织一个（公司 id 隔离）** | **行级 `company_id`** | 仅管理端（可访问公司） | GS 内部 / Partner 的公司层条目 |
| **机构层** | `(ADMIN, ADMIN_ORGANIZATION, organization_id)`（复用已有种子） | 每组织一个 | 空间层 | 本组织**全体**管理端 | LP 的基金层条目 |
| **证词-匿名** | `(APP, EXPERT_TESTIMONY, organization_id)` | 每组织一个 | 空间层 | 公司端 | 证词匿名版 |
| **证词-署名** | `(ADMIN, EXPERT_TESTIMONY, organization_id)` | 每组织一个 | 空间层 | 管理端 | 证词署名版 |
| **跨公司** | `(APP, CROSS_COMPANY, organization_id)` | 每组织一个 | 空间层 | 公司端 + 管理端 | Cross-Company（**仅审核放行的**） |

处理类型均为 `STANDARD`。**租户 = Fireflies 连接所在的那一个组织节点**（9.2.1，第十章 #69）：写入、召回、配置、页面切换租户都只认这个节点；**判断「本租户的人和公司」时含其全部下级节点**，父节点的不算（第十章 #95）。公司从租户 X 挪到 Y 后，它在 X 产出的 APP / ADMIN 条目跟着公司走、归 Y 的 PM / PGM 可见；X 的名册、拒绝名单、跨公司内容留在 X。

- **机构层**承接 LP 的基金层内容：全体管理端可见，**不建基金实体**，条目 `company_id` 为空，配合 Summary Records 的 Portfolio 标记（仅为标记，不作权限依据，9.5）。用独立空间，不在 KB-ADMIN 里放 `company_id` 为空的条目（与管理端会话文件行级上无法区分）
- 组合键里的端类型表示「内容面向哪一端写」，不决定谁能召回（召回代码按提问人的端列出可解空间，第八章 #7、#8）；跨公司内容是匿名、面向创始人的版本故用 `APP`，管理端在召回分支里另解；`end_type` 非空
- 关联业务类型有白名单（种子 `source/rag/domain/enums.py`，`business_association_service.py` 校验，第八章）。**`EXPERT_TESTIMONY` 两份**按 `end_type` 分匿名版与署名版，署名直接存正文、公司端永不看到；**`CROSS_COMPANY` 一份**，两端看到同一份匿名内容，管理端回溯原会议走 Cross company content Tab（9.11.4）与 Content Routing Matrix（仅 PGM / Super Admin，审核与编辑的唯一入口，9.6）
- **Cross-Company 只投影已审核放行的条目**：Authorize 默认不勾（1.7、9.6.4）
- 证词与跨公司条目**不进 Memory 页**（1.2），两端在 Goldie Base 的 Cross company content / Expert Testimony Tab 查看：管理端带会议与来源，公司端只有正文与专长标签（9.11.4 / 9.11.5）

#### 按会议类型的产物归属

**类型一 · GS → 创始人**

| 产物 | 空间 | 份数 | 页面展示 |
|---|---|---|---|
| 1a + 1b 摘要 / Founder KB + Portfolio KB 正文（**一条 APP 条目**，开发设计 7 #Q42） | KB-APP | 唯一关联公司一条（2.3） | Memory 页 Company Memory 层；公司端与管理端知识库页 |
| Cross-Company | 跨公司 | 0~N 条 | 放行后 Cross company content Tab（9.11.4）；审核与编辑在会议管理页（9.6） |
| 专家证词 · 匿名版 / 署名版（**仅当会上有专家**，2.5） | 证词-匿名 / 证词-署名 | 0~N 条，两版一一对应 | Expert Testimony Tab（9.11.5） |

> 1a 与 1b、Founder KB 与 Portfolio KB 各是同一份文本，不另写 ADMIN 条目（管理端能召回可访问公司的 APP 空间）。

**类型二 · GS → LP**

| 产物 | 空间 | 份数 | 页面展示 |
|---|---|---|---|
| 1b + Portfolio KB · **基金层**（一条 ADMIN 条目，`company_id` 为空，带 Portfolio 标记；正文分 Fundraising、LP Concerns & Requests、Fund Matters、Live Deals 四节，开发设计 7 #Q80） | 机构层 | 每场 0~1 条 | Memory 页、管理端知识库页的机构层展示 |
| 证词 · 匿名版 | 证词-匿名 | 0~N 条 | 同类型一 |
| 证词 · 署名版 | 证词-署名 | 与匿名版一一对应 | 同匿名版 |
| Cross-Company | 跨公司 | 0~N 条 | 同类型一 |

> **不按公司拆分**（3.3）：被投公司的进行中交易写进基金层，其余涉及具体被投公司的内容只留原始转录。

**类型三 · GS 内部**

| 产物 | 空间 | 份数 | 页面展示 |
|---|---|---|---|
| 1b + Portfolio KB（按正文提及的公司拆分，只抽结论） | KB-ADMIN | 每命中公司一条 | Memory 页 Portfolio Memory 层；管理端知识库页 |
| Cross-Company | 跨公司 | 0~N 条 | 同类型一 |

**类型四 · GS → Partner**

| 产物 | 空间 | 份数 | 页面展示 |
|---|---|---|---|
| 1b + Portfolio KB（按正文提及的公司拆分；正文分 Exit Readiness、Exit Process 两节；默认放行，5.4） | KB-ADMIN | 每命中公司一条 | 同类型三 |
| 证词 · 两版 | 证词-匿名 / 证词-署名 | 0~N 条 | 同类型一 |
| Cross-Company | 跨公司 | 0~N 条 | 同类型一 |

GS 内部与 GS → Partner 没有基金层：绑不到公司的内容不写 1b，可迁移部分进 Cross-Company。

**四类会议的 Cross-Company 口径相同**：抽市场趋势、商业趋势、战略决议闭环、全公司视角四类，只保留可迁移内容（Portable Trends Only），0 条属正常；共用 6.9（P6），过滤与审核见 1.7；放行后全租户经 Goldie 召回（第十章 #41、#43）。

`Pending` 会议不提取内容，不产出任何条目（1.10）。

#### 召回边界的关键事实

管理端检索范围已含各可访问公司的 APP 空间（`source/ai/tools/knowledge_base_tool.py` 的 `find_app_space_ids`），反向不成立。因此进 KB-APP 的内容管理端自动可见；只给管理端看的写进 ADMIN 端空间即可；**KB-ADMIN 的公司隔离是行级的，`company_id` 必须填对**。

召回链路的三处处理（第八章 #7～#10）：

| # | 规则 | 做法 | 涉及的产物 |
|---|---|---|---|
| 1 | 公司端普通用户能召回本人受邀的会议条目 | 行级过滤为「`created_by` = 本人，或 `file_id` 属于本人受邀的会议」（受邀 = 本人邮箱在受邀名单里，查询时现算，开发设计 7 #Q59）；会议条目以系统用户写入；Company Admin 不叠此过滤 | KB-APP 的会议条目 |
| 2 | 管理端的行级过滤**按空间施加** | `company_id IN 可访问公司 OR thread_id` 只叠在 KB-ADMIN 与 APP 空间上，机构层、证词、跨公司空间不叠 | 机构层、证词署名版、跨公司 |
| 3 | 两端按组织另解会议空间 | 公司端另解证词匿名版与跨公司；管理端另解证词署名版、跨公司与机构层 | 证词两版、跨公司、机构层 |

> **第 2 条不能改成「放开 `company_id IS NULL`」**：管理端会话文件的 `company_id` 同样为空、靠 `thread_id` 区分，放开会召回别人会话里的文件。

### 1.2 登记表业务类型

每条会议条目写一行 `ai_file_registry`，`business_type` 三个值（开发设计 7 #Q42）：`FIREFLIES`（知识库条目）、`FIREFLIES_TESTIMONY`（证词两版）、`FIREFLIES_CROSS_COMPANY`（跨公司）。该列 `VARCHAR(40)`、无 CHECK。由 `register_fireflies_file` 登记（不复用写死 `KNOWLEDGE_BASE` 的 `upsert_kb_registration`）。

| 条目 | `end_type` | `company_id` | 出现在 |
|---|---|---|---|
| GS → 创始人条目 | `APP` | 关联公司 | Memory 页 Company Memory；两端知识库页 |
| 公司层条目（GS 内部 / Partner） | `ADMIN` | 命中公司 | Memory 页 Portfolio Memory；管理端知识库页 |
| 基金层条目（LP） | `ADMIN` | **空** | Memory 页与管理端知识库页的机构层展示 |
| 证词两版 / 跨公司 | `APP` / `ADMIN` | **空** | 只在 Goldie Base 各自的 Tab（9.11.4 / 9.11.5） |

- `organization_id` 一律填租户；证词与跨公司的 `company_id` **必须为空**
- 对 Goldie 检索无影响：`recall` 的 `business_type` 取自 `ai_rag_space`
- 知识库页取 `KNOWLEDGE_BASE` 与 `FIREFLIES`，Memory 页取两者中摘要非空的（第八章 #11）
- 登记表不加会议列：中间表记录投影时的合成 `file_id`（1.3、9.6.6），重投影按它软删（1.6）

### 1.3 产物形态

**每个知识库条目 = 一个纯文本条目 + 一个合成 `file_id`**（开发设计 7 #Q41）：

| 层 | 存储位置 | 说明 |
|---|---|---|
| **原文** | `ff_meeting_meta_info` / `ff_meeting_sentence` | 永久留存，审计源、重算依据与 n-gram 比对基准；不进向量库 |
| **中间表** | 见 9.6.4、9.6.6 | 知识库产物每个去向（与公司）摘要、正文各一行，跨公司每场一行，证词每位发言人署名、匿名各一行（开发设计 7 #Q77）；矩阵的可编辑正本，已授权的行投影为条目 |
| **正文** | `ai_rag_entry.source_type = TEXT`，`content_text` 存按 6.11 生成的 markdown → 800/100 切片（`chunk_kind=body`；证词按空行分段、每段前补来源行成一片，开发设计 7 #Q77） | 知识库页展示，下载时按条目 markdown 现生成 `.md`（9.11.2） |
| **摘要** | 同一条目的 `summary`（摘要行已授权时写，否则为空）+ 一条整段 `chunk_kind=summary` 向量（为空不建） | Memory 页展示（9.11.3）；**不超过 150 个英文单词** |

**合成 `file_id`**：每次投影生成新 id，同时写进条目、切片、登记行与中间表行；不对应 Java `files` 行与 S3 对象。按文件圈定召回（第八章 #11）、三方关联、知识库 Source 列反查会议都按它走。条目与登记行一起写，走「会议派生 markdown 入库」路径（第七、八章；`ingest_text` 不建登记行，不直接用），不生成文件、不调 Java 上传。

| 条目 | 摘要 | 正文 | 来源 |
|---|---|---|---|
| GS → 创始人 | 1a = 1b，≤150 词 | Founder KB = Portfolio KB，不设长度上限 | Fireflies `summary.overview` → 大模型整理为 markdown；overview 为空时从原始转录生成 |
| 公司层（GS 内部 / Partner） | 1b，≤150 词 | Portfolio KB markdown（Partner 分两节，5.4），**附原始转录链接、不复制原文**（指向 Raw Data 详情页 9.3.5，按 9.3.6 鉴权，实际只对 PGM / SA 有效；基金层同此） | 原始转录（第六章） |
| 基金层（LP） | 1b 基金层，≤150 词 | 基金层 markdown（四节，开发设计 7 #Q80），附原始转录链接 | 原始转录 |
| 证词两版 | 不写 | 首行为来源行（3.4）；此人本场各条合成一块，每条一段、段首为专长标签名（开发设计 7 #Q77、#Q85） | 原始转录 |
| Cross-Company | 不写 | 只放 `statement`，本场各条合成一块，每条一段、段首为程序按 `category`（6.9（P6））加的标签；类别不另存，标题不带类别（开发设计 7 #Q77）；P6 的行业 / 阶段 / 问题类型标签不落库 | 原始转录 |

约束：

- **产出一律英文 markdown（6.1），统一经大模型生成或整理**，overview 也不原样入库（第十章 #56）
- **凡进 Memory 页的条目都必须写摘要**；内容很短时摘要与正文接近，接受
- **摘要由我方传入，跳过系统的二次 `summarize`**；超长压缩在写入前做（6.5（P2）；仍超 150 词先走一次只压缩的修订调用，仍超长按最终失败，6.11）；RAG 管理端「重试」遇会议条目同样跳过、保留原摘要（第八章 #4）
- GS → 创始人的摘要不做筛选，只整理与压缩
- **overview 同样过 n-gram 近逐字剔除**（基准为原始转录）：命中删所在整行（成段的按句删），删空按该调用最终失败（6.11）
- Memory 页按 markdown 渲染摘要：详情弹框渲染，列表两行预览去掉标记（第十章 #20）
- 提取前先走**质量判断**（转录为空的程序检查 + 6.4（P1），9.3.4），无实质内容的跳过

### 1.4 去逐字化适用矩阵

去逐字化分 LLM 摘要层（我方提示词转述，第十章 #56）与机械擦除层（实体/姓名剥离 + n-gram 近逐字剔除），**按去向分别适用**：

| 去向 | 非逐字表达 | n-gram 近逐字剔除 | 实体/人名剥离 |
|---|---|---|---|
| 1a | ✅ | ✅ | ❌ |
| 1b（含基金层） | ✅ | ✅ | ❌¹ |
| Founder KB | ✅ | ✅ | ❌ |
| Portfolio KB | ✅ | ✅ | ❌¹ |
| Cross-Company | ✅ | ✅ | ✅ |
| 专家证词 · 匿名版 | ✅ | ✅ | ✅ |
| 专家证词 · 署名版 | ✅ | ✅ | ✅ |

> **图例**：✅ 做 ／ ❌ 不做
>
> ¹ **GS → LP 例外**：基金层条目里提到的被投公司一律剥标识、改为泛指，具体公司内容不写；**进行中的交易照常写出公司名**。由 6.7（P4）提示词处理，不套 1.5 清单。

> **非英文会议**照常提取：n-gram 基本命中不了（产物是英文，不构成逐字风险）；名单剥离对不上转写后的名字，去身份靠大模型加跨公司人工审核兜底。

**实体剥离只在「内容跨出本公司」的去向做**：Cross-Company 与证词必须剥；1a / 1b / Founder KB / Portfolio KB 按 `company_id` 绑定，不剥。需求 I.2 的剥离清单只用于这三个去向。

**证词两版生成时内容完全相同（均为匿名内容）**，只差程序附加的首行来源行；之后各自编辑、各自授权，不同步。

### 1.5 实体/人名剥离的范围

以《会议内容提取规则》I.2 为准，**仅适用于 Cross-Company 与证词两版**。

**直接标识符——机械层为主**

| 类别 | 处理 | 出处 |
|---|---|---|
| 公司名及其简称、变体、曾用名 | 剥离 | 需求 I.2 |
| 产品名、品牌名 | 剥离 | 需求 I.2（产品名） |
| 人名（全名 / 名 / 姓 / 昵称） | 剥离 | 需求 I.2 |
| 邮箱、域名、URL | 剥离 | 需求 I.2（邮箱、域名）；URL 本方案补 |
| 客户 / 供应商 / 合作伙伴 / 投资者名 | 剥离 | 需求 I.2 |
| 「公司 + 职位」组合（如"Acme 的 CTO"） | 剥公司，保留职位 | 本方案 |
| 具体数字：收入、ARR、员工人数、估值、交易条款，以及金额、百分比 | **转量级**，如"约百万级 ARR"、"两位数下滑" | 需求 I.2；金额与百分比本方案补 |
| 具体日期、时间点 | **转阶段**（"A 轮后"）或**时长**（"约一个季度内"）；**禁止绝对时点**——年份、季度、半年、月份一律不保留；相对日历时点（"去年"、"本季度"、"年底"）与带时间锚点的季节、节日同样不写。**只靠 LLM 层改写，机械层不拦** | 本方案 |
| 具体地址 | 剥离；城市、地区可以保留 | 需求 I.2 |

机械层清单**每场固定取下列全部来源**，不随 P1 是否做公司识别而变：

| 来源 | 内容 |
|---|---|
| 公司 | 本租户全部公司的名称（含不在营的） |
| 人与机构 | 本租户 LG 用户（管理端、公司端）的姓名；Cheat Sheet 全部人员的姓名与 Organization（各版本都算）；本场出席记录与说话人的全部显示名，P8 推断出的姓名与机构 |
| 本机构 | 机构名称与基金名称（本租户 Portfolio 名称列表） |
| 模式 | 邮箱、域名、URL；精确数值 |

- **不进清单**：长度小于 3 的词、纯数字、常用英文词（如名为 `1` 的 Portfolio、叫 `Will` / `Mark` 的人；人名按全名与名、姓分别入清单），只靠 LLM 层。其余按整词匹配；常用词表与大小写口径见开发设计
- **数字只拦精确数值**（如 `$1.37M`、`37%`、`142 employees`）；量级写法与不指向某家公司的市场层区间（`4–6x ARR`）不拦（6.8、6.9）
- **命中怎么处理**：实体替换为泛指。提取时（含证词补抽）有命中的条目先交大模型把含命中词的句子改写通顺、命中词一律去掉，程序复查干净才采用，否则直接替换（6.11「修订调用」，开发设计 7 #Q62）；矩阵编辑保存只直接替换（9.6.3）；n-gram 命中删所在整行，精确数值只删所在句子，删空的条目不产出（6.11 步骤 2）
- 清单外的客户、供应商、投资者名靠 LLM 层改写

**准标识符与需判断的事项——靠 LLM 层 + 可迁移判据**（「脱离这家公司仍然成立才保留」）：单个属性不敏感、组合起来可唯一定位（如"做牙科 SaaS、A 轮后、Q3 丢了最大客户"）；**诉讼与纠纷**具体公司或个人涉及的不写，行业层面的趋势可保留。

**保留**：行业 / 垂直范围、公司阶段（ARR 区间、轮次）、通用职位（不带公司）、问题类型、应对方式（需求 I.2）。

**兜底原则**：剥离后仍指向单一公司 → 继续剥离；Cross-Company 审核后才发出（1.7）。n-gram 阈值可配置。

### 1.6 幂等与重算

条目内容没有更新接口（`source/rag/interfaces/routes.py` 只有 retry 与 DELETE），**只能整条替换**。中间表是正本（9.6.4），条目与登记行是它的投影；矩阵编辑、授权、改判、重提取都先改中间表，再**重投影**：

- **写入（上线）**：按中间表当前内容生成 markdown 与新的合成 `file_id`，写新条目与登记行（1.2、1.3），重新向量化、摘要直传，中间表改指向新 `file_id`
- **软删（下线）**：软删旧条目及其登记行
- **只换摘要**（开发设计 7 #Q42）：正文在线时只动摘要行，只替换 `summary` 与摘要向量，不换 `file_id`

**按中间表行投影**，不按 `meeting_id` 整场删写：

- 改内容（已生效且已授权的行 `Save`）先写新条目、成功后再软删旧的，失败时旧条目照常在线
- Start Extraction 即整场下线旧版本；提取后落了行的会议转 `Pending`（待审核），`Confirm & Apply Routing` 后已勾选的整批上线（不设草稿，开发设计 7 #Q81），期间 Goldie 召不回这场会
- 下线（取消勾选、改 `Unknown`、Start Extraction、证词作废）同步执行，上线与改内容异步执行；失败自动重试、不回滚本次操作，用尽记 `PROJECTION_FAILED`（该行显示 Projection failed，不设手动重试）；已授权的行上线 / 改内容失败后由定时清扫每 60 分钟再推一次，非 `Passed` 会议里挂着条目的行按下线推（开发设计 7 #Q88，[卡死清扫开发设计](../../卡死任务清扫/开发设计/dev-design-doc.md) 4.5 F5）
- 会议状态在应用时切换，不等投影结果；重新勾选已下线的行按当前内容写入；投影状态记在中间表行上（9.6.6）
- 编辑保存时重跑机械层清洗、不重跑 LLM 改写（9.6.3）

已知：已下载到本地的文件不随之更新；撤回只对之后的召回生效，已出现在 Goldie 回答里的内容仍留在聊天记录里，页面不提示。

### 1.7 机密性规则

| 规则 | 出处 | 内容 | 本方案适用范围 |
|---|---|---|---|
| **在途交易隔离**（Live-deal Quarantined） | 《会议内容提取规则》II (3)；路由表跨公司列「所有进行中的交易信息永不放出，只放该公司1b」 | 正在跟进、尚未成交的项目、谈判细节、竞标数据不得混入趋势摘要；出自它的做法与教训同样不写 | **四类会议的 Cross-Company**；提取时另由大模型对照整场转录逐条核查，出自在途交易的丢弃（6.11，开发设计 7 #Q63） |

| **Cross-Company 审核后发出** | 需求 I.2「管理员会在任何信息传播前进行审核」 | — | 所有类型：Authorize 默认不勾，放行后才投影 |

- 命中的内容**在写入阶段就不产出**，对所有受众（含 Portfolio Manager）排除，不是存入后按角色隐藏
- 证词与 Cross-Company 是**两条独立管道**，LP 保密与保密过滤各执行一遍（3.6）

### 1.9 参会人识别与公司归属

以《AI Meeting Type 自动映射标准》为准。**禁止使用会议标题作为识别依据。**

**参会人来源**：会议在 Microsoft Teams 内召开、拉入 Fireflies，取 `participants`（邮箱数组）与 `meeting_attendance`（出席记录，含姓名与进出场时间）。`participants` 是受邀名单，含受邀未到的人，按「受邀即有权看」照常算参会人，参与类型判定、公司归属与 Raw Data「本人参加」（第十章 #66）。

**三份名单怎么对上**（第十章 #92）：受邀名单只有邮箱，出席记录与发言人只有名字，三者无关联字段。

- **参会人以受邀邮箱为准**，一个邮箱一位；另加对上名册的非受邀说话人与管理员按 LG 账号登记的说话人（9.5.5）
- **发言人按「姓名对邮箱前缀」配到受邀邮箱**：去掉 `(Unverified)` 后缀，名、姓、首字母的组合对 `@` 前的部分（如 Robert Bowdon 对 `rb@`），只对上一个才采纳；对上多个时，只有这几个邮箱都对应名册里同一个人（会议当天生效的同一条记录，其中一位是平台账号也算）才挂到第一个，否则交 P8（同为 GS 人员或同一家公司的也不采纳，开发设计 7 #Q53）。会议页登记或关联保存成功后，对还没挂上的说话人按同一条件再判一次
- **出席记录只作显示、线索与剥离**：Raw Data 原样显示（9.3.3），传给 P8 作线索（6.13），并入剥离清单（1.5）；没发言、又对不上受邀邮箱的出席者忽略，不算参会人
- 已知：外部人拿链接进会、全程不发言时被当作不在场，会议可能因此判成 GS 内部

识别产出两样**互相独立**的东西：**人的身份**决定会议类型（缺失 → 类型判不出、进 Pending）；**公司归属**决定产物落哪家公司（缺失 → 产物无处可落）。

- 识别结果（公司、外部人员、角色、专家标志）传给下游；专家标志见 1.11

### 1.10 会议状态

**Raw Data 页 · `Invalid`**：无实质内容的会议显示灰色 `Invalid` 标签。复用 1.3 的提取前质量判断，转录为空与 P1 判不可用都由 Python 判，持久化为 `ff_meeting_state.identification_result = NO_SUBSTANCE`（9.5.9；Java 不判）；判据与优先级见 9.3.4。

**Summary Records 页 · `Passed` / `Pending`**

| 状态 | 触发条件 | 是否阻断路由 |
|---|---|---|
| **Passed** | AI 判出会议类型与参会人、内容已路由，且没有待审核内容、没有未处理的专家标记；或 Pending 会议经管理员应用路由（9.6.5） | 否：已授权的内容随即投影 |
| **Pending**（待识别） | 参会人经 P8 后仍 Unidentified；有说话人对不上（1.9）；会议类型未判定成功；GS → 创始人关联了两家及以上公司，或有到场 Founder 归属不到关联的那家（2.1、2.3）；GS → 创始人仅凭 Cheat Sheet Founder 判出、反推不出恰好一家高置信且为到场者所在的公司，或公司方只来自 P8 且与反推公司对不上（2.1）；管理员改为 `Unknown` 并应用（9.9.2）；提取作废（自动提取、自动路由、Start Extraction）、P1 / P8 最终失败（6.11） | **是**；识别结果照常展示，人工补齐后再提取（GS → 创始人只差公司的另有自动路由，9.9.3） |
| **Pending**（待确认专家） | 提取已完成，6.10（P7）给出「可能为专家」标记，还有建议标签没被通过或驳回；标签已全部处理、还没应用的仍属此原因 | **是**：`Confirm & Apply Routing` 在每个建议标签都通过或驳回后可点（矩阵没改动也可以），应用时按勾选投影、视为审核完成，转 `Passed`；没人处理就一直停着。重新提取时旧标记撤下，新提取出标记的同首次提取（9.6.4、9.6.5） |
| **Pending**（待审核） | 提取已完成，有待审核内容：Cross-Company 行、发言人经 P8 识别的证词行（推断身份、对到名册、说话人映射任一由 P8 得出）；Start Extraction 重新提取后只要落了行一律置本原因（9.9.5，开发设计 7 #Q81） | **是**：`Confirm & Apply Routing` 即审核完成，转 `Passed`，勾选的整批投影、未勾选的不放行 |

> **只有 `Passed` 会议的内容进 RAG**（开发设计 7 #Q75）：勾选 `Authorize` 只表示授权；`Pending` 会议（不论原因）的行只落中间表，转 `Passed` 时已授权的才投影。退回 `Pending` 都先整场下线：Start Extraction、改 `Unknown` 整场软删旧内容；证词补抽把 `Passed` 会议转回待审核时（2.5），行与勾选保留、只从 RAG 撤下，应用后整批入库（开发设计 7 #Q88）。
>
> **没有 `Flagged` 状态**：反推公司只采高置信度，低置信度一律 `Pending`。
>
> **Pending 不显示原因**：管理员按就地提示处理——参会人的未识别红点、未对上的说话人、`Please complete` 缺的必填项、有跨公司内容时 Pending 后的问号提示（9.5.1，开发设计 7 #Q78）、矩阵里未勾选的行（9.4.2）。已知：AI 识别失败、到场 Founder 归属不到这两类没有就地提示，只能看到 Start Extraction 可点。

**后台加工中不另设状态**：新会议识别与自动提取跑完前不进 Summary Records，Raw Data 照常可见（Cheat Sheet 增改后的重跑不同：会议保持 `Pending` 留在列表里，详情页显示提取中，9.9.3）；中断由 SQS 重投接手、从头重跑，本次产出全部作废，最多 N 次（SQS 最大接收次数），仍没跑完的交定时清扫（开发设计 P1、7 #Q13）；Start Extraction 超时同该次提取作废（6.11），死信或过期、首轮停在半路的会议也交定时清扫（开发设计 7 #Q12）；不给 Pending 会议设超时。

页面功能见 9.4 ~ 9.6、9.9。

### 1.11 专家身份：补充识别与专家推测

以《AI Meeting Type 自动映射标准》「特殊说明」与《Cheat Sheet》为准。

#### 分类与补充分两步

| 步骤 | 做什么 | 规则 |
|---|---|---|
| **分类** | 定每位参会人的身份，进而定会议类型 | 1.9 匹配链，命中即止 |
| **补充**（enrichment） | 对**每位**参会人另查名册，识别专家身份 | 不论分类命中哪一级都查；按会议日期取当时生效的版本（9.7.2），先邮箱后姓名；姓名完全匹配命中的直接采纳、不经 P8（与分类链不同）；经 P8 对到名册的直接取该条目 |

补充查到的名册记录**不改变分类结果**，只贡献专家标志与专长标签；例外是 LG 平台用户在名册有当天生效的登记时角色以名册为准（1.9 ②，开发设计 7 #Q47）。一场会可同时产出分类结果与专家证词（2.5）。

#### 「被标记为专家」的判定

**该人在 Cheat Sheet 中按会议日期生效的版本至少带一个专长标签**，且本场角色是 Founder、LP、Strategic Partner、Exit Partner 之一。

- GS staff 与 Other 不能当专家，名册里这两个角色的标签下拉置灰（5.2）；会上判为 GS 人员的人即便对上带标签的名册条目也不当专家
- Area of expertise 是自由文本，不参与路由与专家判定
- LG 平台用户要被认作专家同样须在 Cheat Sheet 登记，列表与编辑弹框在姓名旁标 `LG user`（9.7.1、9.7.3；开发设计 7 #Q51）

#### 专长标签

| 项 | 规则 | 出处 |
|---|---|---|
| **取值** | 受控列表，预置 7 项：Multiples、Buyer behavior、Exit trends、Software usage、Commercial buying behavior、Fundraising、Market，带定义（3.4、5.6）；管理员新增的只有名字（9.8.1，开发设计 7 #Q85） | 《Cheat Sheet》给定前 5 项；后 2 项本方案补 |
| **新增** | Cheat Sheet 标签下拉中手动新增，PGM 与 Super Admin 均可 | 《Cheat Sheet》；《AI Meeting Type》特殊说明 |
| **删除** | 已被使用过的标签不允许删除 | 《Cheat Sheet》 |
| **用途** | 专家判定；**证词抽取的类别**（每位专家只抽他会议当日生效版本的全部标签对应的内容，2.5、3.4、5.6）；证词来源行的专长标签（按会议日期回溯）；专家推测的建议标签（开发设计 7 #Q85） | — |

专长标签**不参与会议类型判定**（5.1）。维护页面与数据模型见 9.8。

#### 专家推测

| 项 | 规则 |
|---|---|
| **对象** | 角色为 Founder、LP、Strategic Partner、Exit Partner 的参会人，在册与未入册都算；**GS 人员与 Other 不推测**（含 P8 推断为这两种的）。只推测他还没有的标签，已是专家的人也会被推测新标签 |
| **触发** | 就他还没有的标签（字典全部 − 已有 − 已被拒绝）提出**实质性主张** ≥ 2 条（按人计，多个说话人合并计数，6.11 步骤 5）。实质性主张按 6.10（P7）四条判据：本人主动陈述、落在可推测的标签内、讲一类情况而非个例、带依据（开发设计 7 #Q85） |
| **归类** | 每条主张直接归到最贴切的可推测标签（预置 + 新增）；标记带上主张中出现过的标签 |
| **多标签** | 同一个人可被推测为多个标签 |
| **新标签** | 管理员新增的自动纳入推测范围，只按名字判断（6.10）。如新建 `Sales` 后，「企业客户的销售周期普遍拉长」可推测为 Sales，讲自家销售团队提成的是个例、不算 |
| **排除** | 该人 email + 该标签在本租户**拒绝名单**中（本场邮箱或名册各版本任一邮箱命中即算，9.5.6）→ 不再就该标签推测 |
| **展示** | Summary Records 参会人标签显示「可能为专家」及推测的标签；点姓名弹详情框（9.5.6）；有建议标签未处理时会议停在 `Pending`（待确认专家） |
| **同意** | 建议标签预填进专家确认框的 Expertise tags，**留下即同意**：随登记写入 Cheat Sheet，来源标识 `From FF Summary Records`（9.5.6、9.5.7；开发设计 7 #Q45） |
| **拒绝** | **删掉即驳回**：本次建议标签中保存后不在 Expertise tags 里的，本场 email + 该标签进拒绝名单（查询时按人展开，9.5.6）；此人标签变了的按下方规则重抽本场证词，删光标签的撤下他的证词（2.5，开发设计 7 #Q51、#Q87） |

**抽取侧**：6.10（P7）在 GS → 创始人 / GS → LP / GS → Partner 会议各跑一次，与其余提示词并行，结果不进本场首次证词抽取。程序先剔除 GS 人员、Other 与可推测标签为空的人，给每人附上不再推测的标签，连同标签清单（预置的附定义）交给它（开发设计 7 #Q85）；返回每人的主张及依据，程序按 ≥ 2 条门槛决定是否标记，主张与依据供管理员确认时参考。GS 内部会不调用。P7 最终失败时本场没有专家标记，会议按其余条件放行（记审计，9.10.2）。

**同意只更新名册**，影响此后会议的补充识别，本场不重新提取（9.5.6、9.5.8）。专长标签变了的专家（不限被推测者），在会议页保存、关窗同步把名册新值带回本场时（9.5.7），只为他按此时的全部标签整块重抽本场证词（入口与前提见 2.5；开发设计 7 #Q83、#Q85、#Q87）。

|---|---|---|

| 情形 | 处理 |
|---|---|
| 此人确属别家公司 | 点 Start Extraction（9.5.1）；其机构并入 `other_companies`，P2 不写那家内容（6.5） |
| 只是名册写法不同（`Acme AI` 对 `Acme`） | 在 Participants 改名册 Organization（9.5.5），重判后解除（9.9.3） |

**公司归属只来自到场的创始人**：正文提到、无创始人到场的公司不关联。公司已由邮箱 / Team 域名确定时，6.4（P1）只做质量判断、不做公司识别。

> 人工指定公司后的提取，落了行即 `Pending`（待审核），`Confirm & Apply Routing` 后才进入创始人可读的空间（9.6.4，开发设计 7 #Q81）；公司增改后程序按邮箱或 Team 域名认出公司、自动路由的，按自动提取放行（9.9.3）。

### 2.3 提取规则

**1a + 1b（同一份摘要）**：来源 `summary.overview`，为空从原始转录生成；大模型整理为 markdown、**≤150 英文单词**（自带摘要也须过这一遍）；去逐字化 = 大模型整理 + n-gram 近逐字剔除（基准为原始转录）；**不做敏感过滤与实体剥离**（创始人已参会，1.4），不按记忆分类筛选。

| Company 多于一家 | Start Extraction 与 `Confirm & Apply Routing` 置灰，提示「GS → 创始人会议只能保留一家公司」（9.5.1、9.6.5） |

**Cross-Company（0~N 条）——四类会议统一规则**

### 2.5 GS → 创始人会议的专家证词

出处：《会议内容提取规则》II「GS→Founder / 专家证词」；《AI Meeting Type》「Founder 为专家时的识别」。

**触发条件**

- 会议归入本类型，补充阶段查 Cheat Sheet（先邮箱、再姓名），到场者**被标记为专家**（1.11：会议日期生效版本带专长标签，且角色不是 GS staff / Other）
- **或被 AI 推测为专家**（6.10（P7）达到门槛，1.11）：首次提取不抽，确认标签后补抽（见下）
- **会上所有专家都抽**（创始人之外，列席的 LP、外部董事等也抽），各按自己的专长标签（开发设计 7 #Q85）；「只讲市场」只针对创始人
- 既非标记、也非推测的专家 → 不产出

**确认后重新产出证词**（开发设计 7 #Q83、#Q85~#Q88）：首次提取只抽在册专家；之后专家的专长标签变了，只为他整块重抽。

- **触发**：在本场保存专家确认框、`Edit external party` 或 `Assign new external party`（名册当日生效的标签写进识别结果，9.5.7；前两者在关窗同步时）后，若本场没有参会人改动、上次提取成功，把本场所有专长标签在识别结果与提取输入（9.5.9 `current_extraction_input`）里不同、且不在补抽或排队中的专家（不只这次保存的人）排进补抽，并把提取输入里他们的标签改成新值。专长标签变化不算参会人改动；有参会人改动时不补，要整场 Start Extraction；参会人改动又改回去的，那次保存同样排上待补的人。
- **抽法**：各补跑 6.8（P5，一次一人），按他此时全部标签整块重抽，替换他本场原有证词行（没有就新增）；他那块的人工编辑不保留，其余不受影响。名册里已无专长标签的不产出、原有行软删。
- `Confirm & Apply Routing` 应用时不补证词；在 Cheat Sheet 页改标签按名册变更处理（9.9.3）。
- **上线**：补出的行默认勾选、补完即显示，等 `Confirm & Apply Routing` 才上线：`Pending` 会议等应用转 `Passed`（开发设计 7 #Q75）；已 `Passed` 的补出新证词即转回 `Pending`（待审核），本场在线内容整场下线（行不软删，勾选与内容不动），应用后已勾选的整批重新入库（开发设计 7 #Q88）。删光标签或没抽出新证词的，只撤他的旧证词、会议不转回。
- **失败**：保留原有行，可 Retry，不阻塞之后的应用。

| 项 | 口径（三类会议相同） |
|---|---|
| 不必补跑 | 执行时他的标签与上次为他抽证词所用的（参会人表记录）相同（忽略大小写与顺序）→ 不补，原有行、编辑、勾选不动；不同即按当前全部标签整块重抽，删光则撤证词（开发设计 7 #Q87） |
| 进行中 | 此人胶囊与矩阵证词区显示「证词补抽中」，页面轮询，补完刷新；`Confirm & Apply Routing` 与 Start Extraction 置灰；确认框与 `Edit external party` 的 `Save` 不置灰；他的补抽在跑时又改了标签的，跑完自动排到队尾按最新标签再补（9.5.7） |
| 多人 | 一场会一次只补一人，后保存或点 Retry 的排队（胶囊同显示「证词补抽中」），补完一人（含失败）按先后接下一人；凡判断「补抽进行中」处排队都算；进程中断时定时清扫把卡住与排队的一起置失败，各自 Retry（开发设计 7 #Q86） |
| 失败 | 同一位置显示「证词补抽失败 · Retry」，点击重跑 |
| 替换后 | 新行 Play candidate 为关（9.11.6）；补抽结果直接生效，不随 `Discard Changes` 丢弃 |
| 类别参数 | 同首次提取：传此人当日生效的全部专长标签（预置的附定义）作可抽类别（6.8，开发设计 7 #Q85） |
| 审计 | 记 `EXTRACT`，触发方式为补抽（9.10.2） |

**抽取范围**

| 规则 | 口径 |
|---|---|
| 发言人 | 只抽专家**本人**的发言（`speaker_ref` 限于他们） |
| 主题 | 每人只抽名册当日生效版本全部专长标签对应的内容，类别即标签：预置 7 项按定义（3.4、5.6），新增的只按名字；一次 P5 调用，每人带自己的标签，类别不在此人标签内的整条丢弃（6.8，开发设计 7 #Q85） |
| **只讲市场**（只针对创始人） | 只写市场判断，**不涉及自己的公司、数据、客户或计划**（这些只留在 1a / Founder KB） |
| 交易敏感 | 交易事实与在途交易信息不进；出自在途交易的做法与教训也不写，另由大模型对照整场转录逐条核查、判为在途的丢弃（6.11，开发设计 7 #Q65） |
| 保密过滤 | 剔除机密、未公开客户名单、NDA 条款、核心财务数据（**本方案加严**，与 LP / Partner 证词统一，1.7） |
| 基金层过滤 | 剔除 GS 自有基金的具体信息与 LP 身份（[LP 保密]，1.7）；三类证词共用 6.8（P5） |
| 价值门槛与按角色限制 | 同 3.4 |
| 匿名化 | 按 1.5 剥离清单，两版都做；去逐字化（LLM + n-gram） |

判据示例：「垂直 SaaS 的企业买家近来把安全审查前置到试用阶段」保留；「我们的大客户把安全审查前置了，所以销售周期拉长了一个季度」剔除。

**存储与可见**：与 LP / Partner 共用证词库与两版结构（3.4），生成时正文相同、只差首行，之后各自编辑（9.6.2）。署名版角色取此人角色（创始人为 `Founder`），组织与姓名取 Cheat Sheet 会议当日生效版本；专长标签按会议日期回溯。可见范围同 2.2。与 Cross-Company **不互斥**。

**提取方式**：6.8（P5）独立调用，与其余提示词并行；无在册专家时不调用。各调用读同一份转录快照（6.1）。

### 3.4 专家证词提取规则

**抽取内容**：每位专家只抽他当日生效的全部专长标签对应的内容，同 2.5「抽取范围」（开发设计 7 #Q85）。预置 Fundraising、Market、Multiples 的定义（《会议内容提取规则》(4)）：

| 类别 | 定义 |
|---|---|
| **融资**<br/>Fundraising | 会议中关于引入外部投资、融资轮次、估值预期、向投资人展示的业务进展及资金使用计划的讨论 |
| **市场**<br/>Market | 宏观市场环境、行业规模、竞争格局及外部需求变化 |
| **估值倍数**<br/>Multiples | 资本市场或可比同业公司常用的估值指标（P/E、P/S、EV/EBITDA 等），用于评估公司估值或定价基准 |

LP 谈的基金募资难易、出资意愿与节奏也归「融资」（写在 Fundraising 定义里，P5、P7 共用）。

**价值门槛**（三类证词共用）：只抽给出判断并说明理由、或亲身经历的市场现象；复述新闻、常识、随口感慨不抽（6.8（P5））。

**抽谁**：只抽**专家**（角色为 Founder / LP / Strategic Partner / Exit Partner、当日生效版本带专长标签）；GS staff、Other 与非专家不抽。被 P7 推测为专家的确认标签后补抽（2.5）。

> 「市场」与 Cross-Company「市场趋势」不互斥分流，两边都满足时两边都产出。已知：Goldie 召回时同一观点可能带来源与不带来源各出现一次。

**随条目携带的标签**：

- **角色**：发言人在 Cheat Sheet 的角色（5.2），只会是 Founder、LP、Strategic Partner、Exit Partner
- **专长标签**：按**会议日期**回溯当时生效的版本，不因当前登记变化而重贴
- **时间戳**：会议开始时间（UTC，到分钟），两版都接在来源行后、随内容投影（开发设计 7 #Q74）；会内时间点 `[hh:mm:ss]` 只用于合并成块时块内排序，不存、不显示、不投影（开发设计 7 #Q77）

**存两份**（权限分层，来源行直接存正文）：

| 版本 | 空间 | 正文 |
|---|---|---|
| 匿名版 | `(APP, EXPERT_TESTIMONY, organization_id)` | 匿名内容 + 首行 `Expertise: <expertise tag> · Meeting <YYYY-MM-DD HH:MM> UTC`（当日无专长标签时只有 `Meeting …`） |
| 署名版 | `(ADMIN, EXPERT_TESTIMONY, organization_id)` | **同一份匿名内容** + 首行 `Source: <Organization> <Role> <Name> · Meeting <YYYY-MM-DD HH:MM> UTC` |

两版正文相同（均已实体剥离），只差程序附加的首行，LLM 只抽一次；两行取自同一 Cheat Sheet 版本。**匿名版不写角色**（需求：不向 Founder 展示来源信息，只给内容与专长标签）。已知：会议时间加专长标签可能让创始人反推出说话人（开发设计 7 #Q74）。

公司端只解匿名版空间、管理端只解署名版空间，不会重复命中两版。页面：Goldie Base 的 Expert Testimony Tab（9.11.5）。

> 署名不能放 `chunk.metadata`：`SearchHitDTO` 不透出 metadata。

**创始人端召回**：证词空间按 `organization_id` 键控，创始人不在 `r_organization_user` 中，会话 `organizationId` 由 Java 用 `companyId` 走 `r_organization_company` 反查补齐（第八章 #14）。**检索侧**：`knowledge_base_tool` 公司端分支多解证词空间，调高 top_k。

> 已知：`_normalize_and_merge` 按 `business_type` 分组 min-max 归一，组内最高分恒为 1.0；证词自成一组，与提问无关时也会有一条以满分挤占公司文档名额。

**机密性**：[去身份] + [LP 保密] + [保密过滤]；交易事实不进（3.6）。**LP** 只抽市场判断，他自己（及家族、所在机构）的业绩、持仓、配置决定不写（6.8（P5））。

**专家候选**：同 2.3。

### 3.5 Cross-Company 提取规则

按 2.3 统一规则，由 6.9（P6）从**原文**抽取（与证词各自独立调用，同一次加工任务内完成），落 `(APP, CROSS_COMPANY, organization_id)`；四道过滤同 2.3。

**本类型附加剥离**（在统一 [LP 保密] 之外）：

| 剥离 | 范围 | 处理 |
|---|---|---|
| **GS 自有基金的相关内容** | GS 自己的基金（识别同 1.7）：① **运作信息**——募资（进度、目标规模、关账）、业绩（IRR / TVPI / DPI、整体回报）、条款（管理费、carry、存续期与延期、关键人条款）、LP 出资（承诺、续投、追加、份额转让）、资本调用与分配、组合整体情况；② **投资策略与口径**——投什么公司、入场估值、持有期、退出方式与时机 | ① 删去该部分，删后仍可迁移的保留，否则整条不输出；**改写成泛指也不保留**。② 按可迁移判据（2.3）：只在 GS 内成立的不输出，能提炼出不依赖 GS 的经验按提炼后写。提示词例子只写类别、不给可照抄的整句 |
| **LP 身份信息** | 全部 LP，**含到会 LP**：机构名与人名；组合起来可定位的描述（如「某州教师养老金」）；与 GS 的出资关系；其内部配置决策与投委会安排 | 一律写成泛称（an institutional LP / LPs）；剥后仍可定位的整条不输出 |

- 行业层面的 LP 行为趋势（如「LP 普遍在降低对早期基金的配置」）剥掉身份后可作市场趋势保留（第十章 #39）
- 机械层按 1.5 精确剥离到会 LP 的姓名与机构；可定位描述与基金相关内容靠 LLM 层
- 剥下的基金内容与 LP 关切本就落基金层 1b（3.3、6.7（P4））；交易事实不进 Cross-Company（3.6）
- P6 只在本类型多拼一段「LP 会议附加剥离要求」（6.9）

**须审核后发出**：Authorize 默认不勾（9.6.4）；编辑入口只有 Content Routing Matrix（9.6.3）。**一份匿名版**：管理端回溯来源走会议管理页（9.6）或 Cross company content Tab（9.11.4），按 `meeting_id` 查原文、不经 Goldie / RAG（1.1）。与证词不互斥（3.4）。

### 3.6 机密性

| 标记 | 规则 | 出处 | 适用去向 |
|---|---|---|---|
| **[交易敏感]** | 具体交易事实（被兜售 / 估值 / 买方 / 价格 / 时间表）不进证词与 Cross-Company；进行中的落基金层 1b，其余只留原始转录（3.3） | 需求路由表、证词表 | 证词、Cross-Company 不进 |

> 本类型调用 P1（只做质量判断）、P4、P5、P6、P7（6.2）：基金层 1b 见 6.7（P4），证词 6.8，跨公司 6.9，专家推测 6.10。

## 五、GS → 战略伙伴 / 退出伙伴（合并）

### 5.0 「合并」的含义

`Strategic Partner`（渠道、技术伙伴、联合销售）与 `Exit Partner`（买方 PE、投行、并购顾问）合并为 `GS → Partner` 一类：判定只看角色（5.1）；证词按各专家的专长标签抽（5.6，开发设计 7 #Q85）；Cross-Company 按统一规则（2.3、5.5），无独有从严规则。

### 5.1 判定条件

GS 方 ≥ 1（同 2.1），**且**无公司方（否则 GS → Founder），**且**非全员 GS（否则 GS 内部），**且**有参会人的 Cheat Sheet **角色**（或 6.13（P8）采纳的角色）∈ {`Strategic Partner`, `Exit Partner`}，**且**无 LP（否则 GS → LP）。**只看角色**，不看专长标签。

匹配先邮箱、再姓名（姓名回退见 1.8），按会议日期取生效版本。未收录的只能靠 P8 推断，会上明确表明身份才采纳，否则进 Pending Assignment。

### 5.2 注册表字段口径（本类型引入，全局适用）

以《Cheat Sheet》为准。

| 字段 | 性质 | 取值 | 回答什么 | 用途 |
|---|---|---|---|---|
| **角色**<br/>Role | 受控枚举，**固定 6 项** | `LP`、`Strategic Partner`、`Exit Partner`、`Founder`、`GS staff`、`Other` | 什么身份 | 会议类型判定 + 证词署名版角色 |
| **专长标签**<br/>Expertise tags | 受控列表，下拉多选 | 预置 7 项：`Multiples`、`Buyer behavior`、`Exit trends`、`Software usage`、`Commercial buying behavior`、`Fundraising`、`Market`（后 2 项本方案补，9.8.1）；可在下拉中新增，**已被使用过的不可删**（9.8）；角色为 GS staff / Other 时置灰并清空 | 擅长什么领域 | 专家判定、证词抽取类别与专家推测（1.11，开发设计 7 #Q85）+ 证词专长标签；**不参与类型判定** |
| **专业领域**<br/>Area of expertise | 自由文本 | — | 专长背景 | 仅作上下文，**不参与路由** |
| **有效期**<br/>Validity period | From 必填 / To 可空（空 = present） | — | 各项在会议当日的版本 | 历史证词不因当前登记变化而重贴 |

「外部人员角色」「角色类型」「证词发言人角色标签」是同一个字段。`Founder` 与 `GS staff` 指没有 LG 账户的创始人与 GS 人员，判定时分别计入公司方与 GS 方（2.1）。

**有效期与版本**：有效期重合以最后写入为准（9.7.2）；超 90 天未复核标 `Needs review`（9.7.5）；姓名是唯一识别符，发布后不可改；History 按修改时间倒序、每版完整快照（9.7.6）。

### 5.4 1b 与 Portfolio KB 提取规则

**归属同 GS 内部**（4.3）：按正文提及（6.4（P1））、仅 `high`、N 家 N 条、`company_id` 必填；**没有基金层**。

**抽取内容**（以退出为主轴，术语 (1)）：

1. **退出就绪度**（Exit-Readiness）——为 IPO、并购、融资或业务剥离做的准备：合规性、资产清晰度、运营成熟度、风险筛查，及"是否满足资本市场或投资人要求"的讨论
2. **与退出相关的中长期战略**——为达退出标准定的方向、核心业务布局、资源分配优先级与重大转型决策；与退出无关的不入
3. **具体交易事实**——买方、价格、时间表、竞争性投标，**只能落这里**
4. 退出计划与时间表
5. 买方 / 伙伴对该公司的意向与估值判断

**正文写法**：只分两节、按序——`## Exit Readiness`（1、2：每行只写缺口、风险或决定是什么，要在哪个退出节点前解决，GS 定下的处理方式）→ `## Exit Process`（3~5：交易形式与阶段、流程节点合写一行、每个买方一行，只写名称、意向程度、报价或估值区间、附带条件）；不写 Summary 与 Action Items（开发设计 7 #Q79，提示词 6.6）。与退出无关的合作、采购内容不入 1b，可迁移部分进 Cross-Company（5.5）。

**默认放行**：同 GS 内部，自动提取后默认勾选，不因此进 `Pending`；`Passed` 时随即投影（开发设计 7 #Q75）。已知：退出谈判等敏感内容可能不经审核到达管这家公司的 PM（只到管理端），P1 认错公司时到无关公司的 PM。

**1b 与 Portfolio KB、落库**：同 4.3；**不做实体剥离与敏感过滤**，交易细节完整保留。

### 5.5 Cross-Company 提取规则

按 2.3 统一规则，由 6.9（P6）抽取，落 `(APP, CROSS_COMPANY, organization_id)`；四道过滤同 2.3、5.7。剥离后仍指向单一公司的内容整条不输出（2.3、1.5，第十章 #34）。交易事实、退出计划与在途信息只落该公司 1b；与退出无关的合作 / 采购内容可迁移部分在此产出（5.4）；与证词互不排斥（3.4）。

**须审核后发出**：Authorize 默认不勾（9.6.4）。

### 5.6 专家证词提取规则

**与 LP 共用证词库**——同一 `EXPERT_TESTIMONY` 空间、匿名版 / 署名版两份（3.4），按各专家专长标签抽（开发设计 7 #Q85）；抽谁同 3.4，标签变了只为他补抽（2.5）。下表为预置标签中这 5 项的定义：

| 类别 | 定义 | 细化（本方案） |
|---|---|---|
| **商业采购行为**<br/>Commercial Buying Behavior | 企业级客户在购买、评估、决策软件及服务时的习惯与流程。如：采购决策链条变长、更看重 ROI、对安全合规要求提高、倾向集成化方案（需求 (5)） | 采购流程、预算负责人、销售周期、ACV、价格敏感度 |
| **软件使用**<br/>Software Usage | 终端用户或企业客户实际使用软件产品时的行为数据与反馈。如：功能活跃度、高频使用场景、痛点、流失原因、对特定模块的依赖度（需求 (5)） | 采用、替代、AI 采纳 |
| **估值倍数**<br/>Multiples | 资本市场或可比同业公司常用的估值指标（P/E、P/S、EV/EBITDA 等）（需求 (4)） | 按行业、增长、规模 |
| **买方行为**<br/>Buyer Behavior | — | 谁在买、收购意愿、尽调重点、交易结构 |

### 9.2 Configuration

**只支持 API Key 连接**（《Fireflies Configuration》），不实现 MCP / OAuth。

#### 9.2.1 归属层级

**一个租户一条连接**，归属 `organization_id`：API key 代表一个 Fireflies **workspace**，`transcripts` 返回整个工作区可见的全部会议，拉进来后才按内容分派到各公司。

#### 9.2.2 能否复用 `third_party_connection`

**不复用，用独立的表 `ff_connection_configuration`。**

| # | 问题 | 说明 |
|---|---|---|
| 1 | **归属维度不兼容** | 该表 `company_id` / `project_id` 均 `NOT NULL`，唯一键 `(project_id, tool_id)`；Fireflies 是租户级 |
| 2 | **凭据明文存储** | `access_token` 无加密；Fireflies key 须密文存储（9.2.3） |
| 3 | **业务域不对口** | 该表服务 DI 域，Fireflies 只用得上 `access_token` |
| 4 | **同步状态语义不同** | `sync_status` 是 ETL 三态；这里要连接四态（9.2.4） |

#### 9.2.3 数据模型 `ff_connection_configuration`

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `organization_id` | 租户，**唯一** |
| `api_key_cipher` | **加密后**的 API key |
| `account_email` | key 持有者账号邮箱（`user` 查询），供页面展示「connected as …」与换账号判定（9.2.6）；不存 `account_name` |
| `connection_status` | 四态，见 9.2.4 |
| `last_success_sync_at` | 最近一次**成功完成**的拉取时间 |
| `consecutive_failures` | 连续失败次数，达阈值转 `Disconnected` |
| `sync_started_at` | 非空即正在同步，定时与手动互斥靠它（9.2.6） |
| `email_domains` | 本机构邮箱域名数组（9.7.7） |
| `created_by` / `created_at` / `updated_by` / `updated_at` | 审计 |

不存最近一次尝试的时间与失败原因（写 Java 应用日志）。物理字段以开发设计 J1 为准。

**密钥**：密文入库，只在服务端解密使用；**任何接口都不回传 key 原文或密文**；页面掩码（只露后 4 位）由查询接口在服务端拼好返回（开发设计 7 #Q1）。

#### 9.2.4 连接状态

| 状态 | 判定 | 展示 |
|---|---|---|
| `Unconnected` | 从未配置过 key，或已 Remove（9.2.5） | 灰点 |
| `Connected` | 最近一次调用成功 | 绿点 |
| `Failed` | 有 key，调用返回鉴权错误（key 错 / 被吊销） | 红点 |
| `Disconnected` | 曾连通，此后连续 3 次非鉴权失败（次数写死，开发设计 7 #Q58；限流不算，9.3.1） | 灰点 |

```
Unconnected --Link 成功--> Connected
Connected   --鉴权错误--> Failed
Connected   --连续 3 次非鉴权失败--> Disconnected
Disconnected --鉴权错误--> Failed
Failed / Disconnected --Link 成功 或 Sync 成功--> Connected
任意状态 --Remove--> Unconnected
```

`Failed` 要换 key；`Disconnected` 多为对方服务波动，等待或手动 Sync。**`Failed` 期间暂停定时拉取**，转回 `Connected` 后恢复。连接失败没有主动提醒，只靠本页状态点。

#### 9.2.5 Link

**以设计稿为准**（开发设计 7 #Q1）：已连接时显示 key 掩码（如 `••••a3f9`）；换 key 与 Remove 的交互以设计稿为准。

**Remove**：清空密文、状态回 `Unconnected`、暂停定时拉取；配置行、邮箱域名、`account_email`、`last_success_sync_at` 保留——重新 Link 同一账号接着增量拉，换账号按首次连接（9.2.6）；已入库的会议与产物不动；谁移除的写 Java 应用日志。

**Link 流程**：输入框非空时 `Link` 激活 → 调 Fireflies `user` 查询校验并拿到 `email` / `name` → 失败直接报错、**不落库**、页面状态不变；通过则加密落库、写 `account_email`、置 `Connected`、`consecutive_failures` 清零。

#### 9.2.6 Sync

**Sync now** 与每日定时拉取走**同一入口**：

- 同一连接同时只跑一个拉取，拉取开始时按 `sync_started_at` 条件更新抢占
- 按 `last_success_sync_at` 增量取，并往前回看（9.3.1）
- **首次连接回溯最近 14 天**（可配），不做全量回溯。Link 时 `account_email` 与原值不同（忽略大小写）即**换账号**，同样按首次连接：清空 `last_success_sync_at`；原账号已入库的会议与产物保留、不对账；同一 workspace 的会 id 不变，按 9.3.1 幂等不重复入库

**Last sync 只记成功**，失败不覆盖 `last_success_sync_at`。**定时拉取**每日一次，由 Java 固定计划触发并执行（第八章 #29），页面没有频率配置；`Failed` 期间暂停。

| 接口 | 作用 | 返回要点 |
|---|---|---|
| `GET /api/web/fireflies/connection` | 页面加载 | 状态、`account_email`、`last_success_sync_at`、是否正在同步、key 掩码。**不含 key 原文与密文** |
| `POST /api/web/fireflies/connection/link` | 提交 key | 校验 + 落库；失败返回具体原因（鉴权失败 / 网络不可达） |
| `POST /api/web/fireflies/connection/sync` | 手动同步 | 立即返回，拉取异步执行；重复调用直接拒绝 |
| `POST /api/web/fireflies/connection/remove` | 移除 key（9.2.5） | 清空密文、状态回 `Unconnected` |

**权限**：仅管理端本租户的 PGM / Super Admin；按所选租户执行（PGM 为会话租户，Super Admin 为切换后的租户，9.1）。

### 9.3 Raw Data

**原始逐字稿 + 元数据**的留存与查看入口，只对**原文**负责（9.1）。

#### 9.3.1 拉取

**一次调用拉 50 场，含正文**：`sentences` 直接写进 `transcripts` 列表查询，**不要**做成「列表 + 逐场详情」两段式（配额消耗会从 1 次变成 51 次）。

| 项 | 取值 |
|---|---|
| 增量依据 | `fromDate` / `toDate`（ISO 8601），起点取 `last_success_sync_at` 往前回看 72 小时（可配） |
| 分页 | `limit` **上限 50**，配合 `skip` |
| 首次回溯 | 最近 14 天；换账号同样回溯（9.2.6） |
| 入库门槛 | 只入库已处理完的会议（`meeting_info.summary_status = processed`）；未处理完的本次跳过、靠下次回看补上，超出回看窗口的不再拉（开发设计 J2）。入库的会议不论有没有句子都投递给 Python（第八章 #30） |
| 出错 | 单场返回 `errors`：该场本次不入库、靠回看重拉，不计入连续失败；整次查询失败才计入；鉴权错误转 `Failed` |
| 限流 | 429 中止本次、不推进游标，不计入连续失败 |
| 触发 | 每日定时 + Sync now，同一入口 |
| 不过滤 | 不按 `privacy` / `shared_with` 过滤，私密与他人共享进来的会议照常入库；不想用的在 Summary Records 取消全部勾选（9.9.2） |
| 删除 | 不做删除对账：Fireflies 侧删掉的会议，LG 已入库的原文与产物保留 |

**幂等**：业务唯一键 `(organization_id, Fireflies id)`，两个租户接同一 workspace 各存一份。回看重拉到的会：已进入识别（`dispatched_at` 非空，第八章 #30）的不改原文、不重跑，按 `content_hash` 比对有变时写一条 Java 警告日志（不进审计表，9.10.2）；尚未投递成功的整场重写（upsert 元信息、逐句先删后插），补投后按首次入库走识别。

#### 9.3.4 `Invalid` 标记

没有实质内容的会议判为无效，显示灰色 `Invalid`。**只看有没有实质内容，不看长短**。两步都在 Python 识别阶段，结果记 `ff_meeting_state.identification_result = NO_SUBSTANCE`（9.5.9）：

| 来源 | 时机 | 判据 | 是否调 LLM |
|---|---|---|---|
| 程序检查 | 识别第一步 | 转录为空（没有任何句子）；不按时长、句数判 | 否 |
| LLM 质量门槛 | 参会人识别与类型判定之后、内容提取之前（6.4（P1）） | `quality.usable = false`：通篇寒暄、设备调试、日程协调，或残缺到读不出在谈什么；会短不算理由 | 是 |

**`Invalid` 优先于 `Pending`**：转录为空的不做参会人识别、不调 LLM；P1 对每场会都跑（含参会人认不出的），`usable = false` 即置 `Invalid`（覆盖已判出的类型或 `Pending`）、不调其余提示词。**`Invalid` 不删数据**：原文照常入库、可在本页查看，只是不往下走。**Pending 会议在本页不带标记**（归 Summary Records）。

#### 9.3.5 原始逐字稿详情

`Raw transcript` 进入详情页，展示带时间戳与说话人的完整逐字稿。

- **页头**：标题 + `Raw verbatim transcript — unclassified and unmodified · captured <created_at>`（不显示字数）；公司端与管理端共用原文页与这句固定文案（开发设计 PG-03）
- **信息卡**：Date / Time / Duration / Participants，与列表同源
- **正文**：用 `text`；时间戳按 `start_time` 折算成 **`[hh:mm:ss]`**（如 `[00:00:04]`），与传给大模型的转录同一格式（6.3）；说话人用 `speaker_name`，**照原样显示**、不替换成注册表姓名；无页尾

> **长会议**：接口支持按 `sentence_order` 区间取，这是**加载批次、不是分页**：首批显示后前端在后台连续取完全篇（每批 500 句），整篇直接渲染、不用虚拟滚动，保证 Ctrl+F 覆盖全篇（开发设计 7 #Q29）。

> **系统内唯一保留原文措辞的界面**，其余经 Goldie 触达的产物都已去逐字化（1.4）。只给管理端 PGM / Super Admin 与**受邀参加该会议的创始人本人**（9.3.6）。《会议内容提取规则》I「面向 Founder 的界面绝不呈现原始逐字表述」针对派生产物，不限制参会人读自己受邀那场会的原文（1.9，第十章 #66），中途离场后的内容同样可见。

#### 9.3.6 权限与留存

以《Fireflies Raw Data》权限条为准：

| 谁 | 能看什么 |
|---|---|
| **PGM / Super Admin** | 本租户全部会议 |
| **Portfolio Manager** | **不可见**：菜单不出，接口同样拒绝 |
| **创始人本人**（公司端） | 仅自己受邀（账号邮箱在 `participants` 内）的会议的列表项与详情；会议所属租户须是其会话机构或其任一上级（第十章 #95；无关租户与下级机构的会议看不到） |
| 同公司未受邀的公司端用户（含 Company Admin） | 不可见（第十章 #66） |

**"本人参加过"**：账号邮箱出现在该场 `participants` 中（忽略大小写；Java 的 Raw Data 与 Python 的 Source 列同一口径，同 1.9 完整邮箱匹配）。**姓名回退匹配（1.8）命中的不算**。Cheat Sheet 的 `Founder` 没有账号，无从查看。

**公司端入口**（第十章 #90）：同在 Fireflies Management 页，只显示 Raw Data 一个 Tab，其余 Tab 不显示、接口拒绝；入口放头像下拉，在订阅条件之外、所有公司端用户都显示（开发设计 7 #Q15）；不显示租户切换下拉。列表与搜索只含会议所属租户是会话机构或其上级、且账号邮箱在 `participants` 中的会议；详情接口按会议 id 逐场校验。会话租户取会话的 `organization_id`（第八章 #14）。

**留存**：**永久留存**，不随派生产物重算而删除；幂等重写只发生在进入识别之前（9.3.1），不改 `created_at`。

### 9.4 Summary Records — 列表

**派生产物**的查看与改判入口，权限见 9.1。

**列表范围**：有 `Passed` / `Pending` 状态的会议。新会议识别与自动提取跑完（1.10）才有状态；Cheat Sheet 增改后重跑中的会议保持 `Pending`、照常列出（9.9.3，开发设计 7 #Q92）。`Invalid` 会议不进本页（只在 Raw Data 带徽章），Status 下拉因此没有 `Invalid`。

**Tab 上的 Pending 红点**：有未处理的 Pending 会议时亮起（按 Pending 会议总数计，不分原因），是整个 Fireflies 模块唯一的主动提醒。

#### 9.4.1 列表字段

| 列 | 取值 |
|---|---|
| Meeting | 标题 + 第二行小字 `<fireflies_id> · <duration> min` |
| Time | **单列合并** `Jul 15, 2026 · 10:00 AM` |
| AI Meeting Type | 蓝色标签；`Unknown` 灰色 |
| Companies | 已采纳的公司名，逗号分隔；宽度不够用 `...` 截断 |
| Status | `Passed` 绿 / `Pending` 红，不旁注原因（9.4.2） |
| 行末 | `Review` 链接 |

会议名与 `Review` 都进该会议详情页（9.5）。

**搜索**：模糊匹配 Meeting（标题与会议 id）与 Companies，搜索框提示写明三者（开发设计 7 #Q67）。**筛选**：AI Meeting Type、Status、Period 三个下拉（`All meeting types` / `All statuses` / `All time`），Status 只有 `Passed` / `Pending`。搜索与筛选状态的恢复与清空同 Raw Data（9.3.3，开发设计 7 #Q67）。**分页**：每页 10 条，按会议时间倒序，样式同 Raw Data（开发设计 7 #Q43）。

#### 9.4.2 Status 与阻断关系

**只有两态**，`Pending` 按原因分三种：

| 状态 | 含义 | 是否阻断 |
|---|---|---|
| `Passed` | 类型与参会人均判定成功、内容已路由，且没有待审核内容、没有未处理的专家标记；或 Pending 会议经管理员应用路由（9.6.5） | 否；只有 `Passed` 会议的已授权内容投影（开发设计 7 #Q75） |
| `Pending`（待识别） | 参会人经 P8 后仍未识别；或有说话人对不上参会人与 Cheat Sheet（1.9）；或类型未判出；或 GS → 创始人关联两家及以上公司，或有到场 Founder 归属不到关联的那家（2.1、2.3）；或 GS → 创始人定不出公司（仅凭 Cheat Sheet `Founder` 成立、正文反推不出恰好一家高置信且为到场者所在的公司，或公司方只来自 P8 且反推的公司与推断的机构对不上，2.1）；或管理员改为 `Unknown` 并应用（9.9.2）；或提取作废（自动提取、自动路由、Start Extraction）、P1 / P8 最终失败（6.11） | **是**，路由未执行；识别结果照常展示 |
| `Pending`（待确认专家） | 提取已完成，但有「可能为专家」的建议标签未处理（1.10）；标签已全部处理、还没应用的仍属此原因 | **是**，整场不投影；`Confirm & Apply Routing` 置灰，标签全部处理完才可点（9.6.5） |
| `Pending`（待审核） | 提取已完成，有待审核内容：Cross-Company、发言人经 P8 识别的证词；或人工 Start Extraction 后落了行（1.10，开发设计 7 #Q81） | **是**，整场不投影（开发设计 7 #Q75）；`Confirm & Apply Routing` 后转 `Passed`，勾选的行随即投影 |

没有 `Flagged` 状态（1.10）；仅凭 Cheat Sheet `Founder` 的 GS → 创始人会议的人工复核由「待识别 · 定不出公司」承接。

**Pending 原因不显示**：列表与详情页都只显示 Pending、不按原因筛（开发设计 7 #Q25d）；详情页不列子原因与剩余标签数，`Confirm & Apply Routing` 置灰时不弹悬停提示；唯一例外是有跨公司内容时 Pending 后带问号（9.5.1，开发设计 7 #Q78）。处理方式：待识别——补参会人、类型或公司后点 Start Extraction；待确认专家——点参会人标签打开专家确认框，留下或删掉建议标签后保存（9.5.6），再点 `Confirm & Apply Routing`；待审核——在矩阵勾选要放行的行后点 `Confirm & Apply Routing`。一场会可能同时有待确认专家与待审核。

**待识别的子原因与下一步**（页面不展示，API-21 现算返回）：参会人或说话人未识别 → Participants（9.5.5）；类型未判出或改为 `Unknown` → 类型下拉（9.5.2）；GS → 创始人关联多家或定不出公司 → Company（9.5.3）；到场 Founder 归属不到 → 确属别家直接点 Start Extraction，名册写法不同在 Participants 改其 Organization（2.1）；P1 / P8 / 提取失败 → 补齐后点 Start Extraction（6.11）。

| 无未识别信息（已提取过） | 置灰 | 类型、公司、参会人**有改动**（参会人口径见 9.9.1）且必填项齐全；GS → LP 的公司改动不算（3.3）。`Passed` 会议另有：打开时名册相对本场识别结果有变化（9.9.3，开发设计 7 #Q84） |
| 有未识别信息（`Pending` 待识别） | 置灰 | 必填项全部填好 |
| 提取作废、P1 或 P8 最终失败（待识别，必填项本已齐全） | 置灰 | 必填项齐全即激活，不要求改动（6.11） |
| 到场 Founder 归属不到关联公司（待识别，必填项本已齐全） | 置灰 | 同上；点击即确认此人属别家，其机构并入「其他到场公司」（2.1） |
| 提取进行中 / 提取完成后 | 置灰 | 直到再次出现改动 |
| Start Extraction 发起的提取作废（页头改动仍在） | 置灰 | 必填项齐全即激活，重跑同一组输入；旧产物已在点击时下线，不恢复（6.11） |

> 改 Email Domain、调提示词或质量门槛后，已提取的会议不重跑，也没有「按当前规则重跑」的入口；名册增改的连锁见 9.9.3。

**必填项**：AI Meeting Type 不为 `Unknown`；参会人中没有 `Unidentified`，也没有「未对上的说话人」；**GS → 创始人须恰好一家 Company**（多于一家时提示「GS → 创始人会议只能保留一家公司」，2.3）。Company 只对 GS → 创始人必填（GS 内部 / Partner 可以一家都没有，GS → LP 不识别公司，3.3）。改动后必填项不齐 → 置灰。

**点击**（不设草稿）：先把页头的类型、公司、参会人存为识别结果（9.5.9），本场旧产物整场下线（9.6.4），再异步启动抽取与路由（显示进度）。提取后落了行的会议转 `Pending`（待审核），`Confirm & Apply Routing` 后才上线，一行没落的直接 `Passed`（9.9.5，开发设计 7 #Q81）；失败则转 `Pending`（待识别 · 提取失败），旧内容不恢复，可再点（6.11）。改类型、公司、参会人一律整场重算（9.9）。`Portfolio` 改动**不激活** Start Extraction，只激活 `Confirm & Apply Routing`（9.5.4）。

#### 9.5.2 会议类型改判

下拉五项：**GS → Founder、GS Internal、GS → LP、GS → Partner、Unknown**；`Unknown` 灰色，其余蓝色。

- **GS → Partner 是一项**（Strategic + Exit 合并）；**没有 Board Call**，董事会会议按 GS → Founder
- **`Unknown` 等同于打回 Pending**：不提取，`Confirm & Apply Routing` 后软删全部已入库产物、停止路由（9.9.2）
- 改判本身不触发提取，点 Start Extraction 才触发；重算范围见 9.9

#### 9.5.3 公司指定

已识别的公司以标签展示，带 `×` 可移除；右侧下拉可多选、可搜索添加；GS → 创始人多于一家时 Start Extraction 与 `Confirm & Apply Routing` 置灰（2.3）。**GS → LP 的 Company 不参与路由**（3.3），通常为空，手动添加的只作标记、增删不触发提取（9.9.1）。

**每个公司下方展示识别依据**（《AI Meeting Type 自动映射标准》），只展示命中的那一条依据与具体值（识别链见 1.9）：

| 命中方式 | 依据文案 |
|---|---|
| 参会人完整邮箱 → LG 公司端用户（该公司的 Team 记录） | `Matched via email domain <domain> (<email>)` |
| 参会人邮箱域名 → 公司 Team 域名（1.9 ③） | `Matched via email domain <domain>` |
| 正文提及（6.4（P1），仅高置信） | `Inferred from meeting transcript`（不带模型写的依据） |
| 人工指定 | `Manually assigned by admin`（不带操作人与日期，查 `COMPANY_CHANGE` 审计） |
| 无依据 | 不显示 |

> 文案只用上表几句；设计稿的「Matched via participant name in meeting invite」没有对应的匹配方式，不用。

**未采纳的正文提及候选**（P1 的 `low`，及按类型规则没采纳的 `high`，如 GS → 创始人反推出多家、公司方只来自 P8 且与推断机构对不上，2.1）连同依据留在识别结果里（`adopted` 为否，9.5.9），页面是否展示以设计稿为准；管理员要加时用下拉添加，依据记人工指定。GS → LP 没有候选。

**下拉候选**：当前用户**有权限的公司**（Super Admin 与带 `seeAllPortfolio` 的 PGM 为本租户全部，9.1），**只列本租户的公司**（含下级节点，1.1）。在营公司在前，不在营的（Exited / Shut down / Off journey）在后并标出状态；状态为空按 Thriving（2.1），不标 `No status`。已识别但不在当前用户权限内的公司照常以标签展示，只是下拉里搜不到。

#### 9.5.4 Portfolio 标记

可多选、默认不选、非必选；仅为标记，不作任何权限依据（《Fireflies Summary Records》）。

**GS → 创始人**时不可选，只读实时显示 Company 所列公司所属的 Portfolio（同知识库页 Portfolio 列），不存、不激活按钮；会议原有的手动标记保留，改判为其他类型后照常显示与编辑。

| 项 | 口径 |
|---|---|
| 候选 | 当前用户有权限的 Portfolio，可搜索；Super Admin 为本租户全部（`company_group`，按 `organization_id` 圈定） |
| 用途 | GS → LP 基金层内容的**基金标签**（基金层归属机构、不建基金实体，1.1 / 3.3），知识库页基金层行（无公司）的 Portfolio 列显示它（9.11.2）。本租户 Portfolio 名称列表同时是本机构的基金清单，供基金层过滤识别 GS 自己的基金（1.7），取调用当时现存的 Portfolio（不存名称快照） |

| 存储 | `ff_meeting_state.portfolio_ids`（9.5.9），存 Portfolio id；机构层条目经会议溯源取得，**改标记不重提取、不重投影**。Portfolio 被硬删后接口只返回仍存在的，不专门清理 |
| 生效 | 选择变动 → 激活 `Confirm & Apply Routing`；不激活 Start Extraction |

#### 9.5.6 专家推测

需求见《Fireflies Summary Records》与《AI Meeting Type 自动映射标准》「特殊说明 · 专家推测」；识别侧规则见 1.11，本节只管页面。

**候选**：P7（6.10）对 GS → 创始人 / GS → LP / GS → Partner 各跑一次，程序按 ≥ 2 条实质性主张的门槛给出候选（发言人、建议标签、主张与依据；一人可多个标签，1.11）；GS 内部不调用。以下在调用前排除、回来后再挡一次，**不显示徽标、不进建议标签**：

| 过滤 | 依据 |
|---|---|
| GS 人员（GS 域名、管理端用户及其域名、注册表或 P8 推断的 `GS staff`） | 也不产出证词 |
| 角色为 Other 的人（名册或 P8 推断） | 也不产出证词 |
| 此人已有的专长标签（会议日期生效版本） | 只推测还没有的；已是专家的人也会被推测新标签，同样显示 `Possible expert` |
| 拒绝名单中的（邮箱，标签），按人查 | 只挡这个标签 |

候选只在提取后才有（待识别会议首次提取前不会出现 `Possible expert`）；重新提取产生的建议标签同样要先处理完才能应用（9.6.5）。

**点击姓名 → 专家确认框**：

| 区块 | 内容 |
|---|---|
| 登记字段 | 同 9.5.5 弹框与会议页规则：Name（已在册只读；未在册可订正、失焦查重）、Email(s)（本场邮箱锁定）、Organization、Role（LG 平台用户同样可改，开发设计 7 #Q47）、Expertise tags、Area of expertise、Validity period（须含会议日期；已在册的整份预填会议当日生效那一版含原有效期，新登记默认 From = 会议日期、To 空） |
| 建议标签 | AI 推测的标签（取自 Cheat Sheet 标签清单）**预填进 Expertise tags**，可区分显示为「建议」；已在拒绝名单的不预填，已在当日那一版里的就是普通已有标签。**留下即同意，删掉即驳回**，不逐个点；每个标签各记同意或驳回（开发设计 7 #Q45） |
| 按钮 | `Save`（不要求逐个处理；首轮加工未完、提取进行中置灰，证词补抽进行中不置灰，开发设计 7 #Q51）/ 关闭（什么都不写，徽标保留） |

确认框不展示 AI 的推测依据，不设小节标题与说明文字（开发设计 7 #Q82）；依据照旧落库（9.5.10）。未在册的外部人新建时，保存前同 9.7.4 弹二次确认（姓名提交后不可改）；LG 平台用户 Name 取账号姓名、只读，不弹。

**`Save` 一律写名册**（开发设计 7 #Q51），只追加一条完整记录、旧行不改（同 9.7.2「订正」，开发设计 7 #Q44）：未在册的新建（必填、重名加后缀、邮箱查重同 9.7.4，有效期须含会议日期）；已在册的以会议当日那一版为底，有改动才写；Expertise tags 为空也照建 / 照追加。已知（弹框不提示）：新记录与别的版本区间重合时按「写入最晚」覆盖（9.7.2）；有效期起点早于会议日期时标签从那天起生效；会议日期之后另起的版本不带这次改动。

| 动作 | 结果 |
|---|---|
| **留下建议标签**（同意） | 随登记写入 Cheat Sheet（来源 `From FF Summary Records`），此人从生效日起即为专家；此后仍会就他还没有的标签推测 |
| **删掉建议标签**（驳回） | 本次建议标签 − 保存后的 Expertise tags 记进**拒绝名单**，Java 与名册写入同一事务；此后任何会议不再就这个标签推测他 |
| 建议标签全删 | 名册照写（未在册的照建、照校验），建议标签全进拒绝名单，徽标消失。已知：只想驳回的未入册者也要填齐必填项进名册 |
| 保存之后 | 关窗调同步（9.5.7）：刷新此人识别结果，建议标签记为已同意 / 已驳回；构成参会人改动的（如改了角色）激活 Start Extraction；只改专长标签的即补抽证词（开发设计 7 #Q83），名册里已没有专长标签的原有证词行软删（2.5，开发设计 7 #Q87） |
| 该（邮箱，标签）已入册或已在拒绝名单（别场处理过，或在 Cheat Sheet 直接加过） | **自动消解**：已入册的是已有标签，已拒绝的不预填；保存后的同步一并记为已同意 / 已驳回。专家标记每场单独处理，不跨会议联动（第十章 #63） |

**LG 平台用户被确认为专家**（典型是 GS → 创始人会上的创始人）：同样建名册条目（姓名取账号姓名、只读；角色预填 `Founder`、可改），建议标签全驳回也建（开发设计 7 #Q51）；此后角色以他会议当天生效的记录为准（含改离 Founder 后不再挂被投公司，1.9 ②，开发设计 7 #Q47），不论记录从哪里建；Cheat Sheet 单独标出 `LG user`（9.7.3、9.7.4，第十章 #13）。

**拒绝名单**（Java 表，9.5.10）：只记本场所用邮箱 + 标签；查询（推测前排除、校验、自动消解）按人展开，本场邮箱或此人名册各版本任一邮箱命中即算已拒绝。没有撤销入口，误拒的在 Cheat Sheet 给此人加该标签。

**确认后只补抽证词，不重新提取整场**：同步把每个建议标签记为已同意或已驳回后 `Confirm & Apply Routing` 才可点（1.10）；补抽按专家此时的全部标签整块重抽 P5、替换他本场的证词行（2.5；开发设计 7 #Q83、#Q85），范围与排队见 9.5.7。

#### 9.5.7 回填注册表

本页登记的人**自动写入 Cheat Sheet**，带 `From FF Summary Records` 来源标识（《会议内容提取规则》III /《Summary Records》）：

| 入口 | 写法 |
|---|---|
| `Assign new external party`（下拉里叫 `Create new person`） | 经 Python 登记：LG 平台用户不入名册；填的邮箱在名册某人会议当天生效的记录里——认成他、不新建、名册不改；在名册里但不在当天那版里的拦下、提示先去 Cheat Sheet 调整（开发设计 7 #Q49）；绑未对上的说话人；写公司候选。其余情况新增一条，`Updated by` 记为系统导入并标明来源会议（如 `System (FF-09 import)`） |
| `Edit external party` | 前端直接调 Java，**追加一条完整记录**、旧行不改（9.7.2）；没有改动时不写、也不记复核（9.7.5）。写之前先经 Python 核对页面没过期、会议不在处理中，过期或处理中不写名册（开发设计 7 #Q91） |
| `Link existing person` | 同 `Edit external party`（来源是参会人时含本场邮箱）；随后同步本场（参会人），或经 Python 按邮箱认人把说话人绑到此人（9.5.5，开发设计 7 #Q53） |
| 专家确认框 `Save` | 前端直接调 Java，一律写名册（9.5.6，开发设计 7 #Q51）；填的邮箱已登记在名册别的条目里拦下（9.7.4）；拒绝名单同一事务写 |

每次保存只往名册写一条，有效期须含会议日期，Java 校验拦截（开发设计 7 #Q44）。

**关窗后同步**（`Edit external party` 与专家确认框）：保存成功即关窗，前端再请 Python 按名册现状同步本场，可重复调用：

| 同步发现 | 处理 |
|---|---|
| 总是 | 按会议日期生效的记录刷新此人识别结果（平台用户按开发设计 7 #Q47 以记录的角色为准；新建的人按返回的姓名找记录，拿不到时——如上次同步失败后重开——按本场邮箱找当天生效的记录）；建议标签在名册里的记已同意、在拒绝名单里的记已驳回 |
| 有参会人改动（9.9.1，与提取输入比） | 激活 Start Extraction；类型不自动改、不提示，由管理员手动选（9.9.3） |
| 没有参会人改动（含只改了专长标签） | 本场所有专长标签与提取输入不同的专家（不只这次保存的人），同步提取输入里的标签、排进补抽（一次一人），页面轮询、补完刷新；补抽期间 `Confirm & Apply Routing` 与 Start Extraction 置灰（2.5；开发设计 7 #Q83、#Q86、#Q87） |

首轮加工未完或提取进行中时不同步、提示稍后重试，两个弹框的 `Save` 置灰；证词补抽进行中照常同步、`Save` 不置灰（开发设计 7 #Q51），已有人在补抽时此人排队（开发设计 7 #Q86）。组织改了不重新匹配公司（9.9.2）。**不保存直接关窗**：什么都不写。

- **姓名冲突**：新建时重名（忽略大小写）不拒绝、不合并，自动加后缀（`Tom` → `Tom1` → `Tom2`），失焦即提示；三个新建入口相同（9.7.4，开发设计 7 #Q46）
- **邮箱冲突**：`Assign new external party` 按邮箱认人（见上表）；`Edit external party` 与专家确认框填的邮箱已登记在别的条目里直接拦下（9.7.4，开发设计 7 #Q49）。参会人未挂名册条目、但本场邮箱已在某条记录会议当天生效的版本里时（如会后才在 Cheat Sheet 加了他或调了有效期，或新登记成功但关窗同步失败），打开详情页时按本场邮箱现查、按**已在册**展示：按那条记录预填（姓名只读），保存在其上追加一版（没改动不写），同步按本场邮箱把他挂上；邮箱在名册里但不在当天那版里的，保存照旧被拦、提示先到 Cheat Sheet 调整（开发设计 7 #Q51 ⑤）

登记弹框 `Confirm`、专家确认框 `Save` 即写注册表，**不随页面 `Discard Changes` 撤销**，写错了再编辑一版（9.7.2）。

#### 9.5.8 保存与生效

| 改动 | 怎么提交 | 何时生效 |
|---|---|---|
| 类型、公司 | 点 Start Extraction（改为 `Unknown` 的点 `Confirm & Apply Routing`，9.9.2） | 点击即整场下线旧产物；提取后落了行转 `Pending`（待审核），应用后上线（9.5.1，开发设计 7 #Q81） |
| 参会人登记 / 专家确认与拒绝 | 登记弹框 `Confirm`；专家确认框 `Save` | 立即写注册表 / 拒绝名单，关窗后同步本场（9.5.7）；只改专长标签的即补跑 P5（2.5）；构成参会人改动的要经 Start Extraction（9.9.3） |
| Portfolio 标记（GS → 创始人无此项） | `Confirm & Apply Routing` | 应用时 |
| 矩阵内容、授权 | 见 9.6.5 | |

- 参会人登记**不自动回溯本场**（要点 Start Extraction），专家标签变了的单人补抽除外（2.5）；对本租户其他会议的影响见 9.9.3
- 登记与关联不另写审计：名册行带来源会议与操作人（9.7.1），识别结果带绑定方式与操作人（9.5.9）；由此触发的重新提取记 `EXTRACT`（9.10.2）

### 9.6 Content Routing Matrix

矩阵三列：`Content`（内容块，可编辑）、`Visible to`（谁能看到这一行）、`Authorize`（勾选则授权）。

#### 9.6.1 矩阵从哪来

矩阵是中间表（9.6.4）按去向铺成的呈现，不是独立数据。

- `Pending` 会议初次进来时矩阵为空，补齐必填项、点 Start Extraction 后才出现；GS → 创始人只差公司的也可能由自动路由产出（9.9.3）
- 页头类型、公司、参会人改动后点 Start Extraction 整场重新提取（9.9.1、9.6.4）
- GS → LP 不按公司拆分，公司增删不触发提取

#### 9.6.2 行的构成：按会议类型

#### 9.6.3 Content 编辑

**整格编辑**：保存整段字符串，改动后该格琥珀高亮边框。各行都是 markdown，平时渲染，右下角 `Edit` 换成 markdown 编辑器，Cancel 或保存成功后回到渲染态；证词来源行只读显示在正文上方，不进编辑器。

「每行一条 bullet」只是排版约定，系统不做逐条增删改与排序：提示词输出保持字符串、要求一行一条（6.5（P2）~ 6.9（P6）；证词与跨公司每条 1~3 句一段、不用列表）；中间表 `content` 是文本字段（9.6.6）；`CONTENT_EDIT` 记改前改后整段文本。

**跨公司与证词行整块编辑**（开发设计 7 #Q77）：一个编辑框、一个 `Authorize`；不想放行某一条就删掉那一段。段首标签与段间空行只是排版，删改它们只改变证词的切片粒度，来源行仍由程序补在每片前（1.3）。

摘要行 **≤150 个英文单词**（1.3，词数口径同 6.11「修订调用」），超长不允许保存。

**行内 `Save` / `Cancel`**：只作用于该行。

**保存时重跑清洗**：

| 重跑什么 | 说明 |
|---|---|
| **n-gram 近逐字剔除** | 与原转录比对（阈值同提取时，1.4），命中删整行（摘要写成一段的按句删），同 6.11 步骤 2 |
| **该去向适用的实体剥离** | 只对 Cross-Company 与证词两版（1.4 / 1.5），清单与匹配同提取时：实体直接替换为泛指（不走实体改写，开发设计 7 #Q62），精确数值删所在句；1a / 1b / Founder KB / Portfolio KB 不剥离 |
| **不重跑 LLM 改写** | 人工措辞即所要；n-gram 兜住从原文粘贴回来的情况 |

**两步提交**：

1. `Save` → 服务端清洗、**不落库**，返回清洗后文本与命中明细（删去的行及原因、替换的实体）
2. 无命中直接落库；有命中回显，管理员确认后落库或继续改；清洗后为空不能确认，直接提交空内容也拒绝

落库后：已授权 → 立即重投影（9.6.4；会议 `Pending` 时不投影，等转 `Passed` 统一投影，开发设计 7 #Q75；摘要行在正文在线时只替换 `summary` 与摘要向量）；未授权 → 只改中间表。证词行只改这一版，来源行由程序按版本重新附加（6.11）。

**编辑入口只有本矩阵**（9.1）：Goldie Base 的 Cross company content Tab 只读（Play candidate 除外，9.11.6）。

#### 9.6.4 Authorize 与落库时机

**`Authorize` 是放行开关**：勾选后 `Visible to` 里的角色才看得到，未勾选的不进 RAG、Goldie 召不回。勾选只表示授权：已授权的行在会议 `Passed` 后才投影，`Pending` 会议的行只落中间表（1.10，开发设计 7 #Q75）。

```
提取完成 ──→ 中间表（行粒度见 9.6.6，始终保留）
              │
              ├─ 已授权 ──→ 投影：生成 markdown + 写知识库条目（TEXT 来源）+ 登记（1.1 / 1.3），Goldie 可召回
              └─ 未授权 ──→ 只在中间表，管理端可见、Goldie 不可见
```

中间表是矩阵的**可编辑正本**，知识库条目由它派生；只有一套行，不分当前版本与草稿。

**不设草稿**：点 Start Extraction 即保存页头（类型、公司、参会人写进识别结果，9.5.9），本场旧产物整场下线——中间表行、专家候选与知识库条目软删，未处理的候选置撤下——再整场重新提取。成功：按授权初值落库，落了行即置 `Pending`（待审核）、先不投影，`Confirm & Apply Routing` 后转 `Passed` 才投影（9.9.5，开发设计 7 #Q81）。失败：转 `Pending`（待识别 · 提取失败），旧内容不恢复，可再点。已知：提取期间 Goldie 召不回这场会。人工措辞、勾选与 Play candidate 都不保留（措辞可从 `CONTENT_EDIT` 找回，9.9.4）。未应用的勾选与 Portfolio 标记离开页面不保存。

中间表行另带 `in_playbook`（Play candidate，默认关，9.11.6），只作候选标记，不影响授权、投影与 Playbook 召回。

**证词行**另存 `speaker_participant_id`（9.6.6），姓名、组织、角色与按会议日期回溯的专长标签（3.4）都按它关联参会人表取；来源行由程序生成，矩阵只读显示、投影时拼进正文首行（6.11），Expert Testimony Tab 也按它显示（9.11.5）。

**初始授权状态**

| 场景 | 初始状态 |
|---|---|
| 识别齐全、自动提取完成（含自动路由，9.9.3） | **默认已勾选**；会议 `Passed` 时同时投影，`Pending` 时先不投影。例外见下两行 |
| └ 所有类型的 **Cross-Company** 行 | **默认不勾**，审核后发出；会议因此置 `Pending`（待审核，1.10） |
| └ 发言人经 6.13（P8）识别的**专家证词**行（两版）：P8 推断了他的身份、把他对到名册，或把他的说话人对到参会人 | **默认不勾**，核对身份后放行；会议因此置 `Pending`（待审核，1.10）。程序按邮箱识别、按姓名对邮箱前缀配上说话人的照旧默认勾 |
| 人工点 Start Extraction 后的提取（含 `Pending` 会议人工指定后的首次提取） | 勾选同上；落了行即置 `Pending`（待审核，1.10），应用后才投影（9.9.5，开发设计 7 #Q81） |
| 已提取过的会议再次 Start Extraction | 见 9.9.5 |

**会议 `Pending` 时整场不投影**（开发设计 7 #Q75）：有待审核行置 `Pending`（待审核），有未处理的专家标记置 `Pending`（待确认专家，建议标签全部通过或驳回后才能应用，1.10）；`Confirm & Apply Routing` 转 `Passed` 后按勾选投影。重新提取或改 `Unknown` 应用时，未处理的标记一并撤下、不写拒绝名单。**确认后补抽的证词默认勾选**（2.5，开发设计 7 #Q83、#Q87），优先于本表，经 P8 识别的也勾（确认框已核对身份并入册）。

人工放行 = 在本矩阵勾 `Authorize` 并 `Confirm & Apply Routing`，与 Pending 会议处理同一页面、同一套按钮；不另建审核队列，不做批量操作。

**投影操作**

知识库条目没有内容更新接口，改内容 = 写新条目后软删旧条目；只动摘要行不重写条目（开发设计 7 #Q42）。顺序与失败处理见 1.6。

| 操作 | 中间表 | 知识库条目 |
|---|---|---|
| 编辑 `Content`（`Save`） | 更新 | 已授权且已生效 → 写新条目、成功后软删旧条目（会议 `Pending` 时不投影，开发设计 7 #Q75）；摘要行只替换 `summary` 与摘要向量；未授权 → 不动 |
| 勾选 `Authorize`（应用后） | 置为已授权 | 按当前内容写入；摘要行写进正文在线的条目，正文未授权时不生效（9.6.2） |
| 取消勾选（应用后） | 置为未授权，**内容保留** | 正文行：软删条目与登记行，摘要随之下线；摘要行：只清空 `summary` 与摘要向量（开发设计 7 #Q42）。Goldie、Memory 页、知识库页立即同步消失；同步执行，失败见 1.6 |

取消勾选可逆，重新勾上按当前内容恢复。已被下载到本地的旧文件不追（1.3）。

> 未授权只能靠"不写入"保证：检索侧除 `company_id` 外不做行级过滤（3.4 批注）。
>
> 6.11「后置程序步骤」的落库一步即**中间表 → 知识库**的一次投影，范围由授权状态决定。

#### 9.6.5 保存与生效

| 改动 | 提交方式 | 理由 |
|---|---|---|
| **Content 编辑** | 行内 `Save` / `Cancel`，只作用于该行 | 要逐行回显清洗结果（9.6.3） |
| **提取输入**：类型 / 公司 / 参会人 | `Start Extraction`：整场下线、重新提取（9.6.4） | 旧产物整场作废，没有可预览的中间态；补抽出的证词同样直接替换（2.5） |
| **路由级改动**：`Authorize` 勾选、Portfolio 标记、类型改为 `Unknown` | 页面级 `Confirm & Apply Routing` / `Discard Changes` | 授权与改判往往要一起判断 |

**`Confirm & Apply Routing`**：一次性应用全部路由级改动——勾选（新勾上的异步投影、取消的同步下线，1.6）、Portfolio 标记；改 `Unknown` 的整场下线、打回 `Pending`（9.9.2）。会议状态应用时即切换，不等投影。`Pending`（待确认专家 / 待审核）会议应用后转 `Passed`，已勾选的行此时整批投影（开发设计 7 #Q75）。

**应用时不补证词**（开发设计 7 #Q87）：标签变了的专家都在保存后即补（2.5）；补抽进行中（含排队）该按钮置灰。

**`Discard Changes`**：只撤销页面上未提交的改动（未点 Start Extraction 的页头类型与公司、未应用的勾选与 Portfolio 标记）。不撤销已 Save 的行、名册写入与专家确认 / 拒绝（9.5.7）、补抽出的证词（2.5）、已点过的 Start Extraction。

**按钮状态**：

| 情形 | `Confirm & Apply Routing` | `Discard Changes` |
|---|---|---|
| 无未应用的路由级改动 | 置灰 | 置灰 |
| 只改了授权勾选 / Portfolio 标记，或 GS → LP 的公司增删 | 激活 | 激活 |
| 改了类型、公司（不含 GS → LP：其 Company 不参与路由，9.5.3）或参会人（口径见 9.9.1），但还没点 Start Extraction，或提取进行中 | **置灰**——页头与矩阵不一致 | 激活 |
| 类型改为 `Unknown` | 激活（提取或证词补抽进行中除外）——应用即打回 Pending（9.9.2），不弹二次确认 | 激活 |
| GS → 创始人且 Company 多于一家 | **置灰**（2.3） | 激活 |
| 有「可能为专家」的建议标签未处理 | **置灰**——全部通过或驳回后才激活；改 `Unknown` 不受此限（1.10） | 激活 |
| `Pending`（待确认专家 / 待审核），标签已全部处理，页头与矩阵都没有其他改动 | **激活**——点击即审核完成（未勾选的不放行），转 `Passed`（1.10） | 置灰 |
| 证词补抽进行中（含排队中） | **置灰**（2.5） | 激活 |

上表自下而上优先，后面的行命中即按后面的行。置灰时不提示原因。

**应用前的二次确认**（开发设计 7 #Q48）：三条硬拦（参会人改了未重提、建议标签未处理、GS → 创始人多于一家公司）与提取 / 补抽进行中，统一由服务端在应用时校验（开发设计 7 #Q51）；另有一种只需确认的情形，服务端重算命中即弹框列出，确认后再应用：

| 提示 | 情形 |
|---|---|
| 类型不一致 | 按当前参会人重跑类型判定，结果与当前类型不同（提示可判定为哪一类） |

不校验 GS → 创始人会议 Founder 的组织或公司与关联公司是否对得上（公司在 Start Extraction 时已定，9.5.1）。应用时不重读最新 Cheat Sheet，用会议自己的识别结果。有行在编辑未保存时，先提示该行 `Save` 或 `Cancel`。

**并发**：页面已过期的提交被拒，页面顶部错误提示条 `This page is out of date. Refresh the page.`，不弹框、不自动刷新（开发设计 7 #Q54）；同一场会写操作串行、同时只有一个提取任务（详情页加载时返回 `ff_meeting_state.updated_at`，写操作带回做条件更新，0 行即过期，9.5.9）。

每次应用写审计（9.10），含改了哪些行、授权了哪些去向；行内 `Save` 各写一条 `CONTENT_EDIT`。

#### 9.6.6 数据模型：路由中间表

**行粒度**（第十章 #38）：一行 = 一个 Authorize 格（1.6）；知识库去向的摘要行与正文行合投一条条目（开发设计 7 #Q42），跨公司与证词一行一条条目。

| 去向 | 一行是什么 | 每场行数 |
|---|---|---|
| APP 知识库 | GS → 创始人的摘要（1a + 1b）或正文（Founder KB + Portfolio KB） | 0 或 2（只能有一家公司，2.1） |
| ADMIN 知识库 | GS 内部 / GS → Partner 一家公司的摘要（1b）或正文（Portfolio KB） | 每家采纳的公司两行 |
| 机构层 | GS → LP 的基金层摘要（1b）或正文（Portfolio KB） | 0 或 2 |
| Cross-Company | 一场会的全部跨公司内容合成的一块（开发设计 7 #Q77） | 0 或 1（0 条不写行） |
| 证词-匿名 / 证词-署名 | 一位发言人本场全部证词合成的一块的两版（开发设计 7 #Q77） | 每位发言人两行 |

摘要行与正文行以 `output_type` 区分、共用 `file_id`（开发设计 7 #Q42）。不建唯一约束：同一（去向, 公司, 产出类型）未软删的只有一行，证词为同一（去向, 发言人）一行，由写入逻辑保证（开发设计 P7）。

**`ff_routing_row`**

| 字段 | 说明 |
|---|---|
| `id` | 主键；审计里的中间表行 id 即它（9.10.2） |
| `organization_id` / `meeting_id` | 租户与所属会议 |
| `destination` | 去向，上表六种之一，对应 1.1 的空间，决定投影空间与 `Visible to`（9.6.2）。取值见开发设计 1.4（基金层为 `FUND_LEVEL`） |
| `company_id` | APP / ADMIN 知识库行必填（6.11 步骤 7），其余为空（1.2） |
| `output_type` | 摘要 / 知识库正文 / 跨公司 / 证词（开发设计 7 #Q9） |

### 9.7 Cheat Sheet

平台外人员的登记表。字段口径见 **5.2**，"专家"的判定见 **1.11**；页内另有 Email Domain 一块（9.7.7）。

#### 9.7.1 数据模型：单表存版本

**一张表，一行一个版本快照**，不设主体表。

**`ff_cheat_sheet`**（物理字段以开发设计 J4 为准）

| 字段 | 说明 |
|---|---|
| `id` | 主键；一行即一版，「哪一版」用 `id` 表示（识别结果的 `cheat_sheet_id` 记它，9.5.9） |
| `organization_id` | 租户 |
| `name` | **唯一识别符**，确认发布后不可改；`(organization_id, name)` 标识一个人 |
| `emails` | 可多个 |
| `organization` | 外部机构名，自由文本 |
| `role` | 6 项枚举之一（5.2）：LP、Strategic Partner、Exit Partner、Founder、GS staff、Other |
| `expertise_tags` | 多选，存**标签文本**而非字典外键；非空即为专家（1.11） |
| `area_of_expertise` | 自由文本，仅作描述，不参与路由；不超过 2048 字 |
| `valid_from` / `valid_to` | From 必填，To 可空（空 = `present`） |
| `source` | `MANUAL`（Cheat Sheet 页新增）/ `FF_SUMMARY_RECORDS`（审核会议时登记，含专家确认） |
| `source_meeting_id` | 会议页登记或专家确认时的来源会议 |
| `updated_by` | 操作人 |
| `updated_at` | 写入时间，**重合裁决的依据**；复核不改它（9.7.5） |
| `reviewed_by` / `reviewed_at` | 最近一次「看过无需修改」的复核人与时间（9.7.5），可空；不参与裁决 |

**每次 Confirm 追加一行**（会议页编辑与专家确认同样只追加一条完整记录，9.5.7，开发设计 7 #Q44），不改旧行（复核字段例外，9.7.5）。

| 要什么 | 怎么取 |
|---|---|
| 列表的当前状态 | **最后保存的那一版**：`updated_at` 最晚，相同再按 `id`；不看生效日期与今天（开发设计 7 #Q68）。即 History 最上面那行（9.7.6）。已知：补录旧时段、从旧会议页追加的记录（9.5.7）写入更晚，列表随之显示这条可能已结束的版本，要换回须对当前那一版有改动再保存（9.7.5）。不走 9.7.2 的按日期裁决 |
| History | 该 `(organization_id, name)` 的全部行 |
| 某场会议当时的登记 | 9.7.2 的回溯算法 |
| 最近复核时间 | 此人全部行的 `updated_at` 与 `reviewed_at` 中最晚的（9.7.5） |

姓名唯一性没有数据库约束，重名在应用层处理（9.7.4，开发设计 7 #Q46）；三个新建入口（本页 `Add external party`、会议页 `Assign new external party`、专家确认框）共用（9.5.7）。

**被引用时用姓名**：识别结果以 `(organization_id, name)` 为引用键（证词发言人存参会人 id，开发设计 P7）；另记当时的版本行 id，只作留痕（9.5.9）。

**`Founder` / `GS staff` 角色**：指未使用 LG 平台的创始人与 GS 人员。LG 平台用户也可能在名册里有记录（专家确认框保存时会建，建议标签全部驳回也建，9.5.6；也可能在本页添加）；有会议当天生效的记录时，角色以这一条为准（1.9 ②，开发设计 7 #Q47）。这类条目在列表与编辑弹框姓名旁显示 `LG user`（9.7.3、9.7.4），不加字段、按邮箱现算（开发设计 7 #Q51）。

#### 9.7.2 有效期与版本裁决

**允许重合，重合时取 `updated_at` 最晚的**，不是 `valid_from` 最晚的；不自动闭合上一版的有效期。

**订正**（改错别字、补邮箱）：有效期不变再提交，新版本区间完全重合、写入更晚，自然生效；不单设"订正"操作。

**按会议日期回溯的取值算法**（1.8 的姓名回退、1.9 的注册表匹配、1.11 的专家判定、6.11 的标签回溯共用）：

```
取该 party 下满足 valid_from <= 会议日期 <= COALESCE(valid_to, 无穷) 的全部版本
 → 按 updated_at 降序取第一条
```

> ⚠️ **邮箱匹配（1.9）也走这套回溯，不能只用最新版本的邮箱**（否则换过邮箱的人在旧会议里匹配不上）。角色、专长标签、邮箱三者回溯规则一致。

#### 9.7.3 列表

**顶部汇总条**：不做，逾期只靠 `Needs review` 标记（9.7.5），接口不返回逾期条数。

**列**：Name、Email(s)、Organization、Role、Expertise tags、Validity period，行末 `History` / `Edit`。Area of expertise 只在弹框与 History 展示。

| 列 | 展示 |
|---|---|
| Name | 审核会议时导入的在姓名下方加 `From FF Summary Records` 标签；LG 平台用户加 `LG user` 标记：当前状态那一版（9.7.1）的任一邮箱命中本租户 LG 账号即显示，口径同 1.9 ②（本租户管理端用户、本租户公司的公司端用户，含下级节点，忽略大小写）；取列表时现算（开发设计 7 #Q51） |
| Email(s) | 多个**纵向堆叠全部展示**，放不下再用省略号 |
| Role | 蓝色标签 |
| Expertise tags | 灰色小标签，多个换行展示 |
| Validity period | `Aug 2, 2026 – present`；逾期未复核的在下方加琥珀 `Needs review` 徽章 |

**搜索**：模糊匹配 Name、Email(s)、Organization、Expertise（专长标签与 Area of expertise）。**筛选**：按 Role。**分页**：每页 10 条（可选 10 / 20 / 50），样式同 Raw Data（9.3.3，开发设计 7 #Q43）。

#### 9.7.4 新增与编辑

`Add external party` / `Edit` 字段相同，差别只在 Name：

| | Add | Edit |
|---|---|---|
| Name | 可填 | **置灰只读**；LG 平台用户在姓名旁标 `LG user`（9.7.3，开发设计 7 #Q51） |
| 其余字段 | 空 | 带入当前状态那一版（9.7.1） |

**字段**：

| 字段 | 控件 |
|---|---|
| Name | 文本 |
| Email(s) | 可多个，支持 `+ Add another email` 与逐行 × |
| Organization | 文本 |
| Role | 下拉，6 项固定（5.2） |
| Expertise tags | 下拉多选，取自专长标签字典，下拉内可直接新增（9.8）；**Role 为 LP / Strategic Partner / Exit Partner 时必填**，标签后带红色 `*`；Founder 选填；GS staff / Other 置灰（开发设计 7 #Q24d）。只在前端校验，Java 收空标签；专家确认框（9.5.6）不按角色必填，删光建议标签即拒绝 |
| Area of expertise | 自由文本，选填，不参与路由 |
| Validity period | 两个日历选择器，From 必填 / To 可空 |

Name、Email(s)、Organization、Role、Validity period（From）必填，带 `*`。没有邮箱的人不录入（第十章 #59）；没有邮箱又发了言的是未对上的说话人，在 Summary Records 处理（9.5.5，第十章 #92）。

弹框内提示文案：`"From" is required. Leave "To" empty to show the period as open-ended — e.g. "Aug 2, 2025 – present".`

**Confirm 前弹二次确认**，告知姓名提交后不可编辑。

**姓名重复**（开发设计 7 #Q46）：姓名租户内唯一（忽略大小写）；新建重名不拒绝、不合并，自动加后缀——从 1 起取第一个未占用的编号（`Tom` → `Tom1` → `Tom2`，忽略大小写）。

| 时机 | 做法 |
|---|---|
| `Add` 时姓名输入框失焦 | 查重；重名时在姓名下方提示 `A Cheat Sheet entry with this name already exists. It will be saved as Tom1.`（文案可微调） |
| 保存 | 按同一规则再算，以保存时为准，返回最终姓名 |

同一个人应去 `Edit`。`Assign new external party` 与专家确认框的新登记同此（9.5.5、9.5.6）。已知：换了邮箱又没填在册邮箱的人会建成 `Tom1`，没有合并功能，由管理员自行维护。

**邮箱重复**（开发设计 7 #Q49）：`Add` / `Edit` 填的邮箱（忽略大小写）已登记在别的条目（任一版本；`Edit` 不算本条目自己的版本）即拦下，弹框内提示登记在谁名下（`This email is already registered to Tom in the Cheat Sheet.`，文案可微调），不新建、不合并。`Edit external party` 与专家确认框同此（9.5.6、9.5.7）；`Assign new external party` 则按邮箱认成名册里的那个人、不新建（会议当天生效的记录里没有该邮箱时拦下，9.5.5）。

#### 9.7.5 Needs review

此人最近复核时间（9.7.1）距今超过 90 天即标记。**不单设"复核"按钮**，任何一次 `Edit` 提交即刷新。

**"看过但无需修改"**：`Edit` 弹框不改直接 `Confirm` 时**不追加新行，只在弹框带入的那一版记 `reviewed_by` / `reviewed_at`**（开发设计 7 #Q70）；**`updated_at` / `updated_by` 不动**（否则旧版本会压过新版本，9.7.2）。Summary Records 页的 `Edit external party` 带入会议日期那一版，不改直接 Confirm 不记复核。

#### 9.7.6 History

独立页面，不做行内展开。面包屑 `Fireflies / Cheat Sheet / Role History`，前两级可跳回。标题 `<姓名> — Role History`。

**每行一个完整快照**：Name、Email(s)、Role、Organization、Expertise tags、Area of expertise、Validity period，外加 Updated by（含更新日期）。角色蓝色标签，专长标签灰色小标签。

**排序**：只按 `updated_at` 倒序，不看生效日期（开发设计 7 #Q68）；只记复核不影响顺序（9.7.5）。最上那行即列表的当前状态（9.7.1）。

**`Updated by` 显示实际操作人**（含 Summary Records 登记与专家确认的版本，来源看 `From FF Summary Records` 标签）；系统用户写入的显示 `System`。

#### 9.7.7 Email Domain

维护本租户机构自己的邮箱域名，识别链第 ① 级按它判定「属 GS 方」（1.9）；不是被投公司的域名（那个按公司 Team 域名，1.9 ③）。

| 项 | 口径 |
|---|---|
| 存储 | `ff_connection_configuration.email_domains`（域名数组，小写存），租户内不重复由代码校验。未 Link 也能配置——首次保存域名时建连接记录，状态 `Unconnected`；移除 key 只清密文，域名保留（开发设计 J1） |

### 9.8 专长标签维护

**标签是受控列表**（一张标签字典表），在 Cheat Sheet 的 Expertise tags 下拉内维护，没有独立配置页。

#### 9.8.1 取值与维护入口

**预置 7 项**：

```
Multiples、Buyer behavior、Exit trends、Software usage、Commercial buying behavior、Fundraising、Market
```

预置 7 项带定义（Fundraising、Market、Multiples 见 3.4，其余见 5.6），供证词抽取与专家推测；新增的标签不加定义，只按名字抽取与推测（开发设计 7 #Q85）。新建组织时写入，存量租户由迁移脚本补齐（开发设计 J5）；不做懒加载（Python 直读字典）。

**维护入口**：Cheat Sheet 新增 / 编辑弹框（及 Summary Records 页的同款弹框）的 Expertise tags 下拉——输入不存在的值时末尾出现 `Add "<输入值>"`，确认即加入字典并选中；未被使用过的标签旁带删除入口。

**排序**：预置 7 项在前，新增的按添加顺序追加，不做字母序。

**标签用在哪**：

| 用途 | 说明 |
|---|---|
| 专家判定 | 会议日期生效的版本带至少一个标签即为专家（1.11） |
| 证词抽取类别 | 每位专家只抽他会议当日生效版本的全部标签对应的内容，类别即标签（2.5、6.8（P5），开发设计 7 #Q85） |
| 专家证词来源行 | 匿名版首行 `Expertise: <expertise tag> · Meeting <YYYY-MM-DD HH:MM> UTC`；署名版首行 `Source: <Organization> <Role> <Name> · Meeting <YYYY-MM-DD HH:MM> UTC`（3.4） |
| 专家推测的建议标签 | 只就此人还没有的标签推测（字典全部 − 已有 − 已拒绝），主张直接归到最贴切的一个（1.11、6.10（P7），开发设计 7 #Q85） |

**不参与会议类型判定**：GS → Partner 只看角色（5.1）。

#### 9.8.2 数据模型

**`ff_expertise_tag`**

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `organization_id` | 租户，标签按租户隔离 |
| `name` | 标签文本，**租户内唯一**（不区分大小写） |
| `preset` | 是否预置 7 项（不可删，9.8.3） |
| `sort_no` | 展示顺序，新增追加在末尾 |
| `created_by` / `created_at` | 审计 |

**物理删除，不设软删**（只能删从没用过的，9.8.3）。

#### 9.8.3 增与删

**新增**：能进 Cheat Sheet 的管理员都可新增（9.1）。租户内重名（不区分大小写，`M&A` 与 `m&a` 视为同一个）直接拒绝并提示。

**删除**：

| 标签 | 能否删除 | 依据 |
|---|---|---|
| 预置 7 项 | **不可删** | 带定义，供证词抽取与专家推测（9.8.1，开发设计 7 #Q85） |
| 已被使用过的标签 | **不可删** | 《Cheat Sheet》「已被使用过的标签不允许删除」 |
| 新增后从未被使用的标签 | 可删 | 加错了的补救 |

**"被使用过"** = 出现在 `ff_cheat_sheet` 的**任一版本**（含历史版本），或被未处理的「可能为专家」标记（`ff_expert_candidate` 未软删、未处理，9.5.10）引用。

**不提供改名**：快照存的是标签文本（9.7.1），改名带不动历史；写错的在被使用前删掉重加。

#### 9.8.4 已使用不可删

快照与证词来源行里出现过的标签始终在字典里、始终可选（9.8.3）。已知：过时的标签只能留着。

### 9.9 改判与路由重算

#### 9.9.1 三种触发源

Review 页能改三样东西，改完点 Start Extraction **一律整场重算**（9.6.4）：

| 改了什么 | 影响什么 | 重算范围 |
|---|---|---|
| **会议类型** | 产物形态整体改变 | 见 9.9.2 |
| **公司增删**（类型不变） | 按公司分行的那些行 | **整场重跑**。GS → 创始人加第二家时按钮置灰（2.3）；GS → LP 不按公司拆分（3.3），公司增删不触发提取 |
| **参会人**（类型不变；口径见表下） | 可能改变类型判定（9.9.3）；类型不变时影响证词来源行与可抽的发言人 | **整场重跑** |

**参会人改动**：在本页登记、改登记或关联现有人员后，本场识别结果（是否识别、身份与角色、说话人对到谁、Founder 的组织）有变化，或本场有证词行的人改了组织，才算；只补邮箱、改 Area of expertise 等不算，不激活 Start Extraction、不让 `Confirm & Apply Routing` 置灰。

**专长标签改动不算参会人改动**（开发设计 7 #Q87）：专家确认框或 `Edit external party` 保存关窗后，前端调同步把名册新值带回本场（9.5.7，开发设计 7 #Q44）；只是专长标签 / Area of expertise 变了的，不激活 Start Extraction、不置灰应用按钮，保存后即为标签变了的专家补跑 P5（2.5，开发设计 7 #Q83、#Q87）；同时构成参会人改动的（如改角色）按参会人改动处理，点 Start Extraction 整场重跑（按新名册判专家，不另补）。

`Portfolio` 标记不触发提取（9.5.4）。

#### 9.9.2 按类型改判的重算范围

| 改判 | 重算 |
|---|---|
| `Pending` → 指定类型 | **首次提取**，按新类型跑完整流程；勾选同首次自动提取，落了行置 `Pending`（待审核），应用后才投影（9.9.5，开发设计 7 #Q81） |
| 任意类型之间 | **整场重跑** |
| 任意类型 → `Unknown` | 无需提取。`Confirm & Apply Routing` 后打回 `Pending`：中间表与知识库条目全部软删（可追溯），停止路由；未处理的「可能为专家」标记撤下，不写拒绝名单。这也是**手动改回 Pending** 的方式：已 Passed 的会议，已投影的 Memory 摘要、知识库文档与登记行一并软删（已知：此前放行的内容可能已被看到）。手动打回的会议不随 Cheat Sheet 增改自动重跑（9.9.3，开发设计 7 #Q89），等管理员重新定类型点 Start Extraction |

> **改回 Pending 后的去留**：原始数据（会议元信息、逐字稿）保留，Raw Data 页照常可看，含受邀的创始人（1.9）；Memory 摘要、知识库文档、跨公司内容、证词两版、中间表（内容、人工编辑、勾选、Play candidate）一并软删，不保留停用版本——选回类型一律重新提取，人工编辑只能从审计找回（9.9.4）；名册写入与专家确认 / 拒绝不回滚；审计保留。
>
> **「不想路由」与「判错类型」走两条路（页面上不提示）**：不想路由就取消全部勾选并应用（待确认专家的会议要先处理完建议标签），会议仍是 `Passed`、不占红点，以后重新勾上即可放行；判错类型才改 `Unknown` 打回 `Pending`（一直计入红点，没有「不路由」状态）。

**公司识别不重跑**（6.4（P1））。例外：GS 内部 / GS → Partner 在 Start Extraction 时补跑一次 P1，只取正文提及的公司——类型被改成这两类（与上次成功提取的类型比，从未成功提取过的按改了算），或首轮 P1 最终失败（开发设计 7 #Q50）。状态表不记「P1 当时做没做公司识别」（9.5.9 的 `identification_result`）。

#### 9.9.3 参会人登记与公司增改引起的连锁

在 Review 页登记此前未识别的外部人、或处理「未对上的说话人」（9.5.5），可能让 `Pending` 会议的类型变得可判定。登记提交后（`Edit external party`、`Link existing person` 与专家确认框在关窗后的同步里做，9.5.7）：

1. 重跑类型判定（程序，按 2.1 / 3.1 / 4.1 / 5.1 的规则）
2. 判得出也**不提示、不改判**：类型由管理员在页头手动选、仍要点 Start Extraction；与参会人不符时由 Confirm & Apply 的二次确认兜底（开发设计 7 #Q48）
3. 仍判不出 → 保持 `Pending`

**公司或公司端用户增改后自动路由**（开发设计 7 #Q90）：

| 项 | 口径 |
|---|---|
| 触发 | 本租户任一公司的新增或编辑（含状态变化）、任一公司端用户的新增或编辑；Java 保存成功后即时通知 Fireflies 模块（第八章 #27） |
| 匹配哪些会议 | 本租户 `Pending`（待识别）、类型已判为 GS → 创始人、只因定不出公司而待识别（Company 为空：仅凭 Cheat Sheet Founder 成立而正文反推不出，或公司方只来自 P8 而反推不出与推断机构同名的公司，2.1）、没有进行中提取的会议；多家公司、到场 Founder 归属不到、P1 最终失败的不在此列；只看会议日期在最近 90 天内的，更早的由管理员在详情页指定公司（9.5.3） |
| 怎么匹配 | 只对身份为 Founder、还没认出公司的受邀参会人（名册、P8 或本页登记识别的），用其邮箱按此刻的公司端用户与公司 Team 域名重跑 1.9 ②③；其余参会人身份不变，类型不重判；不调大模型，P1 / P8 不重跑 |
| 匹配成功 | 恰好认出一家在营公司，且认出的人在会议当日的名册机构或 P8 推断的机构（有的话）、其余还没认出公司的 Founder 都对得上这家（同 2.1 的比较口径） |
| 成功后 | 自动关联该公司（依据按 9.5.3 写），之后同首次拉取即认出公司的会议：自动提取，按自动提取的默认授权（6.11、9.6.4） |
| 不成功 | 会议原样不动 |
| 提醒与审计 | 不发提醒；成功的记 `IDENTIFY` / `EXTRACT`，`operator` 为 `System`，`triggered_by` 记做增改的人（9.10） |

**Cheat Sheet 增改后重跑相关 `Pending` 会议**（开发设计 7 #Q84、#Q89、#Q90）：

| 项 | 口径 |
|---|---|
| 触发 | Cheat Sheet 新增人员，或编辑后姓名、邮箱、机构、角色、有效期、专长标签任一有变化（新一版与上一版比，「看过但无需修改」不算）；不论从 Cheat Sheet 页还是会议详情页弹框改的；Java 保存成功后即时通知 Fireflies 模块 |
| 匹配哪些会议 | 本租户所有 `Pending` 会议（待识别、待确认专家、待审核），且与此人有关：参会人邮箱对上他改前或改后的任一邮箱、参会人已挂在他名下，或还没认出的参会人 / 还没对上的说话人的姓名与他改前或改后的姓名完全一致（同 1.9 ⑥）；会议日期落在他改前或改后的有效期内，且在最近 90 天内（更早的不重跑也不等，管理员点 Start Extraction 时按名册刷新参会人）。已认出、没挂名册、专长标签是识别时按同名名册补上的参会人不算 |
| 排除 | 在会议详情页里改名册的那一场（由关窗后的同步处理，9.5.7）；首轮未完、提取或证词补抽进行中的——等通知重投时再跑，不会错过（`Passed` 会议正在 Start Extraction 的也等，提完转 `Pending` 后重跑）；通知重投时已按它重跑过的不再重跑；改动之后才点 Start Extraction 的会议（提取前已按名册刷新）不重跑；管理员改成 `Unknown` 打回的不重跑也不等（等管理员重新定类型点 Start Extraction，同样按名册刷新）。重跑中途服务重启的那一场由定时清扫按识别失败收尾（待识别），交管理员处理 |
| 怎么重跑 | 每场从头重跑，同首次处理：撤下在线内容，清掉识别与提取产物（参会人、说话人、公司、建议标签、矩阵行），重新识别、再自动提取，按自动提取的默认授权与状态规则（6.11、9.6.4）。手动定过的类型、公司以重跑结果为准；人工编辑与勾选不保留 |
| 重跑期间 | 会议保持 `Pending`、留在列表里（Status 列不加新状态）；详情页照常打开，状态后显示提取中，识别完成前类型显示 `Unknown`、公司与参会人为空，各写入口置灰、提交被拒（提示稍后重试），每 5 秒刷新到跑完。重跑判为 `Invalid` 的状态清空、离开列表（开发设计 7 #Q92） |
| 提醒与审计 | 不发提醒；记 `IDENTIFY` / `EXTRACT`，`operator` 为 `System`，`triggered_by` 记改名册的人（9.10） |

**`Passed` 会议不自动重跑**：打开详情页时按会议日期生效的名册与本场识别结果比——挂了名册的参会人的姓名、机构、角色、专长标签有变，或有参会人的邮箱新对上了名册——有变化即 Start Extraction 可点（不加提示）；点击后先按名册刷新这些参会人再整场重提，提完 `Pending`（待审核），应用后才上线（9.9.5，开发设计 7 #Q81、#Q84）。

Email Domain 增改不触发，打开会议也不重新匹配，由管理员在详情页处理（指定公司见 9.5.3，登记参会人走上面 1~3）。管理员正打开着的会议被自动路由或重跑后，其提交按页面已过期处理（9.6.5），`Edit external party` 与 `Link existing person` 也在写名册之前拦下（开发设计 7 #Q91）；重跑进行中详情页显示提取中、提交被拒，跑完自动刷新（开发设计 7 #Q92）。

#### 9.9.4 重跑与人工编辑的冲突

**重跑直接覆盖**（9.6.4）：人工编辑随旧产物作废，不弹确认框、不保留人工条目。新内容停在 `Pending`（待审核），可逐行改内容、调勾选，应用后才上线（9.9.5）；上线后仍可逐行改、取消勾选。

**人工编辑可找回**：每次编辑都有 `CONTENT_EDIT` 审计（9.10.2，含改前改后全文），可查回重新填入。

**范围提醒**：

| 重算 | 被覆盖的范围 |
|---|---|
| 类型、公司、参会人任一改动（一律整场重跑） | 全部行，含已放行后改过措辞的 Cross-Company 行；Play candidate 标记一并重置 |

#### 9.9.5 重跑后的授权状态

提取成功后新行的勾选初值与首次自动提取相同，不沿用上一版（开发设计 7 #Q81）：

| 情形 | 授权初值 |
|---|---|
| 1a / 1b / Founder KB / Portfolio KB（含基金层）、证词 | **默认勾** |
| Cross-Company、发言人经 P8 识别的证词 | **一律不勾**（内容换了就要重审） |

落了行即置 `Pending`（待审核）、整场先不投影，`Confirm & Apply Routing` 后转 `Passed`、勾选的整批投影（1.10，开发设计 7 #Q75、#Q81）；一行都没落的直接 `Passed`。补抽的证词按 2.5：保存即补、默认勾选，同样等应用才上线；已 `Passed` 的会议补出新证词即转回 `Pending`（待审核）、在线内容整场下线，应用后已勾选的行整批重新入库（开发设计 7 #Q83、#Q87、#Q88）。

**Play candidate 标记**：新行 `in_playbook` 重置为关，需在 Goldie Base 重新打开（9.11.6）。

#### 9.10.2 事件清单

| `PROJECTION_FAILED` | 上线、下线或改内容的自动重试用尽仍失败（1.6） | 中间表行 id、去向与所属会议、动作（上线 / 下线 / 改内容）、重试次数、最后一次错误；`operator` 为 `System` |
