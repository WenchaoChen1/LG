## 一、全局约定

以下约定对所有会议类型生效，各类型章节不再重复。

### 1.1 知识库空间与业务类型

沿用现有 RAG 的空间机制：`ai_rag_business_association` 以组合键 `(end_type, business_type, company_id | organization_id)` 唯一确定一个知识库空间，chatbot 检索时按身份解出可见的 `space_ids`。**隔离靠「谁能解出哪个空间」，不靠检索时的行级过滤。**

#### 空间清单

| 代号 | 组合键 | 粒度 | 隔离方式 | 谁能召回 | FF 写入 |
|---|---|---|---|---|---|
| **KB-APP** | `(APP, APP_COMPANY, company_id)` | 每公司一个 | 空间层 | 该公司创始人 + 管理端 | ✅ |
| **KB-ADMIN** | `(ADMIN, ADMIN_COMPANY, organization_id)` | **每组织一个（公司 id 隔离）** | **行级 `company_id`** | 仅管理端 | ✅ |
| **证词-匿名 / 证词-署名** | `(APP / ADMIN, EXPERT_TESTIMONY, organization_id)` | 每租户各一个 | 空间层 | 匿名版两端 / 署名版仅管理端 | ✅ |
| **跨公司** | `(APP, CROSS_COMPANY, organization_id)` | 每租户一个 | 空间层 | 创始人 + 管理端 | ✅ |

处理类型均为 `STANDARD`。**租户 = organization**（需求口径：一把 API key 归属一个租户）。

#### 按会议类型的产物归属

**类型一 · GS → 创始人**

| 产物 | 空间 | 份数 |
|---|---|---|
| 摘要 + 纪要（1a / 1b / Founder KB **共用一份**） | KB-APP | 每关联公司一条 |
| Cross-Company 洞察 | 跨公司 | 0~N 条 |

> 三个目的地共用一份，是因为矩阵给它们的都是「摘要」，内容相同；且管理端能召回 KB-APP，无需另写。

**类型二 · Board Call（手动改判后）**

| 产物 | 空间 | 份数 |
|---|---|---|
| 摘要（1a + Founder KB） | KB-APP | 每关联公司一条 |
| **退出准备 / 战略摘要（1b）** | **KB-ADMIN** | 每关联公司一条 |
| Cross-Company（带 care flag？） | 跨公司 | 0~N 条 |

> ⚠️ **本类型不能共用一份**：矩阵给 1a 的是「摘要」、给 1b 的是「退出准备/战略方面的摘要」，**内容不同**，必须分别产出、分落两个空间。

**类型三 · GS → LP**

| 产物 | 空间 | 份数 |
|---|---|---|
| 1b（按正文提及的公司拆分） | KB-ADMIN | 每命中公司一条 |
| 证词 · 匿名版 | 证词-匿名 | 0~N 条 |
| 证词 · 署名版 | 证词-署名 | 与匿名版一一对应 |
| Cross-Company 市场趋势 | 跨公司 | 0~N 条 |

**类型四 · GS 内部**

| 产物 | 空间 | 份数 |
|---|---|---|
| 1b（按正文提及的公司拆分，只抽结论） | KB-ADMIN | 每命中公司一条 |
| Cross-Company（战略-决议闭环、全公司视角） | 跨公司 | 0~N 条 |

**类型五 · GS → Partner**

| 产物 | 空间 | 份数 |
|---|---|---|
| 1b（按正文提及的公司拆分，退出相关） | KB-ADMIN | 每命中公司一条 |
| 证词 · 两版 | 证词-匿名 / 证词-署名 | 0~N 条 |
| Cross-Company 市场与商业趋势 | 跨公司 | 0~N 条 |

**关键事实**：管理端的检索范围已包含各可访问公司的 APP 空间（`knowledge_base_tool.py:127-135` 并入 `find_app_space_ids`），**反向不成立**——公司端只解出自己公司那一个 APP 空间。因此：

- 内容进 KB-APP 后管理端自动可见，**仅当 1a 与 1b 内容相同时才可共用一份**（只有类型一满足）
- 只允许管理端看到的内容写进 KB-ADMIN，即结构性对创始人不可见，**不需要额外加过滤**
- **KB-ADMIN 的公司隔离是行级的**（同一组织共用一个物理空间，靠条目上的 `company_id` 区分），故 `company_id` 必须填对——这是本方案唯一一处不靠空间层隔离的地方
- **绑不到公司的内容直接丢弃，不写入**（见 3.3 / 4.3 / 5.4）。即便写入也无意义——管理端召回叠 `company_id IN 可访问公司集 OR thread_id` 的析取过滤，`company_id` 为空则两个条件都不满足，永远召不回

**需新增两个业务类型**：`EXPERT_TESTIMONY` 与 `CROSS_COMPANY`，均按租户（organization）键控。具体创建与定位细节留到开发设计阶段。

两者的份数不同：

- **`EXPERT_TESTIMONY` 两份**——权限分层要求管理端在 Goldie 内看到署名、创始人永不看到，而署名直接存正文、不做召回后处理，故按 `end_type` 分匿名版与署名版各存一版
- **`CROSS_COMPANY` 一份**——§7.5 规定管理端回溯原始转录与署名走**管理端系统入口、非跨公司 KB 前台**，Goldie 链路上两端看到的都是匿名版，内容完全相同，故两端共用一份

> 另有 `ADMIN_PORTFOLIO` 的设想（为 LP / GS 内部中绑不到具体公司的基金层内容提供归属），**尚未决定是否引入**，见 3.2 的批注。

### 1.2 登记表业务类型

`ai_file_registry.business_type = FIREFLIES`（该列为 `VARCHAR(40)` 自由文本，无 CHECK 约束，新增取值不需要 DDL 改动）。

该取值**不影响检索**——召回按空间走，`recall` 使用的 `business_type` 取自 `ai_rag_space`（`search_service.py:222`），与登记表的同名字段无关。

### 1.3 产物形态

每条知识条目最多三份产物：

| 产物 | 存储位置 | 说明 |
|---|---|---|
| **原文** | `ff_meeting` / `ff_meeting_sentence`（新建） | 永久留存，审计源与重算依据；不进向量库 |
| **去逐字化纪要**（= body） | `ai_rag_entry.content_text` + 按 800/100 切片 | Goldie 检索细节 |
| **摘要** | `ai_rag_entry.summary` + 单片 `chunk_kind=summary` | Goldie 检索概览；**≤1000 字符** |

**「去逐字化」与「完整纪要」是同一份产物**——前者是处理动作，后者是处理结果。

约束：

- 摘要与纪要的**输入都是原始转录全文**，不直接采用 Fireflies 自带的 `overview` / `notes`（§6.1 的机械清洗层需要原文作为 n-gram 比对基准）
- 摘要由我方生成后**直接写入**，需跳过系统的二次 `summarize`，否则会变成「摘要的摘要」
- **内容短于阈值时只存 body、不生成 summary**（阈值实施期定），避免两者近乎重复、在召回中互相挤占
- 提取前先走**质量判断**，判定为无实质内容的直接跳过，不产出条目

### 1.4 去逐字化适用矩阵

§6.1 的去逐字化包含三种处理，**按去向分别适用**：

| 去向 | 非逐字表达 | n-gram 近逐字剔除 | 实体/人名剥离 |
|---|---|---|---|
| 1a | ✅ | ✅ | ❌ |
| 1b | ✅ | ✅ | ❌ |
| Founder KB | ✅ | ✅ | ❌ |
| Cross-Company | ✅ | ✅ | ✅ |
| 专家证词 · 匿名版 | ✅ | ✅ | ✅ |
| 专家证词 · 署名版 | ✅ | ✅ | ✅ |

> **图例**：✅ 做 ／ ❌ 不做

**判据：实体剥离只在「内容跨出本公司」的去向做。**

实体剥离要防的是 A 公司的信息被 B 公司的人读到。1a / 1b / Founder KB 三者都按 `company_id` 绑定、只对本公司可见，剥离在这里没有收益，只会破坏可用性——1a 剥掉本公司名与产品名后，Goldie 连"Acme 那单谈得怎么样"都召不回。Cross-Company 与证词库是跨公司复用的，必须剥。

**各格依据**：

| 处理 | 依据 |
|---|---|
| 非逐字表达 / n-gram：1a、Founder KB、Cross-Company、证词 | 需求明文 §6.1「任何面向创始人的界面永不出现原文措辞」 |
| 非逐字表达 / n-gram：1b | 用户决定——§6.1 只覆盖面向创始人的界面、管理端不在其中，此项为「1a / 1b 经 Goldie 召回的都是转义后的」这一决定的结果 |
| Cross-Company 做实体剥离 | 需求明文 §7.5「内容为公司标识**完全剥离**后的匿名主题 / 洞察」 |
| 证词两版做实体剥离 | 需求明文 §7.4 存储字段为「**匿名内容**」 |
| 1a / 1b / Founder KB 不做实体剥离 | 用户决定（2026-09-22）。需求侧三处佐证：§5.x「上传内容**完整存入本公司 1a / 1b**，不做去逐字化」——同一空间里自传文档原样存、会议摘要却剥离说不通；§9.3 Board Call 派生物进创始人 KB「**不做第三方来源匿名处理**」；§9.1 要求 1b 保全「X 公司被兜售给 Y 买家，价格 Nx」这类交易事实，若剥离则"Y 买家"与"Nx"会被抹掉，规则要保全的内容不复存在 |

**证词两版的内容完全相同（均为匿名内容）**，差别只在署名版额外附一行来源信息——**不是**内容里保留实体。这与 §9.1 自洽：公司具体交易事实根本不进证词库（只落 1b），故证词内容中本就不应存在可识别的公司实体。

### 1.5 实体/人名剥离的范围

§6.1 仅写「实体/人名剥离」，未定义范围。以下为本方案补充的清单，**仅适用于 1.4 中标 ✅ 的去向**（Cross-Company 与证词两版）。

**直接标识符——机械清洗层处理**

| 类别 | 处理 |
|---|---|
| 公司名及其简称、变体、曾用名 | 剥离 |
| 人名（全名 / 名 / 姓 / 昵称） | 剥离 |
| 产品名、品牌名 | 剥离 |
| 客户名、供应商名 | 剥离 |
| 域名、邮箱、URL | 剥离 |
| 「公司 + 职位」组合（如"Acme 的 CTO"） | 剥公司，保留职位 |
| 具体金额、百分比 | **转量级**，如"约百万级 ARR"、"两位数下滑" |
| 具体日期、时间点 | **转阶段**（"A 轮后"、"上一财年"）或**时长**（"约一个季度内"、"连续两个季度"）；**禁止绝对时点**——年份、季度、月份一律不保留（"2026 Q3"、"去年 Q3"、"今年 8 月"） |
| 可定位的地理信息（如"我们西雅图办公室"） | 剥离 |

**准标识符——机械层无能为力，靠 LLM 层处理**

单个属性都不敏感，**组合起来可唯一定位**。例："一家做**牙科 SaaS** 的、**A 轮后**、**Q3 丢了最大客户**的公司"——三个属性各自无害，凑在一起在组合内可能只对应一家。

这类内容没有可匹配的实体词，机械清洗层扫不到。所以 §6.1 的「双层保障」实际是**分工**而非冗余：

- **机械清洗层**：处理直接标识符，确定性高、可测
- **LLM 摘要层 + 可移植性判据**：处理准标识符，靠「脱离这家公司仍然成立才保留」把独特细节整体抹掉

这也是 Cross-Company 采用「只抽可移植洞察点」而非「整场匿名化」的原因——后者只过得了机械层，准标识符会原样留在文本里。

**保留（剥了即失去价值）**：行业 / 垂直领域、公司阶段（ARR 区间、轮次）、通用职位（CEO / CTO，不带公司）、问题类型、应对方式。

n-gram 阈值需在实施期用真实数据调优。

### 1.7 机密性规则的适用范围

> **出处说明（2026-09-22）**：§9.1 活跃交易隔离与 §9.2 LP／基金机密性过滤**只存在于已改名作废的《Fireflies_Integration过期》**。现行需求中仅《会议内容提取规则》的 Partner 行保留「实时交易信息全部隔离」及关键词 (3) 的 `Live-deal Quarantined` 定义，其余条款（交易事实只落该公司 1b、对所有 Partner 全量适用、LP 基金层过滤、对 Portfolio Manager 亦排除）均无现行出处。

> **机密性部分正在重写中，新版发布前以作废文档为准**，本文档照此实现。新版出来后本节需重新对齐。

| 规则 | 需求原文适用范围 | 本方案适用范围 |
|---|---|---|
| §9.1 活跃交易隔离 | GS → Partner、GS → LP | GS → Partner、GS → LP、**GS 内部** |
| §9.2 LP / 基金机密性过滤 | LP 派生物进入面向创始人界面前（**Cross-Company 匿名主题**与**专家证词匿名版**——LP 不产出 1a、不进 Founder KB），两条管道各执行一遍 | 同左；对 1b 则是**保全**规则 |

>
> 加严后的口径与其他两类一致：**具体交易事实只落该公司 1b**，仅可移植的市场趋势允许进 Cross-Company。

### 1.8 参会人姓名回退匹配

邮箱匹配未命中时，用**姓名**回退匹配，规则如下：

| 项 | 规则 |
|---|---|
| **匹配顺序** | ① **LG 系统内用户**姓名 → ② **Cheat Sheet 维护人员**姓名。命中即止 |
| **匹配方式** | **完全匹配**，不做模糊、不做近似 |
| **重名** | 匹配到多条 → **直接进 Pending Assignment**，不猜测 |

**姓名取值来源**：Fireflies 的 `meeting_attendees` 中 `displayName` / `name` 实测**全为 null**，取不到「日历邀请中的姓名」。可用源为：

1. `meeting_attendance[].name`——平台出席记录，最接近日历邀请，**首选**
2. `speakers[].name`——ASR 说话人识别，**仅作兜底**（人名易被识别错，用于匹配注册表风险更高）

> 采用完全匹配而非模糊匹配，是因为姓名匹配的误判代价不对称：匹配不上只是进 Pending 等人工处理，匹配错则把外部人当成内部人（或相反），直接改变会议类型与整条路由。

### 1.9 参会人识别与公司归属

**明确禁止使用会议标题作为识别依据。**

**参会人来源**：会议在 **Microsoft Teams** 内召开、将 Fireflies 拉入，因此 Fireflies 返回的参会人即 Teams 会议的参会人。实测样本亦印证——`calendar_type = "outlook"`、`meeting_link` 指向 `teams.microsoft.com`。取值用 `participants`（邮箱数组）与 `meeting_attendance`（出席记录，含姓名与进出场时间）。

识别要产出两样**互相独立**的东西：

| 产出 | 用途 | 缺失的后果 |
|---|---|---|
| **人的身份** | 决定会议类型（GS 方 / 公司方 / LP / Partner） | 类型判不出 → 会议进 Pending |
| **公司归属** | 决定产物落哪家公司 | 该公司的产物无处可落 |

**匹配链（命中即止）**

| 顺序 | 匹配方式 | 匹配对象 | 产出 |
|---|---|---|---|
| ① | **完整邮箱** | LG 系统内用户（管理端 + 公司端） | 人员确定；公司端用户同时得到 `company_id` |
| ② | **完整邮箱** | 第三方维护的邮箱——Cheat Sheet，其次 HubSpot | 人员确定 + 角色 / 专长标签 |
| ③ | **邮箱域名** | `goldensection.com` / `whalesongproduct.com` / `gstdev.com` | **仅判定"此人属 GS 方"**，不对应到具体人员 |
| ④ | **姓名** | LG 系统内 → Cheat Sheet（完全匹配，规则见 1.8） | 人员确定 |
| ⑤ | **LLM 推断** | 转录正文 | **只推断【公司】**，不解决"人是谁" |
| ⑥ | —— | —— | Pending Assignment |

> **域名匹配的唯一用途是判定 GS 方**（用于会议类型分类），**不做人员对应**——同一域名下有多个账号，域名本身无法定位到人，也无此必要。
>
> **公司归属只来自 ①**（完整邮箱 → LG 公司端用户 → `company_id`）与 **⑤**（正文推断）。域名不参与公司归属。

**关键规则**

- **LLM 推断这一级只推断公司，不推断人的身份**。因此人未识别时，即便推断出了公司，会议类型仍判不出——**会议照常进 Pending**
- **Pending 阻断的是内容提取，不是识别**。识别阶段照常跑完并留痕——参会人身份（程序）、公司归属（程序按邮箱 + 6.3 的正文提及识别）都要产出，管理端 Summary Records 页要展示它们、人工审核也靠它们。被阻断的是**内容提取**：抽取提示词按会议类型分别编写（6.4~6.8），类型未定就没有提示词可选，强行提取只会拿到质量不可控的结果。**等人工在 Summary Records 页指定会议类型后再触发提取**
- **发言人映射也属识别阶段**：逐句的 `sentences[].speaker_id` 经 `speakers[].name` 映射到已识别的参会人，**映射不上即视为该参会人未识别，整场进 Pending**。`speakers[].name` 来自 ASR（昵称、听错拼写、`Speaker 2`、两人合并为一个 speaker 都会导致对不上），故这一步要在调用 LLM 之前做完——证词的来源行依赖它，留到提取后才发现就晚了
- 一场会议可关联**多个公司**
- 识别结果（公司、外部人员、角色）传递给下游分类步骤

### 2.1 判定条件

**GS 方 ≥ 1**——参会人中任一命中即成立（五者取并）：

|---|---|---|
| ① | 邮箱域名 `goldensection.com` | 平台内外的 GS 人员 |
| ② | 邮箱域名 `whalesongproduct.com` | 同上 |
| ③ | 邮箱域名 `gstdev.com` | 同上 |
| ④ | Cheat Sheet 中 role = `GS staff` | **未注册 LG 平台**的 GS 人员 |

**公司方 ≥ 1**——参会人中任一命中即成立：

| # | 条件 | 覆盖谁 |
|---|---|---|
| ① | **LG 公司端用户**，且其所属公司 `status ∈ {2,3,4,5}` | 已注册平台的创始人／公司成员 |

公司状态取 `CompanyStatusEnum` 的四项正常态：Needs Intervention(2) / Needs Guidance(3) / Thriving(4) / Active(5)；排除 Exited(1) / Shut down(6) / Off journey(7)。**不额外要求公司挂 portfolio**（比现成的 `isActiveCompany` 宽）。

> ⚠️ **仅靠 ② 成立时，会议判得出类型但定不出公司归属**。
>
> 判定「有没有公司方」与确定「是哪家公司」是两件事：前者只要身份，后者要 `company_id`。而 Cheat Sheet 条目只有 `Organization` 文本字段，**没有 `company_id`**。
>
> 于是分两种情形：
>
> | 情形 | 判定 | 公司归属 |
> |---|---|---|
> | 会上有 LG 公司端用户（无论是否也有 Cheat Sheet Founder） | ✅ 第一类 | 从公司端用户取 `company_id`，正常 |
> | **只有 Cheat Sheet Founder，无公司端用户** | ✅ 第一类 | **取不到 `company_id`** —— 1a 定位不出 KB-APP 空间、1b 无法做行级隔离，**产物无处可落** |
>
> **处理方式**：**由会议正文提及反推公司**，复用 LP / GS 内部 / Partner 所用的同一套「公司提及识别」（见 3.3）——从候选公司清单匹配，仅高置信度采纳，低置信度不采纳并记 Pending。
>
> ⚠️ **本类型的误判代价比其余类型高一个量级**：
>
> | 类型 | 误判后果 |
> |---|---|
> | LP / GS 内部 / Partner | 内容落入错误公司的 **1b**，Portfolio Manager 看到越界内容（管理端） |
> | **本类型** | 内容落入错误公司的 **KB-APP**，**该公司创始人可直接读到别家公司的会议摘要**（客户侧泄漏） |
>
> 因此本路径的置信门槛应高于其余类型。**兜底**：按《Fireflies Summary Records》，`Status = Flagged` 的定义即「AI 判定为 GS-Founder 类型的会议」——**本类型默认全部进人工复核**，不直接放行，反推出的公司归属会被人工过一道。

本类型为**兜底类**：LP 或 Partner 若同时也是某家在营公司的公司端用户，按本规则即归入本类。

| Cross-Company | ✅ | 匿名可移植洞察点 |
| 专家证词 | ❌ | 不产出 |

### 2.3 提取规则

**1a / Founder KB（同一份）**

- 摘要：≤1000 字符，我方生成
- 纪要：去逐字化后的完整会议内容
- **一场会关联多家公司时，每家一条 entry，内容不裁剪**。本类型下安全——关联公司由参会人邮箱反推，各家均实际到场听过全场，不存在新增暴露

**1b（仅摘要）**

取与 1a 相同的那份摘要，**不写纪要**——《创始人与管理端问答总结》给管理端在本类型下的口径是「会议摘要」。LLM 不额外生成，两处用同一份文本，不存在漂移。

**Cross-Company**

不做整场匿名化，只抽**可移植洞察点**，一场会产出 0~N 条独立条目：

1. **可移植性判据**：脱离这家公司仍然成立才保留。「B2B SaaS 在这个阶段普遍低估实施成本」保留；「我们的实施成本超了 40%」剔除
2. **硬性剥离**：公司名、产品名、人名、客户名、具体金额与百分比（改为量级描述）、具体时间点（改为阶段描述）
3. **保留**：行业/垂直领域、公司阶段（ARR 区间、轮次）、问题类型、应对方式
4. **产出 0 条是正常结果**——多数例行沟通没有可移植内容，不为凑数降低匿名强度

理由：整场匿名化后仍极易通过上下文还原公司身份（「一家做牙科 SaaS 的公司在 Q3 丢了最大客户」，组合里做牙科 SaaS 的可能只有一家）。

### 3.2 路由

|---|---|---|
| 1a 创始人记忆 | ❌ | |
| 1b 管理端记忆 | ✅？ | 仅能绑定到具体公司的内容 |
| Founder KB | ❌ | |
| Cross-Company | ✅ | 仅可移植市场趋势，一份匿名版 |

### 3.3 1b 提取规则

**归属方式**：LP 会议的参会人映射不到在营公司，公司归属只能靠**正文提及**识别。一场会提到 N 家组合公司 → 产出 N 条 entry，`company_id` 必填。

**绑不到公司的内容直接丢弃**——纯基金层内容（募资进度、基金整体回报、LP 结构）不入 1b。

**公司提及识别策略**：由会议上下文推断，**仅高置信度才入**；低置信度不入并记 Pending 供人工确认。别名表列为可选优化项。

> 错误代价不对称：漏识别只是该公司 1b 少一条内容（静默）；**错识别会让 A 公司的交易事实进入 B 公司的 1b**，而 Portfolio Manager 只能看自己管辖的公司，这构成跨边界泄漏。故宁可漏不可错。
>
> 系统现状：**不存在「按名称匹配公司」的能力**，需新建。（按邮箱域名反查公司的能力同样没有，但公司归属已改走完整邮箱匹配，不再需要它——见 1.9。）

**抽取内容**（限该公司相关）：

1. **具体交易事实**——被兜售 / 估值 / 买方 / 价格 / 时间表。§9.1 明确规定此类内容**只能落该公司 1b**，其他去向一律不可
2. LP 对该公司的评价、关切、要求
3. GS 对该公司的退出计划与估值判断
4. 该公司在基金层面的定位——提及其他被投公司时剥掉对方标识

**§9.2 相关信息不得遗漏**：9.2 要求把基金层与其他 LP 信息从面向创始人的产物中剥离，这些信息的归宿就是 1b。对 1b 而言 9.2 是**保全规则**而非过滤规则。

**落库**：落 **KB-ADMIN** 空间（该组织的管理端知识库），每命中公司一条 entry，**`company_id` 必填**——它是公司隔离与召回过滤的唯一依据，不填则召不回。

### 3.4 专家证词提取规则

**抽取内容**：融资 / **市场？** / 倍数收益。定义引自《会议内容提取规则》(4)：

| 类别 | 定义 |
|---|---|
| **融资**<br/>Fundraising | 会议中关于引入外部投资、融资轮次、估值预期、向投资人展示的业务进展及资金使用计划的讨论 |
| **市场？**<br/>Market | 宏观市场环境、行业规模、竞争格局及外部需求变化 |
| **倍数收益**<br/>Multiples | 资本市场或同类对标企业常用的估值指标（P/E、P/S、EV/EBITDA 等），用于评估公司估值或定价基准 |

一句话概括：提炼适用于**融资路演与估值对标**的市场 / 行业信息。

> **保密过滤（Confidentiality Filter）**——《会议内容提取规则》(4) 要求：总结时**自动剔除机密、敏感或受 NDA 限制的信息**（核心财务数据、未公开的客户名单、敏感条款等）。这是在 §9.2 基金层过滤之外的又一道，两者叠加执行。

> **「市场」与 Cross-Company 的关系（`？` 标记项）**
>
> 需求 §10.1 自己指出这一条未闭环：「"市场趋势"到底是从证词库读取还是从主题库读取，两条管道的过滤责任划分未闭环」。两处主题范围重叠（都含市场行情、倍数）。
>
> **不做互斥分流，接受重复**（2026-09-22 用户决定）：两条管道各自按本管道的标准独立抽取，同一段话同时满足两边标准时**两边都产出**。理由——
>
> - 两个库的**受众不同**：证词库管理端看得到署名、创始人只看匿名内容；Cross-Company 两端都是匿名共识。同一句话在两处的形态与可见范围本就不同，不构成真正的重复
> - 需求把两者**分成两块写**，本身就说明它们不是同一批内容的两种切法。互斥会把这层区分抹平
> - 这两个库的定位**尚未稳定**：Cross-Company 可能演化为"适用于所有公司的泛化描述"，专家证词也未必要求跨公司。在定位定下来之前，互斥规则很可能定错方向，而多产出一条的代价远小于漏产出
>
> 代价是已知的：Goldie 召回时同一观点可能带署名和不带署名各出现一次。**先接受**，等两个库的定位明确后再回来处理。

**随条目携带两个标签**（均来自注册表）：

- **角色类型标签**：取注册表角色枚举（见 5.2）。本类型实际值域为 `GS staff` / `LP` / `Strategic Partner` / `Exit Partner`
- **专长标签**：按**会议日期**从注册表 Effective Dating 回溯当时生效的那一版，历史证词不因当事人当前角色变化而被重贴

**存两份**（因权限分层，且署名直接存库、不做召回后处理）：

| 版本 | 空间 | 正文 |
|---|---|---|
| 匿名版 | `(APP, EXPERT_TESTIMONY, organization_id)` | 匿名内容 + 附一行**泛化来源**，固定首行格式 `来源：某<专长标签>领域的<角色>` |
| 署名版 | `(ADMIN, EXPERT_TESTIMONY, organization_id)` | **同一份匿名内容** + 附一行**署名**，固定首行格式 `来源：<组织> <角色> <姓名>` |

**两版的正文内容完全相同**（均已实体剥离），差别只在程序附加的那一行首行——LLM 只抽一次，不存在两版内容漂移的风险。

**匿名版为什么也要附一行**：需求 §7.4 描述创始人端的措辞是「某医疗 IT 买家指出……」——匿名不等于无出处，泛化的角色 + 领域是这条证词可信度的来源。不附则创始人读到的是一条无主的断言，§7.4 要的那层感受就没了。泛化来源只用注册表的角色与专长标签，**不含姓名、不含组织**，不构成身份泄漏。

两行的取数完全同源（注册表角色 + 按会议日期回溯的专长标签），差别只是署名版多出组织与姓名。

公司端只解匿名版空间、管理端只解署名版空间，**两端都不会重复命中同一条证词的两个版本**。

> 署名**不能放 `chunk.metadata`**：`SearchHitDTO` 只透出 `chunk_id / content / entry_id / entry_title / space_id / space_name / similarity / match_type / uploaded_at / chunk_kind / file_id`，**metadata 不在返回字段中**，管理端召回后拿不到。

**创始人端可召回的前提**：证词空间按 `organization_id` 键控，而创始人登录时 `organizationId` 解析自 `r_organization_user`（`OrganizationRepository:47`），创始人不在该表中，**解出为 null**。需在 Java 登录处补兜底：查不到时用 `companyId` 走 `r_organization_company` 反查（`OrganizationRepository:50` 已有现成查询）。

**检索侧**：`knowledge_base_tool` 公司端分支需多解一个证词空间；**调高 top_k**，具体召回效果在工具内优化。

> 已知行为：`_normalize_and_merge`（`factory.py:289-317`）按 `business_type` 分组做 min-max 归一，**每组内最高分恒归一为 1.0**。证词自成一组，因此即使本轮提问与证词无关，组内最相关的一条也会以满分参与全局排序、挤占公司文档名额。已接受此行为，后续在工具层优化。

## 五、GS → 战略伙伴 / 退出伙伴（合并）

### 5.0 「合并」的含义

原设计是两个独立类型——`Strategic Partner`（商业合作方：渠道、技术伙伴、联合销售）与 `Exit Partner`（退出交易相关方：买方 PE、投行、并购顾问）。因**从参会数据无法可靠区分**，合并为 `GS → Partner` 一类，**下游一律按更保守的 Exit Partner 处理**。

误判代价不对称是合并的依据：把 Exit 会当成 Strategic 会 → 隔离放松 → 交易信息流入 Cross-Company，是实质泄漏；反之只是过度保守、少共享一些商业趋势。

合并落成三条规则：判定不区分、证词范围取并集（5 类）、**§9.1 全量适用**（见 5.5）。

### 5.1 判定条件

GS 方 ≥ 1（口径同 2.1 的五选一），**且**无参会人属于公司方（否则归第一类），**且**非全员 GS（否则归 GS 内部），**且**存在参会人同时满足：

- **角色** ∈ {`Strategic Partner`, `Exit Partner`}
- **且 Expertise Tag** ∈ {`Strategic Partner`, `Exit Partner`}

《AI Meeting Type 自动映射标准》的触发规则写作「参与人命中注册表中 Strategic 或 Exit Partner」——**该句指的是 Expertise Tag**，角色条件隐含未写出。两者都要命中。

**匹配顺序**：先用邮箱匹配注册表；邮箱未命中则**姓名回退匹配，规则见 1.8**（LG 系统内 → Cheat Sheet，完全匹配，重名进 Pending）。

与 LP 一样**强依赖注册表**，未收录即判不出，进 Pending Assignment。

> **备注口径的变化**：旧需求写「两者**不可靠区分**，统一为一类；**下游按更保守的 Exit Partner 处理**」，现行需求改为「两者**无需区分**，统一为一类」——**"按保守的 Exit Partner 处理"一句已删除**。§9.1「对所有 GS → Partner 会议全量适用」正是以该句为依据，现失去出处，见 5.5 与 9.2。

### 5.2 注册表字段口径（本类型引入，全局适用）

以《Cheat Sheet》为准。

| 字段 | 性质 | 取值 | 回答什么 | 用途 |
|---|---|---|---|---|
| **角色** | 受控枚举，**固定 6 项** | `LP`、`Strategic Partner`、`Exit Partner`、`Founder`、`GS staff`、`Other` | 这人是什么身份 | 会议类型判定 + 证词脱敏转义 |
| **专长标签** | 受控枚举，**下拉多选** | 选项来自独立的 **Expertise Tags 配置页**（可增删） | 这人擅长什么领域 | 会议类型判定 + 证词专长标签 |
| **有效期** | From 必填 / To 可空（空 = present） | — | 上述两者在会议当日的版本 | 历史证词不因当事人当前身份变化而被重贴 |

**「外部人员角色」「角色类型」「证词发言者角色标签」三者是同一个字段**，取值即上表角色枚举。《会议内容提取规则》证词表中的 `LP / PE / IB / 买家 / 专家` 是**尚未改完的残留**，`PE` / `IB` / `Buyer` / `Expert` 作废。

**`Founder` 与 `GS staff` 是有意保留的，不是笔误**——《Cheat Sheet》明确说明：「并不是所有的 GS 人员和 Founder 人员都有 LG 的账户，所以 Cheat sheet 保留这两个角色标签」。

**有效期规则**：

- 编辑弹窗用两个日历选择器，From 必填、To 可不选（代表无限制，显示为 `present`）
- **会议发生时间落在的区间若与其他历史记录重合，以最后一个该时间的记录为准**
- 超过 90 天未复核的条目标记 `Needs review`
- 姓名是唯一识别符，发布后不可更改；History 页按生效日期排序，每个版本保留完整快照

**证词角色标签的实际值域只有 4 项**：证词仅由 GS → LP 与 GS → Partner 两类会议产生，这两类的参会人范围是 GS 人员、LP、Strategic Partner、Exit Partner，因此实际出现的是——

```
GS staff、LP、Strategic Partner、Exit Partner
```

`Founder` 与 `Other` 不会出现在证词中。脱敏转义直接用角色名，如「某退出伙伴指出……」「某 GS 员工指出……」。

### 5.4 1b 提取规则

**归属方式与 LP / GS 内部完全一致**：按正文提及识别公司 → 仅高置信度才入 → 一场会 N 家公司产出 N 条 → `company_id` 必填 → 绑不到公司的内容丢弃。落 **KB-ADMIN** 空间（该组织的管理端知识库），每命中公司一条 entry，**`company_id` 必填**——它是公司隔离与召回过滤的唯一依据，不填则召不回。

3. 对方（伙伴）对该公司的评价与意向

### 5.5 Cross-Company 提取规则

**§9.1 在本类型是全量适用**——不做「本场是否提及活跃交易」的条件判断，**默认每一场都涉及**。

操作含义：

| | 其他类型 | 本类型 |
|---|---|---|
| §9.1 触发 | 条件触发（提及被兜售/估值的公司时） | **无条件，每场都适用** |
| 公司具体事实 | 匿名后部分可进 Cross-Company | **一律只落该公司 1b** |
| Cross-Company 可得 | 匿名洞察 | **仅完全脱离具体公司的趋势** |

**抽取范围**，定义引自《会议内容提取规则》(3)：

| 概念 | 定义 |
|---|---|
| **市场趋势**<br/>Market Trends | 外部宏观层面的变化：行业新技术动向、用户需求偏好转变、竞争对手动向、政策法规变化等 |
| **商业 / 变现趋势**<br/>Commercial Trends | 业务与商业化层面的变化：新的盈利模式、定价策略调整、渠道转化效率、客户采购行为的变化等 |
| **仅可移植趋势**<br/>Portable Trends Only | 只保留可复用 / 普适、可跨业务或跨场景迁移的洞察，排除局限于单一客户、单一项目或一次性交易的临时现象 |
| **在途交易隔离**<br/>Live-deal Quarantined | **具体正在跟进、尚未落地**的商业项目、谈判细节或竞争性投标数据，严格过滤隔离，不得混入趋势总结 |

一句话概括：提取与**外部行业风向、竞争态势、商业变现或客户采购偏好**相关的外部情报与洞察。

**判据**：沿用第一类的可移植性判据——*脱离这家公司仍然成立才保留*——并因 §9.1 全量适用而加严：**任何能指向特定公司的内容一律不进**，即使匿名。Live-deal Quarantined 的定义给出了可操作的排除项（正在跟进未落地的项目、谈判细节、竞争性投标数据）。

> **仍待确认**：介于两者之间的内容如何判定，例如"某买方最近对垂直 SaaS 的估值逻辑变了"——它既像可移植的市场趋势，又可能透露在途交易中的买方态度。尚无边界示例。

### 5.6 专家证词提取规则

**与 LP 共用同一套证词库**（按默认实现，待确认）——同一个 `EXPERT_TESTIMONY` 空间，同样匿名版 / 署名版两份，仅抽取主题不同。

**抽取内容（5 类）**：商业采购行为、软件使用、倍数、买方行为、退出趋势。其中两类的定义引自《会议内容提取规则》(5)：

| 类别 | 定义 |
|---|---|
| **商业采购行为**<br/>Commercial Buying Behavior | 企业级客户在购买、评估、决策软件及服务时的习惯与流程。如：采购决策链条变长、更看重 ROI、对安全合规要求提高、倾向集成化方案 |
| **软件使用情况**<br/>Software Usage | 终端用户或企业客户实际使用软件产品时的行为数据与反馈。如：功能活跃度、高频使用场景、痛点、流失原因、对特定模块的依赖度 |

一句话概括：提炼客户在**企业采购决策模式**与**实际软件产品使用偏好 / 习惯**方面的洞察。

**标签来源**：

- **专长标签** → 取专长标签枚举，按会议日期经有效期回溯当时版本

### 5.7 机密性

- §9.1 全量适用（见 5.5），§9.2 的过滤在证词与 Cross-Company 两条管道**各执行一遍**
- §9.1 / §9.2 命中的内容对**所有受众**排除（含 Portfolio Manager），**在写入阶段就不产出**

## 六、抽取提示词

> 本节为核心抽取提示词。落地时按项目惯例迁到 `source/ai/prompts/fireflies/`（`.md` 为权威源，`.py` 经 `_md_loader` 加载，`{{var:name}}` 占位）。

### 6.1 分工与约定

**分工**：LLM 只做「判断与转述」，机械处理交程序。

| 环节 | 谁做 |
|---|---|
| 非逐字转述、内容分类、可移植性判断、公司提及识别、质量判断 | **LLM** |
| 实体/人名剥离、n-gram 近逐字剔除、署名附加、专长标签回溯、落库路由 | **程序** |

**语言**：提示词中文，**产物英文**（与现有 `ai_rag_entry.summary` 及 Goldie 默认作答语言一致）。

**输出**：一律 JSON，`json_mode=True`。截断（`finish_reason=length`）时**整体判失败重试，不抢救半成品**——半份合法外观的结果比没有更危险（沿用 `excel_extract_agent` 的口径）。

**单次处理**：一次调用产出该会议类型的全部派生物，下游不再读原文（需求 §6.1）。

> **唯一例外：改判为 Board Call 后的补跑**（6.5）。需求 §6.1 防的是「下游各自去读原文导致口径不一致」，而改判后的补跑是**加工环节自身的二次触发**，不是下游；且需求 §8.2 要求改判后路由自动重算，重算本就必须重读原文。补跑只产出 1b，不重跑已入库的其余产物。

```

**已定**：摘要 ≤1000 字符（同 §1.3）；**纪要不设长度限制**——它的职责是完整承载会议内容，截断只会丢信息，切片由 800/100 负责。

### 6.3 公司识别（前置，类型无关）

```

### 6.5 GS → Board Call（改判后补跑，只产出 1b）

**触发**：PGM 手动把某场会从「GS → 创始人」改判为「GS → 董事会/创始人（三方）」之后。

**为什么是单独一次调用、只抽 1b**：改判前这场会**已按 6.4 跑过**，摘要、纪要、Cross-Company 均已入库；而 1a / Founder KB 在两种类型下都是「摘要」，**内容完全相同**，真正变的只有 1b（改为退出准备 / 战略摘要，见 1.1 类型二）。

本项与 `testimony` **各自独立抽取**，互不排斥——同一段话若两边的标准都满足，两边都输出。

两类：
- market_trend：外部宏观变化
- commercial_trend：业务与商业化层面的变化（新盈利模式、定价策略调整、渠道转化效率、客户采购行为变化）

本项**独立执行**保密过滤（剔除机密、未公开客户名单、NDA 限制条款、核心财务数据），不要因为证词那边已经过滤过就跳过。

**在途交易隔离（从严）**：具体正在跟进、尚未落地的商业项目、谈判细节、竞争性投标数据，一律不得进入此处。任何能指向特定公司的内容一律不输出，即使已匿名。

### 6.9 后置程序步骤（非 LLM）

**前置**：`Pending` 在**内容提取之前**就已判定。这类会议的识别阶段照常跑完（参会人与 6.3 的公司识别都有结果，并展示在管理端），但**不进入内容提取**，下列步骤一概不执行，等人工指定类型后再触发。

内容抽取返回后，程序依次执行：

1. **写会议状态**——`quality.usable = false` → 置 `Invalid`（1.10）；类型为 GS → Founder → 置 `Flagged`（仅提醒，不阻断）；其余 `Passed`
2. **机械清洗**——按去向执行实体/人名剥离与 n-gram 近逐字剔除（适用矩阵见 1.4、范围见 1.5）
3. **来源行附加**——证词两版均在正文首行附来源行，取数同源（注册表角色 + 步骤 4 回溯的专长标签）：署名版附 `来源：<组织> <角色> <姓名>`，匿名版附 `来源：某<专长标签>领域的<角色>`（无姓名、无组织）
4. **标签回溯**——按会议日期从注册表取当时生效的角色与专长标签（按 1.8 的有效期规则，区间重合取最后一条）
5. **公司归属裁决**——取识别阶段（6.3）的 `company_mentions`，仅 `confidence = high` 的采纳；低置信度不采纳并记 Pending；**无公司归属的内容直接丢弃、不写入**。**GS → 创始人类型加严**：其产物进入创始人可读的空间，误判等于让一家公司的创始人读到另一家的内容，故本类型的采纳门槛高于其余类型，并以 `Flagged` 人工复核兜底（2.1）
6. **落中间表**——按各类型的空间映射逐去向写入中间表（1.1），`company_id` 必填项校验。**是否同步投影到 `ai_rag_entry` 取决于授权状态**：`Passed` 默认已授权、同步写入；`Pending` 改判后首次提取默认未授权、只留中间表（9.6.4）
7. **幂等**——按 `meeting_id` 软删旧条目后写新条

## 九、管理端功能

> 本章覆盖 Fireflies 在管理端的四个页面与三条横切能力。提取与路由本身见第一~六章，本章只管**人怎么看、怎么改、改了之后怎么生效**。

### 9.1 页面清单与职责边界

| 页面 | 回答的问题 | 数据源 |
|---|---|---|
| **Configuration** | 连没连上、上次同步什么时候 | 租户级连接配置 |
| **Raw Data** | 原文拉到了吗、能不能用 | `ff_meeting` / `ff_meeting_sentence` |
| **Summary Records** | AI 判成了什么、路由对不对、要不要改 | `ff_meeting` + 提取产物 |
| **Cheat Sheet** | 平台外的人是谁 | 外部人员注册表 |
| **Expertise Tags** | 专长标签有哪些 | 标签字典（9.8） |

五个页面在同一个 `Fireflies Management` 下以 Tab 组织，顺序按原型：Summary Records（带 Pending 红点）· Configuration · Cheat Sheet · Expertise Tags · Raw Data。

职责不重叠：Raw Data 只对**原文**负责，Summary Records 只对**派生产物**负责。同一场会在两页各出现一次，互不替代。

### 9.2 Configuration

**连接方式只支持 API Key**（《Fireflies Configuration》明确）。MCP / OAuth 仅为调研记录，不实现。

#### 9.2.1 归属层级

**一个租户一条连接**，不按公司、不按项目。

Fireflies 的 API key 代表一个 **workspace**，`transcripts` 返回的是整个工作区可见的全部会议（实测该 key 的 `num_transcripts` 为 1，列表却返回 43 场）。工作区是 GS 侧的，不属于任何一家被投公司——会议拉进来之后才按内容分派到各公司。因此连接的归属只能是 `organization_id`，与证词 / Cross-Company 空间的键控层级一致。

#### 9.2.2 能否复用 `third_party_connection`

**不复用，新建 `ff_connection`。** 四条理由，前两条是硬的：

| # | 问题 | 说明 |
|---|---|---|
| 1 | **归属维度不兼容** | 该表 `company_id` / `project_id` 均 `NOT NULL`，唯一键是 `(project_id, tool_id)`。Fireflies 是租户级，两列都没有对应值。要么填假值，要么把两列改成可空——后者会放松现有 6 个 DI 工具的约束 |
| 2 | **凭据明文存储** | `access_token TEXT`，全表无加密，现有 DI 工具沿用此做法。Fireflies key 能读取整个工作区的会议转录（含在途交易、机密商业内容），不能继承这个做法 |
| 3 | **业务域与字段不对口** | 该表服务 DI 域，`tool_id` 外键指向 `d_tool`（DI 工具字典），`repository` / `host_url` / `target_addresses` / `aws_access_key_id` / `business_scope` 全是 DI 专用列。Fireflies 只用得上 `access_token` 一列，其余全空 |
| 4 | **同步状态语义不同** | `sync_status` 是 ETL 三态（`underway` / `succeed` / `failure`），描述的是"这一次跑得怎么样"；Configuration 页要的是连接四态（见 9.2.4），描述的是"这条连接现在健不健康"。两者不是一回事，硬套会让其中一个语义失真 |

> 若将来要统一管理所有第三方凭据，正确做法是抽一张与业务域无关的凭据表（凭据 + 归属 + 加密），而不是把租户级连接塞进按项目键控的 DI 表。这属于独立的技术改造，不在本次范围。

#### 9.2.3 数据模型 `ff_connection`

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `organization_id` | 租户，**唯一**——一个租户一条 |
| `api_key_cipher` | **加密后**的 API key，密文存储 |
| `account_email` / `account_name` | key 持有者账号，来自 `user` 查询，供页面展示「connected as …」 |
| `connection_status` | 四态，见 9.2.4 |
| `last_success_sync_at` | 最近一次**成功完成**的拉取时间 |
| `last_attempt_at` / `last_error` | 最近一次尝试的时间与失败原因，供排障 |
| `consecutive_failures` | 连续失败次数，达阈值转 `Disconnected` |
| `created_by` / `created_at` / `updated_by` / `updated_at` | 审计 |

**密钥存储**：密文入库，只在服务端解密后使用；**任何接口都不回传 key 原文或密文**。参考系统内 QuickBooks 集成的现状（token 明文存两张表并明文上传 S3、client secret 提交进部署配置），此处不复制该做法。

#### 9.2.4 连接状态

| 状态 | 判定 | 展示 |
|---|---|---|
| `Unconnected` | 从未配置过 key | 灰点 |
| `Connected` | 最近一次调用成功 | 绿点 |
| `Failed` | 有 key，但调用返回鉴权错误（key 错 / 被吊销） | 红点 |
| `Disconnected` | 曾连通，此后连续 N 次调用失败（N 走配置） | 灰点 |

**状态转移**

```
Unconnected --Link 成功--> Connected
Connected   --鉴权错误--> Failed
Connected   --连续 N 次非鉴权失败--> Disconnected
Failed / Disconnected --Link 成功 或 Sync 成功--> Connected
```

`Failed` 与 `Disconnected` 分开，是因为处置动作不同：前者要换 key，后者多半是对方服务波动、等一等或手动 Sync 即可。合并成一个状态会让用户不知道该做什么。

#### 9.2.5 Link

原型上输入框**常驻且始终为空**，已连接时也一样——**页面从不回显 key，连掩码都不显示**。换 key 就是输入新的再点一次 Link，覆盖旧的。没有断开按钮（原型无此入口，本设计也不加）。

流程：

1. 输入框非空时 `Link` 按钮激活
2. 点击后先调 Fireflies `user` 查询做校验——它是最轻的一个接口，同时能拿到 `email` / `name`，一次调用解决"key 对不对"和"连的是哪个账号"两件事
3. 校验失败：直接报错，**不落库**；页面状态不变（避免存下一个用不了的 key）
4. 校验通过：加密落库，写 `account_email` / `account_name`，状态置 `Connected`，`consecutive_failures` 清零

#### 9.2.6 Sync

**Sync now**：手动触发一次增量拉取，与每日定时拉取走**同一入口**，不走两套逻辑。

- 拉取进行中按钮置灰，避免并发拉取产生重复
- 拉取范围按 `last_success_sync_at` 增量取
- **首次连接回溯最近 14 天**（默认值，走配置可调）。全量回溯会在首次连接时灌进整个工作区的历史会议，量不可控且多数已无处理价值

**Last sync 只记成功**：失败的那次不覆盖 `last_success_sync_at`，否则页面显示"刚刚同步过"而实际数据是旧的，比不显示更糟。失败信息进 `last_attempt_at` / `last_error`，需要时在状态区提示。

**定时拉取**：每日一次，服务端排程，页面上没有频率配置项（需求与原型均未提供）。

#### 9.2.7 接口

| 接口 | 作用 | 返回要点 |
|---|---|---|
| `GET /api/web/fireflies/connection` | 页面加载 | 状态、`account_email`、`last_success_sync_at`、是否正在同步。**不含 key** |
| `POST /api/web/fireflies/connection/link` | 提交 key | 校验 + 落库；失败返回具体原因（鉴权失败 / 网络不可达） |
| `POST /api/web/fireflies/connection/sync` | 手动同步 | 立即返回，拉取异步执行；重复调用直接拒绝 |

**权限**：仅管理端，且限本租户的 Portfolio Group Manager / Super Admin。连接是租户级资产，普通管理端账号不应能改。

### 9.3 Raw Data

该页是**原始逐字稿 + 元数据**的留存与查看入口，保证底层数据完整可追溯（需求原话）。它只对**原文**负责——派生产物一律归 Summary Records。

#### 9.3.1 拉取

**一次调用拉 50 场，含正文。** `transcripts` 与 `transcript` 在 Fireflies 是同一个 `Transcript` 类型，`sentences` 可以直接写进列表查询——实测一次 `transcripts(limit:50)` 返回 43 场会议、19,261 条句子。**不要**做成「列表 + 逐场详情」两段式，那会把每 50 场的配额消耗从 1 次变成 51 次。

| 项 | 取值 |
|---|---|
| 增量依据 | `fromDate` / `toDate`（ISO 8601），起点取 `last_success_sync_at` |
| 分页 | `limit` **上限 50**，配合 `skip` |
| 首次回溯 | 最近 14 天（9.2.6） |
| 触发 | 每日定时 + 手动 Sync now，同一入口 |

**幂等**：以 Fireflies 的 `id` 为业务唯一键。重复拉到同一场会时 upsert 元信息、逐句先删后插——Fireflies 侧的转录可能被重新处理，句子数会变，增量比对不如整场重写简单可靠。

#### 9.3.2 数据模型

**`ff_meeting`（会议元信息）**

| 字段 | 来源 | 备注 |

| `participants` | `participants` | 邮箱数组 |
| `attendance` | `meeting_attendance` | `[{name, join_time, leave_time}]`，**姓名的首选来源**（1.8） |
| `speakers` | `speakers` | `[{id, name}]`，`speaker_id` 的解析依据 |
| `host_email` / `organizer_email` | 同名字段 | |
| `transcript_url` / `meeting_link` | 同名字段 | 回跳 Fireflies / 会议平台 |

| `validity` | 我方判定 | `Invalid` 与否，见 9.3.4 |

**不存的字段**，各有理由：

| 字段 | 为什么不存 |
|---|---|
| `meeting_attendees` | 实测除 `email` 外全为 null，信息已被 `participants` + `attendance` 覆盖 |

**`ff_meeting_sentence`（逐句）**

| 字段 | 来源 |
|---|---|

| `idx` | `index` |
| `speaker_id` / `speaker_name` | 同名字段 |

#### 9.3.3 列表

**字段**：Meeting ID、Title、Date、Time、Duration、Participants、Ingested at。

| 列 | 取值 |
|---|---|
| Meeting ID | `fireflies_id`（Fireflies 返回的原生 id） |
| Date / Time | 由 `started_at` 拆分展示，形如 `Sep 15, 2026` / `09:30 AM` |
| Duration | `duration_minutes` **取整到分钟**展示（`58 min`）。**不要**拿 `attendance` 的进出场时间自行推算——实测两者不一致（`39.06` 分钟 vs 实际约 37 分钟），各处推算法不同会让同一场会在不同页面显示不同时长 |
| Participants | 姓名逗号分隔，**全部展示不截断**（原型为换行铺开）；取 `attendance[].name`，无则回退邮箱 |
| Ingested at | `ingested_at`，日期 + 时间 |

**行末**：`Raw transcript` 链接；判为无效的会议在链接右侧追加灰色 `Invalid` 徽章。

**分页**：需求与原型均未给搜索或筛选，本页只做分页，默认按会议时间倒序，**每页 10 条**——与系统内同类管理页面一致（`qboLog` / `normalizationTracing` / `metricsTracing` / `memorySettings` 均为 10；`devSupport` 下的开发者工具用 20，不属同类）。

> **时区**：`started_at` 存 UTC，展示按统一时区换算（Configuration 页的 `Jul 15, 2026 · 10:52 AM` 同此）。展示时区取自哪里（租户配置 / 浏览器）见 9.11。

#### 9.3.4 `Invalid` 标记

需求：「当一些会议很短且无重点内容时，判定为无效会议，显示灰色 `Invalid` 标签」。这句话里其实是**两个判据、两个时机**：

| 来源 | 时机 | 判据 | 是否调 LLM |
|---|---|---|---|
| 程序硬门槛 | 拉取后、识别前 | 时长 / 句数低于阈值（环境变量，见 6.2） | 否 |
| LLM 质量门槛 | 提取时 | `quality.usable = false`——通篇寒暄、设备调试、无实质讨论 | 是 |

**判定顺序：`Invalid` 优先于 `Pending`。** 硬门槛先跑，判为 `Invalid` 的会议**不再做参会人识别、不调 LLM**。这样既省掉无意义的调用，也让状态自洽——不会出现"一场两句话的会因为参会人认不出而挂在 Pending 队列里等人工"。

**`Invalid` 不删数据**：原文照常入库、照常可在本页查看。需求要的是"完整可追溯"，`Invalid` 只是一个不再往下走的标记。

**Pending 会议在本页不带任何标记**——该页只回答"原文能不能用"，`Pending` 是派生侧的状态，归 Summary Records。

#### 9.3.5 原始逐字稿详情

每行末尾 `Raw transcript` 链接进入详情页，展示带时间戳与说话人的完整逐字稿。

> 面包屑与页面命名原型尚未统一（列表 `Fireflies Raw Data`、详情 `Fireflies Meeting Data`），**待定，不在本轮范围**。

**页头**：标题 + 一行元信息 `Raw verbatim transcript — 9,420 words · unclassified and unmodified · captured <ingested_at>`。「unclassified and unmodified」是固定文案，用于向管理员明示本页与其余界面的区别。

**信息卡**：Date / Time / Duration / Participants，与列表同源。

**正文**：

- 用 `text`（清洗后）；`raw_text` 存着备查，页面不展示两版
- 时间戳按 `start_time` 折算成 **`[hh:mm:ss]`**（原型为 `[00:00:04]`），不用 `mm:ss`——超过一小时的会议会歧义
- 说话人用 `speaker_name`（ASR 识别值，可能与注册表姓名不一致，此处**照原样显示**，不做替换——这里是原文界面，替换会破坏可追溯性）
- 页尾 `End of transcript · N words total · stored in the admin library prior to any classification or routing.`

> **长会议的渲染**：448 句/场是均值，长会议更多，一次性渲染会卡。**接口要支持按 `idx` 区间取**，不要做成只有全量一种取法。
>
> 但这里是**加载批次，不是分页**——原型为整篇连续滚动，转录要能从头读到尾、能 Ctrl+F 查找，切成一页页翻会同时破坏这两件事。故不套用列表的 10 条，改为滚动到底续加载，每批数百句量级，具体值在开发设计按渲染性能定。

> **这是系统内唯一保留原文措辞的界面。** 其余所有面向 Goldie 的产物都已去逐字化（1.4）。因此本页限管理端可达，且按 `organization_id` 做租户隔离。
>
> 创始人侧「只能看本人参加会议的完整转录」是另一条入口（《创始人与管理端问答总结》标注为**待确认**），不在本页范围。

#### 9.3.6 权限与留存

- **仅管理端**，按 `organization_id` 隔离；创始人端无任何入口
- **永久留存**（需求 Mode A），不随派生产物的重算而删除
- 幂等重写只影响逐句与元信息，`ingested_at` 保留**首次**入库时间

### 9.4 Summary Records — 列表

该页是**派生产物**的查看与改判入口，只对提取结果负责；原文归 Raw Data。

**Tab 上带 Pending 红点**——有未处理的 Pending 会议时亮起，是整个 Fireflies 模块唯一的主动提醒。

#### 9.4.1 列表字段

| 列 | 取值 |
|---|---|
| Meeting | 标题 + 第二行小字 `<fireflies_id> · <duration> min` |
| Time | **单列合并**展示 `Jul 15, 2026 · 10:00 AM`（与 Raw Data 的 Date / Time 两列不同，两页各按自己的原型来） |
| AI Meeting Type | 蓝色标签；`Unknown` 为灰色 |
| Companies | 已采纳的公司名，多家时逗号分隔；宽度不够用 `...` 截断 |
| Status | `Passed` 绿 / `Flagged` 琥珀 / `Pending` 红 |
| 行末 | `Review` 链接进详情 |

**搜索**：模糊匹配 Meeting 与 Companies。
**筛选**：`All meeting types` / `All statuses` / `All time` 三个下拉。
**分页**：每页 10 条，与 Raw Data 及系统内同类页面一致，默认按会议时间倒序。

#### 9.4.2 Status 与阻断关系

| 状态 | 含义 | 是否阻断 |
|---|---|---|
| `Passed` | 类型与参会人均判定成功，内容已路由 | 否 |
| `Flagged` | 类型判为 GS → Founder | **否**，仅提醒 |
| `Pending` | 参会人未识别，或类型未判出 | **是**，内容提取与路由未执行；识别结果照常展示 |

`Flagged` 只是提醒：GS → Founder 与 GS → Board Call 从参会数据上无法区分，AI 默认归前者，需要人工确认是否改判。它不代表内容有问题。

### 9.5 Summary Records — Review 详情

#### 9.5.1 会议信息卡

| 字段 | 取值 |
|---|---|
| Date | `started_at`，日期 + 时间合并展示 |
| Duration | 取整到分钟 |
| Fireflies ID | `fireflies_id`，Fireflies 返回的原生 id |
| Scrub Status | 三态徽章，同列表 Status |
| AI Meeting Type | 当前值标签 + 下拉，切换时标签实时更新 |

#### 9.5.2 会议类型改判

下拉八个选项：GS → Founder、GS → Board Call with Founder、GS → LP、GS Internal、GS → Strategic Partner、GS → Exit Partner、Unknown，以及当前值。

- **Strategic 与 Exit 拆成两项，但提取侧已合并为一类**（《AI Meeting Type 自动映射标准》「两者无需区分，统一为一类」）。选哪个都走同一份提示词（6.7）、同一套路由，**不产生行为差异**，拆开只为管理端记录得更细
- **`Unknown` 等同于打回 Pending**——清空已有产物、停止路由、回到等待人工指定的状态
- 改判触发的重算范围见 9.9

#### 9.5.3 公司指定

**已识别的公司以标签展示**，每个带 `×` 可移除；右侧下拉可添加。

**每个公司下方展示识别依据**，原型格式：

```
Northwind Labs — Matched via email domain northwindlabs.io
```

这就是需求《AI Meeting Type 自动映射标准》要的「管理端应支持追溯"这场会议为何关联到此公司"」。识别链共六步（1.9），**只展示命中的那一步与命中的具体值**，不展示整条链。各步的依据文案：

| 命中步骤 | 依据文案 |
|---|---|
| ① 完整邮箱 → LG 公司端用户 | `Matched via <email> (LG company user)` |
| ③ 邮箱域名 | `Matched via email domain <domain>` |
| ⑤ LLM 正文推断 | `Inferred from transcript — <evidence>` |
| 人工指定 | `Assigned by <user> on <date>` |

> 手动添加的公司也要写依据，否则时间一长分不清哪些是 AI 判的、哪些是人改的——而这两者的可信度不同。

**下拉的候选范围**：LG 系统内的公司，可搜索。

> **待澄清**：原型只画了一个 `Company` 占位下拉，看不出候选范围。需求写的是「可多选，可搜索下拉添加公司」（即全量 LG 公司）；另一种口径是只列「LLM 识别出来且在 LG 系统内存在」的公司。两者差别很大——后者管理员**无法补充 AI 没识别出的公司**，而 Pending 会议往往正需要人工补。本设计按**全量可搜索**实现，若要收窄需明确。

#### 9.5.4 参会人

**展示格式**：胶囊标签 `姓名 · 组织 (角色)`，按身份着色。

| 身份 | 示例 | 样式 |
|---|---|---|
| GS 方 | `Sarah Chen · GS (PM)` | 蓝 |
| 创始人 | `James Wilson · TechVision (Founder)` | 橙 |
| 外部伙伴 | `Jane Doe · Acme Capital (Strategic Partner)` | 紫 |
| 未识别 | `Michael Brown · — (Unidentified)` | 灰 + 红点 |

**只有外部人员可点开编辑并回流注册表。** 参会人按来源分两类：

| 来源 | 举例 | 能否编辑 |
|---|---|---|
| **LG 平台内用户**（按完整邮箱匹配到管理端 / 公司端账号） | `Sarah Chen · GS (PM)` | **点击无弹框**（需求 2026-09-22 明确）——他们的姓名、组织、角色以平台账号为准，注册表不该有他们的副本 |
| **外部人员**（注册表已登记，或未识别） | `Jane Doe · Acme Capital (Strategic Partner)`、`Michael Brown · — (Unidentified)` | 可编辑，改动回流 Cheat Sheet |

**外部人员的两个弹框，已识别与未识别走不同的一个**：

| | `Edit external party` | `Assign new external party` |
|---|---|---|
| 触发 | 点已识别的人 | 点带红点的 `Unidentified` |
| **Name** | **置灰只读** | **可编辑** |
| 已带入的值 | 注册表中的现有登记 | 仅邮箱（从会议数据带入） |

**Name 的可编辑性差异是有意的**：姓名是注册表的唯一识别符（《Cheat Sheet》明确，确认发布后不可改）。已在册的人改名等于换了一个人；而未识别的人此刻还没进注册表，ASR 给的姓名可能是昵称或听错的拼写（`Mike` / `Michael`、`Speaker 2`），**必须允许订正后再入册**。

**弹框字段**：Name、Email(s)（可多个）、Organization、Role、Expertise tags、Validity period（From 必填，To 留空表示 open-ended）——**与 Cheat Sheet 页的新增 / 编辑弹框完全一致**。

> 原型在这两个弹框里多画了一个 `Company` 下拉，**是画错了**，不实现。外部人员的所属机构只有 `Organization` 一个自由文本字段，注册表不持有 `company_id`。

#### 9.5.5 回填注册表

在本页登记的人**自动写入 Cheat Sheet**（《会议内容提取规则》Pending 单项解决动作第 3 条），并带 `From FF Summary Records` 来源标识。

- 新登记 → 注册表新增一条，`Updated by` 记为系统导入并标明来源会议（原型 History 页的 `System (FF-09 import)` 即此）
- 编辑已有条目 → 按 Cheat Sheet 的版本规则产生新版本（见 9.7）
- **姓名冲突**：`Assign` 弹框填入的姓名若已存在于注册表，不能直接新建——姓名是唯一识别符。此时应提示"该姓名已登记"，并让管理员选择关联到已有条目还是改名

#### 9.5.6 保存与生效

- 类型改判、公司增删、参会人登记**各自独立保存**，不要求整页提交
- 改判与公司变更会触发路由重算（9.9）；参会人登记只影响注册表与后续会议的识别，**不回溯已提取的会议**
- 所有动作写审计日志（9.10）

### 9.6 Content Routing Matrix

矩阵三列：`Content`（内容块，可编辑）、`Visible to`（谁能看到这一行）、`Authorize`（勾选则授权）。

#### 9.6.1 矩阵从哪来

**矩阵是提取结果的呈现**，不是独立数据。上方的会议类型、公司、参会人任一项被改动 → 触发重新提取（9.9）→ 提取产物按去向铺成矩阵的各行。

因此：

- `Pending` 会议**初次进来时矩阵为空**——识别做了、内容没提取。指定类型后触发首次提取，矩阵才出现
- 改判类型会让矩阵**整体重来**，因为不同类型的产物形态不同（见 9.6.2 的行构成差异）
- 公司增删只改变**行内内容的归属**，不改变行的构成

#### 9.6.2 行的构成：按会议类型

**一行 = 一个内容块 + 它的全部去向。** 同一份内容落多个去向时合并成一行展示（需求原话：「不同角色看到的可能是同样的内容，合并展示」）。

**`Visible to` 是展示，不是配置**——它由去向决定，管理员改不了。能改的只有 `Content` 和 `Authorize`。

| 会议类型 | 内容块 | 去向 | Visible to |
|---|---|---|---|
| **GS → 创始人** | 摘要 / 纪要 | 1a + 1b | Founder、PM & PGM |
| | 知识库条目 | Founder KB | Founder、PM & PGM |
| | 匿名洞察点 | Cross-Company | 整个租户 |
| **GS → Board Call** | 退出准备 / 战略摘要 | 1b | PM & PGM |
| | 匿名洞察点（带 care flag） | Cross-Company | 整个租户 |
| **GS → LP** | 按公司拆分的内容摘要 | 1b | PM & PGM |
| | 专家证词 · 匿名版 | 证词-匿名 | 整个租户的创始人 |
| | 专家证词 · 署名版 | 证词-署名 | PM & PGM |
| | 市场趋势 | Cross-Company | 整个租户 |
| **GS 内部** | 涉及具体公司的内容摘要 | 1b | PM & PGM |
| | 战略-决议闭环 / 全公司视角 | Cross-Company | 整个租户 |
| **GS → Partner** | 涉及公司退出的内容摘要 | 1b | PM & PGM |
| | 专家证词 · 匿名版 | 证词-匿名 | 整个租户的创始人 |
| | 专家证词 · 署名版 | 证词-署名 | PM & PGM |
| | 市场与商业趋势 | Cross-Company | 整个租户 |

> **Board Call 的前两行不在矩阵里**：改判为 Board Call 后只补跑 1b（2.5 / 6.5），1a 与 Founder KB 沿用改判前已入库的版本、不重跑。矩阵只展示本次提取的产物。
>
> **证词两版各占一行**，因为受众不同——匿名版给全租户创始人，署名版给管理端。两行的正文相同，差别只在程序附加的来源行（3.4）。管理员改了一版，另一版要同步。

**按公司拆分的行**：`1b` 类内容是一家公司一条 entry，矩阵里按公司分行展示，行标注公司名。公司被移除时，对应的行一并消失。

#### 9.6.3 Content 编辑

**整格文本框编辑**：一个多行 `textarea`，保存的是一整段字符串。改动后该格出现琥珀高亮边框。

需求写的「每行一条 bullet」是**排版约定，不是数据结构**——系统不认识"条"这个概念，不做逐条的增删改与排序。据此：

- `minutes` 的输出契约**保持字符串**，6.4 / 6.6 / 6.7 / 6.8 四份提示词不用改
- 中间表该列是一个文本字段
- 审计的 `CONTENT_EDIT` 记改前改后两段文本，不记"哪一条被改了"

> 提示词侧配合一下即可：要求 LLM **一行一条**输出，别写成整段。纪要现在按主题分节，改为分行列点是顺的。

**编辑后不重跑 LLM**——人工改的就是最终内容，重跑会把它覆盖掉。

#### 9.6.4 Authorize 与落库时机

**`Authorize` 是放行开关**：勾选后 `Visible to` 里的角色才看得到这一行，未勾选的内容不进 RAG 空间、Goldie 召不回。

**提取产物一律先落中间表**，`ai_rag_entry` 是其中已授权那部分的投影：

```
提取完成 ──→ 中间表（每场会、每个去向一条，始终保留）
              │
              ├─ 已授权 ──→ 同步写入 ai_rag_entry，Goldie 可召回
              └─ 未授权 ──→ 只在中间表，管理端可见、Goldie 不可见
```

中间表不只是"授权前的暂存区"——它是矩阵的**可编辑正本**，`ai_rag_entry` 由它派生。这样 `Content` 的编辑、授权的开关、以及将来的重算，都只操作一份数据。

**初始授权状态**

| 场景 | 初始状态 |
|---|---|
| `Passed` 会议提取完成 | **默认已勾选**——内容落中间表的同时写入 RAG 空间，与需求中「`Passed` = AI 已路由全部内容」一致，自动路由无需人工介入 |
| `Pending` 改判后首次提取 | **默认未勾选**，只落中间表，需人工确认后才放行 |
| 改判触发的重新提取 | 沿用改判前该去向的勾选状态；新出现的去向未勾选 |

**三类操作的落库行为**

| 操作 | 中间表 | `ai_rag_entry` |
|---|---|---|
| 编辑 `Content` | 更新 | 该行已授权则同步更新；未授权则不动 |
| 勾选 `Authorize` | 置为已授权 | 按中间表当前内容写入 |
| 取消勾选 | 置为未授权，**内容保留** | 软删（幂等规则同 1.6），Goldie 立即召不回 |

取消勾选不删中间表的内容——撤回是可逆的，重新勾上应当恢复原样，而不是要求管理员重新提取或重打一遍。

> **为什么不能"先写入、再按标记隐藏"**：现有检索侧除 `company_id` 外不做行级过滤，`SearchHitDTO` 也不透出 metadata（见 3.4 批注），召回后拿不到授权标志。未授权只能靠"不写入"来保证。
>
> 这是对 §6.9「路由落库」的结构性改动——落库从提取的收尾动作，变成**中间表 → RAG 空间**的一次投影，投影范围由授权状态决定。

#### 9.6.5 保存与生效

原型底部为 `Discard Changes` / `Confirm & Apply Routing` 两个按钮，**整页提交**；需求文档写的是「Save 只保存该行，Cancel 还原该行」，**按行提交**。

两者取原型：**整页提交**。理由是 `Authorize` 的勾选与 `Content` 的编辑往往要一起判断（改完内容才决定放不放行），按行提交会让管理员在部分授权、部分未授权的中间态里来回切换，也更难写一条完整的审计记录。

- `Confirm & Apply Routing`：把本页所有改动（内容编辑 + 授权变更）一次性落库并应用路由
- `Discard Changes`：还原到进入页面时的状态
- 无改动时两个按钮置灰（原型即此）
- 每次应用写一条审计记录，含改了哪些行、授权了哪些去向（9.10）

### 9.7 Cheat Sheet

平台外人员的登记表。字段口径见 **5.2**（角色 6 项枚举、专长标签、有效期规则），本节只管页面、数据模型与版本机制。

#### 9.7.1 数据模型：单表存版本

**一张表，一行一个版本快照**，不设单独的主体表。

**`ff_registry_party`**

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `organization_id` | 租户 |
| `name` | **唯一识别符**，确认发布后不可改。`(organization_id, name)` 即标识一个人，同一人的多个版本共用同一值 |
| `emails` | 可多个 |
| `organization` | 外部机构名，自由文本 |
| `role` | 6 项枚举之一（5.2） |
| `expertise_tags` | 多选，存**标签文本**而非字典外键 |
| `valid_from` / `valid_to` | From 必填，To 可空（空 = `present`） |
| `source` | `MANUAL`（Cheat Sheet 页新增）/ `FF_SUMMARY_RECORDS`（审核会议时顺手登记） |
| `updated_by` | 操作人；系统导入时记为 `System (<会议 id> import)` |
| `updated_at` | 写入时间，**重合裁决与复核时间的依据** |

**每次 Confirm 追加一行**，不修改旧行。

| 要什么 | 怎么取 |
|---|---|
| 列表的当前状态 | 按 `(organization_id, name)` 分组，取 `updated_at` 最大的一行 |
| History | 该 `(organization_id, name)` 的全部行 |
| 某场会议当时的登记 | 见 9.7.2 的回溯算法 |
| 最近复核时间 | **最新一行的 `updated_at`**——不单设 `last_reviewed_at` 字段 |

> **为什么不用主体 + 版本两张表**：主体表唯一能承载的是姓名和复核时间。姓名不可改，本身就是稳定标识，不需要代理 id；复核时间又与最新版本的 `updated_at` 等价。拆两张表只换来一个多余的 join，还要维护两处的一致性。
>
> 代价是姓名唯一性**没法用数据库约束表达**（同一人本就有多行），新建时的重名校验落在应用层。这是可接受的——`Assign new external party` 那条路径本来也要做同样的校验（9.5.5）。

> **为什么姓名能当唯一识别符**：原型的 History 里，同一个人换过邮箱（`m.whitfield@meridian-health.com` → `eleanor@northbridge-cap.com`）、换过机构（Meridian Health Group → Northbridge Capital）、换过角色（Strategic Partner → LP）。邮箱和机构都会变，能把这些版本串成一个人的只有姓名。

> **被引用时也用姓名**：证词的发言人、参会人识别结果指向的都是 `(organization_id, name)`，不需要代理 id。

#### 9.7.2 有效期与版本裁决

**允许重合，重合时取最新的那条**——按版本的 `updated_at` 取最晚写入的，**不是**按 `valid_from` 最晚的。

不自动闭合上一版的有效期。管理员填什么就是什么，重合由裁决规则兜底。

这条规则顺带解决了**订正**：改错别字、补一个漏填的邮箱时，**有效期保持不变**再提交即可——新版本与旧版本区间完全重合，但写入更晚，于是自然生效，旧版本留在 History 里可查。不需要为"订正"单设一种操作。

**按会议日期回溯的取值算法**（1.8 与 6.9 步骤 4 用的就是它）：

```
取该 party 下满足 valid_from <= 会议日期 <= COALESCE(valid_to, 无穷) 的全部版本
 → 按 updated_at 降序取第一条
```

> ⚠️ **邮箱匹配也要走这套回溯，不能只用最新版本的邮箱。** §1.9 ② 按完整邮箱匹配注册表，若只查最新版本，一个换过邮箱的人在**旧会议**里就匹配不上——原型那位 2023 年用的是 `m.whitfield@meridian-health.com`，而最新版本里根本没有这个地址。角色、专长标签、邮箱三者同源，回溯规则必须一致。

#### 9.7.3 列表

**顶部汇总条**：`N entries are overdue and flagged "needs review".`——原型有、需求没写，是整页唯一的主动提示。

**列**：Name、Email(s)、Organization、Role、Expertise tags、Validity period，行末 `History` / `Edit`。

| 列 | 展示 |
|---|---|
| Name | 姓名；系统导入的在下方加 `From FF Summary Records` 标签 |
| Email(s) | 多个**纵向堆叠全部展示**（原型如此），实在放不下再用省略号 |
| Role | 蓝色标签 |
| Expertise tags | 灰色小标签，多个换行展示 |
| Validity period | `Aug 2, 2026 – present`；逾期未复核的在下方加琥珀 `Needs review` 徽章 |

**搜索**：模糊匹配 Name、Email(s)、Organization、Expertise。
**筛选**：按 Role。
**分页**：每页 10 条，同其余管理页面。

#### 9.7.4 新增与编辑

`Add external party` / `Edit`，两者字段相同，差别只在 Name：

| | Add | Edit |
|---|---|---|
| Name | 可填 | **置灰只读** |
| 其余字段 | 空 | 带入最新版本的值 |

**字段**：Name、Email(s)（可多个，支持 `+ Add another email` 与逐行 ×）、Organization、Role（下拉）、Expertise tags（多选）、Validity period（From 必填 / To 可空）。

弹框内提示文案：`"From" is required. Leave "To" empty to show the period as open-ended.`

**Confirm 前弹二次确认**，告知姓名提交后不可编辑（需求明确）。

**姓名重复**：租户内已存在同名时不允许新建——姓名是唯一识别符。此时提示已登记，引导去 `Edit`。Summary Records 页的 `Assign new external party` 同此（9.5.5）。

#### 9.7.5 Needs review

最新一行的 `updated_at` 距今超过 90 天即标记。

**不单设"复核"按钮**——任何一次 `Edit` 提交即刷新它。复核的实质就是有人看过并确认，单独加一个"我看过了"的控件只会多一个没人点的按钮。

**"看过但无需修改"**：`Edit` 弹框什么都不改直接 `Confirm` 时，**原地更新最新一行的 `updated_at` 与 `updated_by`，不追加新行**。这样 History 里不会多出一条内容完全相同的噪音记录，而那行显示的更新时间恰好就是复核时间——语义是准的，确实有人在那天看过它。

#### 9.7.6 History

独立页面，不做行内展开。面包屑 `Fireflies / Cheat Sheet / Role History`，前两级可跳回。标题 `<姓名> — Role History`。

**每行一个完整快照**：Name、Email(s)、Role、Organization、Expertise tags、Validity period、Updated by（含更新日期）。

**排序**：按 `valid_from` 倒序（原型如此）。同一生效日期有多行时（订正场景），再按 `updated_at` 倒序——与 9.7.2 的裁决口径一致，排在最上的就是当前生效的那条。

**`Updated by` 可以是系统**：由 Summary Records 审核时自动登记的版本，记为 `System (<会议 id> import)`，与人工操作区分。

### 9.8 Expertise Tags

独立 Tab，维护专长标签字典，供 Cheat Sheet 的 `Expertise tags` 多选下拉取值。页面副标题即其定位：`Manage the tags available in the Expertise tags dropdown on the Cheat Sheet.`

#### 9.8.1 页面

- 顶部：`New tag name` 输入框 + `Add tag` 按钮
- 下方单列表格 `Tag`，每行末尾 `Remove`
- **没有编辑入口**——只能增和删

**排序按添加顺序**，不做字母序（原型如此：`Fund-of-funds` / `Healthcare` / `LPAC` / `Hospital procurement` / … 非字典序）。新加的追加在末尾。

#### 9.8.2 数据模型

**`ff_expertise_tag`**

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `organization_id` | 租户，标签按租户隔离 |
| `name` | 标签文本，**租户内唯一** |
| `sort_no` | 展示顺序，新增追加在末尾 |
| `deleted` | 软删标记 |
| `created_by` / `created_at` | 审计 |

**软删而非物理删**：标签被移除后，`ff_registry_party` 的历史版本仍会显示它（那里存的是文本），保留记录便于回答"这个标签当初是谁加的、什么时候删的"。

#### 9.8.3 增与删

**Add tag**：租户内重名直接拒绝并提示，不做大小写敏感区分（`M&A` 与 `m&a` 视为同一个）。

**Remove**：置软删标记。删除前**提示当前有多少条登记正在使用该标签**，但**不阻止删除**——标签过时是正常的，强行拦住只会逼出"Healthcare (deprecated)"这类脏数据。

**不提供改名**，这是有意的：

> Cheat Sheet 的版本快照存的是标签**文本**而非字典外键（9.7.1）。若提供改名，管理员会预期历史登记跟着改，而实际不会——一个做不到用户预期的功能比没有更糟。要换名字就删旧的、加新的，语义清楚。

#### 9.8.4 删除不级联

标签从字典里移除后，历史版本照常显示原标签，只是新建 / 编辑时选不到了。

理由：快照的语义是"当时登记成什么样"，事后改字典不应该改写历史。证词的专长标签按会议日期回溯到某个版本（6.9 步骤 4），若级联删除，已生成证词的来源行会凭空少掉一个标签。

### 9.9 改判与路由重算

#### 9.9.1 三种触发源

Review 页上能改的三样东西，触发的重算范围各不相同：

| 改了什么 | 影响什么 | 重算范围 |
|---|---|---|
| **会议类型** | 产物形态整体改变 | 见 9.9.2 |
| **公司增删** | 只影响**按公司拆分**的行（1b 类） | 新增公司 → 为该公司补跑 1b；移除公司 → 软删该公司的行。Cross-Company 与证词不受影响 |
| **参会人登记** | 可能改变类型判定与证词来源 | 见 9.9.3 |

> 9.6.1 里「公司增删不改变行的构成」说的是 Cross-Company、证词这类**不按公司拆**的行。1b 是一家公司一条 entry，增删公司必然增删对应的行。

#### 9.9.2 按类型改判的重算范围

| 改判 | 重算 |
|---|---|
| `Pending` → 指定类型 | **首次提取**，按新类型跑完整流程 |
| GS → 创始人 ⇄ GS → Board Call | 只补跑 1b（2.5 / 6.5），1a、Founder KB、Cross-Company 沿用已入库版本 |
| 其余任意类型之间 | **整场重跑**——产物形态完全不同，无法增量 |
| 任意类型 → `Unknown` | 打回 `Pending`：软删全部产物（中间表与 `ai_rag_entry` 均软删，保留可追溯），停止路由 |

**公司识别不重跑**。它在识别阶段独立完成（6.3），与会议类型无关，改判不影响其结果。

#### 9.9.3 参会人登记引起的连锁

在 Review 页登记一个此前未识别的外部人，可能把会议类型**从 `Pending` 变成可判定**——比如认出一位 LP，会议就该归 GS → LP。

因此参会人登记提交后：

1. 重跑类型判定（程序，按 2.1 / 3.1 / 4.1 / 5.1 的规则）
2. 判得出 → 提示管理员"已可判定为 X 类型，是否应用"，**不静默改判**
3. 仍判不出 → 保持 `Pending`

不静默改判，是因为管理员在 Review 页的下拉里可能已经手动指定了类型；程序重判的结果与之冲突时，应当由人裁决。

#### 9.9.4 重跑与人工编辑的冲突

同一行的 `content` 有两个写入方——LLM（提取与重跑）和管理员（Matrix 编辑）。重跑会盖掉人工改过的内容，而需求又要求「更改 content → 新的内容将被应用」。

**定：重跑直接覆盖。** 改判即以新类型的 AI 产出为准，人工编辑视为对**旧口径**的临时修正，随旧口径一并作废。不弹确认框、不做"保留人工条目"的例外。

理由：改判意味着这场会的**口径整体换了**——从 LP 改判为 GS 内部后，那条 LP 口径的证词本来就不该存在，保留它只会产生自相矛盾的混合结果。而系统无法区分"对旧口径的修正"（该丢）与"对内容本身的修正"（该留），一律按前者处理，规则简单可预期。

**人工编辑不会凭空消失**：每次编辑都写了 `CONTENT_EDIT` 审计（9.10.2，含改前改后全文），需要时可从审计日志查回并重新填入。

**范围提醒**：

| 改判 | 被覆盖的范围 |
|---|---|
| GS → 创始人 ⇄ Board Call | **只有 1b 行**，其余三行的人工编辑安全 |
| 其余任意类型之间 | 全部行 |
| 公司移除后再加回 | 该公司的 1b 行——加回来的是 AI 原文，不是人工改过的版本 |

#### 9.9.5 重跑后的授权状态

重跑产出新内容，旧的 `ai_rag_entry` 先软删。新内容按什么授权状态投影：

| 情形 | 授权状态 |
|---|---|
| 该去向改判前已授权 | **沿用已授权**，新内容直接投影 |
| 该去向改判前未授权 | 保持未授权 |
| 改判后**新出现**的去向 | 未授权，需人工放行 |

沿用而非清空，与 `Passed` 默认已勾选是同一条口径（9.6.4）——AI 产出默认可路由，人工授权只在 AI 没把握的场合才是必经步骤。

> 副作用要知情：改判后的新内容会**未经人眼就对创始人可见**。这与 `Passed` 会议自动路由的风险等价，不是改判独有的新风险。真正需要人工过目的场合由 `Flagged` 与 `Pending` 兜住。

### 9.10 审计日志

需求要求「所有路由决策与覆盖动作写入审计日志」。系统现状是 `LogAspect` 的 `@Component` 已被注释、无任何写入（见第七章）。

#### 9.10.1 不复用 LogAspect

`LogAspect` 是被停用的通用切面，恢复它要评估全站所有接口的影响，且它记的是**接口调用**，而这里要记的是**业务决策**——同一次改判可能只有一次接口调用，但要记类型变化、重算范围、受影响的去向三件事。

新建 **`ff_audit_log`**，只服务 Fireflies 域。

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `organization_id` | 租户 |
| `event_type` | 见 9.10.2 |
| `meeting_id` | 关联会议；注册表类事件为空 |
| `target` | 受影响对象的标识（去向 + 公司、party 姓名等） |
| `before` / `after` | 变更前后的值，JSON |
| `operator` | 操作人；自动决策记为 `System` |
| `created_at` | 时间 |

#### 9.10.2 事件清单

| 事件 | 触发时机 | 关键内容 |
|---|---|---|
| `IDENTIFY` | 识别阶段完成 | 参会人识别结果（每人命中的是六步链的哪一步）、公司归属与依据、判定出的类型 |
| `EXTRACT` | 内容提取完成 | 会议类型、各去向产出条数、`quality.usable` |
| `TYPE_CHANGE` | 类型改判 | 原类型、新类型、重算范围、是否丢弃了人工修改及条数 |
| `COMPANY_CHANGE` | 公司增删 | 公司、动作、依据文案 |
| `CONTENT_EDIT` | 编辑 Matrix 内容 | 去向、改前改后 |
| `AUTHORIZE_CHANGE` | 勾选 / 取消勾选 | 去向、新状态 |
| `REGISTRY_IMPORT` | 从 Review 页登记外部人 | party 姓名、来源会议 |

**自动决策（`IDENTIFY` / `EXTRACT`）必须记**，不能只记人工动作——Pending 审核时管理员要回答"AI 当初为什么这么判"，靠的就是 `IDENTIFY` 里那条命中步骤记录。9.5.3 页面上展示的识别依据，取的也是它。

**注册表变更不进审计日志**：`ff_registry_party` 本身就是追加写的版本表（9.7.1），每行自带 `updated_by` / `updated_at`，History 页即其审计视图。再抄一份到审计日志只会两处不一致。

#### 9.10.3 保留与查看

- **不随产物重算而删除**——重算会软删中间表与 `ai_rag_entry` 的行，但审计记录必须留着，否则"这条内容当初是怎么来的"就断了
- 查看入口在管理端；MVP 可先不做页面，接口与数据先落地
- 按 `organization_id` 隔离
