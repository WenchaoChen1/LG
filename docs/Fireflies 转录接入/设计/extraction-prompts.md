## 6.1 分工与约定

**分工**：LLM 只做「判断与转述」，机械处理交程序。

| 环节 | 谁做 |
|---|---|
| 非逐字转述（含把 Fireflies 自带摘要整理为 markdown）、内容分类、可迁移性判断、公司提及识别、质量判断、专家候选的领域归类、程序没识别出的参会人推断（姓名变体对名册、从转录推断角色与机构，6.13）、超长摘要的压缩（6.11） | **LLM** |
| 邮箱 / 域名 / 姓名完全匹配的参会人识别、类型判定、实体/人名剥离、n-gram 近逐字剔除、署名附加、专长标签回溯、公司归属裁决、参会人推断的采纳、专家候选过滤（GS 人员 / 角色为 Other / 已有的标签 / 被拒绝的标签）、markdown 文件生成、授权与落库路由 | **程序** |

**语言**：提示词中文，**产物英文**（与现有 `ai_rag_entry.summary` 及 Goldie 默认作答语言一致）。

**输出**：外层一律 JSON，`json_mode=True`；JSON 里承载内容的字段，值一律是 **markdown 文本**，统一经大模型生成或整理（本方案）；Fireflies 自带的摘要也过一遍大模型产出 markdown（需求 I 10-13 版改为「直接使用 Fireflies 的 Summary」，本方案仍经大模型整理，用户决定 2026-10-14，第十章 #56）。截断（`finish_reason=length`）时**整体判失败重试，不抢救半成品**——半份合法外观的结果比没有更危险（沿用 `excel_extract_agent` 的口径）。每个调用各自适用；某个调用最终失败时整场怎么处理，见 6.11「调用编排」。

**调用方式**：

- 一场会的内容加工是**同一次加工任务**：读**同一份转录快照**，按复用矩阵（6.2）分成多次**独立调用**，各调用并行，互不读取彼此的输出（用户决定 2026-10-10）
- 识别阶段先跑：有程序没识别出的参会人或映射不上的发言人时调 P8（参会人推断，6.13），类型判定之后调 P1（质量判断 + 公司识别，6.4）；类型确定且非 `Pending` 后，再并行调用该类型需要的 P2~P7。编排、失败处理与成本见 6.11「调用编排」
- **需求 I 的落实**：《会议内容提取规则》I「去逐字化」要求「完成会议分类后一次性读取原始转录并输出全部衍生内容」，下游不再读原文。落实方式：所有调用属于同一次加工任务、读同一份转录快照，产物一次性落中间表（9.6.4）；Goldie、各页面等下游从不读原文。需求防的是下游各自读原文导致口径不一致，同一快照上的并行调用不构成这个问题
- P1、P8 同样读转录，但只产出识别结果（质量判断与公司提及；参会人身份），不产出任何衍生内容

> 管理员改判类型、增删公司触发的重新提取（9.9）是**加工环节自身的再次触发**，不是下游各自去读原文，不违背本条。管理员编辑内容后只重跑机械清洗、**不重跑 LLM**（6.11）。

## 6.2 提示词总览与复用矩阵

「条件」：P8 在类型判定之前跑、不看类型，只在有程序没识别出的参会人或映射不上的发言人时调用（6.13）；P5 在三类会议里都只抽会上的在册专家（名册带专长标签的人，不管角色），会上没有时不调用；被 P7 推测为专家的人，管理员确认后单独补跑（2.5，用户决定 2026-10-16）。GS 内部全员为 GS 人员，不调 P5、P7（1.11、4.2）。

另有修订调用（6.11）：`summary` 超过 150 个英文单词时程序追加，只压缩已生成的摘要，不读转录。

**为什么按提示词组织**：同一份规则在多个类型复用——公司层 1b 两类会议共用，证词三类会议共用，跨公司四类会议共用。按类型展开就要在每个类型里各写一遍，日久必然漂移；按提示词组织，每份规则只写一处，类型之间的差异只靠参数：P3 的 `extraction_focus`，P5 的 `testimony_speakers` / `testimony_categories`（本方案）；P6 在 GS → LP 多拼一段附加剥离要求（6.9，用户决定 2026-10-10）。

**各提示词的输出键**（字段名与原各类型提示词一致，6.11 与第九章对字段名的引用不变）：P1 `{quality, company_mentions}`；P2 `{summary, kb_doc}`；P3 `{memory_1b: [...]}`；P4 `{fund_1b: {summary, kb_doc} | null}`；P5 `{testimony: [...]}`；P6 `{cross_company: [...]}`；P7 `{expert_candidates: [...]}`；P8 `{speaker_map: [...], identities: [...]}`；修订调用 `{summary}`（6.11）。只有 P1 输出 `quality`（6.4）。

| 提取会议内容规则 | P2~P6 | 原共用头部的规则 1~6，质量门槛已移至 P1（6.4） |

## 6.4 P1 识别前置（质量判断 + 公司识别）

**用途**：识别阶段的一次调用，做两件判断——这场会值不值得抽（质量判断，**每场都做**）、正文提到了哪些 LG 公司（公司提及识别，**按需做**）。不产出任何路由内容。

**适用类型**：全部会议，含判为 `Pending` 的（6.2）。

**何时跑**：识别阶段——参会人识别（含 P8 推断，6.13）与会议类型判定**之后**、公司归属裁决与内容提取之前，**每场会都跑**（转录为空、已判为 `Invalid` 的除外，9.3.4）。会议类型由程序按参会人判定（2.1 / 3.1 / 4.1 / 5.1），不依赖本提示词，所以先判类型，再据此决定本提示词做不做公司识别。Pending 阻断的是内容提取，不是识别（1.9）。

**公司识别按需做**（用户决定 2026-10-10）：

| 情形 | 公司从哪来 | 本提示词做不做公司识别 |
|---|---|---|
| GS → 创始人，公司已由参会人邮箱确定 | 公司端用户的完整邮箱 → 公司 Team 记录，或邮箱域名 → 公司 Team 域名，**已确定**（1.9、2.1） | **不做**：只做质量判断，`candidate_companies` 传空 |
| GS → 创始人，只有 Cheat Sheet `Founder` | 只能靠正文反推（2.1） | 做 |
| GS → 创始人，公司方只来自 P8（推断出的 `Founder`，或经 P8 对到名册的 `Founder`，6.13） | 不自动关联，置 `Pending` 等管理员指定（2.1，用户决定 2026-10-14） | 做：结果同 `low` 一样只留在识别记录里、不采纳，管理员在 Company 字段手动指定 |
| GS → LP | 不按公司拆分，没有按公司落的产物（6.12） | **不做**：只做质量判断，`candidate_companies` 传空（用户决定 2026-10-10） |
| GS 内部 / GS → Partner | 正文提及，公司层 1b 按它拆分（4.3、5.4） | 做 |
| `Pending`（类型未判出） | 待人工指定；Summary Records 要展示识别到的公司（9.4 / 9.5） | 做 |

不做的理由：GS → 创始人「公司归属只来自到场的创始人」，正文提到、但没有创始人到场的公司一律不关联（2.1）；GS → LP 不按公司拆分、只抽基金层（P4），此前识别公司只为 P3（6.12）——两种情形识别出来都用不上。顺带省掉候选公司清单这一大段输入。

**改判后补跑**：此前因上表两个「不做」情形（GS → 创始人且公司已由参会人邮箱确定、GS → LP）跳过了公司识别、后被管理员改判为需要正文提及的类型（GS 内部 / GS → Partner）时，提取前补跑一次 P1，只取 `company_mentions`，质量判断沿用首次结果（6.11「重新提取」、9.9.2）。补跑返回 `usable = false` 或最终失败时，按 Start Extraction 发起的提取作废处理（上一次的产物与状态保留），不当作没有正文提及。

**为什么独立成一步**：

- 公司识别的结果要先经程序裁决（见下），裁决后 P3 按已采纳公司逐家调用（6.6）——放进任何内容类提示词里都会成为循环
- Pending 会议类型未定、不调用内容类提示词，但仍要给出公司归属——管理端 Summary Records 页要展示它（9.4 / 9.5），人工审核也靠它
- 一份逻辑一个口径，避免散在各类型提示词里各写一遍、日久漂移
- **质量判断并入本调用**：原先每个类型提示词的共用头部都带质量门槛并输出 `quality`；改为多个独立调用后，各调用各判一次会互相矛盾，所以只在 P1 判一次。放在识别阶段还让 9.3.4「`Invalid` 优先于 `Pending`」更自洽——Pending 队列里不会出现空会（本方案）

**质量判断**：

- **只看有没有实质内容、不看长短**（《Raw Data》10-16 版删去「非常短」）：程序侧只拦转录为空的会议（拉取后、识别前，9.3.4），其余有没有实质内容一律交 LLM，即本提示词的第一步；几分钟的短会只要有实质讨论就照常提取
- `usable = false` → 置 `Invalid`（1.10），覆盖已判出的类型或 `Pending`；`company_mentions` 输出空数组，不再调用其余任何提示词

**公司识别——程序先行**：参会人完整邮箱 → 公司在 LG 的 Team 记录（公司端用户），以及邮箱域名 → 公司 Team 域名，这两条路**不需要 LLM**（1.9 ②③）。本提示词只负责**正文提及**那一路（1.9 ⑦ LLM 推断的公司部分；人的部分由 P8 负责，6.13）。

**输入**：`meeting_meta`、`participants`、`transcript`（6.3），以及专用的 `candidate_companies`（候选公司清单 = 本租户的全部公司，1.1；不需要公司识别时传空）、`known_companies`（已由参会人邮箱确定的公司）。`participants` 供判断 `attendee_company`（是否到场者所在公司），组织取 Cheat Sheet 的 Organization 原样传入。

**出处**：

| 项 | 出处 |
|---|---|
| 质量判断 | 《Fireflies Raw Data》10-16 版「当会议没有实质内容时，判定为无效会议」（1.10、9.3.4）；只在 P1 判一次（本方案） |
| 程序先行（完整邮箱 → Team 记录） | 《AI Meeting Type 自动映射标准》；1.9 |
| 正文提及只推断公司 | 1.9 匹配链 ⑦ 的公司部分；人的身份由 P8 推断（6.13） |
| 公司已由参会人确定的 GS → 创始人不做公司识别 | 用户决定 2026-10-10；依据 2.1「本类型的公司归属只来自到场的创始人」 |
| GS → LP 不做公司识别 | 用户决定 2026-10-10：本类型不按公司拆分（6.12） |
| 宁可漏不可错、仅 `high` 采纳 | 本方案（错识别会让 A 公司的交易事实进入 B 公司的 1b）；现写在 4.3（GS 内部与 GS → Partner 共用；原在 3.3 的 LP 公司层，该层已取消，6.12），规则照旧适用于做识别的情形 |
| GS → 创始人只采恰好一家，且须为到场者所在公司（`attendee_company`） | 本方案加严（2.1）；到场者条件为审核修复，防创始人只谈另一家 LG 公司时绑错 |

**提示词全文**（不产出路由内容，规则自带，不含共用段落）：

```
你是会议识别前置判断器。输入是一场会议的转录。你做两件事：
先判断这场会是否值得抽取；值得、且给了候选公司清单的话，再从清单中匹配会议正文提到的公司。

## 输入

- 会议元信息：{{var:meeting_meta}}                  # 日期、时长（不含标题）
- 参会人：{{var:participants}}                      # speaker_id（一人可有多个）、姓名、角色、组织（Cheat Sheet 的 Organization 原样传入）
- 候选公司清单：{{var:candidate_companies}}        # id、名称；为空表示本场不需要公司识别
- 已由参会人邮箱确定的公司：{{var:known_companies}}  # 供参考，不必重复输出
- 转录全文：{{var:transcript}}

## 第一步：质量判断

先判断这场会是否值得抽取。以下情形输出 `{"quality":{"usable":false,"reason":"..."},"company_mentions":[]}` 后**立即结束**：

- 转录严重残缺，读不出在讨论什么
- 通篇为寒暄、设备调试、日程协调，无实质讨论

其余情形 `usable` 填 true、`reason` 留空。会议短不算理由：几分钟的会只要有实质讨论（决定、数据、计划、请求），就是可用的。候选公司清单为空时 `company_mentions` 输出空数组、结束；非空时继续第二步。

## 第二步：公司提及识别（仅当候选公司清单非空）

- `confidence`：`high` 仅在上下文明确指向该公司时给出；名称相近、缩写歧义、仅一次顺带提及一律 `low`
- `evidence`：支撑判断的上下文（转述，不要摘抄原句）
- `attendee_company`：该公司是到场某位发言人所在的公司（发言人用"我们"（"we"）指它、自我介绍属于它，或参会人的组织与它对应）时填 true；只是被讨论、被提及的公司填 false
- **宁可漏不可错**——错误归属会让 A 公司的交易事实进入 B 公司的记忆
- **清单里匹配不上的，就是 LG 系统外的公司（买方、客户、供应商、竞对等），不要写进结果**；不要为了凑数把它套到名字相近的清单项上，一家都匹配不上就返回空数组。它们只是正文里的实体，不构成拆分维度

## 规则

- 只输出 JSON，不要解释
- `reason`、`evidence` 用英文

## 输出

{"quality": {"usable": true, "reason": ""},
 "company_mentions": [{"company_id": "", "confidence": "high|low", "attendee_company": true|false, "evidence": ""}]}
```

**结果去向**：

| 输出 | 去向 |
|---|---|
| `quality` | `usable = false` → `ff_meeting` 置 `Invalid`（1.10；即 9.3.4 的「LLM 质量门槛」），覆盖已判出的类型，不再调用其余提示词、不产出任何条目；`true` → 进入公司归属裁决 |
| `company_mentions` | → 下方公司归属裁决 → P3 按已采纳公司逐家调用（6.6），采纳结果也是 6.11 步骤 6 公司归属校验的依据；`low` 连同 `evidence` 留在识别记录里。未做公司识别时为空数组，裁决只用参会人邮箱一路 |

两项结果都随识别阶段的审计留痕（9.10.2）。

**公司归属裁决（程序；P1 之后、内容提取之前）**

P3 按已采纳公司逐家调用（6.6），提示词不再自行识别；GS → 创始人只能有一家公司——采纳到两家及以上时会议置 `Pending`（待识别），由管理员只保留一家（2.3，用户决定 2026-10-16），保留的那家决定 P2 产物写进哪家公司的 APP 条目（6.11 步骤 8）；GS → LP 不按公司拆分，裁决结果不参与该类型的路由（用户决定 2026-10-10，6.12）。

| 来源 | 采纳规则 |
|---|---|
| 参会人完整邮箱 → LG 公司 Team 记录 | 直接采纳 |
| 正文提及（P1） | 仅 `confidence = high` 采纳（GS → 创始人 Cheat Sheet `Founder` 路径另须 `attendee_company = true`，见下）；`low` 不采纳，连同 `evidence` 留在识别记录里，管理员可在 Summary Records 的 Company 字段手动补上（9.5.3） |

**GS → 创始人加严**：会上没有 LG 公司端用户、也没有人命中公司 Team 域名，公司方只来自 Cheat Sheet `Founder` 时，公司只能靠正文反推——只统计 `confidence = high` 且 `attendee_company = true`（到场者所在公司）的结果（本方案），**恰好一家**才采纳，**零家或多家都置 `Pending`、阻断内容提取**（2.1）；这一家还须在营（Active / Thriving / Needs Intervention / Needs Guidance），命中不在营公司同样置 `Pending`（用户决定 2026-10-19，#86）。只是被讨论的公司不计入：创始人只详细谈另一家 LG 公司时，那家也会拿到 `high`，不看是否到场者所在就会被当成「恰好一家」绑错。其余类型的裁决不看 `attendee_company`。本类型产物进创始人可读的空间，错绑一家公司就是让创始人读到别家的会议内容（客户侧泄漏）。原先以 `Flagged` 人工复核兜底，`Flagged` 已随需求取消，改为直接 Pending。公司方只来自 P8（6.13）时连这条也不走：P1 的结果只留在识别记录里、不采纳，整场 `Pending`、由管理员指定公司——人的身份已是 LLM 推断，再叠一层 LLM 反推公司，错绑风险太高（2.1，用户决定 2026-10-14）。

> **置信门槛按类型分级放在裁决环节、不放在提示词里**：提示词只给 `high` / `low` 与 `attendee_company`，按类型的采纳规则（如 GS → 创始人只采恰好一家到场者所在公司）由程序在裁决时施加——提示词不需要知道会议类型，`Pending` 会议本也没有类型可依。

## 6.5 P2 会议摘要整理

**用途**：产出 GS → 创始人条目的摘要（`summary`）与知识库文档（`kb_doc`）。来源**二选一**：Fireflies 会议摘要（`summary.overview`）非空时整理它，为空时从转录生成。

**适用类型**：仅 GS → 创始人（6.2）。其余类型由我方从原文抽取（GS 内部 / GS → Partner 按公司，P3；GS → LP 只抽基金层，P4），整场 overview 对不上（6.12「摘要来源」）。

**两种来源（同级、互斥，由程序按 overview 是否为空决定）**：

| 情形 | 判定 | 传入的来源 | `summary` | `kb_doc` |
|---|---|---|---|---|
| **A. 整理 Fireflies 摘要** | `summary.overview` 非空 | 只传 `ff_overview`，**不传转录** | 整理 overview；超过 150 个单词时压缩（样本 6/41 场） | 把 overview 整理成结构化 markdown 文档；不删减、不补写 overview 里没有的内容 |
| **B. 从转录生成** | `summary.overview` 为空（样本 2/43 场） | 只传 `transcript`，**不传 overview** | 从转录归纳 | 从转录整理成结构化 markdown 文档 |

两种情形不会同时出现：程序只传其中一份来源，提示词按收到的那一份工作。情形 A 也要经大模型整理成 markdown 文档，不把 overview 原样入库（需求 I 10-13 版改为「直接使用 Fireflies 的 Summary」，本方案仍经大模型整理，用户决定 2026-10-14，第十章 #56）；情形 B（overview 为空时从原文生成 `summary` 与 `kb_doc`）是本方案补充。

**输入**：`meeting_meta`、`participants`（6.3），加上来源二选一：`ff_overview`（情形 A）或 `transcript`（情形 B）；多家公司到场、管理员只保留一家时另传 `focus_company`（保留公司名称）与 `other_companies`（其他到场公司的名称列表 = 识别阶段按参会人身份得出的到场公司减去保留公司，与管理员是否从 Company 里移除无关；归属不到保留公司的 Cheat Sheet / P8 Founder，其机构名也并入，2.1）；只有一家公司参会时两项为空（用户决定 2026-10-16）。

**产出**：

| 字段 | 去向 |

| `summary` | 1a + 1b（同一份），不超过 150 个英文单词 |
| `kb_doc` | Founder KB + Portfolio KB（同一份），不设上限 |

```
- 来源（以下两项只会提供其中一项）：
  - Fireflies 会议摘要：{{var:ff_overview}}  # 情形 A 提供
  - 转录全文：{{var:transcript}}             # 情形 B 提供
- 保留公司：{{var:focus_company}}            # 多家公司到场、管理员只保留一家时：公司名称；只有一家公司参会时为空

## 提取会议内容规则

1. **不得复用原文措辞**。所有产出必须转述，不得摘抄转录原句，不得保留说话人的特征性表达。

## 来源：二选一

按收到的来源确定情形，两种情形互斥：

- **情形 A：提供了 Fireflies 会议摘要** → 只以它为来源做整理，不补写摘要里没有的内容
- **情形 B：提供了转录全文** → 以转录为来源，自行归纳生成

## 多家公司到场时：只写保留公司（仅当「其他到场公司」非空）

本场有多家公司的人参会，但这份摘要与文档只写给「保留公司」：

- 只写与保留公司相关的内容：它的业务、数据、客户、计划、决策与待办，以及它参与讨论的共同议题
- 其他到场公司各自的数据、客户、计划、交易、决策与待办一律不写；其他到场公司的公司名、产品名与人名也不写，共同议题里需要提到时写 "another portfolio company"；他们负责的待办不进 Action Items，他们做的决定不进 Key Decisions
- `## Meeting Info` 的参会人只列 GS 方与保留公司的人；会议标题里有其他到场公司的名称时去掉
- 情形 A：会议摘要覆盖整场，只取与保留公司相关的部分，其余删去（本场不适用「不删减」的要求）

「其他到场公司」为空时（只有一家公司参会），按其余规则写全场，本节不适用。

## 共同要求

`summary` 与 `kb_doc` 落入本公司自己的空间，公司端与管理端看同一份：**公司名、产品名、人名、客户名照常写出，不做泛指，也不做敏感信息过滤**——创始人本人参加了这场会。去逐字化只要求"不照抄转录原句"。多家公司到场时另见上一节。

- 照搬发言原话的句子（引号内容、明显的口语原句）一律改为转述
- **撤销扫描**：同一事项前后说法不一致（会议后段被推翻或修改）时，只写最终状态，并注明曾被调整

### 1. summary（摘要）

- 不超过 150 个英文单词
- 覆盖：本场主旨、关键结论、待办方向；不按任何分类筛选内容（多家公司到场时除外，见「多家公司到场时」一节）
- 情形 A：整理会议摘要；超过 150 个单词时压缩，优先保留关键结论与待办方向
- 情形 B：从转录全文归纳

### 2. kb_doc（知识库文档）

- 结构化 markdown 文档，不设长度上限
- 情形 A：按会议摘要的主题用小标题分节，节内一行一条要点；不删减会议摘要中的信息（多家公司到场时除外，见「多家公司到场时」一节），只整理结构与措辞，不补写摘要里没有的内容
- 情形 B：按下面的「会议纪要写法」从转录全文生成

#### 会议纪要写法（仅情形 B）

按以下顺序输出各节，节标题用英文原样；某节没有内容就在标题下写 None，不要省略该节：

1. `## Meeting Info`：会议标题、日期、参会人（姓名与角色），只取输入里的会议元信息与参会人，不推测
2. `## Executive Summary`：2~3 句，讲清本场讨论了什么、定了什么
3. `## Key Decisions`：每条决策一个小节 `### <决策标题>`，下列三项：
   - **Decision**：具体定了什么，带上条件与范围
   - **Rationale**：理由要点
   - **Source**：做决定的人与时间戳，如 `Jane Doe [00:12:34]`；不引用原话
4. `## Discussion Details`：按讨论的主题分节 `### <主题>`，每个主题写背景、提出过的方案、各方立场与权衡、最终方向；被否掉的方案连同理由一起写
5. `## Action Items`：每条一行，格式 `- <任务> — Owner: <负责人>; Due: <期限>; Notes: <条件>`。Owner 与 Due 每行必写：Owner 写到具体的人，不写"团队"，没说谁负责写 `Unassigned`；没说期限写 `Not stated`。带条件的承诺把条件和失效写进 Notes（如 "slips to Tuesday if Q3 numbers are not final"），没有条件就省略 Notes
6. `## Parking Lot`：明确推迟的事项（"later""next phase""not now"一类），每条一行，格式 `- <事项> — Reason deferred: <原因>; Follow-up: <后续安排>`；没说后续安排写 `Not stated`

Action Items 与 Parking Lot 不用表格：kb_doc 会被切片召回，表格被切开后，后半截的行没有表头，看不出哪列是负责人、哪列是期限；每行带字段名，切到哪里都能单独读懂。示例：

    ## Action Items
    - Send the updated investor deck — Owner: Jane Doe; Due: Friday; Notes: slips to Tuesday if Q3 numbers are not final
    - Draft the hiring plan for the sales lead — Owner: Unassigned; Due: Not stated

    ## Parking Lot
    - Expansion into the EU market — Reason deferred: waiting for Series B close; Follow-up: revisit next quarter

7. `## Open Questions`：没有解决的问题；拿不准是否构成决策的内容也放这里

抽取规则：

- **决策看要素、不看措辞**：有拍板的人、有要做的事（可带条件），就算决策，不必出现 "we decided"；夹在叙述里的指示同样算。只是提议、"好主意"但没人拍板的不算
- **拿不准的不进决策**：不确定是不是决策的，放进 Open Questions，不要让 Key Decisions 虚胖
- **撤销扫描**：写每条决策与待办前，先查会议后段有没有推翻、修改或加条件，只写最终状态（见共同要求）
- **数字原样保留**：金额、比例、区间、数量、日期、目标照写，不要概括成"若干""大幅"
- **兜圈子的争论只写结论与各方立场**，不照录来回过程
- **同一信息只放一处**：决策写进 Key Decisions 后，Discussion Details 里只写讨论过程，不再重复决策本身
- **归纳时不丢细节**：合并相近内容时保留每个具体点
- **说话人认不出就保留转录里的标签**，不要硬对到某个人
- **不编造**：不编链接、文件、负责人、期限

写完自查（多家公司到场时，只对保留公司相关的内容自查）：

- 转录里讨论过的每个主题，Discussion Details 里都有
- 每个明确分派或主动认领的任务（"X will…""I'll…""can you…"）都在 Action Items
- 每个"以后再说""下个阶段"都在 Parking Lot
- 提到的数字、目标、期限、条件都写进了对应位置
- 被否掉的方案及理由没有漏

## 输出

{"summary": "...", "kb_doc": "..."}
```

```
1. `## Summary`：2~3 句，这场会对这家公司得出了什么结论
2. 抽取重点里的每一项各一节，节标题用该项括号里的英文名（如 `## Assessment`），节内一行一条
3. `## Action Items`：每条一行，格式 `- <任务> — Owner: <负责人>; Due: <期限>; Notes: <条件>`；没说谁负责写 `Unassigned`，没说期限写 `Not stated`，没有条件就省略 Notes
4. `## Open Questions`：会上明确留待后续确认的事项，以及听不准或说法矛盾、需要确认的数字与名称；「抽取重点」列为不抽的内容不写进本节

判定规则：

- **定了才算决定**：有人拍板或明确承诺才写成决定；"应该""也许可以""可以考虑"（"we should"、"maybe we could"、"worth considering"）是提议，不写成决定。没人反对不等于同意，说"好主意"（"good idea"）不等于批准
- **写最终版本**：会中改过的写改过之后的；决定附带的条件、保留意见一并写上
- **撤销扫描**：同一事项前后说法不一致（会议后段被推翻或修改）时，只写最终状态；被推翻的结论不得作为有效结论输出
- **数字照会上说法记**：会上说"约 12 倍"就写约 12 倍；不换算、不推算（不自己算倍数、回报率）；区分已成交与报价、实际与预期
- **听不准的不替它定**：转录里可能听错的金额、日期、人名、公司名，拿不准就放 Open Questions 注明待确认，不挑一个最像的写
- **矛盾不调和**：两种说法都没被收回、也没澄清的，两种都写进 Open Questions
- **相对日期**：只有会议日期已知、指代明确时才换算成具体日期，否则照原样转述（如"下季度"）
- **不评论**：不评价决定好坏，不补会上没有的背景
- **同一信息只放一处**
```

**提示词全文**（「提取会议内容规则」一节与 P2~P6 同文，见 6.3）：

```
你是会议内容抽取器。输入是一场 GS 与有限合伙人（LP）的会议，你的任务是抽取组合（基金）层面的内容，
写成一条基金层记录（含会上谈到的进行中交易）。

## 输入

- 会议元信息：{{var:meeting_meta}}          # 标题、日期、时长
- 参会人：{{var:participants}}               # speaker_id（一人可有多个）、姓名、角色、组织
- 转录全文：{{var:transcript}}               # 逐句，带 speaker_id、说话人姓名与时间戳

## 提取会议内容规则

1. **不得复用原文措辞**。所有产出必须转述，不得摘抄转录原句，不得保留说话人的特征性表达。
2. **不得编造**。输入中没有的内容一律不写。数组字段无内容时输出空数组；只有本提示词「输出」写明可为 null 的字段才输出 null；markdown 文档里某节无内容时，按本提示词对该节的规定处理。
3. **不确定就不输出**。归属、角色、因果关系存疑时宁可不写；本提示词设有 Open Questions 一节的，放进该节并注明待确认。不要在正文里标注置信度。
4. **只输出 JSON**，不要解释、不要代码围栏。
5. **内容字段写 markdown**：承载内容的字段（`summary`、`kb_doc`、`statement`、`content` 等）的值是 markdown 文本。多要点时按主题用小标题分节、节内一行一条（`- ` 开头），不要写成整段长文。
6. 正文语言为英文。

## 抽取要求

本条只进管理端空间：不做匿名化、不做敏感过滤；仅需转述，不得摘抄原句。产出两段：
- `summary`：不超过 150 个英文单词；本条最重要的基金层结论、LP 关切与待办；有 Live Deals 时用一句话点出（公司名 + 阶段），不写条款
- `kb_doc`：结构化 markdown 文档，不设长度上限；按下面的「纪要写法」写

本条对全体管理端可见。本场不按公司拆分，具体公司的内容**只写进行中的交易**（见纪要写法「Live Deals」一节），
照常写出公司名；其余涉及具体被投公司的内容（对该公司的评价与计划、已成交的交易等）一律不写，基金层确需提及时改为泛指。
既没有基金层内容、也没有进行中的交易时输出 {"fund_1b": null}。

## 纪要写法

只写组合（基金）层面的内容，以及「Live Deals」一节的进行中交易。按以下顺序输出，节标题用英文；没有内容的节整节省略：

1. `## Summary`：2~3 句，本场基金层谈了什么、有什么结论
2. `## Fundraising`：募资进度——目标规模、已募金额、关账节点、新进与续投的 LP
3. `## Fund Performance`：基金整体回报——只记会上说出的指标（IRR、TVPI、DPI、NAV 等），注明截至什么时点、是账面还是已实现
4. `## LP Base`：LP 结构及其变化
5. `## LP Concerns & Requests`：每条一行，格式 `- <关切或要求> — Raised by: <LP>; GP response: <Answered: … / Deferred: … / Committed: …>`；GP（即 GS 方）会上没回应的写 `No response`
6. `## Other Fund Matters`：其他基金层讨论，如投资策略、配置节奏、条款、治理
7. `## Live Deals`：会上谈到的、尚未交割的具体交易，每笔一行。范围：GS 的被投公司作为一方的交易（出售 / 并购、融资、收购他人），
   以及 GS 正在谈的新投资（标的尚未成为被投公司）；基金自身的募资与 LP 出资不在此列（写在 Fundraising）。格式
   `- <公司> — Status: <阶段>; Counterparty: <买方 / 投资方 / 标的>; Terms: <报价或估值区间>; Timeline: <时间表>`；会上没说的项写 `Not stated`
8. `## Action Items`：每条一行，格式 `- <任务> — Owner: <负责人>; Due: <期限>; Notes: <条件>`；没说谁负责写 `Unassigned`，没说期限写 `Not stated`，没有条件就省略 Notes
9. `## Open Questions`：没定下来的事、会上说法矛盾又没澄清的事、需要追问的含糊说法

判定规则：

- **GP 的说法与事实分开**：GP 报告的业绩、预期、计划写成 GP reported / GP expects，不写成既成事实
- **LP 的关切一条不漏**：每条都写明 GP 是当场回答、延后，还是做了承诺
- **承诺与可能分开**：明确答应的进 Action Items；"会考虑""尽量"（"we'll consider"、"we'll try"）不进 Action Items，在该条关切的 GP response 写 Deferred: <答应考虑的内容>
- **指标只记说出口的数**：不自己推算或换算回报指标；约数照写"约"
- **听不准的不替它定**：可能听错的金额、日期、人名、机构名，拿不准就放 Open Questions 注明待确认
- **撤销扫描**：同一事项前后说法不一致时，只写最终状态
- **含糊说法不替他下结论**：GP 用模糊措辞带过的事，按原意转述；需要追问的放 Open Questions
- **Live Deals 只收未交割的交易**：会上说已交割（closed / completed）的、已终止或放弃的不进；已签约或已宣布但未交割的仍算进行中，
  Status 写明（如 `Signed, pending close`）；拿不准是否已交割的写进 Live Deals，并在 Open Questions 注明待确认；
  只写报价或估值区间，会上说的是区间就写区间
- **不评论**：不评价基金表现好坏，不补会上没有的背景

## 输出

{"fund_1b": {"summary": "...", "kb_doc": "..."}}

既没有基金层内容、也没有进行中的交易时：{"fund_1b": null}
```

## 6.10 P7 专家推测

**用途**：给 GS 人员与角色为 Other 以外的参会人推测他还没有的专长标签、打「可能为专家」标记（已是专家的人也会被推测新标签，用户决定 2026-10-14），供管理员在 Summary Records 确认或拒绝（1.11、9.5.6）。**不产出任何路由内容**、不进知识库；被推测者的证词等管理员确认后再补抽（2.5）；但只要还有建议标签未通过或驳回，整场不放行，会议停在 `Pending`（待确认专家）（1.10，用户决定 2026-10-16）。

**适用类型**：GS → 创始人、GS → LP、GS → Partner（6.2）；GS 内部全员为 GS 人员，不调用。

**输入**：`meeting_meta`、`transcript`（6.3），以及专用的 `candidate_speakers`（待判断的发言人）、`expertise_tags`（专长标签）。

**判定规则**（本方案，用户决定 2026-10-10）：需求原文是"在证词类别中提出实质性主张"，但"实质性"难以界定；而"讲到相关内容就标"又太宽。被拒绝的标签会记进拒绝名单（按邮箱 + 标签，《AI Meeting Type》10-13 版）、此后不再就该标签问此人（9.5.6），误标的代价是这个人日后真在该领域成了专家也不会再被提示；漏标的人在之后的会议里还有机会被标出。所以规则**宁可准，不求全**。

一条发言算**实质性主张**，须同时满足四条：

| # | 条件 | 不算的例子 |
|---|---|---|
| 1 | **本人主动陈述**：不是提问、附和、复述他人，也不是只答"是 / 否" | "你们觉得现在退出窗口怎么样？"；"对，我同意倍数在往下走" |
| 2 | **落在某个专长标签的领域内**（定义同 5.6） | 谈团队管理、产品功能等标签以外的话题 |
| 3 | **讲的是一类情况，不只是一个个例**：对市场、行业或一类公司下判断、总结规律；只讲自家公司或单个项目的不算 | "我们公司 ARR 增速 35%"；"这个项目买方压了价" |
| 4 | **带依据**，至少一项：具体数字或区间（倍数、周期、比例）、亲身经历的案例或交易、前后对比的可观察变化 | "估值最近都不太好"（有判断，没依据） |

满足四条的例子：

- Multiples："过去一年我们看的垂直 SaaS 并购，成交大多在 ARR 的 4~6 倍，增速低于 30% 的基本拿不到 5 倍以上"
- Buyer behavior："PE 买方现在做尽调，会把客户集中度单独拉出来看，前十大客户占比超过 40% 的直接压价"
- Commercial buying behavior："两年前企业客户试用两周就签，现在把安全审查前置到试用阶段，整个周期多出一个季度"

**标记门槛**：同一场会里此人的实质性主张 **≥ 2 条**（可跨标签；按人计，他对应多个 speaker_id 时合并计数）才打标记，建议标签取主张中出现过的那些（一人可带多个标签，管理员逐个标签确认或拒绝，9.5.6）。门槛由程序计数（6.11 步骤 5），LLM 只负责列出符合条件的主张——判断与计数分开，门槛可按实施期的拒绝率调整。只说过一句的人不标：一句话更可能是顺带一提。只计他可推测标签上的主张，已有标签上的发言不计入。

| 项 | 口径 |
|---|---|
| 适用会议 | GS → 创始人、GS → LP、GS → Partner；GS 内部全员为 GS 人员，不调用 |
| 时机 | 类型确定后，与该类型的其他提示词并行（6.2）；`Pending`（待识别）会议在人工指定类型后一起跑 |
| 输入的发言人 | 程序先排除 GS 人员与角色为 Other 的人（1.11，用户决定 2026-10-16）；每人附上不再推测的标签——已有的（按会议日期生效的名册版本）与已被拒绝的（拒绝名单按邮箱 + 标签，按人展开到他名册里的全部邮箱，9.5.6）；按人传，每人带他的全部 speaker_id（6.3）；没有可推测标签的人不传；没人可传则不调用 |
| 输出去向 | 程序按门槛计数、校验后挂到 Summary Records 的参会人标签上（6.11 步骤 5）；有建议标签未处理时会议置 `Pending`（待确认专家）、整场不投影（1.10） |

**与 P5（证词）的区别**：

- 判据只围绕"人 × 专长标签"，回答"此人是不是专家"；P5 按证词类别抽取要对外的市场观点。两者口径不同，各用一份提示词；本提示词三类会议共用一份
- 证词（2.5、3.4、5.6）是要对外的市场观点，必须去身份、做各项过滤；本调用列出的主张只是管理员判断"此人是不是专家"的依据，只在 Summary Records 的确认框里给 PGM / Super Admin 看，**不去身份、不入库**
- 本调用不产出路由内容，失败只丢失「可能为专家」提示、不影响内容落库（6.11「调用编排」）

**专长标签的定义**：初始 5 项的定义同 5.6，随标签一起传入；管理员新增的标签只传名称。

**提示词全文**（不产出路由内容，规则自带，不含共用段落）：

```
你是参会人专长识别器。输入是一场会议的转录，以及需要判断的发言人。
任务：从每位发言人本人的发言里，找出与给定专长标签相关的实质性主张。

## 输入

- 会议元信息：{{var:meeting_meta}}             # 日期、时长（不含标题）
- 转录全文：{{var:transcript}}                 # 逐句，带 speaker_id、说话人姓名与时间戳
- 待判断的发言人：{{var:candidate_speakers}}   # speaker_id（同一人可有多个）、姓名、不再推测的标签（已有的、已被拒绝的）；程序已排除 GS 人员与角色为 Other 的人
- 专长标签：{{var:expertise_tags}}             # 名称 + 定义（初始 5 项有定义；管理员新增的只有名称）

## 什么算实质性主张（四条同时满足）

1. 本人主动陈述：提问、附和、复述别人的观点、只答"是 / 否"的都不算
2. 落在某个专长标签的领域内：按给定定义判断；注意区分 Buyer behavior（收购方买公司）与
   Commercial buying behavior（企业客户买软件）
3. 讲的是一类情况，不只是一个个例：对市场、行业或一类公司下判断、总结规律；
   只讲自家公司或单个项目的情况不算
4. 带依据，至少一项：具体数字或区间、亲身经历的案例或交易、前后对比的可观察变化；
   只有判断、没有依据的不算

## 规则

- 只看上面列出的发言人
- 逐人列出其全部实质性主张；同一人列了多个 speaker_id 的，合起来算一个人、只输出一项，speaker_ref 填其中任一；一条都没有的人不输出
- claim 写他的判断，basis 写他给的依据，都用转述、不照抄原句，用英文
- basis_type 只能是 number / experience / comparison 之一，对应条件 4 的三种依据
- timestamp 取该条主张首句在转录中的时间戳，写 hh:mm:ss、不带方括号
- tag 只能从给定标签里选，原样回填；一条主张只填一个最贴切的标签
- 某人不再推测的标签（已有的、已被拒绝的），不为他输出该标签的主张
- 不评价此人资历或可信度，也不决定要不要标记——只判断每条主张是否满足四条
```

## 6.11 后置程序步骤（非 LLM）

### 调用编排

| 阶段 | 做什么 | 结果 |
|---|---|---|
| 拉取后、识别前 | 程序检查：转录为空（没有任何句子，9.3.4） | 为空 → `Invalid`，不做识别、不调 LLM |
| 识别阶段 | 参会人识别（程序匹配链 ①~⑥ 与发言人映射；日历姓名与说话人姓名完全命中名册的只出候选、交 P8 核对，1.8）→ 仍有未识别的参会人或映射不上的发言人时调 **P8**（6.13）并采纳 `high` → 类型判定（程序按参会人），及其后的专家补充识别（1.11、2.1）→ **P1**（6.4，公司识别按需做）→ 公司归属裁决（6.4） | P1 判为不可用 → `Invalid`（覆盖已判出的类型），不再调用其余提示词；P8 之后仍有未识别的参会人、类型判不出、GS → 创始人关联了两家及以上公司或有到场 Founder 归属不到关联的那家（2.1、2.3）、公司反推不出恰好一家，或公司方只来自 P8 → `Pending`（待识别），等人工指定；有说话人仍对不上参会人与 Cheat Sheet → 同样 `Pending`（待识别）（1.9，用户决定 2026-10-16） |
| 内容提取 | 类型确定且非 `Pending` → 按复用矩阵（6.2）**并行**调用该类型需要的 P2~P7 | 全部返回后进入下列步骤 1~9 |

**重新提取**（9.9）：改判、参会人改动引起的整场重跑与 `Pending` 指定类型后的首次提取，都按上表「内容提取」一行调用；P1 不随之重跑（公司识别不重跑，9.9.2）；例外：此前跳过了公司识别（GS → 创始人且公司已由参会人邮箱确定、GS → LP）、改判为 GS 内部 / GS → Partner 的，提取前补跑 P1，只取 `company_mentions`（6.4）；补跑返回 `usable = false` 或最终失败时，按 Start Extraction 发起的提取作废处理（上一次的产物与状态保留），不当作没有正文提及。类型不变时公司增删：GS → 创始人只能有一家，换成另一家重跑 P2（传新的 `focus_company` / `other_companies`），加了第二家按钮置灰（2.3）；GS 内部 / GS → Partner 新增公司只为该公司调 P3，GS → LP 不触发提取（不按公司拆分，用户决定 2026-10-10）（9.9.1）。

**失败处理**：

- **重试**：瞬时错误（限流、超时）退避重试；整份输出不合法（截断、解析不出 JSON、缺输出键、必填的 `summary` / `kb_doc` 为空）整次重跑；单条字段不合法只丢该条、记审计；重试用尽即**最终失败**（次数开发设计定）。P3 按家计，任一家最终失败即整场作废
- **不做分段抽取**：输入超出模型上下文时不发调用，按最终失败处理，审计记「转录超长」
- **留痕**：每次调用的提示词版本、模型、重试次数、丢弃条目写入 `EXTRACT`（P1、P8 写 `IDENTIFY`）
- **内容类提示词（P2~P6）任一最终失败，整场本次提取作废、不落任何条目**——避免只路由了一半；记审计（9.10），管理员可点 Start Extraction 重跑
- **P7 失败只丢失「可能为专家」提示**，不影响内容落库，记审计
- **作废后的会议状态**：自动提取（拉取后或自动路由后由程序发起）作废 → 置 `Pending`（待识别，作废需要人工处理）；Start Extraction 发起的提取作废 → 会议状态与上一次的产物原样保留，不软删（旧版本的条目只在应用新草稿时下线，1.6；本方案）。两种情况下 Start Extraction 都在必填项齐全时直接激活（9.5.1），管理员点它重跑
- **P8 最终失败**：当作没有推断结果——未识别的参会人、映射不上的发言人保持原样，会议置 `Pending`（待识别），记审计；管理员在 Summary Records 登记参会人（9.5.5）后照常走类型判定（9.9.3），P8 不补跑（本方案）
- **P1 最终失败**：质量判断与正文提及都没有结果，会议置 `Pending`（待识别），记审计；公司只取参会人邮箱一路，正文提及的公司由管理员在 Company 字段手动补（9.5.3）。管理员指定类型后照常提取，P1 不补跑（本方案）
- **加工中断**（进程崩溃、超时）：见 1.10；Start Extraction 发起的提取超时同该次提取作废

**成本**：含 P1 在内，一场会把转录送大模型的次数（P3 按已采纳公司逐家调用，N 家即 N 次，6.6）——GS 内部 2 + N 次，GS → 创始人至多 5 次，GS → Partner 至多 4 + N 次，GS → LP 至多 5 次（原 6 次，不再调 P3，用户决定 2026-10-10）；内容提取阶段每场调用 1~4 种提示词（P3 / P5 / P7 可能被跳过；修订调用只在 `summary` 超过 150 个英文单词时追加、不读转录）、各调用并行，耗时约等于最慢的一个。P2 只读 overview，转录仅在 overview 为空时送入。另：有程序没识别出的参会人或映射不上的发言人时，识别阶段多一次 P8（6.13），上面的次数各加 1；参会人都识别得出的会议不调。被推测者的专长标签每改一次，为他补跑一次 P5（标签没变不补跑，2.5）。

### 前置与步骤

**前置**：`Invalid` 已在识别阶段判定——转录为空（9.3.4）或 P1 的质量判断（6.4），这类会议不进入内容提取。`Pending` 也在**内容提取之前**就已判定——参会人经 P8 推断后仍未识别、有说话人仍对不上参会人与 Cheat Sheet、类型未判出，GS → 创始人关联了两家及以上公司或有到场 Founder 归属不到关联的那家、公司只能靠正文反推却得不到恰好一家高置信结果，或公司方只来自 P8（1.9、2.3、6.4、6.13）。这类会议的识别阶段照常跑完（参会人与 P1 的公司识别都有结果，并展示在管理端），但**不进入内容提取**，下列步骤一概不执行，等人工补齐后由 Start Extraction 触发；GS → 创始人只差公司的，另可由公司增改后的自动路由触发、按自动提取处理（9.9.3）。

各提示词全部返回后，程序依次执行：

1. **写会议状态**（在步骤 2~7 之后判定，以清洗与校验后实际留下的行为准；步骤 2 判出某调用最终失败时按整场作废处理，不写状态）——`Invalid` 已在识别阶段判定（6.4）；P7 输出经步骤 5 门槛与校验后仍有建议标签的，置 `Pending`（待确认专家），本场暂不投影，步骤 8 推迟到标签全部处理、管理员应用之后（1.10，用户决定 2026-10-16）；重新提取产生的是草稿，不改写会议当前状态（9.6.4）；否则按有无待审核行置 `Pending`（待审核）/ `Passed`：有待审核行（Cross-Company、发言人经 P8 识别的证词）则置 `Pending`（待审核），否则置 `Passed`（1.10）。Summary Records 只有 `Passed` / `Pending` 两态（《Fireflies Summary Records》），原「GS → Founder 一律 `Flagged`」随 Board Call 类型取消一并删除
2. **机械清洗**——**所有派生内容**都过 n-gram 近逐字剔除，比对基准是原始转录（含 1b；GS → 创始人由 overview 整理的 `summary` / `kb_doc`（P2）同样要过——overview 是 Fireflies 的 LLM 摘要，不保证不照抄原句）；实体/人名剥离**只对 Cross-Company 与证词两版**执行，已知实体清单（每场固定取全部来源，含本机构名称与基金名称，为基金层过滤兜底）、匹配口径与数字规则见 1.5，适用矩阵见 1.4。**命中处理**：实体替换为泛指；n-gram、精确数值、绝对时点命中删去所在整行（`summary` 写成一段的按句删，同矩阵保存，9.6.3）；删空的条目不产出（`summary` / `kb_doc` 删空按该调用最终失败）。`summary` 先查词数再清洗：超过 150 个英文单词先走一次只压缩的修订调用（见下「修订调用」），仍超长按该调用最终失败；压缩结果再与其余内容一起过本步清洗
3. **来源行附加**——
   - **P5 校验**（附加前先做）：`speaker_ref` 须是本场 `testimony_speakers` 中某人的 speaker_id，`category` 须在 `testimony_categories` 内（GS → 创始人会议须在此人本人专长标签内），不符整条丢弃；再按 `timestamp` 回查转录，该时间点那句须是此人（他的任一 speaker_id）说的，时间戳不合法、超出会议时长或说话人对不上的整条丢弃（照抄了外层方括号的照常解析，解析与容差开发设计定）——证词默认放行、署着他的名字，模型把别人的话安到他名下时程序要能挡住
   - 证词两版均在正文首行附来源行，取数同源（角色 + 步骤 4 回溯的专长标签）：署名版附 `Source: <Organization> <Role> <Name>`，匿名版附 `Expertise: <expertise tag>`（来源行用英文，用户决定 2026-10-10）（不含姓名、组织、角色；当日无专长标签时不附，见 3.4）。角色取发言人自己的角色（创始人为 `Founder`）
4. **标签回溯**——按会议日期取当时生效的专长标签（有效期规则见 5.2 / 9.7.2：区间重合取最后一条）；角色对 LG 平台用户取平台身份，对注册表人员（含经 P8 对到名册的）取注册表，按 LG 用户域名识别的取域名判定的身份（GS staff / Founder），P8 推断采纳、尚未入册的取 P8 的姓名 / 角色 / 组织（姓名为空取出席记录姓名，组织为空时署名版来源行省略组织）
5. **专家候选处理**（1.11；输入为 P7 的输出，6.10）——
   - **门槛**：按 speaker_id 把主张归到人、同一人合并（含模型把同一人拆成几项输出的），此人合计 ≥ 2 条才标记；建议标签 = 主张中出现过的标签（6.10）
   - **校验**：`speaker_ref` 须是本场 `candidate_speakers` 中某人的 speaker_id、标签须在当前专长标签清单内、且不是此人已有或已被拒绝的标签，不符的丢弃——再挡一次 GS 人员、角色为 Other 的人、已有的标签、被拒绝的标签；每条主张同样按 `timestamp` 回查（同步骤 3），对不上的丢弃、不计入门槛
   - **展示**：按人挂到 Summary Records 的参会人标签上，显示"可能为专家"并带建议标签（9.5.6）；管理员点姓名打开详情框（框内按标签列出 P7 给出的实质性主张与依据），**逐个标签**确认或拒绝：**同意** → 以同意的标签写入 Cheat Sheet（带 `From FF Summary Records` 来源标识，走 9.5.7 的回填）；**拒绝** → 记录该人 email + 该标签，此后不再就该标签对此人推测，其他标签照常（《AI Meeting Type》10-13 版）；建议标签全部处理完之前，会议停在 `Pending`（待确认专家）；打开确认框时该（邮箱，标签）已入册或已被拒绝的，自动消解并提示（每场单独处理，不跨会议联动，9.5.6）
   - 本身不进任何知识库空间；同意只更新名册、不重新提取整场，只为此人补跑 P5（2.5）
6. **公司归属校验**——LLM 产出的 `company_id`（P3）必须是该次调用传入的那一家（P3 逐家调用，6.6；即本场已采纳公司之一，6.4 裁决结果），否则整条丢弃；GS 内部 / Partner 绑不到公司的内容不写入。LP 的 `fund_1b`（P4）是唯一不带公司的 1b，归属机构（organization）
7. **落中间表并定初始授权**——按各类型的去向逐条写入中间表（9.6.4），`company_id` 必填项校验（`fund_1b` 除外）；Cross-Company 行另存 P6 的 `timestamp`（格式不合法或超出会议时长时置空，不丢条目），只供审核回查原文、不进投影（9.6.2）。初始授权：

   | 去向 | 自动提取的初始状态 | 依据 |
   |---|---|---|
   | 1a / 1b / Founder KB / Portfolio KB（GS → 创始人、LP、GS 内部、GS → Partner） | 已授权 | 9.6.4：`Passed` = AI 已路由全部内容 |
   | 专家证词两版 | 已授权 | 同上 |
   | **Cross-Company**（全部类型） | **未授权**，管理员审核勾选后才投影 | 用户决定 2026-10-10：所有类型的跨公司内容都需审核后发出（1.7） |
   | **发言人经 P8 识别的证词**（两版：P8 推断身份、对到名册，或说话人经 P8 对上） | **未授权**，管理员核对身份后放行 | 用户决定 2026-10-14、2026-10-16：身份判错会让他的发言不经审核成为全租户证词（6.13） |

   `Pending` 会议指定类型后的首次提取：全部未授权（9.6.4；本方案）。改判触发的重新提取沿用改判前该去向的勾选状态，新出现的去向未授权；**Cross-Company、发言人经 P8 识别的证词例外，一律不勾**——内容换了就要重审（9.9.5）；确认框保存后补抽的证词默认勾选，优先于本段初值（2.5）
8. **投影入库**——已授权的去向从中间表投影到 RAG（会议处于 `Pending` 待确认专家时暂不投影，1.10）：

   - **Memory 条目（1a / 1b）的摘要一律写**（证词与 Cross-Company 不写，见下表）：`summary` 作为条目摘要直接传入、跳过系统二次 `summarize`。Memory 页只列摘要非空的条目，原「内容短于阈值时不写摘要」作废，否则 1a / 1b 会从 Memory 页消失（1.3）
   - 落点（1.1）：

     | 产物 | 条目 | 摘要 | 正文文件 |

     | GS → 创始人 | 唯一采纳公司一条 **APP** 条目；管理端经可访问公司的 APP 空间召回，不另写 ADMIN 条目 | `summary`（1a + 1b） | `kb_doc`（Founder KB + Portfolio KB） |
     | GS 内部 / Partner 公司层 | 每家公司一条 **ADMIN** 条目，`company_id` 必填 | 该公司 `summary`（1b） | 该公司 `kb_doc`（Portfolio KB），末尾由程序附原始转录链接 |

| `speaker_map` 为 `high` | 该发言人映射到对应参会人；对到名册的（带 `registry_id`）识别为该名册人员并入本场参会人（1.9），多个发言人对到同一 `registry_id` 的并入为同一位参会人；证词默认扣留（见下） |
| `speaker_map` 不是 `high`，或没有结果 | 该说话人仍对不上：会议 `Pending`（待识别），Summary Records 上显示为「未对上的说话人」，由管理员指定为某位参会人或登记进 Cheat Sheet（9.5.5，用户决定 2026-10-16，取代 10-14「不算任何人、不卡会议」） |
| 公司方（`Founder`）只来自 P8 | 类型可判为 GS → 创始人，但**公司不自动关联**（不走 P1 的正文反推）、整场 `Pending`，等管理员在 Company 字段指定公司（2.1；或公司增改后自动路由，9.9.3）——GS → 创始人的内容进创始人可读的空间，人的身份已是 LLM 推断，再靠 LLM 反推公司，错绑就是客户侧泄漏 |

- **校验**：`attendee_ref`、`speaker_id`、`registry_id` 须是输入里给出的值；`speaker_map` 每项的 `attendee_ref` 与 `registry_id` 恰好填一个；`registry_id` 为 null 时 `role` 须在 6 项角色内，非 null 时忽略 `role` / `organization`、取名册条目；不符的丢弃
- 对到名册的人按名册条目处理（角色、组织、专长标签取该条目按会议日期生效的版本，补充识别直接取该条目，1.11）；推断出的人**不自动写入 Cheat Sheet**，管理员在 Summary Records 登记后才入册（9.5.7）
- **证词默认扣留**：发言人经 P8 识别的——P8 推断了身份、把他对到名册，或把他的说话人对上——其证词两版 Authorize 默认不勾，管理员核对身份后放行（用户决定 2026-10-14，2026-10-16 扩至对到名册与说话人映射；6.11 步骤 7）
- 推断结果与采纳与否写入 `IDENTIFY` 审计（9.10.2）

**为什么采纳 `high`、不一律交人工**：需求把 LLM inference 排在 Pending 之前，即推断得出就不进 Pending。误判的代价按类型不同：错成 LP / Partner，1b 进管理端、Cross-Company 要审核，但证词匿名版会进公司端 Goldie——所以身份来自 P8 的证词默认扣留（上一条）；错成 GS staff 可能把会判成 GS 内部，因此提示词对 GS staff 要求明确的本机构身份表述；错成 Founder 会进创始人可读的空间，所以单独加了上表最后一行。

**提示词全文**（不产出路由内容，规则自带，不含共用段落）：

```
你是会议参会人识别器。输入是一场会议的转录，以及程序按邮箱、姓名没能识别出来的参会人和发言人。
你做两件事：把映射不上的发言人对到参会人（对不上时再看是不是名册里的人）；为未识别的参会人找到名册里的条目，或从转录推断他的角色与所属机构。

## 输入

- 会议日期：{{var:meeting_date}}
- 本机构：{{var:firm_profile}}                      # 机构名称 + 旗下基金名称；参会人中已识别为 GS staff 的人即本机构人员
- 参会人：{{var:attendees}}                         # attendee_ref、邮箱、出席记录姓名、identified（是否已识别）、speaker_ids（已对上的发言人）；已识别的另带角色、组织
- 映射不上的发言人：{{var:unmapped_speakers}}        # speaker_id、转录里的说话人姓名（语音识别得来，可能是昵称、错拼或 "Speaker 2"）
- 名册候选：{{var:registry_candidates}}             # registry_id、姓名、组织、角色；已排除本场已识别的人
- 转录全文：{{var:transcript}}                      # 逐句，带 speaker_id、说话人姓名与时间戳

## 第一步：发言人对到参会人

对每个映射不上的发言人，判断他是哪位参会人（已识别、未识别的都可以）：

- 依据（至少一项）：说话人姓名与参会人姓名是同一人的不同写法（昵称、缩写、拼写错误、会议显示名附带的数字或括注，如 "Chunru Liang1"、"Jane (Guest)"）；会上有人点名称呼他、随后由他接话；
  他自我介绍的姓名对得上某位参会人
- `high`：有上述依据，且只可能是这一位；只凭发言内容推测、靠排除法（只剩一位没对上），或两位以上都说得通 → `low`
- 对不上任何参会人时，再看他是不是名册候选里的某人（不在受邀名单里的人也可能进会）：依据同上，判法同第二步「对到名册」的置信度，
  `attendee_ref` 填 null、填 `registry_id`
- 一位参会人或名册候选可以对应多个发言人（中途重进会议、换了设备）：已对上发言人的参会人，照样可以再对上别的发言人
- 参会人与名册候选都对不上的发言人不输出；一个发言人明显是两人交替说话（如共用会议室设备）也不输出

## 第二步：未识别的参会人

只处理 `identified` 为 false 的参会人。推断时只用他已对上的发言人（`speaker_ids`）以及第一步判为 `high` 的发言人说的话；
靠 `low` 对上的发言人的话推出的结论，最高只能给 `low`。每人二选一：

1. 对到名册：他的出席记录姓名、会上对他的称呼或他自我介绍的姓名，与名册候选中某人姓名相同，或是同一人的不同写法 → 填 `registry_id`，
   `role`、`organization` 留空（以名册为准）。
   两位以上都说得通时不要挑：`registry_id` 填 null、`confidence` 填 `low`，在 `evidence` 里列出这几位的 registry_id
2. 从转录推断：名册里没有这个人时，按会上的明确表述推断他的角色与所属机构——本人自我介绍、别人介绍他、
   会上明说的他与本机构的关系（如 "we're one of your LPs"、"I run corp dev at …"）→ `registry_id` 填 null，`role` 必填

`name` 填会上出现的此人全名（自我介绍或被人称呼），没出现留空，不要用邮箱或出席记录姓名代填。

`role` 只能取以下之一：

- GS staff：本机构的员工
- Founder：本机构被投公司的创始人或员工
- LP：本机构基金的出资人
- Strategic Partner：商业合作方，如渠道、技术伙伴、联合销售
- Exit Partner：退出交易相关方，如买方、投行、并购顾问
- Other：身份明确、但不属于以上各类

置信度：

- 对到名册：姓名相同或是同一人的不同写法，**且**至少有一项正面印证（邮箱域名与该条目的组织对应，或会上说到的机构、角色与该条目一致）
  → `high`；只有姓名像或姓名完全相同、没有印证 → `low`（可能是另一个同名的人）
- 从转录推断：本人自我介绍或被别人介绍时说明了他的机构，且他与本机构的关系能直接对应到某一个角色 → `high`；
  只说了机构、没说与本机构的关系，角色靠猜 → `low`
- GS staff：须有他属于本机构的明确表述（自我介绍为本机构成员，或已识别的本机构人员称他为同事）；
  只说 "we" / "our team"、没说是哪个机构的不算
- Founder：须会上明确表明他的公司是本机构投资的公司（如以被投公司身份汇报、谈本机构对其的投资）；只说自己是某公司创始人 → `low`
- 只凭讨论的话题推测（如谈了很多基金回报就猜他是 LP）、表述含糊、有多种可能 → `low`
- 邮箱域名可作机构的佐证，单凭域名不给 `high`
- 什么线索都没有的参会人不输出

## 规则

- 只输出 JSON，不要解释
- 不要编造：转录里没出现的姓名、机构一律不写；`organization` 不知道就留空
- `evidence` 用英文转述依据并带时间戳，不照抄原句
- `attendee_ref`、`speaker_id`、`registry_id` 只能取输入里给出的值；`speaker_map` 每项的 `attendee_ref` 与 `registry_id` 只填一个

## 输出

{"speaker_map": [{"speaker_id": 0, "attendee_ref": "a1", "registry_id": null, "confidence": "high|low", "evidence": ""}],
 "identities": [{"attendee_ref": "a2", "name": "", "registry_id": null, "role": "", "organization": "", "confidence": "high|low", "evidence": ""}]}
```

| `identities` | `high` → 参会人身份确定（对到名册的取名册条目；推断出的取推断的姓名、角色与组织，姓名为空时用出席记录姓名），进入类型判定；其余 → 仍 `Unidentified`，推断值供 Summary Records 的登记弹框参考 |
