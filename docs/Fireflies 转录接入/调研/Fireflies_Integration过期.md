# Fireflies Integration 需求文档

## 一、业务目标

将 Golden Section 的 Fireflies 会议以租户级方式全量接入 Looking Glass，经过"摄取 → 识别 → 分类 → 加工 → 路由 → 权限过滤"的闭环处理，产出五类可复用的知识资产，供 Goldie（AI 助手）在创始人端与管理端做差异化响应：

1. **1a 创始人可见记忆**：本公司专属，Goldie 面向创始人推理时的记忆源
2. **1b 管理端记忆**：GS 管理端专属，Goldie 面向 GS 侧推理时的记忆源
3. **Founder Facing KB**：创始人可浏览的公司知识库（本人出席会议的加工摘要 + 本公司上传材料）
4. **专家证词库（Expert Testimony）**：跨公司复用的匿名化外部观点
5. **跨公司知识库（Cross-Company Themes）**：租户级跨公司的匿名主题/洞察

在保证机密性（活跃交易隔离、LP/基金过滤、原文不外泄）与可审计性的前提下运行。

---

## 二、角色与权限

Looking Glass 只有以下四类角色，本文档所有权限描述统一以此为准：

| 角色 | 中文口径 | 权限概要 |
|---|---|---|
| **Portfolio Group Manager**、**Super Admin** | 租户管理员、平台超管 | Fireflies 集成配置、注册表编辑、跨租户管理、raw script；全部管理端功能；租户内 Pending Assignment 审核、路由改判与覆盖、专家证词完整署名可见 |
| **Portfolio Manager** | 管理端用户 | 本租户内跨公司知识库可查看原始转录与署名（管理端入口）；专家证词可看署名 |
| **Founder** | 创始人端 | 只可查看本人参加会议的完整转录（管理端不可访问）；仅通过 Goldie 访问 1a、Founder Facing KB、匿名跨公司主题、无署名专家证词 |

## 四、数据摄取层

### 4.1 Fireflies 会议摄取（Mode A：管理端唯一真源）

- 对接 GS **租户级** Fireflies 工作区
- 每场会议**自动拉取**：原始转录 + 元数据（时间、参与人、时长、标题）。
- 原始转录 **永久保留**，**永不直接暴露给创始人**；仅作为审计源与派生内容的唯一源头。
- 管理端"查看完整转录"从内部管理库读取，**不跳转 Fireflies**。
- 集成配置（同步范围、凭证）**Super Admin 、PGM可见可改**；配置界面需明示连接状态与最近同步时间。
- 架构预留多租户能力：允许其他租户接入各自 Fireflies 工作区。

### 4.2 创始人 / 用户文档直传（第二摄取源）***(是否是指Goldie？)***

- 创始人可在公司门户直传：董事会文件、Pitch Deck、客户演示、客户名单、Data Room 资料等。
- 上传内容 **完整存入本公司 1a / 1b**，**不做去逐字化**（创始人本人材料）。
- **跨公司传播默认关闭**；仅当管理员显式去标识并放行时，才允许进入跨公司层。
- **客户名单及其他 PII 内容永久禁止跨公司传播**，无覆盖开关；管理员若尝试放行需 UI 主动阻止并给出说明。
- 上传物 **带时间戳与版本**；Goldie 默认使用最新版本推理，UI 需可读地展示版本（例："Board Deck – v3, uploaded Aug 2026"）。

## 五、识别与分类层

### 5.1 参与人识别与公司关联

**明确禁止**使用会议标题作为识别依据。

**内部人员：**Email域名匹配平台中的公司与人员

**外部人员：**

识别优先级（命中即止）：

1. **专家/参与人注册表** 匹配（见 5.2）
2. **HubSpot 联系人** 记录匹配
3. **LLM 从转录内容推断**
4. 仍无法解析 → 进入 Pending Assignment 队列

补充规则：
- 通过参与人 **邮箱域名** 匹配公司在 LG 中的 Team 记录，实现公司关联。
- 一场会议可关联 **多个公司**（多家公司参与人同时出现时）。
- 识别结果（公司、外部方、角色）传递给下游分类步骤。
- 管理端应支持追溯"这场会议为何关联到此公司"（如"通过邮箱域名 acme.com 匹配至 Acme Inc"）以便 Pending 审核。

### 5.2 专家 / 参与人注册表（Cheat Sheet，唯一真源）

**Schema：** Name / Email(s，支持多值) / Organization / Role（枚举：LP、Strategic Partner、Exit Partner、Founder、GS Staff、Other）/ Expertise Tags（自由文本）/ Last Reviewed Date。

- **支持生效日期（Effective Dating）**：按会议发生日期回溯当时的角色/专业，历史证词不因当前角色变化而被重贴。
- **统一 LP 与专家清单**：Dougal 原有 LP 名单并入本注册表，避免重复维护。
- Pending Assignment 中新解析出的外部人 **自动回写** 注册表。
- 季度人工复核，超期条目 UI 打"需复核"标记。
- 作为参与人识别的 **第一优先** 信号。
- UI 以可搜索表格呈现（姓名、组织、角色、专业标签、上次复核时间），非裸文本文件。

### 5.3 会议摄取单元规则

- 每场会议以"起止时间"为边界，作为 **单一整体** 进行分类和路由。
- **MVP 不做子会议切分**（即使参会人中途变化）。
- 若混合成分会议成为显著问题（如创始人离场后 GS 内部继续开），列为 Post-MVP。管理员可通过手动改判类型作为兜底。

### 5.4 五类会议 AI 分类

由 AI 推断分类（不手工声明），并保留 **发言人级归属**（who-said-what）用于下游证词抽取。

| 类型 | 触发规则 | 备注 |
|---|---|---|
| **GS → Founder**（默认） | ≥1 位 GS 邮箱 + ≥1 位公司邮箱 | 与 Board Call 无法从参会数据自动区分，默认归此 |
| **GS → Board Call with Founder** | 手动 | 由 Portfolio Group Manager 手动改判；改判需低摩擦（单下拉切换） |
| **GS Internal** | ≥2 位 GS 邮箱，无外部/公司方 | |
| **GS → LP** | 参与人邮箱命中注册表 LP；未命中则用日历邀请中的姓名回退匹配注册表 | 依赖注册表已收录 |
| **GS → Partner**（合并 Strategic + Exit） | 参与人命中注册表中 Strategic 或 Exit Partner | 两者不可靠区分，统一为一类；下游按更保守的 Exit Partner 处理 |

- 无法可信判定 → **不猜测**，直接进入 Pending Assignment 队列。

## 六、内容加工层

### 6.1 去逐字化流水线

分类完成后，**单次处理任务**读取原始转录，一次性输出多种派生物；下游不允许再次读取原文。

**核心保证：任何面向创始人的界面永不出现原文措辞。**

去逐字化双层保障：
1. **LLM 摘要层**：负责非逐字表达。
2. **机械式清洗层**：实体/人名剥离 + 与源转录的 **近逐字 n-gram 匹配**；一旦命中即剔除。**n-gram 阈值可调**，需实施期调优。

派生物展示时，UI 需明示为"加工摘要"，强化信任。



## 七、知识资产目的地

### 7.1 1a 创始人记忆

- 本公司专属，作为 Goldie 面向创始人推理的记忆源。
- 内容来源：本公司 GS → Founder / Board Call 派生的精华摘要 + 本公司自传文档。
- 创始人 **不直接浏览** 1a 内容，通过 Goldie 感知。

### 7.2 1b 管理端记忆

- GS 管理端专属，作为 Goldie 面向 GS 侧推理的记忆源。
- 内容涵盖公司相关的 GS Internal、GS → Partner、Board Call、LP 会议（基金层）等派生物。

### 7.3 Founder Facing KB（创始人知识库）

- 创始人 **可浏览** 的公司知识库入口（区别于 1a：1a 是 Goldie 后台记忆，Founder KB 是创始人前台可见 UI）。
- 内容来源：
  - 本人参与的 GS → Founder 会议派生精华（"own call, essence"）
  - 本人参与的 Board Call 派生精华（founder present 情况下）
  - 创始人本人上传的文档（板料、Pitch Deck 等）
- 严格限于创始人 **本人出席** 的会议；未出席会议不进 Founder KB。

### 7.4 专家证词库（Expert Testimony）

**内容来源：** LP 会议、GS → Partner 会议、有外部董事在场的 Board Call。

**存储字段：** 匿名内容 / 发言人角色标签（LP、PE、IB、Buyer、Founder、Expert）/ 时间戳 / **按会议日期生效的专业标签**（读取注册表 Effective Dating）。

**GS → Partner 证词范围（合并后统一）：** 商业采购行为、软件使用、倍数、买方行为、退出趋势。

**证词内容：** 市场行情、倍数、买家行为、商业采购行为、软件采纳等趋势界面。

**分层权限：**

- **Portfolio Group Manager / Portfolio Manager**（Goldie 内）：**看到完整署名**（谁说的、角色、组织），便于判断可信度。
- **Founder**（Goldie 内）：**只看内容摘要 + 专业摘要**，**永不显示署名**；措辞如"某医疗 IT 买家指出……"，避免通过上下文暴露身份。
- 所有证词单元必须遵守机密性边界（9.1、9.2），违规内容 **结构性禁止** 触达创始人界面。

### 7.5 跨公司知识库（Cross-Company Themes）

- 内容为公司标识 **完全剥离** 后的匿名主题 / 洞察。
- **Portfolio Manager / Portfolio Group Manager**（管理端）：**可回溯到原始转录与署名**（通过管理端系统入口，非跨公司 KB 前台）。
- **Founder**（Goldie 内）：**仅**看匿名摘要；**不可**浏览底层 KB，**不可**看原始转录或署名；感受为 Goldie 环境智能（"处于相似阶段的其他公司发现……"）。
- 被 9.1 / 9.2 命中的内容（活跃交易隔离 / LP 基金过滤）**对所有受众均排除**，包括 Portfolio Manager。
- GS Internal 来源主题额外支持"战略解决闭环"和"全公司视图"（**完整交互 UI 属 Post-MVP**）。

### 8.2 管理员干预（Portfolio Group Manager / Super Admin）

- **改判会议类型** → 路由自动重算；改判前需 **预览路由变化**。
- 同一会议内 **按目的地独立开关** 每个路由块（1a / 1b / Founder KB / Expert Testimony / Cross-Company）。
- **创始人转录访问约束**：创始人仅可看 **本人参加会议** 的完整转录；未参加会议只能通过 1a / Founder KB 摘要感知（即便与本公司相关）。
- 所有路由决策与覆盖动作 **写入审计日志**。

### 8.3 Pending Assignment 队列

**触发条件：** 参与人邮箱为私人邮箱、未知域名，或注册表 / HubSpot 均无法匹配。

原则：**原始转录**依然进入管理端库（Mode A 永久留存）；**派生路由被阻断**，直到人工确认。

- 队列可见性：能识别所属组合 → 交给该组合的 Portfolio Group Manager；否则交给 Super Admin。
- 提示：管理端知识库出现"Pending Assignment (n)"角标；可选每日邮件 / Slack 摘要。
- 审核者视图：会议时间、标题、完整参与人列表 + 邮箱、**可直接查看完整转录**（读自管理端库）。
- 单项解决动作：
  1. 指定公司 + 会议类型
  3. 指定为新识别的外部方 → **自动写入注册表**（轻量表单：姓名、组织、角色、专业标签）
- **未确认前**，任何记忆文件、专家证词、跨公司层、创始人界面 **一律无路由**。
- 已解决会议仍可事后改判类型、独立开关路由块。

## 九、机密性边界

### 9.1 活跃交易隔离（Live-Deal Quarantine）

- 当 GS → Partner 或 LP 会议提及某"正在被兜售或估值"的组合公司：
  - **可携带的市场趋势**（例如"某垂直 SaaS 倍数在压缩"）→ 可进入跨公司主题
  - **公司具体交易事实**（例如"X 公司被兜售给 Y 买家，价格 Nx"）→ **仅落到该公司 1b**，其他创始人的 Goldie 永远不可见（即便匿名也不允许）
- 由于 Strategic/Exit Partner 已合并，**该隔离对所有 GS → Partner 会议全量适用**（保守默认）。

### 9.2 LP / 基金机密性过滤

- LP 会议派生物在标准公司匿名之外，**再加一层机密性清洗**：剥离基金层信息、其他 LP 身份信息，才能进入任何面向创始人界面。

### 9.3 Board Call 处理

- 创始人在场并已听到全部内容 → Board Call 派生物按 1:1 对话方式路由至该创始人 KB（不做第三方来源匿名处理）。
- 从 Board Call 派生的跨公司主题传播 **仍需带敏感来源的 care flag**。

## 十、逻辑问题与需求缺口（源自 EPIC 本身）

1. **Cross-Company 对 LP 会议的路由与机密性边界存在潜在冲突**
   路由矩阵允许 GS → LP 派生"仅市场趋势"进入 Cross-Company；机密性 9.2 要求 LP 派生物在到达任何创始人界面前必须再过一层"剥离基金层 / 其他 LP 信息"过滤。EPIC 未明确 Cross-Company 前端呈现是否满足 9.2、"市场趋势"到底是从证词库读取还是从主题库读取，两条管道的过滤责任划分未闭环。

2. **Board Call 中外部董事证词的口径冲突**
   9.3 说创始人已听全部内容，Board Call 派生物路由至创始人 KB **不做匿名**；11.4 又要求有外部董事在场时可产生 Expert Testimony（要求匿名 + 无署名给创始人）。同一段外部董事发言，走 Founder KB 是可署名的、走 Expert Testimony 是不署名的，**同一创始人在两个界面上看到同一句话的处理不一致**，需要澄清是否两侧都产生，还是择一。
