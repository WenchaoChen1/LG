# 需求文档：导入时自动计算 OPEX 总额以避免校验报错

**来源任务**：Auto-Calculate OPEX Total on Import to Prevent Validation Error
**Asana 链接**：https://app.asana.com/1/1170332106480422/project/1215698870864641/task/1215349591481274
**适用页面**：Looking Glass — Financial Entry（财务录入）页、Committed Forecast（承诺预测）页

---

## 一、背景与问题

### 1.1 现有校验规则
Financial Entry 与 Committed Forecast 页面均强制执行以下校验：
> OPEX 总额 ≥ 六个手动录入子项之和

六个手动录入子项为：
1. S&M Expenses（销售与市场费用）
2. S&M Payroll（销售与市场薪酬）
3. R&D Expenses（研发费用）
4. R&D Payroll（研发薪酬）
5. G&A Expenses（管理费用）
6. G&A Payroll（管理薪酬）

第七项 **Miscellaneous Operating Expenses（杂项运营费用）** 为计算字段，公式为：
> Miscellaneous = OPEX − 六个子项之和

该校验规则原本针对手动录入流程设计，在手动录入场景下运行正常。

### 1.2 问题场景（OCR 手动上传带来的边界情况）
当用户通过 OCR 手动上传功能导入财务文件时：
- 导入通道会将六个子项写入数据库；
- 但**不写入 OPEX 总额**，也**不写入 Miscellaneous**（这两项不包含在导入数据中）。

结果：导入提交后，OPEX 字段值为 0 或保留旧值，可能小于新导入的六个子项之和。当用户随后打开 Financial Entry 或 Committed Forecast 页进入编辑模式时，校验规则被触发并报错，导致用户**无法编辑数据**。

---

## 二、解决方案概述

在导入写入过程中，**由系统自动计算并写入正确的 OPEX 总额**，与子项数据在同一次写操作中提交到数据库。

关键约束：
- **仅在导入写入时进行一次性赋值**，不引入持久化的自动计算规则；
- 导入后，OPEX 仍为**手动录入字段**，用户可在页面正常编辑；
- Miscellaneous Operating Expenses 仍为**计算字段**，行为不变；
- 现有 OPEX 校验规则在手动编辑流程中**继续生效**，不做任何修改；
- Financial Entry 与 Committed Forecast 页面的 UI、校验逻辑、编辑行为**均无变更**。

> **适用范围（两条写入路径）**：本逻辑需同时挂在导入的两条写入路径上：
> 1. **Actuals（实际数据）**：走冲突校验/解决流程，子项生效值按第四节四类场景判定。
> 2. **Committed Forecast（承诺预测）**：导入时默认不调用冲突校验接口、直接保存，但**入库时同样必须保证 OPEX 等值正确**——使用相同的计算公式，详见 5.6。

---

## 三、功能描述

### 3.1 触发条件
- 导入包含六个 OPEX 子项中**至少一个**时，触发 OPEX 自动计算；
- 导入**未涉及任何**六个子项时，不执行 OPEX 重新计算，不修改 OPEX 字段。

### 3.2 计算公式（写入时）
> **OPEX = 写入后六个子项的生效值之和 + 该月已有的 Miscellaneous Operating Expenses 值**

### 3.3 写入时机
计算出的 OPEX 总额**与子项值在同一次写入操作中提交**到数据库，**不是后续的单独更新**。

---

## 四、数据来源与"生效值"的判定规则

按月独立判定。每个子项写入后的"生效值"按以下四类场景确定：

| 场景 | 子项生效值的取值 |
|---|---|
| **新月份（无历史数据）** | 使用导入值；未包含在导入中的子项视为 0 |
| **已有月份，无冲突** | 使用导入值；未包含在本次导入的子项，**保留数据库已有值** |
| **已有月份，冲突且用户选择覆盖** | 使用覆盖值（即导入值） |
| **已有月份，冲突且用户选择保留原值** | 保留数据库已有值 |

### 4.1 Miscellaneous 值的获取
- 写入前系统**预先读取该月数据库中已有的 Miscellaneous Operating Expenses 值**；
- 若该月无历史数据，Miscellaneous 在计算中视为 0。

> **产品锁定口径（最终）**：导入时 OPEX **永远**按公式 `OPEX = 六子项之和(写入后) + 已有 Miscellaneous` 计算。
> - 六子项 = 导入值 ∪ 已有值（参见第四节）；
> - **已有 Miscellaneous = 该月数据库 `miscellaneous_operating_expenses` 持久化列存值，原样代入**（`null` 按 0）；新月份（无历史）记 0；
> - **只重算并写 OPEX 一个值，不重算 / 不修正 / 不回写 misc 列**（不做符号判断、不清零）；
> - 推论：负费用场景，若该列存值为 0，则 OPEX = 六个负子项之和。

> **脏数据边界（明确不处理）**：持久化列存值与页面派生显示（`OPEX − 六子项`）在历史脏行上可能不一致（早期路径只改 OPEX/子项没回写列所致）。本功能**只保证公式本身正确**，由此类脏数据引起的现象（如导入后页面 misc 显示变化）**不在处理范围**；存量脏行由数据订正单独处理，新导入逻辑不为其特殊处理。

### 4.2 多月导入
- 每个月份**独立**计算 OPEX，使用该月自身的生效子项值与已有 Miscellaneous 值；
- 未包含在导入中的月份**不受影响**。

---

## 五、操作流程（后端写入流程）

1. 解析导入数据，识别本次导入涉及的月份及六个 OPEX 子项。
2. 判断本次导入是否包含至少一个 OPEX 子项：
   - 否 → 不执行 OPEX 重新计算，按原流程写入，结束。
   - 是 → 进入步骤 3。
3. 对每个涉及月份执行：
   1. 预读取该月已有的 Miscellaneous Operating Expenses 值（无历史数据时取 0）。
   2. 依据冲突解决结果，确定该月六个子项各自的"写入后生效值"（参见第四节判定规则）。
   3. 计算：`OPEX = 六个生效值之和 + 已有 Miscellaneous 值`。
4. 在同一次写入操作中，将六个子项的导入/覆盖值与计算出的 OPEX 总额一起提交至数据库。
5. 写入完成后，数据库中 OPEX 总额与"六个子项之和 + Miscellaneous"保持一致。

> 上述步骤 3.1 的"已有 Miscellaneous 值"取自数据库持久化列 `miscellaneous_operating_expenses`（详见 4.1 实现注意）。

### 5.6 Committed Forecast（承诺预测）直存路径

承诺预测数据导入时默认**不调用冲突校验接口、直接保存**（无"覆盖 / 保留"的用户选择），但**入库前同样要执行 OPEX 自动计算**，且 OPEX 的取数与计算口径与 actuals 一致：从该月数据库已有最新承诺预测数据行（base）取 misc 与"本次未导入的 OPEX 子项"的保留值，再算 OPEX。

> **范围限定（仅 OPEX 相关字段取 base）**：与 actuals 不同，承诺预测路径**只**从 base 取「6 个 OPEX 子项 + Miscellaneous」用于重算 OPEX，**不整行复制 base**。其余字段（Revenue / Cash / 资产负债项，以及承诺预测特有的 p05/p50/p95 分布字段等）维持原有「本次未导入即填 0」行为，不受本需求影响。如此既满足 OPEX 校验闭环，又不把上一版的分布输出与其它非 OPEX 指标带进本次导入版本。

1. 判断本次导入是否包含至少一个 OPEX 子项：否 → 不重新计算 OPEX，按原流程直存，结束。
2. 对每个涉及月份执行：
   1. **读取该月数据库已有最新承诺预测行为 base**（无历史数据时 base 视为空行）。
   2. 取 base 行持久化列 Miscellaneous Operating Expenses 值（base 为空时取 0）。
   3. 确定六个子项的"写入后生效值"：**导入的子项 = 导入值；未导入的子项 = base 行已有值（base 为空时取 0）**。
   4. 计算：`OPEX = 六个生效值之和 + 已有 Miscellaneous 值`。
3. 在同一次写入操作中，将六个子项值与计算出的 OPEX 总额一起直存至数据库。

## 六、关联修复：手动编辑改子项时同步 Miscellaneous 列

**问题**：在 LG 手动编辑里改某个 OPEX 子项后，**保存只更新了子项、没有重算 Miscellaneous 持久化列**（提交落库时原样拷贝缓存里的旧 misc）。于是改完子项后，`miscellaneous_operating_expenses` 列当场就和页面派生显示（`OPEX − 六子项`）不一致；随后再次 OCR 导入（按本需求读该列计算 OPEX）时，misc 就会跳变。

**修复（方案 B，治本于编辑路径）**：手动编辑保存时，**除非用户直接编辑了 Miscellaneous 字段**，否则按定义重算 `Miscellaneous = OPEX − 六子项之和` 写回，与既有手动录入保存路径口径一致。保证"任何保存后，持久化列 == 页面派生显示"，从源头消除列漂移。

- 范围：仅修手动编辑保存路径；用户直接编辑 misc 的行为保持不变；不改校验、不改 Cash 联动。
- 待办（未报先不动）：一键操作（如 OE 分摊）若也改子项/OPEX 而不经此保存路径，可能存在同类漏同步，后续如复现再处理。
