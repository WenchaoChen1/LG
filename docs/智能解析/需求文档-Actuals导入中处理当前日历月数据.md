# 需求文档：Actuals 导入中处理当前日历月数据

**来源任务**：Handle Current Calendar Month Data in Actuals Import
**Asana 链接**：https://app.asana.com/1/1170332106480422/project/1215698870864641/task/1215349591481272
**适用模块**：手动上传 OCR 导入管线 — Proforma 分类逻辑、映射审查（Mapping Review）页面
**Figma 设计稿**：https://www.figma.com/design/QBhTPAljVPx673QWVrvfGw/2026---Portfolio-Portal?node-id=13471-5840

## 一、背景与问题

用户通过**手动上传 OCR**功能上传财务文件时，导入管线会基于**关键字识别**和**日期逻辑**将提取的数据表分类为 **Actuals（实际）** 或 **Proforma（预测）**。

现有 Proforma 检测规则已能：
- 识别含 "proforma" 等关键字的表格；
- 识别含**未来月份数据**的表格。

测试中发现的缺口：**当一个表被分类为 Actuals 时，可能包含当前日历月的数据**——例如公司在月中上传 P&L 文件，文件含本期未完结、不完整的数字。

### 业务约束
- Looking Glass **不允许**手动录入公司在**当前日历月**载入财务数据，因为该数据本质上不完整、未最终化；
- 该规则已在**手动 Financial Entry 流程**中被强制执行，但**未应用到导入通道**；
- 若不补足该规则，用户可能在无意中通过导入将不完整的月中实际数据导入 LG，违背平台数据完整性标准，并可能扭曲基准、预测和财务指标。

---

## 二、解决方案概述

为避免数据丢失同时遵守业务规则，将 Proforma 检测逻辑扩展为**第三种触发条件**：

> 若表被分类为 Actuals，但包含当前日历月的数据，则**该当前月份的数据**自动重新分类为 Proforma，并被路由到**预测表（forecast table）**，而非被剔除或丢弃。

关键点：
- 同一 Actuals 表中**其他月份**正常按实际处理；
- 当前月数据**不被丢弃**，而被作为预测数据——这是不完整月中数据最合理的归类；
- 重分类时需**通过映射审查阶段的内联非阻断提示**告知用户，让用户知情后决定是否继续或调整数据后再提交。

---

## 三、功能描述

### 3.1 更新后的 Proforma 检测逻辑
在原有两个条件之外，新增第三个触发条件，三者并列如下：

1. **关键字匹配**：表中含 "proforma" 或被识别的变体关键字 → **整张表**分类为 Proforma；
2. **未来日期**：表中含任何未来月份 → **整张表**分类为 Proforma；
3. **当前月例外**（新增）：表被分类为 Actuals 但包含当前日历月 → **仅当前月数据**重分类为 Proforma。

注意：
- 前两个条件继续按原行为将**整张表**分类为 Proforma；
- 第三个条件**仅作用于**其余仍为 Actuals 表中**当前月**的那一份数据；该表其他月份**继续**作为 Actuals 处理。

### 3.2 当前月重分类行为
- 当当前月例外触发时，从 Actuals 表中提取的**当前日历月**数据被重分类为 Proforma；
- 重分类后的当前月数据被路由至 LG 的**预测表**，不写入实际表；
- 同一 Actuals 表中**当前日历月之前的所有月份**正常作为 Actuals 处理与映射，不发生变化；
- 重分类**由系统自动应用**，无需用户操作触发；
- 重分类后的当前月数据**遵循与其他 Proforma 数据一致的映射与校验规则**。

### 3.3 用户通知
- 当本次导入会话中存在任何被重分类的当前月数据时，在**映射审查（Mapping Review）步骤**向用户展示一条清晰的**内联提示**；
- 文案示例：
  > "[calendar month] data treated as Proforma — current month data may be incomplete for Actuals."
  告知用户系统在 Actuals 表中检测到当前月数据并已将其重分类为 Proforma；
- 该提示为**非阻断**——用户可查看后继续完成导入，不强制采取任何动作；
- 若本次会话未发生当前月重分类，**不显示**该提示。

### 3.4 与现有规则的一致性
- 当前月例外规则**仅适用于**被分类为 Actuals 的表；**已经**被分类为 Proforma 的表不受影响；
- 不论当前日历月数据在源文件中以何种形式出现（命名列标题、日期值或解析器可识别的任何日期表达），该规则均一致应用；
- 系统使用**上传时的当前日历月**作为判定基准，**不是**最近已关账月或任何其他参考点。

## 四、数据来源

| 数据项 | 来源 |
|---|---|
| 表的初步分类（Actuals / Proforma） | 现有关键字识别 + 日期逻辑 |
| 表中月份信息 | 解析阶段从源文件提取（列标题、日期值或其他日期表达） |
| 当前日历月 | 用户**上传时**的系统日历月 |
| 重分类标记 | 系统在导入管线中产生，传递至映射视图与下游写入 |
| 重分类后路由目标 | LG 预测表（forecast table） |

---

## 五、操作流程

### 5.1 导入管线（系统）
1. 解析上传文件，提取数据表及月份；
2. 按现有逻辑做初步分类（Actuals / Proforma）：
   - 命中关键字或含未来日期 → 整张表为 Proforma，结束本表逻辑；
   - 否则按 Actuals 继续；
3. 在被分类为 Actuals 的表中识别**当前日历月数据**：
   - 无 → 全表按 Actuals 处理，结束；
   - 有 → 进入步骤 4。
4. 将**当前月数据**重分类为 Proforma，路由至预测表；同一表中**其他所有月份**仍按 Actuals 处理；
5. 重分类的数据沿用 Proforma 的映射与校验规则进入后续步骤。

### 5.2 映射审查（用户）
6. 用户进入映射审查页面，查看 Actuals/Proforma 的分类结果与对应数据；
7. 若本次会话有任何当前月重分类发生，页面显示一条内联提示，注明被重分类的月份及原因；
8. 用户可：
   - 继续提交（非阻断）；
   - 调整数据后再提交。
