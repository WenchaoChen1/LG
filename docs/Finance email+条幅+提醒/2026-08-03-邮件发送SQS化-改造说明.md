# 邮件发送统一 SQS 化 · 改造说明与代码入口

> 分支 `sprint115` ｜ 本次改造 11 个提交：`f6d2a833f` .. `1fac64494`
> 所有路径以 `CIOaas-api/` 为根。行号会随后续改动漂移，**定位以类名 + 方法名为准**。

## 一句话

五处各自直连 SendGrid 的邮件调用点，收敛成一条带去重与重试的统一管道：业务处只投递一条轻量指令，真正的内容组装推迟到消费时、由业务侧按已持久化的状态重建。

**发送出口没有变** —— 仍然是 `EmailServiceImpl.sendEmail()`，本次只在它里面提取了一个常量。

## 一、管道链路

```
业务处
  └─ EmailDispatcher.enqueue(EmailSendCommand)      ← 唯一入口
       ├─ validate()                                 收件人二选一校验
       ├─ buildDedupKey()                            算去重键
       └─ TransactionSynchronization.afterCommit     事务提交后才真正投递
            └─ email-queue
                 └─ EmailSendSqsHandler.processMessage()
                      ├─ parse()                     字段断言
                      ├─ 去重探针                     曾经发成功过就 ack 跳过
                      ├─ EmailComposerRegistry.get()  按 composerType 路由
                      ├─ EmailComposer.compose()      业务侧只读重建
                      ├─ EmailServiceImpl.sendEmail() 原有出口，未改逻辑
                      └─ 失败分流                     白名单拒绝→ack；IO 故障→重试
```

### 3.1 位置通知的 bizKey 为什么要带 `org` / `parent`

`PositionNotifier.notify(Set<String> firedCompanyIds, String runId)` —— **签名新增了 runId 参数**，三个调用点在 `BenchmarkPositionMonitorServiceImpl`：

| 调用点 | 传什么 | 原因 |
|---|---|---|

## 五、四个关键机制

### 5.1 去重键

由 `EmailDispatcher.buildDedupKey()` / `buildCanonical()` 生成：

```
canonical = bizKey 按 key 字典序拼接 + "|" + ("uid=" + userId 或 "mail=" + email)
dedupKey  = {composerType} + ":" + sha256Hex(canonical) 前 32 位
```

用哈希而非明文拼接，是因为 `FinancialBenchmarkEntry.edition` 列宽 200、`platform` 50，明文最坏约 373 字符会撑爆 `varchar(128)`；而超长在 `emailRepository.save` 处是**抛异常**（不是返回 `Pair.of(false,…)`），会绕过发送结果的两分支处理直接进 DLQ。

**探针语义是"是否曾经成功过"，不是"最后一次是否成功"** —— 失败重发会不断新插行，看最新一行会误判重发。

### 5.2 bizKey 必须带组织维度（曾经的 Critical）

去重键的输入只有 `bizKey + 收件人`。所以任何"一个收件人可能在多个组织下各收一封"的邮件类型，**组织维度必须进 bizKey**，否则两封合法邮件算出字节相同的键，第二封被探针当成"已投递"静默丢弃。

位置通知最初漏了这条：跨两个组织的 PM 只收到一封，管两家公司的 Company Admin 同样塌成一封，且 Composer 只按 `userId` 过滤导致公司清单变成跨组织并集。修复在 `33a52417d`：`PositionNotifier` 的 `withOrg` / `withParent` 叠加维度，Composer 按 `(userId, orgId)` / `(userId, parentId)` 精确定位。

月度邮件的 `{run, cid}` / `{run, pid}` 本身就带公司/组合维度，天然免疫。

### 5.3 失败分类

分错方向的代价不对称：**该重试的判成不可重试，就是静默永久丢件**。

| 情形 | 异常 | 结果 |
|---|---|---|
| 消息字段非法、未知 composerType、非法 JSON | `NonRetryableEmailException` | warn + 记账 + ack，不进 DLQ |
| run 被删、收件人已失去组织归属 | `NonRetryableEmailException` | 同上 |
| 非 prod 环境白名单拒绝 | `NonRetryableEmailException` | 同上（否则 stage/uat 的 DLQ 会被灌满） |
| 快照行暂时读不到（Stage-1 重投的删除窗口） | 普通 `IllegalStateException` | SQS 重试 3 次后进 DLQ |
| SendGrid IO 故障 | 普通 `IllegalStateException` | 同上 |

`EmailServiceImpl.sendEmail` **失败时返回 `Pair` 而不抛异常**，所以 handler 必须判返回值。白名单拒绝的文案含运行时的 `environment` 值，`equals` 永远匹配不上——这就是为什么提取的是**前缀**常量 `MSG_NOT_WHITELISTED_PREFIX`，用 `startsWith` 判定。

### 5.4 月度邮件的两处数据竞态

**A1 —— Admin 重建只读 `run_snapshot`，绝不重算 diff。**
`BenchmarkEmailCompanyWorker.commitSideEffects` 保持 `sendAdminEmails` 先于 `writeBaselines` 的顺序，但**异步化后这个顺序已不提供任何保护**：消息被消费时 baseline 早已推进，重算 diff 会全变 UNCHANGED、PM 决策从 FIRE 翻成 SILENT、Stage 2 扇出漏掉该公司。保护来自 Composer 只读快照（写在 baseline 推进之前）。

**A2 —— 读不到快照行时抛普通异常，不是 `NonRetryableEmailException`。**
`BenchmarkEmailCompanyWorker` 有四处会删除并重建快照行，消息落在删除窗口里会合法地读到零行。判成"业务失效"就会 ack 掉、**永久丢件**。

## 八、上线步骤

1. 在目标库执行 `V1__email_add_dedup_key.sql`
2. **单独**执行 `V2__email_dedup_key_index.sql`（不能包在事务里）
3. 部署代码
4. 启动即验证：`existsByDedupKeyAndStatusBetween` 是派生查询，方法名只在启动时校验；解析不上会抛 `PropertyReferenceException` 直接起不来（fail-fast，不会静默降级）
5. 端到端冒烟：往 `<前缀>email-queue` 投一条 `BENCHMARK_REPORT_SUCCESS_SUMMARY`，核对 `email` 表有行且 `dedup_key` 已填、`status` 为 2xx；**再投一次相同消息，确认行数不变**
6. 重点验一个场景：找一个跨两个组织的 PM（或管两家公司的 Company Admin），确认他收到**两封**而不是一封

队列无需手工创建 —— `SQSMessageListener.sqsInit()` 是 `@PostConstruct`，会调 `sqsService.initSqsQueues()` 遍历 `InitSqsQueueEnum` 创建或同步属性，且早于监听容器启动。

## 九、已知缺口（已接受，未改代码）

| 项 | 说明 |
|---|---|
| 去重探针挡不住一种重投 | `EmailServiceImpl` 第一次 save 落 `status=0`、第二次才写 2xx，而 `catch` 只捕获 `IOException`。第二次 save 抛 `DataAccessException` 会冒泡触发重投，此时表里只有 status=0 的行、探针必然未命中 → **重复投递一次**。探针把这个场景从"最多 3 封"降到"恰好 2 封"，没有消除 |
| 4xx 被当作已投递 | `sendEmail` 只在 SendGrid 抛异常时返回 false，所以 4xx 存成 `status=400` 后被正常 ack |
| SQS 投递失败会丢邮件 | `SQSServiceImpl.sendMessageToSqs` 把异常 catch→log→返回 null，调用方感知不到。依赖既有 `log.error` + Sentry |
| 查询放大 | 一收件人一条消息，位置通知场景每封邮件独立重查组织/用户/公司名 |
| 三处孤儿未清理 | `notifyExecutor` 线程池已无提交方；`EmailTypeEnum.BENCHMARK_REPORT_FAILURE` 的生产者已删；模板 `BenchmarkReportFailure.html` 失去渲染方 |

完整的后续跟进项（9 条，均判定不阻塞）见 `.superpowers/sdd/MANUAL-STEPS.md`。
