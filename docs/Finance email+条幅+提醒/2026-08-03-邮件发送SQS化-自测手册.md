## ⚠️ 先读这段：选对环境

`EmailServiceImpl` 的白名单拦截**只在 `stage` 和 `uat` 生效**：

```java
if (environment.equals("stage") || environment.equals("uat")) {
    // 不在 white_list_user 表里、且邮箱不含 qq.com → 拒发
}
```

也就是说：

| 环境 | 邮件会发给谁 | 能否跑全量 |
|---|---|---|
| `stage` / `uat` | 只有 `white_list_user` 表里的地址 + 任意 `qq.com` 邮箱 | ✅ 安全 |
| `test` | **数据库里的真实收件人，无任何拦截** | ❌ 危险 |
| `prod` | 真实收件人 | ❌ 禁止 |

**结论**：全量跑批（L4、L5）**只在 stage 或 uat 做**。若只能用 test 环境，就只做 L0–L3——那几级都是单条消息、收件人由你指定，不会波及真实用户。

在 stage/uat 开始前，先把自己加进白名单（或直接用 QQ 邮箱，省这一步）：

```sql
SELECT * FROM white_list_user WHERE email = '<你的邮箱>';
-- 没有就插一条（表结构见 WhiteListUser 实体）
```

## 在 AWS 上投消息：操作方式与全部可用参数

### A. 找到队列

队列实名 = `cio.sqs.name-prefix` 配置值 + 队列后缀。前缀形如 `lg-non-prod-uat-`（由 `app.env` / `app.stage` 拼出），所以你要找的是：

- `<前缀>email-queue` —— 直投单封邮件，收件人由你指定
- `<前缀>scheduler-queue` —— 触发整条业务跑批
- `<前缀>dlq-queue` —— 失败三次后的死信

**Console**：SQS → 搜后缀名 → 认准环境前缀 → 进队列 → 右上 **Send and receive messages** → Message body 粘 JSON → **Send message**。区域默认 `us-east-1`。Standard 队列，Message group ID / Deduplication ID 留空。

**CLI**（适合脚本化重复投）：

```bash
QUEUE=lg-non-prod-uat-scheduler-queue     # 换成你的实际队列名
URL=$(aws sqs get-queue-url --queue-name "$QUEUE" --query QueueUrl --output text)

aws sqs send-message --queue-url "$URL" --message-body '<下面任选一段 JSON>'
```

不确定前缀时，从应用启动日志里搜 `queueArn=`，arn 末段就是实名。

### B. 四类业务跑批的完整参数表

全部投 **`scheduler-queue`**。`messageType` 固定 `Scheduler`，`schedulerType` 决定走哪条业务线。下表的可选字段就是全部——代码里没解析的字段写了也不会生效。

| schedulerType | 可选参数 | 类型 / 格式 | 不传时的行为 |
|---|---|---|---|
| `QuarterlyBenchmarkReport` | `companyId` | 字符串，**单个**公司 | 全量 |
| | `period` | `2026Q1` | 按当前日历推断季度 |
| | `triggeredBy` | 字符串，记审计 | 系统用户 |
| `BenchmarkPositionMonitor` | `companyIds` | 字符串**数组** | 全量 |
| `BenchmarkEmailDaily` | `companyIds` | 字符串**数组** | 全量（约 1000 家，**自测务必带上**） |
| | `asOfDate` | `2026-06-25` | UTC 当天 |
| | `phase` | `DAILY` / `MONTHLY_25TH` | 按当天是不是 25 号推断 |
| | `manualTrigger` | `true` | 走 SCHEDULED，同日同 phase 只跑一次 |

几个要点：

- **季度报告只能指定一家公司**（`companyId` 是单值）；位置通知和月度邮件是**数组** `companyIds`。
- `manualTrigger: true` 会绕过"同日只跑一次"的幂等约束，所以同一天可以反复触发。不带它的话第二次投递只会返回第一次的 runId、**什么都不做**——自测时容易误以为消息没生效。
- `phase: "MONTHLY_25TH"` 让你在任何一天跑 25 号的月度逻辑，不用等到 25 号。
- `asOfDate` 会同时改变 run_date 和 worker 的取数基准日，用来复现历史某天的结果。

### C. 可直接粘贴的消息体

**只跑一家公司的月度邮件**（自测月度链路的推荐姿势）：

```json
{
  "messageType": "Scheduler",
  "schedulerType": "BenchmarkEmailDaily",
  "companyIds": ["<公司ID>"],
  "phase": "MONTHLY_25TH",
  "manualTrigger": true,
  "uuid": "selftest-monthly-001"
}
```

**指定日期复现历史跑批**：

```json
{
  "messageType": "Scheduler",
  "schedulerType": "BenchmarkEmailDaily",
  "companyIds": ["<公司ID>"],
  "asOfDate": "2026-06-25",
  "phase": "MONTHLY_25TH",
  "manualTrigger": true,
  "uuid": "selftest-replay-001"
}
```

**只跑几家公司的位置变化通知**：

```json
{
  "messageType": "Scheduler",
  "schedulerType": "BenchmarkPositionMonitor",
  "companyIds": ["<公司ID-1>", "<公司ID-2>"],
  "uuid": "selftest-position-001"
}
```

**单公司补跑季度报告**：

```json
{
  "messageType": "Scheduler",
  "schedulerType": "QuarterlyBenchmarkReport",
  "companyId": "<公司ID>",
  "period": "2026Q2",
  "triggeredBy": "selftest",
  "uuid": "selftest-report-001"
}
```

**直投单封邮件**（跳过业务跑批，投 **`email-queue`**）：

```json
{
  "messageType": "EmailSend",
  "queueName": "email-queue",
  "composerType": "BENCHMARK_REPORT_SUCCESS_SUMMARY",
  "bizKey": { "run": "<runId>" },
  "recipientEmail": "<你自己的邮箱>",
  "dedupKey": "selftest-direct-001"
}
```

五种 `composerType` 各自要的 `bizKey`：

| composerType | bizKey | 收件人字段 |
|---|---|---|
| `BENCHMARK_REPORT_SUCCESS_SUMMARY` | `{"run": "<runId>"}` | `recipientEmail` |
| `BENCHMARK_ENTRY_UPDATE` | `{"platform":"KeyBanc","edition":"2099","org":"<公司ID>"}`<br>PM 版把 `org` 换成 `"parent":"<组织ID>"` | `recipientUserId` |
| `BENCHMARK_POSITION_UPDATE` | `{"cid":"<公司ID>","org":"<公司ID>"}`<br>或 `{"run":"<runId>","parent":"<组织ID>"}` | `recipientUserId` |
| `BENCHMARK_MONTHLY_COMPANY_ADMIN` | `{"run":"<runId>","cid":"<公司ID>"}` | `recipientUserId` |
| `BENCHMARK_MONTHLY_PORTFOLIO_MANAGER` | `{"run":"<runId>","pid":"<组合ID>"}` | `recipientUserId` |

> `recipientUserId` 和 `recipientEmail` **恰好填一个**，两个都填或都不填会被判为非法消息（一次 ack，不重试）。
> 直投时 `dedupKey` 由你自己起名，起过的名字再投一次就会被跳过——这正是 L3 要验的行为。

### D. 怎么找到要填的 ID

```sql
-- 公司（挑一家有财务数据的）
SELECT company_id, company FROM company
WHERE company_status NOT IN (1, 6) ORDER BY created_at DESC LIMIT 10;

-- 季度报告的 runId
SELECT id, period, status FROM financial_benchmark_report_run
ORDER BY created_at DESC LIMIT 5;

-- 月度邮件的 runId 与它涉及的公司
SELECT id, phase, trigger_type, run_date, total_company_count
FROM financial_benchmark_email_run ORDER BY run_trigger_time DESC LIMIT 5;

-- 某个 run 下的公司与组合
SELECT DISTINCT company_id FROM financial_benchmark_email_run_snapshot WHERE run_id = '<runId>';
SELECT company_group_id, name FROM company_group LIMIT 10;

-- 收件人 userId
SELECT user_id, email, role_type, company_id FROM "user"
WHERE email = '<你的邮箱>' AND is_deleted = FALSE;
```

```
EmailComposerRegistry initialized with 5 composer(s)
```

**期望**：数量是 **5**。少了说明某个 Composer 没被 Spring 扫到，那类邮件消费时会抛"No EmailComposer registered"。

| 报错 | 含义 |
|---|---|
| `PropertyReferenceException` | `existsByDedupKeyAndStatusBetween` 的属性名解析不上（派生查询只在启动时校验）。检查 `Email.dedupKey` 字段是否存在 |

### 0.3 队列是否自动建好

AWS Console → SQS，搜 `email-queue`。

**期望**：存在 `<前缀>email-queue`。前缀由 `cio.sqs.name-prefix` 决定（形如 `lg-non-prod-uat-`）。

无需手工创建——`SQSMessageListener.sqsInit()` 是 `@PostConstruct`，会遍历 `InitSqsQueueEnum` 创建或同步属性。没建出来说明该初始化失败了，看启动日志。

## L2 · 单条链路冒烟（最关键的一步）

这一步一次性验证：入队格式 → 队列 → listener → 路由 → Composer → 发送 → 落库。整条链路任何一环断了都会在这暴露。

**先找一个真实的 runId**：

```sql
SELECT id, period, status FROM financial_benchmark_report_run
ORDER BY created_at DESC LIMIT 5;
```

**往 `<前缀>email-queue` 投**（AWS Console → 该队列 → Send and receive messages）：

```json
{
  "messageType": "EmailSend",
  "queueName": "email-queue",
  "composerType": "BENCHMARK_REPORT_SUCCESS_SUMMARY",
  "bizKey": { "run": "<上面查到的runId>" },
  "recipientEmail": "<你自己的邮箱>",
  "dedupKey": "manual-smoke-001"
}
```

**看日志**，应出现：

```
[email-send] delivered: composerType=BENCHMARK_REPORT_SUCCESS_SUMMARY dedupKey=manual-smoke-001
```

**查库**：

```sql
SELECT id, receiver_email, subject, status, dedup_key, created_at
FROM email WHERE dedup_key = 'manual-smoke-001';
```

**期望**：1 行，`status = 202`（SendGrid Accepted），`subject` 形如 `March Q1 Benchmark Report Available`。

```sql
SELECT message_type, company_id, created_at FROM queue_message_log
WHERE message_type = 'EmailSend' ORDER BY created_at DESC LIMIT 3;
```

**期望**：有记账行。

### L2 失败时怎么判

| 现象 | 大概率原因 |
|---|---|
| 队列里消息被消费了，但日志无 `[email-send]` | `messageType` 拼错。必须是 `EmailSend`（大小写敏感） |
| 日志报 `No message processor found for message type` | 同上，或 handler 未注册成 Spring bean |
| 日志报 `No EmailComposer registered for type` | `composerType` 拼错，或该 Composer 未被扫到（回看 L0.2 的数量） |
| 日志报 `bizKey.run is required` | bizKey 的键名错了，必须是 `run` |
| 消息反复重投最后进 DLQ | 看 `queue_message_log.error_json`，多半是 runId 不存在 |
| `email` 表有行但 `status = 0` | SendGrid 调用抛了 IOException，看日志 `Error sending email` |
| `email` 表有行但 `dedup_key` 为 null | handler 没设 dedupKey——不该发生，属实现问题 |

## L3 · 去重验证（本次改造的核心机制）

### 3.1 重复投递不会重发

**把 L2 那条消息原样再投一次。**

**看日志**，这次应该是：

```
[email-send] already delivered, skip: composerType=... dedupKey=manual-smoke-001
```

**再查一次库**：

```sql
SELECT count(*) FROM email WHERE dedup_key = 'manual-smoke-001';
```

**期望**：**仍然是 1**。你的邮箱也不该收到第二封。

这一条如果不成立，说明探针没生效——检查 `idx_email_dedup_key` 是否真的建好了（L0.1），以及第一次那行的 `status` 是不是 2xx（探针只认 200–299）。

### 3.2 换个 dedupKey 就会重发

把 `dedupKey` 改成 `manual-smoke-002`、其余不变再投。

**期望**：`email` 表多一行，你收到第二封。这证明跳过是**因为去重键相同**，而不是因为别的什么东西恰好挡住了。

## L6 · 重点场景：跨组织不塌陷

**这是本次改造出过 Critical 的地方，也是单元测试证明不了的一点。**

去重键 = `业务键 + 收件人`。位置通知最初的业务键不含组织维度，导致同一个人在两个组织下的两封邮件算出**相同的键**，第二封被探针当成"已投递"静默丢弃。已修复并有回归测试，但**测试只能证明业务键不同，证不了线上分发正确**。

**先找出这样的人**：

```sql
-- 跨多个组织的 PM
SELECT u.user_id, u.email, count(DISTINCT cg.organization_id) AS org_count
FROM "user" u
JOIN r_portfolio_user pu ON pu.user_id = u.user_id
JOIN company_group cg ON cg.company_group_id = pu.company_group_id
WHERE u.is_deleted = FALSE
GROUP BY u.user_id, u.email
HAVING count(DISTINCT cg.organization_id) > 1;

-- 管多家公司的 Company Admin
SELECT email, count(DISTINCT company_id) AS company_count
FROM "user" WHERE role_type = '2' AND is_deleted = FALSE
GROUP BY email HAVING count(DISTINCT company_id) > 1;
```

**触发 5.3 的位置通知后**：

```sql
SELECT receiver_email, count(*) AS 收到几封, array_agg(DISTINCT dedup_key) AS 各自的去重键
FROM email
WHERE email_type = 47 AND created_at > now() - interval '15 minutes'
GROUP BY receiver_email
HAVING count(*) > 1;
```

**期望**：上面查出的跨组织 PM / 多公司 CA，`收到几封` 应等于他的组织数 / 公司数，且 `各自的去重键` **互不相同**。

如果某人只收到一封、或多行共用同一个 dedup_key，说明组织维度没进业务键——那就是这个 Critical 复发了。

> 若 stage/uat 库里根本没有跨组织的人，这一级只能等生产数据验证，或临时造一条 `r_portfolio_user` 关联来模拟。

## 排障速查

| 现象 | 先看哪 |
|---|---|
| 消息发了没反应 | 队列前缀对不对；`onEmailQueue` 是否在拉消息；`messageType` 是否为 `EmailSend` |
| 全部邮件进 DLQ | 多半是路由断了——`getSupportedMessageType()` 与 `SqsMessageType.EmailSend` 必须字符串完全一致 |
| 某类邮件全失败、其它正常 | 该 Composer 的重建逻辑问题，看 `queue_message_log.error_json` 里的异常类型 |
| 邮件内容为空/缺公司名 | Composer 从持久化状态重建时读到空。月度邮件看 `run_snapshot` 是否还在（Stage-1 重投会先删后建） |
| 该发的没发、日志说 already delivered | 去重键撞了。用 `SELECT dedup_key, receiver_email FROM email WHERE ...` 看是不是两封合法邮件共用了一个键 |
| stage/uat 收不到但 `email` 表有行 | 看 `status`——白名单拒绝时不会走到 SendGrid，该消息会被判为不可重试并 ack |
