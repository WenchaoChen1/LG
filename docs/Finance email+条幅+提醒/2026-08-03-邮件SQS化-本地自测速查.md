# 邮件 SQS 化 · 本地自测速查

> 完整分级手册见 `2026-08-03-邮件发送SQS化-自测手册.md`，这份只管**本地跑通每条业务线**。
> 原则：**每条都用最小维度触发**（指定公司 / 组织），不跑全量。

---

## 先记住本地的三个事实

**1. 本地会真发邮件。**
白名单拦截只在 `stage` / `uat` 生效：

```java
if (environment.equals("stage") || environment.equals("uat")) { /* 拦截 */ }
```

本地 `cio.system.environment = ${app.stage} = dev`，**不在拦截范围内**。而本地连的是共享库，公司管理员、PM 都是真实邮箱。

→ **所有触发都必须带 `companyIds` / `companyId` 限定范围。** 不带就是全量（月度邮件约 1000 家公司）。

**2. 你的队列前缀是独立的。**
`name-prefix: lg-${app.env}-${app.stage}-`，`app.env` 是开发者名字。所以本地是 `lg-<你的名字>-dev-*`，**不会和 test 环境的应用抢消息**——这点可以放心。

启动后从日志确认实际前缀（别猜）：

```
Fixed scheduler initialization started, queueArn=arn:aws:sqs:us-east-1:xxx:lg-xxx-dev-scheduler-queue
```

**3. 本地要投的是你自己那套队列。**

| 用途 | 队列 |
|---|---|
| 触发业务跑批 | `lg-<你>-dev-scheduler-queue` |
| 二级扇出（观察用，不用手工投） | `lg-<你>-dev-benchmark-report-queue`、`lg-<你>-dev-benchmark-email-queue` |
| 直投单封邮件 | `lg-<你>-dev-email-queue` |
| 失败三次后 | `lg-<你>-dev-dlq-queue` |

## 先挑好"最小维度"的目标

```sql
-- 一家有财务数据的活跃公司（记下 company_id）
SELECT c.company_id, c.company
FROM company c
JOIN financial_normalization_current f ON f.company_id = c.company_id
WHERE c.company_status NOT IN (1, 6)
GROUP BY c.company_id, c.company
ORDER BY count(*) DESC LIMIT 5;

-- 这家公司的收件人是谁（确认会发给谁）
SELECT user_id, email, role_type FROM "user"
WHERE company_id = '<公司ID>' AND is_deleted = FALSE AND status != 4;

-- 这家公司属于哪个组合 / 组织
SELECT rcg.company_group_id, cg.name, cg.organization_id
FROM r_company_group rcg JOIN company_group cg ON cg.company_group_id = rcg.company_group_id
WHERE rcg.company_id = '<公司ID>' AND rcg.status = 0;
```

> 建议先把这家公司管理员的邮箱临时改成你自己的，测完改回来。这样即使发出去也只发给你。

## 三条业务线 · 最小维度触发

全部投 **`lg-<你>-dev-scheduler-queue`**。

### ① 季度报告 · 单公司

```json
{"messageType":"Scheduler","schedulerType":"QuarterlyBenchmarkReport","companyId":"<公司ID>","period":"2026Q1","triggeredBy":"selftest","uuid":"r1"}
```

> `companyId` 是**单值**（这条线不支持数组）。`period` 缺省则按日历推断当季。

**验证**：

```sql
-- run 建起来了？
SELECT id, period, status, created_at FROM financial_benchmark_report_run
ORDER BY created_at DESC LIMIT 1;

-- 只有这一家公司的 record？
SELECT company_id, status, attempt_count FROM financial_benchmark_report_record
WHERE run_id = '<上面的runId>';

-- 汇总邮件（SME 收件人来自配置 cio.benchmark-report.sme-email）
SELECT receiver_email, subject, status, dedup_key FROM email
WHERE email_type = 44 AND created_at > now() - interval '10 minutes';
```

**期望**：record 只有你指定的那一家；邮件 `dedup_key` 形如 `BENCHMARK_REPORT_SUCCESS_SUMMARY:<32位哈希>`，`status = 202`。

### ② 位置变化通知 · 指定公司子集

```json
{"messageType":"Scheduler","schedulerType":"BenchmarkPositionMonitor","companyIds":["<公司ID>"],"uuid":"p1"}
```

> 这条是**数组**。不合格的 id（已退出 / 无组合归属）会被自动跳过。

**验证**：

```sql
-- run + 本轮哪些公司真的触发了
SELECT id, phase, company_count, fired_count FROM financial_benchmark_position_run
ORDER BY created_at DESC LIMIT 1;

SELECT company_id, metric_id, diff_decision FROM financial_benchmark_position_run_snapshot
WHERE run_id = '<runId>' ORDER BY company_id;

-- 邮件：只有 diff_decision 属于触发类的公司相关方才该收到
SELECT receiver_email, subject, dedup_key FROM email
WHERE email_type = 47 AND created_at > now() - interval '10 minutes';

-- 横幅照常写入（本次未改，回归检查）
SELECT notify_type, count(*) FROM financial_benchmark_notify_alert
WHERE created_at > now() - interval '10 minutes' GROUP BY notify_type;
```

**期望**：触发类决策是 `INITIAL_FIRE` / `SOURCE_FLIPPED` / `PEER_DRIVEN_SHIFT` / `VALUE_AND_PEER_SHIFT` 四种之一；`SILENT_*` 和 `SKIP_NO_DATA` 的公司不该产生邮件。横幅 type 3/4/5 仍应写入。

### ③ 月度基准邮件 · 单公司 + 强制月度相位

```json
{"messageType":"Scheduler","schedulerType":"BenchmarkEmailDaily","companyIds":["<公司ID>"],"phase":"MONTHLY_25TH","manualTrigger":true,"uuid":"e1"}
```

> `companyIds` 是**本次新加的**（`f9c…` 那个提交）。此前这条线只能全量跑——本地自测等于给上千真实收件人发信。
> `manualTrigger:true` 绕过"同日同 phase 只跑一次"的幂等，所以可以反复投。
> `phase:"MONTHLY_25TH"` 让你任何一天都能跑 25 号的月度逻辑。

**先确认范围真的收窄了**：

```sql
SELECT id, phase, trigger_type, total_company_count, run_date
FROM financial_benchmark_email_run ORDER BY run_trigger_time DESC LIMIT 1;
```

**期望** `total_company_count` 等于你传的公司数。日志同时会打印：

```
[benchmark-email] SQS path planned, phase=MONTHLY_25TH triggerType=MANUAL asOfDate=null targetCompanies=1 runId=...
```

看到 `targetCompanies=ALL` 就是 `companyIds` 没解析到——检查是不是写成了字符串而非数组。

**再看两阶段扇出**：

```sql
-- Stage 1：每家公司一条
SELECT company_id, status, attempt_count FROM financial_benchmark_email_company_record
WHERE run_id = '<runId>';

-- Stage 2：涉及的组合（只有 PM 决策 FIRE 才会有）
SELECT portfolio_id, status FROM financial_benchmark_email_portfolio_record
WHERE run_id = '<runId>';

-- 邮件
SELECT receiver_email, subject, dedup_key, status FROM email
WHERE created_at > now() - interval '15 minutes' AND dedup_key LIKE 'BENCHMARK_MONTHLY%';
```

**期望**：record 走到 `COMPLETED`；run 最终 `status = COMPLETED`。

**复现历史某天**（可选）：加 `"asOfDate":"2026-06-25"`，会同时改变 run_date 和 worker 的取数基准日。

## 最小维度对照表

| 业务线 | 限定字段 | 类型 | 不带的后果 |
|---|---|---|---|
| 季度报告 | `companyId` | 单值字符串 | 全量公司 |
| 位置通知 | `companyIds` | 字符串数组 | 全量公司 |
| 月度邮件 | `companyIds` | 字符串数组 | **全量约 1000 家，真发信** |
| 月度邮件（时间） | `asOfDate` | `2026-06-25` | UTC 当天 |

## 不想跑业务跑批？直投单封邮件

这是验证管道最快的方式——跳过所有业务逻辑，收件人完全由你指定。投 **`lg-<你>-dev-email-queue`**：

```json
{"messageType":"EmailSend","queueName":"email-queue","composerType":"BENCHMARK_REPORT_SUCCESS_SUMMARY","bizKey":{"run":"<已有的报告runId>"},"recipientEmail":"<你自己的邮箱>","dedupKey":"local-001"}
```

日志应出现 `[email-send] delivered: ... dedupKey=local-001`。

**紧接着把同一条再投一次**，这次应该是：

```
[email-send] already delivered, skip: ... dedupKey=local-001
```

```sql
SELECT count(*) FROM email WHERE dedup_key = 'local-001';
```
**期望仍是 1**，且你不会收到第二封。这验证了本次改造的核心机制。

五种 `composerType` 各自的 `bizKey`：

| composerType | bizKey | 收件人字段 |
|---|---|---|
| `BENCHMARK_REPORT_SUCCESS_SUMMARY` | `{"run":"<runId>"}` | `recipientEmail` |
| `BENCHMARK_ENTRY_UPDATE` | `{"platform":"KeyBanc","edition":"2099","org":"<公司ID>"}` | `recipientUserId` |
| `BENCHMARK_POSITION_UPDATE` | `{"cid":"<公司ID>","org":"<公司ID>"}` | `recipientUserId` |
| `BENCHMARK_MONTHLY_COMPANY_ADMIN` | `{"run":"<runId>","cid":"<公司ID>"}` | `recipientUserId` |
| `BENCHMARK_MONTHLY_PORTFOLIO_MANAGER` | `{"run":"<runId>","pid":"<组合ID>"}` | `recipientUserId` |

> 两个收件人字段**恰好填一个**，都填或都不填会被判非法（一次 ack、不重试）。

## 第四条链路：外部基准更新

它不由 SQS 触发，走的是页面保存。本地起前端或直接调接口，**新增一个全新的 platform-edition**（如 `KeyBanc` / `2099`）：

```sql
SELECT receiver_email, subject, dedup_key FROM email
WHERE email_type = 46 AND created_at > now() - interval '10 minutes'
ORDER BY receiver_email;
```

**期望**：Company Admin 按 **(人 × 公司)** 各一封——同一个人管两家公司应有**两封**，`dedup_key` 互不相同、正文里的公司名不同。这是曾经出过 Critical 的地方（去重键不含组织维度会把两封塌成一封）。

## 排错速查

| 现象 | 看这里 |
|---|---|
| 消息投了没反应 | 队列前缀是不是你自己那套（`lg-<你的名字>-dev-`）；应用是否真在跑；`messageType` 大小写 |
| `Unknown schedule type` | `schedulerType` 拼错，必须严格驼峰：`QuarterlyBenchmarkReport` / `BenchmarkPositionMonitor` / `BenchmarkEmailDaily` |
| 月度邮件第二次投没反应 | 少了 `manualTrigger:true`——SCHEDULED 同日同 phase 幂等，第二次只返回第一次的 runId 什么都不做 |
| `targetCompanies=ALL` | `companyIds` 写成了字符串，必须是数组 `["id"]` |
| run 建了但没邮件 | 该公司本轮决策是 `SILENT_*` / `SKIP_NO_DATA`，本来就不发。查 `run_snapshot` 的 `diff_decision` |
| 邮件进 DLQ | 看 `queue_message_log.error_json`；多半是 bizKey 里的 id 不存在 |
| `email` 表有行但 `status=0` | SendGrid 调用失败，看日志 `Error sending email`（本地网络 / API Key） |
| 收不到但表里 `status=202` | SendGrid 已接受，去垃圾箱看；或收件人邮箱不是你以为的那个 |

## 收尾

测完把临时改过的邮箱改回去：

```sql
-- 如果你改过收件人邮箱做定向测试
UPDATE "user" SET email = '<原邮箱>' WHERE user_id = '<userId>';
```

本地产生的测试数据（run / record / email 行）留着不影响其它人——你的队列前缀是独立的，但**数据库是共享的**，所以清理一下更礼貌：

```sql
DELETE FROM email WHERE dedup_key LIKE 'local-%';
```
