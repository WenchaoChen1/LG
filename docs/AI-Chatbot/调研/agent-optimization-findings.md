### 0.1 任务书中被推翻的三个数字（重要）

| 任务书写法 | 实际 | 影响 |
|---|---|---|
| 系统提示词「337 行 / ~39KB」 | 那是**源文件**（含大量中文注释）。**渲染给模型的系统提示 17,520 字符**；工具 schema 序列化 **26,663 字符**。固定前缀合计 ≈ **28.8k token**（与实测 `max_cached = 28,804` 吻合） | **长上下文的大头是工具 schema（占 60%），不是系统提示** —— 直接翻转了 A3 的优化落点 |
| 「prompt cache 命中率未知」 | `usage_cached_tokens` 列已存在且在写，**现在就能算** | 埋点缺口在别处（见下） |
| 「缓存命中率 0.8%」 | **统计口径假象**。caching 于 **2026-09-04** 才接进流式 ReAct 路径（`36d088c8` + `d915761a`），此前 245 次调用 cached 恒为 0 是**结构性的**。接线后有效样本仅 **9 次**（2 次命中，平均 cached 19,203） | **当前无可用命中率基线，需重新采集**。凡引用 0.8% 处一律作废 |

### 0.2 知识库覆盖率：42.4% 已作废，按周拆开是 30.6% → 66.7%

**功能一直在演进，全样本聚合会把改之前的数据混进来。** 按周拆：

| 周 | 轮次 | 查了知识库 | 覆盖率 |
|---|---|---|---|
| 07-20 | 62 | 19 | **30.6%** |
| 07-27 | 6 | 3 | 50% |
| 08-03 | 6 | 6 | **100%** |
| 08-10 | 16 | 11 | **68.8%** |
| 08-17 / 08-31 | 各 1 | 0 | 0% |

分界线正好是两次针对性修复：

| 日期 | 提交 |
|---|---|
| **2026-07-27** | `c27d05b3` feat(chatbot): **proactive KB search** + surface platform/document data conflicts |
| **2026-07-28** | `6bb3025f` fix(chatbot): **search the knowledge base even when no company data is fetched** |

```
修复前（07-20 那周，62 轮）：19/62 = 30.6%
修复后（07-28 起，30 轮）  ：20/30 = 66.7%
8 月合计（24 轮）          ：17/24 = 70.8%
```

**42.4% 里有 67% 的样本（62/92）来自修复之前**——拿它说"提示词驱动只有 42% 遵循率"，等于用改之前的数据去证明改之后的问题。

**修正后的口径与论点强度**：

1. 现行覆盖率 **66.7%**（修复后 30 轮），不是 42.4%；
2. **"提示词驱动不保证 100%"这个论点仍成立，但强度要降**——从"最强措辞只换来 42%"降到"**修了两次提示词才把 30% 拉到 67%，且仍未到 100%**"；
3. ⚠️ 剩下那三分之一里有一部分是**合理分工**：08-10 那周 16 轮中有 12 轮来自一个 playbook 测试会话（全是"how do we run our 401k plan"式的方法论问题），模型判定走 `search_playbooks` 而非 `search_knowledge_base`——**提示词允许这种分工，不算违规**。剔掉后真实覆盖率更高。

## 1. 五项主建议

> 排序依据：任务书拍板的优先级（准确率 > 延迟 > 成本 > 并发）+ 实测证据强度 + 实施成本。
> **形状**：第 1 条最该做；第 2~4 条都是 **S 成本的确定收益**；第 5 条收益最大但有未解阻塞。
> ⚠️ 本节按**重要性**排，§3 按**施工顺序**排，两个口径不同——例如埋点在本节是第 3 位，在 §3 里是 P0。

| # | 建议 | 核心依据 | 预期收益 | 成本 |
|---|---|---|---|---|
| **1** | **知识库检索改为结构化前置预检**（A6） | 提示词里全文措辞最强的一条硬命令（"一律调一次"+ 逐条堵死三个借口），**修了两次提示词才把覆盖率从 30.6% 拉到 66.7%，且仍未到 100%**（见 §0.2）。这说明问题不在措辞而在机制——软约束换不来确定性 | 覆盖率 66.7% → 100%；顺带缩短提示词中部约 20 行 | M |
| **2** | **TTFT 拓扑并行包**（B1 + B3 + B4） | guard 审的是**输入**、init/file_gate/rewrite **不产生任何用户可见 token** → 可做**零泄漏**并发；`detect_language` 的消费点在 retrieve 而非 init 出口，await 点可后移；建流到第一张卡片之间界面**空白 7.2s**。三项都是纯拓扑 / 并发改动，不碰提示词、不动任何产品语义 | 省 **~2.0s**（B1 保守版）/ **~3.9s**（B1 激进版）；另消除空白期。**84% 的轮次受益**。⚠️ 两项并行**不叠加**，算法见 §1.1 | **S** |
| **3** | **补两处埋点**（D/E） | `ttft_ms` 今天**没有任何一列直接存**，只能跨两表 + `DISTINCT ON` 拼且只得下界——**没它无法验收 #2**；`cache_write_tokens` 被丢弃导致**分不清"没写入"与"写了没读到"**——**没它无法验收 #4** | 让 #2 / #4 可干净验收，并解锁二期（1h TTL / 拆稳定块 / 数值接地校验） | S（前者零 DDL） |
| **4** | **`session_id` 粘性路由**（C1 ①） | 缓存是**端点本地的**（sonnet-5 / opus-5 在 OpenRouter 有 10 / 11 个上游端点）。OpenRouter 有隐式粘性、但**滞后触发**——不设 `session_id` 时要先观察到一次命中才开始粘，于是每条会话都要先耗掉一个冷启动窗口。retrieve 每轮 2.70 次调用，**轮内命中确定存在**，粘性是它能否落袋的前提。**1h TTL、拆稳定块、rewrite 开缓存均不在本条内**（见 §3.0） | 成本 **−33%**（每轮 $0.187 → $0.125） | **S** |
| **5** | **rewrite 去工具化 + 公司槽位程序化**（A1 + A8 + B2 合并） | rewrite 独占 TTFT 的 **32%**，而它 70% 的篇幅在做三件**真值在数据库里**的事；`init` 早已加载公司清单、`company_cache` 存的就是含 `close_month` 的全字段 record。仓库**已有做对了的样板**（`company_infer_prompt` 的序号式） | 省 **2–3.5s**；消除"上游派活/编造 id/日历月冒充 close month"三类错误 | M（含 `rewrite_scenarios` 改造则 L） |

### 1.1 TTFT 能压到多少（逐段算清，不要简单相加）

**现状**：`guard 2.0 → init 2.0 → rewrite 5.2 → retrieve TTFB 7.2 = 16.4s`

| 组合 | 算法 | TTFT | 相对现在      |
|---|---|---|-----------|
| 只做 guard ∥ init（B1 保守版） | `max(2.0, 2.0) + 5.2 + 7.2` | 14.4s | −2.0s     |
| 只做 `detect_language` await 后移（B3） | `2.0 + 0.1 + 5.2 + 7.2` | 14.5s | −1.9s     |
| **两个都做（= #2 保守版）** | `max(2.0, 0.1) + 5.2 + 7.2` | **14.4s** | **−2.0s** |
| #2 保守版 **+ #5 rewrite 去工具化** | `2.0 + (5.2→1.7~3.2) + 7.2` | **11.0~12.4s** | −4.0~5.4s |
| **B1 激进版 + #5** | `max(2.0, 0.1+1.7~3.2) + 7.2` | **~9.0~10.4s** | −6.0~7.4s |

⚠️ **两项并行不叠加**：B3 让 init 从 2.0s 掉到 ~0.1s（Java IO 已被 `company_service` 的 5 分钟缓存吃掉，剩下的就是 `detect_language` 这一次 haiku 调用）之后，保守版里 `max(guard, init)` 仍被 guard 的 2.0s 卡住——B3 省下的 1.9s 被 guard 吃掉了。**报告初稿把两项相加得出"省 3.5–4.0s"，是重复计算。**

要拿到 ~3.9s，必须上 **B1 激进版**：guard 一路并行到 **retrieve 入口**（而非在 file_gate 前 join），把它的 2.0s 完全藏进 `init + file_gate + rewrite` 里。代价是 B 节标出的副作用——**被拦截的轮次会闪一张 file_gate 的进度卡片**，必须先做卡片抑制。

⚠️ **前置步骤卡片（B4）不产生任何毫秒收益**，它只改善体感（消除建流到第一张卡片之间的 7.2s 空白）。不要把它计入上表任何一行。

**结论**：单靠 #2 到 14.4s；要进 10s 量级必须叠加 #5（而 #5 有未解阻塞）；要进 10s 以内还需 B1 激进版。三者都不触碰模型选择、不动任何产品语义。

## 2. 哪些建议互相印证，哪些互相冲突

四个维度是分头调研的、互相不知道对方在写什么。结果有三条建议被**不同维度各自撞上**（说明它可信），也有三处建议**互相冲突或有先后依赖**（说明不能同时闷头做）。

### 2.1 互相印证：不同维度指向同一改动

| 改动 | 谁提出 | 各自理由 |
|---|---|---|
| **rewrite 去工具化 + 程序化注入公司表** | A1（准确率）· A8（准确率）· B2（延迟） | A：输出"一句话"的形态制造了"上游派活"错误；A8：槽位真值在 DB 里；B：独占 TTFT 32% |
| **工具返回体量上限** | A7（准确率）· C2（成本）· B5（延迟） | A：挤压兄弟结果 + 把红线推远；C：P95 成本封顶；B：二次 prefill 成本 |

### 2.2 互相冲突：三处必须排先后

**① 凡是改系统提示词的动作，合并成一批上线**
改 system prompt 任一字节即整体击穿缓存前缀。C1 的「拆稳定块 + 易变尾」、A3 的指标目录移位、A6 的检索规则缩短都属此列——分三次做就击穿三次。**合并成一批、选低峰期上线。**

**② A7/B5「返回体量上限」 vs C2「ContextEditingMiddleware」——后者暂缓**
C2 明确指出：`ContextEditingMiddleware` 清理工具结果会**改写 message 前缀 → `cache_conversation` 断点失效 → 下一跳重付 1.25x 写入**（Anthropic 官方："Tool result clearing invalidates cached prompt prefixes"），且默认 `trigger=100_000` 对我们（单次均 28k）永不触发。
→ **先做源头截断（A7/B5），不做事后清理（C2）**。C2 等 C1 收益落袋后再评估。

**③ A7「截断」 vs B5「先别截断」——按风险分两步**
A7 主张立刻加上限（78,082 字符是 Anthropic 自家 Claude Code 25,000 token 上限的约 3 倍）；B5 提醒裁剪=丢数据，与项目"宁多提不少提"的既有取向冲突。
→ **合并方案**：第一步只做 ① benchmark 单独收紧 timeout（30s → 10s）+ ② 把返回体大小埋进 span；第二步等分布数据出来后再定阈值，且**必须按结构裁剪**（按公司完整块，绝不切半个公司/半个月）+ **带引导式说明**（"已截断到 N 家 × M 月，要更早月份请缩小公司范围再调一次"），而不是裸 `truncated: true`。

## 3. 全量建议清单（按实施顺序）

### P0 — 前置（做完才能验收后面所有东西）

| # | 改动                                                                                                                                                                                                                                                                                                                                                                                                                              | 落点 | 成本 |
|---|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|---|---|
| P0-1 | **把「每轮对话只有一个值」的指标写进 `ai_trace.attributes`**（该 JSONB 列已存在且基本空着）：`ttft_ms` 首 token 耗时 / `tool_call_count` 本轮工具调用次数 / `budget_exhausted` 是否撞上轮次上限 / `merged_count` 去重合并次数 / `turn_superseded` 是否被新轮取代 / `agent_mode`。<br>这些值既不属于某一次 LLM 调用（放不进 `ai_llm_call_log`）、也不属于整个会话（放不进 `ai_chatbot_thread`），正好落在一轮对话这一层——而一条 `ai_trace`（`name='chatbot.chat'`）就是一轮。现在要算它们得跨表 JOIN，写进去后一句 `attributes->>'ttft_ms'` 即得，且 `ttft_ms` 能拿到真值而非下界 | `chatbot/application/sse_provider.py` 的 `_traced_turn`、`retrieval_agent.py` 收尾 | S（**零 DDL**） |

### P1 — 高收益主体

| # | 改动 | 收益 | 成本 |
|---|---|---|---|
| P1-1 | **知识库结构化前置预检**：进入 agent 前进程内直调一次 `search_service.recall`，结果作为预置 ToolMessage 注入；工具仍保留绑定；`_RULES` 检索段大幅缩短 | 覆盖率 66.7% → 100% | M |
| P1-2 | **拓扑并行**：`build.py` 中 `input_guard ∥ init`；`detect_language` 的 await 点后移到 retrieve 入口（ContextVar 传句柄） | 省 ~3.5–4.0s | S |

#### 3.0 四个子项的依赖关系（不要并列做）

| 措施 | 对轮内命中（−33%） | 对跨轮复用（−72%） |
|---|---|---|
| ① `session_id` 粘性路由 | ✅ **必需** | ✅ 必需 |
| ② rewrite 开 `cache_system` | ❌ **几乎无收益，且做完 #5 后变净亏**（见下） | ⚠️ 取决于提问间隔，未知 |
| ③ system 断点 1h TTL | ❌ 无关 | ✅ **必需**（5 分钟 TTL 下跨轮基本不可能） |
| ④ 系统提示拆稳定块 + 易变尾 | ❌ **无贡献** | ✅ 有贡献 |

**② rewrite 开 `cache_system` 已从主建议中移除**，理由是实测账算不过来：

rewrite 每轮 LLM 调用数分布（66 轮）：**1 次 = 48 轮（73%）**、2 次 = 17 轮、3 次 = 1 轮。**73% 的轮次只调一次，根本不存在轮内复用**——缓存写进去没人读。

按写 1.25× / 读 0.1× 、前缀 ~10,030 token 折算：

| | 不开缓存 | 开缓存 |
|---|---|---|
| 48 个单调用轮 | 48.0 | 48 × 1.25 = **60.0**（净亏 12） |
| 17 个双调用轮 | 34.0 | 17 × (1.25+0.1) = 22.95（省 11.05） |
| 1 个三调用轮 | 3.0 | 1.45（省 1.55） |
| **合计** | **85.0** | **84.4** |

净收益 **0.7%**；rewrite 只占总成本 11.9%，折算到全局约 **0.08%**，等于白干。

**且与 #5 直接冲突**：#5（rewrite 去工具化）会把那 27% 的多调用轮全部消灭（去掉工具后恒定 1 次调用），届时轮内复用为 0、每轮都在付 1.25× 写入而无读取摊销——rewrite 前缀占其输入 89%，**该节点成本将上涨约 22%**。

**要靠跨轮救回来**，需满足"提问连续、间隔在 TTL 内"：5 分钟 TTL 下连续 2 轮即回本（1.35 vs 2.0，省 32%）；1h TTL 写变 2.0×，需连续 3 轮。但"同一会话相邻两轮的时间间隔"属于**用户行为数据**，开发库测不出、生产上未知。

→ **处置：降为条件项。** 先在生产上量出相邻轮间隔分布，只有当相当比例落在 TTL 内时才开；而且**必须在 #5 之前决策**——做了 #5 它就只剩跨轮这一条路。

**为什么 ④ 对轮内没用**：一轮内那 2.70 次调用，`end_type` / `use_playbook` / `question_language` / 日期**四个变量全是常量**（身份固定、开关进图前定死、语言 init 判一次整轮沿用），所以同一轮的所有调用共享**一模一样**的系统提示，碎片化一点都碰不到它。

**碎片化的真实规模**：同时存活的缓存条目原为 `end_type(2) × use_playbook(2) × 语言(N)`，**但 2026-09-17 产品决定 playbook 一直放开**（`use_playbook` 恒 True、不再随轮变化），故降为 **`end_type(2) × 语言(N)`**——碎片直接砍半，且工具集变成完全静态。

⚠️ **不要写成"× 天数"**——缓存 TTL 只有 5 分钟 / 1 小时，条目活不过一天，日期换不换都轮不到它失效，日期因子实际上**不产生任何碎片**。

→ **施工顺序：① + ② 先上（拿轮内），③ 再上（开跨轮），④ 最后（此时碎片化才开始吃掉 ③ 的收益）。** 报告早期版本把四项并列写，暗示同等重要，是错的。

#### 3.1 `session_id` 粘性路由（P1-4 ①，方案已更正）

**原方案 `provider.order` 锁路由已被否决**，改用 OpenRouter 原生的会话亲和机制。

> **先纠正一个容易夸大的说法**：OpenRouter **默认就有隐式粘性**，不是每次调用都在 10~11 个端点里随机乱跳。但它是**滞后触发**的——不设 `session_id` 时，系统"只在检测到缓存命中之后"才开始粘。而要产生命中，就得先偶然落回写入缓存的那个端点。
> 所以缺口不是"全程乱跳"，而是每条会话开头的**冷启动窗口**：这期间的请求可能反复写入不同端点、各付一次 1.25× 写入费，直到偶然命中一次才粘住。设 `session_id` 的价值就是把粘性从"命中之后"提前到"**任意一次成功请求之后**"，消掉这个窗口。
> 在我们的量级上这并非小事——retrieve 每轮平均只有 **2.70 次**调用，冷启动哪怕只浪费 1 次，占比就已经很高。

| 项 | 内容 |
|---|---|
| 参数 | 请求体顶层 `session_id`，或 HTTP 头 `x-session-id`（≤256 字符） |
| 生效时机 | 设了就在**任意一次成功请求后**生效，不用等观察到缓存命中（不设时系统只在检测到命中后才惰性粘住，慢一拍） |
| 过期 | **10 分钟**无活动，每次成功请求重置 |
| 故障切换 | 官方原文：*"If the sticky provider becomes unavailable, OpenRouter automatically falls back to the next-best provider."* |

**为什么不用 `provider.order`**：

| | `provider.order` | `session_id` |
|---|---|---|
| 机制 | 静态优先级列表 | 按会话的动态亲和 |
| 作用范围 | **全局**——所有请求都不再负载均衡 | 只在同一会话内粘住，**跨会话仍负载均衡** |
| 故障切换 | 靠 `allow_fallbacks` | 内建自动切换 |
| 设计意图 | 通用路由偏好 | **就是为缓存亲和设计的** |

`provider.order` 是为了让缓存命中而把全平台的负载均衡关掉，代价远大于收益。

**取值**：用 `thread_id`——同一会话的所有轮次粘同一端点。

**⚠️ 实现约束（不要走捷径）**：`session_id` 是**每请求不同的值**，而 `kernel/config.py:141` 的 `request_extra_body` 是**静态配置**。技术上可以经 `TextRequest.extra_kwargs` 透传 `{"extra_body": {"session_id": ...}}`，但**按本仓库自己定的晋升判据不该这么做**——`capabilities/base.py:55-66` 写明：「某个用法在业务侧出现 ≥2 处、或者让业务代码认识了 provider 的报文结构，满足任一条就该提升为一等字段」。`session_id` 两条全中（retrieve + rewrite 两轨都要用；手搓 wire 结构）。
→ **正确做法**：给 `TextRequest` 加一等字段，`create_agent` / `DBRouterChatModel` 加同名参数透传，由 openai_compat 翻成 wire 格式。与 `reasoning_effort` 完全同构（该字段 2026-09 正是从"散在五处业务代码手搓 extra_body"提升上来的，注释里点名这是"慎用"要防的情形），有现成样板可抄。

**⚠️ 风险：两个时间窗错配**。粘性会话 **10 分钟**无活动过期，而 Anthropic 缓存 TTL 默认 **5 分钟**。
- **轮内**（2.70 次调用相隔几秒）稳赚——这本就是缓存命中的主战场；
- **跨轮**取决于用户思考打字的间隔：超 5 分钟缓存先凉，粘性再准也无用；
- 若同时上 **1h TTL**，10 分钟的粘性窗口**反而成为新短板**——缓存还在、但已经粘不住原端点了。两项要一起评估，不要各自单独调优。
| P1-5 | **rewrite 去工具化 + 公司槽位程序化 + 输出改结构化槽位** | 省 2–3.5s + 消三类错误 | M~L |

#### P2-8 补充：免责翻译的三种方案与取舍

**现状**（比直觉多一层）：`disclaimer_node.py` 已有进程内缓存 `_translation_cache: dict[tuple[str, str], str]`，key 是 **`(语言, 英文原文)`** —— 这个 key 设计已自带失效：**改了英文文案，key 就变了，旧译文不会被命中，无需手动清空**。

**它的真实缺陷**：进程内，每次重启/发版全空，每个语言要重新翻一次。

**实测量级**：disclaimer 共 **9 次**调用（92 轮里只有 9 轮非英文提问），成本合计 **$0.004**（$0.00046/次），平均 1,789 ms。⚠️ **不在 TTFT 路径上**——disclaimer 在 retrieve 之后，答案早已流完，这 1.8s 是尾部延迟。

| | 运行时翻译 + 内存缓存（现状） | 建表持久化 | **译文入代码（推荐）** |
|---|---|---|---|
| LLM 调用 | 每进程每语言 1 次 | 每语言 1 次（全局） | **0** |
| 尾部延迟 | 首次 1.8s | 首次 1.8s | **0** |
| 迁移 | 无 | **要一次人工迁移** | 无 |
| 改文案会不会给错译文 | 不会（key 含原文） | **会，除非按原文 hash 做 key** | **不会——译文与原文同文件，改一个必然看到另一个** |
| 未预置的语言 | 自动翻 | 自动翻 | **回退到现有运行时翻译 + 内存缓存** |

**关键是最后一行**：译文入代码不是替代方案，是**在现有机制前面加一层常量表**。命中常量 → 零成本；未命中 → 走现在的逻辑，两套共存。

**⚠️ 明确不建议建表**：收益（每次发版省几次 1.8s 尾部延迟 + 几分钱）撑不起一次人工迁移 + 一个新的一致性不变式。尤其「改文案时同步清空该表」是**会被忘掉的手动不变式**——改文案的人未必知道有张表要清，而旧译文与新英文原文语义不一致，在合规文案上是实际风险。若将来非英文语言真的多起来再考虑持久化，**届时按英文原文 hash 做 key（自动失效），不要用手动清空**。

**实际语言分布**：实测只有 zh 与 en 两种，而 en 根本不需要翻译（`en`/空直接给英文原文）。所以常量表只需先补 zh 的三段。

#### P2-1 补充：孤儿流为什么「先测再修」

调研初稿写的是「修每次滚动发布都会命中的用户可见挂死」，**这个说法夸大了**，已更正。要产生孤儿流必须同时满足三个条件：

1. 有流**正在生成**（进程在往 Redis 写帧）；
2. 进程**非优雅地**死掉——优雅关闭时 asyncio 会 cancel 任务，`finally` 照常执行、落 partial、终结帧照发。只有 SIGKILL / OOM / 宽限期到点被硬杀才会留下没有终结帧的残帧；
3. 且**有客户端正订阅着**这条流。

三者叠加，概率不高。

⚠️ **初稿引用的「实测 RUNNING 2/94 ≈ 2%」不能作为证据**——开发库里的重启是开发者自己按 Ctrl+C，属于本报告 §0 已剔除的"用户行为污染"那一类数据。

**唯一不能排除的情形**：轮次平均 39.4s、最长 204.6s，若容器 `stopGracePeriod` 是常见的 30s，则发布时**多数在跑的轮次都会被硬杀**。但部署配置（宽限期、是否优雅关闭）本次**未核实**，不能据此认定。

**结论：先观测，达到阈值再修。** 生产上跑一段时间看下面这条，有量再动手——为一个尚未证明会发生的问题写生产者心跳属于过度设计（违反项目 YAGNI 原则）。

```sql
SELECT count(*) FROM ai_trace
WHERE name = 'chatbot.chat' AND status = 'RUNNING'
  AND started_at < now() - interval '10 minutes';
```

真要修时的方案仍然成立：`sse:alive:{id}` 短 TTL 生产者心跳（按秒节流续期）+ `/subscribe` 在「无新帧 + alive 消失 + 无终结帧」时以 error 关流。

## 4. 不建议做的事

> 这一节与推荐同等重要。以下每条都是**检索到了、但对我们不适用**的做法。

### 4.1 被数据直接否掉

| 做法 | 为什么不做 |
|---|---|
| 用滑窗摘要 / 分层记忆替换固定 5 条历史窗口 | 实测历史 + 本轮问题只占单次输入 **2.6%**（29,565 中的 761）。压到 0 也省不过缓存修复的 1/20，还要多付一次 LLM 调用 + 摘要漂移风险 |
| 为省钱合并/砍掉 guard、detect_language、title、file_gate、disclaimer 五类小调用 | 五类合计 **1.07%** 成本。且 Haiku 4.5 的最小可缓存长度是 **4,096 token**，它们输入 200~1,347，物理上不可能缓存。（延迟维度另论——那里它们是主战场） |
| 调整 `_MAX_ITERS=6` | 实测 93.5% 的轮次 ≤3 轮工具、97.8% ≤4 轮，预算耗尽路径触发率 ≤1.1%。**真正无界的是墙钟不是轮数** |
| 删除 `get_chat_history` | 0 调用**在开发样本上无法定性**——开发库里几乎没有指代/翻译/总结类提问，而这本身是开发行为的产物，不能据此判断是"不需要"还是"提示词没驱动起来"。证据不足即不删。它反而是有用的报警器（一旦开始被大量调用 = 历史窗口不够用了）。需生产数据复查后再定 |

### 4.2 机制上不适用

| 做法 | 为什么不做 |
|---|---|
| 换 `ToolCallLimitMiddleware` | 实装源码：`exit_behavior='end'` 遇到**并行 tool_call 直接抛 `NotImplementedError`**——而我们确有并行调用（4 个同参 benchmark 打爆上游是实证） |
| 换 `ModelCallLimitMiddleware` | 收尾走合成 AIMessage + `jump_to: end`，**不经 `StreamEmitter`**，用户在预算耗尽时一个 token 都收不到 |
| 换掉手写的同参去重（含 `CachePolicy`） | 业界现有最接近的提案（Haystack #11588）**只缓存已完成结果，没有 in-flight single-flight**——而那恰恰是拦住 4 路并发的唯一手段。我们的实现比它强 |
| LangGraph `multitask_strategy` | 官方原文：*"It is not available in the LangGraph open source framework"* |
| Anthropic 服务端 context editing | 需 beta 头，社区多处报告 OpenRouter 返回 400。且无必要——LangChain 1.2.18 已内置客户端等价实现 |
| 为并行工具调用引入幂等键 / verify-before-retry | 整套机制针对**有副作用的写操作**，我们 10 个工具全只读，没有落点 |
| 迁 OpenTelemetry GenAI 语义约定 | 截至 2026-05 状态仍是 **Development**，属性名还会变；我们三张表已覆盖核心属性 |
| 把 `/subscribe` 轮询换成 Redis pub/sub | `broker.py` docstring 已写明选轮询正是为规避"回放与订阅之间丢帧"的竞态。换过去是把已解决的竞态重新引进来 |

### 4.3 方向性错误（照搬会做反）

| 做法 | 为什么不做 |
|---|---|
| 引入 Self-RAG / Adaptive-RAG 式"是否需要检索"分类器 | 2025 自适应检索共识优化的是"省掉无用检索的开销"，而我们的知识库检索是**进程内直调、空结果零代价**（均返回 2,585 字符，最小的工具之一）。它优化的变量在我们这里 ≈0，牺牲的变量（漏检）是我们的首要风险 |
| 把全部提示词英化 | 唯一相关实测（arXiv 2502.09331，35 语言）恰恰说 **instruction 部件语言最不敏感**，而我们的提示词几乎全是 instruction、context 与 output 已是英文——**现状就是该文推荐的配置**。反向成本确定为 L（44k 字符重写 + 守卫测试大面积失效 + 缓存前缀整体击穿） |
| 事后中断式输出审核（NeMo `stream_first`） | 我们的 guard 是**输入**侧，能做零泄漏并发，没必要引入"先泄漏后撤回"的代价 |
| 推测性预调取数工具 | 要带用户 token 打 Java 网关，猜错 = 白打请求 + 审计噪音，参数还依赖 rewrite 产物；低风险的两个已被 5 分钟缓存覆盖 |
| 事后 LLM verifier 做数字校验 | 三重否决：多一次串行 LLM 跳打在已 7.2s 的 TTFB 上；低成本方案依赖蒸馏专用模型（拍板 3 排除）；不建评测集 → 阈值无从调校，上线即盲飞 |
| 给 `get_financials.metrics` 硬枚举 | 31 项指标随 Java 侧演进，硬枚举一旦滞后新指标**根本传不进去**。只对 LG 自有封闭集（`benchmark_sources` 4 个、benchmark `metrics` 6 个）硬化 |

### 4.4 总纲（本次最重要的一条方法论结论）

> **不要继续加强提示词措辞来提高规则遵循率。**
>
> 渲染后的提示词已有近 100 条硬命令（绝不×56、红线×12、⚠×13、必须×8、不得×7、严禁×2）。知识库那条已经是全文最强措辞，**修了两次提示词才把覆盖率从 30.6% 拉到 66.7%，仍未到 100%**（见 §0.2）。
>
> ⚠️ **这条总纲要软化**：那两次修改确实把覆盖率翻了一倍多，所以**措辞不是无效的**——它的问题是**换不来确定性**。准确的表述是：<br>「**凡是必须 100% 发生的动作，靠提示词只能逼近、不能保证。这类诉求应优先找结构化落点（程序化注入 / 预置结果 / 尾部重述）；提示词加规则是够用但不够格的手段，且加得越多、已有红线的相对强度越被稀释。**」
>
> **所有"必须做某事"的诉求都应优先寻找结构化落点（程序化注入 / 预置结果 / 尾部重述），提示词加规则是最后手段。**

## 6. 验证方式总览（不依赖评测集）

| 层 | 手段 | 能抓什么 | 天花板 |
|---|---|---|---|
| 契约测试 | 提示词渲染断言、工具绑定同源、指标名跨源一致、前缀 hash 快照 | 文本层面的漂移、schema drift、无声击穿缓存 | **抓不到"规则还在、但模型不再遵守"**（知识库覆盖率那类问题） |
| 确定性单测 | 公司匹配函数、截断逻辑、去重不变式、deadline 短路 | 纯逻辑，可 100% 覆盖 | 只覆盖程序化部分 |
| 线上代理指标 | 5 条 SQL（工具分布漂移 / `result_char_count` 异常 / `finish_reason` 分布 / 缓存命中 / 每轮调用数分布）+ 新增 `ungrounded_number_count` | "有事发生"的报警 | 只说有事、不说是什么；**n=94 太小，现在不能接自动告警**。用户行为类指标（中断率 / 重新生成率 / 语言分布）已剔除，见 §0 |
| 小样本对照 | 固定 15~20 条真实历史问题，改动前后 diff **轨迹**（调了哪些工具、什么参数、几轮）而非散文 | 行为层面的回归 | 成本：20 题 × 36.1s + 真金白银，只在大改时跑 |

**更省的替代**：`ai_llm_tool_call_log` 已存 `tool_args` 与 `tool_result` 全文，改动上线后**直接对比"上线前一周 vs 后一周"的生产流量**即可——零重放成本、样本还是真实分布。
