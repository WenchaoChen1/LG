## 节点现状（参照系）

    START → input_guard      haiku   输入合规审核（fail-closed，最多 3 次尝试）
          → init             haiku   语言检测 ∥ 聊天历史 5 条 ∥ 公司列表 / portfolio 全集 / 用户信息（并发）

## 一、能力全景（按节点聚合）

> 按「节点现状」的顺序逐节点列出：**该节点当前承担、或本应承担的能力**。不属于任何节点的（检索链路、工具自身、会话与流、全局运维、前端）单独成组。
>
> 已具备、以及状态为 ⛔（明确不做）的一律记「—」；「**待评估**」= 还没判断要不要做、做成什么样，谈不上工时。

### `input_guard` — 输入合规审核

| 功能点 | 功能描述 | 状态 | 我们的实际情况 | 预估工时 |
|---|---|---|---|---|
| 输入合规检查 | 在处理前审核用户问题是否违规，违规则中止 | ✅ | 九类违禁审核，fail-closed | — |
| 合规检查与主链并行 | 审核与主流程同时起跑，而非串行阻塞（OpenAI Agents SDK 的默认行为） | ❌ | 我们是串行前置，每轮固定多等约 2s | S |

### `init` — 上下文预取

| 功能点 | 功能描述 | 状态 | 我们的实际情况 | 预估工时 |
|---|---|---|---|---|
| 应答语言检测与控制 | 判断用户用什么语言提问，答案与免责声明跟随该语言 | ✅ | 判定语言码，取数轨与免责节点均跟随 | — |
| 加载聊天历史 | 把最近若干轮对话带进本轮上下文 | ✅ | 按父链取近 5 条 | — |
| 会话锚点注入 | 把上一次**实际取数用的**条件（哪家公司、哪个期间、哪个文件）由程序写进上下文，而非指望模型自己想起来去翻历史 | ❌ | 无。`get_chat_history` 工具实测 **0 调用**——模型感知不到自己缺这个信息，遇到指代缺失会直接猜。⚠️ 前提是生产数据先证明指代类提问确实存在（开发库 68 条提问里只有 1 条命中指代词，但开发库的用户就是开发者，不作数） | M |
| 跨会话长期记忆（自动抽取事实） | 把对话里出现的事实自动抽出来存库，下次对话检索回填 | ⛔ | 无；已评估，见第二章 | — |
| 跨会话偏好 / 口径记忆 | 记住用户惯用的口径与偏好（默认看哪家公司、习惯的期间粒度），下次自动带上 | ❌ | 无；`source/memory/` 只是文件摘要只读面板，与对话无关 | 待评估 |

## 二、外部方案有、但我们明确不做的

列在这里是为了**不必反复重新讨论**。每条都已在前序调研里评估过并给出否决依据。

| 功能点 | 不做的理由 |
|---|---|
| 检索必要性判定（Self-RAG / Adaptive-RAG） | 它省的是"无用检索的开销"，而我们的知识库检索是进程内直调、空结果几乎零成本；它牺牲的漏检恰是我们的首要风险。照搬会把事做反 |
| LLM 滚动摘要压缩历史 | 历史仅占上下文 2.6%；且财务数字摘要可能失真，失真就成了数据污染源 |
| 跨会话长期记忆（自动抽取事实） | 收益数字是在「闲聊记忆」类测试集上测的——那种场景里事实永远不变、也没有别的权威数据源可对不上，恰好绕开了我们最大的风险，分数不能外推到财务问答。而财务事实会被重述、会调 close month，权威源在数据库里，抽进记忆层就是**一份会漂移的旧事实**，模型分不清哪份新。若将来要做，只限偏好/口径层，禁止写任何数值 |
| 时序知识图谱记忆 | 同上，只借"双时间 + 出处"的思想，不引架构 |
| 工具延迟加载 / LLM 工具筛选器 | 适用线是 ≥10 个工具或工具定义 >10k token，我们够不上；工具数过 20 再评估 |
| 让模型写代码在沙箱里调工具 | 需要代码沙箱，且与"取数必须经 Java 网关透传用户身份"的安全边界严重冲突 |
| 多智能体 orchestrator-worker | 提出这套做法的 Anthropic，自己就写明了它**不适用**的场景：「需要共享上下文、智能体之间依赖多的领域」——说的正是我们 |
| 拆成取数 agent + 成文 agent | 首字延迟翻倍且流式要重做 |
| 显式计划 / todo 清单 | 平均 2.70 步的单轮问答，没有"长程"可言 |
| 生成后自我批判 | 外部实测：无标准答案时的内在纠错改对 7.6% 的同时改错 8.8%，净负 |
| 动态工具预算写进提示词 | 实测模型本来就很克制（均值 2.70 轮），且这只是提示词软约束 |
| 单轮总时长上限 | 有的问题本来就需要调更多工具，慢是合理的，不该一刀切掐断 |
| 图状态持久化 / 崩溃恢复 | 未完成状态的对话占比约 2%，且疑似开发期手动中断 |
| 推测性预调取数工具 | 要带用户身份打 Java 网关，猜错就是白打请求 + 审计噪音 |
| 原始思维链流式可视 | 财务场景暴露中间推理，出错时反而摧毁信任 |
| 先流出再撤回的输出审核 | 我们的审核在输入侧，可以做到零泄漏并行，不需要退而求其次 |
| 可编辑画布式答案 | 财务问答是"读并核对"，不是"协作写作" |
| 关键词检索换 BM25 | 剩余增量无外部数据可估，没有评测集量不出来；等评测集建好再评估 |
| 静态供应商优先级路由 | 作用范围是全局，等于关掉整个平台的负载均衡，代价远大于收益 |

## 三、一句话小结

按功能面看，**我们缺的不是"对话智能体的基础能力"**——流式、分支、断流恢复、并行工具、同参去重、成本记账、权限控制这些都已经具备，其中断流恢复与同参去重两项还强于外部参考方案。

真正的缺口集中在三处：

1. **确定性不足** —— 知识库必查、数值接地、输出审核，都是"提示词要求了但没机制保证"，靠软约束换不来确定性；
2. **用户看不见系统在想什么** —— 取数条件不可见不可改、开头 7s 纯 spinner、引用不可点；
3. **验收能力缺位** —— 关键指标没埋、没有评测集，导致大部分优化"做了也说不清有没有用"。

第 3 项是前两项的前提。
