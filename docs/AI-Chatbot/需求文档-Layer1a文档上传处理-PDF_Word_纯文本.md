# 需求文档：Company Memory File Layer 1a 后端 — 文档上传处理（PDF、Word、纯文本）

## 一、业务背景与目标

本故事覆盖 **Company 端用户在聊天界面中上传的非结构化文档格式** 的后端处理，具体为：
- PDF 文件（.pdf）
- Word 文档（.docx）
- 纯文本文件（.txt）

并将其内容存储在 **Layer 1a 记忆文件** 中。

这些文件类型的共同特征是：**内容主要为叙述性、散文式或自由格式文本**，因此适合通过 AI 进行 **摘要生成与上下文提取**。该流水线的核心在于 **读取、理解并将文本内容提炼为有意义的记忆条目**。

### 上传时触发的两个并行流程

当 Company 端用户上传一份此类文档时，系统需同时执行以下两个并行处理流程：

1. **RAG 索引（RAG Indexing）**
   - 文档的 **完整内容** 被处理并索引到 **Layer 1a 向量库（vector store）** 中；
   - 在当前会话及未来所有聊天会话中，该文档内容均可被动态检索；
   - AI 可在用户提问时检索文档中具体相关的段落，**无需用户重新上传或重新引用**。

2. **记忆摘要（Memory Summarization）**
   - 系统通过 AI 阅读整篇文档；
   - 自动生成关于公司相关学习内容的 **高层级摘要**；
   - 该摘要作为一条 **Layer 1a 记忆条目** 保存；
   - 即使未来会话不直接引用原文件，也能让"文档中最具战略意义的内容"作为**长期上下文**持久存在。

### 查询时的检索机制

- **RAG 是主要检索机制**；
- 用户提问时，**查询直接命中 RAG 索引中的完整文档内容**，而 **不是命中摘要**；
- 摘要仅作为辅助上下文，帮助 AI 定位相关文档，**不会对 RAG 检索做门控或过滤**；
- 原因：摘要无法覆盖文档的全部内容；若必须先命中摘要再进入文档，会导致 **摘要未捕获的内容静默不可访问**；
- 所有检索均直接经过 RAG，摘要在其旁提供附加上下文。

### 典型文档示例

创始人可能上传的此类文档常见示例包括：
- 导出为 PDF 的 Pitch Deck；
- Word 格式的董事会会议纪要或备忘录；
- 战略规划文档；
- 投资人更新（Investor Update）；
- 纯文本格式的 Fireflies 会议转录导出；
- 公司概述或定位文档。

每一份都包含丰富的公司专属上下文，AI 应能从中学习并在未来对话中智能引用。

### 数据隔离原则

- 此类文档上传衍生的所有内容 **严格限定在源公司的 Layer 1a 记忆文件中**；
- 在 **任何情况下** 都不会流入 Layer 1b 或 GS Knowledge Base（Layer 2）；
- 本故事仅覆盖 **后端处理**；面向用户的上传界面、文件类型校验、上传确认行为由另一个 Story（Document Upload for Chat Analysis UI）覆盖。

## 二、功能需求（Acceptance Criteria）

### 2.1 支持的文件类型（Supported File Types）
- 本故事仅覆盖以下文件类型的处理：
  - PDF（.pdf）
  - Word（.docx）
  - 纯文本（.txt）
- **Excel（.xlsx、.xls）和 CSV（.csv）的处理由另一独立 Story 覆盖**，不在本范围内。

### 2.2 RAG 索引（RAG Indexing）
- 当 Company 端用户上传 PDF、Word 或纯文本文档时，**文档完整内容** 被处理并索引到 **Layer 1a 向量库**；
- RAG 索引使该公司在 **当前会话及所有未来会话** 中均可动态检索文档完整内容；
- RAG 索引需在 **上传后合理时间内完成**，对典型大小文档目标在 **30 秒以内**；
- **多页 PDF** 与 **多节 Word 文档** 必须 **完整索引**，在合理大小限制内 **不得因文档长度截断或排除任何内容**；
- 纯文本文件（.txt）**包括 Fireflies 导出的转录文本**，必须以其完整文本内容被完整索引并保留。

### 2.3 RAG 作为主要检索机制（RAG as Primary Retrieval Mechanism）
- 查询时，**检索直接通过 RAG 命中索引中的完整文档内容**，不经过摘要；
- 记忆摘要仅作为辅助上下文与定位信息，**不会对 RAG 检索做门控或过滤**；
- 针对已上传文档的查询，**无论摘要是否与查询相关，都通过 RAG 索引直接答复**；
- 该机制确保 **不会因摘要的局限性而导致文档内容静默不可访问**。

### 2.4 记忆摘要（Memory Summarization）
- 在与 RAG 索引并行的情况下，系统使用 AI 分析上传文档并自动生成关于公司相关学习内容的 **高层级摘要**；
- 生成的摘要作为 **Layer 1a 记忆条目** 保存，附带以下元数据：
  - **Source Type**：document summary
  - 原始文档名称（document name）
  - 文件类型（file type）
  - 上传时间戳（upload timestamp）
- 摘要提取适用 **聊天提取已建立的同一内容质量规则**——捕获：
  - 事实（facts）
  - 战略上下文（strategic context）
  - ICP 信号（ICP signals）
  - 竞争引用（competitive references）
  - 其他具持续性价值（staying-power）的信息
- **已定义的提取类别**（company facts、ICP、competition、people、financials、strategic challenges 等）作为 **提取目标（extraction targets）** 引导摘要 prompt——**AI 首先寻找它们**；
- **但摘要不严格受这些类别限制**：若 AI 发现 **超出已定义类别范围但与公司相关、有意义的内容**，应将其摘要化并存储，**而非丢弃**；
- **通用模板文本、标准法律措辞、格式化痕迹**，以及不具公司专属相关性的内容，**需从摘要中排除**；
- **仅当文档完全不含任何与公司相关的内容时，才不生成记忆摘要**；
  - 此时该文档仍可通过 RAG 检索在聊天会话中访问，但 **不会出现在 Memory Settings 面板中**；
  - **没有生成记忆摘要不是错误**，**不需要向用户发出通知**。

### 2.5 数据隔离（Data Isolation）
- **RAG 索引** 与 **记忆摘要** 均 **严格限定在源公司的 Layer 1a 文件**；
- 文档内容及其派生的摘要在 **任何情况下** 都不会流入 Layer 1b 或 GS Knowledge Base（Layer 2）；
- 已处理的文档内容 **不可被平台上任何其他公司访问**。

### 2.6 错误处理与性能（Error Handling and Performance）
- RAG 索引或摘要生成失败时，**记录日志以备排查**，**不向终端用户暴露任何错误信息**；
- 即便某次文档处理步骤失败，**Chatbot 仍正常工作**——**记忆更新失败不阻塞聊天体验**；
- 若文档过大、超出系统处理限制：
  - **记录失败日志**；
  - 用户在聊天界面收到一条 **优雅的内联提示信息（graceful inline message）**。

---

## 四、范围之外

- 不包含 Excel（.xlsx、.xls）与 CSV（.csv）文件处理（由独立 Story 覆盖）；
- 不包含用户端上传界面、文件类型校验与上传确认 UI（由 Document Upload for Chat Analysis UI Story 覆盖）；
- 不包含将内容向 Layer 1b 或 Layer 2 流转的任何能力。
