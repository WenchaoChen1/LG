# 多租户与企业级安全 —— 需求清单

> 关联文档: [参考方案与功能需求](../调研/multi-tenant-reference-and-requirements.md) | [交付说明](../调研/多租户与企业级安全-交付说明.md)
>
> 本清单由调研阶段的功能基线与 LG 现状逐项比对得出，**只列存在差距的项**（已具备的能力不重复列出）。同一改造点上的相关要求已合并为一条。
>
> 用词说明：LG 的租户即**组织树上的节点**——每个组织是一个租户，父租户可管理其子租户。下文统一用"租户"；仅在指数据库实体与字段时用"组织"（组织表、组织 id、建组织 / 挪组织等）。

---

## 优先级定义

| 级别 | 含义 |
|---|---|
| **P0** | 不做则无法安全接入外部租户——门槛项 |
| **P1** | 加固与合规项，可在首个外部租户之后补齐 |
| **P2** | 运营完善项，随客户数量增长再做 |

---

## 一、租户身份识别

| # | 需求 | 现状 | 验收标准 | 优先级 |
|---|---|---|---|---|
| R-01 | **所属租户由登录身份决定** | 登录凭证不带租户，能看哪些数据由页面传来的参数指定；判断"当前是哪个租户"的代码散落多处，口径不一致 | 用户登录后其所属租户写入登录凭证；服务端判断可见范围时只认凭证里的租户，不再采信页面传来的组织参数；全系统只保留一处判断"当前是哪个租户"的代码 | **P0** |
| R-02 | **后台处理也要带上所属租户** | 智能解析的文件解析回调、财务预测批量计算、定时邮件等无用户在线的路径取不到租户 | 上述路径同样能取得所属租户；**取不到时任务报错退出，不能当成"不限租户"继续跑** | **P0** |
| R-03 | **页面统一的"当前租户"** | 组织标识散落在前端多处，取自浏览器本地存储 | 前端只有一处保存和读取"当前租户"；用户切换组织节点时请求带上正确的目标组织，与 R-04 配套 | **P0** |

## 二、数据隔离

| # | 需求 | 现状 | 验收标准 | 优先级 |
|---|---|---|---|---|
| R-04 | **数据归属租户判定与数据访问范围** | 约 40 个功能入口由请求方自报归属；Goldie 知识库检索按客户端给的空间标识放行，不校验调用者；逐级展开子租户的查询能力已存在，但授权时用等值匹配，父租户看不到子租户数据 | 请求仍可携带目标组织（页面需要切换节点），但服务端必须核对它是否在当前用户的租户及其子租户范围内——**传自己范围内的组织应成功，传范围外的必须失败**；知识库检索同样按登录身份圈定；按租户圈定数据时逐级展开其下全部子租户，算出这些租户名下的全部被投企业，**父租户可见整棵子树的数据** | **P0** |
| R-05 | **区分"平台统一维护"与"各租户自己维护"的内容** | 没有这条分界；KPA 方法论正文任一登录用户可改，且按编码对所有租户生效 | 逐项明确 KPA 方法论、财务评分类目权重与等级、技术栈类型、第三方工具目录等属哪一类并与实现一致；平台统一维护的内容对租户只读，仅平台方可编辑 | **P0** |
| R-06 | **全部业务表都能判定所属租户，新建时自动写入** | 少数表没有归属字段，其中文件表（`files`）无可靠反查线索；新建数据的归属依赖业务代码传参，判不出时按"不限租户"处理 | 全部业务表可直接或经关联关系判定所属租户，无盲区；新建数据时所属租户由统一机制写入，业务代码不需要也无法绕开；查询时取不到所属租户直接报错，不返回全部数据、也不静默返回空 | **P1** |
| R-07 | **同行对比跨租户取数，设置取数白名单** | 同行对比从全平台捞参照企业，不分租户（`getActiveCompany()` 为 company 全表、只筛活跃）；参照企业不足 3 家时回退为"全平台所有活跃企业"，范围反而扩大；无清单、无审批 | 需跨出自身租户范围取数的功能有明确清单与审批，不靠代码里零散特判；**跨租户写入一律禁止**（父租户读写子租户属正常权限，由 R-04 覆盖）。当前唯一在册项是**同行对比**：只给出汇总数字、不出现参照企业是谁（已具备）；参照企业数量不足时不出结果，不得回退为全平台取数 | **P1** |

## 三、租户的开通与注销

| # | 需求 | 现状 | 验收标准 | 优先级 |
|---|---|---|---|---|
| R-08 | **一步开通新租户** | 可创建租户组织与首位管理员，但开出来是空壳；初始配置以"数据库里第一家租户的当前设置"为模板复制 | 一次操作完成建租户、建首位管理员、初始化配置，**开通后管理员即可直接登录使用**；初始配置来自版本化的模板，与任何既有租户的运行时状态无关 | **P0** |
| R-09 | **租户注销与数据清除** | 不支持，数据无法清理，已发出的凭证最长可延续约 300 天 | 注销后该租户及其子租户的全部数据可被完整清除；已发出的登录凭证同时失效 | **P1** |

## 四、角色与权限

| # | 需求 | 现状 | 验收标准 | 优先级 |
|---|---|---|---|---|
| R-10 | **平台管理员与租户管理员通过新增角色类型区分，权限由服务端判定** | 角色与菜单表结构完整、页面齐全，但未落地为访问控制，依赖前端传参；角色类型字段 `role_type` 已存在（取值：超管 / 公司管理员 / 项目管理员 / 成员 / ProductOwner），但没有"平台 / 租户"这一层区分；管理端身份以"有没有绑定被投企业"推断，且 Java 与 Goldie 各有一套判法 | 在角色类型（`role_type`）中新增取值，把平台方角色与租户内角色区分开，不再用隐式条件推断、两处判法收敛为一套；菜单与按钮权限在服务端判定，前端控制只用于显示，改前端不影响实际能访问的范围 | **P0** |
| R-11 | **组织树写操作的范围校验与环路检测** | 组织管理功能已有，但任何登录用户可在任意位置创建、移动组织，甚至形成循环引用 | 新建 / 修改 / 移动组织时，**被操作的组织与目标父节点都必须落在**操作者自身租户及其子租户范围内，越界即拒绝；移动时检测环路 | **P0** |
| R-12 | **角色数据模型的租户化** | 角色表本身无归属列，靠关联表 JOIN 反查；`role_key` 为**全局唯一**，两个租户各建一个同名角色即冲突 | 角色表加归属列；唯一约束改为按（租户，key）唯一，存量数据回填 | **P1** |
| R-13 | **角色接口按租户范围校验** | `RoleController` 已有 8 个角色接口，但不校验调用者与目标角色是否同属一个租户 | 查询只返回自己子树内的角色；增 / 删 / 改的目标角色必须在自己子树内，跨租户操作必须失败 | **P1** |
| R-14 | **租户管理员自助维护角色** | 角色管理、菜单配置页面齐全但只挂在平台侧（`devSupport`）；无"可授予权限目录"的概念 | 平台方维护可授予的权限项目录，租户授不出自己没有的权限；租户管理员可自建角色、勾选权限、分配给成员，范围不超出自身子树 | **P1** |

## 五、操作留痕与日志

| # | 需求 | 现状 | 验收标准 | 优先级 |
|---|---|---|---|---|
| R-15 | **打开操作日志写入并定义留存** | 切面已实现但 `@Component` 被注释停用，116 处接入点已标注；无留存期限定义 | 关键操作留痕——谁、什么时间、改了哪条数据——且可按租户检索；有明确留存时长，不能经普通页面或接口修改删除 | **P1** |
| R-16 | **操作日志记录改前改后值** | 切面只记录操作人、时间与方法入参，不取旧值 | 每条操作留痕带上变更前与变更后的值 | **P1** |
| R-17 | **登录记录独立成条** | 登录 IP、地点、失败次数字段存在但从未被写入；登录时间为覆盖式记录 | 登录成功与失败各自独立成条，含 IP 与时间，不被下次登录覆盖 | **P1** |
| R-18 | **知识库对象补记创建人与修改人** | 智能解析的任务、文件、提取数据等表已记录创建人与最后修改人；Goldie 聊天的会话与消息也已具备。缺的是知识库侧——空间（`ai_rag_space`）、playbook 等可编辑对象没有这两个字段 | 知识库空间、playbook 等**可编辑**对象记录创建人与最后修改人；**只增不改**的记录（聊天消息、召回日志、分段）只需创建人与时间，不要求修改人 | **P1** |
| R-19 | **日志和监控带上租户信息** | 一般日志未带租户标识；大模型调用日志已记 token 与美元成本，但只有公司信息，管理端发起的调用无法归属 | 日志、监控、链路追踪均含租户标识，出问题时能判断波及哪些租户；**大模型调用日志同样带所属租户**，为按租户算账提供依据 | **P2** |

## 六、用量与运营

这里的"租户资源"主要指 **OpenRouter 大模型的 token 用量与费用**——它是目前唯一随使用量线性增长、且各租户差异显著的可变成本。

| # | 需求 | 现状 | 验收标准 | 优先级 |
|---|---|---|---|---|
| R-20 | **按租户统计大模型用量并加限制** | 原始用量与成本已逐条落库，但无汇总能力、无上限机制；两端均无任何限流 | 可按租户、按模型、按时间段汇总输入 / 输出 / 缓存 token 与美元成本，**父租户能汇总整棵子树**；可为租户设**每月总量**上限，超阈值告警、超上限可选拒绝或改用便宜模型；同时限制**每秒 / 每分钟的调用次数**，使单个租户短时间内大量调用不影响其他租户 | **P2** |
| R-21 | **租户清单与状态** | 未涉及 | 平台侧可查看全部租户及其状态（启用 / 停用 / 已注销）和层级归属 | **P2** |

## 交付验收：三项整体检查

以上需求全部完成后，用以下三项检验隔离是否真正成立：

1. **参数篡改测试**——以租户 A 的身份登录，把请求里任意标识改成租户 B 的值，全部接口必须失败；
2. **遗漏检测**——新增业务表或接口而没处理租户归属时，在测试阶段就报错，而非默默放行；
3. **删除验证**——注销一个租户后，全库检索它的标识应无残留数据。
