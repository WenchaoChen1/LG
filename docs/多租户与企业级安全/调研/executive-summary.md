## 0. 三句话结论

1. **LG 现在只服务一个客户组织（Golden Section）。** 正因为只有一个，本文列出的所有"看到别人数据"的问题**目前都不可能发生**——没有别人可看。
2. **但系统里从来没有"这是哪家客户的数据"这个概念。** 不是隔离做得不够好，是**根本没做过隔离这件事**——数据表上没有任何字段标明归属，代码里问"我现在代表哪家客户"会得到 **6 个不同的答案**。
3. **第二家客户上线的那一天，所有问题会同时变成真问题，改造成本也会同时翻几倍。** 这是一个有明确截止时间的窗口，不是正在发生的事故。

> 另有 **2 件与多租户无关、但比多租户更紧急**的事（附录 A）——它们让"你是谁"这件事本身可以被伪造。在这两件事解决之前，讨论任何隔离方案都只是纸上谈兵。

## 1. 多租户架构在 LG 语境下的通俗解释

### 1.1 现状与目标的差别

**现在**：所有数据都在**同一个数据库、同一套表**里，**数据表上没有"属于哪个租户"的字段**；登录凭证里也不带这个信息（代码里问"我现在代表哪家客户"会得到 **6 个不同答案**）。因此接口无法校验"发起请求的人"和"要访问的数据"是否属于同一家客户，而是**由请求方自己在参数里指定要看谁的数据，系统照单执行**。之所以至今没出过事——**只有一家客户在用，参数里能填的也就那一家**。

> 打个比方：像一间共享档案室——文件堆在同一个房间，档案盒上没有标签写明归属，门口也没人核对来访者身份。现在没出事，只是因为进出的始终是同一家公司的人。

**多租户之后**：同一套系统、同一个数据库要同时服务多家**互不相识、互相不能看见**的客户，且每次数据访问都必须**强制**判定归属，不能依赖开发者写代码时记得加过滤条件。

### 1.2 "租户"在 LG 具体指什么

产品定义的租户是**组织树上某一级的节点**。当前唯一的租户是 `Golden Section`：

```
Background development organization
    └── Global Authority
            └── Golden Section              ← 这一级是"租户"（一家客户）
                    ├── 子组织 A ──┐
                    │             ├──> Company（被投企业）  ← 同一家企业可挂在多个子组织下
                    └── 子组织 B ──┘
```

> 树上每一级长得一模一样，**数据库里没有任何字段标识"这一级是租户"**；且业务确认**层级深度不固定**，也不能用"第三层就是租户"来推断——**纯人为约定，因此必须新增一个显式标记**。

**企业挂在租户下面的子组织上，且可以同时挂多个**——这是正常业务形态；**但不会跨租户**。这条规则目前同样**只是人为约定，数据层面没有任何东西在守它**。

### 1.3 为什么这件事比想象中麻烦

现有隔离的粒度**落在租户下面若干级**——按最底层的"被投企业"分，而企业与租户之间还隔着子组织（层数不固定）。实测：Java 侧 151 张业务数据表中，85 张带"属于哪家被投企业"的标记，21 张带"属于哪个组织节点"，**53 张两个都没有**——其中多数是全局字典、权限元数据一类，本就不该有归属，**真正需要设计归属方案的是 16 张**；而**带"属于哪个租户"标记的：0 张**。

所以租户级隔离不是加一个筛选条件那么简单，而要走一条链：**确定这个人属于哪个租户 → 展开该租户下的整棵子树 → 算出子树下所有被投企业 → 再按企业筛数据**。这条链目前有三处问题：

| # | 问题 | 说明 |
|---|---|---|
| 1 | **给不出"租户下全部企业"** | 页面靠切换组织树逐个节点看公司（正常用法），但**不具备直查租户下全部公司**的能力——而租户级过滤要的正是这个集合。后端自动圈定时（如 chatbot 知识库检索）取的是"第一个组织"，**取到哪一级不确定，取到租户那一级就返回空**，且无提示 |
| 2 | **没有任何约束保证"不跨租户"** | 那条业务规则**只存在于人为约定里，数据层面完全不设防**——把一家企业挂到另一家客户的组织下，数据库照收不误 |
| 3 | **多归属时"取第一个"，排序口径与页面不一致** | 归属有**两条互不同步的路径**，查哪条得到的集合可能不同。取第一条时：页面树按创建时间排序，**那条 SQL 却不排序**，两边对齐没有保证 |

> **问题 3 的严重度**：目前**无线上错误**（不排序时多半碰巧与页面一致），但属**依赖未定义行为**——执行计划或数据变动后就可能不一致，届时评分权重与评级会跟着变。**修法便宜**：补上与页面一致的排序即可，不必等多租户。

### 1.4 一个必须先解决的矛盾

系统有一条核心假设：**"没有绑定具体企业的账号 = 平台超级管理员"**，被四个模块当作硬前提使用。

多租户会让它直接失效——**租户管理员按定义就是"不属于某一家具体被投企业"的人**，于是会被系统认成平台超管、拿到全平台权限。这不是加个字段能补的，是**判断"你是谁"的依据本身要换掉**，而这个依据散落在四个模块里。**这是改造中风险最高的一块。**

## 2. 支持多租户所需的技术改造与投入

### 2.1 数据隔离模型

把隔离能力分五档，"要做到什么程度"就成了可决策的问题：

| 档次 | 通俗含义 | LG 现状 |
|---|---|---|
| 第 0 档 | 完全不检查，登录了就能看全部 | 还有相当一批接口停在这里 |
| **第 1 档** | **请求方自己在参数里指定要看谁的数据，系统照单执行** | **← 现在在这里** |
| 第 2 档 | 系统按登录身份决定能看谁的数据，请求参数说了不算 | 只有少数几个模块做到 |
| 第 3 档 | 上一档 + 程序员万一忘了写检查，系统会直接拒绝而不是放行 | **完全没有** |
| 第 4 档 | **每张表加一个租户 ID 字段，由数据库按它自动过滤**——程序被绕过也拦得住 | **完全没有**。对应 §2.4 的行级策略 |

**第 1 档与第 2 档的差别是这次调研最核心的发现**：决定"你能看谁的数据"的是**请求参数**而不是**登录身份**，改一下参数就能看别人的。全仓有 **39 个**这样的接口，其中**校验"你是不是这个组织的人"的：0 个**。

**唯一的正面样板**：财务对标模块有一套完整的"请求进来时逐个核对能不能看"的实现，覆盖 3 个接口并配了回归测试（它核对的是“能不能看这家企业”，不是“你是不是这个组织的人”，故不计入上面的 0 个）——它是现成可复用的模板，也是"39 个接口里真正需要独立设计的只有约 5–8 个"这个判断的依据。

改造按依赖顺序分三步（另有**第 4 步**对应 §2.2 的租户开通与运营）：

| 阶段 | 通俗说明 | 具体内容 |
|---|---|---|
| **第 1 步**<br>让"租户"成为系统认识的概念 | 让数据带上租户归属，并统一"这个人属于哪家客户"的答案 | 组织表加显式租户标记（**不能靠层级深度推断**）；6 个互相矛盾的"我属于哪个组织"收敛成 1 个并放进登录环节；补"企业的所有组织归属必须在同一租户内"这条约束 |
| **第 2 步**<br>每次请求都校验归属 | 请求方不能再自己指定看谁的数据 | 39 个接口改为按登录身份判定；修 2 处"报别人的组织反而能看更多"的反向漏洞；"算企业"那段改成展开子树；前端建统一"当前租户"概念；**替换 §1.4 那条超管假设** |
| **第 3 步**<br>制度化，不靠人记得 | 程序员漏写检查也不会放行 | 统一强制过滤机制；补齐 **16 张完全没有归属标记的表**（其中 4 张连反查线索都没有） |

### 2.2 租户开通与配置

**当前不具备可用的"开一家新客户"能力：**

| 问题 | 通俗说明 |
|---|---|
| 谁都能开 | 创建组织的接口**没有任何权限检查**，任何登录用户都能在任意位置创建 |
| 开完是个空壳 | 不会生成角色、菜单、投资组合，也不会把创建者关联进去——**新开的组织没有人能登录进去**，必须再手工挂人 |
| 初始配置来路不明 | **不是固定模板**，而是运行时"复制数据库里碰到的第一家客户的当前配置"——**新客户会继承老客户改过的东西** |
| 关不掉 | 注销组织时投资组合、成员关系、技术栈配置、企业本身都不清理；用户只标记为已删除，**登录凭证仍然有效（约 300 天）** |
| 组织可被随意搬动 | 任何用户都能把节点挂到任意位置，**甚至挂成死循环**；搬完后各种排名口径、可见范围**悄悄改变且无记录** |

**需要的投入**：开通向导（建组织 → 建首个管理员 → 配菜单权限 → 建投资组合 → 用固定模板初始化）、注销时的完整清理、搬动组织的权限控制与循环检测。

### 2.3 组织级权限与管理

- 角色和菜单的表结构完整（16 张相关表），但**没有落地成真正的权限检查**——权限工具类写好了却从没被调用过。**它实质是一套"菜单显示/隐藏配置系统"，不是访问控制系统**；真正生效的只有两处写死的判断。
- **前端权限控制全部基于浏览器本地存储**，用户自己就能改，因此**前端的任何限制都不能算作安全边界**。
- 切换组织的实现方式是**后端把密码传回前端、前端拿着密码重新登录**（与附录 A 第 2 条同源）。

**已有可复用页面**（显著降低 UI 工作量）：公司开通表单、公司列表、组织管理页、用户管理、成员邀请、角色权限矩阵、菜单配置、组织选择器组件。

**缺的（12 项）**：统一"当前租户"概念、不重登切换租户、开通向导、租户自助管理页、跨企业成员总览、邀请状态管理、成员-角色批量分配、按钮级权限统一入口、"当前所属组织"界面提示、套餐与席位管理、租户级操作审计界面、单点登录与独立域名/品牌定制。

### 2.4 实现路径的取舍

> 对应注意事项第 3 条：不得在没有解释的情况下默认采用某一种方案。

| 选项 | 成本（含改什么） | 能得到什么 | 代价 | 结论 |
|---|---|---|---|---|
| **应用层强制**<br>第 1–3 步 + 租户运营<br>**→ 做到第 3 档** | **7 人周**<br><br>**改什么**：① 组织表加租户标记列 + 标定（1 条 UPDATE）；② 收敛 6 处"我在哪个组织"，把租户放进登录凭证；③ 39 个接口改按登录身份判定（需独立设计的约 5–8 个，其余套模板）；④ 前端建统一"当前租户"概念（替换 65 处 + 63 处散落取值）；⑤ 替换"没绑企业=超管"假设（涉 4 个模块）；⑥ 开通向导（先用脚本）+ 初始配置改固定模板 | 达到第 3 档，覆盖已发现的全部问题；不影响跨客户的汇总类功能（如行业对标） | 万一程序被绕过（比如有人直连数据库），没有第二道防线 | **推荐** |
| **行级策略**<br>每张表加租户 ID，数据库按它自动过滤<br>**→ 第 4 档** | 在应用层强制之上**再加 5 人周**<br><br>**改什么**：① 约 150 张表加租户字段 + 回填 + 补索引；② 建数据库行级策略（每表 2 条语句）；③ **关掉 Java 的自动改表**，先把现有表结构收进版本化迁移；④ 拆数据库账号（现全部服务共用一个超级账号，而超级账号默认绕过策略）；⑤ 连接层注入当前租户；⑥ 给定时任务/消息消费者补租户上下文；⑦ 给跨客户汇总功能做策略豁免 | 多一道防线；对部分企业客户的安全问卷是加分项 | ③④⑥⑦ 出问题时表现为**正常业务功能突然查不到数据**，排查成本远高于开发成本 | **不建议现在做**（理由见下，与成本无关） |
| **独立部署**<br>不改代码，每家客户一套<br>**→ 不走档次阶梯** | 近期最低<br><br>**改什么**：不动业务代码，只做部署与环境模板自动化、配置隔离、发布流程 | 立刻能接第二家客户，**隔离强度实际上是最高的** | 运维成本随客户数线性增长；版本容易分叉；跨客户功能（行业对标）做不了；单客户成本高 | **时间不够时的正当过渡选择** |

> ⚠️ **行级策略不是"分库"或"分 schema"。** 它是**共享同一套表**、每张表加租户 ID 字段、再由数据库按这个字段自动过滤。**物理拆库 / 拆 schema 是另一种做法，已在工程评估中排除**——那会直接破坏跨客户的汇总功能（如行业对标）。
>
> 另注意**这两个数字不是"二选一"**：行级策略的 5 人周是**加在应用层强制之上的**，两者相加 = 12 人周；而它的绝对工作量比应用层强制还小，所以对它的判断**跟贵不贵没有关系**。

**对行级策略的判断——不是因为工作量大，而是因为顺序错了。** 它的作用是"程序漏写检查时兜底"，但 LG 的问题**不是漏写**——条件基本都写了，问题是**条件里那个"看谁的数据"是请求方自己填的**，是"我代表谁"有 6 个答案，是多归属取第一个时排序口径与页面不一致。**这些不解决，行级策略里那个"当前租户"没有可信的值可填；一旦解决，它的绝大部分收益已经拿到了。**

若将来仍要做，前提是先给每张表加"属于哪个租户"的字段——那本身就是第 3 步的自然延伸。**它的七项前提条件目前一条都不成立：**

| 前提 | 现状 |
|---|---|
| ① 系统能给出**可信的**"当前是哪家客户" | ❌ 登录凭证里没有这个信息，现在由请求方自己填 |
| ② 每张表都有归属标记 | ❌ 0 张有租户标记；16 张连"属于哪家企业"都没有 |
| ③ 归属字段命名统一 | ❌ 同一概念有 4 种叫法，统一脚本会漏 |
| ④ 归属字段上有索引 | ❌ 测试库扫出 367 个关联字段无索引，只补了 79 个，**剩 288 个**；向量库三张表的归属字段**零索引** |
| ⑤ 数据库账号可分权 | ❌ 全服务共用一个超级账号，而**超级账号默认绕过隔离规则**，不拆等于白做 |
| ⑥ 数据完整性可依赖 | ❌ 外部扫描报 158 个外键有问题；系统全环境配置为"建外键失败就静默忽略"，声称的 305 条外键里只有 61 条真实存在 |
| ⑦ 两个数据库口径一致 | ❌ 业务库 + 向量库各做一遍；另有 3 张 AI 流程状态表由框架启动时自建、**不受版本管理**，且存了解析出的财务数据 |

**关于独立部署**：如果第二家客户的时间早于第 1+2 步能完成的时间，它是**正当选择**，代价是运维和产品形态而不是安全。建议把它作为**时间不够时的明确备选**，而不是让它默认发生。

## 3. 推进企业级安全所需的技术改造与投入

> ⚠️ **分析起点缺失**：需求要求以产品战略附录里的 **SOC 2 阶段划分 / 时间线 / 预算**作为起点，该附录未提供给研发。下面基于代码现状给出差距与外部依赖；**阶段与预算需拿到附录后才能定档**。

### 3.1 SOC 2 Type II

**它是什么**：一份由独立会计师事务所出具的审计报告，证明"这家服务商对客户数据的管控措施是靠谱的"。**不是证书**，是报告，通常在保密协议下提供给客户查阅。

**Type I 与 Type II 的差别是关键**：Type I 只看某个时间点上控制措施**设计**得对不对；**Type II 要看一段时间内它是否持续在运行**——好比前者检查"你装了监控摄像头"，后者检查"这半年摄像头一直开着、录像一直在存、有人定期查看"。企业采购通常只认 Type II。

**审计方会怎么问，我们现在答得上来吗：**

| 审计方会问 | LG 现状 |
|---|---|
| 「谁在什么时候改了什么数据？给我看记录」 | ❌ 审计表是空的——写入的那段代码被注释掉了 |
| 「谁登录过？失败登录有记录吗？」 | ❌ 无独立登录日志；IP、失败次数三个字段从没写入过 |
| 「有多因素认证吗？」 | ❌ 完全没有 |
| 「密码策略是什么？」 | ❌ 无复杂度、不过期、不锁定 |
| 「离职员工的访问权限多久回收？」 | ⚠️ 用户只软删，登录凭证有效期约 300 天且不吊销 |
| 「生产变更有审批吗？」 | ⚠️ **有人工环节但无审批记录**——CI 只构建镜像并推到仓库，实际部署由人工触发；但"谁批准了哪个版本上生产"没有留痕，也没有"批准人不能是作者本人"的规则 |
| 「依赖漏洞怎么管？」 | ❌ CI 无任何扫描，前端还显式关掉了 `npm audit` |
| 「定期做访问权限评审吗？」 | ❌ 无 |

对应到工程侧：**审计日志**（见 §3.4，直接卡住）、**访问控制**（就是多租户第 1–2 步）、变更管理、加密、可用性监控；另有一批基础设施差距——CI 里没有依赖漏洞扫描/镜像扫描/代码安全扫描，基础镜像不固定版本，使用长期有效的云凭证而非短期凭证。

**但决定时间线的不是工程**：Type II 需要**连续 3–12 个月的观察期**来收集"控制措施确实在持续生效"的证据。这是日历时间，**加人无法压缩**，也无法"突击补三个月的日志"。

> ⚠️ 由此推出两条排期含义：① **审计日志必须先上线并稳定运行，观察期才开始计时**——它的排期要按"距离观察期开始还有多久"倒推，而不是按工程量算；② SOC 2 报告有效期通常 12 个月、**每年需重新审计**，它不是一次性投入而是持续的运营负担。

### 3.2 GDPR 合规

现状：**有个人数据，但完全没有应对数据主体权利的能力。**

- 个人数据分布很广，包括**完整的 AI 对话记录**（可还原全部提问内容与财务数据）、聊天正文、搜索日志里的用户原始提问
- **没有数据脱敏、没有"删除我的数据"能力、没有数据导出、没有保留期限策略**
- **目前根本没有"彻底删除一家客户"的能力**——数据之间没有级联删除关系；团队遇到删除引发的问题时，实际做法是**把删除功能注释掉**，线上"删除公司"其实是停用而非真删
- 两处个人数据外发需合规确认：错误监控服务开启了默认上报个人信息；6 家 AI 模型供应商直连，仓库里看不到数据处理协议或地域限制
- 设计文档里写了 GDPR 数据擦除的表和流程，但**代码里一行都没实现**，且它引用的那些表在系统里根本不存在

**需要的投入**：数据清点分类、删除与导出能力、保留策略、个人信息脱敏、供应商协议（需法务参与）。

### 3.3 零信任架构

现状：**登录这一环有，其余基本没有。**

| 项 | 通俗现状 |
|---|---|
| 登录方式 | 自研账号密码登录 + 令牌；**网关不做任何权限检查**，只负责转发 |
| 登录有效期 | 登录凭证与续期凭证**默认都是约 300 天** |
| 会话控制 | 改密码不会让旧凭证失效；**同一账号可无限处同时登录，无法踢下线** |
| 多因素认证 / 单点登录 | **完全没有** |
| 密码策略 | **无复杂度要求、不过期、不检查重复使用、失败也不锁定** |
| 边界防护 | 无调用频率限制、无 IP 白名单、无 Web 应用防火墙；跨域策略全开 |
| 传输加密 | 加密在上游负载均衡完成，配置不在本仓库内 |

**关键判断**：零信任的核心是"每次请求都验证身份和权限"，与 §2.1 的第 1 档现状**直接冲突**。**零信任改造和多租户第 1–2 步其实是同一件事，不应分开排期。**

### 3.4 审计日志

现状：**表建好了、注解也标了，但里面没有数据。**

- 审计表存在、表注释写明用途就是审计追踪、16 个接口文件上标了 116 处审计注解——但**唯一负责写入的那段代码被注释掉了**，表实际不再增长；查询接口还在查这张不增长的表
- **没有独立的登录日志**：登录 IP、地点、失败次数**从来没有被写入过**；登录时间是覆盖式的，只保留最近两次
- 行级"谁创建、谁修改"审计，Java 侧有统一基类，**Python 侧没有**
- AI 调用记录字段很全，但属于"成本与性能追踪"，**不是合规意义上的操作审计**：不覆盖业务增删改，无变更前后值，无防篡改保护，无保留策略
- 局部亮点：知识库写操作审计、任务状态流水两张表是真实有效的

**这是 SOC 2 的必答题，目前是直接的阻塞项。**

### 3.5 外部依赖（不受内部研发产能控制）

> 对应注意事项第 4 条：硬性外部依赖需明确标注。

| 依赖 | 说明 | 对时间线的影响 |
|---|---|---|
| **SOC 2 Type II 观察期** | 需连续 3–12 个月收集控制有效性证据 | **决定性**。即使工程今天全部就绪，最快仍需 3–12 个月才能拿到报告 |
| **审计机构选型与档期** | 审计方排期 | 高 |

| 云厂商与 AI 供应商 | 合规报告 / 数据处理协议获取 | 中（GDPR 前置） |
| 法务 | 个人数据清点、供应商协议、隐私政策 | 中（GDPR 前置） |

## 4. 高层级工作量 / 时间线估算（Rough Sizing）

> **口径**：以人周计，**假设 1 名 Java + 1 名 Python + 1 名前端全职并行**（实际投入更少则工期按比例拉长）。**不含** SOC 2 观察期等日历时间，**不含**测试环境搭建、回归验证、灰度发布与数据迁移演练（经验上另占 20–30%）。因为现在只有一家客户，数据回填与归属歧义清理成本≈0，估算已按此下调。
>
> **下述数字为初步估算，尚未经团队正式预估。**

### 4.1 关于估算基准

> 对应注意事项第 2 条：优先参照团队已完成的相关工作，而不是从零推算。

调研中确实从提交历史提取了团队过往的同类工作（2021 年角色/菜单体系、2022 年组织层、2026 年几次安全整改与登录逻辑重构）。**但这些数据不能作为速率基准**——那些是**人工编写代码**的产出速率，而当前团队已普遍借助 AI 辅助开发，**单位时间产出与历史不可比**，按历史速率外推会系统性高估。因此下面的数字**基于逐项功能改动明细直接初估**。

历史工作中**仍然有效**的是"存量结构"而非"产出速率"——它们影响**要改多少**，与改得多快无关：

| 仍然有效的结论 | 为什么与速率无关 |
|---|---|
| 已有角色/菜单体系实质是**"菜单显示配置系统"，不是访问控制系统**（权限工具类从没被调用） | 决定了"请求期判断能不能看这行数据"属于**新建而非扩展**——影响范围，不影响速度 |
| 财务对标模块 3 个接口**已有完整的授权守卫 + 回归测试** | 可直接复用的模板，决定了 39 个接口中真正需独立设计的只有约 5–8 个 |
| 组织管理 / 成员 / 角色 / 菜单配置等**页面已存在** | 决定了租户运营部分是"改造入口与维度"而非"新建功能" |
| 生产环境存量数据只有一个租户 | 决定了归属回填是一次全量 UPDATE，歧义清洗量≈0 |

| 项 | 要做什么 | 工作量 | 备注 |
|---|---|---|---|
| 审计日志 | 操作审计 + 登录日志 + 保留策略 | **3 人天** | **SOC 2 必答题**，且必须先上线运行、观察期才开始计时 |

### 4.4 合并结论

- 多租户 **7 人周** + 企业级安全工程侧 **约 2 人周** = **约 9 人周**；另有 **GDPR 待定**（取决于法务要求）
- **零信任与多租户第 1 步是同一件事**，合并做可在 9 人周里再省一部分——**建议合并排期，不要分成两个项目**
- **SOC 2 Type II 的完成时间由观察期决定**：即使工程今天全部就绪，最快仍需 **3–12 个月**才拿得到报告，**加人压缩不了**
- 因此若目标是某个销售季拿到认证，**工程就绪时间必须从那个日期倒推**——这个倒推**不依赖工程量数字**，现在就可以做

## 5. 关键风险、依赖与未知项

### 风险

| # | 风险 | 影响 |
|---|---|---|
| R1 | **附录 A 那两件事没解决就上线第二家客户** | 所有隔离设计失效。硬前置 |
| R2 | "没绑定企业的账号 = 超管"这条假设与"每家客户都要有自己的管理员"直接冲突 | 判断身份的依据要整体更换，涉及 4 个模块，是第 2 步最大的单点风险 |
| R3 | 多归属时"取第一个"的排序口径与页面不一致 | 目前无已确认线上错误，但依赖数据库未定义行为；执行计划或数据变动后可能与页面不符，影响评分权重与评级。**修法便宜，当下即可做** |
| R4 | 组织节点可被任意用户搬动，甚至搬成死循环 | 搬完后排名口径、可见范围**悄悄改变且无记录** |
| R5 | 生产环境开着"自动改表"（三个环境都是） | 表结构由代码自动演进，与人工迁移脚本并存；是数据库层方案的直接障碍 |
| R6 | 新租户初始配置是"复制某家现有客户的当前配置" | 客户之间的配置会互相污染 |
| R7 | 错误监控默认上报个人信息 + 6 家 AI 供应商直连 | GDPR 风险，需法务和供应商协议先行 |
| R8 | 前端权限依据存在浏览器本地，用户可自行修改 | 所有前端限制都不能当作安全边界 |
| R9 | 权限类改造历史上未被显式排期过，多为随其他需求附带完成 | 本项涉及跨端、跨模块的语义改动（尤其替换超管假设），**不适合作为附带任务插空做**；需明确排期与责任人 |
| R10 | **设计文档里写的数据库隔离、权限角色、GDPR 擦除能力都没有实现** | 若被引用到客户安全问卷或审计材料里，构成**不实陈述风险** |

- **外部硬依赖**：见 §3.5
- **内部依赖**：产品需先定义租户的商业形态；法务需先完成个人数据清点与供应商协议；需要专职工程投入（见 R9）

### 未知项（需产品/业务确认才能收敛估算）

1. **产品战略附录里的 SOC 2 阶段 / 时间线 / 预算** —— 需求要求以此为起点，本次未获得

3. **租户的商业形态**：一家客户内部允许多少层子组织？是否需要跨客户共享数据（如行业基准）？
4. **是否需要客户级单点登录 / 独立域名 / 品牌定制** —— 直接决定第 4 步的规模

## 6. 研发视角的业务影响 / ROI 判断

### 6.1 外部试点扩展

**这是硬门槛，不是"风险高低"的问题。** 当前系统在结构上无法安全接入第二家客户——不是"有风险"，是"系统里没有客户这个概念"。

**完成最小可行范围即可支撑受控试点**（第 1 步全部 + 39 个接口 + 展开子树 / 替换超管假设 / Python 范围收敛 / 前端租户上下文 + 开通脚本与组织搬动权限），它是 7 人周中的一个子集；若时间来不及，§2.4 的**独立部署**是正当的过渡方案。

### 6.2 企业级客户成交资格

企业采购的安全问卷会直接问到：审计日志、单点登录/多因素认证、数据删除能力、密码策略、渗透测试报告、SOC 2 报告。**目前这些基本全是否定回答**（§3.1 那张表基本就是问卷的形态）。

额外风险：设计文档里已写的数据库隔离 / 权限角色 / GDPR 擦除能力**与实际代码不符**，若被引用到问卷或审计材料中会构成不实陈述（R10）。**清理这些描述本身就是 SOC 2 准备工作的一部分。**

### 6.3 竞争定位

SOC 2 Type II 在很多企业采购中是**准入门槛，不是加分项**。由于观察期不可压缩，竞争位次实际由"**什么时候开始**"决定，而不是由"投入多少人"决定。

### 6.4 不做 / 延迟做的风险

- **窗口期是有限的。** 现在所有问题不可能发生，仅仅因为只有一家客户；**第二家客户上线之日全部同时激活**。如果商务先于工程签下第二家客户，团队将被迫**在生产环境已有客户数据的情况下**做第 1–3 步改造，成本和风险是现在做的数倍。
- **技术债在利滚利。** 每新增一个接口都在延续"看谁的数据由请求方自己填"的模式，39 这个数字**还在增长**。
- **SOC 2 的日历时间无法压缩。** 这是唯一一个"晚一天就是晚一天"、加人也救不回来的项，**也因此是本次最需要现在做出排期决策的部分**。

### 6.5 研发建议的排序

1. **立即做**：附录 A 两件事，不需要排期讨论
2. **与第二家客户的商务节奏对齐**：多租户最小可行范围（7 人周中的子集），外部试点的最小可行前提
3. **从 SOC 2 目标日期倒推**：审计日志 + 零信任（与第 1 步合并做），因为观察期需要控制措施先上线运行
4. **明确不做**：行级策略（第 4 档）。**不是因为贵**（5 人周，比应用层强制还少），而是**前置条件一条都不成立**、且收益已被第 2–3 步覆盖

## 附录 A：两件需要优先处理的事

> 优先级高于全部多租户工作。这两件事让"你是谁"这件事有两条可被伪造的途径——在它们解决之前，本文所有隔离分析都只是纸上谈兵。

| # | 问题（通俗描述） | 后果 | 建议处置 |
