# 多租户与企业级安全

> 关联文档: [决策摘要](./executive-summary.md)（同样内容的完整版，含全部数字与代码依据）

---

## 一、先讲结论

1. **系统里从来就没有"这份数据属于哪家租户"这个概念。** 不是隔离做得不好，是**这件事从头到尾没做过**。

2. **第二家租户上线那天，所有毛病同时变成真毛病，而且那时候再改，成本要翻几倍。** 所以这是一个有截止时间的窗口，不是正在冒烟的火警。

还有**两件比多租户更急的事**（见第七节），它们让"你是谁"这件事本身可以被冒充。这两件不解决，讨论隔离方案没有意义。

## 二、多租户架构在 LG 语境下的通俗解释

### 2.1 现状与目标的差别

**现在**：所有数据都在**同一个数据库、同一套表**里，**数据表上没有"属于哪个租户"的字段**；登录凭证里也不带这个信息。因此接口无法校验"发起请求的人"和"要访问的数据"是否属于同一家租户，而是**由请求方自己在参数里指定要看谁的数据，系统照单执行**。之所以至今没出过事——**只有一家租户在用，参数里能填的也就那一家**。

**多租户之后**：同一套系统、同一个数据库要同时服务多家**互不相识、互相不能看见**的租户，且每次数据访问都必须**强制**判定归属，不能依赖开发者写代码时记得加过滤条件。

### 2.2 "租户"在 LG 具体指什么

产品定义的租户是**组织树上某一级的节点**。当前唯一的租户是 `Golden Section`：

```
Background development organization
    └── Global Authority
            └── Golden Section              ← 这一级是"租户"（一家租户）
                    ├── 子组织 A ──┐
                    │             ├──> Company（被投企业）  ← 同一家企业可挂在多个子组织下
                    └── 子组织 B ──┘
```

> 树上每一级长得一模一样，**数据库里没有任何字段标识"这一级是租户"**；且业务确认**层级深度不固定**，也不能用"第三层就是租户"来推断——**纯人为约定，因此必须新增一个显式标记**。

**企业挂在租户下面的子组织上，且可以同时挂多个**——这是正常业务形态；**但不会跨租户**。这条规则目前同样**只是人为约定，数据层面没有任何东西在守它**。

### 2.3 为什么这件事比想象中麻烦

现有隔离的粒度**落在租户下面若干级**——按最底层的"被投企业"分，而企业与租户之间还隔着子组织（层数不固定）。而**带"属于哪个租户"标记的数据表：一张都没有**；

另有 13 张表连"属于哪家企业"都没标，需要单独设计归属方案——清单与判断依据见**附一**。

所以租户级隔离要走一条链：**确定这个人属于哪个租户 → 展开该租户下的整棵子树 → 算出子树下所有被投企业 → 再按企业筛数据**。这条链目前有三处问题：

| # | 问题                             | 说明 |
|---|--------------------------------|---|
| 1 | **给不出"租户下全部企业"**               | 页面靠切换组织树逐个节点看公司（正常用法），但**不具备直查租户下全部公司**的能力——而租户级过滤要的正是这个集合。后端自动圈定时（如 chatbot 知识库检索）取的是"第一个组织"，**取到哪一级不确定，取到租户那一级就返回空**，且无提示 |
| 2 | **没有任何约束保证"不跨租户"**             | 那条业务规则**只存在于人为约定里，数据层面完全不设防**——把一家企业挂到另一家租户的组织下，数据库照收不误 |
| 3 | 目前风险：**多归属时"取第一个"，排序口径与页面不一致** | 归属有**两条互不同步的路径**，查哪条得到的集合可能不同。取第一条时：页面树按创建时间排序，**那条 SQL 却不排序**，两边对齐没有保证 |

> **问题 3 的严重度**：目前**无线上错误**（不排序时多半碰巧与页面一致），但属**依赖未定义行为**——执行计划或数据变动后就可能不一致，届时评分权重与评级会跟着变。**修法便宜**：补上与页面一致的排序即可，不必等多租户。

### 2.4 一个必须先解决的矛盾

系统有一条核心假设：**"没有绑定具体企业的账号 = 平台超级管理员"**，被四个模块当作硬前提使用。

多租户会让它直接失效——**租户管理员按定义就是"不属于某一家具体被投企业"的人**，于是会被系统认成平台超管、拿到全平台权限。这不是加个字段能补的，是**判断"你是谁"的依据本身要换掉**，而这个依据散落在四个模块里。**这是改造中风险最高的一块。**

## 三、现在的体检结果

| 问一句 | 答一句 |
|---|---|
| 系统知道"这份数据属于哪家租户"吗？ | **不知道。** 数据上没有这个标签，一张表都没有 |
| 那现在怎么决定"你能看谁的数据"？ | **页面自己说要看谁，系统就给谁。** 有四十个这样的功能入口 |
| 有没有哪个入口会核对"你到底是不是这家租户的人"？ | **一个都没有。** |
| 那为什么至今没出事？ | **因为只有一家租户**，页面里能填的也就那一家 |
| 能新开一家租户吗？ | **点得动，但开出来是个空壳**——没有管理员能登进去，还得人工补一堆东西 |
| 新租户的初始配置从哪来？ | **不是固定模板，是"抄数据库里碰到的第一家租户当前的设置"**——老租户改过什么，新租户跟着继承 |
| 能彻底注销一家租户吗？ | **不能。** 数据清不干净，人的登录状态还能继续用大约 300 天 |
| 前端做的那些权限限制算安全吗？ | **不算。** 它们存在浏览器本地，用户自己就能改 |
| 谁改了什么数据，查得到吗？ | **查不到。** 记录用的那段程序被注释掉了，表是空的 |

## 四、要做成什么样

### 先定方式：数据放在一起，但每条数据都能说清属于谁

做多租户常见有三条路线，我们选中间这条：

| 路线 | 大白话 | 判断 |
|---|---|---|
| 一个租户一个数据库 | 每家租户一套库，物理隔开 | **不选** |
| **一个数据库，数据带租户归属，由程序强制判定** | 数据还放在同一套表里，但每条数据都能说清"属于哪个租户"；每次访问由系统按登录身份决定你能看哪些 | **选这条** |
| 再往下一层：让数据库自己按租户过滤 | 在上面的基础上给每张表加租户 ID，连程序被绕过都能拦住 | **暂不做**（见第十节第 4 条） |

选中间这条，四个理由：

- **工作量适中**——不用拆库，也不用给上百张表逐一加字段、再回填历史数据，**7 周的工作量**（换算口径见第五节）。要把过滤做进数据库本身，得在这之上**再加约 5 周**
- **隔离目标已经达到**——每次访问都由系统按登录身份判定归属，"改个参数就能看别人数据"这条路被堵死，而这正是今天最大的敞口
- **不牺牲跨租户功能**——行业对标这类要把多家租户数据横向比较的能力还能继续做；拆成多个库，这类功能直接没了，这也是拆库被排除的主要原因
- **留了升级余地**——将来某家租户的合规要求更严，可以在这个基础上再叠一层数据库层过滤，不用推翻重做

### 再分步走

按依赖顺序分三步，另有第四步是"怎么开新租户"这件运营能力：

| | 干什么 | 做完之后 |
|---|---|---|
| **第 1 步** | 让系统认识"租户"这个概念：给组织打上标记，并且**把"你代表哪家租户"这个答案统一成一个** | 系统第一次能回答"这是谁家的数据" |
| **第 2 步** | 把那四十个功能入口，从"你说看谁就看谁"改成"按你的登录身份决定你能看谁"。同时**换掉第 2.4 节那条"没绑企业就是超管"的假设** | 改参数偷看别人数据这条路被堵死 |
| **第 3 步** | 立规矩：以后程序员万一忘了写检查，系统直接拒绝，而不是放行 | 不再依赖"人人都记得" |
| **第 4 步** | 开通新租户的向导、注销时的清理、以及禁止随意搬动组织 | 能安全地接第二家租户 |

前两步是"能不能安全接第二家租户"的门槛，第三步是加固、可以晚一点。

## 五、要花多久

先说清口径：下表给的是**工作量**，按"一个人全职做一周"换算。**"7 周"的意思是：只安排一个人做，就是 7 周；Java、Python、前端三个人分头并行，日历时间能压到 2 到 3 周。**

| 事项 | 工作量 | 说明 |
|---|---|---|
| 多租户改造（第 1–4 步） | **7 周** | 不含测试环境搭建、回归验证、灰度发布（经验上另占两到三成） |
| 企业级安全的工程部分 | **约 2 周** | 操作记录 + 登录日志 + 登录改造 + 变更管理等 |
| GDPR | **待定** | 不是纯工程活——保留多久、哪些信息要打码、跟 AI 供应商签什么协议，先要法务定 |

> 这些是**初步估算，还没经过团队正式预估**。

### 有一件事加人也没用

拿 SOC 2 报告需要**连续 3 到 12 个月的考察期**，用来证明"管控措施确实一直在生效"。这是日历时间，**加人压缩不了，也没法事后补三个月的记录**。

所以如果目标是某个销售季拿到认证，**工程什么时候必须就绪，要从那个日期倒着推**。这个倒推**不需要等工作量数字**，现在就能做。

### 有一件事可以省

**"零信任"和多租户第 1 步其实是同一件事**（都是让登录环节承载可信身份）。合并做能省一部分，**分开排期就要做两遍**。建议合并成一个项目，不要拆成两个。

## 六、SOC 2 和 GDPR

**SOC 2 Type II** —— 一份由独立会计师事务所出的审计报告，证明"这家服务商管客户数据是靠谱的"。**它不是证书，是报告**，通常在保密协议下给客户查阅。

Type I 只看某个时间点上制度**设计**得对不对；**Type II 要看一段时间里制度是否一直在运行**。好比前者检查"你装了监控摄像头"，后者检查"这半年摄像头一直开着、录像一直在存、有人定期查看"。企业采购基本只认 Type II。

审计方会问的问题，我们现在大多答不上来：谁改了什么数据（没记录）、谁登录过（没日志）、有没有双重验证（没有）、密码有什么要求（没有要求）、离职多久回收权限（登录状态还能用约 300 天）、上生产有没有人批（有人点，但没留痕、也没规定"批的人不能是写的人"）、依赖库的漏洞怎么管（没扫）。

**GDPR** —— 欧盟的个人信息保护法规。核心是"用户有权知道你存了他什么、并要求你删掉"。现状是：**有个人数据（包括完整的 AI 对话记录），但完全没有应对这些要求的能力**——没有打码、没有"删除我的数据"、没有导出、没有保留期限。而且**目前根本没有"彻底删除一家租户"的能力**。

## 七、有两件事比多租户更急

优先级高于全部多租户工作。这两件让"你是谁"有两条可以被冒充的途径——不解决，前面所有隔离分析都是纸上谈兵。

| # | 是什么 | 后果 |
|---|---|---|
| 1 | 生产环境用来给登录状态签名的那把"钥匙"，**就是代码里那句"请在生产环境替换"的示例值**；而且这个配置文件躺在代码仓库里（同一个文件还有数据库密码、云平台密钥、支付平台生产密钥） | **任何人拿到这把公开的钥匙，就能把自己伪装成任意用户** |
| 2 | 有一个按邮箱查组织状态的接口，**要登录但不看你是谁**，专门查超级管理员账号并返回其密码的可解密形式，解密钥匙还写死在代码里 | **任意已登录用户都能拿到任意超级管理员的明文密码** |

具体代码位置、涉及哪些配置文件、以及为什么忽略规则没挡住，已经逐条定位留档，可以随时给到负责修的工程师。**这两件不需要排期讨论，立即做。**

## 八、需要产品 / 业务拍板的事

工程这边无法自己决定、但不定就没法收敛方案的问题：

**关于范围**

1. **一家租户内部允许几层子组织？是否需要跨租户共享数据（比如行业基准）？**
2. **要不要租户级的单点登录 / 独立域名 / 品牌定制？** —— 直接决定第 4 步的规模
3. **历史数据怎么归属？** —— 现在没有组织标记的数据，能否全部归给 Golden Section

**关于配置该按平台还是按租户**

4. **KPA 配置：每家租户各一份，还是全平台统一？** —— 现在两种口径混着：分类骨架和权重是每家租户一份，但方法论正文是全平台统一的（改一处，所有租户跟着变）
5. **财务评分的类目权重和等级：平台统一还是每家租户可自定义？** —— 现在是全平台统一，而同类的开发评分配置却是按租户分的，两边口径不一致
6. **技术栈类型、第三方工具目录：平台统一还是每家租户可自定义？** —— 现在是全平台统一（但技术栈的层级和条目已经是按租户分的）

第 4–6 条**不影响"能不能安全接第二家租户"**，它们是产品形态问题；但第 5 条如果选"按租户"，会多出两张表的改造，要并进第 1 步。

---

## 九、不做 / 拖着不做会怎样

- **窗口是会关的。** 现在所有毛病都不可能发生，仅仅因为只有一家租户。**第二家租户上线之日全部同时激活。** 如果商务先于工程签下第二家客户，团队就得**在生产环境已经有租户数据的情况下**做前三步改造，成本和风险是现在做的数倍。
- **债在利滚利。** 每新增一个功能入口，都在延续"看谁的数据由页面自己填"这个模式，四十这个数字**还在长**。
- **SOC 2 的日历时间补不回来。** 这是唯一一个"晚一天就是晚一天"、加人也救不回来的事，**也因此是现在最需要拍板排期的部分**。

另外还有一条声明风险：**设计文档里已经写了的数据库隔离、权限角色、GDPR 删除能力，代码里都没有实现。** 如果这些描述被引用到客户安全问卷或审计材料里，构成不实陈述。清理这些描述本身就是 SOC 2 准备工作的一部分。

---

## 十、建议的动作顺序

1. **立即做**：第七节那两件事，不需要排期讨论
2. **和第二家租户的商务节奏对齐**：第四节的第 1、2 步是"能安全接第二家租户"的门槛，必须在那之前完成；第 3 步是加固，可以晚一点
3. **从 SOC 2 目标日期倒推**：操作记录 + 登录改造（和第 1 步合并做），因为考察期要求制度先上线运行
4. **明确不做**：在数据库层面再加一道自动过滤的门（让数据库按租户标记自己拦）。**不是因为贵**——它的工作量比上面三步还小——而是它要能工作，前提是系统先能给出可信的"当前是哪家租户"，而那正是第 1 步的事；第 1 步做完，它的大部分好处也已经拿到了

## 附一：那 13 张没有归属标记的表

### 先说判断依据

一张表要不要加"属于哪个租户"的字段，看三条：

1. **里面装的是不是某家租户自己的数据** —— 币种、时区、菜单定义这类全平台共用的，不需要
2. **现在能不能可靠、便宜地查出它属于谁** —— 如果绕一跳就能查到、且被绕到的那张表本身有归属，可以先不加
3. **有没有必须按租户操作它的场景** —— 租户级过滤、注销租户时清数据、GDPR 的"删除我的数据"、出事时判断影响了哪几家租户

下面这 13 张：**第 1 条全部成立**（装的都是租户的业务数据，不是公共字典）；**第 2 条全部不成立或代价很高**；**第 3 条至少命中一项**。所以它们需要单独设计归属方案，而不是简单加个字段就行。

> **已决定移除**：原清单里的 3 张 LangGraph 检查点表（`checkpoints` / `checkpoint_blobs` / `checkpoint_writes`）已确认**当前无用**，将随财务解析图摘掉 checkpointer 一并下线，故不列入归属改造范围（清单由 16 张降为 13 张）。**遗留数据需在下线时一并清理**——表里存着历史全部解析出的财务数据，且全仓无任何清理机制。

### A 组：现在查不出属于谁（4 张）

| 表 | 里面装的是什么 | 为什么查不出 |
|---|---|---|
| `files` | **全站文件的登记表**（谁传的什么文件、存在哪） | 没有可靠的反查线索，得从 6 个以上来源反推，而且这些字段都没建索引 |
| `ai_rag_space` | 知识库空间 | **原本记录归属的那张表被一次数据库变更整表删掉了**，现在这些空间等于"全局资产" |
| `ai_rag_fin_report_chunk` | **财报正文的向量分段** | 只有一个公司参考字段，代码注释明确写了它不是用来过滤的 |
| `ai_rag_playbook_chunk` | 方法论正文的向量分段 | 代码注释写的是"零业务列" |

> 只有 `files` 是**连线索都没有**；其余三张是**线索被删掉了或本来就没建**。这一组是最麻烦的——不设计新方案，租户级过滤在这里根本无从下手。

### B 组：能查出，但要绕一跳（7 张）

| 表 | 里面装的是什么 | 怎么才能查出归属 |
|---|---|---|
| `ai_chatbot_message` | **全部聊天对话正文**和附件绑定 | 经会话表反查（而会话表的公司字段可能是空的） |
| `ai_llm_conversation` | **完整的提问与回答全文** | 经调用日志反查 |
| `ai_trace_span` | 每一步调用的上下文 | 经链路表反查 |
| `ai_rag_search_log` | **用户输入的原始提问** | 只有用户 ID 和一串空间 ID |
| `ai_rag_operation_log` | 知识库的写操作记录 | 只有空间 ID —— 而空间本身就在 A 组，归属已丢 |
| `ai_financial_extraction_mapping_data` | 逐单元格的解析结果和人工修改痕迹 | 经文件反查 —— 而文件登记表也在 A 组，**这条链是断的** |
| `ai_financial_extraction_task_state_log` | 解析任务的状态变化（含模型识别的原文） | 经任务表反查 |

> 这一组"能查出"要打个折扣：其中两张绕过去之后落在 A 组的表上，实际同样查不出。

### C 组：能查出，但要绕两跳，而且量很大（2 张）

| 表 | 里面装的是什么 | 规模 |
|---|---|---|
| `r_financial_normalization` | 归一化财务明细的关联关系 | **63 万行 / 102 MB** |
| `r_financial_forecast_year_version` | 财务预测版本的关联关系 | **13.7 万行 / 24 MB** |

> 这一组技术上查得出，但每次租户级过滤都要多绕两跳 JOIN，在这个数据量上是实打实的性能代价。

### 不加会怎样

- **租户级过滤做不全** —— A 组无从下手，B 组有两张实际也查不出。也就是说即使前三步做完，这些表上仍然没有可靠的租户边界
- **"彻底注销一家租户"仍然做不到** —— 这 13 张表是主要原因；今天所谓的"删除公司"其实只是停用、不删数据
- **GDPR 的"删除我的数据"无法落地** —— 恰恰是这一组里装着**完整的对话正文、用户原始提问、解析出的财务数据**，也就是最需要能定位到人的那部分
- **出事时说不清影响面** —— 一旦有租户投诉数据串了，这些表答不上来"这些行是谁的"
