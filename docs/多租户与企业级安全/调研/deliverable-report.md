# 多租户与企业级安全

> 关联文档: [决策摘要](./executive-summary.md)（含完整数字与代码依据）

---

## 一、目标是什么

**让系统能随时新增一个租户，并且每次数据访问都强制校验、强制隔离。**

拆成四句可验收的话：

1. 新开一个租户，开完就能用——有管理员能登进去、配置来自固定模板
2. 每次访问都由**登录身份**决定能看谁的数据，请求参数说了不算
3. 父租户能看到自己名下**全部**子租户的数据；客户能在自己子树内自助建组织、管账号
4. 注销一个租户时，数据和登录状态都能真正清掉

另有一个并行目标：**具备企业级采购的准入资格**（SOC 2 Type II、GDPR）。

---

## 二、存在的问题

需要产品 / 业务拍板，工程定不了。带 💡 的是我们的建议。

| # | 问题 | 建议 |
|---|---|---|
| 1 | **是否需要跨租户共享数据**（如行业基准） | 💡 **需要**。行业对标是产品核心能力，也是"不拆库"的主要理由。但要拿到客户对数据进入基准的授权立场 |
| 2 | **是否需要租户级 SSO、独立域名、品牌定制** | 💡 **首个外部租户不做**。它直接决定第 4 步规模，等有客户明确要求再上 |
| 3 | **那 13 张无归属列的表怎么归** | 💡 大部分能经关联表反查、不用动；**只有 `files` 需要单独设计**。可等真要做租户级删除时再定 |
| 4 | **KPA 配置：租户级还是平台级** | 💡 现在两种口径混着（分类骨架每租户一份、方法论正文全平台统一）。建议**方法论正文明确为平台级**并拆成全局表，其余保持租户级 |
| 5 | **财务评分的类目权重与等级：租户级还是平台级** | 💡 现为全平台一套，而同类的开发评分配置是租户级的。建议**对齐成租户级**——若选此项，第 1 步内要追加两张表的改造 |
| 6 | **技术栈类型、第三方工具目录：租户级还是平台级** | 💡 **保持平台级**。技术栈的层级与条目已是租户级，这两项作为平台统一目录更合理 |
| 7 | **首个真实外部租户的预期时间** | 💡 这是全部工作的实际截止时间，也是"要不要走过渡方案"的唯一判断依据，请尽早给 |

另有两项不在工程范围内、但会卡住 SOC 2：**审计机构选型与档期**（采购）、**GDPR 的保留期与脱敏范围**（法务）。

## 三、现在是怎么做的

### 3.1 已经做到的

- **隔离键已经在表上**：管理端 `organization_id`、客户端 `company_id`。Java 侧 151 张业务表中 85 张带公司键、21 张带组织键
- **递归展开子树的能力已存在**（`findByTreeInId`）
- **有一个正面样板**：财务对标模块 3 个接口有完整的"请求进来时逐个核对"实现 + 回归测试，可直接当模板
- **知识库的归属链是通的**：分段表 → 空间 → 业务关联表（带组织 ID / 公司 ID），每跳都有索引

### 3.2 完全没做的

| 项 | 现状 |
|---|---|
| **校验用户是否属于本组织** | **40 个功能入口，0 个校验**。由请求方在参数里自报要看谁的数据，系统照单执行 |
| 租户身份进登录凭证 | 没有。登录凭证里不带组织 ID |
| 授权圈定递归展开子树 | 没有，用的是等值查询 → **父租户看不到子租户的数据** |
| 跨租户约束 | 没有。把一家企业挂到另一个租户的组织下，数据库照收不误 |
| 强制过滤机制 | 没有。程序员漏写检查就是放行 |
| 多因素认证 / 单点登录 / 密码策略 / 调用频率限制 | 全都没有 |
| "彻底删除一家租户"的能力 | 没有。所谓"删除公司"实为停用、不删数据 |

### 3.3 做了一半的

| 项 | 做了什么 | 缺什么 |
|---|---|---|
| **租户身份判定** | 有 6 处各自独立的实现 | 口径不统一，取的树层级还不一致（有的取树根、有的取第一个叶子） |
| **企业归属** | 两条路径都在写（直连表 / 经 Portfolio） | **两条互不同步**，可以指向不同组织 |
| **一企业多组织** | 接口收数组、支持多个 | 界面恒为单选并包成单元素数组，所以线上实际一对一 |
| **租户开通** | 点得动 | 开出来是**空壳**——没有管理员能登进去；初始配置是运行时**抄第一家租户的当前设置**，不是固定模板 |
| **组织树维护** | 能建、能搬 | **零权限检查**，任何登录用户能在任意位置建、能搬成环，搬完排名口径悄悄改变且无记录 |
| **权限体系** | 角色菜单 16 张表结构完整 | 没落地成访问控制——权限工具类写好了从没被调用，实质是"菜单显示配置" |
| **审计日志** | 表建好了、116 处注解标好了 | **唯一负责写入的代码被注释掉了**，表是空的 |
| **前端权限** | 有四层门禁 | 全部基于浏览器本地存储，用户自己能改，**不能算安全边界** |
| **知识库授权** | 归属链存在 | **召回路径不走这条链**——空间存在且未软删就放行；`/devSupport` 检索面板直接吃客户端给的空间 ID |

### 3.4 眼下的实际风险

生产现有 **5 个租户**（1 个真实客户 + 4 个测试组织），所以跨租户越权**今天就能复现**；只是跨过去看到的是我们自己的测试数据，**还没有客户间泄露**。

**但有两件事比多租户更急**，它们让"你是谁"本身可以被伪造：

| # | 是什么 | 后果 |
|---|---|---|
| 1 | 生产给登录状态签名的密钥，就是代码里那句"请在生产环境替换"的示例值；该配置文件在代码仓库里（同文件还有数据库密码、云平台密钥、支付平台生产密钥） | **任何人拿到这个公开密钥就能伪装成任意用户** |
| 2 | 有个按邮箱查组织状态的接口，要登录但不看你是谁，专查超管账号并返回其密码的可解密形式，解密钥匙写死在代码里 | **任意已登录用户都能拿到任意超管的明文密码** |

这两件不解决，下面所有隔离工作都只是纸上谈兵。

## 四、为了这个目标要怎么做

### 4.0 立即做（不进排期讨论）

轮换全部凭据 + 更换签名密钥（会导致全员重新登录）+ 从提交历史清除 + 那个接口改成"只能查自己"或直接下线。

### 4.1 四步走

| 步 | 具体做什么 | 完成后 |
|---|---|---|
| **1** | **6 处租户身份判定收敛成 1 处**并写进登录凭证（不需要新增字段）；替换"未绑企业即超管"这条假设（涉 4 个模块）；补"多归属不得越出同一子树"的约束 | 系统首次能可靠回答"这是谁家的数据" |
| **2** | **40 个入口**改为按登录身份判定归属；**圈定范围改成递归展开子树**（否则父租户看不到子租户）；修 2 处"报别人的组织反而能看更多"的反向漏洞；前端建统一"当前租户"概念 | 参数越权这条路关闭 |
| **3** | 建立强制过滤机制：漏写检查即拒绝；**13 张无归属列的表**定归属方案（其中 12 张能反查，只有 `files` 要单独设计） | 不再依赖开发者自律 |
| **4** | 开通向导（平台建根组织 + 管理账号，配置改固定模板）、注销时的完整清理；**把建组织 / 搬组织限制在自己子树内** | 能安全接外部租户，且客户可自助管理 |

前两步是"能不能安全接外部租户"的门槛；第 3 步是加固，可以晚一点。

### 4.2 企业级安全

| 项 | 做什么 |
|---|---|
| 审计日志 | 恢复写入 + 补独立登录日志 + 定保留策略 |
| 零信任 | 登录改造 + 多因素/单点登录 + 短有效期 + 可吊销 + 频率限制。**与第 1 步同源，合并立项**，分开做要做两遍 |
| SOC 2 工程侧 | 变更留痕与职责分离、构建期漏洞扫描、加密、可用性监控 |
| GDPR | 数据清点、删除与导出、保留策略、脱敏、供应商协议（**需法务先定**） |

### 4.3 工作量

按"一名工程师全职一周"计。**初步估算，未经团队正式评审。**

| 事项 | 工作量 |
|---|---|
| 多租户第 1–4 步 | **约 7 人周**（三人并行约 2–3 周；另占 20–30% 用于测试环境、回归、灰度） |
| 企业级安全工程侧 | **约 2 人周** |
| GDPR 工程侧 | 待定（需法务前置） |
| SOC 2 考察期 | **3–12 个月日历时间，加人压不动** |

**SOC 2 Type II 是外部会计师事务所出的审计报告，不是研发交付物。** 研发只负责"让审计方问得出的问题有答案"，就是上表那 2 人周；报告出具、机构选型、审计费、合规工具年费、渗透测试、政策文件、考察期，都不计研发工时。

### 4.4 明确不做

**在数据库层再加一道自动过滤的门。** 不是因为贵（工作量比上面还小），而是它要能工作，前提是系统先能给出可信的"当前是哪个租户"——那正是第 1 步；第 1 步做完，它的大部分收益已经拿到了。
