# 设计理念：LG 多租户的定义、取舍与推进顺序

> 关联文档: [决策摘要](./executive-summary.md) | [系统架构](./system-architecture.md) | [Java 端](./java-design.md) | [Python 端](./python-design.md) | [前端](./frontend-design.md) | [证据代码](./code-examples.md)

本文回答 **WHY**：租户为什么这样定义、几条实现路径怎么取舍、为什么建议先做应用层而不是数据库层。**HOW** 见 [系统架构](./system-architecture.md)。

---

## 1. 租户的定义与它带来的后果

### 1.1 定义（2026-09-07 与团队核实后修订）

**租户 = `organization` 树上的任意一个节点；父节点同时管理其下的子租户（整棵子树）。**

隔离键**已经存在**，分两端：

| 端 | 隔离键 |
|---|---|
| 管理端（Portfolio / 组织视角） | `organization_id` |
| 客户端（被投企业视角） | `company_id` |

所有租户的数据在**同一个数据库、同一套表**里，靠这两个键做逻辑隔离。

> ⚠️ **本节替换了调研初期的锚定。** 早期按「租户 = Golden Section 那一级、全平台唯一租户、数据库里无任何标识字段」立论，与系统实际不符——**每个组织节点都是租户，`organization_id` 就是租户键，不需要新增标识列**。受此影响的结论已在各文档同步修订。

**生产现状（2026-09-07）：5 个租户** —— 1 个 `Golden Section`（真实客户）+ 4 个测试组织（各挂几家公司）。

由此有三个后果：

**后果一：缺的不是字段，是强制。**

租户键早就在表上——`organization_id` 在 21 个 JPA 实体上、`company_id` 在 85 个上。但它**不进认证链**（JWT 只带 `sub`）、**不在查询期被校验**，于是**由请求方在参数里指定要看哪个租户的数据，服务端照单执行**。40 个组织维度端点中，校验"调用者是否属于它操作的那个组织"的是 **0 个**。

**后果二：子租户要求授权链必须递归展开。**

"父租户管理其下子租户"意味着按租户圈定数据时必须展开整棵子树。递归 CTE 在仓里**已经有**（`OrganizationRepository.findByTreeInId`），但**授权链用的是等值**（`CompanyGroupRepository.findVisibleCompanies` 的 `cg.organization_id = :orgId`）。这一处同时造成两件事：

- 父租户**看不到子租户的数据** —— 功能缺失
- 传任意 `organizationId` 就能看任意租户 —— 越权

**后果三：越权今天就能复现，但后果目前限于内部。**

5 个租户都在生产库里，所以"改个参数读另一个租户"不是推演，是**可现场演示**的。但跨过边界看到的是**我们自己的 4 个测试组织**，所以**目前尚无客户间数据泄露**。

因此风险窗口不在"第二家客户上线"，而在**第一个真实外部租户进来的那天**——可能是新签客户，也可能是某个测试组织转正。那一刻同一批缺陷的后果从内部权限问题变成客户数据泄露。

### 1.2 两层边界，只有下面那层被守着

| 层 | 键 | 边界性质 | 违反后果 |
|---|---|---|---|
| **租户间**（organization 子树） | `organization_id` | **信任边界**，互不可见 | 一个租户的数据泄漏给另一个租户 |
| 租户内（portfolio / company） | `company_id` | **权限边界**，按角色可见 | 越权，但仍在同一租户内部 |

团队过去所有的隔离工作——包括做得不错的几处，如财务对标模块那套完整的授权守卫——都在处理**下面那层**。

上面那层的**键是有的，但没有任何一处在请求期强制校验它**。这是本次调研的重点，也是"多租户改造"在 LG 语境下的实际含义：**不是引入租户概念，而是把已有的租户键变成每次访问都必须过的关。**

### 1.3 一个 company 可以挂在多个组织下

**业务规则（2026-09-02 确认）**：一个 company **可以同时挂在多个子组织上**，这是正常业务形态。

在新锚定下这条规则需要重新表述：既然每个组织都是租户，"一家公司挂在多个组织下"本身就意味着它被多个租户共享。因此**不能加"一公司一组织"式的唯一约束**——那会违反业务规则。真正需要约束的是"**共享范围不得超出某个上级租户的子树**"，即多归属必须落在同一棵子树内。这条约束目前在数据层面**零实现**（详见[系统架构](./system-architecture.md) §1.2 与 §3）。

## 2. 一个不能回避的模型冲突

平台当前的核心不变式是：

> **`company_id` 为空 ⟺ 超级管理员**

它被 Java 登录链、Python chatbot 端类型判定、RAG 写操作闸门、财务提取 ACL **四个模块当作硬前提**依赖，并且在多处代码注释中被显式写为"平台不变式，不变式破产属平台级问题"。

它与"每个组织都是租户"直接冲突，而且**不需要等新客户**——只要给现有 5 个组织中的任何一个配一个不绑定具体公司的管理员，他立刻就是平台超管：

- 租户管理员按定义就是"不隶属于某一家具体被投企业"的人 → 其 `company_id` 天然为空
- 于是他在系统里**与平台超管完全不可区分**
- 后果是：他立刻获得跨公司列表与回放、RAG 空间的增删改（而 RAG 空间是全局资产、无归属列）、以及"模拟任意用户/任意组织/任意公司身份"的能力

**这不是加一个字段能补的缺口，是权限判定的基础需要更换**：从"有没有 company_id"换成"显式的角色 + 显式的租户上下文"。它是第 2 步中风险最高、也最不该被拆散的一块。

## 3. 隔离成熟度模型：为什么要分第 0–4 档

把隔离能力分级，是为了让"要做到什么程度"成为一个可决策的问题，而不是一句"要做好隔离"。

| 级别 | 判定标准 | 漏写一处的后果 |
|---|---|---|
| 第 0 档 | 无租户条件 | 全量泄漏 |
| 第 1 档 | 租户 ID 来自**客户端**，手写进 WHERE | 改个参数就越权 |
| 第 2 档 | 租户 ID 来自**会话**，服务端强制 | 漏写一处 = 该处全量泄漏 |
| 第 3 档 | 框架强制，漏写即拒绝 | 漏写 = 报错，不泄漏 |
| 第 4 档 | 数据库强制 | 应用被绕过时仍然安全 |

LG 当前处于 **第 1 档**，且有相当数量的接口停留在第 0 档。

**关键认知**：第 1 档 → 第 2 档是**性质变化**（从"不安全"到"安全但脆弱"），第 2 档 → 第 3 档是**可靠性变化**（从"靠人不漏写"到"漏写也安全"），第 3 档 → 第 4 档是**纵深防御**（从"应用正确就安全"到"应用被绕过也安全"）。

三段的收益递减非常明显，而成本递增同样明显。这是后面"不建议做第 4 档"的全部依据。

## 4. 三条实现路径的取舍

PRD 要求明确多方案的 tradeoffs。以下是三条真实可选的路径。

### 应用层强制（推荐）

**做法**：在认证链中确立单一可信的租户上下文（JWT claim 或强制读会话），所有数据访问从该上下文取租户，客户端入参降级为纯筛选条件；再加一层框架级强制过滤。

| 维度 | 评价 |
|---|---|
| 成本 | **7 人周**（初步估算；明细见系统架构文档 §10） |
| 收益 | 达到第 3 档，覆盖全部已识别的越权面 |
| 风险 | 改动面广（40 个接口 + 前端上下文重构），但每一步可独立验证、可灰度 |
| 对现有功能影响 | 小。跨租户聚合功能（对标基准）不受影响 |
| 可逆性 | 高 |

**取舍**：这条路径不提供"应用被绕过时的兜底"。接受这一点的理由是：当前威胁模型里，"应用被绕过"（直连数据库）意味着攻击者已经拿到数据库凭据，而在那种情形下 RLS 也会因为服务共用超级账号而失效（超级用户默认绕过 RLS）。

### 行级策略（不建议现在做）

**做法**：共享同一套表 + 每张表加租户 ID 列 + PostgreSQL 行级策略（RLS）。同类手段中的分库 / 分 schema / 分区已在系统架构文档 §6.2 排除。详细评估见 §6。

| 维度 | 评价 |
|---|---|
| 成本 | 在应用层强制之上**额外 5 人周**（初步估算；明细见系统架构文档 §11） |
| 收益 | 增加第 4 档纵深；对某些企业客户问卷是加分项 |
| 风险 | 高。需关闭生产 `ddl-auto`、拆分数据库角色、85+ 张表加列回填、两个物理库各做一遍 |
| 对现有功能影响 | 跨租户聚合（benchmark 同侪集、组织级汇总）须逐条做策略豁免，漏排即表现为"数据莫名查不到" |
| 可逆性 | 低 |

**取舍的核心**：数据库级隔离的价值是给应用层兜底，而 RLS 策略需要一个可信的"当前租户"值——**那个值恰恰是当前最缺的东西**。先做行级策略等于在没有地基的情况下先盖二层；而做完应用层强制之后，它的边际收益已经很小。

**若未来要做行级策略**，唯一可行前提是先引入反规范化的 `tenant_id` 列（写入时打戳），让策略谓词从"递归子树集合成员判断"退回"等值判断"。这本身就是第 3 步的自然延伸。

### 独立部署（不改代码，每个客户一套）

**做法**：不改代码，每个客户一套独立部署（独立数据库、独立应用实例）。

| 维度 | 评价 |
|---|---|
| 成本 | 近期最低（仅部署与运维自动化） |
| 收益 | 立刻可以接外部客户，隔离强度实际上是最高的 |
| 风险 | 运维成本随客户数线性增长；版本碎片化；跨租户功能（行业基准对标）无法实现；单客户成本高，不适合中小客户 |
| 对商业模式影响 | 大。基本排除自助注册与低价位产品线 |
| 可逆性 | 中（后续仍需做应用层强制才能合并） |

**取舍**：如果第一个真实外部租户进来的时间早于**第 1 步 + 第 2 步**能完成的时间，**独立部署是一个正当的过渡选择**，不应被视为技术上的失败。它的代价是运维与产品形态，而不是安全。研发建议：**把独立部署作为时间不够时的显式备选，而不是默认发生的结果。**

## 5. 为什么"5 个租户里只有 1 个是真客户"改变了论证方式

生产库现有 **5 个租户**：1 个 `Golden Section`（真实客户）+ 4 个测试组织（各挂几家公司）。这个组合改变三件事。

### 5.1 越权今天就能复现，但目前只伤到自己

本报告列出的 40 个无归属校验的接口、2 处反向权限倒挂、组织树任意读取、RAG 全局空间等，**今天就可以跨租户复现**——生产库里有 5 个租户可越。

但越过去看到的是**我们自己的 4 个测试组织**，所以**目前没有客户间数据泄露**。

这个区分必须在汇报时讲清楚，否则两个方向都会说错：

- 说成"潜伏缺陷、当前不可利用" —— **低估**了，它已经可以现场演示
- 说成"正在泄漏客户数据" —— **高估**了，跨过去只有测试数据

准确说法是：**边界已经能被越过是既成事实，只是被越过的那一侧暂时没有别的客户。**

### 5.2 改造成本仍远低于常规多租户改造，但原因换了

常规多租户改造最贵、最容易出事的部分是**存量数据的租户归属回填与歧义消解**。在 LG 这部分几乎不存在——但原因与调研初期的判断不同：

| | 早期判断（已作废） | 实际 |
|---|---|---|
| 要新增租户标识列 | 需在 `organization` 上加列 | **不需要**，`organization_id` 本身就是租户键 |
| 要标定哪些节点是租户 | 1 个 | **不需要标定**，每个组织节点都是租户 |
| 存量数据归属回填 | 一次全量 UPDATE | **不需要回填**，21 / 85 个实体上的键早就有值 |

省下来的不只是回填工作——**"引入租户概念"这件事整体不存在**。剩下的是纯粹的强制与收敛工作。

但有一项比早期估计**更重**：子租户要求授权链递归展开子树，而现在是等值查询（§1.1 后果二）。这不是加一个 CTE 就完事——`findVisibleCompanies` 的全部调用方、以及依赖"取第一个组织"的 6 处实现都要跟着改。

**净效果需要重估**：加字段与回填的工作没有了，递归改造的工作变重了，两者方向相反。系统架构文档 §10 的改动项清单已按新锚定修订，总量待排期时重新核定。

### 5.3 窗口的定义变了

早期把窗口定在"第二家客户上线"。修订后：**窗口在第一个真实外部租户进来的那天**——可能是新签客户，也可能是某个测试组织转正对外。

这个差别是实质性的：

- 后者**可能比前者早得多**
- 后者**可能不经过商务流程**——把某个测试组织交给外部试点用户，就已经跨过去了

所以排期依据不只是商务节点，还包括**"哪个组织会第一个交到外部人手上"这个运营决定**。这个决定目前没有任何技术门槛在拦着。

## 6. 推进顺序的原则

1. **身份可信优先于隔离。** 存在两条身份伪造路径时，任何隔离设计都只有纸面价值。这两条不进排期讨论，直接做。
2. **可信上下文优先于强制机制。** 先有单一可信的租户来源，再谈在哪里强制它。顺序反了会得到一个"强制过滤了一个不可信的值"的系统。
3. **收敛优先于新增。** 目前"我在哪个组织"有 6 个实现。新增第 7 个（哪怕它是对的）只会让问题更糟。第 1 步的本质是删掉 5 个。
4. **应用层做到第 3 档之后再评估第 4 档。** 不预设第 4 档一定要做——做完第 3 档后重新评估边际收益，很可能结论是不做。
5. **零信任与多租户合并推进。** 零信任工程侧初估 3 人天，其中登录改造与第 1 步是同一件事（认证链承载可信身份与租户上下文），分开排期就要做两遍。
6. **文档与代码对齐是合规前提。** 现有设计文档中描述的 RLS、数据库角色、GDPR 擦除表均无对应实现，若被引用到客户安全问卷或审计材料中会构成实质陈述风险。清理这些描述本身就是 SOC 2 准备工作的一部分。
