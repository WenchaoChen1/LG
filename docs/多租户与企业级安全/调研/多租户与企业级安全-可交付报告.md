## 一、"多租户架构"在 Looking Glass 语境下的具体含义

### 目标是什么——详情
- 使系统能够随时新增一个租户，并且对每个租户的数据、访问进行强制校验和隔离。

### 存在的问题与建议
- **问题**：
  - 租户主体身份的判定散落在代码的 6 处独立实现中，且取树层级不一致；系统硬编码"未绑定企业的账号即平台超级管理员"的假设，被 4 个模块作为前提使用，与"每个组织即租户"的模型直接冲突。
- **建议**：在推进任何隔离方案前，先将租户主体身份的判定收敛为唯一实现，并替换上述硬假设，该项列为改造中风险最高的一环。

### 现状——哪些已实现、哪些未实现
- **已实现**：数据模型层面已存在租户键——管理端 `organization_id`、客户端 `company_id`；Java 侧 151 张业务表中 85 张具备 `company_id`、21 张具备 `organization_id`。
- **未实现**：租户键未纳入登录凭证，也未在查询期被强制校验；接口不核对请求发起者与目标数据的租户归属关系，而由请求方在参数中自行指定可见范围，跨租户越权访问可稳定复现。

### 为达成目标要做什么
- 将租户身份判定统一为唯一实现并写入登录凭证；
- 移除"未绑企业即超管"的硬假设；
- 建立面向组织树的递归归属判定能力，供各访问路径统一调用。

## 二、支持多租户所需的技术改造与工作量

### 目标是什么——详情
- 建立可强制执行的租户隔离机制，覆盖数据隔离模型、租户开通与注销、组织级权限与管理三方面。

### 存在的问题与建议
- **问题**：约 40 个功能入口采用"参数自报归属"模式，数量随新功能持续增长；部分表存在归属反查链路断裂（`ai_financial_extraction_mapping_data` 依赖 `files`，而 `files` 无可靠反查线索）。
- **建议**：采用**共享数据库 + 应用层强制判定归属**的隔离方案。一库一租户方案将丧失跨租户能力且成本过高；数据库层行级过滤方案暂不引入，其价值依赖应用层身份统一后方可兑现。

### 现状——哪些已实现、哪些未实现
- **已实现**：85 张表具备 `company_id`、21 张具备 `organization_id`；递归展开子树的能力在仓库中已存在。
- **未实现**：
  - 递归展开能力未被授权链调用，导致父租户无法访问子租户数据；
  - 53 张无归属键的表中 13 张属于需处理范围（其中 12 张可经关联表反查、1 张 `files` 无从反查）；
  - 租户开通流程无向导，新开租户呈空壳状态，初始配置以"数据库中第一家租户当前设置"为模板复制；
  - 租户不支持彻底注销，数据无法清理，登录状态在注销后仍可延续约 300 天。

### 为达成目标要做什么

| 阶段 | 工作内容 | 完成后效果 |
|---|---|---|
| 第 1 步 | 统一租户身份判定并写入登录凭证；替换"未绑企业即超管"的硬假设 | 系统首次可靠回答数据归属 |
| 第 2 步 | 将约 40 个功能入口由"参数自报归属"改为"按登录身份判定归属"；圈定范围递归展开子树 | 关闭参数越权路径 |
| 第 3 步 | 建立强制校验机制：授权遗漏时系统默认拒绝 | 消除对开发者自律的依赖 |
| 第 4 步 | 租户开通与注销流程；将建/迁子组织的操作限制在自身子树内 | 具备安全接入外部租户的运营能力 |

## 三、SOC 2 Type II、GDPR、零信任与审计日志所需改造

### 目标是什么——详情
- 使系统具备通过 SOC 2 Type II 审计所需的技术支撑；建立 GDPR 数据主体权利响应能力；将登录环节升级为可信身份承载点（零信任）；补齐审计日志。

### 存在的问题与建议
- **问题**：SOC 2 Type II 为独立会计师事务所出具的审计报告，非研发交付物；其考察期 3–12 个月为日历时间，无法通过增员或事后补录压缩。
- **建议**：
  - 从目标 SOC 2 报告日期倒推工程就绪日期，该倒推可即刻进行，无须等待工时评估；
  - 将零信任与多租户第 1 步合并立项，两者均以"在登录环节承载可信身份"为核心，避免重复投入；
  - GDPR 相关工程动作须在法务先行确定保留策略、脱敏范围与 AI 供应商协议条款后启动。

### 现状——哪些已实现、哪些未实现
- **未实现**：数据变更审计、登录日志、双因子认证、密码强度策略、离职权限回收（登录状态可延续约 300 天）、生产发布审批留痕与职责分离、依赖库漏洞管理。
- **部分实现**：表存在，审计日志的记录功能未实现。
- **未实现（GDPR）**：无脱敏、无删除、无导出、无保留期限；尚不具备"彻底注销一家租户"的能力。

### 为达成目标要做什么

| 责任方 | 工作内容 |
|---|---|
| 研发 | 补齐操作记录、登录日志、登录改造、变更管理留痕；对齐设计文档与实际实现，避免不实陈述 |
| 外部审计事务所 | 报告出具与判定 |
| 采购 / 财务 | 审计机构选型、审计费、合规工具年费、独立渗透测试 |
| 管理 / 合规 | 人员、变更、事故响应等政策与流程文件 |
| 法务 | GDPR 保留期、脱敏范围与 AI 供应商协议条款 |

## 四、工作量与时间线的高层次估算

### 目标是什么——详情
- 提供粗粒度的工作量与时间线，用于路线图排期，不涉及详细故事点拆分。

### 存在的问题与建议
- **问题**：当前估算未经团队正式评审，且 GDPR 部分工时待定。
- **建议**：将下表作为路线图排期的输入基准，法务输入到位后再补齐 GDPR 工时。

### 现状——估算依据
- 工时口径采用"人周"（一名工程师全职一周）。
- 7 人周可解释为一人独做 7 周，或 Java / Python / 前端三人并行 2–3 周。
- 测试环境搭建、回归与灰度发布另占 20%–30%。

### 为达成目标要做什么

| 事项 | 工作量 / 时间 |
|---|---|
| 多租户改造（第 1–4 步） | 约 7 人周 |
| 企业级安全工程部分（审计日志、登录日志、登录改造、变更管理） | 约 2 人周 |
| GDPR 工程部分 | 待定（需法务前置输入） |
| SOC 2 考察期 | 3–12 个月日历时间，不可压缩 |

**排期原则**：
1. §六所列两项严重安全缺陷立即修复；
2. 多租户第 1、2 步须在首个真实外部租户接入前完成，第 3 步可稍后加固；
3. SOC 2 工程改造从目标报告日期倒推排期，并与多租户第 1 步合并实施。

## 五、关键风险、依赖与未知项

### 目标是什么——详情
- 识别可能影响范围与时间线的关键变量，为业务与产品决策提供输入。

### 存在的问题与建议
- **问题**：既有设计文档中已声明的数据库隔离、权限角色与 GDPR 删除能力在实现中缺失，若被引用至客户安全问卷或审计材料，构成不实陈述。
- **建议**：在启动 SOC 2 准备工作时，同步清理设计文档与实现之间的差异。

### 现状——风险与依赖清单

**风险**
1. "未绑企业即超管"假设分布于 4 个模块，任一遗漏即造成权限体系失效；
2. §六两项立即需修的安全缺陷未闭合前，任何隔离设计均无实质意义；
3. "参数自报归属"入口数量随新功能持续增长；
4. 13 张无归属表中的 `files` 无可靠反查线索，将导致租户级过滤、注销与 GDPR 删除仍存在盲区；
5. SOC 2 考察期为日历时间，无法通过资源投入压缩。

**依赖**
- 法务 / 合规：GDPR 保留期、脱敏范围、AI 供应商协议；
- 采购 / 财务：审计机构选型、审计与合规工具费用、独立渗透测试；
- 管理 / 合规：政策与流程文件体系；
- 产品 / 业务：见下方待决策事项。

### 为达成目标要做什么——待业务与产品决策事项

**范围类**
1. 是否需要跨租户共享数据（如行业基准），并获取客户对数据共享的授权立场；
2. 是否需要租户级 SSO、独立域名与品牌定制（直接决定第 4 步规模）；
3. 13 张无归属表的归属方案（现有 5 个租户，不宜再统一归入 Golden Section）。

**配置口径类**（不影响外部接客门槛，影响产品形态）
4. KPA 配置：租户级或平台级；
5. 财务评分类目权重与等级：租户级或平台级（若选租户级，需在第 1 步内追加两张表的改造）；
6. 技术栈类型与第三方工具目录：租户级或平台级。

## 六、研发视角的业务影响与 ROI

### 目标是什么——详情
- 明确本次改造所解锁的业务能力，以及延后或不做所带来的代价，为决策提供输入。

### 存在的问题与建议
- **问题**：生产环境存在两项优先级高于多租户全部工作的严重安全缺陷——
  1. 用于签名登录状态的密钥使用示例值，且随代码仓库公开（同文件包含数据库密码、云平台密钥、支付平台生产密钥），任何持有该密钥者可伪装为任意用户；
  2. 存在按邮箱查组织状态的接口，需登录但不校验调用者身份，返回超级管理员账号的可解密密文密码，解密密钥硬编码于代码中。
- **建议**：上述两项立即修复，无须进入排期讨论；未闭合前任何隔离方案讨论均无实质意义。

### 现状——尚未解锁的能力
- 首个真实外部租户接入的前置条件尚未具备；
- 企业级采购流程的准入资格（SOC 2 Type II）尚未具备；
- 欧盟数据主体相关业务的合规基础（GDPR）尚未具备；
- 客户安全问卷与实际实现之间存在差距，回答需依赖文档修饰。

### 为达成目标要做什么

**解锁的能力**
- 具备安全接入首个真实外部租户的前置条件，支撑外部试点扩展；
- 具备进入企业级采购流程的准入资格；
- 具备承接欧盟数据主体相关客户的合规基础；
- 消除因安全与合规缺位而被排除于候选名单的竞争劣势；
- 使客户安全问卷与供应商审查回答与实际实现一致，规避不实陈述。

**延后或不做的代价**
1. 若商务先于工程签下首个外部客户，改造须在生产环境已承载外部数据的条件下进行，成本与风险显著上升；
2. "参数自报归属"入口每增一处即扩大技术债；
3. SOC 2 考察期不可事后补偿，目标报告日期与工程就绪日期呈刚性绑定；
4. 设计文档与实现之间的差距若持续存在，将在审计或客户核对场景下形成商业信誉风险。

**建议动作顺序**
1. 立即修复上述两项严重安全缺陷；
2. 多租户第 1、2 步与首个真实外部租户接入时间对齐；
3. SOC 2 相关工程改造从目标认证日期倒推排期，与多租户第 1 步合并实施；
4. 明确不引入数据库层行级过滤——其价值依赖应用层身份统一，后者完成后主要收益已获得。
