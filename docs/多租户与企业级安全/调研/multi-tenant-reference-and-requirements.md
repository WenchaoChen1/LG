# 多租户最佳实践 —— 三种参考方案与功能需求

> 关联文档: [交付说明](./多租户与企业级安全-交付说明.md) | [系统架构](./system-architecture.md)
>
> 本文先梳理业界三种主流实现方案，再从中提炼"一套完整的多租户系统需要具备哪些功能"，作为需求基线。**不含 LG 的实施排期**。

---

## 一、三种参考实现方案

业界通用分类（AWS SaaS Lens 命名）：**Silo / Bridge / Pool**。三者的差别在于**隔离发生在哪一层**。

### 方案 A：Silo —— 每租户独立资源

**怎么实现**：每个租户一套独立数据库（或独立部署）。租户上下文只用于**路由到哪套资源**，不参与查询过滤。

- 技术落点：Hibernate `MultiTenancyStrategy=DATABASE` + `MultiTenantConnectionProvider` 按租户返回不同数据源
- 隔离强制点：**连接层**。拿到哪个连接，就只能看到哪个租户的数据

| 维度 | 评价 |
|---|---|
| 隔离强度 | 最强，边界是物理的 |[requirement-doc.md](../%E9%9C%80%E6%B1%82/requirement-doc.md)
| 单租户成本 | 最高，资源无法共享 |
| 运维复杂度 | 高，迁移/升级要逐租户执行 N 次 |
| 跨租户分析 | **做不了**（需另建数据仓库汇总） |
| 适用 | 强监管行业、数据驻留要求、单价高的大客户 |

### 方案 B：Bridge —— 共享库、每租户独立 schema（或分层混合）

**怎么实现**：一个数据库实例，每个租户一套 schema；连接建立后切换 `search_path`。也可指"部分资源池化、部分资源独立"的混合形态——如 Web 层共享、存储层按租户隔离。

- 技术落点：Hibernate `MultiTenancyStrategy=SCHEMA`
- 隔离强制点：**会话层**（`search_path`）

| 维度 | 评价 |
|---|---|
| 隔离强度 | 中上，边界清晰但共享实例资源 |
| 单租户成本 | 中 |
| 运维复杂度 | **迁移是主要痛点**——每次 DDL 要遍历全部 schema |
| 跨租户分析 | 需跨 schema UNION，成本高 |
| 适用 | 租户数量可控（几十到几百）、需要较强隔离叙事 |

### 方案 C：Pool —— 共享库共享表 + 租户列

**怎么实现**：所有租户共用同一套表，每行带租户标识；由应用层和/或数据库强制按该标识过滤。

- 技术落点（两层，可叠加）：
  - **应用层**：Hibernate 6 `@TenantId` 注解 + `CurrentTenantIdentifierResolver`，ORM 自动在查询中追加租户条件、写入时自动打戳
  - **数据库层**：PostgreSQL 行级安全（`CREATE POLICY` + `FORCE ROW LEVEL SECURITY`），策略谓词读会话变量（如 `current_setting('app.tenant_id')`）
- 隔离强制点：**ORM 拦截层 + 数据库策略层**

| 维度 | 评价 |
|---|---|
| 隔离强度 | 取决于强制是否无遗漏；两层叠加后接近 Bridge |
| 单租户成本 | **最低**，资源充分共享 |
| 运维复杂度 | 低，一次迁移覆盖全部租户 |
| 跨租户分析 | **最容易**，一条 SQL 即可 |
| 适用 | 租户数量大、单价低、需要跨租户能力的产品 |

> **数据库层的两个前提**：① 必须有可信的"当前租户"值可注入会话；② 应用连接**不能使用超级用户或带 `BYPASSRLS` 的角色**——超级用户默认绕过所有策略，不拆分角色等于策略未生效。

### 三者对比速查

| | Silo | Bridge | Pool |
|---|---|---|---|
| 隔离在哪层 | 连接 | 会话（schema） | ORM + 数据库策略 |
| 跨租户分析 | 不可行 | 困难 | 容易 |
| 新增租户成本 | 建库/建环境 | 建 schema + 迁移 | **插一行** |
| 迁移成本 | × N 套库 | × N 个 schema | × 1 |
| 最大风险 | 成本与版本分叉 | DDL 遍历遗漏 | **强制点有遗漏即泄漏** |

**行业现状**：主流做法是**按资源分别决策**而非全系统统一——计算层池化、数据层视客户等级分层（标准客户 Pool、企业客户 Silo）。这正是 Bridge 一词的实际含义。

## 二、方案选择的决定性因素

选型不取决于"哪个更先进"，而取决于以下四问：

1. **是否需要跨租户分析？** 需要 → 排除 Silo（跨租户聚合会被物理边界切断）
2. **是否有数据驻留或物理隔离的合同要求？** 有 → 该类客户必须 Silo，其余可 Pool（即 Bridge）
3. **租户数量与单价？** 数量大、单价低 → Pool；数量少、单价高 → Silo 可承受
4. **能否保证"每次访问都强制判定租户"？** 不能 → Pool 的隔离强度会退化为"取决于开发者是否记得写条件"

> 第 4 条是 Pool 方案的**成败关键**：租户列存在不等于隔离生效，**强制点无遗漏**才等于隔离生效。

## 三、一套完整多租户系统需要的功能

以下为功能需求基线，与具体方案无关（Silo / Bridge / Pool 都需要，只是实现手段不同）。每条给出**为什么需要**与**验收标准**。

### 3.1 租户身份与上下文

| # | 功能 | 为什么需要 | 验收标准 |
|---|---|---|---|
| 1.1 | **唯一的租户标识** | 无标识则无从隔离 | 每个租户有稳定、不可变、全局唯一的标识 |
| 1.2 | **租户上下文进入认证链** | 上下文若来自请求参数，等于让调用方自报身份 | 登录后签发的凭证内携带租户标识；服务端从凭证取值，**不从请求参数取** |
| 1.3 | **单一权威的上下文来源** | 多处各自实现会产生口径分歧 | 全系统只有一处解析"当前租户"，其余调用它 |
| 1.4 | **跨服务的上下文传递** | 微服务/异步任务丢失上下文即丢失隔离 | 服务间调用、消息消费、定时任务均能取得租户上下文；取不到时**拒绝执行而非放行** |

### 3.2 数据隔离与强制

| # | 功能 | 为什么需要 | 验收标准 |
|---|---|---|---|
| 2.1 | **每条业务数据可归属到租户** | 无归属的数据无法过滤、无法删除 | 所有业务表能直接或经明确路径判定租户归属，**无归属盲区** |
| 2.2 | **查询期强制过滤** | 依赖开发者手写条件必然有遗漏 | 由框架/ORM 统一追加租户条件，业务代码无需也无法绕开 |
| 2.3 | **写入期自动打戳** | 手动赋值会漏 | 新增数据的租户归属由框架写入，不依赖业务代码传参 |
| 2.4 | **越权即拒绝（默认拒绝）** | 默认放行的系统，漏写一处即泄漏一处 | 无法判定租户时返回错误，而非返回全量或空集 |
| 2.5 | **层级租户的子树展开** | 父租户需管理子租户时，等值过滤会漏掉子树 | 按租户圈定数据时递归展开其下全部子租户 |
| 2.6 | **跨租户共享数据的显式豁免清单** | 全局字典、行业基准等必须能跨租户读 | 豁免项有明确清单与审批，不靠代码里零散特判 |

### 3.3 租户生命周期

| # | 功能 | 为什么需要 | 验收标准 |
|---|---|---|---|
| 3.1 | **自动化开通** | 手工开通不可重复、易遗漏 | 一次操作完成：建租户 → 建首位管理员 → 初始化配置 → 分配资源；**开完即可登录使用** |
| 3.2 | **版本化的初始配置模板** | 以"复制现有租户当前状态"为模板会让租户间互相污染 | 初始配置来自受版本管理的模板，与任何既有租户的运行时状态无关 |
| 3.3 | **租户变更（升降级、扩容、迁移）** | 客户等级会变；Pool→Silo 的迁移是常见需求 | 变更有明确流程，且不需要停服重建 |
| 3.4 | **彻底注销与数据清除** | "无法删除租户"本身即合规问题 | 注销后该租户全部数据可被完整清除或加密销毁；**遗留凭证同时失效** |
| 3.5 | **注销前的数据导出** | 客户有权带走自己的数据 | 支持按租户导出完整数据集 |

### 3.4 租户级管理与权限

| # | 功能 | 为什么需要 | 验收标准 |
|---|---|---|---|
| 4.1 | **租户管理员角色** | 平台方不应代客户做日常管理 | 存在"租户管理员"这一角色，权限严格限于本租户子树内 |
| 4.2 | **自助的组织与成员管理** | 每家客户的结构由自己维护 | 租户管理员可自助建下级组织、邀请成员、分配角色 |
| 4.3 | **操作范围约束在自身子树** | 不约束则自助管理等于开放越权入口 | 建/改/搬移组织的目标位置必须落在自己子树内，越界即拒绝 |
| 4.4 | **服务端强制的权限判定** | 前端门禁可被用户篡改 | 权限判定在服务端完成；前端控制仅用于显示，不作为安全边界 |
| 4.5 | **平台方与租户方的职责分离** | 平台超管权限过大是最常见的越权来源 | 平台侧角色与租户侧角色显式区分，不以"是否绑定某实体"隐式推断 |

### 3.5 可观测与审计

| # | 功能 | 为什么需要 | 验收标准 |
|---|---|---|---|
| 5.1 | **租户级操作审计** | 出事后要能回答"谁在什么时候改了什么" | 关键操作留痕，含操作人、时间、对象、变更前后值，且**可按租户检索** |
| 5.2 | **独立的登录与认证日志** | 合规审计必查项 | 登录成功/失败、IP、时间独立记录，不被覆盖 |
| 5.3 | **日志与指标带租户维度** | 无维度则无法定位问题影响了哪家 | 日志、监控、追踪均携带租户标识 |
| 5.4 | **审计记录的保留策略与防篡改** | 无保留期即无法证明"一直在运行" | 有明确留存时长；记录不可被普通路径修改或删除 |

### 3.6 运营与计量

| # | 功能 | 为什么需要 | 验收标准 |
|---|---|---|---|
| 6.1 | **租户资源用量计量** | 计费与容量规划的前提 | 可按租户统计关键资源用量 |
| 6.2 | **噪声邻居防护** | 单租户异常流量不应拖垮其他租户 | 有按租户的调用频率限制或资源配额 |
| 6.3 | **租户级配置项** | 不同客户的业务参数会不同 | 明确哪些配置按租户、哪些全平台统一，且有一致的口径 |
| 6.4 | **租户清单与状态视图** | 运营需要知道有哪些租户、各自什么状态 | 平台侧可查看全部租户及其状态、用量、配置 |

## 四、验收这套功能的三个硬性检查

无论选哪种方案，下面三条是判断"多租户是否真的做成了"的最小检验：

1. **参数篡改测试**：以租户 A 的身份登录，把请求中任何标识改成租户 B 的值，**必须全部失败**。若任一接口返回 B 的数据，隔离未成立。
2. **遗漏检测**：新增一张业务表或一个接口而未处理租户归属时，系统应**在测试阶段即报错**，而不是默默放行。
3. **删除验证**：注销一个租户后，全库检索其标识**应无残留**（或残留数据已不可解密）。

## 五、与 LG 现状的对应关系（简述）

| 本文功能项 | LG 现状 |
|---|---|
| 方案选型 | 已处于 **Pool** 形态（共享库共享表，按组织 / 公司标识隔离） |
| 1.1 租户标识 | ✅ 组织树节点即租户标识 |
| 1.2 上下文进认证链 | ❌ 凭证不带租户标识，由请求参数指定 |
| 1.3 单一权威来源 | ❌ 存在多处独立实现 |
| 2.1 数据可归属 | ⚠️ 大部分可归属，少量表存在盲区 |
| 2.2 / 2.3 / 2.4 强制过滤与默认拒绝 | ❌ 未实现 |
| 2.5 子树展开 | ❌ 能力存在但未用于授权 |
| 3.1 / 3.2 自动化开通与模板 | ⚠️ 可开通但为空壳；模板取自既有租户运行时状态 |
| 3.4 彻底注销 | ❌ 未实现 |
| 4.1 / 4.2 租户管理员与自助管理 | ✅ 页面与数据模型已具备 |

| 4.4 服务端强制权限 | ❌ 依赖前端 |
| 4.5 平台/租户职责分离 | ❌ 以"是否绑定实体"隐式推断 |
| 5.x 审计 | ⚠️ 表与接入点已有，写入未启用 |
