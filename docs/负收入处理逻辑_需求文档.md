# 需求文档：负收入处理逻辑——预测公式、对标公司校验与对标管理页 ARR 展示

## 一、背景与目标

本需求基于平台范围内"负收入排除逻辑（Negative Revenue Exclusion Logic）"统一落地的总体方向，针对该逻辑在三个具体场景中的应用进行修正与补齐，使系统在出现负收入数据时仍能产出正确的预测结果、保持对标计算的数据完整性，并消除前端展示与系统计算口径之间的差异。

---

## 二、需求范围

本需求共包含 3 项更新：

| 编号 | 更新内容 | 影响层 |
|------|----------|--------|
| Update 1 | 系统生成预测公式中 N 锚定到基准月 | 后端 |
| Update 2 | 管理员手动添加的对标公司同样适用 ARR 排除规则 | 后端 |
| Update 3 | 对标管理页（Peer Management）显示"对标校验 ARR" | 前端文案（仅 Banner 文案更新） |

---

## 三、详细需求

### Update 1：系统生成预测公式——N 锚定到基准月

**现状逻辑**

系统生成的毛收入预测公式为：

`Revenue_t = Base_Revenue × (1 + Growth_Rate)^n × Seasonal_Factor_t`

- 原逻辑中 `Base_Revenue` 始终取自最后一个closed month；
- `N` 始终是"预测目标月"与"最近已关账月"之间的间隔月份数。

**问题**

引入负收入排除逻辑后，当最近closed month的收入为负时，系统会回退（fallback）使用最近一个非负月份作为 `Base_Revenue`。此时若 `N` 仍按"closed month"计算，则基准月与增长指数将锚定到不同月份，预测结果会出错。

**变更后逻辑**

- 当 `Base_Revenue` 发生回退（即基准月不再是最近closed month）时，`N` 必须重新计算为"预测目标月"与"实际所用基准月"之间的间隔；
- 在回退场景中，系统须将"基准月"视同"紧邻预测期的前一月"对待；
- 任意预测计算中，`Base_Revenue` 与增长指数 `N` 必须始终锚定到同一参考月份。

**验收标准**

1. 当系统生成预测发生回退（基准月不是最近closed month）时，`N` 按"预测目标月与实际所用基准月"的间隔计算，而不是"与最近closed month"的间隔。
2. 回退场景下，系统将基准月视作紧邻预测期的前一月——下一预测月 `N` = 1。
3. 所有预测计算中，`Base_Revenue` 与 `N` 始终锚定到同一参考月份。

---

### Update 2：管理员手动添加的对标公司同样适用 ARR 排除规则

**现状逻辑**

- 已有规则：若某公司 `ARR_t-1` 为负，则在计算"ARR 增长率分位（ARR Growth Rate percentile）"时，将该公司从对标组中排除；
- 原对标组逻辑中：管理员手动添加的对标公司（admin-added peers）不受标准对标准入条件约束。

**变更后逻辑**

- 上述负 ARR 排除规则须同样适用于"管理员手动添加的对标公司"；
- 若某管理员添加的对标公司在计算期内 `ARR_t-1` 为负，则该公司在本期 ARR 增长率分位计算中被排除；
- 排除是"逐计算期"的，仅在 `ARR_t-1` 为负的具体计算期内排除该数据点，不会将该对标公司从对标组中永久移除。

**验收标准**

1. `ARR_t-1` 负值排除规则适用于对标组中所有公司，无论其加入方式为系统生成还是管理员添加。
2. 若管理员添加的对标公司在相关计算期 `ARR_t-1` 为负，则该公司被排除在该期 ARR 增长率分位计算之外。
3. 该排除仅作用于具体计算期，不从对标组中永久移除该管理员添加的对标公司。

---

### Update 3：对标管理页——展示"对标校验 ARR"

**现状逻辑**

Peer Management 页面在对标准入列（peer criteria columns）中展示每家公司的 ARR 值，当前取自该公司 Financial Statements 页的原始 ARR。

**问题**

该原始 ARR 与系统用于评估对标资格时所使用的 ARR 不一致，会导致用户看到的数字与系统判断口径不符，无法理解为什么某些公司被纳入或排除。

**变更后逻辑**

- Peer Management 页面对标准入列中显示的 ARR 须改为"对标校验 ARR"——即排除负 MRR 和负毛收入月份后计算的 ARR，而非 Financial Statements 上的原始 ARR；
- 在 Peer Management 页面现有 Banner 文案中，加入对该 ARR 含义的说明，让用户知晓所显示的 ARR 为对标校验 ARR；
- 该说明必须整合进现有 Banner，不新增任何 UI 元素、图标或独立 Tooltip；
- 该 ARR 口径变更同时作用于 Peer Management 页面的 **System-Derived Peers** 与 **Admin-Added Peers** 两个区域。

**Banner 更新文案（建议口径）**

> "Peer groups are automatically generated based on company type, stage, and ARR. ARR shown reflects the value used for peer validation and may differ from the ARR shown on Financial Statements. Admins can manually add peer companies to override the System-Derived Peers."

**验收标准**

1. Peer Management 页对标准入列中展示的 ARR 值为"对标校验 ARR"（已排除负 MRR 与负收入月份），不再是 Financial Statements 的原始 ARR。
2. 现有 Banner 文案更新，明确说明所示 ARR 为对标校验 ARR，可能与 Financial Statements 上的 ARR 不一致。
3. 仅更新 Banner 文案，不新增 UI 元素、图标或独立 Tooltip。
4. ARR 口径变更同时适用于 System-Derived Peers 与 Admin-Added Peers 两个区域。

---

## 四、业务逻辑闭环说明

三项更新共同保证"负收入排除逻辑"在系统中端到端一致：

1. **预测层（Update 1）**：当负收入触发基准月回退时，预测公式的基准与指数锚点保持同步，避免错配导致的预测偏差。
2. **对标计算层（Update 2）**：负 ARR 排除规则对所有来源的对标公司一视同仁，保证对标计算的数据完整性。
3. **展示层（Update 3）**：Peer Management 页所展示的 ARR 与系统实际用于对标校验的 ARR 口径一致，并通过 Banner 文案显式告知用户，消除展示与计算之间的认知差异。

至此，负收入排除逻辑在"计算→校验→展示"链路上形成统一闭环。
