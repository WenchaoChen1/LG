#### 若模板进范围：`.xlsx` 的扫描与审阅方案

必须把两件事分开，混在一起会产生虚假信心：

| | 要求 | 能否用「转 HTML」 |
|---|---|---|
| **保密扫描** | 必须覆盖**全部**藏字的地方 | ❌ **不行**——渲染会丢掉元数据与隐藏内容 |
| **审阅呈现** | 让人看清改了哪个单元格 | ✅ 可行，且能复用现有 diff 组件 |

**① 扫描：解包 OOXML 全量，不依赖渲染**

已实现并实测（`scanner.scan_xlsx`），覆盖渲染视图看不到的部分：

**根本原因：HTML 渲染是一次有损投影**——把 zip 里几十个 part 投影成"一张表格的可见文本"。
凡是不落在这个投影像上的字，扫描就看不见。而保密扫描问的恰恰是"**全部字节**里有没有那个词"。

| 藏字的地方 | 渲染后 | 为什么拿不到 |
|---|---|---|
| `docProps/core.xml`：作者 / 最后保存者 | ❌ | **文件级元数据**，不属于任何单元格，渲染器不读这个 part |
| `docProps/app.xml`：公司 / 管理者 | ❌ | 同上 |
| 隐藏 / 极隐藏工作表（`state="hidden"`） | ⚠️ 取决于实现 | 通用「另存为 HTML」只输出可见表；基于 openpyxl 自己遍历的实现能读到（`wb.sheetnames` 含隐藏表） |
| 定义名称、外部链接与跨簿公式引用 | ❌ | **工作簿级对象**（`xl/workbook.xml`、`xl/externalLinks/`），不落在任何单元格 |
| 批注、修订记录 | ❌ | **独立 part**（`xl/comments*.xml`、`xl/revisions/`），不在单元格值里 |
| 图表标题 / 数据标签、透视缓存 | ❌ 多半 | **绘图层与缓存 part**（`xl/charts/`、`xl/pivotCache/`），渲染成表格时不产出 |

⚠️ **"转 HTML 用于扫描"这个方案会自己塌掉**：一旦为了扫描去逐个补齐上述 part，
做的就已经是「解包遍历」而不是「渲染」——那就直接解包，别绕这一圈。

**代价不对称，所以只能选全量解包**：

| | 后果 |
|---|---|
| 漏扫一次 | **永久公开、不可撤回**（实测：关闭 PR + 删分支，内容照样按 SHA 取得到，见 §4.1②） |
| 多扫一些 | 只是噪音，人工判定时排除 |

在这种不对称下，渲染视图省下的便利换不来这个风险。**扫描只对着 zip 内的原始 part 做。**

**② 审阅呈现：两个方案，建议 B 为主、A 为辅**

| | 方案 A · 渲染 HTML 表格并排 | 方案 B · 规范化文本 + 统一 diff |
|---|---|---|
| 做法 | 新旧各渲染成 `<table>`，左右并排 | 把 xlsx 展平成确定性文本，再 diff 那个文本 |
| 优点 | 直观，像 Excel | **精确到单元格**；**复用现有 `diff2html`，零新组件** |
| 缺点 | **一个单元格的改动人眼几乎看不出来**；HTML diff 噪音大 | 不像表格 |
| 定位 | 辅助视图（"看渲染"页签） | **主视图** |

**方案 B 的规范化文本形态**（确定性排序：sheet 按簿内顺序，cell 先行后列）：

```
## docProps
creator          = <值>
lastModifiedBy   = <值>
company          = <值>

## sheet "Pricing Matrix" [visible]
A1   str       "Tier"
B4   formula   =B3*1.2            (cached 120.0)
B5   number    96.0

## sheet "Scratch" [HIDDEN]          ← 隐藏表显式标注，绝不省略
A1   str       "internal notes"

## definedNames
## externalLinks
```

然后 `git diff --no-index 旧.txt 新.txt` → 统一 diff → 喂 `diff2html`。
**和文本变更走同一条渲染管线。**

**③ 两条必须遵守的约束**

- ⚠️ **不能用 git `textconv` 把规范化文本折进 P1**。`.gitattributes` + `diff.*.textconv` 确实能让
  `git diff` 直接输出文本差异——但**上游 CI 没有这个 driver**，那样 P1 就不再等于 CI 扫描的字节，
  整套「审阅人看到的 == 我们哈希的 == CI 扫的」就断了。规范化文本只作**审阅产物**，不进载荷。
  载荷里绑定 xlsx 的方式仍是 **P2 的 sha256**——字节被钉住，而规范化视图由字节确定性派生，
  所以「审阅这个视图」等价于「审阅那些字节」。
- ⚠️ **模板的字节来源是上传，不是工作副本**。Goldie 写不出电子表格，模板只能由人上传。
  因此：上传 → S3（按 sha256 寻址）→ Python 侧据此扫描与规范化，Node 侧据此放入工作副本。
  **双方读同一份字节，避免两处真源。**

**④ 工作量与建议**

| 项 | 量 |
|---|---|
| 扫描（解包全量） | ✅ **已实现并实测** |
| 规范化文本生成器 | 🆕 中等（openpyxl 遍历 + zip part 兜底 + 确定性排序） |
| 审阅 UI 主视图 | ✅ 复用 `diff2html`，**近零** |
| 审阅 UI 辅助视图（渲染表格） | 🆕 小（复用 `excel_preprocess_node` 的渲染逻辑） |
| 上传通道 + S3 寻址 | 🆕 小（有先例） |

**建议**：技术上不构成阻碍，主要成本是规范化生成器。但**模板改动的业务价值需求侧最清楚**——
上游 `templates/README.md` 说 *"Corrections to existing templates — a broken formula, a wrong
reference, an assumption that no longer holds — are the most useful contribution anyone can make here."*
若确认要做，建议**作为第二期**，先让 play / mistake 这条链跑稳。

## 1.2 需求侧必须知情的约束（无需回答）

> 这些不是问题，是会影响他们判断与预期的事实。

### C1 · ⚠️ 保密扫描当前是空转的

**先说清楚这一条不主张什么**：上游的设计立场本来就是「人是控制点、CI 只是兜底」，
`validate.yml` 注释原话：*"This is a **backstop, not the control**. Anonymisation is the
contributor's responsibility, and for LookingGlass it happens inside LookingGlass before a
pull request is ever opened."* 需求答复里 *"The portfolio team will review each one"*
与这个立场**一致**，不是因为依赖 CI 才这么说。

要告知的只是两个并列的事实：

| | |
|---|---|
| **事实 A**（邮件原文） | *"The scan runs against the diff, the commit messages, the branch name, and the PR body… The scan is a backstop."* —— 用的是**现在时**，作者认为它在运行 |
| **事实 B**（我们实测，公开可验证） | `CONFIDENTIAL_TERMS` 未配置 → 扫描从未真正运行过。job 显示绿勾，warning 藏在注解里（F1） |

**影响**：这不改变「人是控制点」的设计，但改变**风险画像**——
原以为控制点之外还有一层自动兜底，实际**没有任何冗余，控制点是单点**。

⚠️ 且启用之前必须先修 F2/F3，否则一开就同时得到「词表大部分失效」和「假披露事件」两个效果。

### C2 · ⚠️ mistake 编号可能被别人抢走，导致已批准的变更作废重来

**这是本节最需要业务侧知情的一条。**

#### 编号怎么分配

新增 mistake 取「**下一个未用编号**」——读上游最新的 `MISTAKES.md`，取 `max(编号) + 1`
（当前 161 → 下一个 162）。编号**永久、不可复用**，被网站、LookingGlass 和所有 fork 引用。

分配发生在 **N3 脱敏阶段**（组装载荷之前），不能更晚——载荷哈希必须包含最终编号，
否则批准之后再写入编号会让哈希变化、必然拒推（详见 §3.2）。

#### 为什么会撞

**真源是上游仓库，不是我们的库。** 我们分配了 162 之后、PR 合并之前，别人也可能提交一条 162：

| 谁 | 可能性 |
|---|---|
| **我们自己另一条在途变更** | ⚠️ **发布串行并不消除它**——编号在 **N3 脱敏阶段**分配，而 N3 **不串行**（审阅可并发）。两条变更完全可能各自分到 162，只是冲突会在 N5 校验时被发现，而不是两个 PR 同时开着 |
| Dougal's knowledge vault（GS 的另一个内部系统） | 有 |
| 外部贡献者 | 有 |
| GS maintainer 直推 | 低但存在 |

#### 我们的选择：不做预防，撞了再处理

**不与上游协商号段预留、不做全局锁、不做号段预分配。** 理由：

- 预防的成本（跨组织协调、或每次发布前锁定上游）**远大于**冲突的概率与代价
- 上游 `main` 自首发（2026-08-23）以来**零提交**，实际频率极低
- 冲突的后果是「重走一遍」，不是数据损坏

#### 撞了会怎样（实测）

drill 仓实测：两条分支同时占用 162，合并其中一条之后，另一条——

| | 结果 |
|---|---|
| CI | **全绿** —— 分支自身的树里只有一个 162，`build.mjs` 校验不出问题 |
| 合并 | `mergeable=false`、`mergeable_state=dirty` —— **GitHub 挡住，需人工解冲突** |

失败形态是**最差的那种**：没有告警，绿勾摆在那里，PR 静静挂着；而解冲突的是**上游维护者**，
我们的自动化不会知道。

#### 两道拦截

| 何时 | 做什么 | 能拦住什么 |
|---|---|---|
| **N5 推送前** | 重新读上游 `MISTAKES.md`，确认 N3 分配的编号仍未被占用 | **绝大多数**——在内容公开之前就拦下 |
| **N6 合并跟踪** | 轮询 `mergeable_state`，绿灯 + `dirty` 视为冲突 | 漏网的（分配→合并之间的窗口） |

两道都触发**回退 → 重新分配编号 → 重走全流程**（自动 or 人工待定，A2）。

**需要业务侧知道的**：编号冲突会让一条**已经批准**的变更作废重来。这不是 bug，
是「编号永久不可复用」这个上游约束的必然代价——我们选择接受它，而不是为它建一套预防机制。

### C3 · 发布不可逆，且 push 那一刻就已公开

上游是公开仓库。**push 完成即全世界可见、可 clone、可被索引，不是开 PR 才公开。**
出问题的处置是「关闭 PR + 上报」，不是「改一版再推」——上游 `GOVERNANCE.md` 原文：
*"close it, do not fix it in place, because a public pull request cannot be unpublished."*

### C4 · 审阅是唯一控制点，其负载直接决定可靠性---审阅量是否需要控制？

*"push more rather than less"* 是刻意的高召回；*"review each one"* 是唯一的脱敏控制。
两者叠加意味着：**审阅量一旦超出承受，可预测的退化是批量接受而非逐条判定。**

> 这一条是**推断，不是实测**。

因此设计上做了两个取舍：**审阅界面不提供批量接受入口**（组合识别本质上无法批量判定；
**暂定，A5**），以及**让筛选松紧可调、每次调整有据可查**（§5.5）。

### C5 · 哪些内容会被送进大模型（事实披露，无需回答）

需求侧已确认转录可以送入外部模型。这里把**具体送什么**列清，便于知情。

| 调用 | 送出的内容 | 含身份信息吗 |
|---|---|---|
| **② 提炼**（§5.3.2） | **单个转录分段的原文** | ✅ **含**——逐字对话、公司名、创始人名、精确数字 |
| **⑤ 起草**（§5.3.5） | `claim`（已泛化）+ 目标条目现有内容（已是公开语料） | ❌ 不含 |
| **N2 与 Goldie 对话** | 审阅人输入 + 当前候选内容 | 视审阅人输入而定 |

**只有 ② 会把带身份的原文送出去。** 三条限定：

1. **一次一段，不送整份转录**——② 的输入是单个分段（§5.3.2）
2. **原文止于 ②**——后续 ③④⑤ 只传 `claim`，看原文靠 `source_doc_id` + `segment_ref` 回查
   （§5.2 数据流转）。这不是省事，是缩小暴露面：原文一旦沿流水线传递，
   就会出现在更多日志、更多中间态、更多 prompt 里
3. **一律走 `llm.llm_db_router`**——项目规范强制，禁止直连厂商 SDK；供应商与模型由该路由统一配置

⚠️ 需要注意的是这与产品现有 LLM 调用**性质不同**：chatbot 与财务提取处理的是
**客户自己的数据**；这里是**被投企业创始人的私密对话**，而这些企业并不是我们的客户。
既然已确认可送，本文档不再作为待确认项——但**供应商的数据留存策略**值得单独确认一次
（属运维/合规事项，不阻塞设计）。

## 1.3 上游仓库实测发现（客观事实）

完整版见 [`upstream-findings.md`](../../../CIOaas-python/docs/playbook-publish/upstream-findings.md)，
此处只列对本设计有直接影响的。

| # | 发现 | 对我们的影响 |
|---|---|---|
| **F1** | **`CONFIDENTIAL_TERMS` 未配置，保密扫描从未真正运行**（公开注解可验证） | 邮件称扫描正在运行（*"The scan runs against…"*），**实际从未运行**。上游本就把人定为控制点、CI 只是兜底，故设计不变；变的是风险画像——**没有任何冗余，控制点是单点**。详见 C1 |
| **F2** | 网页 UI 配的词表带 CRLF，`IFS= read -r` 保留 `\r`，**只有最后一行生效** | 变量一旦配上就大部分失效，UI 上看不出。**配变量之前必须先修** |
| **F3** | 两点 diff 把 base 分支（= 上游唯一的长期分支 `main`）上**比我们分支新**的内容算作本 PR 的删除行 | 命中会算到我们头上。⚠️ 前提不是「有人直推」——见 §4.2 的三条路径，其中「**黑名单后加**」不需要任何 bug 即可发生 |
| **F5** | `.xlsx` 内容对扫描完全不可见（`Binary files differ`） | 模板若进范围，只能靠我们自己解包扫 |
| **F6** | 直推 `main` 完全不扫，且当前允许 | **PR 是唯一能触发扫描的路径** |
| **F7** | `build.mjs` 静默丢弃 `GS:LINKS end` 之后的内容，不报错 | 编辑意图必须落在正文区，不能追加到文件尾 |

> ⚠️ **F1 与 F2 的先后关系很重要**：现在扫描没开，所以 F2/F3 都还没机会发作。它们是
> **变量一配上就立刻生效的地雷**。给上游的信必须写清：**先修 F2/F3，再配变量**，
> 否则一开就同时得到「大部分词失效」和「假披露事件」两个效果。

## 2.1 总览

```
┌── 产出 ──────────────┐  ┌── 审阅 ─────────────┐  ┌── 发布 ──────────────┐
│                      │  │                     │  │                      │
│  N1 产生提交草稿      │  │  N2 组合团队审阅     │  │  N5 发布              │
│    转录/对话接入      │→ │    编辑/对话/       │→ │    落地→推送→提 PR    │

│    入队 + 建档        │  │  N3 脱敏 + 签名      │  │  N6 合并跟踪与终态    │
│                      │  │  N4 GP 批准         │  │                      │
└──────────────────────┘  └─────────────────────┘  └──────────────────────┘
        自动                    人工（唯一控制点）          自动
```

**一条铁律贯穿全流程**：创始人上下文（公司名、人名、精确数字、对话原文）**只存在于 LG**。
公开出去的**五个面**——语料改动、二进制模板、commit message、分支名、PR 正文（§3.1）——
一律从**另一个字段**生成，两者在数据结构上分离。

## 2.2 节点清单

| 节点 | 名称 | 执行者 | 产出 | 状态 |
|---|---|---|---|---|
| **N1** | **产生提交草稿** | 系统 + Goldie（全自动） | LG 变更记录 + 候选改动主张 | `SURFACED` |
| **N2** | 组合团队审阅 | **人** | 接受 / 编辑 / 拒绝 | `REVIEWING` → `SUBSTANTIVE_OK` / `REJECTED` |
| **N3** | 脱敏 + 签名 | **人** | 脱敏声明（署名） | `SCRUBBED` |
| **N4** | GP 批准 | **人** | 批准记录（绑内容哈希） | `RATIFIED` |
| **N5** | 发布 | 系统 | commit + PR | `PUBLISHING` → `PR_OPEN` |
| **N6** | 合并跟踪与终态 | 系统 + 人 | 合并 / 冲突 / 披露 | `MERGED` / `CONFLICT` / `CLOSED_*` |

```

|---|---|
| Insight identified | N1（接入 + 挖掘） |
| potential insight qualification | N1 内部（Goldie 自判，高召回） |
| LG change record creation | N1（**Goldie 浮现时即创建**，以便拒绝后可抑制） |
| SME review inside Looking Glass | N2 |
| sanitization / generalization | N3 |

| PR submission | N5 |
| —（需求方未提） | N6 合并跟踪：**编号冲突的漏网情形只在这里暴露**，见 C2 |

## 2.4 四种审阅动作（N2）

需求方指定：**直接编辑 / 与 Goldie 对话 / 整体接受 / 整体拒绝**。

| 动作 | 效果 | 备注 |
|---|---|---|
| 整体接受 | 进入 N3 | |
| 直接编辑 | 改动内容 → 进入 N3 | 编辑后的内容才是后续脱敏与批准的对象 |
| 与 Goldie 对话 | Goldie 依对话改写 → 回到审阅 | 每一轮都是一个新版本，全部留痕 |
| 整体拒绝 | 终态 `REJECTED`；**是否写抑制表取决于拒绝理由** | 抑制范围由理由推导，见 **§5.9** |

> ⚠️ **审阅之后的任何改动都会作废后续环节**：一旦进入 N3/N4，再回头编辑，
> 签名与批准同时失效、必须重来（决定 D3，建议抛回确认）。

## 2.5 业务侧需要知道的三件事

1. **人工审阅是唯一的脱敏控制。** 上游 CI 的保密扫描当前未启用（F1），启用后还有两个会
   静默削弱它的缺陷（F2/F3）。也就是说现在**没有第二道防线**。
2. **发布是不可逆的。** 上游是公开仓库，**push 完成的那一刻内容即全世界可见**，不是开 PR 才公开。
   出问题的处置是「关闭 PR + 上报」，不是「改一版再推」。
3. **新增 mistake 可能因编号冲突作废重来**（C2）。这是永久编号这个约束的必然代价，不是缺陷。

## N1 · 产生提交草稿（接入 → 挖掘 → 建档）🆕

> 对业务是一件事：**队列里出现了一条待审的草稿**。内部三步，失败模式与责任方各不相同。

### N1-a · 转录 / 对话接入 🆕

| | |
|---|---|
| **前置** | 数据源可用；已确定拉取范围（哪些会议） |
| **输入** | Fireflies 会议转录（含发言人、时间轴、正文）、Goldie 对话 |
| **输出** | `ai_pb_source_doc` 一行 + 分段结果 |
| **触发** | 定时轮询 + webhook（若提供） |

1. 按 `external_id` 幂等落库（重复拉取不产生新行）
2. **原文按内部资产处理**：转录全文属于内部侧，永不进入任何公开路径
3. 分段：按发言轮次或语义边界切段，每段带稳定 `segment_id`（供抑制锚点用）
4. 记录 `company_id` 归属（用于 ACL 与统计）

⚠️ **转录里是逐字对话、公司名、人名、精确数字**——整条链上敏感度最高的原始材料。
其存储、访问、以及是否可送入外部模型，具体送什么给大模型见 **C5**。

⚠️ **这一步是否由我们建，未定**：需求答复说 *"I want Goldie to be mining **those chats
and transcripts**"*，语气上 Goldie 已经能拿到它们。若 Goldie 侧已有接入，我们只消费其产出，
本步骤不存在。**见 Q1。**

### N1-b · Goldie 挖掘候选 🆕

| | |
|---|---|
| **前置** | N1-a 已产出可用分段 |
| **输入** | 转录分段 / Goldie 对话；play 与 mistake 的出站检索索引 |
| **输出** | 一条候选（来源锚点 + `claim` + `change_kind` + 目标条目 + **结构化编辑意图**），交给 N1-c |
| **触发** | 接入事件驱动 + 定时兜底 |

内部是五段流水线 **①–⑤**，连同松紧校准见**第五部分**（专节展开）：

```
① 粗筛 ─> ② 提炼 ─> ③ 定位 ─> ④ 值得看吗 + 定型 ─> ⑤ 起草 + 判空 ─> 交给 N1-c
```

### N1-c · 入队 + LG 建档 ✅（部分）

| | |
|---|---|
| **前置** | N1-b 产出候选（抑制判定已在 N1-b 内完成，见 §5.2「抑制判定的两个时点」） |
| **输出** | `ai_pb_change_internal` + `ai_pb_change_public` 各一行；状态 `SURFACED` |

1. **内外分栏在此刻发生，不是发布前才拆**：
   - `internal_rationale` ← 完整上下文：来自哪次会议、原话要义、精确数字、谁提出
   - `public_change_note` ← 泛化后的「改了什么」，不含 why
2. 生成 `opaque_ref`（CSPRNG，6 位 base36，唯一索引 + 冲突重试）
3. **此时不分配 mistake 编号**（编号在 N3 分配，见 §3.2）

N1-c 是**纯持久化**，不做过滤、不做内容生成——到这里候选已经定稿。

## N2 · 组合团队审阅 ✅（桩）

| | |
|---|---|
| **前置** | 状态 `SURFACED` |
| **输入** | 候选主张 + **完整内部上下文**（审阅人需要它判断实质） |
| **输出** | `ai_pb_review_event` 流水；状态迁移 |

**处理逻辑**

- **整体接受** → `SUBSTANTIVE_OK`
- **直接编辑** → 覆写编辑意图，记录事件，仍在 `REVIEWING`
- **与 Goldie 对话** → Goldie 依对话重新产出，版本号 +1，记录事件
- **整体拒绝** → `REJECTED`；按拒绝理由决定是否写 `ai_pb_suppression`（§5.9.1）——
  「证据不足」走 `evidence_count` 累计、「方向对但质量差」根本不执行拒绝

审阅判据（对照 `CONTRIBUTING.md`）：mistake 必须是**具体行为 + 具体后果**而非风险类别；
play 必须**可排期**（步骤、责任人、诚实的工作量估计）；语气与既有条目一致。

## N3 · 脱敏 + 签名 ✅（机制真 / 人是桩）

| | |
|---|---|
| **前置** | 状态 `SUBSTANTIVE_OK` |
| **输入** | 编辑意图 + 完整内部记录（对照用） + 脱敏清单 v1 |
| **输出** | 语料改动 + 五面载荷 + 自动扫描报告 + **署名的脱敏声明**；状态 `SCRUBBED` |

**处理逻辑**

0. **编号分配（仅 change_kind C）**：取上游最新 `MISTAKES.md` 的 `max(编号) + 1`。
   ⚠️ **必须在组装载荷之前分配**，否则批准的载荷里没有最终编号，N5 一写入哈希就变、必然拒推（§3.2）。
1. **语料落地**：把编辑意图落成受控工作副本上的文件改动
   - play frontmatter 只能用上游手写解析器支持的最小方言（标量 / `- item` / `- k: v`）
   - **不得新增自定义字段**（schema `additionalProperties: false`）
   - 不写 `**Prevented by**` 行、不碰 `GS:` 标记区间
   - ⚠️ 内容必须落在正文区（`GS:LINKS start` 之前），**不能追加到文件尾**（F7）
2. **生成物重建**：Node 跑上游 `scripts/build.mjs`，再 `--check` 必须 `up to date`
3. **⚠️ 意图生效校验（新）**：build 之后**回读文件，确认意图的目标文本确实在里面**；
   不在则报错，而不是当作成功。
   理由：F7 那个丢弃是**完全静默的**——build 不报错、`--check` 显示 `up to date`、
   `git status` 干净（文件被改回原样）。少了这一步，一条改动会悄无声息地不发生，
   而后续 diff、载荷、哈希全部自洽，**没有任何一环会告诉你它丢了**。
4. **五面组装 + 哈希**（详见 §3.1）
5. **自动扫描**（辅助，不构成放行）：五面全扫 + `.xlsx` 解包
6. **人工逐项判定**：清单 A–G 七组；**D 节反向自检必做**
7. **签名**：署名（不接受团队名/账号名）+ UTC 时间 + 清单版本与 sha256 + 载荷哈希 + 反向自检结果

|---|---|
| **前置** | 状态 `SCRUBBED`，已有有效签名 |
| **输入** | 五面载荷 + 内部记录 + 签名声明 |
| **输出** | 批准记录（**含载荷哈希**）；状态 `RATIFIED` |

⚠️ **批准绑定的是那一版载荷的哈希，不是记录 ID**（D2）。且审批界面**必须五面全展示**（D4）。

## N5 · 发布 ✅

| | |
|---|---|
| **前置** | 状态 `RATIFIED`；发布队列空闲（D11 串行） |
| **输入** | `ai_pb_change_public` + 受控工作副本 |
| **输出** | commit SHA + PR URL；状态 `PR_OPEN` |

**处理逻辑**

1. **编号可用性校验（仅 change_kind C）**：`git ls-remote` 取上游 main 顶点 → 拉最新
   `MISTAKES.md` → 确认 **N3 分配的那个编号仍未被占用**。被占则拒推，回退重新分配并重走。
   ⚠️ **分配在 N3、不在这里**——理由见 §3.2；这里只校验，不重新分配。
2. **推前判定**（闸门做早期检查，push 在使用点做权威判定）：
   - 状态必须是 `RATIFIED`
   - **从记录与工作副本重建载荷，比对批准哈希**——不等则拒推
   - 目标 ref 必须匹配 `lg/<opaque>`，**永不为 `main`**（F6：直推不扫）
   - `build --check` 仍干净
   - 结构隔离静态断言通过
   - 目标仓库 `private` 标志（演练期）/ 目标仓库在白名单内
3. **push**：专用机器身份提交（D6）；**这是唯一的不可逆边**
4. **开 PR**：标题正文只能由 `public_change_note` 拼装；`Source:` provenance 行同样公开
5. **回写**：`commit_sha` + `pr_url` 写入公开侧；内部侧**主动拉取**镜像
   （push 路径禁止 import 内部侧，方向只能是 内部 ← 公开）

## N6 · 合并跟踪与终态 ✅（部分）

| | |
|---|---|
| **前置** | 状态 `PR_OPEN` |
| **输入** | GitHub Actions 结论 + PR 的 `mergeable` / `mergeable_state` |
| **输出** | 终态 |

**处理逻辑**

⚠️ **不能只看 checks**。实测：编号冲突时 **CI 全绿、`mergeable_state=dirty`**（C2）。

| 观察到 | 处置 |
|---|---|
| checks 全绿 + 已合并 | `MERGED`，记录合并 SHA 与上游 tag |

| `build` 失败 | 工程问题；修复 = 新载荷 = 重走全流程 |
| **`mergeable_state=dirty`** | **`CONFLICT`**：回退，重新分配编号，重走（**自动 or 人工待定，A2**） |

## 3.1 五个公开面 P1–P5 的定义 ✅

| 面 | 内容 | 来源 |
|---|---|---|
| P1 | 文本 diff | `git diff`（= `merge-base..分支`，与 GitHub PR 页一致） |
| P2 | 二进制变更清单 | `(相对路径, sha256)`；上游扫描的盲区（F5） |
| P3 | commit message | `public_change_note` + `Ref: LG-KB-xxxxxx` trailer |
| P4 | 分支名 | `lg/<opaque>`，无语义 |
| P5 | PR 标题 + 正文 | PR 模板 + `public_change_note` + provenance |

**规范化与哈希**：

```
canonical = json.dumps({..., "_canon": "v1"}, sort_keys=True,
                       separators=(",",":"), ensure_ascii=False).encode("utf-8")
payload_hash = sha256(canonical)
```

`_canon` 参与哈希：将来改序列化写法，旧哈希必须对不上，而不是悄悄仍然相等。

**已验证**：确定性（同输入两次同哈希）；改一个标点即变；改后拒推。

## 3.2 哪些字段的变动会作废批准（D3 的落地清单）

D3 规定「载荷任何变动 → 签名 / SME / GP 三者同时作废」。**"任何"具体指下面这些**——
判据是「它是否进入五面之一」，不是「它看起来重不重要」。

> ⚠️ **本节只回答「哪些字段变了会作废」（机制），不回答「哪个阶段允许谁改它」（策略）。**
> 后者是流程权限，需求侧尚未确定，见 **Q2**（B 组）。两者不能混——机制是从五面反推的数学事实，
> 我们能定；策略决定谁在哪一步有权改，只能由需求侧定。

### 会作废（进入载荷）

| 字段 | 表 | 影响的面 |
|---|---|---|
| `kind` / `target_slug` / `target_mistake_no` | `ai_pb_edit_intent` | P1 |
| `anchor_index` / `anchor_hash` | 同上 | P1 |
| `payload`（JSONB） | 同上 | P1 |
| `is_current`（切换生效版本） | 同上 | P1 |
| 模板文件字节 | S3（按 sha256 寻址） | P2 |
| `note_summary` | `ai_pb_change_public` | **P3 + P5** |
| `note_body` | 同上 | **P3 + P5** |
| `note_provenance` | 同上 | P5 |
| `change_kind` | 同上 | P5（并间接影响 P1） |
| `opaque_ref` | 同上 | **P3 + P4** |
| `base_ref` | 同上 | P1 |
| `mistake_number` | 同上 | P1 |

### 不会作废（不进载荷）

`internal_rationale` · `raised_by` · SME 意见 · 签名人 / 批准人 / 时间戳 ·
`evidence_count` · CI 结果 · `mergeable_state`

> 这些是内部侧内容或流程元数据。改它们不影响「公开出去的是什么」，因此不触发作废。

### ⚠️ 不经人手也会变的两项

| 来源 | 影响 | 备注 |
|---|---|---|
| **上游改了 `scripts/build.mjs`** | 重跑生成物不同 → P1 变 | `scripts/` 在 `CODEOWNERS` 里，改动会走 PR，**可感知但不会通知我们**。推前判定的重算会拦住，但要能读懂拒推原因 |
| 重新 clone 到不同 `base_ref` | P1 变 | 任务重试 / 工作副本重建时可能发生 |

> ✅ **上游 `main` 前进不算**——merge-base 不变，我们的 diff 不变（§10.2 实测）。

### ⚠️ `mistake_number` 必须在 N3 分配，不能拖到 N5（见 C2）

这是列上表时发现的一处设计错误，已修正。若编号拖到 N5（push 前）分配：

```
N4 GP 批准 → 绑定哈希（载荷里还没有编号）
N5 分配编号 → 写入 MISTAKES.md → P1 变 → 哈希变 → 推前判定拒推
```

**新增 mistake 这条路会 100% 推不出去。** 因此：**N3 分配、N5 只校验是否仍可用**。
校验不过（上游期间合并了新 mistake 占了号）→ 拒推 → 重新分配 → 重走全流程（C2 已说明这个代价）。

⚠️ 好处是发现点从 N6（PR 冲突）提前到 N5（推之前），**不用先把内容公开出去再发现撞号**。

### 界面必须显式告知（前提是该阶段允许编辑，见 Q2 B 组）

**凡是允许编辑的阶段**，界面都要标出哪些字段一改就会作废后续环节；
审批页另需写清「批准即绑定以下内容的哈希」。

否则会出现这种情况：有人改了 provenance 里一个标点，**在完全不知情的情况下**让签名与
GP 批准同时失效，而且要到 push 那一刻（推前重算）才报出来。

# 第四部分 · 披露事件处置

> 这是整条链上唯一「出事之后」的路径。它不修复任何东西——**泄漏无法撤回**，
> 本节要做的是把暴露时间压到最短、把事实记全、并阻止把事故当缺陷处理。

## 4.1 已实测的三个事实（本节的全部前提）

### ① push 那一刻就已公开，不是开 PR 才公开

上游是公开仓库。分支一推上去，全世界可 clone、可被搜索引擎索引。
**push 是唯一的不可逆边，它之后没有任何补救窗口。**

### ② ⚠️ 关闭 PR + 删除分支 ≠ 内容消失

**实测**（drill 仓 PR #2，已关闭 + 远端分支已删除）：

```
按 SHA 取 commit          ✅ 拿到了（810da3798aa3）
取该 commit 的文件内容     ✅ 拿到了
分支 ref                  已不存在 —— 但 commit 依然可取
```

GitHub 把 PR 的 head 保留在 `refs/pull/N/head`，**关闭与删分支都不移除它**。
而 SHA 本身是公开信息：出现在已关闭的 PR 页面、邮件通知、事件 API、以及任何 fork 的 reflog 里。

**结论**：「关闭 PR」是**止损动作，不是移除动作**。任何把它当作补救的说法都是错的，
UI 上也不能给人这种暗示。

### ③ 修补已合并的 commit 不可行

`main` 禁止 force-push（上游 ruleset，**维护者也不例外**）。修补已合并的内容需要在
**别人已经 fork 过的仓库**上重写历史。视为不可行。

> 上游 `GOVERNANCE.md` 与需求邮件在这点上完全一致：
> *"close it, do not fix it in place, because a public pull request cannot be unpublished."*
> *"tell me immediately and do not try to quietly amend it; by then we are managing a
> disclosure, not a diff."*

## 4.2 触发条件

| 触发 | 判定 |
|---|---|
| 上游 `confidentiality scan` 失败 | ⚠️ **必须先分流，见下** |
| push 后自动复扫命中（§4.6） | 真，立即启动 |
| 黑名单更新后回扫历史命中（§4.6） | 真，启动（属「后知后觉」型） |
| 人工自查 / 他人举报 / 维护者指出 | 真，立即启动 |
| 已合并之后发现 | 真，且**不可回收**，仍须走完全流程 |

#### CI 报红时的三路分流（不是「真/假」两路）

核对命中词落在哪一段 diff 里——**判据是 `merge-base..我们分支`，不是 CI 用的 `main..我们分支`**：

| 命中落在 | 判定 | 处置 |
|---|---|---|
| **我们的改动里** | 真 · **我们的**事故 | 走完整披露流程（§4.3） |
| **base 更新的内容里**（我们的改动干净） | ⚠️ **不是我们的事故，但是真实的存量暴露** | 我们的 PR **无需关闭**；**上报上游**处理 `main` 上那段内容 |
| 子串误报（`grep -F` 无词边界） | 纯噪音 | 排除，不启动 |

> ⚠️ 中间那一行是最容易处理错的：**不假的是「有泄漏」，假的是「是我们泄漏的」**。
> 关闭我们的 PR 什么问题都解决不了——真正要处理的是 `main` 上那段存量内容。

**别人的内容为什么会带着黑名单词躺在 `main` 上**（三条路，按可能性排序）：

| # | 路径 | 需要什么 | 可能性 |
|---|---|---|---|
| 1 | ⚠️ **黑名单是后加的** | **不需要任何 bug、不需要直推**：合并当时该词不在名单里，之后才加入 | **随投资节奏必然发生** |
| 2 | 别人的 PR 过了 CI 但当时没抓到 | F1（扫描根本没开）/ F2（CRLF 让该词不在生效行） | **当前 100%**——F1 意味着至今所有 PR 都没被真正扫过 |
| 3 | 直推 `main` | F6：`push` 事件不扫；`GOVERNANCE.md` 自陈 maintainer 目前可直推 | 低（单人团队，上游首发后零提交） |

> 「别人提交肯定过了 CI」这个直觉在路径 1 面前不成立：**过 CI 只证明「合并当时它不在黑名单里」**。
> 而扫描只看 diff、不看全库，没人会回头查已合并内容——这正是 §4.6 **M2（黑名单更新后回扫历史）** 存在的理由。

⚠️ **合并本身不受影响**：三方合并走 merge-base，实测别人那行原样保留（§10.2）。被误导的只有扫描那一行 shell。

⚠️ **误判必须被明确排除，而不是"宁可当真"**。理由：把存量暴露或子串误报当成我们的事故来处置，
既解决不了真问题，又会让最不该有噪音的那类告警失去可信度。

## 4.3 处置流程（不可跳步）

```
① 冻结发布队列 ──> ② 关闭 PR（不 amend / 不 force-push）──> ③ 立即通知
      │                                                          │
      └── 系统自动，不需人触发                                    ▼
                                                    ④ 评估扩散面 ──> ⑤ 记录归档 ──> ⑥ 复盘
```

| 步 | 动作 | 执行 |
|---|---|---|
| ① | **冻结发布队列** —— 阻止同批次其他变更继续推 | 系统自动 |
| ② | 关闭 PR。**不 amend、不 force-push、不改动已推内容** | 系统一键 |
| ③ | 通知（§4.4） | 系统自动 + 人 |
| ④ | 评估扩散面（§4.5） | 系统采集 + 人判断 |
| ⑤ | 记录归档 | 系统 |
| ⑥ | 复盘：为什么人工判定没拦住 | 人 |

**是否删除远端分支**：可以做，它减少可发现性。但由 ②/⑤ 记录清楚——
**它不是移除，实测已证明（4.1②）**。

## 4.4 通知与时限

| 对象 | 内容 | 时限 |
|---|---|---|
| 需求方对接人（邮件明确要求 *"tell me immediately"*） | 事实 + 已做的止损 + 尚未确定的部分 | **发现即通知**，不等评估完成 |
| GP / portfolio admin（批准人） | 同上 | 同上 |
| 签名人（脱敏责任人） | 同上 | 同上 |
| 洞察提出人 | 涉及其提供的材料 | 评估后 |

⚠️ **不设"N 小时内"**。设了小时数就等于允许在窗口内先自己看看——而暴露时间是唯一
还能压缩的变量。**发现即通知**，哪怕信息不全。

## 4.5 记录什么

落 `ai_pb_disclosure_incident`。分两类，**严格分开**：

**A. 内部完整记录**（永不离开 LG）
- 时间线：push 时刻 / 发现时刻 / 关闭时刻 / 通知时刻（前两个之差 = **暴露时长**，核心指标）
- 泄漏了什么：具体是哪些字节、涉及哪家公司/哪个人
- 携带它的公开面：五面逐一标注（P1–P5 哪几面）
- 责任链：谁签名、谁批准、清单里的哪一项判定失效
- 扩散面：fork 数、stars/watchers、是否已被搜索引擎索引、commit SHA 是否已出现在别处

**B. 可对外说明的部分**
- 一条变更被撤回、原因类别（不含具体内容）
- ⚠️ **披露事件的记录本身也可能是二次泄漏源**——对外说明必须走同一套脱敏清单

## 4.6 系统必须做 / 必须不做

### 必须做

| # | 机制 | 为什么 |
|---|---|---|
| **M1** | **push 后立即自动复扫**（我们的四面扫描器 + 当前黑名单） | 把「push → 发现」压到秒级，而不是等 CI（可能空转）或等人。**不能撤回，但能把暴露时长从几天压到几秒** |
| **M2** | **黑名单更新后回扫已发布内容** | ⚠️ 黑名单是**活的**（推断：投资组合会增长）。新加一个公司名后，**过去合规通过、已在 main 上的内容可能变成匹配项**。而扫描只看 diff 不看全库，不回扫就永远不会发现 |
| **M3** | 一键进入披露流程，自动冻结队列 + 自动采集时间线 | 事故当下最不该做的是手工拼时间线 |
| **M4** | 暴露时长作为长期指标持续观测 | 唯一还能优化的变量 |

> M1 与 M2 是本节唯一有**实际防护价值**的两条——其余都是事后管理。

### 必须不做

| # | 禁止 | 为什么 |
|---|---|---|
| **N1** | 提供「修改后重推」入口 | 会诱导把事故当缺陷处理，违背上游明文要求 |
| **N2** | 提供 force-push / 历史重写能力 | 上游 ruleset 本就禁止；我们这边也不该有这个按钮 |
| **N3** | 把「已关闭 PR」显示为「已解决」 | 实测已证明内容仍可取（4.1②）。UI 文案必须是「已止损」而非「已移除」 |
| **N4** | 自动重试发布 | 冻结期间任何自动重试都可能扩大暴露 |

## 4.7 与状态机的关系

`CLOSED_DISCLOSURE` 是**终态**，从 `PUSHED` 起的任意状态可达，且**不可回退**——
内容已公开，作废传播对它无效。

⚠️ 对应的那条变更**不会重走流程**：它的内容已经公开，重新脱敏没有意义。
若那条经验仍值得回流，走的是**一条新记录**，并在内部记录里交叉引用事故编号。

# 第五部分 · Goldie 如何产出修改内容

> **本部分是 N1-b 的展开**。位置：
>
> ```
> N1-a 转录接入 ──> N1-b Goldie 挖掘（= 本部分 ①–⑤）──> N1-c 入队 + LG 建档 ──> N2 人工审阅
> ```
>
> ⑤ 之后没有别的挖掘步骤：候选对象直接交给 **N1-c**，由它做抑制判定与建档
> （见 §5.2「交给 N1-c 的候选对象」）。
>
> 需求方对这块没有指定做法，只给了政策：*"push more rather than less and we can calibrate
> over time"*。以下是我们的设计提案。
>
> ⚠️ **"可校准"意味着要能持续调整，不是填个值就完事**。所以要设计三样东西：
> **① 一个能调的参数 · ② 判断调得对不对的数据 · ③ 什么情况该往哪调的规则**。
> 而**候选量不是一个需要事先谈定的数字**：命中即提取，有多少命中就有多少候选。
> 本部分定义「什么算命中」和「筛选松紧怎么调」，不做量级预估。

## 5.1 何时触发

**事件驱动 + 定时兜底**：

```
N1-a 转录入库 ──event──> 挖掘任务入队 ──> Goldie 处理
                定时任务（兜底，捞漏掉的分段）
```

不做「实时流式挖掘」——转录是批量到达的，没有实时性要求，队列化更容易做限流与重试。

## 5.2 五段流水线总览

```
转录分段 ─① 粗筛─> ② 提炼 ─> ③ 定位 ─> ④ 值得看吗 ─> ⑤ 起草 + 判空 ─> 入队
          规则     LLM        检索       θ_c          LLM，写出语料文字
```

| 段 | 做什么 | 丢弃什么 |
|---|---|---|
| ① 粗筛 | 纯规则：段长下限、会议管理内容、纯确认应答、段内重复 | 明显不可能成为经验的段落。**不调模型，成本近零** |
| ② 提炼 | LLM 产出 `claim`（泛化的经验陈述）+ `confidence`（值不值得看）+ `kind_hint`（mistake / play） | — |
| ③ 定位 | `claim` 作 query 召回目标 play / mistake，得 `target_score` | — |
| ④ 值得看吗 | `confidence ≥ θ_c` | 低于阈值的丢弃（**但要抽样留档**，见 §5.5.2） |
| ⑤ 起草 + 判空 | 写出真正要进语料的文字，再确认改动非空 | 落地后没有实际变化的 |

### 数据流转

**传递模型：累积，不是接力。** 每一段的产出**追加**到同一个候选上下文里，后段可以读到
前面所有段的产出——④ 同时要用 ② 的 `confidence` 和 ③ 的 `target_score`，做不到「只吃上一段」。

| 字段 | ① | ② | ③ | ④ | ⑤ | 说明 |
|---|:--:|:--:|:--:|:--:|:--:|---|
| `source_doc_id` + `segment_ref` | **产生** | 透传 | 透传 | 透传 | 透传 | ⚠️ **贯穿全程**：审阅对照原文、抑制锚点、抽样留档都要它 |
| 分段正文（原文） | **产生** | 读 | ✖ | ✖ | ✖ | ⚠️ **止于 ②**——后续要看原文靠锚点回查，不靠传递 |
| `claim` | | **产生** | 读 | 读 | 读 | |
| `confidence` | | **产生** | | 读 | | 只有 ④ 用 |
| `kind_hint` | | **产生** | 读 | 读 | 读 | ③ 用于检索权重，④ 用于定型 |
| Top-K 目标 + `target_score` | | | **产生** | 读 | 读 | |
| 命中条目现有内容 | | | **产生** | | 读 | ⑤ 判空要用 |
| `change_kind` | | | | **产生** | 读 | 定型结果，见下 |
| 「疑似重复」标注 | | | | **产生** | 透传 | 给审阅人的提示，不参与判定 |
| `edit_intent`（含语料文字） | | | | | **产生** | 交给 N1-c |

⚠️ **原文只在 ② 出现一次**。这不是省事，是缩小暴露面：原文一旦沿流水线传递，
就会出现在更多日志、更多中间态、更多 LLM prompt 里，每一处都是新的泄漏面。
后续要看原文，一律靠 `source_doc_id` + `segment_ref` 回查。

### 抑制判定的两个时点

**抑制表**是 `ai_pb_suppression`（§5.9）——记录被拒绝过的候选，让 Goldie 不再浮现同一条。
它有三个键，**可用时点不同，因此各自尽早查**：

| 键 | 构成 | 最早可查 | 查在哪 | 省下什么 |
|---|---|---|---|---|
| 来源锚点 | `source_doc_id` + `segment_ref` | ① 之后 | **① 与 ② 之间** | ② 的 LLM 调用 |
| 目标锚点 | `play:slug#field` / `mistake:NNN` | ④ 定型之后 | **④ 与 ⑤ 之间** | ⑤ 的 LLM 调用 |
| 语义指纹 | `semantic_vec`（需要 `claim`） | ② 之后 | 同上（与目标锚点一并查） | ⑤ 的 LLM 调用 |

```
① 粗筛 ─[查来源锚点]─> ② 提炼 ─> ③ 定位 ─> ④ 定型 ─[查目标锚点 + 语义指纹]─> ⑤ 起草
```

⚠️ **不要等到 N1-c 才查**：N1-c 在两次 LLM 调用之后，一条早该被抑制的候选会白跑两次模型。

⚠️ 「证据不足」型拒绝**不在抑制表里**（§5.9.2）——它走 `evidence_count` 累计，
在第二个时点一并处理：累计 +1，未达 `resurface_threshold` 则丢弃，达到则放行并标注
「本主张已在 N 次独立会议中出现」。

### 交给 N1-c 的候选对象

⑤ 通过后，下列字段作为**一条候选**交给 N1-c 建档：

```
来源锚点  source_doc_id + segment_ref
经验陈述  claim
判定分    confidence
定型      change_kind + 目标条目（slug / mistake 编号）+ target_score
编辑意图  edit_intent（含要写进语料的文字）
标注      疑似重复提示（若有）
```

N1-c 拿到之后做两件事：**抑制判定**（命中则丢弃）与**建档**（内外分栏、生成 `opaque_ref`）。

## 5.3 各段展开

### 5.3.1 ① 粗筛

**输入**：N1-a 产出的转录分段（含 `segment_id`、说话人、时间、正文）。

**输出**：通过的分段进入 ②；被丢的**按比例**写入 `ai_pb_discarded_sample`
（`stage=COARSE` + `rule_id` 记是哪条规则丢的）。

**这一层的职责是省钱，不是把关。** 无模型调用，只丢「确定不可能含经验」的段落——
真正的判断交给 ② 段的 LLM。任何「为了提高精度」而加的规则都不该放在这一层。

**原则：宁可放过，不可误杀。** 放过的代价是多一次 LLM 调用；误杀的代价是那段话
**永远不会出现在任何地方**（见下方 ⚠️）。

#### 规则清单

| # | 规则 | 判据 | 丢什么 | 风险 |
|---|---|---|---|---|
| **R1** | 长度下限 | 词数 < `min_words`（**暂定 10，需抽样验证**） | 「嗯」「对」「好的」这类应答 | ⚠️ 短句可能有内容（*"They never wrote it down."* 才 5 个词），阈值宁低勿高 |
| **R2** | 会议管理内容 | 匹配固定句式：录制开始/结束提示、`can you hear me`、`let's wait for … to join`、日程宣读、时间安排 | 会议流程本身 | 句式稳定，误杀风险低 |
| **R3** | 纯确认应答 | 整段仅由确认词构成（`yeah` / `right` / `exactly` / `mm-hmm` / `got it` / `sure` 等，词表可配） | 附和 | 低 |
| **R4** | 段内重复 | 与本次转录中已处理段落的**归一化文本完全相同** | 转录工具偶发的重复片段 | 极低（要求完全相同，不做模糊匹配） |

⚠️ **刻意不做的规则**：

| 想做但不做 | 为什么 |
|---|---|
| 「寒暄/闲聊」识别 | 纯规则做不准。*"How's the team holding up after the layoffs?"* 是寒暄开头，但后面接的往往正是经验 |
| 按说话人过滤 | 创始人与 GS 侧都可能说出可泛化的观察，没有理由过滤任一方 |
| 「纯问句」过滤 | 问题里常藏着教训（*"Why did nobody check the escalator clause?"*） |

#### 每条规则必须可开关、可计数

- 每条规则**独立开关**（配置项），可单独关掉
- **按规则分别统计丢弃量**——某条规则丢的比例异常时能立刻看出来
- 规则的调整同样落 `ai_pb_calibration`（用 `kind` 区分是 θ_c 还是粗筛规则）

#### ⚠️ 粗筛丢弃也要抽样留档

这是写本节时发现的一个缺口：§5.5.2 只对 **④ 段**丢弃做了抽样留档，
但**① 段丢掉的东西同样不会出现在任何指标里**——而且比 ④ 更危险：

| | ④ θ_c 丢弃 | ① 粗筛丢弃 |
|---|---|---|
| 依据 | 模型给的 `confidence`，会随提示词/模型改进 | **死规则，不会自适应** |
| 调整方式 | 调一个数 | 改规则，改动更少、更容易被遗忘 |
| 可见性 | 已有抽样留档 | **原本完全不可见** |

因此：**① 段丢弃同样按比例抽样写入 `ai_pb_discarded_sample`**，
用 `stage` 字段区分是粗筛丢的还是 θ_c 丢的，`miss_rate` 分别统计。

### 5.3.2 ② 提炼：有没有可泛化的经验、是什么、属于哪一类

**输入**：通过粗筛的**单个**分段（原文，内部侧）。

**输出**：`claim` + `confidence` + `kind_hint` 三样，逐段一组。
⚠️ **原文到此为止**——后续各段只传 `claim`，不再往下传转录原文。

LLM 读一段转录，产出**三样**：

| 产出 | 是什么 | 用在哪 |
|---|---|---|
| **`claim`** | 一句话的可泛化经验陈述 | ③ 的检索 query；队列展示；抽样留档 |
| **`confidence`** | 0–1，这条观察值不值得人看 | ④ 条件 1 |
| **`kind_hint`** | `MISTAKE` / `PLAY` / `BOTH` | ③ 检索时的权重；决定可能的 `change_kind` |

#### 为什么体裁要在这一步判

`CONTRIBUTING.md` 对两者的要求完全不同：

| | 上游的要求 | 从转录里能直接得到吗 |
|---|---|---|
| **mistake** | *"a specific behaviour with a specific consequence"* | ✅ **能**——会议里说的就是「谁做了什么、结果怎样」 |
| **play** | *"tells someone what to do on Monday morning. Steps, owners, an honest effort estimate"* | ❌ **几乎不能**——转录里不会有步骤清单、责任人和工作量估计 |

⚠️ **由此推出一个对预期很重要的结论**：**`PLAY_CREATE`（change_kind A）实际上极少发生。**
从一段对话里凑不出一个可排期的流程。转录挖掘的现实产出只有三种：

1. **新增 mistake**（`MISTAKE_CREATE`）
2. **给已有 mistake 补 play 映射**（`PLAY_PREVENTS_ADD`）
3. **修正已有 play 的某一段**（`PLAY_BODY_REPLACE`）

`kind_hint` 是**提示不是结论**：③ 的检索结果和审阅人都可以推翻它。

#### `claim` 是什么

**一句话的「可泛化经验陈述」** —— 说清「什么行为 → 什么后果」，**不含具体身份**。

⚠️ **它不是「改动主张」**：此刻还没定位到目标条目（那是 ③ 的事），说不出「要改哪里」。
改动主张要到 ③ 之后才成形，落成 `edit_intent`。

它有三个用途，决定了它必须长成这样：

| 用途 | 要求 |
|---|---|
| 作为 ③ 的**检索 query** | 必须用**泛化语言**——索引里的 play / mistake 全是泛化表述，拿带公司名和精确数字的原话去检索，相似度会被噪声拉低 |
| 在候选队列里**一眼看懂这条是什么** | 一句话，可读 |
| 抽样留档时**代替原文存进 `ai_pb_discarded_sample`** | 不能含身份信息（那张表存的是锚点，不是原文） |

> 所以 claim 的泛化发生在 **② 判定**——LLM 直接产出泛化表述，③ 拿它去检索。

#### ⚠️ claim 的泛化 ≠ 脱敏

这两件事都叫「泛化」，但标准、责任、约束完全不同，**混用会直接绕过整条控制链**：

| | claim 的泛化 | 语料正文的脱敏 |
|---|---|---|
| 目的 | **检索效果**——用语料的语言去查语料 | **保密**——决定什么能公开 |
| 去向 | 内部（检索 query、队列展示、抽样留档） | **公开，永久不可撤回** |
| 标准 | 够用即可，无强制清单 | **脱敏清单 A–G 逐项判定** |
| 谁负责 | LLM，无人签字 | **人，署名签字**（N3） |
| 判错的后果 | 检索效果差，人一眼能看出来 | **泄漏** |

**硬约束：`claim` 不得被直接用作语料正文。**

否则会出现这条路径：LLM 泛化一次 → 看着挺干净 → 直接写进 play → 没人做过 A–G 判定 →
公开。**整条控制链从这里被绕过，而且看不出来**——因为产物读起来是泛化的。

⚠️ 尤其是**组合识别**（清单 D）：LLM 会去掉公司名，却保留那个独特的属性组合
（「一家 X 行业、Y 规模、在 Z 地的公司」）。claim 读起来完全泛化，实际仍可唯一定位。
这类只有 N3 的人工反向自检能发现。

#### 三段例子

**例 1 —— 最终成为「补 play 映射」**

| | |
|---|---|
| 转录原文（内部） | *"…we did three implementations for them and every one we just kind of winged it. The third slipped like eleven weeks because nobody had written down what onboarding actually means here."* |
| **`claim`** | **没有书面的客户导入流程，会让实施反复返工、工期显著延后** |
| `confidence` | 0.8 |
| ③ 定位 | play `saas-customer-onboarding` 高相似；mistake `#50 Unstructured implementations` 高相似；**二者关系尚不存在** |
| 最终意图 | `PLAY_PREVENTS_ADD`（change_kind B） |

**例 2 —— 最终成为「新增 mistake」**

| | |
|---|---|
| 转录原文（内部） | *"They signed a three-year renewal and nobody checked for an escalator clause. By year two the margin was basically gone."* |
| **`claim`** | **多年期合同续签时不检查涨价条款，会在合同期内被通胀侵蚀掉利润** |
| `confidence` | 0.85 |
| ③ 定位 | mistake 索引 Top-1 相似度**低** → 语料里没有等价条目 |
| 最终意图 | `MISTAKE_CREATE`（change_kind C）；同时 play 索引命中 Contract Playbook，可并发一条 `PLAY_PREVENTS_ADD` |

**例 3 —— 判定不通过（低 confidence 长什么样）**

| | |
|---|---|
| 转录原文（内部） | *"Q3 was rough. Revenue was down but I think we're turning it around."* |
| **`claim`** | 季度收入下滑后需要调整策略 |
| `confidence` | **0.2** —— 有陈述但**没有具体行为、也没有具体后果**，泛到不可操作 |
| 结果 | 低于 θ_c → 丢弃，按比例抽样留档 |

> 例 3 演示的是：**claim 存在不等于有价值**。`confidence` 判的正是
> `CONTRIBUTING.md` 那条标准——*"a specific behaviour with a specific consequence,
> not a category of risk"*。「需要调整策略」就是典型的 category of risk。

#### 别和另外两样混淆

流程里有三段听起来相似、但性质完全不同的文本：

| | 是什么 | 内部/公开 | 什么时候产生 |
|---|---|---|---|
| **`claim`** | 一句话经验陈述，检索 query + 队列展示 | **内部** | ② 判定 |
| **语料正文** | 真正写进 play / mistake 的文字 | **公开** | ③ 之后，落成 `edit_intent` |
| **`public_change_note`** | commit message / PR 正文的来源 | **公开** | 由 diff 确定性推导（D7），不调 LLM |

⚠️ 提示词的约束见 §5.10——从转录起草文本是整条链风险最高的一步。

### 5.3.3 ③ 定位：改的是哪个 play / mistake

**输入**：② 产出的 `claim`（已是泛化表述，见 §5.3.2）+ `kind_hint`（决定两个索引的检索权重）。

**输出**：Top-K 候选 play 与 Top-K 候选 mistake，每条带相似度 `target_score`；
并一并取回**命中条目的现有内容**（`preventsMistakes` 数组、段落哈希、字段现值）——
④ 判「改动是否为空」要用它，不能等到落地才发现没变化。

**需要新建一份出站专用索引，不能复用现有的入站索引。**


| 索引 | 内容 | 用途 |
|---|---|---|
| play 索引 | frontmatter 全字段 + 正文分段 + **`preventsMistakes`** | 定位目标 play、判断关系是否已存在 |
| mistake 索引 | 编号 / 标题 / 分类 / 正文 | 定位目标 mistake、判断是否重复 |

数据源是 **git 仓库的 Markdown**，以**上游 tagged release** 为基准构建
（`GOVERNANCE.md`：*"ingests this repository at a tagged commit"*）。

```
claim ──作为 query──> play 索引    ──> Top-K 候选 play    + 相似度
                  ──> mistake 索引 ──> Top-K 候选 mistake + 相似度
```

### 5.3.4 ④ 值得看吗

**输入**：② 的 `claim` / `confidence` / `kind_hint` · ③ 的 Top-K 与命中条目现有内容 ·
配置项 `θ_c`。

**输出**：通过则产出 `change_kind` + 「疑似重复」标注，连同前面各段的产出一起交给 ⑤；
不通过则丢弃，**按比例**写入 `ai_pb_discarded_sample`（`stage=THRESHOLD`）。

**判据只有一条**：`confidence ≥ θ_c`。

#### 顺带定型：`change_kind` 在这里确定

④ 是**第一个同时拿到 ② 和 ③ 全部产出**的步骤，因此定型放在这里。
它是**确定性推导**（阈值比较），不是判断，不增加本段的职责：

| 输入 | 来自 |
|---|---|
| `kind_hint`（mistake / play） | ② |
| `target_score`（Top-1 相似度） | ③ |
| 高 / 低阈值 | 配置，判定规则见 **§5.7** |

```
kind_hint=MISTAKE + 相似度 < 低阈值  →  MISTAKE_CREATE
kind_hint=MISTAKE + 相似度 ≥ 高阈值  →  PLAY_PREVENTS_ADD（把该 mistake 挂到命中的 play 上）
kind_hint=PLAY    + 相似度 ≥ 高阈值  →  PLAY_BODY_REPLACE / PLAY_FIELD_SET
kind_hint=PLAY    + 相似度 < 低阈值  →  PLAY_CREATE（⚠️ 极少发生，见 §5.3.2）
落在高低之间                         →  两种都产出，交审阅人选（§5.7）
```

**`θ_c` 控制筛选的松紧**：调低=放进来更多、宁滥勿缺；调高=只放高把握的。
它是**配置项，不是写死的常量**——这就是需求方说的「可校准」要落到的那个地方。

#### ⚠️ 「疑似重复」是标注，不是丢弃依据

③ 能看出一类情况：**语料里已有一条很像的条目**（`target_score` 极高，但不是完全相同）。

**这类不丢**，而是作为**标注**带给审阅人：

```
⚠️ 疑似与 #50 Unstructured implementations 重复（相似度 0.91）
```

理由：*"push more rather than less"* 是需求方的明确政策，而「像不像到该算重复」是判断
不是事实——`CONTRIBUTING.md` 明说 *"Improvements to what is here are the most valuable
contributions"*，一条「很像但更准」的改进恰恰是最该提的。

**判断交给人，事实由系统裁。**

#### 实现顺序可以短路

流水线图上的 ②→③→④ 是**逻辑顺序**。实现时 `confidence < θ_c` 可以直接跳过 ③（省一次检索），
只是抽样留档里不会有目标信息——可接受。

### 5.3.5 ⑤ 起草：写出真正要进语料的文字

**输入**：④ 通过的候选——`change_kind`（④ 定型）+ `claim` + 目标条目及其现有内容 + 来源锚点。

**输出**：完整的 `edit_intent`（含要写进语料的文字）；判空不通过则丢弃。

#### 为什么必须有这一步

`claim` **不能直接用作语料正文**（§5.3.2 那条硬约束）：它是一句话、为检索而生。
而真正要提交的内容是另一回事：

| 意图类型 | 要写出什么 | 需要 LLM 吗 |
|---|---|---|
| `PLAY_PREVENTS_ADD` | 只往 `preventsMistakes` 加一个数字（编号来自 ③） | ❌ **不需要，一个字都不写** |
| `MISTAKE_CREATE` | 标题 + 分类 + 一到三句正文 | ✅ |
| `PLAY_BODY_REPLACE` | 一整段新正文 | ✅ |
| `PLAY_FIELD_SET` | 字段新值 | 视字段而定 |
| `PLAY_CREATE` | **完整 frontmatter（14 个必填字段）+ 全文正文** | ✅ 且**最重**，见下 |

⑤ 放在 ④ **之后**是为了省钱：起草要调 LLM，只对通过筛选的候选做。

#### 起草的约束与 ② 完全不同

| | ② 提炼 | ⑤ 起草 |
|---|---|---|
| 产出去向 | 内部（检索用） | **公开**（写进语料） |
| 长度 | 一句话 | mistake 一到三句 / play 一整段 |
| 体例 | 无要求 | **必须匹配上游语气**——`CONTRIBUTING.md`：*"short, blunt, and earned"*；对照现有 161 条 |
| 格式 | 无 | frontmatter 最小方言、`#### Steps` 段标题、四空格缩进、`> **The goal:** …` 回调块 |
| 落点 | — | ⚠️ **必须在正文区**，不得落在 `GS:LINKS end` 之后（F7，会被静默丢弃） |

⚠️ **⑤ 的产出仍然不是「已脱敏」**。它由 LLM 写成，无人签字。脱敏在 **N3**，由人逐项判定
清单 A–G 并署名。**这一点与 §5.3.2 对 `claim` 的约束是同一条**：LLM 的泛化不能替代人的签字。

#### 收尾：判空

起草完成后，比对新内容与目标条目现有内容；**相同则丢弃**。

| 意图类型 | 比对什么 |
|---|---|
| `PLAY_PREVENTS_ADD` | 编号是否已在 `preventsMistakes` 数组里 |
| `PLAY_BODY_REPLACE` | 新段落 vs 目标段落 |
| `PLAY_FIELD_SET` | 新值 vs 现值 |
| `MISTAKE_CREATE` | 恒非空，跳过 |

空改动必须丢，理由不是「没价值」，而是**它物理上推不出去**：build 之后 diff 为空，
没有可提交的内容。这是**确定性事实，不是判断**。

⚠️ 但 N3 落地后仍要做最终校验：起草文本与现值肉眼不同，
`build.mjs` 规范化空白与换行之后可能是同一份字节。**只有真实 diff 说了算。**

#### ⚠️ `PLAY_CREATE` 的 `preventsMistakes` 从哪来

`preventsMistakes` 在 `schema/play.schema.json` 里是 **required 字段**——新增 play 必须填。
（可以是空数组，但空数组意味着这是个**孤儿 play**，上游 `CHANGELOG` 把现有 7 个孤儿标为 open work。）

它的来源与 `PLAY_PREVENTS_ADD` **不同**：

| | `PLAY_PREVENTS_ADD` | `PLAY_CREATE` 的 `preventsMistakes` |
|---|---|---|
| 查询文本 | `claim`（一句话） | **起草出来的 play 全文** |
| 要几条 | Top-1 | **阈值以上的一组**（一个 play 可防多条 mistake，上游平均 227÷63 ≈ 3.6 条） |
| 什么时候查 | ③ 定位 | ⚠️ **必须在起草正文之后**——没有正文就没有查询文本 |

所以 `PLAY_CREATE` 要**多一次检索**，且这次检索发生在 ⑤ 内部、起草之后：

```
④ 通过 ─> ⑤ 起草 frontmatter + 正文 ─> 用正文反查 mistake 索引 ─> 填 preventsMistakes
```

⚠️ 反查结果**必须逐条校验编号存在**——`build.mjs` 对不存在的编号直接报错
（`preventsMistakes #N does not exist in MISTAKES.md`）。LLM 不参与这一步，编号只能来自检索结果。

> 这也再次印证 §5.3.2 的判断：**`PLAY_CREATE` 是最重的一类**——14 个必填字段、全文正文、
> 外加一次反查，而转录里根本凑不出 `steps / owners / effort estimate`。
> 现实中它极少发生，实现优先级应排在最后。

#### ⚠️ `MISTAKE_CREATE` 会产生孤儿

上游的图是**单向声明**：只有 play 声明 `preventsMistakes`，mistake 不声明任何东西。
所以单独提一条 `MISTAKE_CREATE`，产出的必然是一条**没有任何 play 映射的孤儿 mistake**
——正是上游现有 14 条孤儿的由来。

因此 ⑤ 对 `MISTAKE_CREATE` 应当**并发产出一条配套的 `PLAY_PREVENTS_ADD`**：
用起草出的 mistake 正文反查 play 索引，命中则一并提出。

两条意图属于**同一次变更**（同一个 `opaque_ref`、同一个 PR），因为它们必须同时合并——
先合 mistake 后合映射会在中间留下一个孤儿，先合映射则会引用一个不存在的编号、
直接被 `build.mjs` 拦下。

> 顺带：`PLAY_PREVENTS_ADD` 是唯一不需要 LLM 写一个字的类型，也是改动面最小、
> 最容易被接受的一类——这正是 §5.8 建议把它作为**首批回流内容**的原因。

## 5.4 ⚠️ 两个阈值，不要混

流水线里有**两个**阈值，性质完全不同，校准方式也不同。文档其余部分凡提到「阈值」，
都要看清是哪一个。

| | `θ_c` | 相似度阈值（高 / 低） |
|---|---|---|
| 在哪一段 | ④ 成候选 | §5.7 新增 vs 修改 |
| 判定什么 | 这段**该不该成为候选** | 该**新增**还是**修改已有条目** |
| 输入 | `confidence`（LLM 给的） | `target_score`（检索给的） |
| 判错的后果 | 太高 → 漏掉真经验；太低 → 淹没审阅人 | 判错只是**方案给偏了**，审阅人当场能纠正 |
| 标注数据从哪来 | 审阅结果（accept / reject）+ **丢弃抽样**（§5.5.2） | **审阅人在两个方案间选了哪个**（§5.7） |
| 留痕 | `ai_pb_calibration` | 同表，用 `kind` 区分 |

⚠️ **严重性不对等**：`θ_c` 判错会**静默丢东西**（漏报看不见）；相似度阈值判错只是把方案
给偏了，人一眼就能看出来并改。**所以 θ_c 需要主动抽检，相似度阈值不需要。**

## 5.5 怎么调 θ_c（松紧校准）

### 5.5.1 精度可测，召回不可测

审阅结果天然回流：`ai_pb_review_event` 里每条候选最终是 `ACCEPT` / `EDIT`→接受 / `REJECT`。

```
precision = (整体接受 + 编辑后接受) / 候选总数
```

按 *"push more rather than less"* 的政策，**目标精度应当明确定得偏低**（例如 0.3–0.6）：
精度太高说明阈值卡太严、在漏东西；精度太低说明在浪费唯一控制点的注意力。

⚠️ **但 precision 单独不够，而且这是本节最容易漏的一点：**

> **漏报是看不见的。** 被 θ_c 丢掉的分段永远不会进入审阅，所以它们**不会出现在任何指标里**。
> 只看 precision 调阈值，会稳定地往「越调越严」漂移——因为调严总是让 precision 变好看，
> 而这与需求方 *"push more"* 的政策**方向相反**。

### 5.5.2 因此需要定期召回抽检

- ④ 段丢弃的分段**按比例抽样留档**（存 `confidence` 与 `claim`，不存原文，只存来源锚点）
- 每个校准周期人工看一批被丢掉的样本，判断「这里面有没有本该浮现的」
- 得到 `miss_rate`，与 `precision` 配对使用

| 观察 | 判断 | 动作 |
|---|---|---|
| precision 低、miss_rate 低 | 阈值偏松但没漏 | 符合政策，**保持** |
| precision 高、miss_rate 高 | 阈值太严 | **调低 θ_c** |
| precision 低、miss_rate 高 | 判定质量本身差 | 改提示词 / 换模型，**别动阈值** |
| precision 高、miss_rate 低 | 判定质量好 | 可适度调低 θ_c 换更多召回 |

第三行是关键：**precision 与 miss_rate 同时坏，说明问题不在阈值**，调阈值只会左右横跳。

### 5.5.3 量级是涌现的，只需可观测

```
候选量/周 = 转录分段数 × 粗筛通过率 × P(confidence ≥ θ_c)
```

三项**全部是我们可测、可调的**，没有外生变量需要事先问。上线后一个周期即可实测出真实分布。

因此对量级的要求只有两条：

1. **θ_c 可在不改代码的情况下调整**（配置项，不是常量）
2. **候选队列必须可观测**：当期候选数、precision、miss_rate 三个数随时能看到

⚠️ 不做的事：不设「每周最多 N 条」的硬上限。硬上限会**静默丢弃**命中的内容，
而丢弃的东西不会出现在任何指标里（同 §5.5.1 的问题）。要压量就调 θ_c——
调阈值是显式的、可记录的、可回溯的。

### 5.5.4 校准要留痕

每次调整都要记录：改动人、时间、改动前后值、当时的 precision 与 miss_rate。
否则「calibrate over time」几个月后就变成没人说得清为什么是现在这个值。

## 5.6 编辑意图：改的是哪几行

**Goldie 产出「结构化编辑意图」，不产出自由文本 diff。**

理由：自由文本 diff 无法校验、无法审阅、也无法在 build 之后保持稳定。结构化意图可以被
程序确定性地翻译成文件改动，并且**审阅人编辑的是意图，不是 diff**。

意图的形态（对应 `ai_pb_edit_intent` 表）：

| `kind` | 目标 | 载荷 | 对应 change_kind |
|---|---|---|---|
| `PLAY_FIELD_SET` | `slug` + frontmatter 字段名 | 新值 | B |
| `PLAY_PREVENTS_ADD` | `slug` | mistake 编号 | B |
| `PLAY_BODY_REPLACE` | `slug` + 段落锚点 | 新段落文本 | B |
| `PLAY_CREATE` | 新 `slug` + `category` | 完整 frontmatter + 正文 | A |
| `MISTAKE_CREATE` | —（编号 N3 才分配） | 标题 + 分类 + 正文 | C |
| `MISTAKE_EDIT` | 编号 | 标题 / 分类 / 正文 | D |

> `change_kind` 取值：**A** 新增 play · **B** 修改 play · **C** 新增 mistake ·
> **D** 修改 mistake · **E** 模板（待定，Q1）· **F** story（待定，Q1）。

#### ⚠️ `preventsMistakes` 是什么（容易被误解成「前置节点」）

`prevents` 是**预防**，不是前置。上游 schema 原文：

> "Mistake numbers from MISTAKES.md. This is the **ONLY** place the **play-to-mistake**
> relationship is declared; every link in the other direction is generated from it."

```yaml
# plays/sales-marketing/saas-pricing-matrix.md
preventsMistakes:
  - 4      # Letting customers dictate the terms
  - 20     # Hip-shot product pricing
  - 139    # Disjointed pricing with sales cycle
```

读作：**做了「定价矩阵」这个 play，能避免第 4、20、139 号这三个错误。**
`PLAY_PREVENTS_ADD` 就是往这个数组里加一个编号。

**允许为空**——schema 明说 *"May be empty for a play that prevents no catalogued mistake."*
上游现有 **7 个**这样的 play。但上游把它们标为 **open work**（`CHANGELOG`：*"several of these
plainly prevent mistakes that exist in the list"*）——空是合法的，通常意味着**映射还没补上**，
而不是「这个 play 天生不防任何错误」。

⚠️ **别和入站的 play↔play 关系混淆**：

| | 上游 `preventsMistakes` | 我们入站 rag 的 `depends_on` / `feeds` / `refers_to` |
|---|---|---|
| 关系 | play → **mistake** | play → **play** |
| 来源 | **人工维护**，写在语料里 | **LLM 推断**（`html_parser.py`：*"源站从不写依赖关系…全靠 LLM 推断"*） |
| 上游有吗 | ✅ | ❌ **完全不存在** |

后者是我们入站侧造出来的，**不能回流**——上游 schema 没有这些字段，且
`additionalProperties: false`，想加也加不进去。

**段落锚点**用「段落序号 + 段首文本哈希」双键：序号定位快，哈希校验没错位。上游正文变了
（哈希对不上）就判为**过期意图**，退回重新挖掘，而不是盲改。

⚠️ 三条硬约束（`build.mjs` 与 schema 决定，不是我们的偏好）：
- 关系只能改 play 的 `preventsMistakes`，**绝不能手改 `MISTAKES.md` 的 `**Prevented by**` 行**
- frontmatter **不得新增字段**（`additionalProperties: false`）
- 内容不得落在 `GS:LINKS end` 之后（**F7**：会被静默丢弃，且 build / `--check` / `git status`
  三处都显示正常）

## 5.7 何时新增、何时修改

> **在流水线的哪一步执行**：④（见 §5.3.4「顺带定型」）。本节只定义判定规则与校准方式。

用检索相似度做初判，**但不让它单独决定**：

```
Top-1 相似度 ≥ 高阈值  → 判为「修改已有条目」
Top-1 相似度 < 低阈值  → 判为「新增」
落在中间             → 两个方案都产出，交给审阅人选
```

「两个方案都产出」是刻意的：需求方要求 *"push more rather than less"*，而模棱两可的情况
恰恰最需要人判断，不该由阈值替人做决定。

### 校准方式与 θ_c 不同

**审阅人选了哪个方案，就是这个阈值的标注数据**——不需要额外抽检：

| 观察 | 含义 | 动作 |
|---|---|---|
| 落在「中间」的比例过高 | 高低阈值离得太开 | 收窄区间 |
| 判为「修改」但审阅人改成新增 | 高阈值偏低 | 调高 |
| 判为「新增」但审阅人指到已有条目 | 低阈值偏高 | 调低 |

⚠️ 初始值需要用**评测集**定：`scripts/eval_playbook_recall.py` 与 `scripts/data/playbook/`
有现成的基线与打分口径，但 **`rag/CLAUDE.md` 反复强调「换切法数字不作数」**——
出站索引（§5.3.3）是新切法，**必须重新跑基线**，不能沿用入站的数字。这是一项独立的前置工作。

## 5.8 mistakes 的产出（已确认在范围内）

**从转录挖掘最自然的产物其实是 mistake**——`CONTRIBUTING.md` 的措辞就是
*"one you have watched happen, more than once or once vividly"*，这正是会议里会出现的东西。

两条产出路径：

1. **新增 mistake**（`MISTAKE_CREATE`）：编号 N3 才分配（C2）
2. **给已有 mistake 补 play 映射**（`PLAY_PREVENTS_ADD`）：**改动面最小、最容易被接受**。
   上游 14 条 mistake 无映射、7 个 play 无 mistake，`CHANGELOG` 自己标为 open work——
   建议把这类作为**首批回流内容**

## 5.9 拒绝与抑制：由拒绝理由推导抑制范围

需求方要求 *"if rejected, Goldie won't resurface that one in the future"*，但没说「那一条」
指什么。**这个不必反过来问他们——拒绝时让审阅人选一个理由，抑制范围由理由推导即可。**

### 5.9.1 「抑制范围」是什么

需求方要求 *"if rejected, Goldie won't resurface that one in the future"*。
问题在于 **"that one" 指什么**——这就是抑制范围。

#### 一段话可能挖出多个主张

假设某次会议里有这么一段：

> *"我们跟他们续签了三年，没人看有没有涨价条款。而且实施也是三次都在返工，
> 因为压根没有书面流程。"*

Goldie 从**这同一段话**可以挖出**两个不同的主张**：

| | 主张 | 目标 |
|---|---|---|
| 主张 1 | 多年期合同不查涨价条款会被通胀侵蚀利润 | 新增一条 mistake |
| 主张 2 | 没有书面实施流程会导致返工 | 给 `saas-customer-onboarding` 补映射到 #50 |

现在审阅人**拒绝了主张 1**。

#### 抑制范围 = 封的是「这段话」还是「这个主张」

| 抑制范围 | 主张 2 以后还会出现吗 | 别的会议说同样的事还会出现吗 |
|---|---|---|
| **封这段话**（`SOURCE`） | ❌ **连带封杀** | ✅ 会 |
| **封这个主张**（`TARGET`） | ✅ 不受影响 | ❌ 会被拦 |

**两种封法的作用面完全不同，选错就出错**：

- 封错成 `SOURCE` → 主张 2 这条好建议永远出不来了，**而且没人知道**
- 封错成 `TARGET` → 那段「其实没有可用经验」的话，下次换个角度又挖出一个新主张来烦人

#### 为什么由理由推导，而不是让人选

| 拒绝理由 | 该封什么 | 为什么 |
|---|---|---|
| **这段话没有可泛化的经验** | **这段话** | 整段没用，连带封掉它能挖出的其他主张**正是对的** |
| **语料里已有等价条目** | **这个主张** | 只是这一个主张重复了；这段话可能还有别的价值 |
| **自带不可去除的识别性** | **这段话** | 来源本身不能用，不管挖出什么主张 |

**理由已经隐含了作用面。** 让人再选一次「封哪个」，只会多一次出错机会——
而且是**无声的错**：封错了不报警，只是某条建议从此再也不出现。

#### 落到字段

拒绝时**必选一个理由**（可附自由文本），系统据此决定写哪些键：

| 理由（枚举值） | `scope` | 写入哪些键 | 语义 |
|---|---|---|---|
| `NOT_GENERALIZABLE`<br>不是真实/可泛化的模式 | `SOURCE` | `source_doc_id` + `segment_ref` + `semantic_vec` | 这段话本身不含可用经验，再挖一次还是同样结果 |
| `ALREADY_EXISTS`<br>语料里已有等价条目 | `TARGET` | `target_key` + `semantic_vec` | 这个**改动主张**已被否；来源可能还有别的价值，不封 |
| `CANNOT_PUBLISH`<br>自带不可去除的识别性 | `SOURCE` | `source_doc_id` + `segment_ref` + `semantic_vec` | 来源本身不能用 |
| `INSUFFICIENT_EVIDENCE`<br>证据不足 | — | **不写抑制表** | 走 `evidence_count` 累计，见 §5.9.2 |
| `NEEDS_REWORK`<br>方向对但质量差 | — | **不执行拒绝** | UI 引导到「与 Goldie 对话」，见 §5.9.3 |

`target_key` 的构造：`play:{slug}#{field}` / `mistake:{NNN}`。
⚠️ `ALREADY_EXISTS` 记的是**被复制的那条已有条目**（例如 `mistake:50`），不是被拒的候选——
被拒的候选此时还没有编号（编号在 N3 才分配）。

> ⚠️ 这五个枚举值是我们拟的（**暂定，A6**）。实际审阅中若出现「映射本身不成立」这类
> 现有五项覆盖不到的情形，需要补充枚举——**不要让人硬套一个不准的理由**，那会写出错误的抑制。

### 5.9.1b 抑制范围怎么用：匹配什么

对应 §5.2 的**两个判定时点**，各查各的键：

| 时点 | 位置 | 查什么 | 命中后 |
|---|---|---|---|
| **时点 1** | ① 与 ② 之间 | `scope=SOURCE` 且 `source_doc_id` + `segment_ref` 完全匹配 | **跳过整段**，省下 ② 的 LLM 调用 |
| **时点 2** | ④ 与 ⑤ 之间 | ① `scope=TARGET` 且 `target_key` 相同<br>② **任意 scope** 的 `semantic_vec` 相似度 ≥ 阈值 | **丢弃候选**，省下 ⑤ 的 LLM 调用 |

⚠️ **为什么 `SOURCE` 型也要存语义指纹**：转录若被重新分段，`segment_ref` 会变，
时点 1 就匹配不上了。此时该候选会照常跑完 ②，在**时点 2 靠语义指纹兜住**——
损失是白跑一次 ② 的调用，但抑制本身不失效。这是刻意的降级路径，不是漏洞。

#### 除了过滤，抑制记录还有三个用途

| 用途 | 怎么用 |
|---|---|
| **给审阅人上下文** | 候选与某条抑制记录**相似但未达阈值**时，在队列里标注「类似内容曾于 YYYY-MM-DD 被拒绝，理由：X」——让人知道这不是第一次看到 |
| **校准信号** | 抑制命中率异常高，说明 θ_c 太松或挖掘质量差；应改提示词而不是调阈值（同 §5.5.2 第三行的判据） |
| **审计** | 「为什么这条经验从来没被提出来过」——答案在抑制表里，带拒绝人与时间 |

#### ⚠️ 必须有解除入口

抑制会**永久**掐掉一条路径，因此必须能撤销。两类情形：

| 情形 | 说明 |
|---|---|
| **拒错了** | 人会误判，尤其在批量浏览队列时 |
| **前提变了** | `ALREADY_EXISTS` 抑制指向 `mistake:50`，而 #50 后来被上游改写或语义漂移——抑制的理由就不再成立 |

**解除是一个写操作，需要留痕**（谁解除、何时、为什么），与拒绝本身同等对待。
⚠️ 谁有权解除：未定，归入 **Q2 C 组**（职责与触发权）。

### 5.9.2 「证据不足」不该抑制，该计数

上游 `CONTRIBUTING.md` 对 mistake 的准入标准是：

> one you have watched happen, **more than once or once vividly**

**「出现次数」本身就是判据。** 所以一条「现在证据不够」的观察，将来在别的会议里再次出现时
**恰恰应该浮现**，而且更有说服力。抑制它等于把最有价值的信号掐掉。

处理方式：不写抑制表，而是在候选上记 `evidence_count` 与 `resurface_threshold`：
同一 `target_key` 的观察累计到阈值（**暂定默认 2，A7**）时重新入队，并在候选上标注
「本主张已在 N 次独立会议中出现」——这个标注本身就是给审阅人的最强证据。

### 5.9.3 「方向对但质量差」不该走拒绝

拒绝会写抑制表、永久掐掉。而「Goldie 起草得不好但主张是对的」应该走
**与 Goldie 对话**（N2 的四种动作之一），改到能用为止。

UI 上的落地：拒绝对话框里把「方向对但质量差」列为一个选项，选中后**不执行拒绝**，
而是切到对话面板。这是刻意的引导——防止把可修的东西当垃圾扔掉。

### 5.9.4 抑制的两个键

`ai_pb_suppression` 同时保留两个键，按理由写其一：

| 键 | 构成 | 稳定性 |
|---|---|---|
| 来源锚点 | `source_doc_id` + `segment_ref` | ⚠️ 转录重新处理后段落偏移会失效 |
| 目标锚点 | `play:slug#field` / `mistake:NNN` | 稳定 |

⚠️ **来源锚点的脆弱性是已知缺陷**：转录若被重新分段，`segment_ref` 对不上，抑制失效、
同一段会再次浮现。缓解手段是同时存**语义指纹**（`semantic_vec`，pgvector），
按相似度阈值兜底。**这条需要在实际数据上校准，不能凭猜设阈值。**

## 5.10 ⚠️ 本部分最大的风险

Goldie 从**转录**起草面向公开的文本，直接命中脱敏清单两条最难防的：

| 清单条目 | 为什么 LLM 特别容易犯 |
|---|---|
| **C1 无逐字引用** | 转录里信息量最大的就是原话，模型倾向保留措辞 |
| **D 组合识别** | 模型会改写措辞但**保留那个独特的属性组合**——那正是原文最有信息量的部分 |

而这两类：**我们的扫描器抓不到**（没有黑名单词）、**上游 CI 抓不到**（同上，何况现在空转）。
**只有 N3 的人工判定能抓。**

设计上的应对：

1. Goldie 的产出**必须标注来源锚点**，审阅人可一键对照原文，判断「是不是把原话搬过来了」
2. 提示词显式要求 essence only，并**禁止输出引号包裹的片段**
3. 自动扫描器已实现「疑似逐字引用」检测（成对引号 + 长度阈值）作为弱信号

⚠️ **第 4 条已确认可行**：转录会被送入外部模型，具体送什么见 **C5**（事实披露）。

## 6.3 diff 组件选型

**结论：`diff2html`**（3.4.56，2026-01）。

| 候选 | 输入 | React 16 | 判定 |
|---|---|---|---|
| **`diff2html`** | **统一 diff 字符串** | ✅ 无 peerDeps，框架无关 | **选它** |
| `react-diff-viewer` | 新旧两份全文（自己重算） | ✅ 仅 15/16 | ✗ 2020 年后停更 |
| `react-diff-viewer-continued` | 新旧两份全文（自己重算） | ✅ 15–19 | ✗ 见下 |

**决定性理由不是维护状态，是输入形态。**

后两者接收新旧全文、**用 jsdiff 自己重算 diff**。而我们整套设计的前提是：

> 审阅人看到的 == 我们哈希的 == CI 扫描的

重算就破坏了这个对应关系。我们已经实测过同类问题：Python `difflib` 在 `MISTAKES.md`
上因 autojunk 把 1 行改动算成 **1736 条内容行**（git 是 2 条）。jsdiff 没有 autojunk，
但仍是另一套算法，hunk 边界与插入点归属都会不同。

`diff2html` 吃的正是 `git diff` 的原始输出——**我们手上就有**，渲染出来和 GitHub 一致。

**已实测的对齐结论**（可放心依赖）：

```
本地 git diff  ==  GitHub commit API 的 files[].patch   （去掉 header 后逐字节相同，4/4 文件）
```

配套：
- `markdown-it` ^11 / `react-markdown` ^8 **已在依赖里**，用于渲染 play 正文预览
- `react-markdown-editor-lite` 1.3.4 已在依赖里，可用于 P2 的正文编辑

## 6.4 审阅发现问题怎么改

| 发现时机 | 处置 | 状态影响 |
|---|---|---|
| P2 审阅中 | 直接编辑 / 与 Goldie 对话 | 仍在 `REVIEWING`，无成本 |
| P2 脱敏判定不通过 | **回到编辑意图重写**（不是就地改 diff） | 回 `REVIEWING` |
| P3 批准前发现 | 打回 P2 | 签名作废，回 `REVIEWING` |
| 已批准、未推送 | 打回 | **签名 + 批准同时作废**，重走（D3） |
| **已推送 / 已开 PR** | **不可回退**——关闭 PR + 上报，按披露事件处置 | `CLOSED_DISCLOSURE` |

> ⚠️ UI 上**不能提供**「已推送后修改并重推」的入口。上游 `GOVERNANCE.md` 明确：
> *"close it, do not fix it in place, because a public pull request cannot be unpublished."*

# 第七部分 · Node 发布节点的数据一致性

## 7.1 为什么必须单独一个节点

| 依赖 | 用途 | 能否去掉 |
|---|---|---|
| **Node ≥18** | 跑上游 `scripts/build.mjs` 产出生成物 | ❌ 去不掉。自己复刻生成逻辑 = 两处真源，上游 CI 的 `--check` 会红 |
| **git** | clone / diff / commit / push | ⚠️ 理论可用 API 替代，但产 diff 要自己算，会破坏「我们哈希的 == CI 扫的」 |

在线 API 容器（`python:3.12-slim`）为一个低频离线动作背 200MB+ 的 Node + git 不划算，
且需要可写工作目录与到 `github.com` 的出网。**独立节点顺带把出网范围、凭据范围、
可写目录范围全部收窄到一个进程**，也部分弥补 D8。

## 7.2 一致性的核心原则

> **数据库是唯一真源，工作副本是可丢弃的缓存。**

工作副本随时可以从 `ai_pb_change_public.note` + `edit_intent` + 上游 base 完整重建。
服务重启、容器漂移、磁盘丢失，都只是「重建一次」，不产生不一致。

## 7.3 发布作业状态机

`ai_pb_publish_job` 承载，**每一步都先写库再执行**：

```
PENDING ──lease──> RUNNING ──> PUSHED ──> PR_OPENED ──> DONE
                      │            │           │
                      └── FAILED ──┴───────────┴──> （可重试；重试前先对账）
```

## 7.4 危险窗口与对账

真正的风险只有一个：**push 成功但回写失败**（进程被杀 / 网络断 / 数据库不可用）。
此时远端已经有了分支（**内容已经公开**），而库里还是 `RUNNING`。

**解法：以分支名作幂等键，重启后先对账再动作。**

`p4_branch = lg/<opaque_ref>`，而 `opaque_ref` 在 N1 就已入库、全局唯一 →
**分支名在 push 之前就是已知且确定的**，可以拿它去远端反查。

对账逻辑（服务启动 + 每次重试前）：

| 远端状态 | 库内状态 | 动作 |
|---|---|---|
| 分支不存在 | `RUNNING` | 未推成功 → 重建工作副本，重新走推前判定 |
| 分支存在，tip == 预期 commit | `RUNNING` | 已推成功 → **补写** `PUSHED`，继续开 PR |
| 分支存在，tip ≠ 预期 commit | `RUNNING` | **异常**：置 `FAILED` + 人工介入，**绝不强推** |
| 分支存在 + PR 已存在 | `PUSHED` | 补写 `PR_OPENED` + 回写 SHA/URL |

「预期 commit」怎么算？重建工作副本后重新组装载荷、比对批准哈希——哈希相同则内容相同，
但 commit SHA 还依赖提交时间与作者。因此**提交时使用固定的 author/committer 日期**
（取批准时间戳），使 commit SHA 对同一载荷可复现，对账才能精确到 tip 比对。

⚠️ 若不固定日期，对账只能退化为「分支存在即认为推成功」，仍可用但精度低。**建议固定。**

## 7.5 串行与租约

- **发布串行**（D11）：`ai_pb_publish_job` 上用 `SELECT … FOR UPDATE SKIP LOCKED` 取一条，
  或用 PG advisory lock 锁住「发布」这一个逻辑资源
- **租约**：`lease_owner` + `lease_expires_at`，防止实例假死后作业永久卡住；
  租约过期由另一实例接管，接管前必须走 §7.4 的对账
- 审阅**不串行**，只有 N5 串行

## 7.6 与 Python 侧的边界

| | Python（`CIOaas-python`） | Node 发布节点 |
|---|---|---|
| 职责 | N1–N4、N6 的状态管理、Goldie、检索、ACL | N5：git + `build.mjs` + push + 开 PR |
| 数据 | 读写全部业务表 | **只读 `ai_pb_change_public` + 读写 `ai_pb_publish_job`** |
| 内部侧 | 可读 | **无 `SELECT` 权限**（DB 角色隔离） |
| 触发 | 写入 `PENDING` 作业 | 轮询 / 队列消费 |

Node 节点**在数据库角色层面读不到 `internal_rationale`**——这是 D8 之外真正的机制隔离，
且它是部署这个节点的自然副产品，不是额外成本。

# 第八部分 · 语言选型

**发布节点用 Node.js。** 理由按权重排序：

1. **`build.mjs` 必须由 Node 执行**（第七部分 7.1）。选 Node 意味着**不需要跨语言起子进程**——
   发布节点可以直接 `import` 上游的构建逻辑，或以子进程调用，两种都自然
2. **版本等价性已实测**：Node **22.23.2** 与上游 CI 的 Node **20** 产出**字节一致**
   （根因：`build.mjs` 零外部依赖、纯字符串处理，无浮点 / locale / Intl）。
   已在真实 PR 上验证：我们用 22 生成的产物，被上游 CI 的 20 判为 `up to date`
   ⚠️ 上游改动 `scripts/` 后需重验（`scripts/` 在 `CODEOWNERS` 里，改动会走 PR，可感知）
3. **后续 Slack / Teams 需求**需要 Node 把 chart 转图片（已知需求），同一节点复用

**依赖**：`git` CLI（不用 nodegit 等绑定，避免原生编译）、`node ≥ 20`（对齐上游 CI）、
GitHub REST（用内置 `fetch`，不引 SDK）。

**不选 Python 的原因**：Python 侧要么起 Node 子进程（那 Node 依然要装，白搭一层），
要么自己复刻 `build.mjs`（两处真源，必然漂移）。

# 第九部分 · 数据库设计

> 10 张表，全部落在业务库（PG）。命名沿用 `ai_` 前缀 + 域名 `pb`（playbook）。
> DDL 走版本化迁移 `CIOaas-python/sql/migrations/business/`，启动期不自动建表。

| 字段 | 说明 |

| `target_slug` / `target_mistake_no` | 目标条目 |
| `anchor_index` / `anchor_hash` | 段落锚点双键（§5.6），哈希对不上即判为**过期意图** |
| `payload` | JSONB，按 `kind` 定形 |
| `is_current` | 当前生效版本 |

### `ai_pb_review_event` — 审阅流水

| 字段 | 说明 |
|---|---|
| `id` / `change_id` | PK / FK |
| `action` | `ACCEPT` / `EDIT` / `CHAT` / `REJECT` |
| `actor` | 操作人（真实姓名） |
| `payload_hash_at` | 操作时的载荷哈希——**证明「评审的是哪一版」** |
| `detail` | 意见原文 / 对话轮次引用 |
| `created_at` | UTC |

### `ai_pb_suppression` — 拒绝抑制

| 字段 | 说明 |
|---|---|
| `id` | PK |
| **`scope`** | **`SOURCE` / `TARGET`——决定匹配时查哪个键（§5.9.1），由 `reason` 推导，不由人选** |
| `source_doc_id` / `segment_ref` | 来源锚点键（`scope=SOURCE` 时写） |
| `target_key` | 目标锚点键（`play:slug#field` / `mistake:NNN`；`scope=TARGET` 时写） |
| `semantic_vec` | 语义指纹（pgvector）——**两种 scope 都写**，用于来源锚点失效时兜底 |
| `reason` | 拒绝理由枚举（必填）：`NOT_GENERALIZABLE` / `ALREADY_EXISTS` / `CANNOT_PUBLISH` |
| `rejected_by` / `rejected_at` | 留痕 |
| **`active`** | **是否生效——解除后置 false，不物理删除** |
| **`revoked_by` / `revoked_at` / `revoke_reason`** | **解除留痕（§5.9「必须有解除入口」）；解除与拒绝同等对待** |

> 抑制范围**由拒绝理由推导**，不由人选（§5.9.1）：`reason` 决定 `scope`，`scope` 决定写哪个键。
> ⚠️ 来源锚点在转录重新分段后会失效，因此两种 scope 都并存 `semantic_vec` 兜底，
> 相似度阈值需在实际数据上校准。

> ⚠️ 拒绝理由为「证据不足」时**不写本表**——改为在候选上累计 `evidence_count`，
> 达到 `resurface_threshold`（默认 2）时重新入队（§5.9.2）。上游 `CONTRIBUTING.md`
> 的准入标准是 *"more than once or once vividly"*，**出现次数本身就是判据**，抑制它等于
> 掐掉最有价值的信号。

### `ai_pb_discarded_sample` — 丢弃抽样留档

| 字段 | 说明 |
|---|---|
| `id` | PK |
| `source_doc_id` / `segment_ref` | 来源锚点（**只存锚点，不存原文**） |
| `stage` | 哪一段丢的：`COARSE`（① 粗筛）/ `THRESHOLD`（④ θ_c） |
| `rule_id` | `stage=COARSE` 时记哪条规则丢的（R1–R4） |
| `claim` | LLM 产出的一句话主张（`stage=COARSE` 时为空——还没跑到 ② 段） |
| `confidence` | 判定分，用于分析阈值边界（同上，粗筛阶段为空） |
| `theta_at` | 当时生效的 θ_c |
| `audited` / `was_miss` | 人工抽检结果 —— `miss_rate` 由此算出 |

> 存在的唯一理由：**漏报看不见**。被 θ_c 丢掉的分段不会进入任何指标，
> 只看 precision 调阈值会稳定地往「越调越严」漂移，与需求方 *"push more"* 的政策相反（§5.5.1）。

### `ai_pb_calibration` — θ_c 调整记录

| 字段 | 说明 |
|---|---|
| `id` | PK |
| `theta_before` / `theta_after` | 调整前后值 |

### `ai_pb_disclosure_incident` — 披露事件

| 字段 | 说明 |
|---|---|
| `id` | PK（事故编号，内部引用用） |
| `opaque_ref` | 涉事变更 |
| `detected_by` / `detected_at` / `detect_source` | 谁/何时/怎么发现（`POST_PUSH_RESCAN` / `BLOCKLIST_RESCAN` / `CI` / `HUMAN` / `EXTERNAL`） |
| `pushed_at` | ⚠️ 与 `detected_at` 之差 = **暴露时长**，核心指标 |
| `surfaces` | 携带泄漏的公开面（P1–P5 哪几面） |
| `leaked_detail` | ⚠️ 内部：具体泄漏了什么 |

### `ai_pb_publish_job` — 发布作业

| 字段 | 说明 |
|---|---|
| `id` | PK |
| `opaque_ref` | FK → `ai_pb_change_public`，**唯一索引**（一条变更只有一个作业） |
| `state` | `PENDING` / `RUNNING` / `PUSHED` / `PR_OPENED` / `DONE` / `FAILED` |
| `branch_name` | `lg/<opaque>`，**幂等键**，push 前即已确定（§7.4 对账靠它） |
| `expected_commit_sha` | 重建后算出的预期 SHA（需固定 author/committer 日期才可复现） |
| `lease_owner` / `lease_expires_at` | 租约，防实例假死卡死作业 |
| `attempt` / `last_error` | 重试与诊断 |
| `ci_conclusion` / `mergeable_state` | N6 轮询结果——⚠️ **`mergeable_state` 必须存**（C2） |

## 9.3 状态机

```
SURFACED ──> REVIEWING ──> SUBSTANTIVE_OK ──> SCRUBBED ──> RATIFIED ──> PUBLISHING
    │            │               │                │            │            │
    └── REJECTED ┘               └────────────────┴────────────┘            ▼
   （是否写抑制表看理由）            任一环节内容变动 → 回 REVIEWING       PR_OPEN
                                    （签名 / SME / GP 三者同时作废）          │
                                                            ┌───────────────┼──────────────┐
                                                            ▼               ▼              ▼
                                                         MERGED        CONFLICT     CLOSED_DISCLOSURE
                                                                     （回 REVIEWING   CLOSED_REJECTED
                                                                      重分配编号）
```

⚠️ **`PUBLISHING → PR_OPEN` 之后不可回退**：内容已公开，处置只有披露事件流程。

## 9.4 索引要点

- `ai_pb_source_doc(provider, external_id)` 唯一 —— 幂等拉取
- `ai_pb_change_public(opaque_ref)` 唯一；`(state)` 普通索引 —— 队列扫描
- `ai_pb_publish_job(opaque_ref)` 唯一；`(state, lease_expires_at)` —— 取待办 + 租约回收
- `ai_pb_edit_intent(change_id, is_current)` —— 取当前版本
- `ai_pb_suppression(scope, source_doc_id, segment_ref)` —— **时点 1** 查来源锚点（§5.9.1b）
- `ai_pb_suppression(scope, target_key)` —— **时点 2** 查目标锚点
- `ai_pb_suppression.semantic_vec` 建 HNSW（向量库）—— 时点 2 的兜底匹配
- ⚠️ 以上三处查询都要带 `active = true`，否则解除过的抑制会继续生效
- `ai_pb_discarded_sample(stage, audited)` —— 召回抽检取样（§5.5.2）
- `ai_pb_disclosure_incident(opaque_ref)` —— 由变更反查事故

## 10.3 通读发现的缺口

### ① 五面载荷的持久化归属未定

N4 批准页要展示五面，N5 推前要重算五面。但**五面是 Node 侧从工作副本算出来的**，
而 N4 发生在 Python 侧的页面上。

两个选项：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 只存哈希，展示时现算** | 批准页请求 Node 节点实时组装 | Node 必须常驻可用；批准页依赖它 |
| **B. N3 结束时把五面快照入库** | 存一份 `payload_snapshot` | 多一份存储；**但快照与工作副本可能漂移** |

**倾向 A**，因为 B 的快照会引入第二个真源——而我们整套设计就是在防「两处真源」。
但需要接受「批准页依赖 Node 节点在线」。**待定，需评审。**

### ② `base_ref` 的选取策略未定

邮件与 `GOVERNANCE.md` 要求摄取 pin 在 **tagged release**（当前 `v1.0.0` = `fab61ef3`）。
但**回流的分支应该基于 main 还是 tag？**

- 基于 **tag**：与摄取基线一致，但 tag 落后 main（当前落后 3 个提交），PR 会带上无关差异
- 基于 **main**：diff 干净，但与我们索引的基线不一致，Goldie 可能基于旧内容提改动

**倾向：索引 pin tag（保证可追溯），回流分支基于 main（保证 diff 干净）**，
并在 N1 产出意图时用段落锚点哈希校验目标是否已变（§5.6）。**待评审。**

### ③ 披露事件已补设计，但暴露出一个更根本的问题 ✅→⚠️

第四部分已补齐。补的过程中实测出一条改变基调的事实：

> **关闭 PR + 删除远端分支之后，commit 与文件内容依然完整可取**
> （GitHub 把 head 留在 `refs/pull/N/head`，关闭与删分支都不移除）。

所以「关闭 PR」是**止损**，不是移除。这条推翻了一个很自然的直觉，也直接决定了：
UI 文案不能写「已解决」、不能提供「修改后重推」、不能把删分支当补救。

**由此得出的真正结论**：披露事件流程本身**不提供任何防护**，它只做事后管理。
唯一有实际防护价值的是两条 tripwire：

| | 作用 |
|---|---|
| **M1 push 后立即复扫** | 把「push → 发现」从几天压到几秒。**暴露时长是唯一还能优化的变量** |
| **M2 黑名单更新后回扫历史** | 覆盖「当时合规、后来才成为泄漏」——黑名单是活的，不回扫永远发现不了 |

**这两条应当优先于披露事件的 UI 实现**——前者能减少事故，后者只是记录事故。

### ④ Goldie 置信度与阈值校准未量化

§5.7 的相似度阈值必须用评测集校准，而**出站索引是新切法，入站的基线数字不作数**
（`rag/CLAUDE.md` 反复强调）。这是一项独立的、有工作量的前置任务。

### ⑤ templates / stories 未覆盖

Q1 只确认了 mistakes。若模板进范围，`.xlsx` 的处理（F5 盲区、文档属性、隐藏表）
需要单独一节，且 `diff2html` 对二进制无能为力，审阅 UI 要另想办法。
