## 这份文档怎么用

我们把所有悬而未决的事分成三类，**分类标准是「谁能回答」**：

| 部分 | 是什么 | 你们要做什么 |
|---|---|---|
| **第一部分** | 只有你们能回答的问题 | **需要答复**——不答我们就得靠猜 |
| **第二部分** | 你们必须知道、但不用回答的事实 | **知悉即可**——这些会影响你们对风险和进度的判断 |
| **第三部分** | 我们替你们做的决定 | **请复核**——不同意的地方告诉我们 |

我们刻意**没有**把自己能设计、能决定的事放进第一部分。把设计问题包装成需求问题，
只会换回一个猜测，不如我们先提方案、你们复核。

## 先约定几个说法

后面反复出现，这里说清楚，读到时不用回头查。

| 说法 | 意思 |
|---|---|
| **上游仓库** | GitHub 上公开的 `Golden-Section-Tx/playbook`，我们的改动最终要提交到那里 |
| **play** | 「该怎么做」的操作流程，共 63 个 |
| **mistake** | 「别人踩过的坑」，一句话的观察，共 161 条，每条有一个**永久编号** |
| **提交请求（PR）** | 向上游仓库提出「我想改这些内容」的正式请求，由上游的人决定是否接受 |
| **公开出去的五样东西** | 一次改动会同时公开五样：① 改动内容本身 ② 附带的 Excel 模板 ③ 提交说明 ④ 分支名 ⑤ 提交请求的标题与正文。**这五样全部永久公开** |
| **脱敏** | 把「哪家公司、哪个创始人、多少钱」这类信息去掉，只留下可复用的经验 |
| **内容指纹** | 给「这一版要公开的全部内容」算出的一串校验码。内容改一个标点，指纹就变 |
| **Goldie** | 负责从会议记录里挖掘经验、起草改动的智能体 |

# 第一部分 · 需要你们回答的问题

## Q1 · 除了 play 和 mistake，Excel 模板和长文案例要不要一起做？

### 背景

上游仓库里有四类内容。你们已经确认了前两类：

| 内容 | 数量 | 是否在本次范围内 |
|---|---|---|
| play（操作流程） | 63 个 | ✅ 是 |
| mistake（踩坑记录） | 161 条 | ✅ 是（已确认） |
| **templates（Excel 模板）** | **59 个** | ❓ **待确认** |
| **stories（长文案例）** | 目前为空 | ❓ **待确认** |

上游自己说模板是最有价值的贡献方向：*"修正现有模板里坏掉的公式、错误的引用、
不再成立的假设——这是任何人能做的最有用的贡献。"*

### 需要你们回答

**Excel 模板和长文案例，这一期做还是留到下一期？**

### 不回答会怎样

**做不了模板相关的任何功能，而且会返工。** 模板是 Excel 文件，和纯文字改动完全不同：

- **审阅界面要另做一套**。文字改动可以左右对照高亮，Excel 不行——得先把表格拆成
  可比对的文本，再做一个「看渲染效果」的辅助页签
- **上传通道要另做**。Goldie 写不出 Excel 表格，模板只能由人上传
- **保密检查要另做**。Excel 文件里藏字的地方特别多：作者名、公司名、隐藏的工作表、
  单元格里的示例数据、图表标题。**上游的自动检查对这些完全看不见**

我们的**建议是留到第二期**——技术上不难，但会让第一期的工作量接近翻倍。
先把 play / mistake 这条链跑稳，模板作为增量。

**说白了就两件事**：文字改动能一眼看出改了哪一行，Excel 不能；文字改动的每个字都能被
自动检查读到，Excel 里的字一个都读不到。

| | 文字（play / mistake） | Excel 模板 |
|---|---|---|
| **能看出改了哪儿吗** | ✅ GitHub 上直接高亮到行 | ❌ **只显示「二进制文件有差异」**，改了哪个单元格完全看不见 |
| **自动检查能读到内容吗** | ✅ 逐字扫描 | ❌ **一个字都读不到**——我们实测过：往模板里塞进一个公司名，检查完全无感 |

这两件事都得我们自己从头做一套：**把表格拆成能比对的文本**给人看，
**把文件解包**逐层扫描里面的作者名、隐藏工作表、单元格内容。

## Q2 · 谁有权做什么？（本清单最需要回答的一条）

### 背景

这一条包含三件互相依赖的事，**必须一起回答**，只答其中一个另外两个也定不了：

```
有哪些角色？ ──> 每个角色在哪一步能改什么？ ──> 谁有权触发不可逆的动作？
```

*"GP 和 portfolio admin 是一回事"*？系统需要的细致程度比这句话高很多。

### 已经确定的（不用再答）

| | 出处 |
|---|---|
| 审阅时有四种操作：直接编辑 / 和 Goldie 对话 / 整体接受 / 整体拒绝 | 你们的答复 |
| GP 批准的对象是「改好之后的 play 内容」 | 你们的答复 |
| 流程顺序：SME 审核 → 脱敏 → GP 批准 | 你们确认过 |

**SME 审核和 GP 批准是两个独立步骤**。两者可以并存（同一批人走两道手续），
但系统必须能分清这两道手续各自是谁完成的。

### 需要你们回答

#### A 组 · 角色怎么定

1. **SME 和 GP 对应现有哪个角色？** 五个现有角色里没有对得上的——是用「产品负责人」？
   用「超级管理员」？还是**新增两个角色**？
2. **权限管到哪一层？** 有这个角色就能处理所有条目，还是只能处理**自己负责的被投企业**
   相关的条目？
3. **同一个人能不能既做脱敏签字、又做批准？** 如果可以，等于自己审自己；
   如果不可以，人手不够时流程会卡住。

   > 参考：上游 GitHub 就遇到过同样的两难。它不允许自己批准自己的提交请求，
   > 而上游维护团队只有一个人，结果只能保留「直接改主干」的后门。

#### B 组 · 每一步能改什么

4. **那四种操作（编辑 / 对话 / 接受 / 拒绝）是在哪一步？** SME 那步、GP 那步、还是两步都有？
5. **SME 审的是什么？** 只判断「这是不是一条真实、可复用的经验」，还是也要做脱敏判断？
6. **脱敏那道手续（逐项检查 + 签字）由谁执行？** 是 SME 的一部分，还是单独一个角色？
7. **GP 在批准页面能不能直接改内容？** 还是只能「同意」或「打回」？

#### C 组 · 谁能触发什么

8. ⚠️ **GP 批准之后，是自动发布，还是要人再点一次「发布」？**（设计里原本完全空白）
9. 编号撞车时（见 C2），**自动回退重来，还是由人决定**？
10. **出了泄漏事故，谁有权宣布？谁有权判定「这是误报，不用启动」？**
11. **泄漏事故要通知哪些人？**
12. **谁能看到内部完整记录**（含公司名、创始人名、具体金额）？
13. **打回的时候退回到哪一步？** 退回 Goldie 重挖、退回 SME、还是退回脱敏？
14. **审阅界面要不要「批量接受」按钮？**
15. 若模板进范围（Q1），**谁能上传模板文件？**

### 不回答会怎样

**审阅、批准、发布三个页面全都做不了**，因为不知道该给谁看、给谁按钮。具体地说：

| 不知道 | 做不了什么 |
|---|---|
| 角色怎么定（A 组） | 登录之后不知道该显示哪个页面。而且要不要让 Java 那边加角色、要不要改登录信息，都定不了 |
| 每步能改什么（B 组） | 界面上的「编辑」按钮该出现在哪一页定不了。**而且这会影响返工量**——如果批准页也能编辑，就要多做一套「改完重新签字重新批准」的逻辑 |
| 谁能触发（C 组第 8 问） | ⚠️ **这个最要紧**。如果是「批准即自动发布」，那 GP 点下批准的**那一瞬间内容就公开了**，中间没有任何缓冲。而发布是**不可撤回**的（见 C3） |
| 谁能看内部记录（第 12 问） | 审阅页面要展示会议原文供对照，但不知道该给谁看，页面就没法做 |

⚠️ 我们**暂时按「两个独立角色」实现**——因为合并容易（一个人同时持有两个角色即可），
拆分难（事后要补一整层权限和记录）。但这是猜的。

## Q3 · LG 拿到上游仓库的写权限之后，还受不受「必须通过检查才能合并」的约束？算不算外部？

### 背景

你们说会给 LG 开通上游仓库的写权限。但上游的规则文件里写着两句话，
它们对「有写权限的人」的处理不一样：

- 「**外部**提交的请求，必须通过自动检查才能合并」
- 而 LG 一旦有了写权限，**就不再算「外部」了**

也就是说，开通写权限有可能**顺带把自动检查从我们头上摘掉**——而那道检查
恰恰是整条链上唯一的自动兜底。

另外规则文件还写着「写权限只属于维护者团队，其他任何人都不能推送」，
和「要给 LG 开写权限」字面上是冲突的，上游那份文件需要改一行。

### 需要你们回答

请上游**明确把 LG 的提交请求纳入「必须通过检查」的范围**，不要依赖默认判定。

### 不回答会怎样

**可能出现一种最坏的组合**：我们有了写权限，可以推送，但推上去的内容不再被自动检查。
**权限变大了，防护变小了。**

## Q4 · 邮件说自动检查覆盖四个方面，实际代码只覆盖一个

### 背景

邮件里写的是：*"检查会扫描改动内容、提交说明、分支名和提交请求正文——这四样在
提交请求打开的那一刻就都公开了。"*

我们读了上游的实际代码：**只扫描改动内容，另外三样一个都没扫。**

| 公开的东西 | 邮件说会扫 | 实际 |
|---|---|---|
| 改动内容 | ✅ | ✅ |
| 提交说明 | ✅ | ❌ |
| 分支名 | ✅ | ❌ |
| 提交请求正文 | ✅ | ❌ |

三种可能：邮件写错了现状 / 这是还没上线的计划 / 另有我们看不到的检查。
第三种我们排除不掉，因为上游的组织级配置我们无权查看。

### 需要你们回答

**确认一下究竟是哪种情况。**

### 不回答会怎样

**影响不大，我们已经自己补上了。** 我们的检查覆盖全部五样公开内容，不依赖上游。
问这一条是为了**对齐认知**——如果对方以为有四道防线、实际只有一道，
他们对风险的判断就是错的。

# 第二部分 · 需要你们知道的事实（不用回答）

> 这几条不是问题，是会影响你们判断和预期的客观情况。

## C1 · ⚠️ 上游的保密检查，到今天为止一次都没真正运行过

### 事实

那道检查需要配一份「禁用词清单」（比如被投企业的名字）。我们查了上游的公开运行记录：

```
警告：CONFIDENTIAL_TERMS 未配置——检查已跳过
```

**清单没配，所以检查每次都直接跳过、返回成功。** 页面上显示的是绿色对勾，
那条警告藏在需要展开才能看到的地方。

这一点**任何人都能验证**——上游仓库是公开的，运行记录也是公开的。

### 这不改变什么

上游本来的设计立场就是「**人是控制点，自动检查只是兜底**」。你们答复里说
「组合团队会逐条审」，和这个立场是一致的，不是因为依赖自动检查才这么说的。

### 这改变什么

**风险画像变了**：原本以为控制点之外还有一层自动兜底，实际**没有任何冗余，
控制点是单点**。

⚠️ 而且**在配上那份清单之前，必须先修两个缺陷**（我们已经实测确认，详见下方），
否则一配上就会同时出现「大部分词失效」和「误报别人的问题算到我们头上」两种情况。

### 我们实测出的两个缺陷

**缺陷一：在网页上配置词清单，大部分词会失效。**

网页表单提交的换行符和脚本期待的不一样，导致**除了最后一行，其余每个词都永远匹配不上**。
配 3 个词失效 2 个，配 10 个词失效 9 个——而界面上完全看不出异常。

我们做了三次对照实验来确认：完全相同的内容，只改换行符，一次放行一次拦下；
加上一行修复代码之后，原来放行的那次也被拦下了。

**缺陷二：会把别人的内容算到我们头上。**

检查比对的范围取错了，导致**别人后来加到主干上的内容，会被当成「我们这次要删掉的东西」**
一起扫描。命中了就算我们的问题。

而检查失败时给出的提示是「关闭这个提交请求」——于是**别人的问题会被当成我们的泄漏事故来处理**，
真问题没解决，还抓错了人。

## C2 · ⚠️ 新增 mistake 时编号可能被别人抢走，导致一条已经批准的改动作废重来

### 背景

每条 mistake 有一个**永久编号**（现在是 1–161，下一个是 162）。这个编号：

- **永远不能改，也不能重复使用**——官网、LookingGlass、以及任何人复制的副本都在引用它
- **真实来源是上游仓库，不是我们的系统**

我们分配了 162 之后、提交请求被合并之前，**别人也可能提交一条 162**：

| 谁 | 可能性 |
|---|---|
| 上游的另一个内部系统（Dougal 的知识库） | 有 |
| 外部贡献者 | 有 |
| 上游维护者直接改主干 | 低但存在 |
| **我们自己另一条同时在走流程的改动** | **有**——审阅是可以并行的 |

### 撞了会怎样（我们实测过）

我们在测试仓库里造了这个场景：两条改动都占 162，合并其中一条之后，另一条——

| | 结果 |
|---|---|
| 自动检查 | **全绿** |
| 能不能合并 | **不能，GitHub 挡住了，提示需要人工解决冲突** |

**这是最难发现的一种失败**：没有任何告警，绿色对勾摆在那里，提交请求静静挂着；
而去解决冲突的是**上游的维护者**，我们这边的系统根本不会知道。

### 我们的选择：撞了再处理---做不了预防

**不去跟上游协商预留号段、不做全局锁。** 理由：

- 预防的成本（跨组织协调）**远大于**撞车的概率和代价
- 上游主干从今年 8 月 23 日首次发布至今**一个提交都没有**，实际频率极低
- 撞了的后果是「重走一遍流程」，**不是数据损坏**

我们会做两道拦截：**推送之前**重新确认编号还没被占（能拦住绝大多数，
而且是在内容公开之前拦下的）；**提交请求打开之后**持续观察是否出现冲突（拦漏网的）。

### 你们需要知道的

**编号撞车会让一条已经批准的改动作废重来。** 这不是缺陷，是「编号永久不可复用」
这个上游规则的必然代价——我们选择接受它，而不是为它建一套预防机制。

## C3 · ⚠️ 发布是不可撤回的，而且「推送」那一刻内容就已经公开了

### 三个事实

**一、不是提交请求打开才公开，是推送完成就公开。**
上游是公开仓库，内容一推上去，全世界立刻可见、可复制、可被搜索引擎收录。

**二、关闭提交请求 ≠ 内容消失。**

我们实测过：关闭提交请求、并且删掉分支之后，**那次提交的内容依然可以完整取回**。
GitHub 会把它保留在一个特殊位置，关闭和删分支都不移除。

**所以「关闭提交请求」是止损动作，不是移除动作。** 界面上也不能给人这种暗示。

**三、已经合并的内容改不掉。**
上游禁止任何人改写主干历史，包括维护者自己。修补已合并的内容需要在
**别人已经复制过的仓库**上重写历史，视为不可行。

### 因此处置方式是

**关闭提交请求 + 立即上报**，不是「改一版再推」。

上游规则文件原话：*"关闭它，不要就地修复，因为公开的提交请求无法收回。"*
邮件原话：*"立刻告诉我，不要试图悄悄修补；到那一步我们处理的是一次信息披露，不是一个改动。"*

## C4 · 人工审阅是唯一的控制点，它的工作量直接决定可靠性

### 背景

你们的两句要求放在一起看：

- *"让智能体多推一些而不是少推一些，我们慢慢校准"* —— 刻意要求**宁滥勿缺**
- *"组合团队会逐条审，有问题我们能发现"* —— 人工审阅是**唯一**的脱敏控制

### 需要注意的

**审阅量一旦超出承受，可以预见的退化是「批量接受」而不是逐条判断。**

这不是我们实测出来的，是推断。但它决定了两个设计取舍：

1. **审阅界面不提供「批量接受」按钮** —— 因为最难的那类判断（见下）本质上无法批量做
2. **筛选的松紧做成可调的**，而且每次调整都留记录

### 为什么最难的那类判断无法批量做

有一类泄漏，**任何自动检查都抓不到**：

> *"一家位于塔尔萨、14 人的 HVAC 排班软件公司"*

这句话里**没有公司名、没有人名、没有任何禁用词**。自动检查看到的是一段完全合规的
泛化描述。但它**唯一地指向一家公司**。

而且判断的基准不是「全世界所有公司」，是**投资组合本身**——几十家，
而且大概率官网上就公开列着。在几十家的池子里，**一个行业加一个规模区间往往就只剩一家**。

**只有人逐条看、并且拿脱敏后的文字去搜索引擎实际查一遍，才能发现这类问题。**

## C5 · 哪些内容会被送进大模型

你们已确认转录可以送入外部模型。这里把**具体送什么**列清，便于知情。

| 环节 | 送出去的内容 | 含公司名/人名吗 |
|---|---|---|
| **挖掘经验** | **单段会议记录原文** | ✅ **含**——逐字对话、公司名、创始人名、具体金额 |
| **起草文字** | 已泛化的一句话 + 上游公开语料 | ❌ 不含 |
| **审阅人与 Goldie 对话** | 审阅人输入 + 当前候选 | 视输入而定 |

**只有第一个环节会把带身份的原文送出去。** 三条限定：

1. **一次只送一段，不送整份会议记录**
2. **原文只在这一步出现一次**——后面几步只传泛化后的一句话，要看原文靠索引回查。
   这不是省事，是缩小暴露面：原文一旦一路传下去，就会出现在更多日志、
   更多中间数据、更多模型请求里
3. **统一走公司内部的模型调用通道**，不直连厂商

⚠️ 需要注意这与产品现有的模型调用**性质不同**：智能客服和财务提取处理的是
**客户自己的数据**；这里是**被投企业创始人的私密对话**，而这些企业并不是我们的客户。

既然已确认可送，就不再作为待确认项——但**模型供应商的数据留存策略**值得单独确认一次
（属运维/合规事项，不阻塞开发）。

## 3.1 技术决定（12 条）

| # | 我们定的 | 为什么 | 你们不同意的话 |
|---|---|---|---|
| D1 | 脱敏排在 SME 审核之后、GP 批准之前 | 你们确认的流程就是这个顺序；先审实质，再花力气泛化 | — |
| D2 | **GP 批准绑定的是「这一版内容」，不是「这条记录」** | 否则批准之后内容还能改，批准就形同虚设 | 这条改了整个流程失去意义，**建议保留** |

| D7 | 提交说明、分支名、提交请求正文**按规则生成，不调大模型** | 提交说明描述的是「改了什么」，而改动内容本身已经公开，不需要看内部理由 | 保留 |

| D11 | **发布串行**：同一时刻只有一条改动在推送 | 消除我们自己造成的基线漂移 | ⚠️ 注意它**不消除编号撞车**（见 C2） |
