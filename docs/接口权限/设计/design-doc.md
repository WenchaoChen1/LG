# 管理端接口级权限 — 设计方案（第一期）

> 关联文档: [附录 A：后端写接口映射](./endpoint-permission-map.md) · [附录 B：前端按钮清单](./frontend-button-map.md) · [多租户调研 · 执行摘要](../../多租户与企业级安全/调研/executive-summary.md) · [多租户需求 M-9](../../多租户与企业级安全/需求/requirement-doc.md)

- 状态：方案稿，待评审。没有改任何代码。
- 日期：2026-10-13，依据 sprint121 的代码和本地 `lg_test` 库。

## 1. 背景与目标

**现状：系统只验身份，不验权限。**

- 网关只记日志，不做任何校验。
- web 服务只检查 token 有效、且在 Redis 里存在，其余接口一律放行（`CommonSecurityConfiguration.java:56`）。
- Spring 方法级鉴权已开启（`WebApplication.java:24`），但全仓没有一处权限注解。
- 认证时用户的权限列表写死为空（`JwtAuthenticationFilter.java:43`）。
- 现成的权限检查组件 `@rc.check`（`PermissionConfiguration.java:17`）从没被调用过。

库里已经有「角色 → 菜单 → 功能点」的表和管理页，但只用来控制前端显示哪些菜单。没有任何"接口 ↔ 权限"的映射。

**目标：**

1. 管理端用户调写接口（新增 / 修改 / 删除）时，服务端按「模块 × 动作」判定，无权限返回 403。
2. 权限通过一个新的管理页分配给角色。
3. 前端按权限隐藏没有权限的按钮。

**和多租户需求的关系：**
- 本方案落实多租户需求 M-9 里"按钮权限由服务端判定、前端只负责显示"中的**功能权限**部分。
- "能不能动这家公司 / 这个组织的数据"属于**数据归属**，不在本方案范围，仍归多租户第 2 步。

## 2. 已定决策（2026-10-13）

| # | 问题 | 决定 |
|---|---|---|
| D1 | 权限粒度 | 按「模块 × 动作」细分，动作只有新增、修改、删除三种 |
| D2 | 适用范围 | 第一期只管管理端用户（`user.role_type = 1`）；公司端用户的请求不做检查，行为不变 |
| D3 | 新增和修改合一的接口、流程动作（提交、接受、发布、同步、分享等） | 有该模块的新增或修改任一权限即放行 |
| D4 | 前端按钮 | 第一期就做隐藏 |

## 3. 范围

**做：**
- `gstdev-cioaas-web` 里全部写接口（附录 A：143 个要声明，42 个豁免）。
- 新的"权限管理"页。
- 管理端页面上的按钮隐藏（附录 B：约 150 个入口，约 75 个页面文件）。
- 后端 403 和前端提示"无权限"。

**不做：**

| 不做的事 | 原因 |
|---|---|
| 读权限（GET 查询） | D1 只定了新增、修改、删除 |
| 公司端用户 | D2；公司端是另一套角色体系（Company Admin / Company User + 订阅菜单），放到第二期 |
| 数据归属 / 跨公司越权 | 多租户第 2 步；本方案不解决"能不能动这家公司" |
| Python 服务自己的接口（`/api/ai/*`，比如 RAG 知识库管理） | 第一期后端校验只在 Java；前端只隐藏、后端不拦不构成防护，所以 RAG 页的按钮也不隐藏 |
| 菜单可见性 | 继续用现有的角色-菜单配置，不变 |
| 已有的约 110 处 `roleType` 判断和约 49 处 `seeAllPortfolio` 判断 | 它们管的是"哪一端"和"能看哪些数据"，和本方案正交，保留 |

## 4. 权限模型

### 4.1 权限码

- 格式：`模块:动作`，比如 `company:create`、`user:delete`。
- 动作只有 `create`、`update`、`delete` 三种。
- **权限码由代码定义，不能在页面上增删。** 每个权限码都要和接口上的声明一一对应，开放页面增删只会出现"配了没人用"或"代码用了库里没有"。管理页只负责把已有的权限码分给角色。

### 4.2 模块清单（22 个模块，共 59 个权限码）

管理页按三组展示。每个模块只展示它实际用到的动作，详见附录 A §1。

| 分组 | 模块（code） | 用到的动作 |
|---|---|---|
| 公司数据 | 公司（company） | 新增、修改、删除 |
| | 投资（investment） | 新增、修改 |
| | 财务数据（companyFinancial） | 新增、修改、删除 |
| | 文档（companyDocument） | 新增、修改、删除 |
| | 产品 / 项目（project） | 新增、修改、删除 |
| | KPA 评审（kpa） | 新增、修改、删除 |
| | Exit Readiness（erl） | 新增、修改、删除 |
| 平台配置 | 技术栈配置（techStack） | 新增、修改、删除 |
| | KPA 配置（kpaConfig） | 修改 |
| | SDP 评分配置（scoreConfig） | 新增、修改、删除 |
| | 财务健康分配置（financeScore） | 新增、修改 |
| | 告警配置（alert） | 修改 |
| | ERL 配置（erlConfig） | 新增、修改、删除 |
| | 同行组（peerGroup） | 新增、修改、删除 |
| | Benchmark 录入（benchmarkEntry） | 新增、修改、删除 |
| | 指标（indicator） | 新增、修改、删除 |

| | 业务问题（businessIssue） | 新增、修改 |
| 组织与账号 | Portfolio 分组（portfolioGroup） | 新增、修改、删除 |
| | Portfolio（portfolio） | 新增、修改、删除 |
| | 用户（user） | 新增、修改、删除 |
| | 角色与权限（role） | 新增、修改、删除 |

### 4.3 角色、用户和权限的关系

- **用户 → 角色**：沿用现有的 `r_user_role`。本地库里 59 个管理端用户每人恰好 1 个角色；设计上支持多个角色，权限取并集。
- **角色 → 权限码**：新建关联表 `r_role_permission`（见 §8）。

**为什么不复用菜单表的功能点（`menu.type = 2`）：**
1. 菜单表是界面导航配置，本地库里混着大量测试行（`test1`、`123213213` 等），挂在菜单下的功能点不等于业务模块。
2. 现有角色管理页保存时会**整体覆盖**角色的菜单集合（`modifyOrganizationRoleMenu`）。权限混进去后，改一次菜单就可能把权限洗掉。
3. 菜单还受组织订阅过滤（`r_organization_menu`、`r_subscription_menu`），会让"角色有没有这个权限"的判断多出一层组织维度。

`role.permission` 和 `menu.permission` 两个旧字段本来就几乎全空，不再使用。

### 4.4 超级管理员

- 持有 `role.is_super_admin = true` 角色的用户，拥有全部权限，不受配置影响。
- ⚠️ 本地库里只有名为 "Super Admin" 的那 1 个角色打了这个标记；名叫 "super"（16 个管理端用户在用）、"super admin"、"LG admin" 的角色**都没有打标记**。所以它们会走正常的权限配置。上线时靠初始化授予全部权限（§11），所以行为不变。生产库上线前要先查一遍（§11 步骤 0）。

## 5. 服务端判定规则

### 5.1 接口怎么声明

- 每个写接口在 Controller 方法上声明"所属模块 + 接受哪些动作"，接受多个动作时命中任一即放行。
  - 新增和修改合一的接口、流程动作，声明为"新增或修改"（D3）。
  - 用 PUT 做的软删除声明为删除。
- 不需要检查的写接口，显式声明为"豁免"并写明原因（查询、个人自助、匿名、个人关闭提示、基础设施），见附录 A。
- 声明逐个接口落地。附录 A 是逐个核对过 service 代码的分类结果，开发时照着加。

### 5.2 一次请求怎么判定

请求命中带声明的接口时，按以下顺序判定，命中任意一步即结束：

1. 接口声明为豁免 → 放行。
2. 调用者不是管理端用户（`role_type ≠ 1`）→ 放行（D2，第一期不管公司端）。
3. 调用者持有超级管理员角色 → 放行。
4. 特例：`PUT /users/{userId}` 改的是调用者自己 → 放行。注册、选公司等流程里用户会改自己的记录。
5. 取出调用者的权限码集合（§6），和接口声明的动作有交集 → 放行。
6. 否则返回 **HTTP 403**，提示文字如 "You don't have permission to delete Companies."。

### 5.3 判定放在哪一层

放在 **web 服务内部的请求拦截层**，读取 Controller 方法上的声明。不放在网关，也不用 Spring 自带的 `@PreAuthorize`：

| 备选 | 不选的原因 |
|---|---|
| 网关 | 网关不依赖公共模块，拿不到用户和角色；路由只有两条通配，没有接口级信息 |
| 在 JWT 过滤器里加载权限，再用 `@PreAuthorize` | 过滤器在 `common` 模块，而角色和权限表在 `web` 模块，会让 `common` 反向依赖 `web`。另外 `@PreAuthorize` 拒绝时抛的 `AccessDeniedException` 会落进全局兜底处理，变成 **500**（`GlobalExceptionHandler.java:131`）。端类型、超管、改自己这几条规则写在 SpEL 里也难读、难测 |
| 复用 `@rc.check` | 每次调用都查库，而且依赖的角色缓存用邮箱做 key（§6 已知问题） |

### 5.4 403 返回

- 现在的业务异常（`BadRequestException` 等）统一返回 **HTTP 200** 加 `success=false`（`GlobalExceptionHandler.java:158-161`）。连 `DirectoryQueryUtils` 里传了 `FORBIDDEN` 的地方，实际返回的也是 200。
- 本方案新增一个专用的"无权限"异常，全局处理时返回 **HTTP 403** 加提示文字。前端据此区分"无权限"和"业务失败"。

### 5.5 守护测试

- 加一条单测：扫描所有接口，任何 POST / PUT / DELETE 方法，以及附录 A 里那 8 个会改数据的 GET，必须带权限声明或豁免声明，否则测试失败。
- 以后新加的写接口忘了声明，在构建期就会被拦下，不会悄悄漏到线上。

## 6. 权限缓存与生效时机

- 每个用户的权限码集合按 **userId** 缓存在 Redis，**只用 Redis、不用本地内存缓存**。
  - 现有的两级缓存（`TwoLevelCache`）没有跨实例清理本地缓存的机制。多实例部署时，其他实例最多会滞后 10 分钟，权限收回不及时。
  - 只有写接口才查一次 Redis，开销可以忽略。
- 以下情况清缓存：
  - 保存角色权限 → 清全部用户的权限缓存。管理端用户只有几十个，全清最简单可靠。
  - 改用户的角色（`/users/adminUser` 等）→ 清该用户。
  - 删除角色 → 清全部。
- **生效时机**：后端在下一次请求就生效，不需要重新登录。前端按钮在下一次进页面时刷新（§10.2）；刷新之前按钮仍显示，但点了会收到 403 提示。
- **已知问题，不在本方案内修**：现有角色缓存 `loadPermissionByUser` 用邮箱做 key（`RoleServiceImpl.java:433`），同一个邮箱属于多个组织或公司时会串缓存。本方案不用它。

## 7. 新增接口

| 接口 | 用途 | 权限 |
|---|---|---|
| `GET /permissions/modules` | 模块和动作的定义：名称、分组、可用动作，给矩阵页渲染 | 豁免（只读） |
| `GET /permissions/roles/{roleId}` | 某个角色当前拥有的权限码 | 豁免（只读） |
| `PUT /permissions/roles/{roleId}` | 整体替换某个角色的权限码 | `role:update` |
| `GET /permissions/current` | 当前用户的权限：是否超管、权限码列表 | 豁免（个人自助） |

- 路径只是示意，实施时按 `standards/coding.md` 的 REST 和传输实体约定定。
- 保存接口要校验：提交的权限码都在代码定义的清单里；目标角色不是超管角色。

## 8. 数据模型

新增一张表 `r_role_permission`：

| 字段 | 说明 |
|---|---|
| 主键 | 和现有关联表同风格 |
| `role_id` | 关联 `role.id` |
| `permission_code` | 比如 `company:delete` |
| 审计字段 | 沿用 `created_at` / `created_by` / `updated_at` / `updated_by` |

- 约束：`(role_id, permission_code)` 唯一，`role_id` 建索引。
- 删除角色时，同步删除它的权限行。
- 建表和初始化数据都写成 SQL 脚本，放进 `java/CIOaas-api/deploy/upgrade_doc/<sprint>/`，人工执行。不依赖 `ddl-auto: update` 自动建表，见 Java 待优化项里 ddl-auto 的已知问题。

## 9. 权限管理页

- **位置**：`/devSupport/permissionManagement`，和现有的角色管理页放在一起。
  - 入口有两个：右上角下拉菜单，和 Dev Support 左侧导航的「平台管理」组。
  - 页面访问沿用 `/devSupport` 整区的菜单门禁；保存需要 `role:update`。
- **布局**：
  - 左侧：组织选择器 + 角色列表。这部分复用角色管理页，先把这两块抽成 `devSupport` 内的共享组件；本页只读，不提供增删角色。
  - 右侧：权限矩阵。
    - 行 = 模块，按 §4.2 分三组；列 = 新增、修改、删除。模块没用到的动作显示为"—"。
    - 每行一个"整行全选"，表头一个"全部全选"。
    - 一个"保存"按钮。
- **交互细节**：
  - 切换角色时，如果有没保存的改动，弹框确认。
  - 选中超管角色时，矩阵全部勾选且不可改，提示"超级管理员拥有全部权限"。
  - 如果修改的是自己当前所用的角色，并且去掉了 `role:update`，保存前提示"保存后你将无法再修改权限"。
  - 保存成功后立刻刷新当前用户的前端权限（§10.2）。
- **不复用角色管理页右侧的菜单树**：菜单树是按菜单组织的，模块 × 动作用矩阵更直观；而且两者保存是分开的，互不覆盖（§4.3）。

## 10. 前端按钮隐藏

### 10.1 判定规则

| 条件 | 结果 |
|---|---|
| 当前不是管理端（`roleType ≠ 1`） | 一律显示，公司端维持原逻辑 |
| 当前是超管 | 一律显示 |
| 按钮动作是"新增或修改" | 有其中任一权限就显示 |
| 其他 | 有对应权限码才显示 |

**前端隐藏只是体验优化，不是安全边界。** 权限存在浏览器本地，用户自己能改，真正拦截靠后端 403。

### 10.2 权限的加载与刷新

- **登录后加载**：在 `src/models/login.ts` 的 `enterAccount` 里，管理端拉取 `GET /permissions/current` 并存到本地。切换账号也走这里，所以一并覆盖。
- **进页面时刷新**：`BasicLayout` 挂载时重新拉取，拉完广播一个事件，让各组件重新渲染。
- **退出时清理**：`clearUserInfo`、`logout`、改密码页三处退出路径都要清掉。
- **拉取失败**：保留上一次的结果；本地也没有时按"全部显示"处理，交给后端拦截。这样接口异常不会导致整页按钮消失。

### 10.3 统一组件与接入

- 提供一个权限判断 hook 和一个包裹式组件，统一使用。
- 按附录 B 逐个入口接入，约 150 个入口、约 75 个页面文件。
- 约 85 处在两端共用的组件里，必须遵守 §10.1 的第一条，不能影响公司端。

### 10.4 现有按功能名的判断

有 6 个页面现在用功能点的**显示名称**判断按钮（'Add Admin'、'Edit Admin'、'Add Company'、'add Indicator' 等）。

- 其中和本方案重叠的几处要改用新的权限码，避免两套口径：
  - 新增 / 编辑管理员 → `user:*`
  - 新增公司 → `company:create`
  - 新增 / 删除指标 → `indicator:*`
- 和增删改无关的开关类功能保留原样：'Search Switch'、'Roles Portfolio Switch'、'Set KPA' 等。

### 10.5 403 提示

`src/utils/request.ts` 现在把 401 以外所有 ≥400 的错误都显示成全局横幅"An unexpected error occurred... our technical team is already working on resolving it"。

要单独处理 403：弹出后端返回的提示文字，并且不触发全局横幅。

## 11. 上线与数据迁移

| 步骤 | 内容 | 说明 |
|---|---|---|
| 0 | 生产库核查 | 列出所有管理端用户及其角色、各角色是否标了超管；确认初始化脚本覆盖哪些角色 |
| 1 | 执行建表和初始化 SQL | **给所有现存的非公司类角色（`role_type` 为 organization、admin 或空）授予全部 59 个权限码**，保证上线当天行为不变 |
| 2 | 发布 Java | 拦截生效；因为步骤 1 已全量授权，没有人被拦 |
| 3 | 发布前端 | 管理页、按钮隐藏、403 提示上线；全量授权下没有按钮被隐藏 |
| 4 | 管理员在新页面上收权 | 业务方按需逐个角色调整 |

- **发布顺序必须 Java 先、前端后**：前端先上的话 `GET /permissions/current` 不存在。即使有 §10.2 的兜底，也会多出一批无意义的报错。
- **回滚**：
  - 收权导致误伤时，在页面上加回权限即可，或者用 SQL 给角色补回全部权限码。
  - 不加"总开关"配置项：步骤 1 的全量授权已经保证上线当天零影响，额外加开关属于预留。
- **新建角色的默认权限**：建议为空，由管理员在新页面上分配。这和现在"新角色什么都能写"不同，见 §13 待确认 Q1。

## 13. 风险与待确认

**待确认（不影响开工，上线前要定）：**

| # | 问题 | 建议 |
|---|---|---|
| Q1 | 新建角色默认有哪些权限 | 默认为空，由管理员分配（安全优先） |
| Q2 | 哪些角色能进权限管理页 | 沿用 `/devSupport` 整区门禁，保存再要求 `role:update` |
| Q3 | 投资（investment）是单独一个模块，还是并入公司 | 附录 A 按单独模块拆；并入只需改枚举和映射 |

**风险：**

1. **第一期不修 P0 问题 `POST /users`**：这个 P0 是"任何登录用户都能建管理员账号"。本方案只对管理端调用者生效；**公司端用户调 `POST /users` 仍然没人拦**。P0 照原计划另开一项修。
   - 可选的低成本加固：给纯管理端模块的接口（role、portfolioGroup、portfolio、user 的管理员部分等）加一条"公司端调用直接拒绝"。这算范围扩展，需要另外决定。
2. **数据归属仍然缺失**：有 `company:update` 的人可以改**任意**公司。这是多租户第 2 步的事；本方案不让它更好，也不让它更坏。
3. **会改数据的 GET 和名不副实的 POST**：附录 A 已经逐个标出。守护测试只能自动兜住 POST / PUT / DELETE，那 8 个会改数据的 GET 要靠清单人工确认。
4. **角色数据很脏**：本地库有大量重复或测试角色。初始化脚本按"全部非公司类角色"授权，不会漏人，但管理页的角色列表会比较乱。清理不在本方案范围。
5. **多租户改造之后**：第一期用 `role_type = 1` 判断"管理端"，这和多租户文档里要替换的"超管假设"是同一个判断依据。多租户改造替换这个依据时，本方案的判定条件要跟着换，但权限码和配置数据不受影响。
6. **越权问题，另行处理**：`PUT /users/profile`、`/users/checkPasswordByUserId`、`/users/changePasswordByUserId` 的目标用户 id 取自请求体、没有和调用者绑定（附录 A §4.5）。这和本方案无关，需要另外修。
7. **Python 侧没有影响**：Python 调 Java 的写方法只有两个 POST 查询（`/invite/aiDetail`、`/financialNormalized/chatSummary`），都已列为豁免。
