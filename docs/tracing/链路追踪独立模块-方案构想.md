# 链路追踪（Tracing）独立业务模块 — 方案构想

> 状态：方案构想（brainstorming 收敛稿，待 `/team-design` 细化为正式 dev-design）
> 范围：CIOaas-python `source/tracing/` + CIOaas-web `pages/ai/tracing/`
> 红线：**不复用、不修改 llm 的页面与存储**；与 llm 仅通过共享 `trace_id` 软关联

---

## 1. 背景与动机

当前链路能力寄居在 `llm` 模块：`/api/ai/llm-calls/*`（含 `/trace/{trace_id}` 时间线、`/stats` 仪表盘）+ 前端 `pages/ai/llm/`（TraceView/CallList/CallDetail）。它**只追踪 LLM 调用**，无法表达一条完整业务链路（一个任务里：SQS 入口 → graph 各节点 → 多次 LLM 调用 → rag 操作 → DB 写入）。

目标是建一个**项目级、自成体系**的链路追踪模块，追踪「整条业务链路」并可视化，而 **llm 现有的调用日志与页面保持原样、互不影响**。

## 2. 目标与非目标

**目标**
- 独立业务模块 `source/tracing/`（DDD 四层）+ 独立前端 `pages/ai/tracing/`
- 自建链路存储（trace + span 树）、采集 SDK、查询 API、可视化页面
- 端到端链路：一条 trace 串起跨模块的多个 span（graph node / LLM 调用 / rag 操作 …）
- 埋点对业务**低侵入**（`with start_span(...)`）、对延迟**零影响**（异步写）

**非目标（红线）**
- ❌ 不改 `ai_llm_call_log` 存储结构、不改 llm 任何代码
- ❌ 不复用/不改 `pages/ai/llm` 页面与组件
- ❌ 本期不做跨进程（Java↔Python）链路，仅 Python 进程内；但 SDK/表结构为其预留
- ❌ 不取代 llm 自己的调用日志（llm 照存不误）

## 3. 总体架构

```
                    ┌─────────────────────────────────────────┐
   业务模块          │  tracing 业务模块（自建，独立闭环）        │
  (ai/rag/...)  ───► │  采集 SDK → application/service → 存储     │
   start_span()     │  ai_trace / ai_trace_span                 │
                    │  interfaces → 前端 pages/ai/tracing       │
                    └─────────────────────────────────────────┘
                              ▲ 共享 trace_id（非侵入软关联）
                              │
   ┌──────────────────────────┴───────────────────────────┐
   │  llm 模块（完全不动）：ai_llm_call_log + pages/ai/llm   │
   └────────────────────────────────────────────────────────┘
```

- 依赖方向：业务模块 → `tracing.application`（§2.1 跨模块走对方 application/service）
- tracing **不依赖 llm**；llm **不依赖 tracing**。两者解耦，仅约定同一条业务链路使用同一个 `trace_id` 值。

## 5. 数据模型（自建表）

### `ai_trace`（一条链路）
| 列 | 说明 |
|---|---|
| `id` (PK, varchar36) | trace_id（业务侧生成，跨节点串联；预留外部注入） |
| `name` | 链路名 / 业务类型（如 financial_extract） |
| `source` | 入口来源（sqs / http / cron / mcp …） |
| `status` | RUNNING / SUCCESS / FAILED / PARTIAL |
| `company_id` / `user_id` / `task_id` | 多租户 + 业务软关联（可空） |
| `started_at` / `finished_at` / `duration_ms` | 起止 + 总耗时 |
| `attributes` (JSONB) | 开放扩展（入口参数摘要等） |
| `created_at` | |

### `ai_trace_span`（链路上的节点，父子树）
| 列 | 说明 |
|---|---|
| `id` (PK, varchar36) | span_id |
| `trace_id` (FK→ai_trace) | 所属链路 |
| `parent_span_id` | 父 span（构成调用树；根 span 为空） |
| `name` | span 名（identify_fs / extract_cells / rag_ingest …） |
| `span_type` | 节点类型：graph_node / llm_call / rag_op / db / external |
| `status` | RUNNING / SUCCESS / FAILED |
| `started_at` / `finished_at` / `duration_ms` | 时序 + 耗时（瀑布图用） |
| `attributes` (JSONB) | 节点上下文（如 llm_call 存 provider/model/tokens/cost 摘要、关联的 llm call_log_id） |
| `error` (text) | 失败原因 |
| `created_at` | |

> 索引：`ai_trace(company_id, started_at DESC)`、`ai_trace(status, started_at)`、`ai_trace_span(trace_id, started_at)`、`ai_trace_span(span_type)`。
> 与 llm 的关联：`llm_call` 类型的 span 在 `attributes.call_log_id` 存 llm call_log 主键 → 前端可跳 llm 页面查看 prompt 详情（非侵入，靠值约定）。

## 6. 采集 SDK（`infrastructure/trace_context.py`）

```python
# 链路入口（consumer / graph 入口）
with start_trace(name="financial_extract", source="sqs", task_id=tid, company_id=cid) as trace_id:
    # 链路内逐节点埋点（自动继承 trace_id + 父 span，构成树）
    with start_span("identify_fs", span_type="graph_node"):
        with start_span("llm_identify", span_type="llm_call",
                        attributes={"provider": ..., "model": ...}):
            router.complete(...)        # llm 完全无感
```

- 基于 tracing **自己的 ContextVar**（`_current_trace_id` / `_current_span_id`），与 llm 的 ContextVar 互不干扰
- `with` 退出自动补 `finished_at` / `duration_ms` / `status`；异常分支记 FAILED + error
- **异步写**：`start_*` 进出仅排队，落库走 `async_writer` fire-and-forget；DB 失败仅日志，绝不阻塞/打断业务
- **跨线程**：`ai/nodes` 的 `ThreadPoolExecutor` 路径需 `copy_context().run(...)` 透传（SDK 提供 helper + 文档说明）
- 依赖倒置：`async_writer`（infra）只调度无参回调，落库编排由 `trace_record_service`（application）注入——保持 infra 不反依赖 application

## 7. 查询 API（`interfaces/routes.py`，前缀 `/api/ai/traces`）

- `GET /api/ai/traces` — 链路列表：筛选 时间 / source / status / company_id / task_id / name + 分页
- `GET /api/ai/traces/{trace_id}` — 链路详情：返回 trace 元数据 + span 树（含层级、时序、耗时、状态、error）
- （预留）`POST /api/ai/traces/spans` — HTTP 上报入口（跨进程时启用，本期不实现逻辑）
- 鉴权：复刻 llm tracking 的开关式 Bearer Token（`TRACING_API_TOKEN` 未配则放行，dev 友好）
- 多租户：列表/详情强制 `company_id` 过滤

## 8. 前端（`pages/ai/tracing/`，独立新建，不碰 llm 页面）

- **TraceList**：链路列表表格（时间 / 名称 / 来源 / 状态 / 耗时 / task），多维筛选 + 分页
- **TraceDetail**：**瀑布 / 时间线**视图展示 span 树——层级缩进 + 耗时条 + 状态色 + 错误下钻；点击 `llm_call` span 可（按 `attributes.call_log_id`）跳转到现有 llm CallDetail（软链接，非耦合）
- 独立 service / api 层（`services/api/tracing/`），不引用 `pages/ai/llm` 任何组件

## 9. 与 llm 的关系（零改动确认）

- llm 的存储、页面、代码**全部不动**
- 覆盖 LLM 调用：由**业务侧**在调 llm 处用 `start_span(span_type="llm_call")` 包裹，llm 无感
- trace_id 一致性：业务侧在链路入口生成 trace_id，**同一个值**既传给 tracing 的 `start_trace`，也（沿用 llm 现有的 `trace_id_scope`）传给 llm —— 这是业务侧的协调，**不改 llm 代码**
- 前端互跳靠 trace_id / call_log_id 值约定，双向非侵入

## 10. 非功能

- **性能**：埋点零阻塞（异步写 + 上限保护 + lifespan flush）；span 写入批量化可后续优化
- **数据保留**：span 量大 → 30 天 cron 清理（与 rag 软删清理风格一致），可配置
- **多租户**：所有查询强制 company_id 过滤
- **安全**：attributes 不存敏感全文（prompt 全文留 llm 侧，tracing 只存摘要 + call_log_id 引用）
- **ruff TID251**：tracing 模块零 LLM SDK 依赖

## 11. 分期计划

- **Batch 1（最小闭环）**：建模块骨架 + 两表 + 采集 SDK + 查询 API + 前端 TraceList/TraceDetail；在 `financial_extract` 一条 graph 链路上完整埋点（入口 trace + node span + llm_call span）→ 交付一条真实可视化端到端链路
- **Batch 2**：rag 操作（入库/检索/迁移）接入采集；财务 / consumer 入口接入
- **Batch 3（预留）**：HTTP 上报 + 跨进程 trace_id 透传（Java 网关）

## 12. 风险与对策

| 风险 | 对策 |
|---|---|
| 埋点侵入业务、易漏 | SDK 极简（`with start_span`）；优先装饰器/上下文管理器封装；node 级统一切面 |
| ThreadPoolExecutor ContextVar 丢失 | SDK 提供 `copy_context` 透传 helper + 强制文档 |
| span 写入拖累延迟 | 全异步 fire-and-forget；DB 失败仅日志 |
| 与 llm trace_id 不一致导致关联断裂 | 业务入口单一来源生成 trace_id，同值喂两边；前端容错（无关联时仅不展示跳转） |
| span 数据膨胀 | 30 天保留清理 + 索引 + attributes 只存摘要 |
