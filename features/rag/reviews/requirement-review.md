## 功能理解

RAG 管理模块让公司用户把内部文档（文件或文本）"装入"若干主题空间（Space），系统自动切片并向量化，使资料可被语义检索。空间分"公司级"和"个人"两种所有权，公司管理员对本公司所有空间（含员工个人空间）有完整管理权。模块的最终目的是为尚未上线的 Chatbot 提供 RAG 检索基础——Chatbot 接入时可指定一个或多个空间作为回答依据。本期不做 Chatbot UI，仅交付RAG 管理和检索能力。

## 🔴 阻断性问题（共 4 个，必须修复才能进入设计）

### §4.1 F1 空间管理（1 个）

**1. 模型迁移期间新上传文件的处理语义完全缺失**

- 位置：§4.1.4 规则 3、§3.2 场景 S7
- 原文：「迁移过程中检索仍可正常返回结果（使用旧向量），迁移完成后自动切换到新向量」
- 问题：文档明确了迁移期间"检索用旧向量"，但对"迁移进行中时用户新上传的文件"完全没有规则。新上传文件应用哪个模型向量化？立即用新模型（可能导致迁移期内出现两套向量，检索行为不一致）？还是等迁移完成再入队？还是用旧模型向量化待迁移任务结束后再重算？这三种语义对后端实现差异巨大，且影响 F2 文件入库的完整流程。pm-writer 自审已将此列为重点验证项，但文档中确实缺失。
- 建议：在 §4.1.4 规则 3 增加一条明确规则，例如："迁移期间的新入库操作**排队等待**，待全量重向量化任务完成后再使用新模型处理；或，新上传文件使用新模型立即处理，并在迁移完成后合并进新向量索引。"选择哪种方案需业务明确，两种方案各有权衡（排队方案用户有等待感；立即用新模型方案实现更复杂但体验好）。建议同时在 §3.2 场景 S7 补充一个"迁移中有新文件上传"的 Then 描述。

---

### §4.2 F2 文件入库（1 个）

**2. 重试策略"从头重做"未覆盖"部分成功"状态**

- 位置：§4.7.2 失败重试（与 §4.2.4、§4.2.5 规则 6 共同构成矛盾）
- 原文：「入库失败的条目可由用户点击"重试"按钮重新处理」；「重试方式：从头重做——删除该文件已生成的全部中间结果（含部分片段、部分向量），重新执行整套入库流程」
- 问题："重试"入口的触发条件仅写了"失败的条目"（§4.7.2 第一行和 §4.2.5 规则 6），但 §4.2.4 出参中明确存在"部分成功（PARTIAL）"状态，且 §4.2.5 规则 5 描述 OCR 失败后状态为"部分成功"。"部分成功"的条目是否可以点击重试？若可以，"从头重做"的语义与"部分成功"中"文件名已可检索"的状态是否一致（重做会清除文件名检索能力吗？）？若不可以，用户如何在 OCR 失败后再次尝试让图片入库正文？这是一个三处规则相互牵扯但没有统一处理的逻辑断点。
- 建议：明确"部分成功"条目是否允许重试，以及重试后"已保留的文件名检索能力"是清除重建还是保留。建议补充规则："状态为'部分成功'的条目同样支持点击'重试'，重试行为与'失败'条目一致（从头重做）"，并说明重试期间该条目的旧检索能力保持不变直到新入库成功。

### §4.6 F6 统计（1 个）

**3. "部分成功"条目的统计处理逻辑完全缺失**

- 位置：§4.6.2、§4.6.3、§4.6.4
- 原文：§4.2.4「处理成功后能查看该文件被切成的片段列表与片段内容」；§4.2.5 规则 5「OCR 失败时正文片段数为 0、不参与语义检索；文件名与元数据仍可被检索」；§4.6.4 规则 1「top_k 范围内所有命中片段都累加 1 次」
- 问题："部分成功"条目的文件名可被关键词检索命中，但正文片段数为 0。当这样一个条目被关键词检索命中时：(1) 它会出现在检索结果中吗？(2) 如果出现，命中次数是否 +1？(3) 在统计页的"被命中最多的片段排行"中如何展示（片段为空）？(4) 在条目维度统计中"该条目被命中次数"是否被累计？这四个问题均无答案，开发无法实现统计逻辑。
- 建议：在 §4.6.4 或 §4.2.5 规则 5 中补充"部分成功"条目的统计处理规则。例如："'部分成功'条目被关键词检索命中时，命中次数累计规则与正常条目一致；在统计页片段排行中不展示（片段数为 0），但在条目维度命中次数中体现。"

### §2 业务背景与目标（1 个）

**4. P95 < 3 秒检索指标与 OCR 场景的适用边界不明确，且和 §6.2 存在微妙出入**

- 位置：§2.3 衡量指标、§6.2 性能
- 原文：§2.3「检索响应速度（P95）：用户在"检索测试"输入框按下回车后，3 秒内返回结果 | 单空间检索」；§6.2「检索响应（P95，单空间，top_k ≤ 10）< 3 秒」
- 问题（1）：§2.3 注解给"入库可见性"加了 OCR 例外，但"检索响应 P95 < 3 秒"未注明该指标**是否也适用于包含大量 OCR 内容的空间**。向量检索性能与索引规模、模型维度强相关，在包含大量高维 OCR 提取片段的空间中，P95 < 3 秒是否仍然可承诺？该指标对开发来说是验收硬性标准（G1=A），但适用范围不清晰。
- 问题（2）：§2.3 只写"单空间检索"，但 §4.5.1 和 §3.2 场景 S5 都明确支持跨空间混合检索——跨空间场景的检索响应目标完全缺失。
- 建议：在 §2.3 和 §6.2 的 P95 指标后补注"（不含首次冷启动；仅适用于已完全建好索引的空间；跨空间检索暂不设 SLA）"，或显式说明"跨空间检索时 P95 目标按空间数线性放宽"，避免测试阶段对跨空间场景直接套用 < 3 秒标准产生争议。

## 🟡 重要问题（共 8 个，建议修复后再进入设计）

### §2 业务背景与目标（1 个）

**5. "入库可见性 < 10 秒"的图片 OCR 注解范围只适用于"可见"，但任务状态变更后无上限保证易造成用户困惑**

- 位置：§2.3、§6.2
- 原文：「图片 / 扫描件类型由于走 OCR，10 秒内可见任务但不保证 10 秒内完成处理」；§6.2「文件处理时长：不做硬性上限，但应在条目列表中持续可见进度，避免'卡住但无反馈'」
- 问题：文档对 OCR 类文件的处理时长"不做硬性上限"，仅要求"进度持续可见"。这对开发来说是合理的，但缺少一个**超时保护机制**的描述：如果 OCR 服务挂了或文件极其复杂，任务会无限制"处理中"吗？最终会变成"失败"吗？失败触发机制是什么？没有超时失败机制，用户就无法知道什么时候该点"重试"。
- 建议：在 §6.3 可靠性或 §4.7.2 中补充："入库任务处理时长超过 [N] 分钟（平台级配置，不向用户暴露具体数值）后，若仍未完成，自动置为'失败'并展示'处理超时，请重试'"。

### §3 用户画像与典型场景（1 个）

**6. 场景 S3 中"管理员可见"的告知时机不完整**

- 位置：§3.2 场景 S3
- 原文：「系统在创建表单中明确告知"本公司管理员可查看本空间内容与统计"」
- 问题：场景 S3 只描述了"创建时告知"，但 §5.2 规则 3 要求**上传文件和录入文本时**也必须在上传对话框显示该文案。场景中缺少对"已有个人空间后向其中上传内容时"这一关键告知时机的描述，导致场景与规则不对齐。即便规则写了，场景的不完整会让开发在实现时遗漏上传对话框的告知逻辑。
- 建议：在场景 S3 或 S4 中补充一个 Then 步骤："小李向个人空间点击'上传文件'时，上传对话框内同样可见上述告知文案"；或新增场景 S3b 专门描述上传时的告知行为。

### §4.1 F1 空间管理（1 个）

**7. §4.1.4 规则 3"全量重向量化"的进度展示与失败处理规则缺失**

- 位置：§4.1.4 规则 3
- 原文：「迁移完成后自动切换到新向量，旧向量被清理」
- 问题：§3.2 场景 S7 描述了"进度条"，但 §4.1.4 规则 3 中未说明迁移任务的**失败处理**：(1) 迁移中途失败（如部分文件重向量化失败），空间状态变成什么？(2) 迁移失败后是否回滚到旧模型、旧向量？(3) 用户是否可以主动取消迁移？这些是开发实现模型迁移任务时必须知道的边界，缺失会导致实现时自行决策。
- 建议：在 §4.1.4 规则 3 末尾补充迁移失败的处理规则，例如："若迁移中途部分文件失败，空间状态变为'迁移失败'，保留旧向量仍可检索，用户可选择'重新迁移'；本期不支持用户主动取消迁移。"

### §4.2 F2 文件入库（2 个）

**8. 同名覆盖操作在"迁移中"状态下的行为未定义**

- 位置：§4.2.5 规则 4、§4.1.4 规则 3
- 原文：「覆盖即先删除旧条目（其片段、被命中统计一并清零），再以本次上传内容重建」
- 问题：如果空间正处于"迁移中"状态，用户此时进行同名覆盖操作——新内容应使用哪个模型入库？旧条目的旧向量已在迁移任务中，删除旧条目是否会对迁移任务造成影响？这个边界场景在两处规则之间均无描述。
- 建议：在 §4.2.5 规则 4 增加注记："若目标空间处于'迁移中'状态，覆盖上传行为[排队/立即用新模型/暂时禁止]，与 §4.1.4 规则 3 迁移期间新上传语义保持一致"（与阻断问题 1 的答案联动，需一并明确）。

**9. 批量上传中"部分覆盖"的整体任务状态缺失**

- 位置：§4.2.2 步骤 3、§4.2.4 业务出参
- 原文：「10 个文件中，5 个需要覆盖确认，3 个无冲突，2 个用户跳过」（假设场景）；「入库任务编号（用于查询整体进度）」
- 问题：批量上传时用户可以对每个同名文件逐一选择"覆盖"或"跳过"，但文档描述的是"弹出提示"，未说明：(1) 是一次性弹出所有同名冲突、还是逐个弹出？(2) 如果用户在浏览器中关闭了弹窗，后续同名文件如何处理？这个交互流程对前端实现影响较大，但文档中仅有一句话描述。
- 建议：在 §4.2.2 步骤 3 补充同名冲突的批量处理方式："同批次中存在多个同名文件时，一次性列出所有冲突文件供用户统一选择覆盖/跳过；用户未作选择时默认跳过。"

### §4.4 F4 拆分（1 个）

**10. 默认拆分规则的具体值范围未给出，"开箱即用"无法验收**

- 位置：§4.4.3、§4.4.4
- 原文：「默认值范围：由平台为不同文件类型提供合理默认」；「默认规则对非技术用户应'开箱即用'」
- 问题：文档仅说"由平台提供合理默认"但完全没有给出范围区间，连"典型的 chunk_size 在 500-1500 字符之间"这类描述都没有。这导致两个问题：(1) "开箱即用"是一个无法被测试的描述——验收标准 §4.4.7 没有任何与默认值相关的 checkbox；(2) 开发不知道平台该在什么范围内提供默认值，可能随意填入不合理的数值。
- 建议：补充"平台为不同文件类型提供的 chunk_size / chunk_overlap 默认值参考区间"（如"文档类 chunk_size 默认 800 字符，chunk_overlap 默认 100 字符"），并在验收标准 §4.4.7 增加一条"用户不修改默认值时，一个 1000 字的文档能被切成至少 1 个、不超过 [N] 个片段"。

### §4.5 F5 检索（1 个）

**11. "部分成功"条目在检索结果中的呈现规则缺失**

- 位置：§4.5.3 业务出参、§4.2.5 规则 5
- 原文：§4.5.3「每条命中结果包含：命中片段的文本内容、该片段所属的条目名称、所属空间名称、命中相似度、命中类型标识」；§4.2.5 规则 5「文件名与元数据仍可被检索（命中关键词），但正文片段数为 0、不参与语义检索」
- 问题：§4.5.3 给出了命中结果的结构，但这个结构假设了每条结果都有"片段文本内容"。当"部分成功"条目通过文件名被关键词检索命中时，返回结果中的"命中片段的文本内容"是什么？是空字符串？还是文件名本身？还是不参与 top_k 排名但以特殊格式展示？这是检索结果展示的核心问题，前端和后端必须对齐。
- 建议：在 §4.5.3 或 §4.2.5 规则 5 末尾补充："'部分成功'条目的文件名检索命中在结果中以特殊格式呈现，片段内容字段显示'[仅文件名可检索，正文未入库]'，并标注命中类型为'关键词命中'；不计入语义召回的 top_k 排名"（或选择其他合理方案）。

### §5 权限模型（1 个）

**12. 隐私告知"不可关闭"的技术实现层面未定义，仅靠文案是否足够**

- 位置：§5.2 规则 3、§3.2 场景 S3
- 原文：「该告知不可被关闭、不可隐藏」；「所有者类型为'个人'时的强提示：表单内显著位置展示文案」
- 问题：文档要求告知"不可被关闭、不可隐藏"，但仅靠表单内静态文案是否足够满足"知情同意"要求，取决于业务场景的合规标准。问题在于：(1) 用户是否需要**主动勾选**"我已知晓管理员可见"才能创建个人空间？(2) 还是仅被动看到文案即可（不需勾选）？两种方案对业务意义不同——前者有明确的"同意"证据，后者仅有"告知"但无"确认"。文档描述为"告知"，这足以满足本产品的合规场景吗？
- 建议：明确告知的交互形式：是"强展示无需勾选"还是"必须勾选确认才可提交"。如果是前者，建议在文档中说明"本产品定性为内部管理工具，仅告知无需明确勾选"，以便后续被问责时有依据。

## 🔵 改进建议（共 6 个，可在开发过程中完善）

### §3 用户画像与典型场景（1 个）

**13. 场景 S5 中 Chatbot 代用户检索的权限裁剪逻辑描述过于简短**

- 位置：§3.2 场景 S5
- 原文：「Chatbot 在"产品手册 + 小李的个人空间"两个空间范围内执行一次混合检索」
- 问题：此场景作为"系统调用方 — Chatbot 检索"的典型场景，缺少对"Chatbot 请求被拒绝"的 unhappy path 描述（如 Chatbot 传入了小李无权访问的空间 ID 时发生什么）。虽然规则在 §4.5.4 和 §5.2 有描述，但典型场景不呈现拒绝场景，开发和 QA 容易忽略。
- 建议：在 S5 末尾或新增 S5b，补充"Chatbot 传入小李不可见的空间 ID 时，该空间被过滤，只返回小李有权访问的空间内的结果（或整体请求被拒绝）"。

### §4.1 F1 空间管理（1 个）

**14. 验收标准 §4.1.5 中"迁移期间检索仍能返回结果"无法量化，难以 QA**

- 位置：§4.1.5 验收标准最后一条
- 原文：「迁移期间执行检索仍能返回结果」
- 问题：此验收条目描述的是"能返回"，但没有说明返回的是旧向量结果还是空结果。如果迁移实现有 bug 导致返回新向量的部分结果，这条验收也会"通过"（因为确实"返回了结果"）。
- 建议：改为「迁移期间执行检索，返回结果基于**迁移前**的向量（不出现无结果或结果乱序的情况）」。

### §4.2 F2 文件入库（1 个）

**15. §4.2.5 规则 5 措辞"实现说明"踩了业务/技术边界**

- 位置：§4.2.5 规则 5
- 原文：「实现说明：图片 OCR 由平台内部能力提供，具体技术选型与服务调度由 Arch Team 决定，不在本需求范围」
- 问题：这句话本身在业务边界内是合理的（告知 QA 和开发不要在此处追问 OCR 怎么实现），但"服务调度"是纯技术术语，不应出现在业务需求文档中。pm-writer 自审已标注 §4.2.5 需审查，此处正是边界泄漏点。该措辞虽不构成阻断，但设计文档中见到"服务调度"会混淆层次。
- 建议：将「具体技术选型与服务调度由 Arch Team 决定，不在本需求范围」改为「具体 OCR 服务的选型由技术团队决定，不在本需求范围」，去掉"服务调度"一词。

### §4.5 F5 检索（1 个）

**16. 验收标准 §4.5.5 缺少"部分成功"条目被检索命中的专项测试**

- 位置：§4.5.5 验收标准
- 问题：所有验收标准均假设正常入库成功场景，未包含"用户上传一张图片 OCR 失败（部分成功），再执行关键词检索，该图片文件名在结果中出现"的测试场景。
- 建议：在 §4.5.5 增加：「用户对一个状态为"部分成功"的条目所在空间执行关键词检索，检索结果中能找到该条目的文件名，且命中类型标注为"关键词命中"」。

### §4.7 F7 维护（1 个）

**17. §4.7.2 重试描述未明确"部分向量"清理的边界**

- 位置：§4.7.2 失败重试
- 原文：「删除该文件已生成的全部中间结果（含部分片段、部分向量），重新执行整套入库流程」
- 问题：「含部分片段、部分向量」的括号说明准确，但未说明**"已生成的部分文件名/元数据是否也被清理"**。对"部分成功"的条目而言，文件名和元数据是当前可检索的唯一数据，重试时是否先清除这些元数据再重建？还是保留到新入库完成再替换？
- 建议：补充："重试期间，原条目的文件名检索能力保持不变（不预先清除），待新入库成功后替换；若新入库也失败，原状态恢复为'失败'。"

### §9 术语表（1 个）

**18. "条目"的术语定义与正文部分使用不完全一致**

- 位置：§9 术语表
- 原文：术语表「条目（Entry）：一个被装入空间的'知识单元'。可以是一个文件，也可以是一段直接录入的文本」
- 问题：正文中 §4.2.2 步骤 3、§4.6.3 等处出现「文件/文本」或「文件条目」「文本条目」，与术语表统一用「条目」的意图一致。但 §4.5.3 中出现「该片段所属的条目名称」，而 §4.2.2 中出现「文件名」——两处对同一概念的称谓不一致（"条目名称"和"文件名"可能指同一字段，也可能不同，文本直传时尤其不清晰）。
- 建议：在术语表补充说明："文本条目以用户填写的'标题'作为条目名称展示；文件条目以文件名作为条目名称展示"，并在 §4.5.3 将「条目名称」统一为有此定义支撑的术语。
