## 2. 业务背景与目标

### 2.1 现状痛点

- LG（CIOaaS）平台当前已具备 AI 财务抽取能力，但**没有面向公司内部资料的通用知识沉淀手段**。
- 公司内部的政策文档、产品手册、销售话术、客户案例等只能散落在各处文档系统里，无法被平台统一管理，也无法被未来的 Chatbot / Agent 调用。
- 用户在与 AI 对话时，只能反复把同一段文字粘贴到对话框里作为背景，效率低、易出错、无法沉淀。
- 平台未来要上线的 Chatbot 缺乏"公司专属知识"作为回答依据，回答内容只能停留在通用模型层面，业务价值受限。

### 2.2 业务目标

1. 提供一个完整的**RAG 管理**模块，让公司能把内部资料沉淀为可被 AI 检索的"空间"。
2. 让普通用户能在自己可见的范围内，把文件或文本"装入"空间，并能在装入后立刻验证是否能被正确检索。
3. 为后续 Chatbot 上线提供稳定的检索能力（RAG，即检索增强生成）——Chatbot 接入时可指定一个或多个空间作为回答依据。
4. 让管理员能直观看到每个空间被使用的程度（被检索次数、热门 query），辅助判断资料是否值得继续维护。

### 2.3 衡量指标（用户可感知）

| 指标 | 目标值 | 说明 |
|---|---|---|
| 可承载场景 | 支撑后续 Chatbot 上线 | RAG + 检索能力具备后，Chatbot 项目可在不再依赖外部RAG系统的前提下立项 |
| 检索响应速度（P95，单空间） | 用户在"检索测试"输入框按下回车后，**3 秒内**返回结果 | 适用条件：（1）单一空间；（2）该空间已完成全量索引建立（不含冷启动）；（3）top_k ≤ 10。完整 SLA 分级见 §6.2 |
| 检索响应速度（P95，跨空间 2-5 个） | **5 秒内**返回合并结果 | 跨空间联合检索的 SLA 分级见 §6.2 |
| 检索响应速度（跨空间 6 个及以上） | **不设 SLA**，best-effort | 用户在前端可见进度提示；不作为硬性验收标准 |
| 入库可视性 | 用户上传文件后，**10 秒内**能在列表中看到该文件的处理状态（处理中/成功/部分成功/失败） | 不要求 10 秒内处理完成，要求 10 秒内可见任务。**注解**：纯文本 / Office 类型 10 秒内可见；**图片 / 扫描件类型由于走 OCR，10 秒内可见任务但不保证 10 秒内完成处理**；上述 SLA 不适用于"包含大量 OCR 待处理片段"导致的整体处理时长，OCR 处理时长由 §6.2 单独描述 |
| 资料沉淀效率 | 一名普通用户在 5 分钟内能完成「建空间 → 上传 3 个文件 → 跑通一次检索测试」 | 衡量上手成本（不含图片 OCR 类型） |

## 3. 用户画像与典型场景

### 3.1 角色清单

| 角色 | 简述 |
|---|---|
| 公司管理员 | 公司层级的RAG维护者，负责创建和维护公司级空间、管理本公司全部空间下的条目与统计；**对本公司内员工的个人空间亦具备完整查看与操作权限（详见 §5）** |
| 普通用户 | 公司内部员工，可使用本公司所有公司级空间，也可创建自己的个人空间用于私人资料沉淀；**需理解：本公司管理员可查看其个人空间内容与统计** |
| 系统调用方（Chatbot / Agent） | 未来上线的对话式 AI，以"代用户"身份在指定空间范围内执行检索；本期不做 UI，但需求文档中预留其调用边界 |

### 3.2 典型场景（Given-When-Then）

**场景 S1（公司管理员 — 建库与上传）**

- Given：管理员小赵刚加入公司，他希望把公司产品手册沉淀进 AI 平台
- When：他在RAG 管理页点击"新建空间"，命名为"产品手册"，选择 embedding 模型，并依次上传 5 份 PDF
- Then：5 个条目都出现在该空间的条目列表里，状态从"处理中"陆续变为"已就绪"；点开任意一个条目能看到它被切成的若干片段；他在"检索测试"输入框输入"退货流程"能看到相关片段命中

**场景 S2（公司管理员 — 监控使用情况）**

- Given：上线 2 周后，管理员小赵想了解哪些资料对 Chatbot 真正有用
- When：他打开"产品手册"空间的统计页
- Then：他能看到该空间被检索的总次数、最近的热门 query 列表，以及"被命中次数最多的片段"；点击某个条目能看到该条目被命中的次数和被命中最多的片段

**场景 S3（普通用户 — 个人空间创建告知）**

- Given：普通员工小李想把自己整理的客户调研笔记沉淀下来，且只想供自己使用
- When：他在RAG 管理页点击"新建空间"，所有者类型选"个人"。系统在创建表单中明确告知"本公司管理员可查看本空间内容与统计"
- Then：该空间对其他**普通用户**不可见，也无法搜索；但**本公司管理员**可见、可查看与可操作（小李在创建时已被透明告知此规则）

**场景 S3b（普通用户 — 个人空间上传告知）**

- Given：小李已创建了个人空间"客户调研笔记"，准备向其中上传文件或录入文本
- When：他在该个人空间内点击"上传文件"或"录入文本"
- Then：上传 / 录入对话框内同样可见固定告知文案"本公司管理员可查看本空间内容与统计"；该告知在每一次上传 / 录入入口均可见，不可关闭、不可隐藏

**场景 S4（普通用户 — 文本直传）**

- Given：小李刚收到客户的口头反馈，没有现成文件，想把这段话沉淀进个人空间
- When：他打开个人空间，点击"录入文本"，填入标题"客户A口头反馈 0526"和正文
- Then：该文本作为一个"条目"出现在条目列表里，类型标识为"文本"，并和上传的文件条目享有同等待遇（被切片、可检索、可统计）

**场景 S5（系统调用方 — Chatbot 检索）**

- Given：未来上线的 Chatbot 接入用户小李身份，准备回答"我们的退货流程是什么"
- When：Chatbot 在"产品手册 + 小李的个人空间"两个空间范围内执行一次混合检索
- Then：返回若干命中片段及来源条目信息；同时这次检索在统计页中体现为一次新的命中

**场景 S5b（系统调用方 — 越权请求被裁剪）**

- Given：Chatbot 接入用户小李身份，但请求体中传入了小李无权访问的空间 ID（例如其他员工小王的个人空间）
- When：Chatbot 发起检索请求
- Then：系统按小李的可见范围对空间列表做权限裁剪——小王的个人空间被剔除，仅在小李有权访问的空间范围内执行检索并返回结果；若裁剪后空间列表为空，则整体请求被拒（鉴权失败）

**场景 S6（普通用户 — 入库失败排查）**

- Given：小李上传的一份 PDF 显示"处理失败"
- When：他点开失败的条目
- Then：能看到失败原因（如"文件损坏"或"不支持的格式"），并能选择"重试"或"删除"

**场景 S7（公司管理员 — 切换 embedding 模型）**

- Given：管理员小赵希望把某个空间的 embedding 模型升级到效果更好的新版本
- When：他在空间编辑页选择新模型并确认
- Then：系统提示"切换后将对该空间已有数据全量重新向量化，期间空间将显示'迁移中 N%'"；确认后空间页顶部出现"迁移中"横幅与进度条，迁移过程中检索仍可正常返回结果（使用旧向量），迁移完成后自动切换到新向量
- **And（迁移期间新上传不阻塞）**：迁移进行过程中，小赵或本空间其他用户**仍可正常上传新文件 / 录入新文本**；新上传的条目**立即使用新模型**完成切片与向量化（其向量直接归属于"新版本向量索引"），不需要等迁移结束，也无需在迁移完成后被重算

## 4. 功能范围

### F1. RAG空间管理

#### 4.1.1 功能描述
用户能创建、查看、编辑、删除"空间"。一个空间是一组同主题资料的容器（例如"产品手册""销售话术""我的调研笔记"），用户在空间内做上传、检索、统计等所有操作。

#### 4.1.2 业务入参（用户视角）

创建空间时填写：

| 字段 | 说明 | 是否必填 |
|---|---|---|
| 空间名称 | 显示用名称 | 必填 |
| 空间描述 | 用途说明 | 选填 |
| 所有者类型 | "公司级"或"个人" | 必填 |
| 默认拆分规则 | 条目入库时默认按此规则切分（**片段大小、片段之间的重叠量**两项，详见 F4）；用户可在创建时改默认值，也可在每次入库时临时覆盖 | 选填，未填则使用系统提供的默认值 |
| Embedding 模型 | 用于把文本转成向量的模型，决定该空间的检索效果与成本 | 必填，从平台提供的候选列表中选 |

**所有者类型为"个人"时的强提示**：表单内显著位置展示固定文案"本空间属于个人空间。请注意：本公司管理员可查看本空间内容与统计"。该告知为**强展示，无需用户主动勾选确认**——本产品定性为公司内部管理工具，"告知"即满足合规所需，无需"勾选同意"。

#### 4.1.3 业务出参（用户视角）

- 列表页：显示当前用户**可见的**所有空间，每行展示名称、所有者类型、条目数、最近一次更新时间、被检索次数；若空间正处于"迁移中"状态，显示对应标识及百分比进度
- 详情页：上述信息 + 空间描述、默认拆分规则、所使用的 embedding 模型

#### 4.1.4 业务规则

1. **空间名称**在同一所有者范围内不允许重复（公司级空间内不能两个同名；同一用户的个人空间不能两个同名）
2. **删除空间**为强提示二次确认动作；删除确认弹窗须告知"30 天内可联系平台管理员恢复"；删除后空间内所有条目、片段、检索记录一并进入软删除窗口（详见 F7）
3. **Embedding 模型允许变更（模型迁移）**：空间已有数据后仍可修改 embedding 模型；变更确认后系统自动触发**全量重新向量化任务**——
   - 迁移期间空间整体状态显示为"迁移中 N%"（在列表页和详情页顶部均有标识，N 为已完成条目比例）
   - 迁移过程中检索功能**仍可正常使用**，返回的是基于旧向量的结果
   - 迁移完成后自动切换到新向量，旧向量被清理
   - 切换前 UI 须二次确认并明确告知"全量重新向量化会消耗较长时间"（成本说明不出现在用户感知 UI 上；具体计费 UI 不在本期范围，见 §7 第 5 条）
   - **迁移期间新上传的语义**：迁移进行过程中，用户**不被阻塞**，仍可正常向该空间上传文件或录入文本——新上传的条目**立即使用新模型**完成切片与向量化，其向量直接归属于"新版本向量索引"，迁移完成后无需重算；新上传的条目在迁移完成前不影响检索（检索仍走旧向量），迁移完成后自然纳入统一检索范围
   - **迁移失败处理**：若迁移任务整体或部分条目失败，空间状态变为"迁移失败"——已完成重向量化的条目保留新向量但暂不切换，旧向量仍保留可供检索；用户可在空间详情页点击"重新迁移"再次触发；本期**不支持用户主动取消迁移中任务**
4. **可见性**：见 §5

#### 4.1.5 验收标准

- [ ] 用户能创建一个公司级空间，填完必填项后在列表页能看到
- [ ] 用户能创建一个个人空间，且该空间在其他**普通用户**那里不可见
- [ ] 用户创建个人空间时，表单内可见"本公司管理员可查看本空间内容与统计"的告知文案（强展示，无需勾选）
- [ ] 用户能编辑空间名称和描述，编辑后列表刷新
- [ ] 用户尝试删除一个空间时会被要求二次确认，且确认弹窗包含"30 天内可联系平台管理员恢复"提示
- [ ] 同名空间提交时会被告知"已存在同名空间"
- [ ] 空间列表只包含当前用户有权限看到的空间（管理员可看到本公司全部空间含他人个人空间；普通用户只能看到公司级空间 + 自己的个人空间）
- [ ] 用户对一个已有数据的空间切换 embedding 模型，系统弹出迁移确认，并在确认后展示"迁移中 N%"标识；**迁移期间执行检索能返回基于迁移前向量的结果**（不出现无结果或结果乱序）
- [ ] 迁移进行期间，用户向该空间上传一个新文件，该新文件不被阻塞，状态正常推进到"成功"；迁移完成后该新文件无需被重新向量化即可参与统一检索
- [ ] 模拟一次迁移失败场景，空间状态变为"迁移失败"，旧向量仍可被检索，且用户可点击"重新迁移"重新触发

### F2. 文件入库

#### 4.2.1 功能描述
用户能把本地文件上传到指定空间。系统自动把文件按规则切成若干片段并向量化，完成后该条目即可被检索。

#### 4.2.2 业务流程（用户视角）

1. 用户进入某个空间 → 点击"上传文件"
2. 选择一个或多个本地文件（单次最多 **10 个**）→ 文件开始上传，前端显示每个文件的上传进度
3. 上传前系统对每个待上传文件检查"同空间内是否已存在同名条目"——
   - 存在 → 提示"已存在同名条目'X'，是否覆盖？"（用户可选择"覆盖"或"跳过"）；覆盖即先删除旧条目（其片段、被命中统计一并清零），再以本次上传内容重建
   - 不存在 → 正常上传
   - **批量冲突处理**：同批次中存在多个同名文件时，系统**一次性列出所有冲突文件**供用户在同一对话框内统一勾选"覆盖"或"跳过"；用户关闭对话框未作选择时，所有冲突文件**默认按"跳过"处理**，无冲突的文件正常上传
4. 用户可在上传过程中选择"使用空间默认拆分规则"或"为本次上传临时调整拆分规则"
5. 文件上传完成后，系统自动开始处理（切片 + 向量化；图片类文件先 OCR 再切片），用户**不需要等待**，列表中该条目状态为"处理中"
6. 用户可随时刷新或停留在页面，状态会自动从"处理中"变为"成功"、"部分成功"或"失败"

#### 4.2.3 业务入参

- 目标空间
- 一组本地文件（单次最多 10 个；详见 §6.1）
- 拆分规则（可选；不填使用空间默认）
- 同名冲突时的用户选择（覆盖 / 跳过）

#### 4.2.4 业务出参

- 入库任务编号（用于查询整体进度）
- **整体任务状态**：按结果分四类计数（处理中 / 成功 / 部分成功 / 失败），任务列表上同时显示四项数值
- 每个条目在处理完成后呈现的状态：处理中 / 成功 / **部分成功** / 失败（含失败原因）
- 处理成功后能查看该条目被切成的片段列表与片段内容
- 状态为"部分成功"的条目也可查看其已成功的片段（若有），并可被重试

#### 4.2.5 业务规则

1. **支持的文件类型**：CSV、PDF、DOC、DOCX、XLS、XLSX、PNG、JPG、JPEG、EPUB、纯文本（共 11 类）。其他类型在选择文件时即提示"不支持"
2. **单文件大小上限**：默认 50 MB，超过即在上传前被拒
3. **单次批量上传文件数量上限**：**10 个**。前端在选择超过 10 个文件时提示"单次最多上传 10 个文件"并阻止提交
4. **重复上传同一文件到同一空间（同名去重）**：按文件名识别，命中已存在条目时弹出"已存在，是否覆盖"——
   - 选择"覆盖"：删除旧条目（含其全部片段与被命中统计），用本次内容重建
   - 选择"跳过"：本次上传中该文件被忽略，不影响同批其他文件
   - **若目标空间处于"迁移中"状态**：覆盖上传**不被阻塞**，按照 §4.1.4 规则 3 的"迁移期间新上传"语义处理——新内容立即使用新模型完成切片与向量化，旧条目在覆盖时被正常删除（其旧向量随删除消除，不影响迁移任务的剩余部分）
5. **图片类文件（PNG / JPG / JPEG）处理方式**：所有图片入库时**走 OCR**提取文字后再切片入库——
   - **实现说明**：图片 OCR 由平台内部能力提供，具体 OCR 服务的选型由技术团队决定，不在本需求范围
   - OCR 处理时间通常显著长于普通文本提取，对应入库可见性要求详见 §2.3 注解
   - **OCR 失败回退（部分成功语义）**：若 OCR 调用失败或返回空文本，该条目状态置为"部分成功"——文件名与元数据仍可被关键词检索命中，但正文片段数为 0、不参与语义检索；UI 中标注"OCR 失败，已仅保留文件名可检索"
6. **失败 / 部分成功条目的重试**：状态为"失败"或"部分成功"的条目均可由用户点击"重试"重新处理，重试行为统一为"从头重做"（详见 §4.7.2）
7. **入库失败不影响其他文件**：批量上传的一个失败不会阻断其他文件
8. **入库超时保护**：单条目处理时长超过平台级配置阈值（具体数值不向用户暴露）仍未完成的，自动置为"失败"并展示原因"处理超时，请重试"

#### 4.2.6 验收标准

- [ ] 用户选择 3 个 PDF 上传，3 个条目都在列表中以"处理中"状态出现，并能拿到任务编号
- [ ] 用户尝试一次选择 11 个文件，前端阻止并提示"单次最多上传 10 个文件"
- [ ] 用户上传一个超过 50 MB 的文件，前端在上传前阻止并提示
- [ ] 用户上传一个 ZIP 压缩文件，前端阻止并提示"不支持的文件类型"
- [ ] 用户上传一个文件名与空间内已有条目同名时，系统弹出"是否覆盖"选项
- [ ] 用户对同名条目选择"覆盖"，旧条目（含被命中次数）被清理，新内容入库后片段列表反映新内容
- [ ] 用户一次上传 5 个文件，其中 3 个与空间内已有条目同名，系统一次性列出 3 个冲突文件供统一勾选；用户关闭对话框未选时，3 个冲突文件全部按"跳过"处理，另 2 个无冲突文件正常上传
- [ ] 用户上传一张清晰的扫描件图片（PNG），最终状态为"成功"，能在片段列表中看到 OCR 出来的文字
- [ ] 用户上传一张无文字的图片，最终状态为"部分成功"，片段数为 0，文件名仍可被关键词检索
- [ ] 状态为"部分成功"的条目可被点击"重试"重新处理，重试期间其旧的"文件名可检索"能力**保持不变**直到新入库流程完成（成功则替换为新结果，失败则恢复为"失败"）
- [ ] 用户上传一个损坏的 PDF，最终状态为"失败"，并能看到失败原因
- [ ] 失败条目点击"重试"后状态重新变为"处理中"
- [ ] 单条目处理时长超过平台超时阈值时，状态自动置为"失败"，原因为"处理超时，请重试"
- [ ] 用户上传文件后离开页面再回来，能看到最新状态
- [ ] 当目标空间状态为"迁移中"时，用户仍可正常上传新文件，新文件不被阻塞，且使用新模型完成入库

### F3. 文本直传入库

#### 4.3.1 功能描述
用户可不上传文件，直接输入一段文字（带标题）作为知识条目沉淀进空间。

#### 4.3.2 业务入参
- 目标空间
- 标题（必填）
- 正文（必填，**字数上限 100,000 字**）
- 拆分规则（可选）

#### 4.3.3 业务出参
- 入库任务编号
- 该文本条目在列表中以"文本"类型出现，处理流程与文件入库一致

#### 4.3.4 业务规则
1. **正文长度上限**：100,000 字。超过即在提交前被拒，并提示"正文超过 100,000 字上限，请精简或分多条录入"
2. 文本条目与文件条目在列表中**统一展示**，只通过"来源类型"列加以区分
3. 文本条目同样可重试、删除、查看片段
4. 同标题文本在同一空间内的去重规则与文件入库一致（见 §4.2.5 规则 4），命中已存在同标题条目时提示"是否覆盖"
5. **个人空间内录入文本的告知**：当目标空间为个人空间时，录入对话框内同样可见固定告知文案"本公司管理员可查看本空间内容与统计"（见 §5.2 规则 3）

#### 4.3.5 验收标准
- [ ] 用户提交一条标题+正文，列表中以"文本"类型出现
- [ ] 文本条目最终能进入"成功"状态并可被检索
- [ ] 用户提交超过 100,000 字的正文，被前端阻止并提示
- [ ] 文本条目可被删除并进入软删除窗口
- [ ] 同标题文本提交时弹出"是否覆盖"
- [ ] 用户向个人空间录入文本时，录入对话框内可见管理员可见性的告知文案

### F4. 条目读取与拆分（可参数化）

#### 4.4.1 功能描述
系统按照"先空间默认、再本次覆盖"的两层规则把条目（文件 / 文本）切成若干**片段**。用户能在条目处理完成后预览该条目被切成了哪些片段，便于评估切分质量。

#### 4.4.2 拆分规则的两层覆盖

1. **空间级默认拆分规则**：在创建/编辑空间时设定，作为该空间所有入库操作的默认值
2. **单次入库的临时覆盖**：在文件上传 / 文本提交时允许临时调整，只对本次入库生效，不影响空间默认

#### 4.4.3 用户可调整的拆分参数（仅 2 项）

| 参数 | 含义 | 默认值参考区间 |
|---|---|---|
| 片段大小（chunk_size） | 单个片段的目标字符数 | 文档类（PDF / DOC / DOCX / EPUB / 纯文本）：800 字符；表格类（CSV / XLS / XLSX）：1200 字符；图片 OCR 结果按文档类处理 |
| 片段重叠量（chunk_overlap） | 相邻两个片段重复的字符数，用于保留上下文 | 文档类：100 字符；表格类：0 字符 |

> **分隔符、最小块大小、标题保留策略等高级项**由系统按文件类型自动处理，本期不暴露给用户调整。这样做的目的是让非技术用户也能开箱即用。

#### 4.4.4 默认规则要求

- 平台为不同文件类型（如表格类与文档类、PDF 与纯文本）提供差异化的默认 chunk_size / chunk_overlap，参考值见 §4.4.3
- 默认规则对**非技术用户**应"开箱即用"——用户不修改默认值时，切分效果应能满足绝大多数场景

#### 4.4.5 业务出参
- 单条目片段列表：每个片段显示序号、字数、内容预览
- 当前条目使用的拆分规则（让用户事后可追溯本次入库用的是空间默认还是临时覆盖）

#### 4.4.6 业务规则

1. **本期不支持手动编辑片段**（不允许用户拖动调整切分位置 / 手动合并片段）。在片段预览页提示用户："如需调整切分效果，请修改拆分规则后重新入库"
2. **同一条目用不同拆分参数二次入库**：以"覆盖"方式处理——删除该条目原有的全部片段（被命中统计随之清零），以新参数重新切割与向量化

#### 4.4.7 验收标准
- [ ] 用户能查看一个已处理成功的条目被切成的片段列表
- [ ] 片段列表显示每个片段的内容预览
- [ ] 用户能看到本次入库使用的拆分规则
- [ ] 用户对已入库条目以不同 chunk_size 重新入库，原片段被清理、被命中统计清零，新片段反映新参数
- [ ] 用户用默认拆分规则入库一个约 1000 字的纯文本文档，得到至少 1 个、不超过 3 个片段（落入默认 chunk_size = 800、chunk_overlap = 100 的合理区间）

### F5. 检索（搜索）

#### 4.5.1 功能描述
用户能输入一段 query，在一个或多个空间范围内查找相关片段。检索同时支持语义相似度（向量召回）和关键词命中（关键词召回），并把结果融合返回。检索结果可在"检索测试"页直观查看；同样的能力也提供给未来 Chatbot 调用。检索响应的 SLA 按"单空间 / 跨空间 2-5 个 / 跨空间 6 个及以上"分级，详见 §6.2。

#### 4.5.2 业务入参
- 查询语句（query）
- 检索的空间范围：一个或多个空间
- 返回数量（top_k）：**默认 5；最大允许 20**
- 可选过滤条件：
  - 文件类型（PDF / DOCX / 图片 ……）
  - 来源类型（文件 / 文本）
  - 上传时间区间
  - 指定的条目范围

#### 4.5.3 业务出参

每条命中结果包含：
- 命中片段的文本内容
- 该片段所属的条目名称、所属空间名称
- 命中相似度（一个 0-1 之间的数值，越大越相关）
- 命中类型标识（语义命中 / 关键词命中 / 两者都命中）

**"部分成功"条目的命中呈现**：状态为"部分成功"的条目被关键词检索通过文件名命中时——
- 在结果列表中正常返回一条记录
- "命中片段的文本内容"字段显示固定占位"[仅文件名可检索，正文未入库]"
- "命中类型标识"为"关键词命中"
- 不参与语义召回的 top_k 排名（即只在关键词召回路径出现）
- 命中相似度仅基于文件名与 query 的字符串匹配度计算

**条目名称的统一展示**：文件条目以**文件名**作为条目名称展示；文本条目以用户填写的**标题**作为条目名称展示。两者统称"条目名称"。

#### 4.5.4 业务规则

1. **检索范围必须在用户可见范围内**：用户检索时只能指定自己可见的空间作为范围，越权指定会被拒；系统调用方代用户检索时按代表用户的可见范围**做权限裁剪**（详见场景 S5b）
2. **检索行为会被记录**：每次检索都会被记录用于统计（详见 F6）；被命中的片段其"被命中次数"+1（计数规则详见 §4.6.4）
3. **空结果场景**：query 在指定范围内无命中时，返回空列表 + 提示"未找到相关内容"
4. **本期不返回命中片段的上下文**：仅返回命中片段本身，不返回其前后相邻片段。如未来 Chatbot 需要上下文，另行设计补丁方案
5. **关键词召回不做中文分词**：本期关键词召回仅做字符串匹配，对中文场景关键词召回效果会弱于英文，混合检索仍以语义召回为主
6. **不做时效衰减**：检索结果纯按相似度从高到低排序，不因上传时间新旧而调整顺序
7. **不做跨语种检索**：中文 query 不召回纯英文资料，英文 query 不召回纯中文资料。建议用户在创建空间时将不同语种资料分置不同空间

#### 4.5.5 验收标准
- [ ] 用户在某空间的"检索测试"输入一段 query，能看到若干命中片段及其来源
- [ ] 用户指定多个空间作为检索范围，能拿到跨空间的合并结果
- [ ] 用户指定一个自己无权访问的空间作为检索范围，请求被拒（若混合了有权 / 无权空间，无权部分被裁剪，仅在有权空间内执行检索）
- [ ] 用户不指定 top_k 时默认返回 5 条；指定大于 20 时被截至 20
- [ ] 一次检索完成后，统计页相应数据有更新
- [ ] 检索结果按相似度从高到低排序
- [ ] **用户对一个包含"部分成功"条目的空间执行关键词检索（query 与该条目文件名匹配），检索结果中能找到该条目；命中片段内容字段显示"[仅文件名可检索，正文未入库]"；命中类型标注为"关键词命中"**

### F6. 使用统计（Dify 风格统计页）

#### 4.6.1 功能描述
为空间和条目提供使用情况洞察，帮助维护者判断哪些资料真正被 Chatbot 用到、哪些资料应当继续完善或淘汰。

#### 4.6.2 空间维度统计

每个空间提供一个统计页，展示：
- **总片段数**：该空间下所有条目切片后的总和；**"部分成功"条目按其实际成功的片段数计入**（OCR 失败导致正文片段数为 0 时，对总片段数贡献为 0）
- **总 token 数**：该空间向量化过程中累计消耗的 embedding token 量（来自平台对 LLM / embedding 服务调用的计量记录）；"部分成功"条目按其实际成功向量化的片段对应的 token 数计入
- **被检索次数**：该空间被作为检索范围的累计次数
- **最近热门 query**：最近 **30 天**内被查询次数最多的若干条 query
- **命中次数最多的片段排行**：被检索命中最多的前若干个片段

#### 4.6.3 条目维度统计

每个条目（文件 / 文本）提供：
- 自身被命中次数（累计，永久保留）
- 该条目下被命中最多的片段排行（"部分成功"条目若无成功片段，本节展示为空，不影响"自身被命中次数"的累计）

#### 4.6.4 业务规则
1. **命中次数计数**：一次检索中，top_k 范围内**所有**命中片段都累加 1 次。即若 top_k=5，则本次检索完成后有 5 个片段各 +1（无命中则不增加）
2. **"部分成功"条目的统计处理**：
   - "部分成功"条目通过文件名被关键词检索命中时，**该条目维度的"被命中次数"+1**（与正常条目相同）
   - 由于该条目正文片段数为 0，**不出现在"命中次数最多的片段排行"中**（无片段可参与排名）
   - 在空间维度的"被检索次数"和"总 token 数"上的贡献按上文 §4.6.2 的具体规则计入
3. **统计数据保留策略**：
   - **热门 query 列表**：保留最近 **30 天**（超出 30 天的 query 不再展示，但底层日志保留方式由平台决定）
   - **命中次数累计值**：**永久保留**（每个条目、每个片段的命中累计不清零，除非条目被覆盖或彻底删除）
4. **统计页本期不提供导出**
5. **管理员视角**：公司管理员可查看本公司**全部空间**（含个人空间）的统计聚合与按用户钻取的详细统计；普通用户仅能看到自己可见空间的统计

#### 4.6.5 验收标准
- [ ] 空间统计页能正确显示总片段数、被检索次数
- [ ] 一次新的检索发生后，空间统计页对应数字按规则 1 增加
- [ ] 条目统计能显示该条目被命中的累计次数
- [ ] **"部分成功"条目（正文片段为 0）被关键词检索命中后，其条目维度"被命中次数"+1，且不出现在"命中次数最多的片段排行"中**
- [ ] **"部分成功"条目对空间维度"总片段数"的贡献为其实际成功的片段数；OCR 完全失败的图片条目对"总片段数"的贡献为 0**
- [ ] 热门 query 列表只展示最近 30 天的数据
- [ ] 管理员能在统计页看到本公司全部空间的聚合数据，并可钻取到某个普通用户的个人空间统计
- [ ] 普通用户在统计页看不到他人个人空间的数据

### F7. 配置与维护

#### 4.7.1 系统级配置（用户可感知）

| 项目 | 默认值 | 说明 |
|---|---|---|
| 单文件大小上限 | 50 MB | 超过即拒绝上传 |
| 单次批量上传文件数上限 | 10 个 | 超过即在前端被拒 |
| 文本直传字数上限 | 100,000 字 | 超过即在提交前被拒 |
| 软删除窗口 | 30 天 | 删除的空间 / 条目在 30 天内仍占用资源，30 天后彻底清除 |
| 单条目入库处理超时 | 平台级配置（不向用户暴露具体数值） | 超时后状态置为"失败"，原因为"处理超时，请重试" |
| 单空间 / 单公司条目数与存储容量 | 不设上限（本期） | 后端字段预留，但本期不出配额 UI |

#### 4.7.2 失败 / 部分成功重试

- 状态为"失败"或"部分成功"的条目均可由用户点击"重试"按钮重新处理
- **重试方式**：**从头重做**——删除该条目已生成的全部中间结果（含部分片段、部分向量），重新执行整套入库流程（解析 / OCR / 切片 / 向量化）。本期不做断点续传
- **"部分成功"重试的特别说明**：
  - 在重试触发到新流程完成之间，**原条目的"文件名可检索"能力保持不变**（不预先清除元数据）
  - 新入库流程成功后，原"部分成功"状态的元数据 / 检索能力被**新的成功结果替换**
  - 新入库流程仍然失败时，条目状态恢复为"失败"（不保留旧的"部分成功"占位检索能力）
- 重试入口在条目列表与条目详情页均提供

#### 4.7.3 软删除与恢复

- 空间或条目被删除后，进入软删除窗口（默认 30 天），30 天后由平台彻底清除
- **本期不提供用户自助恢复 UI**——用户在删除确认弹窗中会看到"30 天内可联系平台管理员恢复"的告知。30 天内的恢复操作由平台运维兜底执行

#### 4.7.4 配额（成本控制）
- 本期**不出收费 UI、不出配额超限提示 UI**
- 后端字段需为未来配额功能预留（如单空间 token 累计、单公司存储累计等口径）
- 离职用户的个人空间**自动进入软删除窗口**，30 天后清除，规则与普通删除一致

| 看公司级空间统计页 | ✅（本公司全部） | ✅（本公司全部） | ❌ |
| 创建个人空间 | ✅（自己的） | ✅（自己的） | ❌ |
| **查看/编辑/删除他人个人空间** | **✅（本公司内任意员工的个人空间，完整管理权限）** | ❌ | ❌ |
| **查看他人个人空间的统计聚合与详细统计** | **✅（按用户钻取）** | ❌ | ❌ |
| 在自己的个人空间内全部操作 | ✅ | ✅ | ✅（仅当代用户为该用户时） |
| 跨公司访问任何空间 | ❌ | ❌ | ❌ |

### 5.2 数据隔离要求

1. **公司之间硬隔离**：任何角色都不能跨公司看到、检索、操作别家公司的空间
2. **个人空间的可见范围**：对**其他普通用户**完全不可见；对**本公司管理员**完整可见可操作。这是本公司的内部治理需要
3. **隐私告知（透明化义务）**：
   - 用户**创建个人空间**时，表单内必须显示固定文案"本公司管理员可查看本空间内容与统计"
   - 用户**向个人空间上传文件 / 录入文本**时，上传 / 录入对话框内必须显示同一文案
   - 该告知不可被关闭、不可隐藏
   - **告知形式定性**：强展示，**无需用户主动勾选确认**。本产品定性为公司内部管理工具，"告知"即满足合规所需，不引入"勾选同意"形式以避免对内部高频上传行为造成不必要摩擦。该定性记录在 §8 决策记录中作为合规问责时的依据
4. **系统调用方代用户检索**：Chatbot / Agent 调用检索时**必须携带"代表哪个用户"的身份**；权限按该用户的可见范围裁剪，越权传入的空间被裁剪剔除（见场景 S5b）
5. **无用户身份的系统调用一律拒绝**：未携带 user_id 的 Chatbot / Agent 调用，无论调用方是定时任务还是其他系统场景，均一律拒绝（返回鉴权失败）。如有"无具体用户上下文"的检索场景需求，另行立项设计 service account 体系

### 5.3 角色边界细则

- **用户离职后其个人空间的处置**：账号停用同步触发该用户名下个人空间**自动进入软删除窗口**（30 天后彻底清除），与普通删除规则一致；不做"自动转交管理员"流程
- **用户可创建的个人空间数量**：本期不设上限（待未来配额功能落地时统一管控）
- **公司级空间的"只读分发"模式**：本期不做，所有公司级空间默认任何普通用户都可上传

## 6. 非功能需求

### 6.1 业务容量上限（用户侧）

| 维度 | 上限 | 说明 |
|---|---|---|
| 单文件大小 | 50 MB | 超出即拒 |
| 支持的文件类型 | 11 类（见 §4.2.5 规则 1） | 其他类型本期不支持 |
| 单批量上传文件数 | 10 个 | 超出即在前端被拒 |
| 文本直传单条字数 | 100,000 字 | 超出即在前端被拒 |
| 单空间条目 / 片段数上限 | 本期不设上限 | 后端字段预留 |
| 单公司存储总量上限 | 本期不设上限 | 后端字段预留 |
| 单用户个人空间数上限 | 本期不设上限 | 待配额功能落地后统一管控 |

### 6.2 性能（用户可感知，作为验收硬性标准）

| 指标 | 目标 |
|---|---|
| **检索响应（P95，单空间，top_k ≤ 10）** | **< 3 秒** |
| **检索响应（P95，跨空间 2-5 个空间联合）** | **< 5 秒** |
| **检索响应（跨空间 6 个及以上）** | 不设 SLA，best-effort（前端给出进度反馈即可） |
| 上述检索 SLA 的适用前提 | （1）不含首次冷启动；（2）相关空间已完成全量索引建立；（3）适用于"包含或不包含 OCR 内容"的空间——OCR 仅影响入库时长，不影响检索响应时间 |
| 上传文件后任务可见时间（非图片类型） | **< 10 秒** |
| 上传文件后任务可见时间（图片 / 扫描件类型） | < 10 秒任务可见，但**不保证 10 秒内完成 OCR 处理**（见 §2.3 注解） |
| 文件处理时长（非超时场景） | 不做硬性上限，但应在条目列表中持续可见进度，避免"卡住但无反馈" |
| 单条目入库处理超时 | 由平台级配置兜底（见 §4.7.1），超时后状态变为"失败" |
| 资料沉淀效率 | 一名普通用户在 5 分钟内能完成「建空间 → 上传 3 个文件 → 跑通一次检索测试」（不含图片 OCR 类型） |

### 6.3 可靠性

1. 任务失败必须显式展示给用户，并附**可理解的失败原因**（不是堆栈，而是诸如"文件已损坏"、"OCR 服务暂时不可用，请稍后重试"、"处理超时，请重试"等业务化提示）
2. 用户离开页面再回来，状态信息应保持一致
3. 单个文件失败不影响同批其他文件
4. OCR 失败导致的"部分成功"状态，须在条目列表与详情页清晰标注
5. 入库任务处理时长超过平台超时阈值时，自动置为"失败"并展示"处理超时，请重试"，避免用户面对"无限处理中"无可操作

### 6.4 合规与多租户

1. 公司之间数据严格隔离（见 §5.2）
2. 删除操作进入软删除窗口（默认 30 天），用户感知层面为"已删除"，30 天内可联系管理员恢复，30 天后彻底清除
3. 检索行为被记录（用于统计；不出审计页面）
4. 个人空间对管理员可见的事实须在创建/上传/录入时透明告知用户（见 §5.2 规则 3）

### 6.5 国际化

- 本期界面文案以中英双语为基础（按平台现有惯例）
- **不做**多语言知识 / 跨语种检索（划在范围外，见 §7）

## 9. 术语表

| 术语 | 英文对照 | 解释 |
|---|---|---|
| **空间** | **Space** | 一组同主题资料的容器；是用户做上传、检索、统计等操作的基本单位。例："产品手册""销售话术""我的调研笔记"。**正文中"空间"作为对象名统一使用，不混用"RAG"作为对象代词**（"RAG"仅作模块名出现） |
| **条目** | **Entry** | 一个被装入空间的"知识单元"。可以是一个文件，也可以是一段直接录入的文本。**正文统一以"条目"作为对象代词**，不再混用"文件 / 文本"指代单个对象——具体类型通过条目的"来源类型"字段加以区分（文件 / 文本）。条目名称的展示规则：文件条目以**文件名**展示；文本条目以用户填写的**标题**展示 |
| **片段** | **Chunk** | 一个条目被自动切分后的小段文本。检索的最小单位就是片段，而不是整个条目。**正文统一使用"片段"**，不使用"分块"作为对象代词；"chunk"一词仅在参数名（chunk_size / chunk_overlap）中保留英文形式 |
| 拆分 | Chunking | 把一份文件 / 一段文本按规则切成若干片段的过程；拆分质量直接影响检索效果 |
| 入库任务 | — | 一次"上传文件 / 录入文本到空间"动作所对应的后台处理任务，含切分 + 向量化等步骤；用户可通过任务编号查看进度。任务整体状态按结果分四类计数：处理中 / 成功 / 部分成功 / 失败 |
| Embedding（向量化） | Embedding | 把一段文字转成数学向量的过程，转完之后才能做语义检索；平台支持多种模型，由空间创建时指定 |
| **全量重新向量化（模型迁移）** | **Re-embedding / Model Migration** | 当空间的 embedding 模型被切换时，系统自动把该空间已有的全部条目按新模型重新计算一遍向量的过程。迁移期间空间显示"迁移中 N%"，检索仍可使用旧向量返回结果；**迁移期间用户新上传的条目立即使用新模型入库**，归属新版本向量索引；迁移完成后自动统一切换 |
| **OCR**（光学字符识别） | **Optical Character Recognition** | 从图片 / 扫描件中识别并提取文字的能力。本平台对 PNG / JPG / JPEG 类文件入库时统一走 OCR，提取后的文字按普通文本流程切片与向量化 |
| 检索 | Retrieve / Search | 用户输入一段 query，在指定空间范围内找到最相关片段的过程 |
| 混合检索 | Hybrid Retrieval | 同时使用"语义相似度（向量召回）"和"关键词命中"两种方式，再把结果融合，比单独用任一种效果更稳 |
| top_k | — | 一次检索返回的命中片段数量上限。本期默认 5，最大 20 |
| 软删除窗口 | Soft-delete Window | 删除后用户层面看不到，但平台仍保留一段时间（默认 30 天）以便恢复或彻底清理 |
| **部分成功** | **Partial Success** | 条目入库时主流程未能完整完成（如图片 OCR 失败），但仍保留了文件名与元数据可供关键词检索的状态。"部分成功"条目可被检索（关键词路径）、可被重试（从头重做），其对空间统计的贡献按其实际成功的片段数计入 |
| RAG（检索增强生成） | Retrieval Augmented Generation | 让 AI 在回答前先到RAG里检索相关片段，然后基于这些片段生成答案的方式；本需求是 RAG 的"检索"侧能力 |
| 系统调用方 | — | 未来的 Chatbot / Agent；以"代某个用户"的身份调用本模块的检索能力；本期严格要求必须携带用户身份 |
