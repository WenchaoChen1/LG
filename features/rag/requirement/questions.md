## A. 空间所有者与权限

### A1. 公司管理员能否查看或操作普通员工的个人空间？

**背景**：需求文档（§5.1）把管理员查看他人个人空间标注为"默认否"，但没有最终确认。如果管理员完全看不到员工个人空间，则员工离职后该空间会孤立在系统里无人处置；如果管理员能看到，则员工会担心私人资料泄露。

**选项**：
- [ ] A. 默认否：管理员看不到，员工个人空间完全私密（推荐/默认）
- [ ] B. 管理员仅能看到个人空间的"存在"（名称、大小），但无法查看内容
- [ ] C. 管理员可完整查看并操作员工的个人空间
- [ ] D. 可配置：管理员权限由公司自行设置
- [ ] 其它（请描述）

**影响**：若选 A，员工离职后需要另行设计孤儿空间的清理机制（见 A3）；若选 C，需在 UI 上对员工做清晰告知（"管理员可见"标注），否则会产生隐私纠纷。

---

### A2. 管理员查看"公司全部空间统计"是否包含个人空间的统计入口？

**背景**：需求文档（§5.1）写"看公司级空间统计页 — 管理员可查看本公司全部"，但未明确"全部"是否包括公司内所有员工的个人空间统计聚合。[来源：pm-writer 自审 §5.1]

**选项**：
- [ ] A. 仅包含公司级空间统计，个人空间统计对管理员不可见（推荐/默认）
- [ ] B. 管理员能看到公司全部空间（含个人空间）的统计聚合，但无法看个人空间内容
- [ ] C. 管理员既能看到统计聚合，也能查看员工个人空间的详细统计
- [ ] 其它（请描述）

**影响**：若选 B 或 C，个人空间的检索行为（热门 query 列表）会暴露给管理员，属于隐私边界问题，需要在产品层面明确告知用户。

---

### A3. 员工离职后，其个人空间如何处置？

**背景**：员工账号被停用后，其名下的个人空间（含已向量化的数据）还占用系统资源，且可能含有对公司有价值的资料。目前需求文档（§5.3）仅列为待澄清，未给出处置规则。

**选项**：
- [ ] A. 自动进入软删除窗口（30 天后清除），与普通删除规则一致（推荐/默认）
- [ ] B. 账号停用时发送通知给管理员，由管理员决定是否转交或归档
- [ ] C. 账号停用不影响个人空间，空间本身继续保留直到主动删除
- [ ] D. 自动转交给公司管理员名下
- [ ] 其它（请描述）

**影响**：若选 B 或 D，需要开发"空间转交"流程；若选 C，则孤儿空间会持续占用 embedding 存储资源和 token 配额（如将来有配额管理）。

### A4. 单用户可创建的个人空间数量是否有上限？

**背景**：输入材料（七、问题 3）提出了此问题，但需求文档未给出边界值。不设上限会导致少数重度用户占用大量资源；设置过低又会限制正常使用。

**选项**：
- [ ] A. 本期不设上限（推荐/默认，等配额需求落地时再统一管控）
- [ ] B. 每个用户个人空间上限 5 个
- [ ] C. 每个用户个人空间上限 10 个
- [ ] D. 按公司级配置，每个公司设定每用户上限
- [ ] 其它（请描述）

**影响**：若选 A，本期开发更简单，但需要在 §6 容量上限处做出说明，避免将来被问"没有限制吗？"

---

### A5. 系统调用方（Chatbot / Agent）是否允许以"无具体用户"身份做全公司范围检索？

**背景**：需求文档（§5.3）列为待澄清，但未给出推荐选项。当前设计要求 Chatbot 必须携带"代表哪个用户"的身份，才能根据该用户的可见范围过滤检索结果。如果 Chatbot 在没有具体用户上下文的场景（如定时任务、系统通知场景）下需要检索，这条规则就会形成障碍。

**选项**：
- [ ] A. 严格要求必须携带用户身份，无 user_id 则拒绝（推荐/默认，安全性更高）
- [ ] B. 允许使用 service account 身份，service account 仅能检索公司级空间（不能检索任何个人空间）
- [ ] C. 允许使用 service account 身份，无权限限制（可检索全公司所有空间）
- [ ] 其它（请描述）

**影响**：若选 A，Chatbot 在未来的对话场景中每次都需要传入触发对话的用户身份，设计稍复杂但安全；若选 B，可以支撑定时任务类场景，但需要设计 service account 的发放机制。

---

### A6. 公司级空间能否被设置成"只读分发"模式（创建者或管理员维护，普通用户只读检索不能上传）？

**背景**：输入材料（七、问题 4）提出此需求。当前权限矩阵（§5.1）中普通用户对所有公司级空间有上传权限，这在某些场景下（如公司正式政策文档）并不合适。

**选项**：
- [ ] A. 本期不做，所有公司级空间默认任何普通用户都能上传（推荐/默认，MVP 简化）
- [ ] B. 本期支持：创建公司级空间时可选"仅管理员可上传"
- [ ] C. 支持更细粒度的每空间上传权限控制（如白名单用户）
- [ ] 其它（请描述）

**影响**：若选 B 或 C，前端创建空间的表单需要新增权限设置项，权限矩阵也需要相应更新；若选 A，日后产品迭代时可能需要大面积补权限控制。

## B. 文件入库

### B1. 图片文件（PNG / JPG / JPEG）是否需要走 OCR 提取文字？

**背景**：需求文档（§4.2.5 规则 5）和输入材料（七、问题 8）均标注为待澄清。OCR 能让扫描件、截图等图片中的文字被检索，但需要额外的 OCR 服务调用，成本和延迟都更高。[来源：输入材料七-8]

**选项**：
- [ ] A. 本期不走 OCR，图片文件入库时提示"图片文件仅支持文件名检索，正文不可被语义检索"
- [ ] B. 走 OCR，所有图片都提取文字后入库（推荐/默认，用户体验更完整，esapiens 有现成实现可评估）
- [ ] C. 可选：用户上传图片时选择是否走 OCR
- [ ] 其它（请描述）

**影响**：若选 A，图片文件入库后检索效果很差，用户可能感到困惑；若选 B，需要明确 OCR 服务选型（调第三方还是用现有方案），并在文件处理时间预期上做说明（OCR 比普通文本提取慢很多）。

---

### B2. 同一文件是否允许重复入库到同一空间？

**背景**：需求文档（§4.2.5 规则 4）临时假设"允许并存为不同条目"，但输入材料（七、问题 5）对此未下结论。如果用户反复上传同一份合同，空间里会出现大量重复片段，导致检索结果噪音大。

**选项**：
- [ ] A. 允许并存，作为独立条目处理（当前假设，适合多版本场景）
- [ ] B. 按文件名去重：同名文件提示"已存在，是否覆盖"（推荐/默认，用户体验更友好）
- [ ] C. 按文件内容哈希去重：内容相同无论文件名是否一样都提示重复
- [ ] 其它（请描述）

**影响**：若选 B 或 C，需要在入库前做一次去重检查，开发量略增，但能防止重复数据污染检索结果；若选 A，需要在 UI 上考虑如何让用户区分"同名的多个版本"。

---

### B3. 单次批量上传文件数量上限是多少？

**背景**：需求文档（§4.2.3 / §6.1）均标注为"待澄清"。如果不设上限，用户一次选择几百个文件可能会导致后台队列积压；设置过低又会给大批量导入场景带来不便。[来源：输入材料七-6]

**选项**：
- [ ] A. 每次上传上限 10 个文件（推荐/默认，MVP 阶段保守）
- [ ] B. 每次上传上限 20 个文件
- [ ] C. 每次上传上限 50 个文件
- [ ] D. 不设上限（不推荐，可能影响系统稳定性）
- [ ] 其它（请描述）

**影响**：此数值直接决定后台任务队列的设计规格；同时影响前端上传组件的交互设计（如是否展示"已选 N 个，超出上限"提示）。

## C. 文件读取与拆分

### C1. 文本直传正文的字数上限是多少？

**背景**：需求文档（§4.3.4 / §6.1）暂定默认 100,000 字，但标注为待澄清。100,000 字约为一本中等长度的技术书籍，若用户粘贴超大文本可能导致处理超时或 token 成本异常。[来源：pm-writer 自审 §4.3.4]

**选项**：
- [ ] A. 10,000 字（适合会议纪要、邮件、短报告等典型场景）
- [ ] B. 50,000 字（约一篇长报告）
- [ ] C. 100,000 字（当前默认值，约一本小册子）（推荐/默认）
- [ ] D. 不设上限（不推荐，有 token 成本失控风险）
- [ ] 其它（请描述）

**影响**：上限越高，单条文本条目的 embedding 成本越难管控；上限越低，用户可能需要手动拆分大段资料，体验变差。该值也会影响单空间 token 配额的预估。

---

### C2. 用户能调整哪些拆分参数？仅基础项，还是包含高级项？

**背景**：需求文档（§4.4.2）提到"可调整项以平台提供的可配置项为准"，但未明确边界。[来源：pm-writer 自审 F4]

**选项**：
- [ ] A. 仅基础 2 项：片段大小（chunk_size）和片段重叠量（chunk_overlap）（推荐/默认，够用且对用户友好）
- [ ] B. 基础 2 项 + 分隔符选择（按句 / 按段落 / 按固定字数）
- [ ] C. 全部高级项开放：chunk_size、overlap、分隔符、最小块大小、标题保留策略等
- [ ] 其它（请描述）

**影响**：开放的参数越多，UI 越复杂；对非技术用户而言，过多参数反而会降低使用信心。建议至少确认"分隔符"是否需要开放，因为对 PDF 和 Markdown 等不同格式效果差异明显。

---

### C3. 同一文件用不同拆分参数二次入库，是覆盖原有条目还是并存为新条目？

**背景**：需求文档（§4.4.5 规则 2）标注为待澄清。用户可能因为初次拆分效果不好而想用不同参数重新切割同一份文件，此时旧的向量化数据是否保留会影响检索结果和存储成本。[来源：输入材料七-12]

**选项**：
- [ ] A. 覆盖：删除该文件原有的所有片段，以新参数重新切割（推荐/默认，避免重复噪音）
- [ ] B. 并存：在列表里作为新条目出现，用户手动删除旧的
- [ ] C. 由用户在重新入库时选择"覆盖"或"新增版本"
- [ ] 其它（请描述）

**影响**：若选 A，覆盖时原有的被命中统计数据会丢失；若选 B，用户容易忘记删除旧条目，导致重复片段干扰检索。

## D. 检索

### D1. 检索结果默认返回多少条（top_k 默认值），最大上限是多少？

**背景**：需求文档（§4.5.2）标注为待澄清。top_k 越大，检索覆盖越全，但 Chatbot 后续拼入 prompt 的 token 成本也越高。[来源：输入材料七-13]

**选项**：
- [ ] A. 默认 5 条，最大允许 20 条（推荐/默认，平衡效果与成本）
- [ ] B. 默认 10 条，最大允许 50 条
- [ ] C. 默认 3 条，最大允许 10 条（最保守，成本最低）
- [ ] 其它（请描述）

**影响**：默认值直接决定检索测试页的展示数量，也影响 Chatbot 接入时的 prompt 长度预估。最大值影响后端查询性能预算。

---

### D2. 检索时是否返回命中片段的上下文（前后相邻片段）？

**背景**：仅返回精确命中的片段，在某些情况下会截断句子或缺少语境，Chatbot 生成的答案可能不完整。但同时返回前后文会使每次检索的 token 量翻倍甚至更多。[来源：输入材料七-16]

**选项**：
- [ ] A. 本期不返回，仅返回命中片段本身（推荐/默认，MVP 简化）
- [ ] B. 返回命中片段 + 紧邻的前一个和后一个片段
- [ ] C. 允许 Chatbot 调用时按需指定 context_window（返回前后 N 个片段）
- [ ] 其它（请描述）

**影响**：若选 B 或 C，API 返回数据量增加，检索响应时间可能超出 3 秒目标；若选 A，未来 Chatbot 如需上下文要另外设计补丁方案。

---

### D3. 混合检索的关键词召回是否支持中文分词？

**背景**：输入材料（七、问题 14）提出此问题。中文没有天然空格分隔，不做分词直接走关键词匹配效果很差；但引入分词器会增加技术依赖（如 jieba 或 ES 的 IK 分词插件）。[来源：输入材料七-14]

**选项**：
- [ ] A. 本期不做中文分词，关键词召回仅做字符串匹配（推荐/默认，暂时仅以语义召回为主）
- [ ] B. 支持中文分词（需确认分词方案，会对部署和性能有影响）
- [ ] C. 由运维侧配置，业务层不感知（中英文自适应）
- [ ] 其它（请描述）

**影响**：若选 A，中文资料的关键词召回质量会明显弱于英文资料，混合检索对中文场景的增益有限；若选 B，需要额外的技术调研和测试，可能影响本期交付排期。

---

### D4. 是否支持时效衰减（新文件被优先召回）？

**背景**：输入材料（七、问题 15）提出此场景。对于政策类文档，用户通常希望最新版本优先于旧版本被检索到，但时效衰减会使检索逻辑更复杂且效果难以预测。[来源：输入材料七-15]

**选项**：
- [ ] A. 本期不做，纯按相似度排序（推荐/默认，MVP 简化）
- [ ] B. 支持：新上传的条目在相似度接近时优先返回
- [ ] C. 可配置：每个空间可开关时效衰减
- [ ] 其它（请描述）

**影响**：若选 B 或 C，需要确认"时效衰减"的具体算法（如按上传时间的指数衰减系数），会增加检索测试场景的复杂度。

## E. 统计

### E1. 被命中次数如何计算：所有命中的片段都 +1，还是有其他规则？

**背景**：需求文档（§4.6.4 规则 1）标注为待澄清。一次检索 top_k=10 时会命中 10 个片段，如果每个都 +1，则一次对话后统计数字会虚高；若只统计 top-1 或用户点击的，则更能反映真实价值。[来源：输入材料七-18]

**选项**：
- [ ] A. 所有命中的片段（在 top_k 范围内）都 +1（推荐/默认，统计简单，反映召回广度）
- [ ] B. 只有 top-3 的片段 +1（反映最相关的内容）
- [ ] C. 只有 Chatbot 实际引用生成答案时才 +1（最精确，但需要 Chatbot 侧回传引用信息）
- [ ] 其它（请描述）

**影响**：若选 C，本期无法实现（Chatbot 尚未上线，无法回传引用信息），只能作为未来功能预留；若选 A，统计页的命中次数排行会体现为"被召回广度"而非"真实有用度"。

---

### E2. 统计数据保留多长时间？

**背景**：需求文档（§4.6.4 规则 2）标注为待澄清。永久保留会导致数据库持续增长；短时间窗口（如 30 天）则无法看到长期趋势。[来源：输入材料七-19]

**选项**：
- [ ] A. 热门 query 列表保留最近 30 天，命中次数累计值永久保留（推荐/默认，兼顾近期洞察和长期积累）
- [ ] B. 全部统计数据保留 90 天
- [ ] C. 全部永久保留
- [ ] D. 可配置（按公司或空间设置）
- [ ] 其它（请描述）

**影响**：若选 C 或 D，对数据库存储容量规划有直接影响；若选 A，需要在 UI 上明确告知用户"热门 query 只显示最近 30 天"，避免误读。

## F. 配置与维护

### F1. Embedding 模型一旦有数据后是否允许变更？

**背景**：需求文档（§4.1.4 规则 3）当前假设"有数据后不允许变更"，但输入材料（七、问题 22）对此明确标注为开放问题。不允许变更能保持向量空间一致性，但用户可能因为成本或效果原因希望切换到更好的模型。[来源：pm-writer 自审 §4.1.4 规则 3]

**选项**：
- [ ] A. 有数据后不允许变更（当前假设，推荐/默认，避免向量空间不一致导致检索乱序）
- [ ] B. 允许变更，但变更后所有历史数据需要重新向量化（全量重跑，用户需等待）
- [ ] C. 允许变更，旧数据保留旧向量不重跑，新上传文件用新模型（混合向量，效果会下降）
- [ ] 其它（请描述）

**影响**：若选 B，需要设计"模型迁移任务"的 UI 反馈（类似大批量重新入库），否则用户不知道变更在进行中；若选 A，应在创建空间时的模型选择步骤加强提示"选定后无法更改"。

---

### F2. 失败文件的"重试"是从头重做还是断点续传？

**背景**：需求文档（§4.7.2）标注为待澄清。从头重做逻辑最简单；断点续传节省时间和 embedding 成本，但实现复杂度更高。[来源：输入材料七-20]

**选项**：

- [ ] 其它（请描述）

**影响**：若选 A，对超大文件重试成本较高（需重新调 embedding API）；若选 B，本期开发排期可能受影响，建议先评估实际场景中文件多大会让"重新重试"显得不可接受。

## G. 容量与性能

### G1. 检索响应 P95 < 3 秒、入库可见性 < 10 秒、5 分钟上手——这三个指标的依据和接受度如何？

**背景**：需求文档（§2.3 / §6.2）给出了三个量化目标，但均未说明依据。这三个数值会成为验收标准，若定得过紧，技术实现成本显著增加；若定得过松，对用户体验没有保障。[来源：pm-writer 自审 §2.3]

**选项**：
- [ ] A. 确认：三个指标均已充分考量，作为验收硬性标准
- [ ] B. 检索 P95 可放宽到 5 秒（RAG 场景用户接受度更高）
- [ ] C. 入库可见性 < 10 秒 可放宽到 30 秒（轮询间隔调整即可满足）
- [ ] D. 5 分钟上手仅作为设计参考，不作为验收标准
- [ ] 其它（组合调整，请描述）

**影响**：P95 < 3 秒在 ES 后端相对容易达到，在 PG 后端（pgvector）对大空间可能需要额外的索引调优；若作为硬性验收标准，需要在测试计划中加入专项性能测试用例。

### G2. 单空间（或单公司）是否设置文件数量或存储容量上限？

- [ ] C. 设置硬上限：单公司存储总量上限，由平台运维配置
- [ ] 其它（请描述）

**影响**：若选 A，后端模型无需配额字段，但大规模使用后可能面临资源失控；若选 B 或 C，需要在 §4.7.4 中明确字段设计，以便后端预留配额字段——即便本期不出收费 UI，字段也要设好。

## H. 范围边界确认

### H1. 图片/扫描件 OCR 是否从"不在范围"变为"在范围"？

**背景**：输入材料（八）虽未明确把 OCR 列为"不做"，但 esapiens 原有实现默认走文本提取不走 OCR。此疑点与 B1 相关，单独列出是因为这是一个"是否扩大范围"的决策，而不只是实现方式问题。

**选项**：

- [ ] B. 决定纳入本期：图片走 OCR（与 B1 选 B 一致，需评估 OCR 服务选型和排期）
- [ ] 其它（请描述）

**影响**：若选 B，需要补充 §7"不在本次范围"中的说明，并在 §4.2.5 文件类型规则中更新 PNG/JPG/JPEG 的处理描述。

### H2. 跨语种检索（中文 query 检索英文资料）是否仍排除在范围之外？

**背景**：需求文档（§6.5 / §7 第 3 条）已明确"不做多语言翻译/跨语种检索"，但部分公司的内部资料可能是英文为主。确认一次可防止实现阶段被追加。

**选项**：
- [ ] A. 确认：本期不做跨语种检索，中文 query 只匹配中文资料，英文 query 只匹配英文资料
- [ ] B. 补充到本期（需要评估 embedding 模型的多语言能力及排期影响）
- [ ] 其它（请描述）

**影响**：若选 A，在空间创建时应考虑是否提示用户"建议将中英文资料放入不同空间以获得更好的检索效果"；若选 B，需要评估当前选定的 embedding 模型是否天然支持多语言（如 multilingual-e5 系列），成本变化较大。

### H3. 片段手动编辑是否仍排除在范围之外？

**背景**：需求文档（§4.4.5 规则 1 / §7 第 6 条）已明确本期不支持手动编辑片段。但在用户体验演示时，Dify 等竞品都支持此功能，用户可能在看到 MVP 后提出要求。提前确认一次可避免开发阶段的范围蔓延。

**选项**：
- [ ] A. 确认：本期不做片段手动编辑，用户只能查看切分结果
- [ ] B. 纳入本期（需要评估工作量，可能影响排期）
- [ ] 其它（请描述）

**影响**：若选 A，应在 UI 的片段预览页明确告知用户"如需调整切分效果，请修改拆分规则后重新入库"，引导用户正确使用参数调整功能。
